向量数据库用于解决海量高维向量的相似度匹配问题。在企业知识库、检索增强生成（RAG）以及多模态搜索场景中，文本和多媒体数据通常先通过嵌入模型转化为浮点数向量，再通过距离函数（如余弦相似度、内积或欧氏距离）找出最相关的候选内容。

为了让讨论有据可依，本文以一个具体的工程场景贯穿全程：
假设我们正在搭建一套多租户 SaaS 知识库系统，库内存放 **100 万条** 文档切片向量，维度为 **1536 维**（采用单精度浮点数 FP32）。每次检索不仅要在几毫秒内找出与用户提问语义最相近的 Top-10 结果，还必须携带业务约束——限定租户标识 `tenant_id = 42` 且文档状态 `status = 'published'`。

关于向量存储在系统架构中的分工边界，可参考 [/interview/rag-interview/vector-database.md](/interview/rag-interview/vector-database.md) 与 [/interview/rag-interview/vector-db-vs-traditional.md](/interview/rag-interview/vector-db-vs-traditional.md)。

## 1. 近似最近邻检索与主流索引算法

当向量维度为 $D$、库内向量总量为 $N$ 时，若执行线性暴力扫描（Flat 索引），单次查询需要进行 $N$ 次完整的向量距离计算，其浮点运算复杂度为 $O(N \cdot D)$。
在我们的贯穿案例中（$N = 10^6, D = 1536$），单次查询需要执行超过 15 亿次浮点乘加操作（约 30 亿次浮点运算）。在未加针对性量化或索引优化的常规多核 CPU 服务器上，全量暴力扫描延迟往往在数十至数百毫秒，难以稳定满足在线接口的低延迟与高并发要求。

为了在交互式延迟内返回结果，工程上普遍采用**近似最近邻（ANN, Approximate Nearest Neighbor）**检索。ANN 放弃了 100% 绝对精确的全局穷举保证，换取毫秒级的检索速度。主流索引算法主要分为三类：暴力扫描（Flat）、倒排量化（IVF-PQ 系列）与基于图的层次化可导航小世界网络（HNSW）。

![三种主流向量索引结构与内存权衡](/images/content-rebuild/ab5f31423b789a12/fig-1.png)

*图释：图中横向对比了 Flat、IVF-PQ 与 HNSW 三种索引的核心数据结构。左侧 Flat 展现了无损全扫描；中间 IVF-PQ 展示了 Voronoi 聚类与子空间量化编码；右侧 HNSW 展示了多层跳表式图网络结构。*

### 1.1 Flat 暴力扫描

Flat 并不构建额外的索引拓扑结构，原始向量以连续数组形式存放在内存或磁盘中。检索时，系统逐条计算查询向量与所有库内向量的距离或相似度，并利用容量为 $K$ 的优先队列（堆）维护当前最优的 Top-K 结果。
- **召回率**：理论上穷举全量数据，在不考虑浮点微小舍入误差和距离完全相同的平分截断时，召回率最高（Recall@K = 1.0）。
- **使用场景**：通常作为离线评测其他 ANN 索引精度的基准真值（Ground Truth），或用于数据量在万级以下的小规模轻量查询。

### 1.2 IVF-PQ（倒排文件乘积量化）

IVF-PQ 是一种通过“空间分区剪枝”与“数据有损压缩”降低计算量和内存占用的复合算法，分为两个核心部分：

1. **IVF 倒排聚类**：在建索引阶段，先通过 K-Means 算法在空间中训练出 $C$ 个聚类中心（Voronoi 单元）。查询时，系统先计算查询向量与这 $C$ 个中心的距离，仅选取最近的 $nprobe$ 个聚类中心所属的倒排链表进行搜索，跳过了其余不相关的区域。
2. **PQ 乘积量化**：将原始 $D$ 维向量切分成 $M$ 个低维子向量，每个子向量维度为 $D/M$。在每个子空间内训练 $K^* = 2^b$ 个局部质心（常见配置 $b=8$，即 256 个质心，刚好可用 1 个字节存储索引下标）。这样，一条原始 1536 维的浮点向量（占用 6144 字节）就被压缩成了 $M$ 个字节的量化码。
3. **不对称距离计算（ADC）**：查询向量不进行量化，保持 FP32 精度；系统预先计算查询向量各子段与码本中 256 个质心的距离表。遍历倒排桶中的向量时，只需通过查表累加即可逼近实际距离，大幅降低了 CPU 浮点运算量。

### 1.3 HNSW（层次化可导航小世界图）

HNSW（Hierarchical Navigable Small World）通过构建多层近邻图拓扑来实现高效路由：
- **分层结构**：底层（Layer 0）包含库内的全部数据节点，节点间建立高密度的近邻边；越往上层，节点以指数递减的概率稀疏分布，提供跨区域的长距离快速跳转通道（机制类似于跳表 Skip List）。
- **贪心游走**：检索从顶层的入口节点开始，计算当前节点邻居与查询向量的距离，贪心地移向更近的邻居；当局部收敛无法更近时，下降到下一层继续以此为起点搜索，直至 Layer 0。
- **参数控制**：构建时的邻居连接数 $M_{\text{links}}$ 决定了图的稠密度与建图耗时；查询时的动态候选队列长度 `efSearch` 则可在检索耗时与召回率之间按需微调。

### 1.4 索引内存开销估算模型

以贯穿案例（$N = 1,000,000$ 条，维度 $D = 1536$，数据类型为 32 位浮点数 FP32，每标量 4 字节）为例，不同索引方案的内存开销估算如下（注：此处为纯算法结构估算，未计入系统内存对齐与元数据额外开销）：

1. **Flat / 原始向量体积**：
   $$\text{Memory}_{\text{raw}} = N \times D \times 4 \text{ Bytes} = 10^6 \times 1536 \times 4 = 6,144,000,000 \text{ Bytes} \approx 5.72 \text{ GiB}$$
2. **HNSW 索引**：
   HNSW 需要在内存中保留原始向量（以便在 Layer 0 进行精确距离计算），同时维护图的邻居指针表。假设节点出度参数设为 $M_{\text{links}} = 16$，双向边指针使用 64 位整数（8 字节）：
   $$\text{Memory}_{\text{graph}} \approx N \times (2 \times M_{\text{links}}) \times 8 \text{ Bytes} = 10^6 \times 32 \times 8 = 256,000,000 \text{ Bytes} \approx 244 \text{ MiB} \ (256 \text{ MB})$$
   在实际工程实现（如 Faiss 或 Hnswlib）中，由于多层指针结构、内存对齐与动态扩容预留，图拓扑往往会额外占用原始向量大小的 $20\% \sim 50\%$ 内存。百万级 1536 维数据整体通常需要预留 $7 \sim 9\text{ GiB}$ 物理内存。
3. **IVF-PQ 索引**：
   若配置 $M = 64$（即切分为 64 段，每段 24 维），码本大小设为 256（1 字节），则每条向量被压缩为 64 字节：
   $$\text{Memory}_{\text{PQ}} = 10^6 \times 64 \text{ Bytes} = 64,000,000 \text{ Bytes} \approx 61 \text{ MiB} \ (64 \text{ MB})$$
   即便加上倒排表头和码本本身，整体常驻内存通常仅在百兆字节量级，但代价是量化引入了不可逆的精度损失。

## 2. 标量过滤与元数据检索陷阱

在实际生产中，纯粹的全库向量检索极少出现。查询往往必须附带业务过滤条件。例如在我们贯穿的客服场景中，查询请求要求携带 `tenant_id = 42 AND status = 'published'`。标量条件与向量索引的协同机制，直接决定了查询响应延迟与召回结果的有效性。

![标量与向量过滤三种策略的时序与失败分支](/images/content-rebuild/ab5f31423b789a12/fig-2.png)

*图释：流程图横向对比了后置过滤、前置过滤与单阶段迭代过滤的执行过程。图中用红叉标注了后置过滤的召回塌陷分支，以及前置过滤导致索引拓扑断裂的问题，最终指向通过单阶段动态路由维持图遍历与过滤匹配的最优路径。*

### 2.1 后置过滤（Post-filtering）与“召回塌陷”

后置过滤的逻辑是：先在全量向量索引中检索出 Top-$K'$ 个语义最近的向量，然后再对这批候选记录逐一核对标量条件，剔除不满足条件的数据，直到凑满最终的目标 $K$ 条。

这种方式最容易遭遇**召回塌陷（Recall Collapse）**：
设标量条件在全量数据中的满足率（选择率）为 $p$。系统若要获取 $K = 10$ 个有效结果，假设候选集分布与全量分布相似：
- 当 $p = 0.001$（例如某小租户的数据仅占全库千分之一）时，系统为了在过滤后留存 10 条结果，理论上需要初始召回的候选集规模：
  $$K' \approx \frac{K}{p} = \frac{10}{0.001} = 10,000$$
- 如果系统默认设置的候选池深度（如 `efSearch`）仅为 100，这 100 个在全库中距离最近的向量在经过 `tenant_id = 42` 过滤后，期望保留的记录数仅为 $100 \times 0.001 = 0.1$ 条。此时系统将直接返回空结果或仅有 1 条记录，即使数据库里明明存有该租户的完全匹配文档。

### 2.2 前置过滤（Pre-filtering）的工程困境

前置过滤的逻辑是：先利用传统索引（如 B-Tree、倒排索引或位图）筛选出满足条件的所有文档 ID 集合 $S_{\text{valid}}$，再将向量检索限制在 $S_{\text{valid}}$ 范围内。

这种方式在工程实现上面临两难抉择：
1. **暴力计算退化**：由于一般的图索引是针对全量节点构建的，筛选出特定 ID 集合后，传统系统往往无法直接利用现成的图结构，只能转而在 $S_{\text{valid}}$ 内部执行 Flat 暴力距离计算。如果筛选出来的文档集有数万条，单次查询延迟会直接上升至数百毫秒。
2. **子图连通性断裂**：如果强行在原图上搜索并直接将非 $S_{\text{valid}}$ 节点视为空白不可访问，原先构建好的连通路径会被大量切断。贪心搜索在遇到阻断节点时极易陷入局部最优，无法顺利漫游到真正的最近邻。

### 2.3 单阶段联合过滤与迭代扫描机制

为了兼顾检索召回率与图连通性，主流向量数据库在引擎层实现了标量条件与图遍历的联合求解，但具体实现路径因架构而异：

1. **标量位图与中继游走（如 Milvus）**：在执行向量搜索前，先利用标量索引生成满足过滤条件的布尔位图（Bitset）。在 HNSW 图遍历时，不满足标量条件的节点**依然可以作为图搜索的游走中继跳板**，算法可以沿着其外向边继续向近邻探索以保持拓扑连通，但仅有位图中标记有效的节点才被允许压入最终的 Top-K 候选池。当有效点过于稀疏时，引擎还支持动态扩大探索范围的迭代过滤。
2. **可过滤图索引与动态路由（如 Qdrant）**：将标量 Payload 索引与 HNSW 图拓扑直接协同。Qdrant 在查询前会评估标量过滤条件的选择率（Selectivity）：当满足条件的记录极少时，算法会自动切换为利用 Payload 索引构建的候选集路由；当选择率较高时，则在主图漫游过程中实时校验 Payload 过滤规则，避免拓扑断裂或盲目游走。
3. **迭代索引扫描（如 pgvector 0.8.0+）**：在 pgvector 0.8.0 之前，带 `WHERE` 条件的向量查询若走 HNSW 索引通常需要回表后过滤，遇到低选择率条件极易发生结果不足 $K$ 条的召回塌陷；0.8.0 版本引入了迭代索引扫描（`iterative scan`）机制，执行器在遍历 HNSW 或 IVFFlat 时，允许按需分批流式提取近邻并逐一检查元组标量条件，直到凑满目标数量或达到探索上限（如 `hnsw.iterative_scan` 参数），避免了在图搜索前强制构造全量位图。

## 3. 架构选型：专用向量数据库 vs 传统引擎扩展

在架构选型时，团队通常面临“引入独立的专用向量数据库”还是“沿用既有数据库的向量插件”的选择。

![专用向量存储存算分离与传统单机扩展架构对比](/images/content-rebuild/ab5f31423b789a12/fig-3.png)

*图释：图左展示了 Milvus 等专用数据库通过协调节点、消息日志队列、计算节点（Query/Index）与对象存储构成的存算分离架构；图右展示了 pgvector 在 PostgreSQL 单体引擎内共享缓冲区、WAL 与事务执行器的进程内插件架构。*

### 3.1 独立专用向量数据库

以 Milvus、Qdrant、Weaviate 为代表的系统，从底层存储布局、内存管理到查询调度均围绕高维向量检索进行设计：
- **存算分离架构**：以 Milvus 为例，写入的数据流经过消息队列（如 Kafka/Pulsar）持久化后分发为只读段（Segment）。查询节点（QueryNode）专门在内存中加载段并执行图搜索；索引节点（IndexNode）异步在离线资源中构建 HNSW 索引并保存至对象存储，两者在计算资源上物理解耦。
- **向量与元数据一体化设计**：Qdrant 针对包含 JSON Payload 的记录设计了专有存储格式，支持在图遍历过程中无缝评估复杂标量嵌套过滤。
- **适用边界**：向量规模达千万至数亿级别、有高并发批量写入要求、需多向量字段路由或极低 P99 查询延迟 SLA 的场景。

### 3.2 关系型与搜索引擎扩展

以 PostgreSQL pgvector 和 Elasticsearch Dense Vector 为代表，依托成熟的数据平台扩展高维向量能力：
- **PostgreSQL pgvector**：以插件机制运行在 Postgres 进程内部。业务数据与向量字段存放在同一张表中，天然具备完整的 ACID 事务能力，且可在一条 SQL 中直接完成业务表与向量检索的 `JOIN` 操作。Postgres 依赖共享缓冲区（`shared_buffers`）与操作系统页缓存（OS Page Cache）协同缓存索引页面；当工作集尺寸显著超出可用物理内存并触发随机磁盘读时，检索延迟会出现较明显波动。
- **Elasticsearch / OpenSearch**：依托底层 Lucene 的 HNSW 实现，与原生的 BM25 文本倒排索引天然共存。优势在于多模态混合查询无需跨系统同步，且 Lucene 向量数据主要通过堆外内存与文件内存映射（`mmap`）借助操作系统页缓存访问；但 Lucene 的分段合并（Segment Merge）在合并大段时需要构建新图索引，会产生不可忽视的后台 CPU 与 I/O 负载。

| 评估维度 | 专用向量数据库（如 Milvus / Qdrant） | 关系型插件（如 PostgreSQL pgvector） | 全文搜索引擎扩展（如 Elasticsearch） |
| :--- | :--- | :--- | :--- |
| **主要索引类型** | 依据引擎而定：Qdrant 主推 HNSW（含 SQ/PQ）；Milvus 支持 HNSW、IVF 系列、SCaNN、DiskANN 等 | HNSW, IVFFlat | HNSW（基于 Lucene 堆外文件实现） |
| **一致性模型** | 多支持可调一致性级别（如 Milvus 支持强一致、Bounded Staleness 到最终一致；Qdrant 基于 Raft 支持多副本读写配置） | 严格 ACID 事务一致性 | 近实时检索（基于 Lucene Flush/Refresh 机制） |
| **内存管理** | 堆外内存管理，配合定向 mmap 或自研缓存池 | 共享缓冲区（shared_buffers）配合操作系统页缓存 | 向量与倒排索引通过 mmap 依托操作系统页缓存，JVM 堆承载协调与状态 |
| **关联查询能力** | 较弱，跨业务实体关联通常需应用层通过 ID 关联 | 完善，原生支持 SQL 多表 JOIN、视图与窗口函数 | 支持父子文档与嵌套对象，不支持关系型 JOIN |
| **运维维护成本** | 依形态而定（轻量单机二进制文件运维简单；分布式存算分离版需维护多组件） | 极低（直接复用成熟的关系数据库运维生态） | 中等（复用现有的 ES/Lucene 集群运维栈） |

## 4. 混合检索与结果评分融合机制

单纯依赖稠密向量（Dense Vector）的语义相似度，在面对特定实体缩写、零件编号（如 `A12-X900`）、内部错误码等强精确字符匹配场景时容易发生偏差。因此，工程实践中普遍采用“稠密语义检索 + 稀疏关键词检索（如 BM25）”的混合检索管道。关于稀疏与稠密特征差异的对比，可参考 [/fundamentals/embedding/sparse-dense-vectors.md](/fundamentals/embedding/sparse-dense-vectors.md)。

![混合检索双路召回与 RRF 融合计算流水线](/images/content-rebuild/ab5f31423b789a12/fig-4.png)

*图释：数据流水线展现了一个包含自然语言查询的请求，分别经过稠密嵌入模型与 BM25/稀疏编码器，兵分两路进入向量数据库和全文索引，各自输出带排名的候选列表，最后在 RRF 模块中应用倒数加权公式合并并截断为最终候选。*

在混合检索中，稠密向量给出的余弦相似度（通常处于 $[-1, 1]$ 或归一化到 $[0, 1]$）与 BM25 检索得分（受词频和语料分布影响，无固定上界且在未截断的经典 IDF 变体中可能存在负值）在量纲和取值范围上截然不同。若不经校准直接将原始分值相加，数值偏大的一方将显著主导最终排序，破坏多路召回的平衡。主流方案通过以下两种方式进行分值融合：

### 4.1 倒数排名融合（RRF, Reciprocal Rank Fusion）

RRF 不依赖检索返回的绝对分值，而是直接依据各通道返回结果的**相对排名（Rank）**进行综合打分。对于文档 $d$ 在各检索通路 $m \in M$ 中的排位 $r_m(d)$（从 1 开始递增），其综合评分公式为：

$$RRF\_Score(d) = \sum_{m \in M} \frac{1}{k + r_m(d)}$$

其中 $k$ 为平滑常数（学术界与工业界常规实践一般取 $k = 60$，用于避免排在第 1 名的文档产生过大的分值垄断）。

**逐步计算算例**：
假设待融合系统包含两路召回（稠密向量路 $m_1$，BM25 文本路 $m_2$），取 $k = 60$：
- **文档 A**：在稠密路排第 1 名（$r_1=1$），在 BM25 路排第 4 名（$r_2=4$）：
  $$RRF(A) = \frac{1}{60 + 1} + \frac{1}{60 + 4} = \frac{1}{61} + \frac{1}{64} \approx 0.01639 + 0.01562 = 0.03201$$
- **文档 B**：在稠密路排第 10 名（$r_1=10$），但精准命中了关键词在 BM25 路排第 1 名（$r_2=1$）：
  $$RRF(B) = \frac{1}{60 + 10} + \frac{1}{60 + 1} = \frac{1}{70} + \frac{1}{61} \approx 0.01428 + 0.01639 = 0.03067$$

RRF 无需预先假定分数分布，对异常极端值具有较强的鲁棒性，是多路召回合并中最常用的确定性算法。

### 4.2 线性加权归一化融合（Weighted Sum Fusion）

当业务明确需要偏向某一模型时，可先在批次内对各路分值执行 Min-Max 归一化，再按权重系数相加：

$$S_{\text{norm}}(d) = \begin{cases} 1.0, & \text{若 } S_{\text{max}} = S_{\text{min}} \\ \frac{S(d) - S_{\text{min}}}{S_{\text{max}} - S_{\text{min}}}, & \text{若 } S_{\text{max}} > S_{\text{min}} \end{cases}, \quad Score_{\text{final}}(d) = \alpha S_{\text{norm, dense}}(d) + (1 - \alpha) S_{\text{norm, sparse}}(d)$$

需要注意的是，当单路召回所有候选得分完全相同时需避免除以零错误；此外 Min-Max 极易受到批次内长尾离群值（Outlier）的扰动，实际应用中建议先对得分进行截断过滤或采用分位数归一化。

## 5. 多租户数据隔离与增量维护权衡

在企业落地场景中，多个租户通常共用一套底层存储基础设施。多租户架构不仅涉及数据安全边界，更直接决定了集群的内存利用效率。关于向量写入与更新细节，可参考 [/interview/rag-interview/vector-db-incremental.md](/interview/rag-interview/vector-db-incremental.md)。

![三种多租户隔离架构的资源开销与隔离级别矩阵](/images/content-rebuild/ab5f31423b789a12/fig-5.png)

*图释：图中矩阵划分了“独立实例”、“独立集合（Collection）”与“元数据标量过滤”三种隔离模式。坐标轴显示了从硬物理隔离到软逻辑隔离的资源占用递减与隔离安全性权衡。*

### 5.1 三种多租户隔离模式

1. **物理实例隔离（Instance-level）**：每个租户独占独立的数据库进程或容器。能够有效杜绝同进程内的内存越界与线程干扰，但计算与常驻内存成本随租户数量线性上升；且其安全性仍依赖于下层宿主机与网络访问控制策略。
2. **集合/表级隔离（Collection/Table-level）**：多租户共享一个集群实例，但每个租户对应一个独立的 Collection 或表。适用于租户数量有限且各租户数据量分布相对均匀的场景。若集合数量过多，各引擎维护独立图索引、文件句柄与元数据缓存的底噪开销会显著累积，需结合具体引擎的集合上限评估。
3. **标量逻辑分区（Payload / Metadata Partitioning）**：所有租户共享同一个大型 Collection，文档附带 `tenant_id` 属性。查询时通过单阶段联合过滤限定检索范围。该方案资源利用率最高，数据安全通常需依赖应用层注入过滤参数或数据库原生访问控制策略（如 PostgreSQL 的行级安全性 RLS）进行防越权约束。

### 5.2 增量更新与软删除机制

由于 HNSW 图索引的节点之间存在紧密的互联指针，直接在图内部物理删除一个节点，会导致局部大量连通边断开，实时修复代价极高。因此主流引擎普遍采用**软删除（Soft Delete / Tombstone）**机制：
- **删除阶段**：系统在内存位图中将该文档 ID 标记为已删除，图拓扑保持不变。后续遍历遇到该节点时直接跳过，不计入检索结果。
- **整理阶段（Compaction / Segment Merge）**：后台异步执行垃圾回收或段合并时，读取旧段中所有未被标记删除的有效数据，一次性构建全新的紧凑图结构，随后原子切换读指针并释放旧段空间。

这意味着高频写入与频繁更新会持续占用后台 CPU 资源，并造成短期的内存膨胀。业务设计时应尽量采用批量导入机制，避免逐条实时更新。

## 6. 技术选型路径与工程决策依据

向量数据库选型应当从业务的数据规模、写入并发特征以及团队已有技术储备出发，避免脱离场景盲目引入分布式组件。

![向量数据库选型与工程权衡决策树](/images/content-rebuild/ab5f31423b789a12/fig-6.png)

*图释：决策树从“现有技术栈是否有已验证的关系/检索底座”开始分支，依次经过“业务联查与事务强依赖”、“多路混合检索需求”与“大规模存算分离弹性扩展”，最终将技术选型导向 pgvector、Elasticsearch、单机 Qdrant 或分布式 Milvus。*

### 6.1 决策对照表

| 业务现状与需求约束 | 建议选型方案 | 决策依据与工程考量 |
| :--- | :--- | :--- |
| **已有 PostgreSQL 技术栈，依赖关系表强事务与复杂 JOIN，中轻量向量规模（索引可充分常驻内存）** | **PostgreSQL + pgvector** | 无需引入新组件；向量与业务表同事务提交；当索引体积可由 shared_buffers 与系统页缓存充分覆盖时，延迟平稳且运维成本极低。 |
| **已有成熟 Elasticsearch/OpenSearch，侧重文本倒排与语义多路召回融合** | **ES / OpenSearch Dense Vector** | 直接复用现有检索集群；原生支持 BM25 与稠密向量联合召回并支持段管理；规避跨数据系统双写与同步一致性延迟。 |
| **元数据具备复杂 JSON 结构，要求高效联合过滤与低内存占用，适合单机多核或轻量集群部署** | **Qdrant (单机版 / 集群版)** | Payload 存储与过滤检索深度协同；动态选择率路由降低拓扑断裂风险；二进制交付且资源底噪相对紧凑。 |
| **大规模向量池、高并发写入吞吐，需要计算/查询节点弹性独立扩缩容** | **Milvus / 云托管服务** | 存算分离架构解耦查询与离线建索；段机制与消息队列可承接大吞吐写入，支持多类型向量索引横向扩展。 |
| **本地应用分发、轻量原型验证、无独立数据库守护进程要求** | **LanceDB / Chroma** | 嵌入式或轻量运行；开箱即用无需单独运维网络中间件，便于快速原型验证或端侧桌面部署。 |

在完整的端到端检索增强管线中，向量存储仅承担底层索引与检索职责，前序的文本分块、嵌入模型选择与后置重排（Rerank）机制，请参考 [/resources/rag-framework.md](/resources/rag-framework.md) 及 [/llm-100/rag/vector-db-in-rag.md](/llm-100/rag/vector-db-in-rag.md)。
