在开发大语言模型应用时，开发者常在开源项目和云端服务之间难以取舍。关注度高的项目不一定适合生产环境，开源协议、部署依赖、网络延迟和维护人力都会影响实际交付。为了帮助开发者按需选型，本专栏把常用技术资源划分为四个层级，并提供可落地的评估方法。

我们以一个具体场景贯穿全文：假设团队要为公司内部知识库和在线客服搭建一个问答助手。系统需要检索产品手册、调用订单接口，并保证数据在受控范围内运行。面对这一目标，团队必须依次决定：阅读哪些规范、采购云端 API 还是自建模型、向量数据存在哪里，以及如何安全调用外部系统。

## 资源库定位与选型原则

技术选型不是追求功能最全的工具，而是在满足业务需求的前提下控制维护成本。建议遵循以下三项原则：

1. **官方规范与源码优先**：以官方文档、标准化 RFC 和经测试的源码为准，避免依赖未注明版本和运行环境的二次解读。
2. **区分原型演示与生产可用**：单次演示（Demo）运行成功，不等于具备并发控制、重试幂等、超时隔离和监控追踪能力。选型时需要审查异常处理机制。
3. **业务逻辑与模型实现解耦**：业务编排代码应当通过统一接口调用模型，避免将厂商专有字段或私有 SDK 硬编码到业务流中，保留更换底层供应方的空间。

## 知识输入层：理论源头与系统工程

构建客服助手时，如果直接把长篇产品手册整篇塞给大模型，容易遇到上下文窗口限制或推理成本激增。要解决这类问题，需要理解注意力机制的计算开销与检索增强生成（RAG）的基本原理。

* [论文资源](/resources/papers.md)：收录注意力机制、模型对齐、检索增强生成（RAG）和思维链（CoT）等领域的原始文献，帮助理解算法的假设条件与局限。
* [技术书籍](/resources/tech-books.md)：涵盖深度学习基础、自然语言处理系统实现与分布式计算，提供更成体系的工程背景知识。

![知识理论层向工程实现层的映射与依赖关系](/images/content-rebuild/056d3c1d53b6a7de/fig-1.png)

学术论文验证的是算法在特定基准数据集上的可行性，而工程落地需要进一步考虑显存占用、吞吐量限制与网络开销。理论资料用于指导技术边界的判断，而不是直接照搬实验配置。

## 模型与计算层：基础设施与推理供给

客服助手的问答核心需要大模型提供推理能力。团队通常面临两类选择：直接调用第三方商业托管 API，或者在自备算力上部署开源模型。

* [AI 开源项目](/resources/ai-opensource.md)：收录高性能推理引擎（如 vLLM）、轻量化部署运行时以及模型接入网关。
* [模型平台](/resources/model-platform.md)：汇总开源模型权重托管社区、本地运行测试工具与镜像仓库。
* [API 平台](/resources/api-platform.md)：整理主流商用大模型接口、中转网关及协议规范。

在做出选择前，应对比两者的典型边界：

| 评估维度 | 商业托管 API | 自建模型托管集群 |
| :--- | :--- | :--- |
| **资源启动** | 无需购买物理 GPU，注册获取密钥即可调用 | 需要采购或租赁 GPU 实例，需预先下载模型权重与配置运行环境 |
| **网络与延迟** | 请求经由公网传输，排队时长受多租户负载影响 | 部署在私有网络内部，延迟主要取决于内网带宽与当前实例并发处理情况 |
| **数据流向** | 数据通过网络发送至第三方服务器，受服务协议与数据保护条款约束 | 数据留在私有 VPC 或本地机房，网络拓扑完全由团队自管 |
| **运维工作量** | 无需维护底层驱动与显卡硬件，需被动适配接口版本更替 | 需自行维护驱动兼容、显存分配、多实例负载均衡与节点故障替换 |

![商业 API 与自建托管集群的选型决策树](/images/content-rebuild/056d3c1d53b6a7de/fig-2.png)

如果客服场景包含严格的数据不出域合规要求，且团队具备 Linux 运维和 GPU 集群调度经验，自建部署更为安全可控；如果业务处于验证阶段，调用成熟商业 API 可以更快验证产品逻辑，节省前期硬件投入。

## 框架与组件层：数据存储与业务编排

在客服助手把文档片段传给模型之前，系统需要先进行文档切分、文本嵌入（Embedding）与向量检索；在生成回答后，还需要按照业务逻辑执行下一步操作。应用架构的详细设计可进一步参考 [AI 工程架构](/architecture/README.md)。

* [向量数据库](/resources/vector-db.md)：收录专用向量数据库（如 Qdrant、Milvus）与关系型数据库扩展（如 PostgreSQL 的 pgvector 插件）。
* [RAG 框架](/resources/rag-framework.md)：提供文档解析、文本分块、嵌入检索与结果重排（Rerank）管道的开发套件。
* [Agent 框架](/resources/agent-framework.md)：提供状态机维护、工具调用循环与人工介入确认（Human-in-the-Loop）的编排工具。

### 算例参考：向量检索存储选型评估（相同工作量假设）

假设客服系统目前包含 200 万条切分后的文档片段，向量维度为 768 维（float32 类型），日均检索请求 50 万次。团队已有稳定的 PostgreSQL 数据库基础设施。两种选型对比如下：

* **方案 A：引入独立专用向量数据库集群**
  * **架构调整**：需要新增至少两个独立节点做高可用部署，业务服务需要维护与主数据库、向量数据库的双写一致性逻辑。
  * **资源开销**：承担新增节点的计算、内存与存储成本，增加跨组件网络调用的延迟开销。
  * **适用场景**：向量量级上升到数千万以上，或单日查询吞吐接近现有主库上限时。
* **方案 B：复用现有 PostgreSQL 数据库并安装 pgvector 插件**
  * **架构调整**：复用现有的连接池、备份容灾策略、只读从库和身份鉴权，无需新增独立存储组件。
  * **资源开销**：向量索引（如 HNSW）需要占用现有主库或从库的共享内存与存储空间，高并发检索可能争抢主库 CPU。
  * **适用场景**：数据规模在数百万以内，团队更希望减少组件依赖、降低运维复杂度。

**决策边界**：在数据量和并发未达到瓶颈前，优先复用现有关系型数据库扩展，降低架构复杂度；当向量吞吐显著影响主业务交易时，再考虑拆分至独立专用向量集群。

## 协议与生产力层：上下文连接与辅助开发

客服助手往往不能只停留在文本答复，还需要查阅订单、查询物流。这需要将模型与外部系统连接。同时，开发者自身也可以使用代码生成工具加速这一流程。

* [MCP Server](/resources/mcp-server.md)：介绍遵循模型上下文协议（Model Context Protocol）的服务器实现，用于标准化暴露工具接口和上下文数据源。
* [AI 编程工具](/resources/ai-coding-tools.md)：整理终端辅助工具、IDE 代码补全扩展及架构分析插件。
* [AI 工具](/resources/ai-tools.md)：收录面向文档转换、音频转录及测试数据生成的通用工具。

在设计外部系统交互时，注意区分标准通信协议（如 MCP）、纯可执行脚本与带有自然语言操作说明的 [Agent Skills](/frontier/agent-skills/README.md)。工具函数本身也可包含业务逻辑、状态变更或复杂外部交互；带有操作指南的 Skill 则用于指导宿主和模型理解任务边界。无论采用哪种形式，涉及状态变更与外部调用的操作都需要显式设置权限范围与参数校验规则。

## 技术选型评估清单与实验验证

在正式将开源库或商业服务接入生产环境前，建议执行以下四项最小验证实验：

```python
# 伪代码：第三方依赖准入评估逻辑示意
def evaluate_dependency(candidate_package):
    # 1. 许可证审查：排查是否有不兼容的开源协议限制商用代码闭源
    license_ok = candidate_package.check_license_compatibility(allowed=["MIT", "Apache-2.0", "BSD"])
    if not license_ok:
        return "许可证不合规，终止评估"
    
    # 2. 状态隔离检查：确认编排层是否将用户状态耦合在进程内存中
    is_stateless = candidate_package.supports_external_session_store()
    if not is_stateless:
        return "内部状态未隔离，无法水平扩展"
    
    # 3. 可观测性追踪：检查是否提供结构化日志或 OpenTelemetry 标准埋点
    has_tracing = candidate_package.supports_opentelemetry()
    if not has_tracing:
        return "缺乏标准追踪接口，生产排查困难"
    
    # 4. 超时与降级验证：模拟下游服务延迟，验证是否支持超时熔断
    fallback_ok = candidate_package.test_timeout_handling(timeout_ms=500)
    if not fallback_ok:
        return "下游异常未正确捕获，存在级联雪崩风险"
    
    return "准入验证通过"
```

![技术选型四步验证与准入流水线](/images/content-rebuild/056d3c1d53b6a7de/fig-3.png)

终审清单概括为三项硬性指标：
1. **许可证（License）**：确认允许商业使用，且不要求分发时强制公开业务专有源码。
2. **可观测性（Observability）**：框架应能抛出请求级耗时、Token 统计与错误码，便于接入已有监控平台。
3. **降级保障（Fallback）**：当模型服务或向量存储超时不可用时，系统应有兜底方案（例如直接返回预设提示或转入人工队列），防止系统级联崩溃。
