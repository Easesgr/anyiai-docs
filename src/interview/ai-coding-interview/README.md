面试中讨论 AI 编程系统时，面试官通常不是在考察某一个大模型的接口参数，而是在考察开发者如何解决实际的代码工程问题：在几百毫秒的时延预算下如何组织光标上下文？多文件改动时如何避免模型胡乱修改？终端命令执行如何防止把仓库误删？

为了让讨论具体可感，我们用一个贯穿全篇的开发任务来说明各项机制：

> **贯穿示例**：在电商系统的 `discount.py` 中，我们需要为 `calculate_discount(order, user)` 函数增加一条规则——“VIP 用户的每笔订单折扣封顶 50 元”，并确保 `tests/test_discount.py` 里的单元测试全部通过。

## 核心分野：行内代码补全与自主代码 Agent

面试时被问到“GitHub Copilot 和 Cursor Composer 架构有什么区别”时，可以先给出结论：**行内补全是低时延、单点触发的文本生成任务；代码 Agent 是多步骤、带状态与工具交互的端到端任务。**

![代码补全与自主 Agent 的系统工程维度对比](/images/content-rebuild/f743434a0ad7fd94/fig-1.png)

结合贯穿示例，两者的执行逻辑完全不同：

1. **行内补全（Inline Completion）**：
   * **发生场景**：开发者打开 `discount.py`，在光标处敲下 `if user.is_vip:` 后停顿。
   * **系统目标**：在 100~300 毫秒内预测光标后应该出现的代码（如 `return min(discount, 50.0)`）。
   * **输入范围**：主要提取光标前的代码（Prefix）和光标后的代码（Suffix），辅以当前打开的几个标签页代码片段。
   * **输出与控制**：仅返回一段建议文本，由用户按下 `Tab` 键确认是否采纳，系统本身不运行测试，也不修改其他文件。
2. **自主代码 Agent（Coding Agent）**：
   * **发生场景**：开发者在输入框中提出需求：“给 VIP 折扣增加 50 元封顶，并跑通单测”。
   * **系统目标**：跨文件定位逻辑、自动修改文件、调用命令行执行测试、遇到失败时自动读取报错并修正。
   * **输入范围**：整个项目目录树、相关文件的符号定义、测试运行结果等。
   * **输出与控制**：通过工具调用（Tool Calls）发起文件检索、读写补丁和终端执行，直到单测通过或达到步数上限。

## 五大高频面试考点解析

### 考点 1：FIM 机制如何让自回归模型看到光标后的代码？

* **简洁口述回答**：标准语言模型按从左到右的顺序预测下一个 Token，如果只输入光标上文，模型就不知道光标后已经写了什么闭合括号或变量。FIM 在训练阶段通过特殊分隔符重组文本，将一段代码切成 Prefix、Suffix 和 Middle，重排为 `<PRE> Prefix <SUF> Suffix <MID> Middle`。这样模型仍然执行常规的自回归因果生成，但在输出 Middle 时，自注意力已经可以同时计算 Prefix 和 Suffix 对应的键值（KV）。
* **常见错误**：误以为 FIM 需要把模型换成 BERT 那样的双向注意力编码器，或者误以为推理阶段打破了因果自注意力掩码。

### 考点 2：为什么不能把整个代码仓库直接拼进上下文？

* **简洁口述回答**：直接拼装整个仓库会带来三个问题：一是 Token 消耗巨大且导致首字时延极长；二是长上下文下模型对分散在中间细节的注意力召回率下降；三是无关代码会引入大量同名变量或混淆逻辑。实际系统通常使用两阶段检索：先用 Ripgrep 快速过滤文件名与文本关键词，再用 AST 抽取类与函数签名，仅当需要查看具体实现时才加载函数体。
* **常见错误**：以为长窗口模型支持 100 万 Token 后，代码检索技术就失去了工程价值。

### 考点 3：全文件重写、Unified Diff 与块匹配替换（Search/Replace）如何选择？

* **简洁口述回答**：在修改 `discount.py` 时有三种落盘方案：
  1. **全文件重写**：让模型输出修改后的整份文件。实现最简单，但如果文件有 2000 行，模型生成极慢，且极其容易在未修改区域漏掉原有代码。
  2. **Unified Diff**：让模型输出类似 `git diff` 带有 `@@ -10,6 +10,7 @@` 的补丁。输出 Token 极少，但大模型对严格的行号计算能力不可靠，常常因为行号偏移 1~2 行导致 `patch` 命令报错。
  3. **块匹配替换（Search/Replace）**：让模型输出“待替换的代码块”和“新代码块”。模型无需计算绝对行号，程序通过精确字符串匹配来执行修改；若有重复代码段，可通过多保留两行上下文标记来唯一确定位置。这是目前主流代码 Agent 的首选折中方案。
* **常见错误**：认为 Unified Diff 效率最高就一定是最优解，忽略了模型在字符行号对齐上的脆弱性。

### 考点 4：如何防止 Agent 在终端执行破坏性操作？

* **简洁口述回答**：靠提示词约束“请不要运行 rm -rf”无法作为安全边界。工程防御必须依赖宿主程序与运行环境：
  1. **命令静态过滤与白名单**：在执行前解析命令抽象语法，拦截 `rm -rf`、格式化磁盘、修改环境变量等高危指令。
  2. **权限与环境沙箱**：将 Bash 工具限制在无 root 权限的隔离容器（如轻量 Docker 或微虚机）中运行，工作目录严格限制在项目目录内。
  3. **输出流硬截断**：终端输出限制最大行数（如 100 行），防止单次 `cat` 大日志撑爆上下文窗口。
  4. **版本快照防护**：在执行 Agent 任务前自动打 Git 临时快照（Stash 或 Temporary Commit），出错时允许一键无损回滚。
* **常见错误**：声称只需要写好 System Prompt 就能彻底杜绝危险命令。

### 考点 5：单测报错后，Agent 如何实现纠错？死循环怎么停机？

* **简洁口述回答**：当 `pytest tests/test_discount.py` 失败时，程序将退出码、标准错误（Stderr）以及 Traceback 截取为工具返回内容输入模型。模型基于报错堆栈调整代码。为避免“改代码 -> 报错 -> 瞎猜修补 -> 产生新报错”的死循环，系统必须设置硬性护栏：
  1. **步数限制**：单任务设置最大执行轮数（如最多 8 轮循环）。
  2. **重复状态检测**：比对每次修改后的 Diff，若连续两轮产生完全相同的代码或相同的报错信息，立刻中断执行并提示用户介入。
  3. **测试回滚机制**：如果某一步修改导致原本通过的单测大面积变红，主动执行 `git checkout` 撤销该步改动，重新制定修改路线。
* **常见错误**：向面试官声称 Agent 具备“全自主思考自愈”，可以一直自动重试直到代码写对。

## 技术面试口述模板：四步应答法

面对“如果让你来设计一个仓库级代码修改 Agent，你会怎么做”这类开放架构题，可以使用四步框架作答，保证逻辑清晰且细节可核验：

![技术面试四步口述应答模型流程图](/images/content-rebuild/f743434a0ad7fd94/fig-3.png)

### 四步法演练：以“修改 VIP 折扣规则并跑通单测”为例

1. **结论先行**：给出明确的技术选型。“针对这个需求，我会设计一个基于‘符号检索 + Search/Replace 块编辑 + 沙箱运行测试’的五阶段任务流，而不是直接让模型全文件重写。”
2. **机制因果**：说明每一步的具体动作与执行链路。“第一步，通过 Ripgrep 搜索 `calculate_discount` 找到定义文件；第二步，用 AST 提取该函数的局部上下文；第三步，让模型生成局部替换块应用修改；第四步，在隔离环境中运行 `pytest`；第五步，解析测试输出确认完成。”
3. **工程权衡**：说明为什么选 A 不选 B。“在应用修改时，我选择块替换而不是全量重写，因为 `discount.py` 可能包含大量其他业务逻辑，全量输出会增加几十秒等待时间，且容易漏掉其他函数；而不用 Unified Diff 是为了规避行号计算偏差导致的补丁应用失败。”
4. **边界防御**：说明异常与兜底。“如果模型修改后测试抛出 `AssertionError`，将错误堆栈回传给模型再次尝试，但上限设为 3 次重试；如果 3 次未过，回滚到最初的 Git Commit，并将错误报告呈现给人工排查，防止代码库被污染。”

## 专栏复习自测清单

在阅读后续各讲前，可以用以下问题自测当前的准备程度：

- [ ] **FIM 格式**：能否在白板上写出 FIM 训练重组格式，并解释因果掩码如何支撑 Middle 预测？
- [ ] **代码检索**：能否说出仅靠向量检索（Embedding）定位代码符号调用链的缺陷？
- [ ] **代码写入**：能否讲清 Search/Replace 块在处理文件内多处重复代码时的消歧规则？
- [ ] **沙箱隔离**：能否列出至少 3 项防止模型生成破坏性 Shell 脚本的防御机制？
- [ ] **循环终止**：能否设计一套机制，防止代码 Agent 在测试报错时无限循环耗尽 Token？
