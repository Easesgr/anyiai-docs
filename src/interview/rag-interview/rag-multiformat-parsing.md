在检索增强生成（RAG）系统中，文档解析是整个流水线的数据入口。如果文档在解析阶段出现了阅读顺序颠倒、表格串行或页眉噪声残留，后序的切块（Chunking）、向量化（Embedding）与召回重排（Rerank）都会受到直接污染。

以一份典型的企业《2024季度技术规划与预算报告》为例：
* 技术人员提交的 **Markdown** 草稿逻辑清晰，但常有人为书写的跳级标题；
* 财务部门流转的 **Word（.docx）** 审批稿包含大量多级嵌套编号和跨行跨列的预算审批表；
* 最终归档的 **PDF** 研报则是双栏排版，页眉带着公司水印，末尾还附带了发票扫描件。

面对这三种格式，文档处理流水线如何将它们还原为统一、结构完整且没有格式噪声的结构化内容？本篇承接 [/interview/rag-interview/rag-document-pipeline.md](/interview/rag-interview/rag-document-pipeline.md) 的整体设计，深入拆解异构文档解析中的核心问题与处理方案。

## 1. 核心口述答案：格式抽取的核心痛点与技术路线选型

在面试中被问及“如何统一处理 PDF、Word 与 Markdown 文档”时，可以按以下脉络简明作答：

> **面试口述核心结论**：
> 企业文档解析的关键难点在于**底层物理存储格式与人类阅读逻辑结构的不一致**。解析任务的目标，是把不同格式还原为一棵包含章节层级（大纲树）、段落、表格与列表的**文档语义对象树**：
> 1. **Markdown**：自带显式逻辑结构。利用 CommonMark 语法树解析器（如 `markdown-it-py`）提取标题层级（H1–H6），在切块时维护一个标题栈，为正文段落注入祖先面包屑路径（如 `一级标题 > 二级标题`），补足独立上下文。
> 2. **Word（.docx）**：属于基于 XML 的半结构化压缩包。通过解压读取 `word/document.xml` 与 `word/styles.xml`，读取段落样式映射大纲级别，并根据 `numbering.xml` 还原多级编号，通过构建虚拟二维网格平铺合并单元格。
> 3. **PDF**：底层是面向打印呈现的无结构绘图指令流，没有天然的“段落”或“表格”标记。工程上采用**分级路由策略**：纯文字排版使用 `PyMuPDF` 或 `pdfminer.six` 提取字符坐标流，结合 XY-Cut 算法重排双栏阅读顺序；复杂版面或多表格文档采用版面分析工具（如 Docling、Marker 等）；对于模糊扫描件与图片，则路由至 OCR（光学字符识别）识别流水线。

## 2. PDF 双栏排版、跨页断句与页眉页脚噪音过滤

PDF（Portable Document Format）最初是为了保证在不同打印机和屏幕上呈现相同视觉效果而设计的。它的文件主体由一系列 PostScript 绘图指令构成。例如一段文字在 PDF 底层其实是定位坐标与字形编码：

```text
BT
/F1 12.00 Tf
72.00 712.00 Td
(Retrieval-Augmented Generation) Tj
ET
```

PDF 数据流中不包含“这一行属于正文段落”或“这行文字处于左栏”的元数据。直接按文件物理流读取字符，容易引发以下三类典型问题。

### 双栏排版的“Z 字形穿插”与 XY-Cut 切分

基础抽取工具如果仅按文件中的对象顺序提取字符，或简单从上到下按纵轴（Y 轴）全局扫描，遇到双栏学术论文或研报时，会把左栏第一行与右栏第一行拼成同一行，导致整段语义交织错乱（称为 Z 字形穿插）。

恢复正确单栏流的常见确定性算法是 **XY-Cut（递归投影切分）**：
1. **边界框统计**：获取页面内所有字符或词块的包围盒（Bounding Box：`[x0, y0, x1, y1]`）。
2. **X 轴投影与栏间隙（Gutter）查找**：将所有文字块向水平 X 轴投影，统计投影直方图。如果中央区域存在一条贯穿上下的空白带（即投影直方图计数为 0 或低于极低阈值），说明该页存在分栏间隙。
3. **区域切分与独立排序**：沿空白带将页面划分为左、右子包围盒，然后在各个子区域内，分别按 Y 轴（自上而下）和 X 轴（自左而右）将文字排序合并。

![PDF 双栏排版 Z 字穿插与 XY-Cut 切分机制](/images/content-rebuild/62f2ed030b643948/fig-2.png)

### 跨页截断与连字符合并

长文档在换页时，段落常常被切断，英文专业词汇可能在行尾出现连字符（如 `infor-` 跨页接 `mation`）。
* **连字符修复**：如果前一页末尾非空白字符为 `-`，且后一页首字符为小写字母，则剥离连字符并拼接两个片段；
* **段落未完结判定**：检测前一页尾部是否包含句末终止符（如英文句点 `.`、问号 `?` 或中文句号 `。`）。若无终止符，且后一页开头不是独立标题或大写句首，在构建段落对象时保持段落合并状态，避免在换页处强行截断语义。

### 页眉、页脚与版权声明去噪

页眉、页脚在每页重复出现（如“某某证券研究报告·第 3 页”）。如果不做过滤，切分出来的块就会携带大量重复文本，稀释向量相似度，甚至让检索模型误将版权文字当成正文关联。

过滤机制通常由两道检查组成：

$$[y_{\min}(p), y_{\max}(p)] \subseteq [0, \alpha H_{\text{page}}] \cup [(1 - \beta) H_{\text{page}}, H_{\text{page}}]$$

1. **空间坐标比例过滤**：根据页面总高度 $H_{\text{page}}$（以页面左上角为原点），将顶部与底部的相对高度区间（典型取 $\alpha, \beta \in [0.05, 0.08]$）划为页眉页脚候选区。若文本块垂直范围落在该区域内，则触发进一步校验，避免误删正文。
2. **跨页文本频次比对**：在候选区提取文字，计算跨页编辑距离。如果某行文本在全书超过 70% 的页面中相似出现，或内容由纯页码数字构成，则在生成逻辑段落前直接剔除。

## 3. Word 文档的 OpenXML 结构解析与大纲还原

现代 Word 文档（`.docx`）表面是一个单独文件，实际上是符合 OpenXML 规范的 ZIP 压缩包。将其解压后，主要内容与格式配置分布在特定 XML 文件中：

```text
example.docx (ZIP 压缩包)
├── word/
│   ├── document.xml   <-- 主文本流、段落与表格定义
│   ├── styles.xml     <-- 样式定义（Heading 1, Normal 等）
│   └── numbering.xml  <-- 有序列表、多级大纲配置
└── [Content_Types].xml
```

### XML 节点树与层级抽取

在 `document.xml` 中，正文被拆解为具体的层次标签：
* `w:p`：段落节点（Paragraph）；
* `w:pPr`：段落属性节点，其子标签 `w:pStyle w:val="Heading1"` 记录了当前段落关联的样式名称；
* `w:r`：排版格式相同的文本运行块（Run）；
* `w:t`：实际存放字符串的纯文本节点（Text）。

```xml
<w:p>
  <w:pPr>
    <w:pStyle w:val="Heading1"/>
  </w:pPr>
  <w:r>
    <w:t>第 1 章 架构设计</w:t>
  </w:r>
</w:p>
```

![DOCX OpenXML 树结构解析与标题抽取](/images/content-rebuild/62f2ed030b643948/fig-4.png)

### 样式映射与复杂表格处理

解析 Word 文档如果只遍历 `w:t` 提取字符串，会导致全部大纲和表格拓扑丢失。规范的解析逻辑应处理以下要素：
1. **大纲级别映射**：读取 `word/styles.xml`，获取自定义样式名底层的实际大纲级别（`w:outlineLvl`）。即使用户把一级标题命名为“自定义章节头”，解析器也能根据其大纲级别将其转化为 Markdown 的一级标题 `#`；
2. **跨行跨列单元格对齐**：Word 表格由 `w:tbl`、`w:tr`（行）和 `w:tc`（单元格）构成。遇到合并单元格时，OpenXML 使用 `w:gridSpan`（跨列）和 `w:vMerge`（跨行 restart/continue）。解析器需要构建一个二维虚拟网格，把被合并区域的值按业务规则广播或填充，避免表格行数据错位；
3. **多级编号回填**：很多文档的“1.1”、“(1)”并非手工输入在 `w:t` 中，而是通过 `w:numPr` 引用 `word/numbering.xml` 动态生成。必须查询编号映射表，把对应序号补齐到段落开头，否则抽出的内容将缺失编号信息。

## 4. Markdown 语法树与上下文路径补全

在各类格式中，Markdown 对检索系统最友好。它原生采用纯文本内联标记，具备标准的 CommonMark 规范，不需要处理物理坐标投影。

### 维护标题栈与面包屑上下文注入

孤立的文本块被切分出来后，常常缺乏主语和上级背景（例如一段关于“参数配置”的文字，无法脱离前文得知是关于哪套系统）。解析 Markdown 时，可以通过标准语法树（AST）维护一个标题层级栈：

```python
# 基于 AST 标题层级维护上下文路径（原理示意）
class MarkdownOutlineParser:
    def __init__(self):
        self.breadcrumb_stack = []  # 存储结构: [(level, title_text), ...]

    def handle_token(self, token_type, level, text):
        if token_type == "heading":
            # 弹出栈中同级或更深层级的旧标题
            while self.breadcrumb_stack and self.breadcrumb_stack[-1][0] >= level:
                self.breadcrumb_stack.pop()
            self.breadcrumb_stack.append((level, text))
        elif token_type == "paragraph":
            # 拼装带有祖先上下文路径的增强文本块
            current_path = " > ".join([item[1] for item in self.breadcrumb_stack])
            return {"breadcrumb": current_path, "text": text}
```

通过该机制，一段位于 `### 索引压缩配置` 下的正文，输出时会附加字段：`面包屑：系统设计 > 向量检索 > 索引压缩配置`。在生成嵌入向量或进行全文检索时，该段落能自然保留完整的上级语境。关于切块窗口大小与重叠策略的进一步讨论，可参考 [/interview/rag-interview/rag-chunk-strategies.md](/interview/rag-interview/rag-chunk-strategies.md)。

![Markdown AST 遍历与面包屑路径注入](/images/content-rebuild/62f2ed030b643948/fig-5.png)

### 实际解析中的书写异常容错

即使格式规整，人工编辑的 Markdown 仍可能出现以下特殊情况：
* **标题跳级**：作者在一级标题 `#` 后直接使用了 `####`。解析栈必须支持自适应容错，不能因为缺失二级标题抛出异常；
* **伪标题（单行加粗）**：部分作者习惯使用单行加粗 `**一、背景概述**` 来替代真正的 Markdown 标题 `#`。解析预处理阶段可用正则匹配这类独占单行的简短加粗文本，将其规范化为同等层级的大纲节点。

## 5. 扫描件与复杂版面：OCR 介入时机与资源权衡

在企业文档库中，相当一部分 PDF 属于扫描件（本质是一张或多张包裹在 PDF 容器内的位图），或者是矢量文字与扫描表格混排。全量调用 OCR 或视觉多模态大模型会导致严重的吞吐瓶颈；而只用传统文本抽取库又会导致扫描页解析成空文本。

### 页面级分级路由机制

高效的解析服务通常在页面粒度设置判定逻辑，根据内容特征分流：

```text
输入 PDF 单页
  │
  ├── 步骤 1: 尝试字符流提取 (PyMuPDF / pdfminer)
  │     └── 统计字符数 N_chars、覆盖率 S_text/S_page 与乱码率 R_garbled
  │
  ├── 判定: 字符充沛且编码有效？
  │     (N_chars > 50 且 S_text / S_page > 0.15 且 R_garbled < 阈值)
  │     ├── [是] ──> 有效文字流 (原生排版或高质量双层 PDF) ──> 走坐标几何切分 (XY-Cut / 轻量版面模型)
  │     └── [否] ──> 字符缺失或乱码率超标 (纯扫描图或低质双层 PDF)
  │
  └── 步骤 2: 图像级重构与兜底
        └── 忽略或剥离异常文字图层 ──> 触发 OCR / 视觉版面模型 (如 PaddleOCR / Docling)
```

![PDF 多级解析路由与 OCR 触发时机](/images/content-rebuild/62f2ed030b643948/fig-6.png)

### 解析方案的特征与适用条件

不同技术路线在单页处理耗时与算力消耗上差异明显，工程落地时需按场景匹配选型：

| 解析技术路线 | 常见工具 | 典型页处理时延（单页参考） | 硬件依赖 | 适用场景 | 局限性 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **基于坐标与字符流的规则提取** | `PyMuPDF`、`pdfminer.six` | 10 ~ 50 ms | 单核 CPU 即可 | 规范排版的纯文字合同、电子书、常规文档 | 无法处理扫描件，遇复杂双栏或跨页表需大量规则修复 |
| **多模态与视觉版面分析** | `Docling`、`MinerU`、`Marker` | 300 ~ 1500 ms | 推荐多核 CPU 或 GPU | 复杂学术文献、多栏研报、密集排版手册 | 算力消耗较高，极端密集文本可能存在偶发漏字 |
| **端到端 OCR 识别** | `PaddleOCR`、`Tesseract`、云厂商 OCR | 800 ~ 3000 ms | 依赖 GPU 并发以维持吞吐 | 纸质盖章扫描件、传真翻拍、历史档案 | 相比直接读取矢量字体有一定字形误识概率，计算开销最大 |

注：表中时延数据受页面分辨率、图像尺寸及具体硬件配置影响，仅作为工程规划时的量级参考。关于非文本元素（表格还原、公式提取）的更详细处理，请参阅 [/interview/rag-interview/rag-content-types.md](/interview/rag-interview/rag-content-types.md)。

## 6. 面试追问与常见认知陷阱

### 常见追问 1：处理双栏排版的学术 PDF 时，规则抽取工具最常出现的阅读顺序错误是什么？如何解决？
**回答要点**：最常见的是**左右两栏横向穿插合并（Z 字形错乱）**。原因在于规则抽取器默认按全页单一 Y 轴坐标从上向下扫描。解决方法是引入 **XY-Cut 递归投影切分** 或基于字符边界框进行**垂直空白列（Gutter）检测**，先将页面划分为互不相交的垂直分栏包围盒，再在各栏内部独立执行自上而下的流式拼接。

### 常见追问 2：过滤文档页眉、页脚及版权声明等重复噪音的方案是什么？
**回答要点**：采取**空间几何门限**与**跨页频次比对**结合的双层策略。首先界定页面顶部与底部特定比例（如 $\le 8\%$ 页面高度）的区域为候选区；其次在候选区文本中统计跨页重复率。由于正文每页各异，而页眉、页脚在跨页中具有极高的编辑距离相似度与高频重复特性，一旦出现频率高于阈值（例如全书 $70\%$ 以上页面重复），即可在构建语法树阶段统一滤除。

### 常见认知陷阱
* **陷阱 1：无差别对所有文档使用重型视觉多模态模型**。视觉解析大模型虽然泛化能力强，但处理耗时与显存开销极大。面对数百页的纯文字技术文档，直接调用版面大模型不仅吞吐低下，还可能在密集文字区出现少量的字词幻觉。合理的架构应是“轻量规则判定优先，复杂版面与图片定向调用模型”。
* **陷阱 2：认为 Markdown 是纯文本，直接按字符切块即可，不需要 AST 解析**。忽略 Markdown 标记语法直接切分，容易把代码块截断破坏闭合标签，或将表格切碎丢失表头。先将其解析为 AST 块级对象树，再按节点切分才安全。
* **陷阱 3：虚构未经测试的准确率收益数字**。不同业务场景下文档质量差异极大，不应在面试中随意声称“采用某方案使知识库召回率直接提升 30%”。应重点说明**阅读顺序修复、表头关联与祖先上下文注入**如何防止语义打散，讲清因果逻辑即可。
