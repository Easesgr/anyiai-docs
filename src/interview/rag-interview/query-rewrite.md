在检索增强生成（RAG）系统中，检索质量直接影响最终回答的准确度。然而，用户直接输入的原始问题常常带有口语化表述、代词指代、关键信息省略，或者与知识库专业术语不一致。如果直接将这类输入送去做向量化或关键词检索，系统很容易召回不相关的切片。**Query Rewrite（查询重写）** 是在检索执行前，利用规则或语言模型对原始输入进行消歧、补齐、扩展和对齐的技术手段。

![Query Rewrite 模块作为预检索转换桥梁的核心示意图](/images/content-rebuild/8aa42cecf7711a0d/cover.png)

## 1. 核心口述答案

面试中被问到“什么是 Query Rewrite？有哪些常见策略？”时，可以按以下结构口述：

> **核心口述回答：**
>
> Query Rewrite 是预检索（Pre-Retrieval）阶段的处理机制，目的是解决用户原始提问与知识库文档之间的表达差异，将不完整或有歧义的输入转化为更容易精确检索的规范查询。
>
> 生产中最常见的三类策略包括：
>
> 1. **指代消解与补齐（Standalone Query）**：结合多轮历史，把省略主语或带有代词的问题（如“那它的高可用怎么做”）还原为语义完整的独立问题（如“分布式数据库 TiDB 的高可用架构设计”）；
> 2. **多查询扩展（Multi-Query Expansion）**：从不同角度或同义词切入生成 3 到 5 个子查询，并发检索后用倒数排名融合（RRF）合并结果，降低单一用词无法命中知识库的概率；
> 3. **假设性文档嵌入（HyDE）**：先让模型生成一段假设性的回答样段，用该段落的向量去匹配知识库，缩小短问句与长陈述句在向量空间中的非对称差异。
>
> 它的主要代价是**增加了检索前的模型推理延迟和 Token 成本**。因此通常配合规则分流或小模型，避免简单查询也无差别调用改写。

![Query Rewrite 的三大核心策略与检索分流机制](/images/content-rebuild/8aa42cecf7711a0d/fig-1.png)

在理解 [向量检索与混合检索基础](/interview/rag-interview/retrieval-methods.md) 后，我们可以通过一个具体的运维问答场景，逐一分析这三类方法的运行逻辑与适用边界。

## 2. 贯穿示例：多轮对话中的指代消解与上下文补齐

以分布式数据库技术支持助手为例，用户与系统进行了三轮交互：

- **第 1 轮提问**：“分布式数据库 TiDB 支持悲观事务吗？”（系统给出解答）
- **第 2 轮提问**：“那它的高可用架构是怎么设计的？”
- **第 3 轮提问**：“升级到最新版本会有停机时间吗？”

### 2.1 为什么直接检索会失效？

在第 2 轮中，用户的输入是 `那它的高可用架构是怎么设计的？`。如果直接拿这句话去计算文本向量并在知识库中匹配：

- 向量模型提取的核心语义特征偏向“通用高可用架构设计”，由于缺少主语实体“TiDB”，召回的切片可能是 MySQL、Redis 甚至微服务网关的高可用文档，产生明显的语义偏差；
- 如果粗暴地将前几轮对话全文直接拼接到当前问题后送去检索，历史对话中的“事务机制”、“隔离级别”等内容可能冲淡当前提问中关于“高可用架构”的权重，引入冗余干扰。

### 2.2 独立查询生成（Standalone Query Generation）

通用的工程解法是引入一个提示词或轻量模型，将多轮历史与最新提问整合成一个无需外部语境也能读懂的“独立检索查询”。

```python
# 独立查询重写提示词示例
STANDALONE_QUERY_PROMPT = """
你是一个检索系统的预处理模块。
请根据给定的历史对话与用户最新输入，将其重写为一个语义完整、不依赖上下文也能独立理解的单句问题。

规则：
1. 将代词（如“它”、“这个”、“该系统”）替换为历史中对应的具体实体；
2. 补齐省略的操作对象与必要约束，不要添加历史未提及的事实；
3. 不要回答问题本身，只输出重写后的单行问题文本。

对话历史：
{chat_history}

最新输入：
{current_query}

重写问题："""
```

经过该模块处理后：
- 输入：“那它的高可用架构是怎么设计的？”
- 输出：“分布式数据库 TiDB 的高可用架构是如何设计的？”

此时再送入检索，命中对应文档切片的概率大幅提升。

![多轮对话上下文指代消解与独立查询生成流程](/images/content-rebuild/8aa42cecf7711a0d/fig-2.png)

### 2.3 异常保护与降级

在实际工程中，重写模块不能作为黑盒无条件放行：

1. **确认型短语直通或拦截**：若用户输入为“好的”、“收到”、“继续”，重写模块可直接标记为跳过检索，防止无效查询打满后端；
2. **长度与格式异常兜底**：如果重写输出长度异常膨胀（例如原提问 8 个字，重写结果超过 100 字），或者输出了“好的，为您重写如下：”等模板套话，系统应回退至“历史提取实体 + 原始提问”进行检索，避免模型幻觉污染检索条件。

## 3. 假设性文档嵌入（HyDE）：利用生成样段缩小向量差异

### 3.1 问句与陈述句的非对称性

在稠密向量检索中，用户输入的短问句与知识库中存储的答案切片存在**文本形态非对称**：
- 提问：“为什么 Kafka 的写入吞吐量这么高？”（短疑问句，信息量较少）
- 目标切片：“Kafka 采用顺序写盘、操作系统页缓存（Page Cache）以及零拷贝（sendfile）技术，有效减少了内核态与用户态之间的上下文切换……”（长陈述句，高密度专业名词）

如果嵌入模型在预训练或微调阶段未对这类问答非对称对进行充分对齐，短问句向量与专业陈述句向量的余弦距离可能偏大。

HyDE（Hypothetical Document Embeddings）采取两步法：
1. 让语言模型根据问题先撰写一段简短的“假想答案文档”（不要求内容百分之百准确）；
2. 将这段假想文档进行向量化，用该向量去检索知识库中的真实切片。

其原理在于：假想文本虽然可能存在局部细节错误，但它已经转化为长篇陈述段落，包含类似的技术术语结构。在向量空间中，陈述句与陈述句的距离通常比问句与陈述句更接近。

![HyDE 假设性文档作为向量空间检索桥梁的原理与漂移风险](/images/content-rebuild/8aa42cecf7711a0d/fig-3.png)

### 3.2 适用边界与负面风险

HyDE 并非对所有场景都有效：

1. **私有未公开领域易引发检索漂移**：若提问涉及公司内部自研框架（如“如何配置订单系统的 split-bucket-v3 参数”），通用语言模型没有相关背景，生成的假想文档多由推测构成。使用这些虚假概念向量去检索，会导致检索结果脱靶（Query Drift）；
2. **精确错误码排障**：当用户输入具体的堆栈报错时，系统更需要 [BM25 关键词检索](/interview/rag-interview/hybrid-retrieval.md) 进行字面精确匹配，HyDE 生成的泛化解释反而会稀释精准错误标识；
3. **首字延迟开销**：检索前必须等待模型生成 100 到 200 个 Token，会为整体链路增加数百毫秒的固定等待。

## 4. 多查询扩展（Multi-Query）与倒数排名融合（RRF）

### 4.1 词汇差异与查询扩展

文档作者与提问者的用词往往不一致。例如用户提问：“线上服务频繁发生内存溢出怎么排查？”
- 文档 A 标题：“JVM 堆内存 OOM 故障处理与 Heap Dump 分析”；
- 文档 B 标题：“Linux 容器触发 OOM-Killer 机制排查指南”；
- 文档 C 标题：“应用内存泄漏与垃圾回收（GC）停顿调优实践”。

单一提问容易漏掉不同表述。Multi-Query 让语言模型将原始问题扩写为 $N$ 个侧重点不同的子查询：

```text
子查询 1：Java 虚拟机堆内存溢出分析与 Heap Dump 排查
子查询 2：Linux 容器进程被 OOM Killer 杀死的日志与配置检查
子查询 3：高频 GC 停顿与内存泄漏的排查命令与定位流程
```

![Multi-Query 并发检索与 RRF 融合去重流程](/images/content-rebuild/8aa42cecf7711a0d/fig-4.png)

### 4.2 倒数排名融合（RRF）合并打分

系统并发执行这 $N$ 路检索，各自得到初步候选列表，随后通过倒数排名融合（Reciprocal Rank Fusion, RRF）进行综合排序与去重。

对于出现在多个召回列表中的切片 $d$，其综合得分定义为：

$$score(d \in D) = \sum_{q \in Q} \frac{1}{k + r_q(d)}$$

其中：
- $Q$ 表示所有发起的子查询；
- $r_q(d)$ 是切片 $d$ 在子查询 $q$ 结果中的排名（从 1 开始计；若未进入该路召回的前列，则不计入该项）；
- $k$ 为平滑常数（常见默认取值 $k = 60$）。

**算例推导（示意）：**
假设系统发起了 3 个子查询，常数 $k = 60$：
- **文档 A**：仅在子查询 1 中排在第 1 名，未进入子查询 2 和 3 的候选集：
  $$score(A) = \frac{1}{60 + 1} \approx 0.01639$$
- **文档 B**：在 3 个子查询中均排在第 5 名：
  $$score(B) = \frac{1}{60 + 5} + \frac{1}{60 + 5} + \frac{1}{60 + 5} = \frac{3}{65} \approx 0.04615$$

虽然文档 A 在单一路线拿到了第 1 名，但文档 B 在多路检索中表现稳定，综合 RRF 得分反超文档 A。这种机制降低了单一查询偶发偏置的影响。关于混合召回后的重排序计算，可参考 [Rerank 重排序原理](/interview/rag-interview/rerank.md)。

## 5. 性能损耗与分级路由设计

查询改写是在检索前增加了模型计算，必须在召回效果与系统开销之间做权衡。

### 5.1 性能指标对比

| 处理策略 | 首字时间（TTFT）影响 | 模型 Token 消耗 | 向量库请求负载 |
| :--- | :--- | :--- | :--- |
| **不改写（原始提问直检）** | 仅检索耗时（约 30~80ms） | 无前置消耗 | $1 \times \text{QPS}$ |
| **单次独立查询重写** | 增加单次简短模型推理（+150~400ms） | 增加少量输入/输出 Token | $1 \times \text{QPS}$ |
| **Multi-Query（扩写 3 路）** | 增加多项生成时间（+250~600ms） | 增加扩写提示词 Token | $3 \times \text{QPS}$ 并发检索 |
| **HyDE 假想文档生成** | 增加段落生成时间（+400~1000ms） | 增加段落级生成 Token | $1 \times \text{QPS}$（单篇长段检索） |

### 5.2 分级路由与降级策略

为避免全量请求无差别经过改写模块，生产系统通常采用分级路由控制：

1. **首轮提问短路规则**：
   若为会话第 1 轮提问，字符长度适中（例如 15~50 字符）且包含明确名词，无需多轮指代补齐，**直接进入检索**；
2. **选用专用轻量模型**：
   改写任务通常不需要千亿级大模型，可选用 7B/8B 级别的专用轻量模型或经过蒸馏的微调模型，将改写延迟压制在可接受范围；
3. **超时强行降级**：
   为改写调用配置超时阈值（如 300ms）。一旦触发超时或接口异常，系统自动使用原始用户提问发起检索，避免阻塞整个回答流程。

## 6. 面试追问与常见认知误区

### 追问 1：为什么不直接把多轮对话全文拼进 Embedding 检索，非要做改写？

> **参考解答：**
> 粗暴拼接历史多轮文本容易稀释当前问题的语义权重。稠密嵌入模型在将长文本映射为固定维度向量时，池化操作会整合整段文字的信息。如果历史讨论占了 80% 的字数，生成的向量会大量包含历史概念，导致当前真正要查的核心意图被噪声覆盖。查询重写的作用是去粗取精，把分散在多轮上下文中的实体与当前动作重新提炼为单一问题。

![多轮历史粗暴拼接与独立重写检索的向量空间对比](/images/content-rebuild/8aa42cecf7711a0d/fig-6.png)

### 追问 2：Multi-Query 裂变为多路查询后，下游 Rerank 模型计算压力过大如何处理？

> **参考解答：**
> 可以在检索与 Rerank 之间设置两级筛选漏斗：
> 1. **单路截断（Top-K Cutoff）**：每路子查询只取前 10~15 条，控制初步候选集总量；
> 2. **RRF 快速合并**：利用 RRF 算法在内存中完成去重与粗排（属于纯数值运算，耗时通常不足 1ms），截取综合排名前 15~20 的唯一文档；
> 3. **精排重排**：仅将这 20 个切片输入 Cross-Encoder 类型的 Rerank 模型计算打分，锁定重排阶段的算力消耗。

### 常见误区辨析

- **误区一：改写后应该直接丢弃用户原始 Query。**
  - **事实**：应始终保留原始 Query。一方面，最终交给回答模型的提示词需要包含用户的真实问法；另一方面，检索阶段也可将原始 Query 与改写 Query 一同召回，防止改写模块理解偏差导致单点失败。
- **误区二：HyDE 总能提高检索准确率。**
  - **事实**：HyDE 的前提是底层模型具备该领域的常识。在私有 API 参数、内部故障码或未公开专有知识库上，HyDE 生成的推测性假象文档往往会导致向量严重偏离真实切片，效果常逊于关键词检索。

在完善查询处理链路时，可参考 [上下文查询增强与无关问题处理](/interview/rag-interview/contextual-query-enhancement.md)；针对需要跨工具与多步分解的复杂问答，可进一步查阅 [Agentic RAG 查询规划与多步检索](/frontier/agentic-rag/complex-query-planning.md)。
