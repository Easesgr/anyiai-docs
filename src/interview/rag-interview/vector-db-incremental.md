在 RAG 系统中，知识库文档并非一成不变。企业的规章制度、技术规范、产品手册会持续经历新增、修订与废止。若在文档更新时仅做简单的追加插入，不仅会重复调用 Embedding 模型造成算力浪费，还会导致向量数据库中残留过期切片，让检索召回相互矛盾的上下文，最终导致大模型生成幻觉回答。

理解增量更新，需要掌握切片指纹识别、向量索引的物理更新限制、孤岛切片级联清理，以及主数据库与向量库之间的一致性保障。

## 1. 核心口述答案：增量更新的四个核心环节

面试中遇到“**RAG 中如何实现向量数据库的增量更新？**”，可以先给出分层次的结构化回答：

> **核心口述回答：**
>
> “在 RAG 工程中，向量数据库的增量更新不同于传统关系型数据库的原地修改，通常包含四个核心环节：
>
> 1. **双层哈希比对**：通过‘文档级哈希’判断文件是否变更；若变更，再通过‘切片级内容哈希’找出具体修改的切片，未变动的切片跳过向量计算，控制 Embedding 接口调用开销。
> 2. **两阶段更新与级联删除**：由于 HNSW 等常见向量图索引直接修改向量坐标会破坏连通邻居关系，向量引擎普遍采用‘先逻辑标记删除旧向量，再插入新向量’的更新机制。同时，必须维护文档与多切片的一对多映射，当文档内容缩减时，级联清理已被移除的旧切片，避免孤岛切片残留。
> 3. **段合并与垃圾回收**：向量删除在底层通常只是打上删除位图（Tombstone），检索时仍可能遍历该节点并消耗计算资源。存储引擎会通过异步段合并（Compaction）在后台清理失效数据并重构索引拓扑，这一过程需避开业务查询高峰。
> 4. **CDC 异步一致性管道**：在架构层面，主文档通常存放在 PostgreSQL 或 MySQL 等主数据库中。为避免应用层双写出现超时与乱序覆盖，业界通常采用基于 CDC（如 Debezium 监听 Binlog/WAL）加消息队列的异步管道，按文档 ID 分区保序，并配合版本号实现幂等消费，保障最终一致性。”

## 2. 贯穿示例：一份《差旅报销制度》的变更

为了直观理解增量更新的每一个步骤，本文使用一个统一的贯穿示例：

企业知识库中有一份文档《差旅报销制度.md》（文档 ID 为 `doc_reimburse`），旧版本（v1）切分为 5 个切片：
- `chunk_0`：总则与审批流程
- `chunk_1`：住宿报销标准（每晚最高 400 元）
- `chunk_2`：交通与餐饮补贴标准
- `chunk_3`：纸质发票贴票规范
- `chunk_4`：财务收件地址与邮寄要求

现在财务部门发布新版本（v2）：
1. 住宿标准调高到 500 元（修改了 `chunk_1`）。
2. 全面推行电子发票，直接废除纸质贴票和邮寄规则（删除了 `chunk_3` 和 `chunk_4` 的内容）。
3. `chunk_0` 和 `chunk_2` 内容完全不变。

此时，文档从 5 个切片减少为 3 个切片。如果系统处理不当，就会发生两类典型问题：一是无脑重新向量化所有切片；二是只覆盖了前 3 个切片，导致包含旧贴票规范的 `chunk_3` 和 `chunk_4` 残留在向量库中，用户提问“纸质发票怎么寄”时依然搜出过期的假指引。

## 3. 文档指纹与内容哈希去重

增量同步的第一步是识别变更范围。文本切片向量化需要调用计算资源，如果每次文档有小改动都全量重新生成向量，成本会随着文档规模线性膨胀。

<ReadMoreLock />

高效的更新检测依赖两级哈希指纹：

1. **文档级哈希（Document Hash）**：对原始文本全文计算 SHA-256 摘要。在《差旅报销制度》更新时，比对发现哈希值不同，触发更新流程；若完全相同，则整篇文档直接跳过。
2. **切片级哈希（Chunk Hash）**：文档切分后，对每个切片的正文及绑定的元数据（如所属章节）计算哈希值。
   - 在示例中，`chunk_0` 与 `chunk_2` 的切片哈希与旧记录一致，无需重新调用 Embedding API。
   - `chunk_1` 的哈希改变，进入重算队列。
   - 旧的 `chunk_3` 与 `chunk_4` 在新列表中不存在，进入清理队列。

![文档与切片双层哈希比对机制](/images/content-rebuild/839aca65e4f8918f/fig-2.png)

### 状态记录表设计

数据管道需要维护一张元数据追踪表（例如 LangChain 的 `RecordManager`，或自研的数据同步状态表）：

```sql
CREATE TABLE rag_document_record (
    doc_id VARCHAR(64) NOT NULL,            -- 源文档标识，如 'doc_reimburse'
    chunk_id VARCHAR(128) NOT NULL,         -- 切片唯一标识，如 'doc_reimburse#chunk_1'
    content_hash VARCHAR(64) NOT NULL,      -- 切片内容与元数据的哈希摘要
    doc_version BIGINT NOT NULL DEFAULT 1,  -- 文档版本号
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (chunk_id)
);
CREATE INDEX idx_rag_doc_id ON rag_document_record(doc_id);
```

### 切分边界偏移陷阱

固定字符长度的滑动窗口切分存在“偏移量扩散”缺陷：若在文章开头增删几个字，会导致后续所有切片的起始边界全部后移，原本内容未变的段落其切片哈希全部失效。

**缓解措施：**
- 优先依据 Markdown 标题、段落换行、HTML 标签等天然结构切分，使单个段落的文字变动被局限在当前节点内，切断对其他切片的哈希污染。
- 使用稳定的标识符拼接方式生成 Chunk ID（如 `doc_id#section_name`），而不是无意义的自增序号。

## 4. 更新机制：Delete-Insert 两阶段与级联删除

### 为什么向量数据库普遍不直接原地修改？

在传统关系型数据库中，定长字段可以直接在原磁盘页上覆盖更新。但在向量数据库中，向量是高维稠密浮点数数组，且依赖近似最近邻（ANN）索引结构（如 HNSW 分层图或 IVF 倒排单元）来支撑毫秒级检索。

以 HNSW 为例，每个向量是图中的一个节点，与周围的邻居节点建立了固定的连边关系。若原地修改某个向量的数值，该点在几何空间中的位置发生位移，原有连边关系全部失效；若直接改动，可能导致图遍历出现断路，大幅降低召回精度。因此，多数向量引擎的更新操作在底层均表现为**先标记删除旧节点，再在图中插入新节点**的两阶段机制（Delete-Insert）。

### 级联删除解决孤岛切片

源文档与向量切片是一对多的映射关系。在《差旅报销制度》示例中，切片数量从 5 个缩减为 3 个。若数据管道仅按列表前 3 项去更新（覆盖旧的 `chunk_0` 到 `chunk_2`），原先的 `chunk_3` 与 `chunk_4` 就会变成**孤岛切片（Orphan Chunks）**。它们依然存留在向量库中，带有旧的文档标签，持续参与检索并误导模型。

因此，增量更新必须包含完整的级联清理逻辑：比对该文档下“原切片集合”与“新切片集合”的差集，将不再存在的切片从向量库中删除。

```python
def sync_document_incremental(doc_id: str, new_content: str, record_mgr, vector_store):
    new_doc_hash = calculate_hash(new_content)
    old_doc_record = record_mgr.get_doc(doc_id)
    
    # 1. 文档级哈希快速校验
    if old_doc_record and old_doc_record.content_hash == new_doc_hash:
        return "SKIPPED"
        
    new_chunks = semantic_split(new_content)
    new_chunk_records = []
    chunks_to_insert = []
    
    for chunk in new_chunks:
        c_hash = calculate_hash(chunk.text + str(chunk.metadata))
        # 使用稳定锚点生成切片 ID
        chunk_id = f"{doc_id}#{chunk.anchor_id}"
        new_chunk_records.append((chunk_id, c_hash))
        
        # 2. 切片哈希校验：若内容变动或切片不存在，则加入待向量化列表
        if not record_mgr.chunk_exists(chunk_id, c_hash):
            vector = get_embedding(chunk.text)
            chunks_to_insert.append((chunk_id, vector, chunk.metadata, chunk.text))
            
    # 3. 找出已删除的旧切片集合（差集计算）
    old_chunk_ids = record_mgr.get_all_chunk_ids_by_doc(doc_id)
    new_chunk_id_set = {cid for cid, _ in new_chunk_records}
    stale_chunk_ids = list(set(old_chunk_ids) - new_chunk_id_set)
    
    # 4. 执行向量库更新：清理孤岛切片，写入新切片
    if stale_chunk_ids:
        vector_store.delete(ids=stale_chunk_ids)
    if chunks_to_insert:
        vector_store.upsert(chunks_to_insert)
        
    # 5. 更新状态表
    record_mgr.update_state(doc_id, new_doc_hash, new_chunk_records, stale_chunk_ids)
    return "UPDATED"
```

## 5. 向量索引的动态维护与段合并开销

在运维 Milvus、Qdrant 等向量数据库时，更新操作不仅影响写入吞吐，还会直接影响检索性能。

### 墓碑机制（Tombstoning）与图路径退化

为了保障高吞吐写入，向量引擎在接收到删除指令时，通常不会立即物理重构索引图，而是在内存或索引结构中打上删除标记（Tombstone / Bitset）。

在随后的向量检索阶段，图遍历算法遇到带有墓碑标记的节点时，会通过位图过滤将其从最终候选集中排除。但需要注意：
- **距离计算仍可能发生**：搜索遍历路径可能依然会路过被标记删除的节点，消耗向量相似度计算资源。
- **召回路径退化**：如果短期内积累了大量被删除节点，连通图的有效路径可能被切断，导致检索过早陷入局部极值，影响 Top-K 召回率。

### 段合并（Compaction）

主流向量数据库通常参考 LSM-Tree 类似的不可变数据段（Segment）架构：
1. **写入缓冲**：新增与更新的数据先写入内存缓冲，达到阈值后刷盘为不可变的小段。
2. **异步合并**：后台进程定期扫描多个小段，读取存活向量并丢弃带有墓碑标记的数据，合并为一个紧凑的大段。
3. **索引重建**：在干净的大段上重新构建 HNSW 或 IVF 索引，物理释放旧段占用的磁盘空间。

**工程策略**：段合并是 CPU 与磁盘 I/O 密集型操作。在生产环境中，应合理配置合并触发阈值，避免在白天高并发检索期集中触发；可以设定夜间定时执行深度合并，保障线上查询的低延迟。

## 6. 主数据库与向量库的一致性：双写 vs CDC 架构

在多数业务架构中，文档的正文、编辑状态和权限存储在关系型数据库（如 PostgreSQL 或 MySQL）中，向量数据库充当只读的二级检索索引。如何保障两者状态一致，是面试的高频考察点。

### 应用层同步双写的隐患

常见初级做法是在业务逻辑代码中同时写入两端：

```text
用户修改文档 -> 保存到 MySQL -> 调用 Embedding 接口 -> 写入向量库 -> 接口返回成功
```

这种做法存在两个主要隐患：
1. **缺乏事务保障导致状态不一致**：主库事务已提交，但 Embedding 模型网络超时或向量库写入失败，导致主库有最新文档，而向量库仍停留在旧数据。
2. **并发时序错乱**：用户快速连续保存版本 1 和版本 2。由于网络波动或模型推理延迟，版本 2 的更新先完成写入，版本 1 随后才到达向量库，导致旧数据覆盖新数据。

### CDC 异步解耦方案

生产环境推荐采用基于变更数据捕获（CDC）的异步事件驱动架构：

1. **捕获变更日志**：通过 Debezium 或 Canal 等组件，实时监听主数据库的事务日志（MySQL Binlog 或 PostgreSQL WAL），捕获文档表的修改与删除事件。
2. **分区保序传输**：将变更事件投递至 Kafka 等消息队列，**以文档 ID（`doc_id`）作为消息 Key**，确保同一篇文档的所有变更严格路由到同一个 Partition，按顺序被消费。
3. **异步消费与重试**：Ingestion 消费集群从队列拉取消息，执行切分、哈希计算与 Embedding 生成。如果 Embedding 服务暂时不可用，消息积压在队列中，消费者通过重试恢复，不影响主库业务操作。
4. **版本屏障与幂等写入**：切片写入向量库时带上主库的 `doc_version` 或时间戳。若消费到的版本低于当前记录版本，则直接丢弃，防止乱序写覆盖。

## 7. 面试追问与常见认知误区

### 追问 1：检索时如何避免搜到“正在更新中”的半截文档？

若某篇长文档切分为 40 个切片，更新耗时数秒。在更新执行到一半时，前 15 个切片已写入，后 25 个切片尚未处理，此时线上请求可能检索到残缺的内容。

**应对方案：**
1. **元数据版本隔离（推荐）**：新切片写入时标记为新版本号 `version: 2`。线上检索请求默认携带元数据过滤条件 `filter: {version: 1}`。待 40 个切片全部写入并校验完成，在配置表原子修改当前有效版本为 `2`，检索端同步切换过滤条件，随后后台异步清理 `version: 1` 的切片。
2. **集合别名切换（蓝绿切换）**：对于周期性全量重建或中小型知识库，可以直接构建全新的 Collection，写入并建好索引后，通过向量数据库的 Alias（别名）API 将读流量秒级切换到新集合，再销毁旧集合。

![版本隔离与原子切换方案](/images/content-rebuild/839aca65e4f8918f/fig-6.png)

### 追问 2：CDC 架构相比应用层双写有哪些核心收益？

**回答要点：**
- **解耦主业务吞吐**：主库事务落盘仅需数毫秒，无需同步阻塞等待重型的文本切分与外部 Embedding API 推理。
- **故障容错与缓冲**：外部模型接口限流或向量库抖动时，消息在队列中缓冲并按策略重试，不会阻断主业务流程。
- **按 Key 分区保障时序**：相同文档的写事件在单个 Partition 内严格有序处理，规避网络抖动引起的并发时序倒挂。

### 常见错误认知清单

- ❌ **错误观点**：“向量数据库可以像关系数据库那样直接对向量字段执行原地 UPDATE。”
  - **事实纠正**：由于高维向量及其 ANN 索引结构（如 HNSW 拓扑或 IVF 倒排列表）的几何连通性约束，更新通常在底层表现为先标记删除（Tombstone）旧向量，再插入新向量的两阶段过程。
- ❌ **错误观点**：“只要调用了向量删除接口，磁盘空间就会立刻释放。”
  - **事实纠正**：删除操作通常仅在内存或索引中置位删除标记，物理空间的回收和图连接的修剪需要依赖后端的段合并（Compaction）任务。
- ❌ **错误观点**：“增量比对直接用全文字符串做对比即可，不需要维护哈希表。”
  - **事实纠正**：长文本的跨网络传输与数据库全文字段逐字比对开销较大；维护定长哈希摘要（如 SHA-256）存储开销极小，且能在切片后借助键值比对以近乎常数时间快速过滤未变内容，避免全量长字符串在网络与数据库层面的高开销逐字比对。
