在构建检索增强生成（RAG）系统时，文档切分不仅依赖于切分策略（如按段落、Markdown 标题或语法语义切分，详见 [/interview/rag-interview/rag-chunk-strategies.md](/interview/rag-interview/rag-chunk-strategies.md)），还取决于两个关键的数值参数：块大小（`chunk_size`）与重叠大小（`chunk_overlap`）。

这两个参数直接决定了文本索引的粒度、向量检索的精度，以及最终输入大模型（LLM）的上下文信噪比。

## 1. 面试口述答案：设定逻辑与验证流程

在面试中被问到“`chunk_size` 和 `chunk_overlap` 如何设置”时，建议按照**设计目标、上下游约束、经验基准与测试集验证**四个层次口述：

> **口述要点：**
> 1. **核心权衡**：`chunk_size` 决定单次检索单元的信息密度。上限受限于 Embedding 模型的最大输入长度与多主题混合带来的表征稀释，下限受限于表达完整独立事实所需的最小语境；同时它需要配合 Top-K 检索数量，适配下游 LLM 的提示词上下文预算。
> 2. **重叠机制**：`chunk_overlap` 通过滑动窗口让相邻切片产生共享文本，防止物理硬截断导致人名、实体分裂或因果逻辑断裂。通常将重叠比例保持在 `chunk_size` 的 $10\% \sim 20\%$。
> 3. **初始基线**：通用非结构化文档通常以 512 tokens 搭配 10%~15% overlap（例如 50~80 tokens）作为实验基准。
> 4. **验证调优**：参数不能主观拍定，应准备包含真实查询与标注证据的评测集，并划分为验证集与留出测试集；在验证集上对 `chunk_size`（如 256、512、1024）和重叠比例进行网格搜索，结合命中率（Hit Rate@K）、平均倒数排名（MRR@K）选出候选组合，最终在独立测试集上验收泛化表现，防止数据泄漏导致指标虚高。

## 2. 决定 chunk_size 的两个边界约束

`chunk_size` 受到向量检索链条上下游两端的物理与模型约束：

### 边界一：Embedding 模型的输入与表征特性

文本切片必须经由向量模型转换为致密向量（原理详见 [/interview/rag-interview/embedding-in-rag.md](/interview/rag-interview/embedding-in-rag.md)）。
1. **最大序列截断**：开源稠密向量模型（如基于 BERT 架构调整的模型）多数有明确的序列上限（如 512 tokens，部分支持 8192 tokens）。如果 `chunk_size` 超过模型的 `max_seq_length`，尾部文本将被模型直接截断丢弃，导致信息丢失。
2. **多主题稀释**：稠密向量通常通过池化（如 Mean Pooling）将整段文本压缩为一个定长向量。切片过长时，内部可能包含多个互不相关的从句或事实，局部关键信息的表征容易被全局背景平摊，降低对细粒度问题的余弦相似度区分度。

### 边界二：下游 LLM 的上下文预算与候选多样性

检索到的切片最终会组装进 Prompt 提供给 LLM：

$$\text{Prompt 长度} = \text{模板前缀} + \text{用户问题} + \sum_{i=1}^{K} \text{切片}_i$$

在总 Token 预算固定的前提下，`chunk_size` 越大，系统所能容纳的切片数量 $K$（即 Top-K，详见 [/interview/rag-interview/rag-topk.md](/interview/rag-interview/rag-topk.md)）就必须减小。这会减少来自不同文档来源的候选切片数量，削弱召回结果的多样性；反之，若 `chunk_size` 过小，单条切片缺乏完整前后因果，LLM 容易因信息破碎而难以推导结论。

## 3. chunk_overlap 的作用机制与步长计算

按固定长度切分文本时，句子常在分块边界被切成两段。`chunk_overlap` 借助滑动窗口（Sliding Window）在相邻切片之间共享部分文本，让边界处的内容在至少一个切片内完整保留。

### 步长（Stride）与切片生成

滑动窗口的步长定义为：

$$\text{Stride} = \text{chunk\_size} - \text{chunk\_overlap}$$

以一篇长度 $L = 1000$ tokens 的文档为例，设定 `chunk_size = 400`，`chunk_overlap = 100`，步长为 $300$：
* 切片 1 区间：$[0, 400)$
* 切片 2 区间：$[300, 700)$
* 切片 3 区间：$[600, 1000)$

假设文档中有一句关键因果描述（例如：“由于网络交换机配置错误，导致支付网关超时报警”）位于 Token 360 到 420 之间：
* 在切片 1 中，该句在 Token 400 处被截断，只保留了前半句（“由于网络交换机配置错误”）；
* 在切片 2 中，由于窗口回退了 100 tokens（从 300 开始），该句完整出现在切片 2 内部（对应切片 2 内的偏移位置 60 到 120）。

这样就避免了因为分块物理截断导致关键实体或因果从句无法在同一切片内被完整向量化。

## 4. 重叠大小的权衡：存储膨胀与语境完整

`chunk_overlap` 的设置需要在存储成本与语境连贯性之间做权衡。

### 重叠过大（例如 Overlap $\ge 50\%$）的成本

1. **切片总量激增**：在总长度 $L$ 一定的情况下，切片总数近似为 $\lceil \frac{L - \text{chunk\_size}}{\text{stride}} \rceil + 1$。当重叠率从 $10\%$ 增加到 $50\%$ 时，步长缩小，切片总数接近翻倍。向量数据库的存储占用和向量化计算成本随之翻倍。
2. **Top-K 内容高度冗余**：重叠过大的相邻切片在向量空间中距离极近。检索时，相似度最高的几条切片很可能来自同一段落的不同偏移版本。如果系统没有去重逻辑（如基于文档 ID 聚合），重复切片会挤占 LLM 上下文窗口，挤掉其他真正包含补充证据的文档。

### 重叠过小（例如 Overlap $< 5\%$ 或 0）的风险

1. **实体与因果割裂**：位于切分边界的复合名词、条件判断从句被生硬拆开，单条切片在向量模型中失去关键信息。
2. **指代断裂**：上文的主语在切片 1 末尾，而代词或宾语在切片 2 开头，导致单独检索切片 2 时缺乏主语支撑。

| 重叠比例 | 相对存储开销 | 检索多样性 | 边界断裂风险 | 常见适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **0%** | 基准（最小） | 高（切片无重合） | 高 | 严格按独立表格行、独立 FAQ 切分 |
| **10% ~ 20%** | 增加约 10% ~ 25% | 平衡 | 低 | 通用非结构化文档（技术手册、规章制度） |
| **≥ 50%** | 翻倍或更高 | 易出现近邻冗余 | 极低 | 搭配分组去重（如 `group_by`）的特殊召回管线 |

## 5. 基于评测集划分与网格搜索的调优方法

分块参数通常通过离线评测集结合网格搜索（Grid Search）实验确定（评测体系详见 [/interview/rag-interview/rag-evaluation.md](/interview/rag-interview/rag-evaluation.md)）。为防止超参数调优产生数据泄漏导致指标虚高，应将标注样本划分为调优验证集与独立的留出测试集。

### 离线调优流程

```
[准备评测集并划分] -> [设定参数网格] -> [验证集检索与指标诊断] -> [留出测试集泛化验收]
(验证集/测试集隔离) (256/512/1024, 10%/20%) (Hit Rate, MRR, 相关度分析) (验证最优组合未过拟合)
```

1. **准备与划分评测集**：
   整理 50~100 个典型业务查询，标出每个查询对应的标准参考切片或文本位置，并严格划分为调优验证集与独立的留出测试集（例如按 6:4 划分）。
2. **划定参数网格**：
   * `chunk_size` 选取候选集合：`[256, 512, 1024]`；
   * `overlap_ratio` 选取候选集合：`[0.10, 0.20]`；
   形成 6 组参数组合。
3. **在验证集上构建索引并计算检索指标**：
   在相同向量模型和相同 Top-K 检索条件下，在验证集上对比各组参数表现，分别计算两项核心指标：
   * **命中率（Hit Rate@K）**：在全部查询中，Top-K 检索切片至少命中一个标注证据的查询占比：
     $$\text{Hit Rate@}K = \frac{1}{|Q|} \sum_{q=1}^{|Q|} \mathbb{I}(\text{Top-}K \text{ 包含标注切片})$$
   * **平均倒数排名（MRR@K）**：首个标注证据切片在 Top-K 列表中排名的倒数均值（若未命中计为 0）：
     $$\text{MRR@}K = \frac{1}{|Q|} \sum_{q=1}^{|Q|} \frac{1}{\text{rank}_q}$$
4. **根据指标异常反推参数调整**：
   * **现象 1：Hit Rate 偏低，但切片与问题语义看似相关**
     * **排查方向**：`chunk_size` 可能过小，单块上下文不足以支撑与 Query 的语义相似度匹配；或者 `chunk_overlap` 偏小导致关键术语被断开。
     * **调整**：调大 `chunk_size` 到 512 或 1024，并保持 10%~20% 重叠。
   * **现象 2：Hit Rate 较高，但下游生成答案幻觉多、包含噪音（排查详见 [/interview/rag-interview/rag-troubleshooting.md](/interview/rag-interview/rag-troubleshooting.md)）**
     * **排查方向**：`chunk_size` 过大，单个切片混入了过多无关内容，干扰了 LLM 的生成聚焦。
     * **调整**：缩小 `chunk_size`；或者采用“小块检索、大块返回”的父文档展开策略（Parent-Document Retrieval），用小切片做精准向量匹配，命中后再读取其所属的父级完整段落送入大模型。
5. **在留出测试集上复核验收**：
   在验证集上选定最优参数后，在未参与调优的留出测试集上进行最终指标验证，确认 Hit Rate@K 与生成质量稳定，避免因调优过程造成数据泄漏与过拟合。

## 常见追问与回答要点

### 追问 1：如果语料库里既有简短的 FAQ 问答，又有长篇技术白皮书，能否使用同一套 chunk_size？

* **回答要点**：不建议统一设置。FAQ 问答通常只有几十到一百多 tokens，若强行用 512 切分，会导致多个互不相关的问答对被拼在同一个切片内，造成检索串扰；而长篇技术白皮书若切得太碎，跨段落的推演逻辑会被割裂。
* **处理方案**：按文档类型实施针对性分块。FAQ 走结构化通道，一条 QA 作为独立切片（overlap 设为 0）；长文档走通用分块（如 512 tokens + 15% overlap），并在元数据中打上 `doc_type` 字段，检索时支持元数据过滤或分路召回。

### 追问 2：为什么不把 overlap 设置为 0，然后在检索召回后动态把相邻切片拼回去？

* **回答要点**：分块是索引构建时的静态操作。如果建立索引时 overlap 为 0，被硬截断的词组或句子在向量库中就永远不会以完整连贯的形式出现。Embedding 编码时得到的是受损切片的特征向量，相似度计算分数降低，在初检召回阶段就可能直接掉出 Top-K，下游动态拼接便无从谈起。
