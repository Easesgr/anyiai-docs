在文档问答系统中，真实企业文档往往不是平铺直叙的纯文本，而是混杂着多栏表格、嵌套代码块、架构图与扫描截图的复杂富文本。很多开发者在搭建 RAG 时，直接把文档统一按固定字符数（如 500 字符）切分，结果表格被横腰斩断、代码函数缺失外层作用域、图片说明与原图脱钩，导致检索阶段关键词命中率低或生成阶段上下文缺失。

本篇承接上一讲 [/interview/rag-interview/rag-multiformat-parsing.md](/interview/rag-interview/rag-multiformat-parsing.md) 中解析器抽取的结构化文档流，针对**表格、代码块与图像**这三类高密度异构元素，分析其切分、索引与向量化检索的具体工程实践。

## 1. 核心口述答案：多类型富文本的差异化表示原则

在面试中被问到“如何处理 Markdown 中的表格、代码和图片”时，切忌笼统回答“切小块后全部存进向量库”。面试官考察的是你对**异构信息结构**与**语义自包含性**的理解。建议采用如下结构化口述：

> **核心口述回答：**
>
> “处理表格、代码块与图像等复杂元素，核心原则是**避免无差别的机械字符切分，实施结构感知的语义对齐**：
>
> 1. **表格处理（降维与元数据补全）**：表格依赖二维行列对齐，机械截断会导致列名与单元格脱节。常规尺寸表格推荐采用**行级序列化（Row-wise Serialization）**，在切分时将表头元数据注入每一行文本；对整表建立‘自然语言摘要 + 原始 Markdown/HTML’的双层索引，检索时匹配摘要或行记录，填充上下文时提供完整表格；针对多列大宽表，则路由到 Text-to-SQL 或数据库查询。
> 2. **代码块切分（AST 语法感知）**：代码具有严格的作用域和缩进层级。切分时采用 **AST（抽象语法树）解析器**（如 Tree-sitter），以类或函数为自然边界切块，并在切片头部附带文件路径、Import 依赖与函数签名上下文，保证切片语义独立可读。
> 3. **图像与图表检索（多模态与文本代理双轨）**：在以技术文档和报表为主的场景中，**文本代理检索**是稳定且低成本的做法：利用 OCR 提取图中文字，结合视觉模型（VLM）生成图像描述摘要（Caption），编入主干文本索引库；对依赖复杂空间排版或视觉特性的资产库，再引入端到端多模态 Embedding（如 CLIP 或 ColPali）进行图文多模态对齐。
> 4. **上下文关联（父子索引与边界约束）**：通过 **Parent-Child 挂载机制**，让细粒度的表格行、代码函数或图片 Caption 作为子块（Child Chunk）负责精准匹配，检索命中后拉取父章节（Parent Chunk）送入大模型，保证跨模态引用和前置说明不丢失。”

## 2. 表格切分：行级序列化与双层表征

### 为什么固定字符切分会导致表格检索失效？

文本嵌入模型（Dense Embedding）依赖序列中的上下文词序，BM25 等稀疏检索依赖关键词匹配。而表格依赖的是二维坐标系中的行列交叉点。

当 Markdown 表格被按固定长度（例如每 200 字符）机械切断时：
1. **表头丢失**：第一块含有列名，后续切块只剩下裸数据（例如 `| 2024Q3 | 45.2% | 1200 |`）。检索模型缺乏字段名称，无法判断数字是属于“净利润率”还是“库存周转天数”。
2. **行列语义分离**：复杂表格常有跨行或跨列单元格，按字符切片后，数据行与上级分组关系断裂，嵌入向量难以表达其完整业务事实。

### 表格表征对比示例

以一份服务器监控表为例：

| 机房编号 | 节点类型 | CPU 峰值负载 | 内存使用率 |
| :--- | :--- | :--- | :--- |
| BJ-01 | 计算型-C8 | 89.5% | 76.2% |
| BJ-01 | 存储型-S5 | 32.1% | 94.8% |
| SH-02 | GPU型-G10 | 98.2% | 88.0% |

#### 方案 A：固定字符暴力切分（反面示例）

切块 1（前 70 字符）：
```text
| 机房编号 | 节点类型 | CPU 峰值负载 | 内存使用率 |
| :--- | :--- | :--- | :---
```
切块 2（后续字符）：
```text
| BJ-01 | 计算型-C8 | 89.5% | 76.2% |
| BJ-01 | 存储型-S5 | 32.1% | 94.8% |
```
**问题**：当用户查询“BJ-01 存储节点的内存使用率是多少”时，切块 2 缺少列头“内存使用率”，BM25 无法匹配该关键词，稠密向量也难以确定 `94.8%` 的具体属性。

#### 方案 B：行级序列化（Row-wise Serialization，推荐）

以每一行为切分单元，将表头字段作为键、单元格内容作为值，组装为自包含文本：

```text
[表格：服务器资源利用率监控表]
机房编号: BJ-01 | 节点类型: 计算型-C8 | CPU 峰值负载: 89.5% | 内存使用率: 76.2%
---
[表格：服务器资源利用率监控表]
机房编号: BJ-01 | 节点类型: 存储型-S5 | CPU 峰值负载: 32.1% | 内存使用率: 94.8%
```
此时每个文本块都保留了完整的字段名与数值对应关系，无论关键词检索还是语义向量计算，均能匹配。

#### 方案 C：双层索引（Parent-Child / Summary Index）

针对整张复杂报表，生成一份结构化摘要：
- **子检索层（Child Chunk）**：索引自然语言摘要（例如：“该表统计了北京 BJ-01 与上海 SH-02 机房的各类型节点 CPU 与内存使用率”）或行级序列化文本，供检索召回；
- **父填充层（Parent Chunk）**：命中后，将整张完整的 Markdown 表格或 HTML 片段注入 Prompt 上下文，供大模型进行综合横向与纵向对比。

## 3. 代码块切分：基于 AST 的语法树切块与上下文补全

代码并非普通自然语言，其语法结构（作用域、缩进、嵌套括号）具有强约束。若按行数或段落机械切分，容易将函数在循环体中腰斩，丢失外层签名与依赖。

### 机械切分 vs AST 语法切分

- **按固定行数切分**：切断在 `try...except` 块中间或 `if` 分支内，前一个切块丢失异常处理逻辑，后一个切块丢失函数参数与局部变量定义，导致生成的向量残缺不全。
- **基于 AST（抽象语法树）切分**：使用 Tree-sitter 等多语言语法解析器，将代码解析为树形结构，以类（`class_definition`）、函数或方法（`function_definition`）为切分边界。

### 上下文注入机制

切分出单个函数后，若脱离所属文件与类，模型仍可能不清楚其调用的全局变量或库。工程中常在每个代码切块前部显式注入元数据头：

```python
# 经过 AST 切分并注入上下文的代码切块示例
"""
[上下文注入元数据]
文件路径: services/auth/jwt_handler.py
依赖模块: import jwt; from datetime import datetime, timedelta
所属类: class TokenManager
"""

def verify_token(self, token: str) -> dict:
    """验证传入的 JWT 令牌并返回 Payload"""
    try:
        payload = jwt.decode(token, self.secret_key, algorithms=["HS256"])
        return payload
    except jwt.ExpiredSignatureError:
        raise AuthenticationFailed("Token has expired")
    except jwt.InvalidTokenError:
        raise AuthenticationFailed("Invalid token")
```

通过拼接文件路径、关键导入与所属类，当用户检索“JWT 过期抛出什么异常”时，关键词（`jwt`, `ExpiredSignatureError`）与类级别的上下文均可被完整捕捉。

## 4. 图像与图表检索：文本代理 vs 端到端多模态检索

文档中的架构图、时序图、流程图和扫描件无法直接被文本 Tokenizer 处理。当前主要有两条工程落地路径：

| 对比维度 | 路线 1：文本代理检索（主流工程方案） | 路线 2：端到端多模态 Embedding | 
| :--- | :--- | :--- | 
| **工作原理** | 离线调用 OCR 提取文本，配合 VLM 生成描述性 Caption，统一写入文本向量库 | 使用多模态模型（如 CLIP、ColPali）直接将图像像素映射到向量空间 | 
| **索引库要求** | 复用现有文本检索体系（BM25 + 稠密向量库） | 需要向量数据库支持高维多模态向量或多向量（Multi-vector）检索 | 
| **小字与数据表现** | 依靠专用 OCR 引擎，数字与文字识别精确度高 | 依赖图像编码器，小字与低对比度文字易受缩放与分辨率压缩影响 | 
| **成本与开销** | 写入时一次性推理，检索阶段仅有文本匹配开销 | 图像向量存储量大，多模态推理与交互计算成本较高 | 
| **适用场景** | 包含大量文字、指标的技术文档、合同、报表截图 | 纯图形资产检索、对版式结构极敏感的图文检索 | 

### 工业落地的文本代理处理流程

1. **解析提取**：文档解析阶段抽取图片文件，调用 OCR 引擎获取文字内容，同时通过视觉语言模型（如 GPT-4o-mini 或开源轻量 VLM）生成摘要（Caption）。
2. **组合切块**：将 `[图片描述: ...] + [图中文字: ...]` 拼装为文本块存入数据库，元数据中记录原图 URL 或对象存储路径。
3. **检索与召回**：用户输入文本 Query 时，通过常规文本检索命中该代理切块；在生成回答时，将原图以图片输入形式或 Markdown 图片链接返回给模型与前端。

## 5. 混合文档切分与上下文跨块拼接

当 Markdown 文档中交替出现正文、列表、表格和插图时，如果生硬截断，常常破坏自然语言的上下文依赖，例如上一段写“具体参数见下表：”，而表格已经被分到了下一个独立切块中。

### 解决上下文断裂的工程策略

1. **显式指代解析（Contextual Anchoring）**：在预处理解析 AST 时，将具有相对指代的词（如“如下图所示”、“下表中的指标”）补充具体锚点信息，如自动替换为“如 [系统架构图-图2] 所示”。
2. **父子文档关联（Parent-Child Indexing）**：
   - **Child Chunk（子块）**：细粒度的表格行、代码方法、图片 Caption，长度一般在 100~300 Token，便于向量模型提取精准的局部特征；
   - **Parent Chunk（父块）**：包含该元素的完整二级/三级标题章节，长度在 800~1500 Token；
   - 检索时使用 Child Chunk 计算相似度，命中后根据元数据中的 `parent_id` 提取 Parent Chunk 注入到大模型的 Prompt 中，保证模型看到完整的上下文论述。
3. **受结构约束的滑动窗口（Boundary-aware Overlap）**：常规滑窗按 Token 数硬截断，而在解析 Markdown 时，重叠窗口应当对齐语法边界：遇到代码块围栏（` ``` `）或表格结束符时，窗口必须延伸至语法闭合处，不得中途截断。

关于文本块大小与重叠窗口的定量配置与权衡，我们在下一讲 [/interview/rag-interview/chunk-strategy.md](/interview/rag-interview/chunk-strategy.md) 与 [/interview/rag-interview/rag-chunk-size-overlap.md](/interview/rag-interview/rag-chunk-size-overlap.md) 中展开分析。

## 6. 面试深度追问与常见认知误区

### 追问 1：如果文档里有一张 50 列的大宽表，无法直接序列化成一行，该怎么处理？

**回答要点**：
- **列分组（Column Grouping）**：先固定主键列（如“员工编号、姓名”），再按业务属性拆分为若干垂直子表（如“基本信息组”、“薪资绩效组”、“社保公积金组”）分别序列化；
- **路由至 Text-to-SQL / 数据库分析工具**：超大规模结构化数据不适合强行切碎存入向量库。可在预处理阶段将其提取为 SQLite / DuckDB 内存表或 CSV，在检索管道中配置意图路由，遇到全局汇总、排序或多条件过滤问题，通过 Text-to-SQL 或结构化查询接口执行。

### 追问 2：为什么不建议用大模型对所有代码文件全量生成自然语言描述来检索？

**回答要点**：
- **成本与耗时**：几十万行代码的工程项目全量调用 LLM 生成摘要，耗时漫长且 Token 成本极高；
- **细节平滑与漂移**：大模型的概括性描述容易抹平具体的局部变量名、内部错误码与特定 API 参数。而在代码排障与工程检索中，开发者经常直接搜索具体的异常类或函数签名，保留原始代码并配合 BM25 稀疏检索往往比纯自然语言描述更准确。

### 常见错误认知与纠错

| 常见错误说法 | 真实底层机制 | 修正方案 |
| :--- | :--- | :--- |
| “把 Markdown 表格转换成纯文本空格对齐，模型就能看懂” | 纯文本连续空格在多数 Tokenizer 中会被合并或拆成单字符 Token，导致行间错位 | 转换为具备显式键值结构的 JSON、Markdown 或键值对文本 |
| “多模态 RAG 就是把图片直接喂给大模型做 Embedding，不需要 OCR” | 通用多模态嵌入模型对低对比度文字、表格细粒度数字的分辨率有限 | 结合 OCR 提取关键文本与参数，与图像语义描述共同入库 |
| “代码切块直接按行数固定切，只要 Overlap 设置大一点就不会丢逻辑” | 代码作用域受语法缩进和括号约束，机械换行会造成语法闭包截断 | 基于 AST 节点边界切分，或按类/函数边界切分 |
