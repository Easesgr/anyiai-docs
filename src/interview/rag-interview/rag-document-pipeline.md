在检索增强生成（RAG）系统中，在线检索的召回质量和生成准确度，直接受离线数据预处理阶段的影响。如果切入向量数据库的文本块存在格式乱码、上下文指代断裂、缺失结构路径或脏数据残留，在线检索阶段的重排序与模型提示词很难弥补这些信息缺失。

在上一讲[/interview/rag-interview/rag-pipeline.md](/interview/rag-interview/rag-pipeline.md)中，我们了解了 RAG 的整体运转机制。本篇聚焦离线文档处理流水线，说明一份原始文档如何经过解析、清洗、分块、富化、向量化并安全写入向量存储。关于异构文档的解析细节，可参考[/interview/rag-interview/rag-multiformat-parsing.md](/interview/rag-interview/rag-multiformat-parsing.md)；切块长度与重叠窗口调优可参考[/interview/rag-interview/rag-chunk-size-overlap.md](/interview/rag-interview/rag-chunk-size-overlap.md)。

## 1. 核心口述答案：文档预处理的六个阶段

在面试中被问及“RAG 文档处理流水线如何设计”时，可以按照以下六个阶段结构化表达：

> **面试口述要点**：
> 典型的 RAG 离线文档预处理流水线分为六个连续处理阶段：
> 1. **文档解析（Parsing）**：读取 PDF、Word、HTML 等源文件，提取出纯文本并尽可能还原标题大纲、段落与表格的层级关系。
> 2. **数据清洗（Cleaning）**：执行 Unicode 标准化（如统一转为 NFC 格式）、剔除不可见控制字符、修复断行连字符，并规范化段落间距。
> 3. **分块建模（Chunking）**：根据句子边界或段落层级将文本切片。为缓解小切片语义不足与大切片主题发散的矛盾，常采用 Parent-Child（父子节点）层次切分。
> 4. **元数据富化（Metadata Enrichment）**：为每个分块附加全局文档 ID、章节层级路径（面包屑）、时间戳与权限分类，支持多维过滤与上下文补充。
> 5. **批量向量化（Batch Embedding）**：按照模型单次处理的 Token 上限组合批次，通过并发控制和重试机制完成向量计算。
> 6. **幂等写入与索引（Idempotent Upsert）**：通过生成确定性分块主键与版本标记，写入向量索引和全文倒排索引，并清理同一文档旧版本产生的遗留分块。

![文档预处理流水线六个核心阶段拓扑流](/images/content-rebuild/eba718f5f17c4406/fig-1.png)

为了让整套流程更清晰，我们以一份《企业云平台运维手册.pdf》为例贯穿后续各个处理环节：该文档包含多级目录（如“第二章 存储系统 > 2.3 数据冷备份”）、代码配置清单、版本更新日期，以及因 PDF 排版产生的断行连字符。

## 2. 数据清洗：编码对齐与不可见字符处理

文档解析器提取出的原始文本往往夹杂格式控制字符与排版断词。如果不做清洗直接送入分词器（Tokenizer），会导致分词碎片化，进而影响后续的向量生成质量。

### 2.1 Unicode 规范化
同一个人类可读字符在 Unicode 中可能有多种表示形式。例如带声调的字母 `é`，可以由单码点 `\u00e9`（NFC 形式）表示，也可以由字母 `e` 加组合重音符 `\u0065\u0301`（NFD 形式）表示。如果知识库中同一词汇的编码方式不同，在某些词表映射和字符级精确匹配中就会被判定为不同字符。因此，清洗第一步通常使用标准库进行 `NFC` 规范化。

### 2.2 控制字符与断词修复
常见的数据噪声包括：
- **零宽字符**：如零宽空格（`\u200b`）和零宽不连字（`\u200c`），可能造成分词异常。
- **软连字符与换行断词**：PDF 排版为对齐文本行，常会在行尾单词中插入连字符和换行符，例如把 `back-\nup` 拆开，需将其恢复为完整的 `backup`。
- **连续空白与换行**：水平空白（制表符、多个空格）需合并为一个空格；连续空行需受控压缩，但应保留单个段落换行，避免破坏后续依靠换行切分的段落逻辑。

```python
import re
import unicodedata

def clean_text_pipeline(raw_text: str) -> str:
    # 1. 规范化为 NFC 格式，保证等价字符编码一致
    normalized = unicodedata.normalize("NFC", raw_text)
    
    # 2. 移除不可见控制字符，保留换行(\n)与制表符(\t)
    cleaned = re.sub(r"[\x00-\x08\x0b\x0c\x0e-\x1f\x7f\xad\u200b-\u200f]", "", normalized)
    
    # 3. 修复换行断词：将 "back-\nup" 还原为 "backup"
    cleaned = re.sub(r"(\w+)-\n(\w+)", r"\1\2", cleaned)
    
    # 4. 压缩多余水平空白为单个空格
    cleaned = re.sub(r"[\t\f\r ]+", " ", cleaned)
    
    # 5. 将 3 个及以上的连续换行压缩为 2 个换行，保留段落边界
    cleaned = re.sub(r"\n{3,}", "\n\n", cleaned)
    
    return cleaned.strip()
```

## 3. 分块策略：父子节点（Parent-Child）关系建模

切块长度存在权衡：
- **切块过小（如 100~200 Token）**：向量更容易聚焦在具体实体或单一概念上，向量检索匹配精准，但送给大语言模型时容易缺少上下文因果，导致模型回答不完整。
- **切块过大（如 1000~2000 Token）**：虽然包含足够的上下文，但切块内往往涵盖多个主题，向量表征被多处信息平均化，反而降低了特定关键词检索的命中率。

针对这个矛盾，工程中常用的一种方案是 **Parent-Child（父子节点）** 层次分块机制。

### 3.1 层次数据结构
在切分阶段，流水线执行两层切分：
1. **父节点（Parent Node）**：按长段落或章节切分，保留较大篇幅（例如 800~1500 Token），用于承载完整上下文。
2. **子节点（Child Node）**：由父节点进一步细切而成，保留较小篇幅（例如 200~400 Token），相邻子节点之间可设置 10%~15% 的重叠窗口（Overlap），用于高精度向量匹配。

```json
{
  "child_chunk_id": "doc_001_p3_c1",
  "parent_chunk_id": "doc_001_p3",
  "doc_id": "manual_cloud_ops_2024",
  "chunk_index": 1,
  "page_span": [12, 13],
  "text": "在进行对象存储冷备份时，需使用 rsync 工具配合 --checksum 参数核验哈希值...",
  "is_leaf": true
}
```

![Parent-Child 分块数据结构与映射检索流](/images/content-rebuild/eba718f5f17c4406/fig-3.png)

### 3.2 离线存储与在线回溯
- **离线入库**：仅对细粒度的子节点计算 Embedding，并将其存入向量索引；粗粒度的父节点全文则保存在文档存储（如 MongoDB、关系型数据库或向量库的元数据 Payload 字段）中，不需要为其构建昂贵的向量索引。
- **在线检索**：系统根据提问在向量库中召回 Top-K 个相关子节点，随后根据子节点的 `parent_chunk_id` 聚合并去重，取出对应的父节点完整文本，拼接进提示词送给大模型生成回答。更多切分策略原理可参考[/interview/rag-interview/chunk-strategy.md](/interview/rag-interview/chunk-strategy.md)。

## 4. 元数据富化：章节路径与属性注入

如果文本分块脱离了所属文档的章节背景，单独看一句话容易产生歧义。例如分块中只有一句话：“故障时需立刻执行降级开关”，如果没有标题说明这是属于“支付交易核心模块”还是“用户打卡模块”，语义向量就会发生偏离。

### 4.1 层级路径（面包屑）注入
在遍历文档大纲树时，维护一个当前层级标题栈。切分每个分块时，将面包屑路径显式拼接在文本前端，作为向量化输入的一部分：

$$\text{待向量化文本} = \text{"【路径：企业运维手册 > 数据库 > 容灾方案】 "} + \text{分块正文}$$

这种做法让通用 Embedding 模型在计算稠密向量时，包含了该分块所处的全局主题信息，有助于区分同名但不同场景的业务规则。

![层级路径注入与元数据富化流程](/images/content-rebuild/eba718f5f17c4406/fig-4.png)

### 4.2 常用元数据载荷（Payload）设计

在分块入库时，需要记录结构化元数据以支持精确条件过滤（机制详解见[/interview/rag-interview/rag-metadata-filtering.md](/interview/rag-interview/rag-metadata-filtering.md)）：

| 字段名 | 类型 | 用途说明 |
| :--- | :--- | :--- |
| `doc_id` | string | 文档唯一标识，用于按文档生命周期批量更新或下线 |
| `doc_hash` | string | 原始文档 SHA-256 哈希，用于内容比对，跳过未修改文档 |
| `breadcrumb` | array[string] | 章节路径列表，如 `["存储系统", "数据冷备份"]` |
| `version` | int | 文档迭代版本号，用于蓝绿切换与孤儿数据清理 |
| `created_at` | int64 | 发布时间戳，用于按时间范围过滤或时效性打分 |
| `department` | string | 部门或权限标签，用于多租户与权限隔离过滤 |

## 5. 批量向量计算与幂等写入机制

完成清洗、分块与元数据组装后，流水线进入批量向量化与存储入库阶段。面对偶发的网络抖动、模型服务限流或单节点宕机，该阶段需具备批量调用优化和幂等重试能力。

### 5.1 受控批量向量化（Batch Embedding）
频繁发送单个字符串的 HTTP 请求会带来可观的网络握手开销并容易触碰接口 QPS 限制：
- **Token 预算控制**：按照模型支持的最大批次（如每次最多 32 个分块，或总 Token 不超过 8192）动态合并请求。
- **带抖动的指数退避重试**：遇到 429（限流）或 503（服务瞬时不可用）时，等待时间采用指数级增加并叠加随机波动（Jitter），防止所有重试请求在同一时刻再次冲击服务端。

### 5.2 确定性主键与版本清理机制

如果重新处理一份文档时，每次都随机生成 UUID 作为分块主键，旧分块就会残留在向量数据库中（即“孤儿分块”），导致检索召回过时或矛盾的信息。

实现数据一致性更新的常见做法：
1. **确定性主键生成**：为支持蓝绿版本隔离写入，分块主键需纳入版本号（或内容哈希）与位置序号：
   $$\text{Chunk ID} = \text{SHA-256}(\text{doc\_id} + \text{"\_v"} + \text{version} + \text{"\_"} + \text{chunk\_index})$$
   带版本的主键能确保新版本分块作为独立记录写入，避免原地覆盖正在对外服务的旧版本数据。
2. **换版与孤儿清理**：
   若新版本文档分块数发生变化（如从 10 块缩减为 6 块）或切分边界变动，新版本（如 `version: 2`）在新主键空间下完整写入并校验通过后，再将检索流量切换至新版本，随后执行异步范围删除：
   - 清理过期数据：`DELETE WHERE doc_id = 'manual_001' AND version < 2`。
   若主键不包含版本号（仅按 `doc_id + "_" + chunk_index` 原地覆写），写入中途若崩溃将导致新旧数据错位混杂，无法实现零停机的版本隔离。
3. **短路跳过**：在流水线最开始比对文件全局 SHA-256，若与库中文档指纹一致且处理参数未变，直接跳过处理。更多增量同步策略见[/interview/rag-interview/vector-db-incremental.md](/interview/rag-interview/vector-db-incremental.md)。

## 6. 面试深度追问与常见认知误区

### 追问 1：如果一个长文档包含 500 个分块，写入第 480 个时 Worker 进程异常崩溃，系统如何恢复？如何避免检索脏数据？

**回答要点**：
- **状态机与断点记录**：文档处理任务交由带持久化能力的任务调度系统（如 Temporal、Celery 或自研任务表）管理，将状态拆分为 `PARSED`、`CHUNKED`、`INDEXING`、`ACTIVE`。任务异常重启后，可根据已落盘的分块进度继续处理，无需从头重跑。
- **可见性状态翻转**：在入库时，分块的元数据标记为 `status: "indexing"`。在线检索接口强制配置过滤条件：`status == "active"`。当且仅当 500 个分块全部写入完成后，再执行一条元数据批量更新，将属于该 `doc_id` 且对应新版本批次的所有分块状态翻转为 `active`，并废弃或物理删除旧版本分块。这样在写入中途崩溃时，未完成的新切片不会对在线查询可见，旧版本数据也不会提前被破坏。

![分布式崩溃恢复与事务可见性翻转机制](/images/content-rebuild/eba718f5f17c4406/fig-6.png)

### 追问 2：为什么不建议把模型生成的几百字长摘要，直接完整拼在正文分块前面去计算 Embedding？

**回答要点**：
- **均值池化（Mean Pooling）的稀释效应**：常见的文本 Embedding 模型在 Transformer 最后一层通常采用均值池化，即对整个序列的所有 Token 向量求平均来生成最终句向量。如果拼接过长的主观摘要，摘要中的虚词、总结性句式和高层概念词会占据大量 Token 比重。均值池化后，向量重心会偏向宏观概括，正文切片中具体的错误代码、特定参数和生僻实体名词在向量中的权重相对被拉低，导致用户针对具体细节查询时，余弦相似度匹配分数下滑。
- **替代方案**：将摘要放在元数据中，或者单独建立一条摘要的向量与全文倒排索引。在混合检索阶段，分别根据摘要与正文进行多路召回，再通过重排序（Rerank）融合打分，避免单一向量承载过多不同尺度的信息。

### 常见错误认知清单

1. **“向量库支持 Upsert 就等于实现了文档更新幂等”**：
   - **事实**：如果新文档切出的分块数量少于旧版本，或者切分切入点改变导致分块哈希变化，仅用 Upsert 会残留旧版本的尾部分块。必须配合按 `doc_id` 的版本清理或预先清空机制。
2. **“清洗时把所有换行符替换为空格，向量匹配最平滑”**：
   - **事实**：段落换行符（`\n\n`）是文档自然的语义终止符。如果粗暴将全部换行符替换为空格，切分算法就无法感知自然的段落边界，容易把上下文完全无关的相邻段落拼进同一个切片中。
3. **“Parent-Child 结构必须搭建两套独立的向量数据库”**：
   - **事实**：Parent 节点主要用于向大模型提供完整上下文，通常按 ID 直接读取，并不需要执行相似度搜索。Parent 节点保存在普通的文档数据库、对象存储或向量库自带的 Payload/元数据中即可，无需承担两份 HNSW 向量索引的内存开销。
