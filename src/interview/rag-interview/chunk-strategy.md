在检索增强生成（RAG）系统中，文档切分（Chunking）是把长文本拆解为若干独立片段的预处理步骤。随着大语言模型上下文窗口扩展到 128k 甚至 1M Token，很多开发者常问：既然模型能装下整篇文档，为什么不把完整文档直接拼进提示词，或者直接对整篇长文档提取一个向量？

本文结合推理硬件开销、密集向量表征能力与检索信噪比，梳理文档切分的因果机制与工程边界。

## 1. 核心口述答案

在面试中被问到“文档切分为什么重要？不切分直接塞进长上下文或直接整篇向量化会有什么后果？”时，可按以下三个核心点回答：

> **核心口述回答：**
>
> 文档切分是在**向量检索的区分度**与**生成阶段的语境完整性**之间寻找平衡，主要由三方面原因决定：
>
> 1. **向量表征的局部特征稀释**：主流嵌入模型输出固定维度向量（如 768 或 1536 维）。若把上万字长文做均值池化压入一个向量，局部微观事实（如具体参数、数字）所占权重极低，在余弦相似度计算中容易被全局背景词掩盖，导致精准检索召回率下降。
> 2. **模型推理的延迟与显存开销**：在预填充（Prefill）阶段，自注意力机制的浮点计算量通常随序列长度呈二次方趋势增长；在解码（Decode）阶段，KV Cache 显存占用随有效上下文长度线性增长。全量输入长文本会导致首字时间（TTFT）大幅延长，并显著降低系统的并发吞吐。
> 3. **检索信噪比与注意力干扰**：文本块过大会带入大量无关信息，引发模型在长上下文下的注意力分散或中间信息遗忘；文本块过小则容易切断主语、转折与生效条件，导致模型断章取义。
> 
> 切分并非单纯的字符截断，而是根据模型上下文预算与检索单元，重构高密度的有效信息输入。

## 2. 推理计算与显存约束：为什么不能全量拼入长上下文？

以一份 8,000 字的《服务治理与熔断规范》为例，其中包含上百条跨模块约定，而用户仅询问其中一句：“网关层熔断阈值是多少？”。若不切分直接将全量文档注入提示词，系统在推理时会遇到两重硬件开销约束。

### 2.1 预填充（Prefill）阶段的注意力计算量

在模型处理输入提示词的预填充阶段，标准多头自注意力机制（Multi-Head Attention）的核心计算为：

$$\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V$$

长度为 $L$ 的序列在进行 Query 与 Key 矩阵内积时，注意力矩阵的运算规模为 $[L, L]$。在全注意力设定下，计算复杂度通常呈 $\mathcal{O}(L^2)$ 增长。FlashAttention 等底层算子优化降低了显存读写（IO）开销，但并未普遍改变全注意力的理论浮点运算量（FLOPs）。

当单次请求输入的上下文从 $2\text{k}$ Token 扩大至 $32\text{k}$ Token 时，内积阶段的计算量扩大为原来的 256 倍。这会使处理提示词的计算耗时显著增加，首字响应时间（Time to First Token, TTFT）变长，难以满足低延迟交互要求。

### 2.2 解码（Decode）阶段的 KV Cache 显存占用

在模型逐字生成回答的解码阶段，为了避免重复计算历史 Token 的 Key 和 Value，推理引擎会将它们的隐层张量保存在显存中（即 KV Cache）。其显存占用计算公式如下：

$$\text{Memory}_{\text{KV}} = 2 \times 2 \times n_{\text{layers}} \times n_{\text{kv\_heads}} \times d_{\text{head}} \times L \quad (\text{Bytes})$$

*参数说明：第一个系数 $2$ 代表 Key 与 Value 两个张量；第二个系数 $2$ 表示使用 16 位浮点数（FP16/BF16，每个数值占 2 字节）；$n_{\text{layers}}$ 为网络层数；$n_{\text{kv\_heads}}$ 为 Key/Value 头数；$d_{\text{head}}$ 为单头隐藏层维度；$L$ 为总上下文长度。*

**算例推导（以未启用 GQA 的标准 MHA 架构为例）：**

假设模型为 32 层、32 个注意力头（即 $n_{\text{kv\_heads}}=32$）、单头维度 $d_{\text{head}}=128$：

若未切分长文档使单请求上下文长度达到 $L=32,768$ Token，其在解码阶段占用的 KV Cache 显存约为：

$$\text{Memory}_{\text{KV}} = 4 \times 32 \times 32 \times 128 \times 32,768 \approx 17.18 \text{ GB}$$

这意味着单个并发请求就需要占用超过 17 GB 的显存。如果改为通过切分检索，仅提取 4 个高相关的切块（如 $4 \times 512 = 2,048$ Token），单请求的 KV Cache 显存则降为约 1.07 GB，系统可服务的并发请求数便大幅提升。

*注：在启用分组查询注意力（GQA，如 $n_{\text{kv\_heads}}=8$）的模型中，显存会按头数比例下降，但 KV Cache 显存占用随有效上下文长度 $L$ 线性增长的规律依然成立。*

## 3. 密集向量表征瓶颈：为什么不能整篇长文本生成一个向量？

除了生成阶段的推理开销外，另一个关键瓶颈在检索阶段的密集向量表示上。具体原理可参考 [Embedding 在 RAG 中的核心机制](/interview/rag-interview/embedding-in-rag.md)。

### 3.1 均值池化（Mean Pooling）下的微观特征稀释

主流双塔文本嵌入模型通常将 Token 的隐层状态通过加权或均值池化汇总为单一向量 $\mathbf{v}_{\text{doc}}$：

$$\mathbf{v}_{\text{doc}} = \frac{1}{N} \sum_{i=1}^N \mathbf{h}_i$$

回到前文贯穿案例：假设在 8,000 Token 的技术文档中，包含关键规则：“*网关层熔断超时阈值设为 450ms*”，该句占约 15 个 Token。

在全文均值求和中，这 15 个 Token 的特征权重仅占约：

$$\frac{15}{8000} \approx 0.19\%$$

剩余 $99.81\%$ 的权重均被整篇文档通篇出现的主题词（如“系统、高可用、集群、配置、负载均衡”）所占据。当用户发起细粒度查询：“*网关层熔断超时阈值是多少？*”时，查询向量与该短句的特征具有高度相关性；但在计算查询向量与全文向量 $\mathbf{v}_{\text{doc}}$ 的余弦相似度时，局部的微观特征被全局主题特征淡化，导致该文档在检索排序中得分落后，未能进入 Top-K 召回结果。

分块处理后，包含该规则的切块长度若为 256 Token，该规则的权重占比提升至约 $5.8\%$，与查询向量的相似度区分度显著增强。

![固定维度向量平均池化长文本导致的局部微观事实稀释过程图](/images/content-rebuild/850fb6ef750e3520/fig-3.png)

## 4. 检索信噪比：过大切块与过小切块的双向问题

文档切分并不是切得越碎越好，而是在“检索信噪比”与“语境完整性”之间做折中。

| 切分粒度 | 典型取值 | 检索侧表现 | 生成侧表现 |
| :--- | :--- | :--- | :--- |
| **切块过大** | $2000 \sim 4000$ Token | 向量偏向文档宏观主题，对局部细粒度属性的区分度减弱。 | 注入较多无关上下文，信噪比降低；容易加重注意力衰减并增加模型产生幻觉的概率。 |
| **切块过小** | $20 \sim 50$ Token | 容易因为零散关键词的字面重合出现误召回；缺乏足够的语义限定词。 | 上下文被截断。主语丢失（代词悬空）、转折与前置生效条件缺失，容易误导大模型给出断章取义的回答。 |

### 4.1 语义依赖截断示例

考察以下规范文本：
> “*在满足所有前置审核通过的前提下，管理员方可执行批量销毁操作；严禁在未做数据冷备份前触发该接口。*”

若采用固定 30 字符进行机械切分，文本可能被拆分为：
*   **切块 A**：“*在满足所有前置审核通过的前提下，管理员方可执行批量销毁操作；*”
*   **切块 B**：“*严禁在未做数据冷备份前触发该接口。*”

当用户询问：“*管理员可以直接执行批量销毁吗？*”，系统仅召回了切块 A。大语言模型在缺少切块 B 约束的前提下，很可能会给出“可以执行”的肯定答复。切块粒度过小带来的语义隔离，破坏了命题的完整逻辑条件。

## 5. 切分粒度对 Top-K 召回覆盖范围的影响

在 RAG 系统中，输入给大模型的上下文通常受限于提示词预算上限，假设允许注入的上下文预算为 $B$（例如 $B=2048$ Token）。在[确定 Top-K 召回参数](/interview/rag-interview/rag-topk.md)时，单块大小 $S$ 与召回数量 $K$ 满足乘积约束：

$$K \approx \frac{B}{S}$$

切块大小直接影响检索结果覆盖不同知识源的广度：

### 5.1 覆盖源上限的权衡

*   **大块方案**（如 $S=1024$）：在固定预算下最多召回 $K=2$ 块。若用户的复合问题（如“对比 A 方案与 B 方案在不同集群下的网络与存储配置差异”）需要跨越文档库中 4 处分散事实，召回 2 块在物理容量上无法覆盖全部所需依据。
*   **适中切块方案**（如 $S=256$）：在相同预算下可容纳 $K=8$ 块，能容纳更多分散的证据片段，提升跨段落、跨章节问题的多源整合能力。

### 5.2 重叠窗口（Overlap）的作用与边界

为了缓解机械切分刚好在关键句子中间“腰斩”的问题，工程上通常设置相邻块之间的重叠率 $\alpha$（Overlap Ratio，通常设为 $10\% \sim 20\%$）。相邻两个切块之间的移动步长（Stride）为：

$$\text{Stride} = S \times (1 - \alpha)$$

重叠区域为切分点两侧的短语提供了缓冲区，降低了短句被边界拦腰截断的概率。但需要明确，单纯的重叠滑动无法解决跨越数百字乃至跨章节的远距离指代或前置依赖问题，长程逻辑仍需结合结构化切分策略解决。

## 6. 面试深度追问与常见误区

### 追问 1：长上下文大模型窗口已达 1M Token，为什么工业落地仍普遍保留分块？

*   **响应延迟与计费成本**：全量输入 100k 以上 Token，Prefill 耗时以秒级递增，商业 API 计费通常按输入 Token 线性计费，单次交互成本成倍上升。
*   **注意力分散与中间位置遗忘**：多项长文本评测显示，当相关信息夹杂在大量无关上下文的中间区域时，模型的检索与抽取准确率容易出现不同程度的下降。
*   **动态更新维护成本**：如果将几十篇长文档原样喂给大模型，一旦其中某个段落发生变更，依赖全量拼接的缓存或索引就需要整体重置；采用分块后，只需更新发生变化的切块向量，降低了维护开销。

### 追问 2：小块利于向量精确检索，大块利于模型理解语境，工程上如何兼顾？

*   **解答**：核心思路是**解耦“检索单元”与“生成单元”**：
    *   **父子切分（Parent-Child / 层次化分块）**：先将文档切分为较大父块（如 1024 Token），再将父块细分为若干重叠子块（如 256 Token）。向量数据库中仅对子块构建索引。检索时命中子块后，通过子块保存的 `parent_id` 自动取回其所在的完整父块，将父块文本注入给 LLM。
    *   **句子窗口检索（Sentence Window Retrieval）**：以单句或极短片段建立向量索引，检索命中后，通过元数据动态向前后各扩展若干个句子，拼接成具备完整语义的上下文递交给大模型。

![面试场景中讲解员梳理小块检索与大块阅读解耦的父子切分架构图](/images/content-rebuild/850fb6ef750e3520/fig-6.png)

### 常见认知误区辨析

*   **误区 1：“Embedding 模型支持最大 8192 Token，因此 chunk_size 设为 8192 最合适。”**
    *   *辨析*：支持 8192 Token 仅说明模型位置编码和注意力层在此长度内能完成前向传播且不报错，并不代表其池化向量能等比例保留 8192 Token 内的微观细节。均值池化对微观事实的稀释效应依然存在。
*   **误区 2：“分块大小存在统一的黄金参数（例如必须设为 512）。”**
    *   *辨析*：512 只是针对 BERT 类模型的历史习惯值，而非通用标准。切分粒度应由业务文档的行文结构决定。例如，API 参考文档宜按接口定义或 Markdown 标题分块，法律条款宜按法条条款分块。具体选型可参见 [RAG 文档切分策略体系](/interview/rag-interview/rag-chunk-strategies.md) 与 [chunk_size 和 overlap 设置实操](/interview/rag-interview/rag-chunk-size-overlap.md)。

## 总结与延伸阅读

文档切分不仅是为了规避硬件显存与延迟瓶颈，更是为了提高密集向量对微观事实的表征敏锐度，并在上下文预算限制下平衡信噪比与覆盖源广度。
