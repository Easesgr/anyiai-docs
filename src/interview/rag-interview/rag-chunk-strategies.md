在检索增强生成（RAG）管道中，原始文档不能直接作为单一单元入库。切分（Chunking）的核心目标是在**检索单元的聚焦度**与**生成上下文的完整度**之间取得平衡。上一讲我们在 [文档切分为什么重要？](/interview/rag-interview/chunk-strategy.md) 中分析了分块对检索信噪比的决定性影响。本篇将系统剖析四种主流切片策略的工作机制、优缺点以及选型边界。

## 1. 核心口述答案：四种切分策略的技术全景与选型原则

在面试中被问及“RAG 中有哪些切分策略，如何选型”时，可以按照以下结构口述回答：

> “文本切分策略主要有四种实现路径：
>
> 1. **固定长度切分（Fixed-size Chunking）**：按固定的字符数或 Token 数机械滑窗切割。计算速度最快、内存开销极低，但容易切断专业词汇和句法结构，主要用于基准测试或无格式纯文本的快速原型验证。
> 2. **递归字符切分（Recursive Character Chunking）**：设置层级分隔符列表（如段落、单换行、标点），优先在自然语义边界断开，单个片段超长时才递归使用下一级分隔符。这是大多数通用文本的首选基线方案。
> 3. **语义切分（Semantic Chunking）**：先按单句切分并向量化，通过计算相邻句子的余弦距离突变点来确定分块边界。切块内的语义主题内聚，但引入了额外的 Embedding 计算开销与延迟，且切出的块大小不易均匀控制。
> 4. **父子层级切分（Parent-Document / Small-to-Big）**：将文档切分为小子块与大父块，向量数据库仅存储小子块用于保证检索召回精度；检索命中后，通过元数据指针回溯拉取对应的大父块，送入大语言模型以保证回答上下文的完整性。
>
> **选型原则**：通用文本默认采用**递归字符切分**；对上下文因果链依赖强的技术或规章文档采用**父子层级切分**；段落结构散乱且计算预算充裕的场景评估**语义切分**；代码与表格需配合专用 AST 或 Markdown 结构化解析器。”

## 2. 贯穿案例：分布式故障排查手册的切分对比

为了直观理解四种切分方式的差异，我们以一段典型的分布式系统运维文档为例：

```text
【原始文档片段】
### 故障现象：节点网络分区导致主从切换
当集群主节点发生网络分区故障时，RAFT 协议自动触发选举机制；经多数派节点投票，Node-02 成功晋升为新 Leader。
### 处置指令
1. 执行 `cluster nodes` 确认新拓扑状态。
2. 检查旧 Leader 的持久化日志是否同步。
```

我们看这四种策略如何对这段内容进行处理：
* **固定长度切分**：设定 35 字符无脑步进，实体“RAFT 协议”可能在中间被腰斩成“RA”和“FT 协议”，破坏检索 Embedding 的语义表征。
* **递归字符切分**：优先在 `### ` 标题与换行处切开，将“故障现象说明”与“处置指令”划分为两个自然段落块。
* **语义切分**：在单句向量化后发现，前一段讲述的是“主从选举原理”，后一段则是具体的“命令行操作命令”，两者在相邻余弦距离上出现波峰跳变，系统在此处切出主题分界线。
* **父子层级切分**：将整段故障手册作为一个 800 字的父块存储；在向量库中分别索引“网络分区主从切换”和“执行 cluster nodes 检查状态”两个 80 字的子块。用户搜索“怎么确认新 Leader 拓扑”时精准命中子块，实际喂给模型的则是整段包含原因与步骤的完整父块。

## 3. 固定长度切分（Character/Token Splitter）的盲区与断句瑕疵

固定长度切分通过滑动窗口长度 $L$（`chunk_size`）和相邻窗口步长重叠 $O$（`chunk_overlap`）机械推进指针。

### 字符切分与 Token 切分的底层差异

固定切分在工程实现上分为两类：
* **Character-level**：直接按编程语言中的字符串下标或 Unicode 字符切分。
* **Token-level**：先使用目标模型的 Tokenizer（如 `cl100k_base`、`o200k_base`）将文本编码为 Token ID 数组，按固定 Token 数量截断后再解码（Decode）回文本。

大语言模型与 [Embedding 向量模型](/interview/rag-interview/embedding-in-rag.md) 的上下文限制是基于 Token 计数的。如果按字符切分，中文字符在不同分词器下可能映射为 1 到 3 个 Token 不等，容易导致最终序列超限。按 Token 切分能锁定长度，但直接截断 ID 数组再解码时，可能会将词汇拆碎（如把一个多 Token 的专有名词或英文单词从子词中间拆开）。

### 断句截断示例

固定长度切分不感知自然语言的句法结构，其缺陷在于**边界硬截断**：

```text
【原始输入】
由于集群主节点发生网络分区故障，RAFT协议自动触发选举机制；经多数派节点投票，Node-02成功晋升为新Leader。

【chunk_size=27 字符, overlap=0 硬截断结果】
Chunk 1: "由于集群主节点发生网络分区故障，RAFT协议自动触发选"
Chunk 2: "举机制；经多数派节点投票，Node-02成功晋升为新Le"
Chunk 3: "ader。"
```

当动名词短语“选举机制”被切为“选”和“举机制”时，两端向量表征均会产生偏差：
1. Chunk 1 丢失了“选举”的完整谓语和宾语组合，句意未完。
2. Chunk 2 的首部出现残缺短语，削弱了与用户问题“RAFT 协议如何选出 Leader”的向量相似度。
3. 即便配置了 10%~20% 的 Overlap，重叠区也只能缓解单点截断，无法杜绝表格行破坏、代码块闭合标签撕裂等结构性损毁。在后续 [RAG 检索中的 chunk_size 和 overlap 设置](/interview/rag-interview/rag-chunk-size-overlap.md) 中我们会专门探讨参数权衡。

## 4. 递归字符切分（Recursive Character Chunking）的分隔符优先级设计

为了避免硬截断破坏语义，工程上通用的基线策略是**递归字符切分**（例如 LangChain 的 `RecursiveCharacterTextSplitter`）。

![递归字符切分的分层降级决策机制](/images/content-rebuild/c347849ba14e51e8/fig-2.png)

### 分隔符列表的逻辑关系

典型递归切分器的默认分隔符配置如下：

```python
separators = ["\n\n", "\n", "。", " ", ""]
```

这个列表的顺序体现了文本层级的包含关系：
1. `\n\n`（双换行）：代表段落边界。段落通常是表达单一完整论点的单元，优先在段落间切分能较好维持论点独立性。
2. `\n`（单换行）：代表列表项或意群行。如果在段落级别切分后内容依然超过 `chunk_size`，降级为在单行之间切分。
3. `。`（句号/终止符）：如果单行仍然超长，退化到单句边界切分。句子是语法层面的最小命题单位。
4. ` `（空格）：在西文字符或含空格文本中，避免拆散完整单词。
5. `""`（空字符）：兜底手段。当单个词或无空格长字符串（如长哈希串、无标点长文本）仍然超限时，退化为字符级截断，避免超出长度阈值。

### 递归切分算法逻辑实现

递归切分器处理文本的流程是一个自顶向下的分治与合并过程：

```python
def recursive_split_text(
    text: str,
    separators: list[str],
    chunk_size: int,
    chunk_overlap: int
) -> list[str]:
    """
    递归切分逻辑示例：
    1. 寻找当前文本中第一个匹配的高优先级分隔符；
    2. 按该分隔符拆分文本；
    3. 合并小片段，若单片段超长则递归降级。
    """
    final_chunks: list[str] = []
    if len(text) <= chunk_size:
        return [text]

    # 寻找当前文本中匹配的最高优先级分隔符
    chosen_sep = ""
    for s in separators:
        if s == "":
            chosen_sep = ""
            break
        if s in text:
            chosen_sep = s
            break

    # 降级到空字符时执行字符滑窗切分
    if chosen_sep == "":
        step = max(1, chunk_size - chunk_overlap)
        return [text[i : i + chunk_size] for i in range(0, len(text), step)]

    # 按所选分隔符拆分片段
    splits = text.split(chosen_sep)
    next_separators = separators[separators.index(chosen_sep) + 1 :]

    current_doc: list[str] = []
    total_len = 0

    for piece in splits:
        piece_len = len(piece)
        # 若单个片段本身超长，调用下一级分隔符对该片段递归切分
        if piece_len > chunk_size:
            if current_doc:
                final_chunks.append(chosen_sep.join(current_doc))
                current_doc = []
                total_len = 0
            sub_chunks = recursive_split_text(piece, next_separators, chunk_size, chunk_overlap)
            final_chunks.extend(sub_chunks)
            continue

        # 尝试合并片段
        sep_overhead = len(chosen_sep) if current_doc else 0
        if total_len + sep_overhead + piece_len <= chunk_size:
            current_doc.append(piece)
            total_len += sep_overhead + piece_len
        else:
            if current_doc:
                final_chunks.append(chosen_sep.join(current_doc))
            current_doc = [piece]
            total_len = piece_len

    if current_doc:
        final_chunks.append(chosen_sep.join(current_doc))

    return final_chunks
```

通过这种机制，长文本大多能在段落或标点处自然断开，兼顾了处理效率与语法结构完整度。

## 5. 基于语义距离的切分（Semantic Chunking）：滑动窗口与距离突变点检测

固定切分与递归切分依据的是格式符号（如标点、换行）而非文本语义内容。若两段话紧密论证同一事件，仅因为作者敲了两次回车就被拆开；或者单个段落中话题发生了转换，按字符规则切分就容易出现语义割裂。

基于语义距离的切分（Semantic Chunking）利用 Embedding 模型来定位语义边界。

![语义切分余弦距离曲线与阈值突变点检测](/images/content-rebuild/c347849ba14e51e8/fig-3.png)

### 算法处理步骤

1. **原子单句拆解**：使用分句工具或标点规则将长文档拆分为基础单句序列 $[S_1, S_2, \dots, S_n]$。
2. **滑动窗口上下文缓冲**：为避免单句过短造成向量信息稀薄，通常引入局部缓冲窗口，例如将 $S_{i-1}, S_i, S_{i+1}$ 拼接为一个联合窗口句。
3. **单句向量化计算**：调用 Embedding 模型，计算每一个缓冲窗口的向量表示 $\vec{v}_i$。
4. **相邻距离度量**：计算连续句子窗口之间的余弦距离 $D_i$：
   $$D_i = 1 - \cos(\vec{v}_i, \vec{v}_{i+1}) = 1 - \frac{\vec{v}_i \cdot \vec{v}_{i+1}}{\|\vec{v}_i\| \|\vec{v}_{i+1}\|}$$
5. **突变切分点判定**：遍历距离序列，检测语义跳变点：
   * **固定阈值法**：当 $D_i > \tau$（例如经验值设定为 0.35）时断开。
   * **百分位数阈值法**：统计整篇文档所有相邻距离分布，取分位数（例如 90 分位数）的跳变点作为切分边界。
   * **梯度标准差突变法**：计算距离序列的移动均值 $\mu$ 与标准差 $\sigma$，当 $D_i > \mu + k\sigma$ 时判定为主题转换。

### 收益与代价权衡

* **收益**：切分后的块围绕单一主题聚合，减少“多主题杂糅块”的产生，提升细粒度向量相似度匹配度。
* **代价**：
  1. **入库计算开销增加**：在切分阶段就需要调用 Embedding 接口对全量句子逐一向量化，预处理耗时与 API 消耗远高于纯字符串处理。
  2. **块尺寸不可控**：如果文本持续讨论同一主题，算法可能输出数千 Token 的过大块；而在频繁对话或论点交替处，可能切出过多碎片块，对下游检索排序带来扰动。

## 6. 父子层级分块（Parent-Document / Small-to-Big）：小块检索与大块返回机制

在 RAG 系统中，检索阶段与生成阶段对 Chunk 粒度的要求存在权衡冲突：
* **检索阶段偏好小块（Small Chunk）**：小 Chunk 语义聚焦、主题单一，向量表征不容易被其他无关段落稀释，更容易命中用户的具体问题。
* **生成阶段偏好大块（Big Chunk）**：大模型生成回答需要完整的前后语境、限定条件与因果逻辑支持。如果只提供几十 Token 的短句，模型容易因语境残缺而出现断章取义。

父子层级分块通过解耦**检索索引单元**与**生成上下文单元**来处理这种权衡冲突。

![父子层级分块的小块检索与大块回溯链路](/images/content-rebuild/c347849ba14e51e8/fig-4.png)

### 系统架构与存储分工

在父子分块方案中，底层通常配合两种存储机制：
1. **文档存储（DocStore / KV 存储）**：保存较大的父块（Parent Chunk，例如 1024~2048 Token）或整个段落章节，每个父块有唯一的 `parent_id`。
2. **向量数据库（Vector DB）**：将每个父块切分为数个小子块（Child Chunk，例如 128~256 Token），向量库中存储子块的 Embedding，并在元数据（Metadata）中固化指向其父块的指针：`metadata = {"parent_id": "P_001"}`。

```python
# 核心数据结构示意
parent_store = {
    "parent_001": "节点网络分区导致主从切换：当集群主节点发生网络分区故障时，RAFT 协议自动触发选举机制；经多数派节点投票，Node-02 成功晋升为新 Leader。处置指令：1. 执行 cluster nodes 确认新拓扑状态；2. 检查旧 Leader 的持久化日志同步进度。"
}

child_vectors = [
    {
        "id": "c_01", 
        "text": "当集群主节点发生网络分区故障时，RAFT 协议自动触发选举机制...", 
        "embedding": [...], 
        "metadata": {"parent_id": "parent_001"}
    },
    {
        "id": "c_02", 
        "text": "处置指令：1. 执行 cluster nodes 确认新拓扑状态；2. 检查旧 Leader 持久化...", 
        "embedding": [...], 
        "metadata": {"parent_id": "parent_001"}
    }
]
```

### 运行时查询流程

```mermaid
graph LR
    Q[用户查询] --> VS[向量数据库检索引擎]
    VS -->|Top-K 向量相似度计算| C[命中 Child Chunks]
    C -->|提取 parent_id 集合去重| M[元数据解析去重]
    M -->|主键查询| DS[(DocStore / KV 存储)]
    DS -->|加载完整 Parent Chunks| P[构建 Prompt 上下文]
    P --> LLM[送入大语言模型生成回答]
```

1. 用户发起检索时，向量引擎在小子块集合中进行相似度计算。由于子块聚焦，能够较为敏锐地捕获细粒度提问。
2. 召回 Top-K 个子块后，检索服务读取子块中的 `parent_id` 字段。
3. 执行**去重逻辑**：若命中的多个子块均归属于同一个父块，仅保留该 `parent_id` 一次，防止上下文中注入重复信息。
4. 依据 `parent_id` 到文档存储中拉取完整的父块正文，组合构建最终 Prompt 送入大模型。

这种机制的代价在于增加了存储冗余（小块与大块均需保存）并提升了系统维护成本。在多路检索场景中，通常配合 [BM25 + 向量检索的混合召回](/interview/rag-interview/hybrid-retrieval.md) 与 [Rerank 精排](/interview/rag-interview/rerank.md) 使用。

## 7. 策略横向选型与场景匹配

![四大切分策略的复杂度与表现象限选型图](/images/content-rebuild/c347849ba14e51e8/fig-5.png)

在实际工程架构中，各切分策略的技术指标对比如下：

| 切分策略 | 核心切分依据 | 入库计算开销 | 语法结构完整度 | 块尺寸均匀性 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **固定长度切分** | 纯字符数 / Token 计数 | 极低（纯字符串切片） | 差（存在单点硬截断） | 严格均匀 | 纯文本粗粒度切分、快速原型验证 |
| **递归字符切分** | 层级语法分隔符降级 | 低（多层规则字符串匹配） | 较好（尽可能保留段落与句式） | 相对均匀 | 通用企业知识库、技术说明书、百科词条 |
| **语义切分** | 句子向量余弦距离跳变 | 高（需全量前置向量计算） | 高（按主题关联聚合） | 较不均匀 | 缺少规范排版的口语纪要、会议速记、散文 |
| **父子层级切分** | 两级分块与元数据指针映射 | 中等（需两级存储与索引维护） | 优（检索点细，生成语境完整） | 子块均匀，父块按章节设定 | 逻辑推理链长、条款约束严密的法律或技术规范 |

### 边界与异常情况处理

![不同切分策略在特殊文档结构下的破坏与应对案例](/images/content-rebuild/c347849ba14e51e8/fig-6.png)

在处理特殊格式时，需针对性设计策略：
1. **Markdown 表格破坏**：如果使用通用切分器，表格可能从中间某一行被切断。后续的数据行失去表头后，单独的单元格向量将失去含义。**应对措施**：使用 Markdown 语法感知切分器，将表格整体作为独立 Chunk 保留，或在切分后为每个子块强制拼回表头行。
2. **代码块被拆散**：通用切分器可能会在函数中间截断，导致大模型无法推断完整的参数列表与异常分支。**应对措施**：使用针对编程语言的 AST 解析器，按函数或类级别整体切分。
3. **语义切分的距离失真**：在长篇配置单或由键值对组成的日志中，相邻项的 Embedding 距离可能剧烈波动或持续平缓，导致语义切分产生大量碎片或超大块。在这类高度结构化的内容上，基于规则的格式切分通常更稳定。

## 面试追问与常见误区

### 追问 1：为什么 Overlap（重叠区）不能替代递归或语义切分？

**口述要点**：
> “Overlap 是滑动窗口在边缘处的过渡缓冲。首先，它只能缓解长度小于 Overlap 窗口的短语被截断；面对跨段落的因果逻辑链，机械重叠无法提供结构性的上下文支持。
> 其次，如果盲目调大 Overlap，相邻 Chunk 之间会出现大量冗余内容。这会导致向量召回的 Top-K 结果被几乎重复的片段挤占，浪费了大模型有限的上下文窗口，反而降低了答案的有效信息密度。”

### 追问 2：在父子层级切分中，如何防止召回多个父块导致上下文超限？

**口述要点**：
> “工程上通常采取两层防护：
> 1. **ID 去重**：召回 Top-K 子块后，先提取其 `parent_id` 集合去重，确保同一父块只会被读取一次。
> 2. **父块评分聚合与截断**：将属于同一父块的多个子块相似度得分进行加权汇总，对去重后的父块进行重新排序，设置总 Token 预算上限；如果累积的父块内容超过上限，按综合得分从高到低截断低优先级父块。”

### 常见错误说法辨析

* **错误说法 1：“语义切分的效果一定优于递归切分。”**
  * **反驳依据**：语义切分依赖前置 Embedding 模型质量，且切出的 Chunk 尺寸差异较大，极短或极长均不利于后续稳定的检索调优。对于格式排版规整的技术文档或法律文书，基于标题和段落的层级切分在稳定性和吞吐成本上往往更占优势。
* **错误说法 2：“父子切分只能划分‘一大一小’两层。”**
  * **反驳依据**：父子切分可以扩展为多级树状结构（Hierarchical Chunking），例如‘篇章 -> 章节 -> 段落 -> 句子’。检索时可在段落或单句层级进行向量打分，生成时依据置信度回溯到章节甚至整篇，与递归归纳总结逻辑配合使用。
* **错误说法 3：“按 Token 切分就不会切碎词汇。”**
  * **反驳依据**：大模型的分词器使用 BPE 或 WordPiece 等算法将单词拆分为 Subword。直接按 Token 计数的硬截断依然可能在一个复合词或生僻专业实体的中间 Token 处断开，解码后同样会出现残缺碎片。
