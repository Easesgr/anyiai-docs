# 什么是 Spring AI 提出的模块化 RAG 架构？预检索、检索和后检索阶段各自负责什么？

这道题考的是 RAG 架构的完整理解和模块化设计思想。面试官想看你能不能说清楚"检索增强生成"这件事是怎么工作的，以及为什么 Spring AI 要把 RAG 分成三个阶段来设计。

我从四个方面来讲：RAG 是什么、预检索阶段、检索阶段、检索后阶段。

---
## RAG 是什么？为什么要模块化？

RAG，Retrieval-Augmented Generation，翻译过来就是"检索增强生成"。

大白话解释：大模型肚子里有知识，但它不是全知全能的。特别是企业私有知识、业务实时数据，大模型根本不知道。你让大模型回答"我们公司去年Q3的营收是多少"，它答不上来，它没学过这个数据。

RAG 就是来解决这个问题的：给大模型配一个"实时更新的知识外挂"。

流程是这样的：用户提问 → 先去知识库检索相关答案 → 把检索到的内容和用户问题一起喂给大模型 → 大模型基于真实资料生成回答。

这样做最大的好处就是**减少幻觉**。大模型不是凭空编造，而是基于真实检索到的内容来回答。


Spring AI 把 RAG 分成了三个模块：**预检索、检索、后检索**。每个模块各司其职，可以独立优化。

为什么要分这么细？因为实际应用中，"检索"这件事没那么简单。用户问一句话，你不能直接拿这句话去知识库搜。搜出来的结果可能不相关、可能太多太杂、可能缺少关键信息。

模块化的好处就是：**可以在每个阶段做针对性优化，互不影响**。预检索做查询扩展、检索做精准召回、后检索做上下文压缩，各管各的事。

## 预检索阶段——打磨你的 Query

预检索阶段的任务很明确：**把用户的问题变成更好检索的形态**。

用户的问题是原始 Query，直接拿去检索，效果往往不好。

举几个例子你就明白了：

用户问："感冒咋办？"

你直接搜"感冒咋办"，可能搜不到最相关的内容。但如果预检索阶段帮你生成几个变体：

- "上呼吸道感染怎么办"
- "发烧处理方法"
- "感冒用药建议"

再拿这些变体去检索，召回率就高多了。

这就是**查询扩展（Multi-Query）**的思路：一个问题生成多个检索表达，覆盖更多可能的答案。

预检索阶段通常包括这几个步骤：

**第一步，查询扩展**。用大模型或者规则，把用户的问题改写、分解、扩展成多个检索词。

**第二步，读取文档**。从数据源读取原始文档，可能来自文件、数据库、网页。

**第三步，文档切片**。文档太长，直接检索效果差。切成小块（Chunk），每个小块是一个独立的知识点。

切片大小很关键。太长，相关性被稀释；太短，上下文不完整。一般 512 到 1024 个 token 比较常见。

**第四步，向量化**。把文档切片转成向量，存进向量数据库。这一步叫 Embedding。

为什么？因为向量能捕捉语义。"感冒"和"发烧"在向量空间里距离很近，即使文字不完全匹配，也能被检索到。


预检索阶段的核心目标就是**提升召回率**——让相关的内容尽可能被找出来。

---

## 检索阶段——精准召回

检索阶段的任务：从向量数据库里找出最相关的文档切片。

这里有个关键问题：怎么定义"相关"？

常用方法有几种：

**向量检索**：把 Query 转成向量，在向量空间里找最近的邻居。语义相近的内容会被找出来。

**关键词检索（BM25）**：传统的全文检索，根据词频、逆文档频率来算相关性。

**混合检索**：同时用向量检索和关键词检索，然后融合结果。

为什么要混合？因为向量检索擅长语义匹配，关键词检索擅长精确匹配。两者结合效果更好。

比如用户问"Spring Boot 怎么配置 Redis"：

- 向量检索可能找到"Redis 使用方法"这种语义相关的文档
- 关键词检索会精准匹配"Spring Boot"+"Redis"+"配置"这几个词

多路召回就是让两种方法各找一遍，然后合并。

召回结果怎么排序？这就涉及**重排序（Rerank）**。

常用的做法是 CrossEncoder。把 Query 和文档一起喂给一个专门的模型，输出一个相关性分数，按分数排序。

检索阶段有几个常用参数：

- **topK**：取前 K 条结果。一般 3 到 5 条。
- **相似度阈值**：低于某个分数的直接过滤掉。比如 0.6。


检索阶段的核心目标：**精准找到最相关的文档切片**。

## 检索后阶段——提纯上下文

检索阶段找到了相关文档，但这些文档可能有问题：

- 太长，包含太多无关信息
- 相关性参差不齐，有高有低
- 格式混乱，不好理解

后检索阶段的任务就是**提纯**：把检索结果处理成最适合大模型理解的上下文。

常用手段有几种：

**上下文压缩**：只保留最相关的部分，删掉无关内容。比如一个文档切片有 1000 字，但和用户问题真正相关的只有 200 字，那就只取这 200 字。

压缩的依据通常是**余弦相似度**。只保留相似度高的段落。

**元数据过滤**：根据文档的元数据做筛选。比如按日期过滤，只要最近一年的文档；按权限过滤，排除用户无权查看的文档。

**动态提示模板**：把检索结果塞进提示词模板，生成结构化的上下文。比如：


参考信息：
[文档1的摘要]
[文档2的摘要]
[文档3的摘要]

请基于以上信息回答：{用户问题}


这样做的好处是：上下文精简了，大模型处理起来更快更准。

有数据为证：**上下文压缩可以让准确率从 62% 提升到 85%**。效果很显著。


后检索阶段的核心目标：**提纯上下文，让大模型看到最关键的信息**。

## 面试怎么答

**基础版**（直接背）：

Spring AI 的模块化 RAG 架构把检索增强生成分成三个阶段：预检索、检索、后检索。

预检索阶段负责优化 Query，通过查询扩展生成多个检索变体，同时对文档进行切片和向量化，目的是提升召回率。

检索阶段负责精准召回，采用混合检索（向量+关键词）结合多路召回，用 CrossEncoder 重排序找出最相关的文档切片。

后检索阶段负责提纯上下文，做上下文压缩去掉无关信息，配合元数据过滤和动态提示模板，最终生成结构化的上下文喂给大模型。

模块化设计的优势是各阶段可独立优化，不需要改动其他模块。

**加分版**（有深度）：

在基础版基础上，补充这些细节：

- 查询扩展可以用 Multi-Query 策略，用大模型生成 5-10 个检索变体
- 切片策略影响很大，常用的有固定窗口切片、语义切片、递归切片
- 混合检索的融合方式：RRF（Reciprocal Rank Fusion）或者分数加权
- CrossEncoder 重排序比单纯用向量距离排序效果更好
- 上下文压缩可以结合 LLM 进行智能摘要
- Spring AI 提供了 DocumentReader、EmbeddingModel、VectorStore 等抽象组件，支持灵活的模块替换

---

## 一句话总结

Spring AI 的模块化 RAG 架构通过预检索打磨 Query、检索精准召回、后检索提纯上下文三阶段分工，实现了大模型与知识库的有效结合，让 AI 回答更准确、更可控。
