在检索增强生成（RAG）系统中，许多开发者会遇到这样的现象：向量数据库明明召回了包含关键名词的文档，但最终大模型给出的回答却依然不准确，甚至与事实完全相反。

来看一个贯穿本文的典型例子。假设用户的查询是：
> **查询**：“甲公司可以向乙公司转让专利吗？”

知识库中存在两条条款相似但结论相反的文档：
- **文档 A**：“经双方书面确认，甲公司可以向乙公司转让专利。”
- **文档 B**：“未经特别授权，甲公司严禁向乙公司转让专利。”

如果仅使用常规的向量检索（基于双塔架构），这两篇文档与查询的实体词（“甲公司”“乙公司”“转让”“专利”）高度重合。由于独立向量池化会稀释掉“严禁”这类否定词的权重，文档 A 和文档 B 的余弦相似度得分可能只有 0.01 级别的微小差距，甚至负面条款 B 还会因为其他词项匹配被排在首位。送入大模型的上下文顺序一旦混乱，生成结果就会出现错误。

**Rerank（重排）解决的核心问题，就是在粗排召回后，用更精细的语义交互模型重新评估候选文档与查询的相关性，把真正符合逻辑语义的文档排到最前面。**

---

## 1. 面试口述答案：两阶段检索中的 Rerank 定位

在面试中被问到“Rerank 解决了什么问题？为什么不直接一次检索到位？”时，建议分层组织回答：

### 基础口述版本（约 120 字，适合 30 秒作答）
> Rerank 是两阶段检索中的精排模块。第一阶段向量检索采用双塔架构（Bi-Encoder），将查询与文档独立编码为向量，依靠内积或余弦距离从海量库中快速召回候选集（如 Top 50）。但双塔编码因独立压缩会丢失主谓关系、否定词等细粒度信息。第二阶段 Rerank 采用交叉编码器（Cross-Encoder），将查询与候选文档拼接后进行全自注意力计算，输出高精度的相关性得分并选出前 3 到 5 篇文档，在延迟可控的前提下弥补粗排的精度不足。

### 进阶口述版本（约 200 字，适合深入追问）
> 引入 Rerank 是**精度与算力成本的工程折中**。双塔模型的文档向量支持离线预计算，在线只做单次查询编码和近似最近邻（ANN）检索，适合百万级文档的毫秒级召回；但 Query 和 Document 在编码时互不可见，定长向量池化存在信息压缩瓶颈。交叉编码器让 Query 与 Document 的每个 Token 在多层 Transformer 中做跨文本全连接注意力，能够准确捕获主谓颠倒、否定排他和细粒度匹配，但其计算量与候选文档数呈线性增长，无法离线预计算。两阶段架构先用低成本的双塔模型或混合检索做高召回（Recall），再用交叉编码器做高精确率（Precision）重排，兼顾了线上吞吐与语义排序质量。

![两阶段检索流水线架构数据流向示意图](/images/content-rebuild/7a07566a8c04bea9/fig-1.png)

上图展示了典型的两阶段检索漏斗：全量文档库先经过第一阶段快速召回数十个粗排候选结果；再由 Rerank 重排模型计算真实语义相关性，最终输出 3 到 5 个高置信度文档供大语言模型消费。

## 2. 双塔（Bi-Encoder）独立编码的信息瓶颈

要理解 Rerank 的必要性，先要看清第一阶段向量检索的局限。关于向量编码的基础知识，可以参考 [/interview/rag-interview/rag-embedding.md](/interview/rag-interview/rag-embedding.md)。

### 独立前向传播与相似度计算
在双塔模型（Bi-Encoder）中，查询 $q$ 和文档分块 $d$ 分别通过编码网络（通常共享同一套 Transformer 权重，有时也使用不同权重）：

$$\mathbf{u} = \text{Encoder}(q), \quad \mathbf{v} = \text{Encoder}(d)$$

最终的相似度完全由两个独立向量的几何内积或余弦值决定：

$$s(q, d) = \frac{\mathbf{u} \cdot \mathbf{v}}{\|\mathbf{u}\| \|\mathbf{v}\|}$$

这种解耦结构是向量数据库得以成立的基础：知识库中的百万级切片只需在导入时离线计算一次向量，构建成 HNSW 或 IVF 索引。用户发起提问时，系统只需要编码一次查询，就能在线上以毫秒级时间完成搜索。

![Bi-Encoder双塔架构计算分离机制图](/images/content-rebuild/7a07566a8c04bea9/fig-2.png)

### 信息瓶颈是怎样形成的
这种分离也带来了不可避免的信息损失。如图 2 所示，在双塔模型的前向计算中，编码文档 $d$ 时模型无法看到查询 $q$；编码 $q$ 时也无法看到 $d$。

无论文档原本包含多么复杂的转折、否定或条件从句，最终都必须经过均值池化（Mean Pooling）或提取 `[CLS]` 向量，压缩成一个固定长度（例如 768 或 1024 维）的向量。把一个数百 Token 的段落压缩到有限维度的浮点数数组中，必然会导致局部语法关系的弱化：

1. **主谓语序颠倒**：“中国队战胜了巴西队”与“巴西队战胜了中国队”。两句话的词汇完全一致，经过池化后的向量距离极近，双塔模型很难区分谁胜谁负。
2. **否定词被稀释**：在贯穿示例中，“严禁向乙公司转让”和“可以向乙公司转让”，由于核心专有名词和动词占满了主要的维度贡献，单个否定词“严禁”对整体向量方向的改变有限，常常导致排他性条款无法被正确剔除。
3. **多义实体缺少动态约束**：对于查询“苹果 15 价格”，双塔模型在编码查询时只能靠先验统计，无法结合具体文档内容在“水果”与“消费电子”之间进行动态交互解歧。

关于如何合理设置第一阶段召回数量以减少遗漏，可以参考 [/interview/rag-interview/rag-topk.md](/interview/rag-interview/rag-topk.md)。

## 3. 交叉编码器（Cross-Encoder）：Token 级别的全连接注意力

Rerank 模块普遍采用交叉编码器（Cross-Encoder）架构，以此打破双塔模型的独立压缩瓶颈。

### 拼接输入与跨文本自注意力
Cross-Encoder 不再为文本生成独立的文档向量，而是把 Query 与候选 Document 直接拼接为一个序列送入 Transformer：

$$\text{Input} = [\text{CLS}], q_1, q_2, \dots, q_m, [\text{SEP}], d_1, d_2, \dots, d_n, [\text{SEP}]$$

在 Transformer 的多头自注意力计算中：

$$\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V$$

此时，注意力矩阵的维度是 $(m+n) \times (m+n)$。这意味着 Query 中的每一个词 $q_i$ 与 Document 中的每一个词 $d_j$，在模型的每一层中都可以直接产生注意力权重交互。

![Cross-Encoder交叉编码器自注意力全连接矩阵图](/images/content-rebuild/7a07566a8c04bea9/fig-3.png)

### 标量打分输出
经过所有 Transformer 层的交叉计算后，模型提取首个 Token `[CLS]` 的隐藏层输出 $\mathbf{h}_{\text{CLS}}$，通过一个线性层直接映射为一个实数评分（Logit）：

$$s(q, d) = \mathbf{w}^T \mathbf{h}_{\text{CLS}} + b$$

这个得分直接代表当前 Query 与该 Document 的逻辑相关度，不再需要计算向量余弦。

### 实际表现对比
用刚才的贯穿例子来看两种架构在打分上的真实区别：

```python
# 伪代码示意：Bi-Encoder 与 Cross-Encoder 对逻辑关系的判定差异
query = "甲公司可以向乙公司转让专利吗？"
doc_positive = "经双方书面确认，甲公司可以向乙公司转让专利。"
doc_negative = "未经特别授权，甲公司严禁向乙公司转让专利。"

# 1. Bi-Encoder 流程（独立向量计算）
v_q = bi_encoder.encode(query)
v_pos = bi_encoder.encode(doc_positive)
v_neg = bi_encoder.encode(doc_negative)

score_pos_bi = cosine_similarity(v_q, v_pos)  # 示例值：0.881
score_neg_bi = cosine_similarity(v_q, v_neg)  # 示例值：0.865（分差仅 0.016，极易受切片噪音干扰）

# 2. Cross-Encoder 流程（拼接输入，全自注意力计算）
score_pos_cross = cross_encoder.predict([[query, doc_positive]])  # 示例值：0.93
score_neg_cross = cross_encoder.predict([[query, doc_negative]])  # 示例值：0.05（分差达到 0.88，逻辑清晰区分）
```

![语义反转与逻辑排他性判别对比图](/images/content-rebuild/7a07566a8c04bea9/fig-4.png)

如图 4 所示，在 Cross-Encoder 内部，“严禁”这一否定词与 Query 中的“可以”在多层注意力中直接交互，模型能清晰感知到两者存在条件冲突，从而给出低分。

## 4. 为什么不能直接全量使用 Cross-Encoder？计算开销与延迟权衡

既然 Cross-Encoder 判别更准确，为什么不淘汰向量数据库，直接用 Cross-Encoder 对整个知识库做检索？

关键在于**在线计算复杂度**与**硬件时延约束**。

### 检索过程的复杂度对比
设知识库共有 $M$ 个文档切片，用户输入查询包含 $L_q$ 个 Token，每个切片平均长度为 $L_d$ 个 Token：

| 对比维度 | 双塔架构（Bi-Encoder 向量检索） | 交叉编码器（Cross-Encoder 重排模型） |
| :--- | :--- | :--- |
| **离线预处理** | 需对 $M$ 个切片进行前向计算并建立向量索引 | 无需生成文档向量，原样存储切片文本即可 |
| **在线前向推理量**| **仅 1 次**（仅需对用户 Query 进行一次前向编码） | **$M$ 次**（Query 必须与每个切片拼接后单独前向推理） |
| **单次推理序列长度** | 查询长度 $L_q$ | 拼接长度 $L_q + L_d$ |
| **主要在线耗时** | 向量库近似最近邻检索（如 HNSW，约 $O(\log M)$） | 深度神经网络全量推理（$O(M \cdot (L_q + L_d)^2)$） |
| **10 万切片在线耗时** | 约 10 ~ 25 毫秒 | 约 10 ~ 30 秒（单卡 GPU，无法满足在线响应） |

![算力消耗与时间延迟对比散点图](/images/content-rebuild/7a07566a8c04bea9/fig-5.png)

### 具体硬件算例推演
为了直观理解这个性能差距，我们做一个基准假设相同的算例测算：
- **硬件条件**：单张 NVIDIA A10（24GB 显存），FP16 半精度推理。
- **数据规模**：知识库包含 $M = 100,000$ 个切片，平均长度 $L_d = 256$ Token，用户查询 $L_q = 32$ Token。
- **模型规格**：基于 BERT-base 架构（1.1 亿参数）的 Embedding 模型与 Reranker 模型。

**方案 A：双塔全量检索**
1. 10 万个切片的向量在离线导入时已全部计算完毕并建立 HNSW 索引。
2. 用户提问到达：GPU 对 32 Token 的查询执行 1 次前向计算，耗时约 3 毫秒。
3. 在内存索引中执行 Top 50 向量距离搜索，耗时约 8 毫秒。
4. **总线上耗时：约 11 毫秒**。

**方案 B：交叉编码器全量检索**
1. 由于 Query 在用户提问前未知，Query 无法提前与 10 万个切片拼接，必须在线实时推理。
2. 总共需要对 100,000 个长度为 288 Token 的序列执行前向传播。
3. 即使设置 Batch Size = 64，也需要执行约 1,563 次批推理。在单张 A10 上，每次批推理耗时约 12 毫秒。
4. **总线上耗时：$1,563 \times 12\text{ ms} \approx 18.7$ 秒**。

18 秒的耗时完全超出了在线系统允许的范围（通常要求在 500 毫秒以内完成检索）。因此，Cross-Encoder 绝对不能用于第一阶段的全量搜索，只能在粗排将文档数缩减到几十篇之后，再介入精排。

## 5. 生产环境中的两阶段流水线设计与边界

在实际工程实现中，成熟的检索链路通常采用“大粗排 + 精细重排”的组合。

### 推荐流水线配置
1. **粗排阶段（召回 Top 50 ~ 100）**：
   - 建议采用混合检索（稠密向量检索 + BM25 稀疏检索，详见 [/interview/rag-interview/hybrid-retrieval.md](/interview/rag-interview/hybrid-retrieval.md)），利用关键词匹配弥补专有名词漏召回，利用向量检索补充同义泛化。
   - 粗排的首要目标是**高召回率（Recall）**：宁可带入部分低相关切片，也绝不能把包含正确答案的切片漏掉。
2. **精排阶段（重排后取 Top 3 ~ 5）**：
   - 输入粗排返回的 50 到 100 个切片，送入中小型专门 Cross-Encoder 模型（例如 BGE-Reranker 系列）。
   - 精排的首要目标是**高精确率（Precision）与排序保真度（MRR / NDCG）**：剔除表面词频重合但逻辑不匹配的分块，把最精准的片段排在最前面，供大模型作为上下文生成回答。

![生产级两阶段检索故障边界与异常分支处理图](/images/content-rebuild/7a07566a8c04bea9/fig-6.png)

### 三个关键的工程边界与常见陷阱

#### 陷阱一：粗排候选数量（Top-K）并不是越大越好
有的团队为了防止漏召回，把送入 Rerank 的候选数设置为 200 甚至 500。这会带来明显的问题：
- **边际收益递减**：根据实测经验，相关文档大多分布在粗排的前 50 命中，超过 100 之后正样本命中的概率极低。
- **延迟与显存排队**：Cross-Encoder 的在线推理时间与送入的候选文本对数量呈线性正比。当并发请求上来时，过大的候选集会导致 GPU 显存占满，排队时延剧增。

#### 陷阱二：Token 截断导致的关键信息丢失
主流 Rerank 模型的最大上下文长度通常为 512 Token。如果 Query 占用了 50 Token，文档切片达到 500 Token，拼接后长度为 550 Token，超出的 38 个 Token 会被模型直接截断。
若决定逻辑走向的关键定语或免责条款恰好落在切片末尾，重排模型将完全无法感知。因此，文本切分时切片长度建议控制在 250 ~ 400 Token 之间，为 Query 和拼接标记留足安全余量。

#### 陷阱三：Rerank 无法凭空解决知识库的缺失问题
必须明确：**Rerank 只能对粗排召回的内容做相对排序，无法生成知识库中不存在的答案**。如果粗排阶段因为切分破坏或关键词完全不匹配漏掉了目标切片，重排无论如何打分也无济于事；同样，若知识库本身缺乏相关证据，重排只会选出“相对不那么离题”的次优片段，大模型仍可能因此产生幻觉。关于幻觉的成因与治理，可以参考 [/interview/rag-interview/rag-hallucination.md](/interview/rag-interview/rag-hallucination.md)。

## 6. 面试高频追问与概念辨析

### 追问 1：ColBERT 属于 Bi-Encoder 还是 Cross-Encoder？它解决了什么？
> **回答策略**：
> ColBERT 属于**晚期交互（Late Interaction）**架构，处于两者的折中位置。它像 Bi-Encoder 一样对 Query 和 Document 独立前向编码，但输出的不是单句向量，而是保留每个 Token 的词向量列表（Multi-vector）。在检索计算时，不需要通过深层 Transformer 做跨文本自注意力，而是使用轻量级的 MaxSim 算子（计算 Query 中每个 Token 与 Document 中所有 Token 向量的最大点积之和）。这样既允许文档词向量预先离线存储，又保留了 Token 级别的交互能力，兼顾了检索速度与细粒度语义匹配。

### 追问 2：为什么不直接用大语言模型（LLM-as-a-Judge）做在线 Rerank？
> **回答策略**：
> 核心原因在于**推理吞吐量与调用成本**：
> 1. 生成式 LLM（如 7B/14B 模型）通常基于自回归解码，打分时需要生成判别词或计算生成概率，单次推理耗时多在几十毫秒到数秒之间，远慢于判别式 BERT 架构的 Cross-Encoder（通常仅需毫秒级）。
> 2. 大模型打分容易受到提示词波动和位置偏置（Position Bias，即倾向于给排在前面的文档打高分）的影响。
> 在实际应用中，LLM-as-a-Judge 多用于离线评估测试集或蒸馏小模型，在线实时重排依然以专门训练的中小型判别式 Cross-Encoder 为首选。

### 常见错误答法警示
- **错误说法**：“Bi-Encoder 之所以不准是因为维度太低，只要把向量维度升到 4096 就等于 Cross-Encoder 了。”
  - **辨析**：错误。增加向量维度只是扩大了单向量的表征空间，无法改变“两个独立文本必须先池化成固定向量再做线性点积”的结构限制。点积无法替代多层神经网络中的双向全连接注意力。
- **错误说法**：“Rerank 计算完成后，会生成新的文档向量并写回向量数据库。”
  - **辨析**：错误。Cross-Encoder 的输出是一个标量相关性得分，属于单次查询与文档对的实时计算结果，不产生通用的单文本向量，也不涉及向量库写回。
