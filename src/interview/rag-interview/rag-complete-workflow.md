在面试中被问到“RAG 的完整工作流程与核心步骤”时，许多求职者容易走向两个极端：要么只背诵离线文档切块与向量入库，忽略了真实在线运行时的状态流转；要么只谈提示词拼接，漏掉了混合检索、重排序与首字延迟控制等工程细节。

完整的 RAG（Retrieval-Augmented Generation，检索增强生成）系统由两条互相关联的主线构成：**离线数据索引流水线**与**在线检索合成流水线**。

## 1. 核心口述答案：双线并行的工作流程

在面试中，可以用结构化的两阶段框架进行回答：

> “RAG 的完整体系分为离线构建与在线服务两大主线：
>
> 1. **离线数据索引阶段**：负责将多源异构文档转换为检索系统可理解的格式。主要包含文档提取、内容清洗、文本分块（Chunking）、生成嵌入向量（Embedding），并将切片与向量分别写入向量数据库和全文索引库。
> 2. **在线检索生成阶段**：按时间顺序可划分为五个核心步骤：
>    - **查询预处理**：进行意图过滤与安全检查，并在多轮对话场景下结合历史上下文完成查询改写（Query Rewrite），随后生成查询向量；
>    - **多路召回（Hybrid Retrieval）**：并发向向量数据库发起稠密向量近似最近邻搜索（ANN），并向倒排索引发起稀疏关键词搜索（如 BM25），各自拉取 Top-K 候选；
>    - **排序融合与重排（RRF & Rerank）**：通过倒数排名融合（RRF）消除不同检索器之间的打分量纲差异并去重，再由交叉编码器（Cross-Encoder Reranker）对候选段落进行深度重排序与相关性阈值过滤；
>    - **提示词组装与上下文装配**：依据大模型的上下文窗口预算，将核心证据、系统指令与用户问题组合，按注意力友好的顺序注入 Prompt；
>    - **模型生成与流式输出**：大模型执行 Prefill 计算生成首个 Token，通过流式通道（如 SSE）返回增量文本，同时输出引文溯源信息并记录全链路监控日志。”

![单次 RAG 查询端到端生命周期状态机与时序阶段转换](/images/content-rebuild/4a5cb7a49396894f/fig-1.png)

为了让整套机制更具体，我们以一个典型场景贯穿全文：用户在微服务运维知识库中提问：“**它的默认连接超时是多少？应该怎么修改？**”（上一轮用户提问为：“请介绍 Kubernetes 环境下的 Ingress-Nginx 网关组件配置。”）。

## 2. 离线数据索引阶段：建立高质量检索底座

在线检索的准确性高度依赖离线构建的索引质量。离线流水线主要完成数据摄入与结构化索引：

1. **文档加载与解析（Data Ingestion & Parsing）**：从 Git 仓库、Wiki 或 PDF 中读取原始资料。对于包含表格、代码块或树状层级的复杂格式，需要利用专用解析工具提取纯文本和元数据（如章节标题、文档修改时间、文件路径）。
2. **文本分块（Chunking）**：将超长文档切分为模型嵌入所支持的长度（常见单块长度为 256~512 Token）。通常保留 10%~20% 的重叠区域（Overlap），避免因机械截断丢失关键上下文。在我们的案例中，Ingress-Nginx 官方文档中关于 `proxy-connect-timeout` 的配置说明会被完整保留在某一个 Chunk 内。
3. **多模态与双向索引写入（Indexing & Storing）**：
   - 调用 Embedding 模型生成稠密向量，连同分块元数据存入向量数据库（如 Qdrant、Milvus）；
   - 同时提取关键词或保留完整文本，写入 Elasticsearch、OpenSearch 或数据库的倒排索引表，为后续关键词精确检索准备数据。

## 3. 在线阶段一：查询预处理与意图过滤

请求到达在线网关后，不能直接拿用户的原始输入去查询底层索引，需要经过标准化规整与安全检查。

![预检索阶段的意图过滤、查询改写与嵌入计算时序流](/images/content-rebuild/4a5cb7a49396894f/fig-2.png)

### 意图判断与安全阻断（Fast-Fail）

网关首先判断该查询是否属于检索范围：
- **日常问候或通用闲聊**（如“你好”、“今天天气怎么样”）：直接路由给通用对话模型或预设模版，跳过耗时的检索环节。
- **提示词注入与越狱探测**：如果输入包含试图覆盖系统指令的内容，由安全护栏程序直接拦截。
- **垂直领域问答**：符合条件，放行进入重写链路。

### 上下文查询改写（Query Rewrite）

用户的问题是：“**它的默认连接超时是多少？应该怎么修改？**”。
这里的“它”存在代词省略，如果直接把这句话向量化去检索，向量数据库无法得知主体是 Ingress-Nginx。

系统调用一个轻量级文本模型（或利用提示词规则），结合会话历史将问题重写为独立查询（Standalone Query）：
> **重写后查询**：“Kubernetes 中 Ingress-Nginx 网关的默认连接超时时间是多少？如何在配置文件中进行修改？”

改写完成后，将该标准化查询发给 Embedding 模型计算查询向量，准备发起检索。

## 4. 在线阶段二：并发混合检索与重排序

单纯依赖向量检索（稠密检索）可能在精确匹配版本号、特殊配置键名（如 `proxy-connect-timeout`）时出现偏差；而单纯依靠关键词检索（稀疏检索）又无法捕捉同义词和语义关联。因此生产系统普遍采用混合检索（Hybrid Search）。

![多路并发召回合并、RRF 倒数排名融合与重排模型时延流水线](/images/content-rebuild/4a5cb7a49396894f/fig-3.png)

### 并发检索与超时容错

在代码实现上，向向量库发起的 ANN 检索与向全文搜索引擎发起的 BM25 检索必须并发执行，并设置严格的超时控制。若某一路网络抖动，系统应做降级处理，而不是无限阻塞请求。

```python
import asyncio
from typing import Any

async def parallel_retrieval(
    query_text: str,
    query_vector: list[float],
    vector_store,
    keyword_engine,
    timeout_ms: int = 80
) -> tuple[list[dict[str, Any]], list[dict[str, Any]]]:
    # 封装为并发任务
    dense_task = asyncio.create_task(vector_store.search_ann(query_vector, top_k=50))
    sparse_task = asyncio.create_task(keyword_engine.search_bm25(query_text, top_k=50))
    
    # 并发等待，设置整体超时阈值
    done, pending = await asyncio.wait(
        {dense_task, sparse_task},
        timeout=timeout_ms / 1000.0
    )
    
    # 及时取消未完成的任务，释放下游连接资源
    for task in pending:
        task.cancel()
        
    # 安全获取已完成路段的结果，若超时、取消或抛出异常均降级为空列表
    dense_results = (
        dense_task.result()
        if dense_task in done and not dense_task.cancelled() and dense_task.exception() is None
        else []
    )
    sparse_results = (
        sparse_task.result()
        if sparse_task in done and not sparse_task.cancelled() and sparse_task.exception() is None
        else []
    )
    
    return dense_results, sparse_results
```

### 倒数排名融合（RRF）

向量检索返回的是余弦相似度（区间多为 $[-1, 1]$），而 BM25 返回的是基于词频和逆文档频率计算出的统计分数（取值无上限）。两者的数值分布和物理含义完全不同，**不能直接把原始分数相加**。

倒数排名融合（Reciprocal Rank Fusion, RRF）通过比较文档在各路检索中的**名次**来实现去重融合：

$$RRF\_Score(d \in D) = \sum_{m \in M(d)} \frac{w_m}{k + r_m(d)}$$

- $M(d)$：成功召回文档 $d$ 的检索通路集合（若某通路未召回文档 $d$，则该通路得分不累加）；
- $r_m(d)$：文档 $d$ 在第 $m$ 路检索结果中的名次（从 1 开始）；
- $k$：常数平滑项（经验取值通常为 60，用于减小头部排名细微名次差距带来的分值剧烈波动）；
- $w_m$：该通路的相对权重（标准 RRF 中默认各路权重均等，即 $w_m = 1$）。

通过 RRF，两路返回的各 50 个候选被合成为一份包含 20~30 个候选片段的有序列表。

### 交叉编码重排序（Cross-Encoder Rerank）

双塔向量模型在检索时，查询与文档分别独立编码，无法直接捕捉 Query 和 Doc 之间细微的词对词交叉注意力。为了提升最终输入材料的质量，通常将候选送入 Cross-Encoder 模型（如 BGE-Reranker）。

Cross-Encoder 将 `[CLS] + Query + [SEP] + Document + [SEP]` 整体输入模型，计算两者的真实语义相关度打分。由于它的计算复杂度正比于输入序列长度的平方，因此通常只对 RRF 筛选出的前 20~30 个片段进行精排，并按照预设的相似度阈值（例如过滤低于 0.35 分的无关段落），最终筛选出 3~5 个高质量证据块。

## 5. 在线阶段三：提示词装配与流式生成

筛选出核心文档片段后，进入向大语言模型提交生成的阶段。

![Prompt 动态装配布局与大模型首 Token 延迟产生机制对比](/images/content-rebuild/4a5cb7a49396894f/fig-4.png)

### 动态上下文装配

Prompt 的拼装需要严格遵守 Token 预算分配规则：
1. **系统角色与边界约束**（System Prompt）：固定指令，限定模型只能依据给定的上下文事实作答，如果上下文未提供信息，明确回答不知道；
2. **历史问答上下文**：保留最近几轮核心对话，辅助理解语义代词；
3. **检索证据内容**：拼接筛选后的 3~5 个知识片段。根据模型“注意力易在长文中间迷失”（Lost in the Middle）的特点，**相关度最高的核心证据通常排布在证据区的前部或尾部**；
4. **用户标准化提问**：重写后的最终提问。

### 首 Token 延迟（TTFT）与推理生成

大模型的生成过程主要分为两个物理阶段：
- **Prefill 阶段（首字延迟 TTFT）**：大模型必须同时计算提示词中所有 Token 的注意力，并将计算得到的 Key-Value 向量写入显存中的 KV Cache。提示词越长，Prefill 阶段耗时越长。
- **Decode 阶段（逐字生成）**：大模型复用已有 KV Cache，每个步长仅计算新生成的一个 Token，以流式形式逐字推回给客户端。

针对 TTFT 偏高的问题，工程上常使用**前缀缓存（Prefix Caching）**技术，将固定不变的系统提示词部分在显存中缓存，减少每次重复计算。

## 6. 引用归属与端到端可观测性

生产级系统不仅要能输出内容，还要保证生成结论有据可查，并具备全链路性能分析手段。

![流式输出场景下两种引用标注时序模式对比](/images/content-rebuild/4a5cb7a49396894f/fig-5.png)

### 引文标注的时机选择

在流式输出（SSE）过程中，前端如何拿到参考引文？主要有两种模式：

| 方案类型 | 模式 A：前置元数据帧推送 | 模式 B：后置文本归因校验 |
| :--- | :--- | :--- |
| **下发时机** | 在大模型开始流式吐字前，通过 SSE 的首帧（第 0 帧）下发命中文档列表。 | 等大模型全文生成完毕后，再追加一帧引文列表。 |
| **实现机制** | Prompt 引导大模型在输出时带上引用标号 `[^1]`，前端自动关联第 0 帧中对应索引的文档信息。 | 后台接收模型完整文本，使用小模型或 NLI（自然语言推理）算法比对文本真实引用的段落，剔除未使用文献。 |
| **时延影响** | **无额外延迟**，保持极低的 TTFT。 | **增加额外延迟**（需要等待全文生成完并跑一次后处理校验）。 |
| **适用场景** | 强调实时交互的用户对话场景。 | 医疗、法律或金融等对证据引用真实性要求极高的场景。 |

### OpenTelemetry 分布式追踪

![端到端分布式链路 Trace 监控树与高耗时 Span 瓶颈排查](/images/content-rebuild/4a5cb7a49396894f/fig-6.png)

在请求入口处生成统一的 `TraceId`，并在预检索、向量数据库查询、BM25 全文检索、Rerank 排序和 LLM 推理等环节记录对应的 Span。这样当系统偶发超时（P99 飙升）时，排查人员可以在监控看板中快速分辨是由于向量数据库索引检索变慢，还是由于精排模型批处理积压，亦或是大模型 Prefill 耗时突增导致的瓶颈。

## 7. 面试深度追问与常见误区

### 追问 1：在混合检索与重排序全链路中，P99 尾部延迟通常出现在哪个环节？如何优化？

**参考思路**：
在各组件正常工作的前提下，向量库的 ANN 检索和 BM25 检索通常在 20ms~50ms 内完成，真正的 P99 瓶颈多集中在以下两处：
1. **Cross-Encoder 重排序模型**：候选段落较长或批大小较大时，交叉编码器的自注意力计算开销显著增加。优化方式包括：
   - 控制进入精排的候选数量（例如从 50 截减至 20）；
   - 对 Rerank 模型进行 FP16 或 INT8 量化，使用 ONNX Runtime 或 TensorRT 部署加速；
   - 在大并发排队时支持降级策略，直接采纳 RRF 分数排序并旁路跳过精排。
2. **大模型的 Prefill 计算（影响 TTFT）**：注入提示词的文档内容过长导致首字生成慢。优化方式包括：引入前缀缓存（Prefix Caching）避免重复计算静态指令；在保证证据完整的前提下对切片进行句子级抽取和压缩。

### 追问 2：为什么不同检索通路的结果不能直接按原始得分相加？

**参考思路**：
因为不同检索器的打分机制和尺度不同：
- 稠密向量检索通常采用余弦相似度，值域在 $[-1, 1]$ 之间，或经过归一化限制在 $[0, 1]$；
- 稀疏关键词检索（如 BM25）的分数依赖于词频、逆文档频率和文档长度，是没有理论上限的正实数，且不同 Query 之间的分值绝对值不可比。

若直接相加，BM25 的高数值会彻底掩盖向量检索的特征。因此需要通过 RRF 基于名次排序做相对融合，或者先使用 Min-Max 归一化对多路分值进行校准，再做线性加权。

### 常见口述误区清单

1. **忽略离线准备，单谈在线调用**：面试官问“完整流程”时，只回答 Prompt 组装与大模型调用，完全不提文档解析、切块和索引构建，容易给面试官留下缺乏数据工程背景的印象。
2. **把多路召回设计为串行调用**：误以为必须先查 BM25、再查向量库。在实际工程中，多路检索必须并发执行并设置超时保护。
3. **脱离计算成本谈 Rerank**：认为可以将几百个候选片段全部送进 Cross-Encoder 模型。Cross-Encoder 是单模型全注意力计算，计算量随序列长度平方增长，吞吐瓶颈明显。
4. **代码实现逻辑缺陷**：在实现并发等待异步任务时，对非序列类型（如 Python 中的 `set`）直接做下标访问导致运行时异常。
