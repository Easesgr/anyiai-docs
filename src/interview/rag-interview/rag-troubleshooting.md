![检索结果不相关与生成异常的端到端工程排障树封面](/images/content-rebuild/d72c455dcf7da5e7/cover.png)

在检索增强生成（RAG）系统中，业务端常反馈“模型回答牛头不对马嘴”或“参考文档根本不相关”。此时如果盲目修改 Prompt 或直接重新微调 Embedding 模型，排查成本极高且难以定位真因。

RAG 系统由数据处理、索引、检索、重排和生成多个阶段串联而成。排查线上故障时，需要将多阶段流水线拆开观测，通过上下文快照快速定界，再逆向回溯具体节点。

我们以一个具体问题贯穿全文排查过程：用户提问**“数据库连接池超时参数 `connect_timeout` 怎么配置？”**，系统却回答了通用网络故障或回答“知识库未提及”。

---

## 1. 核心口述答案：分段排查的四步法

在面试中被问到该问题时，可按以下结构作答：

> **面试口述参考：**
>
> “排查 RAG 检索不相关或回答异常，我遵循**‘断点定界、逆向回溯、观测验证’**的原则，不把整条链路当成黑盒。
>
> **第一步，查看上下文快照快速定界**：直接调取该次请求实际拼装进 LLM 的 Context 内容。如果相关文档块已在 Context 中，说明问题出在**下游生成推理阶段**（如长文本注意力偏置、系统提示词冲突或过于严苛）；若重排结果有目标文档但 Context 缺失，说明被 **Prompt 组装预算截断**；若全链路均未命中，说明问题出在**上游检索召回与重排阶段**。
>
> **第二步，若为检索召回问题，逆向倒查三层**：
> 1. **融合与重排层**：排查 Cross-Encoder Rerank 输入是否被截断（如丢弃了 512 Token 之后的内容）、BM25 分词是否把关键参数切碎、多路融合（如 RRF）权重是否失衡；
> 2. **向量检索层**：排查元数据硬过滤（如租户或时间条件）是否把文档误杀、ANN 近似索引参数（如 HNSW 的 `efSearch`）是否过小导致剪枝漏检、向量化时是否漏掉了模型必须的 Query 前缀；
> 3. **数据切分与预处理层**：排查分块（Chunking）是否把参数名和配置说明切断到了两个文档块、文档解析时是否丢失了表格结构或代码下划线。
>
> **第三步，引入全链路 Trace 观测与回归测试**：在生产环境中为各阶段配置 Span 埋点，记录输入输出，将出错的 Case 转化为自动化回归评测样本，避免局部调优破坏整体表现。”

## 2. 第一阶段定界：上下文快照判定断点

排查线上异常时，不要直接对比用户 Query 与最终生成的 Answer。第一步应调取**实际拼装后发给 LLM 的 Context 内容**作为排查断点。

![判定断点：通过上下文快照划分检索与生成失效边界](/images/content-rebuild/d72c455dcf7da5e7/fig-1.png)

调取 Context 快照后，根据内容状态将排查方向一分为二：

| Context 快照实际状态 | 根因定界 | 在贯穿案例中的典型表现 | 排查责任环节 |
| :--- | :--- | :--- | :--- |
| **包含准确答案所需的信息** | **生成推理阶段失效** | Context 中有 `connect_timeout` 配置说明，但模型回答“未找到”或编造了其他参数 | Prompt 指令冲突、长文本位置偏置、模型指令遵循能力 |
| **完全不包含目标文档** | **检索召回阶段失效** | Context 里全是通用网络连接介绍，完全没有该参数说明 | 数据切分、Embedding 向量表征、ANN 索引、元数据过滤 |
| **包含片段，但关键字段残缺** | **切分与预处理失效** | Context 中只有参数名 `connect_timeout`，具体的单位与示例被切到了下一块 | 分块大小（Chunk Size）、重叠度（Overlap）、文档解析清洗 |
| **包含目标片段，但排位极低且混入大量噪声** | **重排与融合失效** | 目标片段被排在第 15 位，前 5 位全是表面词频重合的无关日志片段 | 多路融合（RRF）权重、Rerank 模型截断或领域偏置 |

关于系统化的量化评估指标，可参考 [如何评估一个 RAG 系统？](rag-evaluation.md)。

## 3. 召回阶段排查：从数据源到向量索引

如果 Context 中完全没有目标文档，说明在多路检索阶段就未命中，需要沿着数据流向排查四个节点：

![召回阶段四大物理失效点排查树](/images/content-rebuild/d72c455dcf7da5e7/fig-2.png)

### 3.1 分块越界截断（Chunk Boundary Fragmentation）
* **现象**：文档库中记录了“`connect_timeout`：单位为毫秒，建议设为 3000；`read_timeout`：建议设为 5000”，但检索出来的 Chunk 只有前半截参数名，配置建议丢失。
* **成因**：使用固定字符长度切分时，切分点刚好落在参数名与说明文字之间。关于切分边界的设计，可参考 [文档切分为什么重要？](chunk-strategy.md) 与 [RAG 中文档切割的 chunk_size 和 overlap 应该如何设置？](rag-chunk-size-overlap.md)。
* **排查方式**：在存储元数据中保留各 Chunk 的起始字符索引（`start_char_idx`、`end_char_idx`），对比原文。如果关键定义常被切断，需增大分块重叠长度（`chunk_overlap`），或采用按 Markdown 标题、段落层级的语义切分方案。

### 3.2 文本清洗与解析损坏
* **现象**：PDF 或 Markdown 中以表格形式记录的参数配置，被解析器提取后变成扁平文本，列名与数值错位；或者文本清洗脚本把变量名中的下划线（`connect_timeout`）清洗为空格，导致后续匹配失效。
* **排查方式**：打印入库前 Document 对象的纯文本，比对源文件排版，检查特殊字符与表格是否保持语义完整。

### 3.3 Embedding 向量表征与检索任务不匹配
* **现象**：短查询“`connect_timeout` 怎么配”无法匹配到详尽的配置手册段落。
* **成因**：部分双向编码器（Bi-Encoder）模型区分非对称检索任务。如果模型规定 Query 端需添加特定前缀（如 `query: `）而文档端需添加 `passage: `，漏加前缀会导致向量分布偏移。更多机制解析参见 [RAG 中的 Embedding 向量化是什么？如何工作的？](rag-embedding.md)。
* **排查方式**：检查在线向量化逻辑与离线入库逻辑是否使用了完全相同的模型权重、文本截断规则、归一化方式（如 L2 归一化）及任务前缀。

### 3.4 元数据过滤与 ANN 近似剪枝误差
* **现象**：离线单测算出的余弦相似度很高，但在线查询未返回该文档。
* **排查方式**：
  1. **检查硬过滤（Metadata Filtering）**：确认请求附带的元数据条件（如 `tenant_id = 'A'`、`status = 'active'`、`env = 'prod'`）是否误将目标文档排除，参考 [RAG 系统如何利用元数据过滤提升检索精度？](rag-metadata-filtering.md)。
  2. **检查 ANN 索引检索参数**：使用 HNSW 索引时，若在线检索参数 `efSearch`（或 IVF 的 `nprobe`）设置过小，搜索算法在图上过早剪枝停止，会降低近邻召回率。可临时调大 `efSearch`（如从 16 调整为 64 或 128）观察目标文档是否出现。
  3. **检查固定阈值设置**：检查检索层是否硬编码了相似度过滤阈值。由于不同向量模型的余弦相似度分布不同，过高的阈值会直接滤除相关文档，参考 [RAG 检索时相似度阈值如何设置？设置不当有什么影响？](rag-similarity-threshold.md)。

## 4. 融合与重排阶段排查：多路召回与 Rerank 异常

生产方案通常采用“向量检索 + BM25 关键词检索”的双路召回，并接 Rerank 模型，详见 [为什么 RAG 中常用 BM25 + 向量检索的混合召回？](hybrid-retrieval.md) 与 [Rerank 在 RAG 中解决什么问题？](rerank.md)。此环节若配置不当，可能导致召回的正样本被后置模块过滤。

![混合检索融合与 Rerank 异常机制排障树](/images/content-rebuild/d72c455dcf7da5e7/fig-3.png)

### 4.1 BM25 词项分词碎裂
* **成因**：Query 包含 `connect_timeout`、`ErrCode_404` 等专有名词时，若分词器缺少专业词库，可能将其拆为 `connect`、`_`、`timeout` 三个词项，导致原本具备精准特征的关键词退化为普通词，BM25 词频统计失真。
* **排查方式**：打印分词器对该 Query 的 Tokenizer 结果，若专有名词被拆碎，需在分词器中补充自定义词表或调整切分规则。

### 4.2 倒数排名融合（RRF）权重失衡
两路召回结果混合时，常使用倒数排名融合（Reciprocal Rank Fusion, RRF）计算综合分数：

$$Score_{RRF}(d) = \sum_{m \in M} w_m \cdot \frac{1}{k + r_m(d)}$$

其中 $r_m(d)$ 为文档 $d$ 在通道 $m$ 中的名次（从 1 开始），$k$ 为平滑常数（通常设为 60），$w_m$ 为通道权重。

* **算例对比**：
  * 设平滑常数 $k = 60$。
  * **文档 A**（精准包含参数说明）：BM25 排名第 1（$r_{sparse}=1$）；向量检索未进入前列，假设排名第 100（$r_{dense}=100$）。
  * **文档 B**（泛讨论网络连接）：BM25 排名第 50（$r_{sparse}=50$）；向量检索排名第 1（$r_{dense}=1$）。
  * **情况 1（等权重 $w_{dense}=1.0, w_{sparse}=1.0$）**：
    $$Score(A) = 1.0 \cdot \frac{1}{60 + 1} + 1.0 \cdot \frac{1}{60 + 100} \approx 0.01639 + 0.00625 = 0.02264$$
    $$Score(B) = 1.0 \cdot \frac{1}{60 + 50} + 1.0 \cdot \frac{1}{60 + 1} \approx 0.00909 + 0.01639 = 0.02548$$
    在此权重下，文档 B 分数高于文档 A，导致精准命中参数的文档 A 排序落后。
  * **情况 2（调整权重 $w_{sparse}=2.0, w_{dense}=1.0$）**：
    $$Score(A) = 2.0 \cdot \frac{1}{61} + 1.0 \cdot \frac{1}{160} \approx 0.03279 + 0.00625 = 0.03904$$
    $$Score(B) = 2.0 \cdot \frac{1}{110} + 1.0 \cdot \frac{1}{61} \approx 0.01818 + 0.01639 = 0.03457$$
    调整权重后，包含精准关键词的文档 A 成功排到前列。
* **排查方式**：若业务查询重度依赖精确编码、配置项名，应检查融合配置，避免向量通道权重过大压制稀疏通道结果。

### 4.3 Rerank 模型输入长度截断
* **成因**：Cross-Encoder 重排模型通常有最大输入 Token 限制（例如 512）。当传入的 Chunk 较长（如 800 Token）时，模型会丢弃后半段内容。若关键配置信息处于该 Chunk 的后半段，Rerank 模型评估时无法看到关键信息，打分会大幅下降，导致正样本被淘汰。
* **排查方式**：检查送入 Rerank 模型的各候选 Chunk 长度，确保 Chunk 大小与 Rerank 模型的有效输入窗口匹配。

## 5. 组装与生成阶段排查：从上下文截断到推理异常

若断点判定显示重排环节已召回目标文档，但模型最终未给出正确答案，需进一步排查上下文组装截断与生成推理两大环节。

![上下文组装截断与生成注意力衰减机制](/images/content-rebuild/d72c455dcf7da5e7/fig-4.png)

### 5.1 上下文物理截断（Token 预算超限）
* **现象**：检索和重排阶段拿到了 5 个文档块，但大模型收到的请求中只有前 2 个。
* **成因**：系统在组装 Prompt 时计算了整体 Token 上限，加上历史多轮对话后超出了模型预算，系统直接从尾部截断了上下文，丢失了排在后面的参考内容，参考 [RAG 中如何设计 Prompt 来有效利用检索到的文档？](rag-prompt-design.md)。
* **排查方式**：打印模型接收到的最终完整请求 Payload，校验其 Token 总数是否触发了客户端截断。

### 5.2 位置偏置（Lost in the Middle）
* **成因**：在长上下文输入下，大语言模型对处于输入头部和尾部的信息关注度较高，对中间段落信息的提取能力可能出现衰减。
* **排查方式**：尝试调整上下文段落拼接顺序（例如将相似度评分最高的文档块放在 Prompt 中靠近提问的位置或 Prompt 最前部），观察生成表现是否有改善。

### 5.3 提示词约束过紧或存在冲突指令
* **成因**：系统提示词中包含“若上下文没有完全一致的表述，必须回答不知道”。当文档中的表述是“超时连接设置项为 `connect_timeout`”，而用户提问“连接超时参数怎么配”时，轻微的用词差异可能导致模型过于保守而拒绝回答。相关原理详见 [RAG 为什么仍然会产生幻觉？](rag-hallucination.md)。
* **排查方式**：微调 Prompt 约束，明确要求模型允许根据上下文做合理的语义同义归纳。

## 6. 生产观测：Trace 埋点与断点诊断代码

排查线上问题需要依赖链路追踪。通过 OpenTelemetry 规范捕获各阶段的输入输出快照：

![全链路 Trace 观测架构与 Span 划分](/images/content-rebuild/d72c455dcf7da5e7/fig-5.png)

### 6.1 各阶段 Span 记录内容

1. `Span: query_transform`：记录原始 Query、改写后 Query 及提取出的元数据 Filter 条件。参考 [Query Rewrite 是什么？](query-rewrite.md)。
2. `Span: retrieval_dense` 与 `retrieval_sparse`：记录双路检索各自召回的文档 ID 列表、原始评分及单路耗时。
3. `Span: rank_fusion`：记录融合算法参数及融合后的排序列表。
4. `Span: rerank`：记录送入重排模型的文本长度、重排前后得分与位次变化。
5. `Span: prompt_assembly`：记录最终送给 LLM 的完整 Prompt 文本、Token 计数及截断标记。
6. `Span: llm_generation`：记录模型返回文本、首字延迟与生成耗时。

### 6.2 断点自动诊断脚本示例

以下 Python 示例展示了如何读取一次请求的 Trace 快照，快速定位故障发生在哪一个阶段：

```python
from typing import List, Dict, Any

def diagnose_rag_pipeline(
    query: str,
    ground_truth_token: str,
    trace_snapshot: Dict[str, Any]
) -> str:
    """
    根据 Trace 记录的快照自动定位 RAG 失效环节
    """
    # 1. 检查 Context 断点：大模型实际收到的参考文档
    context_chunks: List[str] = trace_snapshot.get("llm_context_chunks", [])
    context_hit = any(ground_truth_token in chunk for chunk in context_chunks)
    
    if context_hit:
        # 目标信息已进入上下文，问题在模型推理或 Prompt 阶段
        llm_answer = trace_snapshot.get("llm_answer", "")
        if ground_truth_token not in llm_answer:
            return "【定界结论】：生成推理阶段异常。排查 Prompt 约束过紧、位置偏置或模型指令理解偏差。"
        return "【定界结论】：全链路正常，模型已给出包含目标信息的回答。"

    # 2. 上下文中无目标信息，向前回溯 Rerank 阶段
    rerank_inputs: List[str] = trace_snapshot.get("rerank_candidates", [])
    rerank_hit = any(ground_truth_token in chunk for chunk in rerank_inputs)
    if rerank_hit:
        return "【定界结论】：融合/重排阶段异常。目标文档在 Rerank 输入中，但在重排后跌出 Top-K（排查输入截断或重排模型打分偏置）。"
        
    # 3. 回溯双路召回输出
    dense_results: List[str] = trace_snapshot.get("dense_results", [])
    sparse_results: List[str] = trace_snapshot.get("sparse_results", [])
    dense_hit = any(ground_truth_token in chunk for chunk in dense_results)
    sparse_hit = any(ground_truth_token in chunk for chunk in sparse_results)
    
    if dense_hit or sparse_hit:
        return f"【定界结论】：多路融合阶段异常。单路已召回（向量命中: {dense_hit}, 关键词命中: {sparse_hit}），但在融合计算中被截断。"
        
    # 4. 底层召回均未命中
    return "【定界结论】：底层检索召回异常。排查数据分块边界截断、文档清洗损坏、ANN 索引剪枝参数或元数据硬过滤。"
```

## 7. 面试追问与常见误区

![排障优先级漏斗与反直觉陷阱对比](/images/content-rebuild/d72c455dcf7da5e7/fig-6.png)

### 追问 1：如果离线暴力计算余弦相似度达到 0.88，为什么在线向量检索却没召回该文档？

* **回答要点**：
  1. **元数据过滤条件误杀**：请求中可能带有多租户隔离、环境标签或过期时间等过滤字段，目标文档因属性不匹配在检索前或检索过程中被排除。
  2. **ANN 近似索引图搜索剪枝**：在线查询使用了 HNSW 等近似算法。若服务为了控制延迟将 `efSearch` 设置过小，遍历路径未延伸到该向量所在的分支。
  3. **向量化处理不一致**：离线测试脚本与在线服务采用的代码逻辑存在微小差异，例如在线端漏加了任务前缀（如 `query: `）、离线脚本做了 L2 归一化而在线端未做、或文本截断长度不一致。
  4. **索引未完成写入**：增量数据可能仍停留在内存缓冲区，尚未落盘或完成图索引构建。

### 追问 2：线上遇到返回完全无关文档时，工程上如何做兜底处理？

* **回答要点**：
  1. **相似度保底阈值与拒答**：设定相似度安全基线。当召回结果的最高分数仍低于安全线时，不将噪声文档拼入 Context，而是直接返回兜底文案（如“知识库暂未收录相关依据”）或引导转人工。
  2. **Query 改写监控**：部分无关检索是前置 Query 改写漂移造成的。需监控原始 Query 与改写后 Query 的语义偏离度，若漂移过大则回退使用原 Query。
  3. **失败样本异步沉淀**：将触发低分兜底的请求与检索结果记录到审计队列，排查是否属于分块切断或未收录内容，作为优化索引和扩充测试集的依据。

### 常见认知辨析

* ❌ **误区 1：“检索不准，第一反应是重新微调 Embedding 模型。”**
  * **辨析**：微调模型成本高、周期长，且无法解决工程配置错误。实践中大量检索质量问题往往出在**文档切分混乱、表格解析错位、专有名词被切碎、元数据过滤配置错误**。先理顺数据预处理与检索参数，再评估是否需要微调模型。
* ❌ **误区 2：“混合检索直接把余弦相似度和 BM25 分数加起来即可。”**
  * **辨析**：余弦相似度取值在 $[-1, 1]$ 之间，而 BM25 得分通常是大于 0 的非归一化数值，两者的量纲和数值范围完全不同。直接相加会导致 BM25 得分占据绝对主导。应使用 RRF（基于排名的融合）或通过 Min-Max 归一化对齐两路分数后再做加权。
* ❌ **误区 3：“引入 Rerank 模块后，召回效果一定优于单独的向量检索。”**
  * **辨析**：Rerank 模型大多有严格的 Token 输入长度限制。若候选 Chunk 较长，Rerank 截断会导致关键证据丢失；此外，若通用 Rerank 模型对特定垂直领域的专有名词不敏感，也可能出现负向重排。
