在构建调用大语言模型（LLM）的业务系统时，外部模型服务响应慢、并发限流（HTTP 429）、推理显存溢出以及流式连接中途断开，是系统工程中必然会遇到的常态问题。如果直接套用传统后端接口的简单重试逻辑，往往会引发更严重的问题：面对限流盲目重试会放大请求峰值，造成集群雪崩；在流式响应中断时缺乏状态标记会导致前端界面文字撕裂；在包含工具调用（Tool Call）的 Agent 场景下，重试模型请求可能导致写操作被重复触发。

本文结合一个支持问答和订单退款的 AI 助手实例，拆解从请求发起、首字生成、流式吐字到工具执行全流程中的容错降级方案。

---

## 面试口述速答

如果面试官要求在 1 到 2 分钟内概括大模型调用的容错与降级方案，可以按以下四个维度回答：

> “处理大模型调用异常主要关注四个核心环节：分段超时控制、精细化退避重试、阶梯熔断降级和流式状态对齐。
>
> 1. **分段超时控制**：大模型由于预填充（Prefill）和自回归解码（Decode）耗时差异大，不能只设一个固定总超时。生产中通常拆解为**连接超时**（2~3秒）、**首字到达超时 TTFT**（如 8~15秒）和相邻 Chunk 的**块间间隔超时**（如 3~5秒），避免排队挂起占用连接池，也避免长文本正常生成被误杀。
> 2. **故障分类与抖动退避**：将错误严格分为硬错误与瞬态错误。参数越界、鉴权失败与合规拦截直接终止；面对 429 限流与 503 服务过载，使用**带全抖动（Full Jitter）的指数退避重试**打散并发。特别注意：若请求包含非幂等的外部写工具（如退款、转账），网关层禁止自动重试，必须由编排层配合业务唯一幂等键处理。
> 3. **阶梯熔断与降级**：通过滑动窗口统计调用失败率。触发阈值后开启熔断，将流量按梯度切换：旗舰主模型 $\to$ 同级别备选模型 $\to$ 轻量低成本模型 $\to$ 静态知识库/兜底话术。降级到小模型时，需要同步裁剪上下文窗口，防止次级模型上下文溢出。
> 4. **流式截断与状态一致性**：流式 SSE 传输中途异常无法修改 HTTP 状态码，后端通过自定义流式错误帧（如 `event: error`）通知前端保留已渲染片段，避免界面白屏；服务端将会话状态记为‘未完成’，用户点击继续时利用前缀续写（Prefill Assistant Message）接续生成，降低重复计算成本。”

## 1. 大模型系统调用故障的分类与触发阶段

以一个“电商客服 Agent”为例，用户向模型输入：“请查询我昨天的订单，并申请退款”。大模型服务的物理执行过程分为建立连接、输入预填充（Prefill）、自回归逐步解码（Decode）以及可能触发的外部函数调用。不同阶段发生的故障机理截然不同：

![大模型调用五大核心故障分类与触发阶段关系图](/images/content-rebuild/fb2507dc84010249/fig-1.png)

上图展示了从请求发起、网络传输、首字推理到流式生成的完整生命周期中所对应的五种核心异常分支：

1. **网络握手与鉴权失败（Connection / Auth Error）**：在 TCP/TLS 握手或 HTTP 请求头解析阶段发生。例如 DNS 解析超时、网关证书异常，或 API Key 失效返回 HTTP 401/403。此类问题无法通过原地重试解决。
2. **供应商限流与过载（HTTP 429 / 503）**：HTTP 429 代表请求超出了模型厂商分配的 RPM（每分钟请求数）或 TPM（每分钟 Token 数）配额；HTTP 503 表明推理集群算力饱和或正在发生服务调度。这类故障具备瞬态特征，适合延迟重试。
3. **首字超时（TTFT Timeout）**：客户端请求已发送完毕，但模型服务在 Prefill 阶段处理超长提示词耗时过长，或处于推理并发排队队列中，导致首个 Token 返回时间超过了客户端忍受极限。
4. **流式传输中途截断（Stream Interruption）**：在自回归逐字生成（Decode）阶段，客户端已接收了部分字符（如“您的订单已为您提交申请...”），但服务实例突然遭遇显存溢出（OOM）、达到模型的 `max_tokens` 截断上限，或中间反向代理（如 Nginx）的 Keep-Alive 空闲超时触发断连。
5. **安全合规拦截（Safety & Guardrail Truncation）**：包含输入 Prompt 触发前置审核模型被直接拦截，或模型在生成过程中触碰了后置敏感词策略导致流式传输被服务商强行切断。

下表明确了各类异常的处理原则：

| 故障类型 | 发生阶段 | HTTP/协议表现 | 是否允许原地重试 | 应对策略 |
| :--- | :--- | :--- | :--- | :--- |
| 参数或认证异常 | 接入层 | 400 Bad Request, 401/403 | 否 | 修正入参或更新凭据，直接报错告警 |
| 额度限流 / 集群抖动 | 网关排队 | 429 Too Many Requests, 503 | 是（有条件） | 指数退避加抖动重试，达到上限切换备用供应商 |
| 首字排队过长 | Prefill 阶段 | 网关读超时（Read Timeout） | 是（切换目标） | 断开当前链路，触发同等能力备用模型路由 |
| 流式中途截断 | Decode 阶段 | SSE / WebSocket 异常关闭 | 否（禁止直接重试全量）| 保留当前片段，投递错误帧，提供断点续写 |
| 内容合规拦截 | 前置/后置审核 | 400 或特定 Event 帧阻断 | 否 | 替换为友好合规话术，不计入模型重试 |

## 2. 超时控制与重试退避策略

在传统 Web 接口中，通常为整个 HTTP 请求设置一个固定的整体超时时间（例如 10 秒）。在大模型场景下，由于长文本的 Prefill 和 Decode 计算本身需要十几秒甚至数分钟，固定总超时会产生两难困境：设短了（如 10 秒），长文档问答的首字还未算出就被频繁掐断；设长了（如 60 秒），当模型后端排队假死时，客户端与网关的连接池会被长期占满无法释放。

### 分段超时设计

合理的做法是将超时监控拆解为针对不同推理周期的分段阈值：

*   **连接建立超时（Connect Timeout）**：设置在 $2\text{s} \sim 3\text{s}$ 左右，仅覆盖 TCP 三次握手和 TLS 协商。
*   **首字到达超时（TTFT Timeout）**：客户端完成请求发送到收到第一个 SSE 数据包的时间。普通任务通常设为 $8\text{s} \sim 15\text{s}$。一旦超时，说明模型服务排队严重，应主动放弃该连接并转寻备用路由。
*   **块间间隔超时（Chunk-to-Chunk Idle Timeout）**：自回归生成阶段两个相邻 Token Chunk 返回的时间差。正常自回归解码每秒可输出几十个 Token，两个 Chunk 间隔通常在几十毫秒到几百毫秒。将块间超时设为 $3\text{s} \sim 5\text{s}$，一旦超过该阈值，即可认定下游计算节点出现故障或连接假死，直接中断。
*   **总流程兜底硬超时（Wall-clock Timeout）**：整个任务的最大允许时间（如 $60\text{s} \sim 120\text{s}$），防止模型进入死循环反复吐字。

![分段超时（TTFT与块间超时）和退避抖动机制时序图](/images/content-rebuild/fb2507dc84010249/fig-2.png)

### 指数退避与全抖动（Full Jitter）

当遇到 429 限流或 503 服务不可用时，如果多个并发客户端在固定间隔（例如每隔 1 秒）同时重试，会导致供应商服务遭遇“惊群效应（Thundering Herd Problem）”，加剧拥堵。必须采用**带全抖动的指数退避算法**打散重试时机。

退避时间的数学计算方式如下：

$$T_{\text{ceiling}} = \min\left(T_{\max},\; T_{\text{base}} \times 2^{\text{attempt}}\right)$$
$$T_{\text{sleep}} = \text{Uniform}\left(0,\; T_{\text{ceiling}}\right)$$

其中 $T_{\text{base}}$ 为基础重试间隔时间（如 $1.0\text{s}$），$T_{\max}$ 为最大上限（如 $16.0\text{s}$），$\text{Uniform}(0, T_{\text{ceiling}})$ 从 0 到当前指数上限区间内进行均匀随机采样。

```python
import time
import random
from typing import Callable, Any

class TransientLLMError(Exception):
    """临时性异常，包括 429 限流或 503 服务过载"""
    pass

def retry_with_full_jitter(
    max_attempts: int = 3,
    base_delay: float = 1.0,
    max_delay: float = 16.0
) -> Callable:
    def decorator(func: Callable) -> Callable:
        def wrapper(*args: Any, **kwargs: Any) -> Any:
            attempt = 0
            while attempt < max_attempts:
                try:
                    return func(*args, **kwargs)
                except TransientLLMError as e:
                    attempt += 1
                    if attempt >= max_attempts:
                        raise e
                    # 计算全抖动退避时长
                    ceiling = min(max_delay, base_delay * (2 ** attempt))
                    sleep_duration = random.uniform(0, ceiling)
                    time.sleep(sleep_duration)
        return wrapper
    return decorator
```

### 幂等性控制：只读与外部写操作的边界

重试操作的先决条件是操作具备**幂等性（Idempotency）**：
*   **普通文本补全与 RAG 检索**：属于只读操作，多次执行不会对外部产生副作用，在满足重试条件时可以安全执行重试。
*   **Agent 外部工具调用（Tool Call）**：在客服场景中，如果模型生成了 `refund_order(order_id="10086", amount=50)` 的工具调用。如果网关层在等待模型响应时断开，由于无法确定大模型是否已经将参数发出并交由执行器执行，**网关层严禁盲目发起重试**。若盲目重发请求，可能导致大模型再次产生相同的退款指令，下游系统若无幂等校验就会执行两次退款。此类包含写副作用的请求，必须由 Agent 框架层结合业务唯一的幂等键（Idempotency Key）进行去重判断，具体异常治理可参考 [/llm-100/agent-engineering/agent-tool-failure.md](/llm-100/agent-engineering/agent-tool-failure.md)。

## 3. 滑动窗口熔断与阶梯降级设计

当某个模型供应商发生大面积机房故障或网络光缆中断时，重试机制不仅无法恢复服务，反而会迅速堆积线程池导致系统级瘫痪。此时需要熔断器切断故障路由，并顺次触发多级降级链。

![阶梯熔断与多级降级状态迁移图](/images/content-rebuild/fb2507dc84010249/fig-3.png)

### 熔断器状态流转

系统通过滑动窗口（例如统计最近 50 次请求或最近 30 秒的样本）持续计算指标：
1.  **CLOSED（正常关闭态）**：所有请求正常打入主模型。当窗口内失败率（含网络中断、429、TTFT 超时）超过设定阈值（例如 $30\%$）时，熔断器打开。
2.  **OPEN（开启熔断态）**：直接拦截发往主模型的调用，不再发起真实网络请求，请求无缝旁路路由至下一级降级链路，持续保持一个冷却期（例如 $30\text{s}$）。
3.  **HALF-OPEN（半开试探态）**：冷却期结束后，放行固定数量的探针请求（Probe Requests，如 5 个）打向主模型。若探针请求全部成功，熔断器恢复至 CLOSED 状态；若依然出现异常，重新回到 OPEN 状态并重新计时冷却期。

### 降级链路与参数适配

熔断降级链的设计通常按能力和成本自顶向下排列：

```
用户请求
   │
   ├── (熔断正常) ──> [主模型：例如旗舰级推理模型]
   │                     │ (超时 / 熔断开启)
   │                     ▼
   ├── (一级降级) ──> [备选模型：另一供应商同等级模型]
   │                     │ (仍不可用)
   │                     ▼
   ├── (二级降级) ──> [轻量模型：高吞吐小参数量模型]
   │                     │ (仍不可用)
   │                     ▼
   └── (兜底防御) ──> [降级兜底知识库 / 预置规则话术]
```

在将请求降级至不同模型时，不能直接复用原本的请求体（Payload），需要完成两处工程适配：
1.  **上下文窗口对齐与剪裁**：主模型若支持 $128\text{k}$ 上下文，而降级到的轻量模型可能仅支持 $32\text{k}$。降级网关必须在转交请求前裁剪历史会话轮次，或采用滑动窗口保留最新的关键信息，防止次级模型直接抛出 `Context Window Exceeded` 异常。会话管理的具体裁剪策略可参考 [/interview/ai-system-design-interview/session-context-management.md](/interview/ai-system-design-interview/session-context-management.md)。
2.  **调用参数与结构兼容**：不同模型对于 `temperature` 的有效范围不同，且部分轻量模型不支持 `tools` 字段或结构化 JSON Schema 强制约束。降级中间件必须过滤不支持的高级字段，转为纯文本提示（Prompting）模式。

## 4. 流式传输断裂处理与状态一致性

在使用 Server-Sent Events（SSE）或 WebSocket 的大模型应用中，最具挑战性的故障是**流式生成中途断裂**：模型已经输出了“退款已成功，金额将在”，此时由于连接中断，后续 Token 无法抵达客户端。

由于 SSE 在刚建立连接时，HTTP 响应头（`HTTP/1.1 200 OK`、`Content-Type: text/event-stream`）就已经发送完毕，当传输途中发生异常时，**服务端无法再将 HTTP 状态码回写为 500**。如果中间连接直接掐断，前端界面只看到光标悬停，最终抛出原生的网络断开异常，导致用户体验割裂。

![流式传输中途断裂时的前后端状态对齐与补偿流程图](/images/content-rebuild/fb2507dc84010249/fig-4.png)

### 流内显式错误帧设计

为保证前端感知并优雅处理中途断裂，系统应在 SSE 协议层定义结构化错误事件：

```text
data: {"delta": "您好，经查询您的订单处于正常退款周期内。"}

data: {"delta": "退款将在1-3个工作日内退回原账户，具体"}

event: error
data: {"error_code": "STREAM_DECODE_TIMEOUT", "message": "推理节点响应中断", "received_tokens": 32, "resumable": true}
```

前端通过监听 `error` 事件捕获通知，执行以下操作：
1.  停止光标跳动，**锁定并保留当前已渲染出来的文本**，禁止页面直接白屏清空；
2.  在文本末尾显示“（连接已断开）”，并渲染“继续生成”或“重新回答”的操作按钮。

### 后端状态一致性与前缀续写（Prefill Assistant Message）

在服务端数据库层面，流式生成中的消息若中途挂掉，不能简单记录为生成成功：
*   **状态字段标记**：消息表对应记录标记为 `STATUS_INTERRUPTED`，并保存已成功输出的文本切片与 Token 计数。
*   **断点前缀续写补偿**：当用户点击“继续生成”时，服务端无需让大模型把整段文字从头到尾重算一遍。若底层模型支持前缀填充（Prefill Assistant Response），可将已生成的片段直接塞入 `assistant` 角色的前缀中：

```json
[
  {"role": "user", "content": "请帮我写一份退款政策说明。"},
  {"role": "assistant", "content": "退款政策说明如下：1. 用户在下单后7天内可申请...具体办理步骤：", "partial": true}
]
```

模型接收到该请求后，会直接从“具体办理步骤：”后面接着生成剩余内容。这避免了重新自回归解码（Decode）已输出文本的高额延迟与前端界面的重复吐字；若底层推理引擎命中该前缀的 KV 缓存，还能进一步降低预填充（Prefill）阶段的重复计算开销。

## 5. 内容安全拦截降级：双阶段审查与响应转换

内容安全审查是大模型系统特有的故障来源。当用户提问或模型回答触发合规拦截时，这不是服务不稳定，而是预设的安全保护，**绝对不能当作普通网络错误去发起重试**。

![双重内容安全拦截处理机制图](/images/content-rebuild/fb2507dc84010249/fig-5.png)

内容审查在工程上拆分为前置和后置两个阶段：

### 前置输入审查（Pre-filter 拦截）
用户输入在发往大模型前，先通过轻量级审核模型或正则关键词树进行检测。若命中违规策略：
*   **直接在网关层截断**：不向大模型发起调用，节省算力和 Token 成本；
*   **返回预置友好话术**：返回标准应答（例如：“您输入的内容涉及敏感安全策略，无法为您生成回答”），将 HTTP 状态码设为 400，并在元数据中注明安全拦截标识。

### 后置流式输出审查（Post-filter 拦截）
大模型在生成过程中可能在前半句表达合规，而在后半句突然生成涉敏内容。系统通常采用**滑动缓冲窗口**机制：
1.  网关接收到模型产生的 Token 后，不立即推给前端，而是暂存在一个微小缓冲区内（如 10~20 个字符）；
2.  合规检测服务对缓冲区文本做滑动审核；
3.  一旦命中违规，网关立即向前端发送 `event: content_blocked` 帧并切断连接；
4.  前端接收到此事件后，将最后一句涉敏内容清理并替换为合规兜底说明；
5.  后端将会话记录打上安全拦截标记，**在下一轮多轮对话拼接 Prompt 时，禁止将这轮涉敏输出装配到上下文**中，防止污染后续对话。

![非幂等 Agent 动作与流式断点故障处理反模式与正解对比图](/images/content-rebuild/fb2507dc84010249/fig-6.png)

### 典型面试追问

#### 追问 1：在流式生成中途模型超时断开，如何在前端与持久层之间做好状态对齐？

**口述要点**：
*   **协议层**：因为 HTTP 200 响应头已发出，不能靠 HTTP 状态码报错。必须在 SSE 或 WebSocket 协议中推送自定义错误事件（如 `event: error`），携带结构化错误原因和断点信息。
*   **视图层**：前端捕获错误后冻结已渲染的文本内容，禁止白屏，并在末尾展示断点续写提示。
*   **数据层**：服务端将会话标记为不完整状态，保存当前已经投递成功的文本段落。
*   **补偿策略**：支持前缀填充的模型可通过组装未完成的历史回复作为 Prompt 前缀直接“断点续写”；不支持前缀续写的模型则提示用户“重新生成”，并在重试时清空该条未完成记录。

#### 追问 2：为什么针对包含外部写操作的 Agent（如转账、下单），网关层绝对不能做无脑自动重试？

**口述要点**：
*   **副作用非幂等**：写操作执行会改变外部状态。如果大模型已经生成了调用工具的参数，但在等待模型接收或返回阶段发生超时，网关无法断定外部动作是否已经落地。
*   **盲目重试产生二次写入**：若网关层直接对模型请求重新发起调用，大模型大概率会再次生成相同的 Tool Call 参数，导致下游执行器重复执行，造成扣款翻倍等事故。
*   **治理原则**：在网关层识别到请求包含非幂等工具声明时，应禁用网关自动重试；将重试决策移交至 Agent 编排层，并在工具执行端注入全局唯一的业务幂等键（Idempotency Key）进行去重。更多网关与路由设计可参考 [/interview/ai-system-design-interview/multi-model-gateway.md](/interview/ai-system-design-interview/multi-model-gateway.md)。

### 生产可观测性验收指标

评估容错与降级机制运行状态时，推荐关注以下核心指标：

| 监控指标 | 计算定义 | 生产参考范围 | 异常指示含义 |
| :--- | :--- | :--- | :--- |
| **降级触发率（Fallback Rate）** | $\frac{\text{降级处理请求数}}{\text{总调用请求数}} \times 100\%$ | 建议 $< 1.0\%$ | 持续偏高说明主模型配额不足、供应商稳定性恶化或超时阈值偏窄。 |
| **重试有效率（Retry Success Rate）** | $\frac{\text{重试后成功的次数}}{\text{发起重试的总次数}} \times 100\%$ | 建议 $> 50\%$ | 若低于 $30\%$，说明重试多为无法恢复的硬故障，应减少重试以保护下游。 |
| **TTFT P99 超时率** | $\frac{\text{因首字超时主动切断的请求数}}{\text{总请求数}} \times 100\%$ | 建议 $< 0.5\%$ | 反映推理服务排队拥塞与 Prefill 性能瓶颈。 |
| **流式异常中断率（Stream Drop Rate）**| $\frac{\text{流式生成途中被动断开的请求数}}{\text{成功建连的流式请求总数}} \times 100\%$ | 建议 $< 0.1\%$ | 反映长文本解码期间网络连接保活状态或推理实例显存稳定性。 |
| **非幂等重复拦截数** | 依赖幂等键成功拦截的重复 Tool Call 计数 | 依业务并发而定 | 验证 Agent 写操作在网关与工具层面的幂等防重机制是否实际生效。 |

通过对超时细分治理、退避抖动控制、熔断阶梯流转与流式状态对齐，系统可以在面对外部模型抖动与网络断连时，兼顾服务可用性与业务数据一致性。
