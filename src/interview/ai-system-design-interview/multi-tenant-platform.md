在同时面向多个企业或内部多团队的 AI 问答场景中，系统不仅要完成检索增强生成（RAG）的常规流程，还要解决多租户环境下的几个典型矛盾：如何在控制硬件成本的同时保证数据隔离？如何防止长尾小客户拖垮向量数据库的内存索引？如何在外部大模型 API 限流的情况下避免离线灌库影响在线客服？

我们以一个具体场景贯穿全文：平台上有 1 家拥有 10 万份合同的大型企业客户（租户 A），同时还有 5,000 家各自只有几十份规章手册的中小团队（长尾租户 B 群）。系统必须在同一套平台上安全、稳定地支撑这两类客户。

### 面试口述核心回答

> **面试官提问**：如何设计一个支持多租户与多知识库的 AI 问答平台？
>
> **口述回答结构**：
> “设计多租户 AI 问答平台的核心，是在**安全隔离、检索性能与资源成本之间做分层折中**。整体方案分为四个部分：
>
> 1. **分级存储与向量隔离**：针对关系型元数据，采用共享库表结合租户 ID 逻辑隔离（配合数据库行级安全策略 RLS）；针对向量数据，对长尾小租户采用固定数量的共享分片集合并结合标量过滤，对数据量大或合规要求高的 VIP 租户分配独立集合（Collection）或物理集群，避免海量小索引耗尽系统内存。
> 2. **服务端强制鉴权**：建立‘租户 - 空间/部门 - 知识库 - 文档切片’四层权限模型。在网关层完成身份校验后，由业务服务端根据该用户的组织与角色权限，自动构造只读的过滤条件（Filter）硬编码拼入检索请求，不信任前端传入的过滤参数，从源头防止跨租户越权。
> 3. **双轨资源调度防抢占**：将‘在线低延迟问答’与‘离线批量切分/Embedding’拆分为两条独立的计算流水线。在模型接入层实现两级令牌桶配额（平台全局限流 + 租户私有配额），为在线问答预留硬保障配额，限制离线任务的瞬时并发，防止单个租户大批量上传文档耗尽外部 API 速率。
> 4. **异步事件驱动计量**：在网关与计算 Worker 埋点，将 Token 消耗、切分字符量与向量存储量封装为事件异步写入消息队列，经流处理引擎按租户与知识库聚合后写入持久化库，并联动缓存做准实时额度扣减与超额熔断。”

### 隔离维度权衡：物理独占 vs 共享集群

多租户系统并不是在“完全物理独立”和“完全共享”之间二选一，而是要根据计算、存储和网络等不同模块的成本敏感度和合规要求，进行分层选型。

![多租户系统在计算、存储与网关各层的隔离选型决策矩阵](/images/content-rebuild/46dca57f4aefd065/fig-1.png)

| 架构层级 | 物理独占（Silo / Dedicated） | 共享集群 + 逻辑隔离（Pool / Shared） | 混合分级（Tiered Hybrid） |
| :--- | :--- | :--- | :--- |
| **业务与检索服务** | 租户独占容器实例或独立集群；完全无资源争抢；实例闲置成本高。 | 所有租户共享无状态服务，通过请求上下文（Context）传递 `tenant_id`；成本利用率高。 | 网关与调度中心统一共享，高价值大客户调度至专属弹性计算节点。 |
| **关系型元数据** | 单租户独立数据库实例（Database per Tenant）；合规性好，但跨库升级与运维复杂。 | 共享数据库与表，使用 `tenant_id` 字段结合 PostgreSQL RLS（行级安全）；开发需严格防范注入。 | 共享数据库但按租户分区存储，大客户支持动态挂载独立库。 |
| **向量数据库** | 租户独占向量节点/集群；无索引内存干扰；小数据量下节点内存底噪大。 | 共享集合，靠元数据过滤；小数据量下成本低，极端数据不均衡下检索耗时增加。 | 长尾小租户归入共享分片池，大租户按需创建独立集合或分片。 |
| **模型与网关配额** | 租户绑定独立商用 API Key 或私有部署卡；成本高，但无配额争抢风险。 | 共享企业主账号与网关配额，网关层通过软限制限流；单租户超载易拖垮全局。 | 共享网关底座，但在网关内实施租户级双级令牌桶与配额硬隔离机制。 |

在绝大多数 SaaS 平台中，主流做法是**控制面与基础网关统一共享，数据面与计算资源按客户量级分层隔离**。

### 向量检索的多租户策略与性能问题

在多租户 RAG 架构中，向量数据库是隔离与成本矛盾最集中的地方。关于单知识库内部的检索与切分机制，可参考 [企业知识库问答系统设计](/interview/ai-system-design-interview/knowledge-base-qa.md)。在多租户场景下，常见的组织方式有以下三种：

![向量数据库三种多租户实现方案及其索引图结构对比](/images/content-rebuild/46dca57f4aefd065/fig-2.png)

#### 1. 独立集合（Collection / Namespace per Tenant）
每个租户创建独立的集合，拥有完全独立的图索引文件（如独立的 HNSW 图结构或 IVF 列表）。
* **机制**：检索仅在租户自己的索引内部执行，不存在跨租户查出无关数据的风险。
* **问题**：以主流的 HNSW 索引为例，每个集合都有基础开销（包括固定内存、段文件元数据和文件句柄）。如果平台有 5,000 个长尾小租户，每个租户只有 20 篇文档，创建 5,000 个集合会导致向量节点产生海量微小索引结构，内存底噪激增，文件句柄耗尽，集群管理面压力极大。

#### 2. 纯元数据过滤（Metadata Filtering in Shared Collection）
所有租户的数据放在同一个大集合中，每个向量的属性字段携带 `tenant_id`。
* **后过滤（Post-filtering）的问题**：系统先在全量向量中通过距离计算选出全局 Top-$K$ 个候选项（例如 $K=50$），随后剔除 `tenant_id != 当前租户` 的记录。若当前小租户的数据量仅占全库的 $0.1\%$，召回的 50 个全局最近邻中，极大概率 1 个都不属于该租户，导致最终返回给用户的有效证据直接为空（召回失败）。
* **前过滤（Pre-filtering / Single-stage）的问题**：系统先找出满足 `tenant_id` 的所有向量 ID，在图索引遍历时只访问符合条件的节点。如果某大租户数据量极大（占库里 $90\%$），其余小租户在图中的目标节点非常稀疏，前过滤会导致遍历算法在图节点间跳跃时频繁遇到无效节点并产生大量回溯，甚至退化为局部的暴力扫描，查询延迟明显上升。

#### 3. 分级策略实践
为了兼顾成本与性能，生产中通常采用分级组合：
* **单租户向量数 $< 10^4$（长尾小租户）**：进入预先创建的固定数量共享分片集合（如 128 个 Shard），利用单阶段过滤协同遍历，保持底层 HNSW 图的连通性。
* **单租户向量数 $\ge 10^5$ 或企业大客户**：动态创建独立的 Collection 或专属物理分片，享受独立索引的高性能与完全物理隔离。

### 知识库元数据与权限治理

知识库的安全不仅是区分 A 租户与 B 租户，还涉及租户内部部门、团队及员工个人的访问授权，必须防止员工检索到越权的敏感文档。基础的安全与数据隔离规范可延伸阅读 [AI 系统权限控制与数据隔离](/interview/ai-system-design-interview/security-privacy.md)。

![租户、部门、知识库与切片权限的级联鉴权流向图](/images/content-rebuild/46dca57f4aefd065/fig-3.png)

#### 资源层级建模
系统通常建立四层树状结构：
1. **Tenant（租户）**：顶层计费与隔离边界，具有全局唯一的 `tenant_id`。
2. **Workspace / Department（工作区/部门）**：租户下的业务分组，定义数据边界。
3. **Knowledge Base（知识库）**：挂载在部门下的文档集，包含切分规则与模型配置。
4. **Document & Chunk（文档与切片）**：最小检索单元。切片的 Payload 固化继承上层标签：
   ```json
   {
     "chunk_id": "chk_9821a",
     "tenant_id": "tenant_enterprise_01",
     "kb_id": "kb_hr_policy",
     "acl_read": ["role:all_employees", "dept:hr"],
     "vector": [0.012, -0.045, 0.088]
   }
   ```

#### 检索链路的服务端强制鉴权
用户提问时的过滤条件不能信任前端传入的参数，必须在服务端组装：
1. **身份解析**：网关验证 JWT，提取经过签名的 `tenant_id`、`user_id` 及其所属角色和部门。
2. **权限条件组装**：业务服务从元数据库查询当前用户被允许访问的 `kb_id` 列表与访问控制标签（ACL），在服务端组装成过滤表达式：
   $$\text{Filter} = (tenant\_id == \text{CurrentTenant}) \land (kb\_id \in [KB_1, KB_2]) \land (acl\_read \cap UserRoles \neq \emptyset)$$
3. **强制拼入检索**：该过滤条件在底层被硬编码传入向量库与全文索引，业务接口层不暴露绕过该条件的通道。

### 资源争抢（Noisy Neighbor）防范与调度

多租户系统中最常见的运行问题，是某个租户上传了上千份长文档触发批量 Embedding，将平台的大模型网关并发打满，导致另一个租户的客服问答请求因超时失败。

![在线低延迟与离线高吞吐双轨流水线及多级限流调度图](/images/content-rebuild/46dca57f4aefd065/fig-4.png)

#### 1. 在线与离线计算双轨分离
必须将离线高吞吐任务与在线低延迟任务拆开：
* **离线链路**：文档 OCR、解析、切分与批量 Embedding。任务进入异步队列（如 Kafka、Celery），限制离线 Worker 的总并发数，保证吞吐可控。
* **在线链路**：用户的交互式问答，对端到端延迟敏感（通常要求控制在数秒内）。此链路走独立的无状态服务与网关信道。

#### 2. 双级限流机制
外部大模型服务商通常会对整个企业账号设置总并发限制（如 10,000 RPM 或固定的每分钟 Token 数 TPM）。有关多模型路由的基础设施可参阅 [多模型网关设计](/interview/ai-system-design-interview/multi-model-gateway.md)。平台内可采用双级限流策略：
* **第一级：平台全局模型配额**：受控于外部大模型服务商的物理上限。
* **第二级：租户私有配额**：按租户付费等级分配：
  * 租户 A（大客户）：分配固定保障比例（例如 $40\%$ 的配额保障），突发流量允许临时借用空闲资源。
  * 租户 B（免费/入门）：限制瞬时吞吐上限，离线批量任务只能使用低优先级队列。

当租户 A 进行大批量离线切片时，其离线 Worker 只能消耗受限的离线配额。一旦租户 B 发起前台问答，网关通过加权公平排队（WFQ）或保留配额，确保在线请求立即被转发，阻断离线任务对在线问答的挤占。相关的降级与熔断实现可参考 [AI 系统故障处理与降级策略](/interview/ai-system-design-interview/failure-handling.md)。

### 按租户计量与计费流水线

AI 问答平台的成本主要来自三部分：**大模型 Token 成本（调用产生）、向量库与文档存储成本（持有产生）以及离线计算资源（解析产生）**。监控体系建设可参阅 [AI 应用日志监控与成本统计](/interview/ai-system-design-interview/logging-monitoring.md)。

![端到端多维度异步计量、事件上报与账单汇总数据流](/images/content-rebuild/46dca57f4aefd065/fig-5.png)

#### 计量数据指标
1. **大模型调用**：记录 `tenant_id`、`kb_id`、`model_name`、`prompt_tokens`、`completion_tokens` 与耗时。
2. **向量与文档处理**：
   * 文档解析：按解析文档页数或 OCR 耗时计量。
   * Embedding：按送入切分模型的总字符数转换后的 Token 计量。
   * 向量存储：定期统计各租户持有的向量条数与存储占用大小（GB·天）。

#### 异步计量架构
计量操作不能与在线问答同步写库，避免拖慢主流程：
1. **事件采集**：网关在模型调用正常结束、客户端流式提前断开或网络超时终止时，均在连接清理钩子（Hook）中提取实际已消耗的 Prompt 与 Completion Token（防止用户主动中断流式输出导致平台为上游模型已产生的计费垫资），随后向消息队列发送轻量级计量事件：
   ```json
   {
     "event_id": "evt_77182931",
     "tenant_id": "tenant_enterprise_01",
     "timestamp": 1718002931,
     "service": "llm_generation",
     "sku": "gpt-4o-completion",
     "quantity": 342,
     "cost_unit": "tokens"
   }
   ```
2. **流式聚合与准实时扣费**：流计算引擎消费消息队列，按 `(tenant_id, 1-minute)` 窗口进行滑动聚合，并将已消耗额度同步到 Redis 缓存。
3. **配额超额处理**：当租户额度耗尽时，更新 Redis 状态。网关在后续请求鉴权时拦截并提示充值，或降级为低成本小参数模型，防止平台发生亏损透支。

### 面试高频追问与方案权衡

#### 追问 1：在几十万长尾小客户场景下，如何避免向量索引耗尽内存？

![针对长尾小租户与 VIP 大租户的混合向量路由存储方案](/images/content-rebuild/46dca57f4aefd065/fig-6.png)

**口述要点**：
* **原因**：每个独立的向量 Collection 都有固定的内存开销和句柄占用。几十万个微型集合会产生海量微小索引结构，导致操作系统句柄耗尽和严重的内存碎片化。
* **方案**：采用**哈希共享池与动态升级**：
  1. **长尾小租户**：创建固定数量的共享集合（例如 128 个 Shard），小租户通过 `hash(tenant_id) % 128` 路由到对应集合。集合内使用租户 ID 进行标量过滤检索。数千个小租户合并后维持了索引图的合理规模，避免创建过多物理集合。
  2. **大客户升级**：当某租户向量条数超过设定阈值（例如 5 万条），后台触发迁移任务，为其创建独立集合并更新元数据路由。
  3. **冷分片与专属集合卸载**：由于共享分片内部无法单独剥离单个租户的图拓扑，内存卸载只能以集合或段（Segment）为粒度。对于独占集合的 VIP 租户，长期无访问时可直接将其索引从内存卸载（Release）降级为磁盘存储；对共享池中的长尾租户，则可结合访问热度定期归档到独立的冷数据分片中，查询时再按需加载或利用 mmap 按页调度。

#### 追问 2：为什么直接用 `tenant_id` 元数据过滤在数据极不均衡时会导致检索延迟上升？

**原理与原因**：
* **图遍历受阻**：HNSW 索引依赖在多层图上沿着相近向量跳跃。如果一个集合中 $99\%$ 的数据属于大租户，仅 $1\%$ 属于目标小租户，单阶段前过滤算法在图上每一步试探，遇到的节点大概率都不符合过滤条件。
* **回溯与探索激增**：由于目标节点极度稀疏，算法需要遍历和回溯远超正常数量的节点才能找齐 Top-$K$ 个符合条件的候选点。当预设的搜索深度（`efSearch`）耗尽仍未集齐候选点时，甚至可能被迫降级为大面积局部扫描，导致检索时间从数毫秒拉长到上百毫秒。

#### 追问 3：大租户大量上传文件做 Embedding，如何避免挤爆外部 API 导致其他租户在线问答超时？

**应对方案**：
* **根因**：外部模型供应商（如 OpenAI、Anthropic）通常以组织为单位限制全局并发（RPM/TPM）。离线批量切分 Worker 会迅速占满全部配额，导致后续在线问答请求遭遇 HTTP 429。
* **防范措施**：
  1. **配额硬切分**：网关层把外部 API 的总 TPM 切分为两部分，例如 $60\%$ 划归“在线专属池”，离线任务绝对不能占用；剩余 $40\%$ 作为离线与共享池。
  2. **离线任务漏桶限速**：切分 Worker 的 Embedding 请求必须通过漏桶进行平滑整形，限制单租户的最大并发线程数，严禁批量任务瞬间打满共享池。
  3. **主动降级退避**：当网关检测到外部 API 接近限速阈值时，优先对离线 Worker 返回限流信号，触发离线任务指数退避，优先保障在线问答的正常响应。
