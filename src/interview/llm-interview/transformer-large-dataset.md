在预训练一个百亿至千亿参数级别的 Transformer 模型时，工程团队通常面临两个紧密交织的问题：一是如何从数十 TB 甚至 PB 级的原始网络抓取文本中，清洗出低噪声、低重复率的高质量语料；二是如何将远超单卡显存容量的模型参数与海量数据，切分并映射到数百乃至上千张 GPU 组成的集群上高效训练，并在发生硬件故障时准确恢复。

我们将以一个具体的工程场景作为贯穿示例：**预训练一个 130B（1300 亿）参数的解码器模型，处理 1 万亿（1T）Token 的清洗后语料，底层集群为 1024 张 80GB 显存的 A100 GPU**。通过该场景，本文系统梳理从离线数据预处理、批次打包到多维并行训练与故障恢复的完整协作过程。

## 30秒口述结论

> 面试回答要点：
> 
> **处理海量语料与超大模型训练，核心在于“离线数据清洗与序列打包”结合“3D 分布式并行与显存状态切分”。**
> 
> 1. **在数据端**：原始网页先经过**规则过滤**（剔除异常符号、过短过长文本和低质文档），再通过 **MinHash LSH** 完成海量文档的模糊去重与有害信息过滤；分词后使用**序列打包（Sequence Packing）**将多个短文本拼接为固定长度输入，配合**分段因果掩码（Block-diagonal Mask）**和**重置 Position IDs** 避免跨样本注意力污染与位置错乱，消除常规填充带来的无效矩阵计算。
> 2. **在集群训练端**：130B 模型的静态权重、梯度与优化器状态远超单卡显存（常规 FP16 训练需 2000GB 以上）。工程上采用 **3D 并行（TP + PP + DP）结合 ZeRO-1**：节点内部借助高速 NVLink 进行**张量并行（TP，如 8 卡）**切分单层矩阵乘法；节点间通过网络进行**流水线并行（PP，如 8 阶段）**切分层级并采用 1F1B 调度；数据维度采用 **ZeRO-1（如 16 路）**分片优化器状态。在训练中结合**异步检查点（Async Checkpointing）**保存优化器动量、随机种子与数据游标，实现硬件故障时的精确续训。

## 数据预处理流水线：从原始抓取到高质量语料

模型的泛化能力与知识储备直接取决于预训练数据的质量与多样性。从 Common Crawl 等网络抓取渠道获取的原始 HTML 文本含有大量乱码、导航栏模板、广告轮播和低质文本，必须经过多阶段流水线处理。

![数据工程流水线：从原始网络抓取到高质量预训练语料的分层清洗机制](/images/content-rebuild/64d08fbdcda30fef/fig-1.png)

### 1. 文本抽取与规则过滤

在完成基础的 HTML 标签剥离与编码转换后，首先利用统计规则进行初筛：

* **异常字符分布**：计算标点符号、特殊符号、数字及大写字符占全文字符的比例。若非标准字符占比过高（例如特殊标点占比超过 30%），通常判定为机器生成的干扰字符、未解析的代码片段或乱码。
* **长度与词汇特征**：过滤总词数过少（如低于 50 个 Token）或段落行数极少的文档；计算文档的平均词长，丢弃词长严重偏离正常语言范围的文本；统计停用词密度，过滤缺少完整语法结构的词汇堆砌页面。
* **重复度统计**：统计单篇文档内部的字符级、字词级（$n$-gram）及行级重复率。网页抓取中常见的网站版权声明、导航栏菜单、防爬蜜罐段落会呈现极高的局部重复性。若直接输入模型，会导致生成时倾向于陷入无限重复循环。
* **语种识别与质量模型初筛**：使用轻量分类器（如 fastText 语种识别模型）过滤非目标语种及代码与自然语言严重混杂的无效页面。

### 2. 海量文本模糊去重：MinHash 与局部敏感哈希（LSH）

在数 TB 到数 PB 的文本中，存在大量微小差异但内容高度近似的文档（例如带有不同时间戳的新闻转发、模板化产品介绍）。精确哈希（如 SHA-256）只要有一字之差就会输出完全不同的哈希值，无法检测近重复文本。工程上通常采用 **MinHash + LSH** 算法计算 Jaccard 相似度并完成近邻聚类：

1. **$k$-shingle 分词集合化**：将文本按字符或单词滑动切分为长度为 $k$ 的短语集合 $S$（例如 $k=5$ 的 5-gram）。
2. **最小哈希签名（MinHash）**：
   两篇文档 $A$ 和 $B$ 的 Jaccard 相似度定义为：
   $$J(A, B) = \frac{|A \cap B|}{|A \cup B|}$$
   采用 $m$ 个相互独立的哈希函数 $h_1, h_2, \dots, h_m$。对文档切分出的每个元素计算哈希值，取集合中的最小值作为特征：
   $$\text{sig}_i = \min_{x \in S} h_i(x)$$
   在数学上，随机置换后两个集合最小哈希值相同的概率恰好等于它们的 Jaccard 相似度：
   $$P(\min_{x \in A} h(x) = \min_{y \in B} h(y)) = J(A, B)$$
   因此，长度为 $m$ 的签名向量中匹配元素的比例，即为文档相似度的无偏估计。
3. **LSH 分桶筛选（Banding）**：
   若对所有文档两两比对签名向量，时间复杂度为 $O(N^2)$，在亿级文档下不可行。LSH 将长度为 $m$ 的签名分为 $b$ 个桶组（Band），每个 Band 包含 $r$ 个哈希值（$m = b \times r$）。两篇文档只要在任意一个 Band 内的哈希签名完全一致，就被归入同一个候选桶，直接列入疑似重复对。相似度为 $s$ 的两篇文档成为候选对的概率为：
   $$P_{\text{candidate}} = 1 - (1 - s^r)^b$$
   该公式形成一条陡峭的 S 曲线，在较低计算代价下过滤掉大部分相似度低于阈值的文档对。
4. **聚类与消除**：在候选桶内部通过图连通分量算法（Connected Components）聚类，每组相似文档中仅保留一篇基准文本。

### 3. 内容安全处理与多领域配比混编

* **个人敏感信息（PII）脱敏**：通过正则表达式与命名实体识别模型，定位并掩码替换身份证号、电话号码、真实住址与邮箱等私密字段。
* **毒性过滤**：训练轻量判别模型，丢弃包含严重偏见、暴力及低俗内容的样本。
* **配比采样与全局混洗**：不同领域数据（如通用网页、学术论文、开源代码、百科词条）具备不同的知识密度。数据团队依据模型目标设定采样比例（例如网页 60%、代码 20%、学术文献 10%、百科与图书 10%），对分词后的 Token 数据集进行打散洗牌（Global Shuffle）。

## 序列打包（Sequence Packing）：消除 Padding 浪费

在预训练中，模型的上下文窗口通常固定为 2048、4096 或 8192。如果直接将单篇文档独立作为一行并用 `<pad>` 补齐至最大窗口：
* 自然文本的长度往往高度倾斜，数百 Token 的短文档占很大比例。
* 批次张量中可能会充斥 30% 以上的 `<pad>` 标记，GPU 算力被大量消耗在计算与输出无关的无用矩阵乘法上。

**Sequence Packing（序列打包）**算法将多篇独立短文档连续拼接在同一个长度为 $L_{\max}$ 的序列张量中，几乎填满每一行，彻底消除无用填充。

![序列打包机制：文档拼接与分段因果掩码阻断跨样本注意力](/images/content-rebuild/64d08fbdcda30fef/fig-2.png)

### 打包带来的两个问题与解决方法

将多个独立文档拼入同一行张量，打破了“单个序列内所有 Token 属于同一上下文”的常规假设，必须在计算中做隔离处理。

#### 1. 注意力跨文档泄露（Attention Leakage）
若直接沿用标准的下三角因果注意力掩码（Causal Mask），位于后方的文档 B 在做自注意力计算时，会看到位于它前面的文档 A 的全部 Token，造成错误的跨文本语义关联。

* **解决方法**：构造**分段因果掩码（Block-diagonal Causal Mask）**。仅允许每个子文档内部的 Token 进行自回归因果注意，跨越文档边界的注意力权重在计算 Softmax 前强制置为 $-\infty$。
* **工程高效实现**：在 FlashAttention-2 等优化算子中，无需在显存中生成庞大稀疏的二维掩码矩阵，而是直接向算子传入包含各文档累计长度边界的一维数组 `cu_seqlens`（例如 `[0, 128, 512, 4096]`）。算子在底层 GPU 共享内存（Shared Memory）中分块计算，仅在属于同一文档的范围内计算注意力，既节约显存又避免了多余计算。

#### 2. 位置编码错位（Position ID Mismatch）
若将整行拼接张量按照 $0, 1, 2, \dots, L_{\max}-1$ 单调递增进行位置编码，排在后面的文档 B 会获得极大的绝对位置索引，导致相对位置编码（如 RoPE 旋转位置编码）计算出过大的旋转角度，破坏相对位置不变性。

* **解决方法**：在打包拼接的同时，**重置每个子文档的位置索引**。每个独立文档内部的 Position IDs 均从 0 重新递增：

```python
# 示例：序列打包与位置重置机制
# 拼接两个独立短文档：Doc A (长度 3), Doc B (长度 2)
doc_a_tokens = [101, 205, 308]
doc_b_tokens = [402, 509]

# 拼接输入张量
packed_tokens = doc_a_tokens + doc_b_tokens         # [101, 205, 308, 402, 509]

# 位置索引分别从 0 重新递增
packed_position_ids = [0, 1, 2] + [0, 1]            # [0, 1, 2, 0, 1]

# 传给 FlashAttention varlen API 的序列边界前缀和数组
cu_seqlens = [0, 3, 5]
```

## 分布式 3D 并行拓扑：千亿参数如何切分

以我们的贯穿示例 **130B 参数模型** 为例，在 FP16/BF16 混合精度训练并采用标准 AdamW 优化器的设定下：
* **模型参数**：$130 \times 10^9 \times 2\text{ 字节} \approx 260\text{ GB}$；
* **梯度缓存**：$130 \times 10^9 \times 2\text{ 字节} \approx 260\text{ GB}$；
* **AdamW 优化器状态**：通常包含 FP32 参数主副本（4 字节）、一阶动量（4 字节）与二阶动量（4 字节），合计 12 字节/参数，即 $130 \times 10^9 \times 12\text{ 字节} \approx 1560\text{ GB}$。

仅上述静态显存占用就达到 $260 + 260 + 1560 = 2080\text{ GB}$，而单张 A100 GPU 显存仅为 80GB，甚至无法装入静态参数。因此必须采用张量并行（TP）、流水线并行（PP）与数据并行（DP/ZeRO）结合的 **3D 并行方案**。

![分布式 3D 并行拓扑：张量并行、流水线并行与 ZeRO 数据并行的层级部署与通信映射](/images/content-rebuild/64d08fbdcda30fef/fig-3.png)

### 1. Tensor Parallelism（TP，张量并行）：节点内算子切分

张量并行（主要采用 Megatron-LM 架构）将单个 Transformer 层内部的矩阵乘法切分到单台服务器内的多张 GPU 上执行。

![Megatron-LM 张量切分原理：列并行与行并行在 Attention 和 MLP 层的通信闭环](/images/content-rebuild/64d08fbdcda30fef/fig-4.png)

* **自注意力层切分**：
  * 投影权重 $W_Q, W_K, W_V$ 采用**列并行（Column Parallel）**切分，各卡保存部分注意力头（Attention Heads），前向传播时输入 $X$ 复制到各卡，独立计算局部头输出，无需卡间通信。
  * 输出投影矩阵 $W_O$ 采用**行并行（Row Parallel）**切分，各卡计算部分特征积，最后通过一次 **All-Reduce（Sum）** 通信操作将各卡的局部结果求和，恢复完整的隐层维度。
* **MLP 层切分**：
  * 第一层升维矩阵（如 SwiGLU 中的门控与上投影矩阵）采用**列并行**切分。
  * 第二层降维矩阵采用**行并行**切分，乘积计算完成后再次通过一次 **All-Reduce（Sum）** 同步聚合。
* **通信约束与硬件限制**：
  每个 Transformer 层在前向传播中需要 2 次 All-Reduce，反向传播中同样需要 2 次 All-Reduce。由于通信频次高且传输张量处于关键路径，**TP 通常严格限制在单机 8 卡以内（如 TP=8）**，高度依赖服务器内部数百 GB/s 带宽的 NVLink 高速总线。若跨网络交换机执行 TP，算力大部分时间将被通信延迟阻塞。

### 2. Pipeline Parallelism（PP，流水线并行）：跨节点层级切分

流水线并行将 Transformer 的多层结构按深度切分（例如将 80 层均分给 8 个流水线阶段 Stage，每个 Stage 包含 10 层），部署在不同的服务器节点上。

* **通信特性**：通信仅发生在相邻两个 Stage 之间，属于点对点（P2P）通信，传输内容仅为切分边界的中间激活值（Forward 阶段）和激活值梯度（Backward 阶段），通信数据量相对可控，适合在跨主机的 InfiniBand 网络上运行。
* **1F1B（One Forward, One Backward）调度**：
  如果简单按大批次串行执行，后半段的 GPU 在前半段计算完成前完全闲置，产生巨大的“流水线气泡（Pipeline Bubble）”。1F1B 调度将全局批次拆解为 $M$ 个微批次（Micro-batches）：
  * 在初始的预热阶段后，每张 GPU 每执行完一个 Micro-batch 的前向计算，立刻执行另一个 Micro-batch 的反向计算。
  * 这种交替执行机制使得激活值张量能被反向传播及时消费并释放，有效限制了显存中激活值的峰值堆积，同时将气泡占比压缩至大约 $\frac{P - 1}{P + M - 1}$（其中 $P$ 为流水线级数，$M$ 为微批次总数）。

### 3. 数据并行与 ZeRO 显存优化配合

在 TP 与 PP 确定后，集群剩余的算力卡组成数据并行（Data Parallelism, DP）。传统 DP 要求每张卡都持有完整的优化器状态副本，千亿模型下不可行。ZeRO（Zero Redundancy Optimizer）技术消除了数据并行的状态冗余：

* **ZeRO-1（优化器状态切分，$P_{os}$）**：将 AdamW 的优化器状态均分到 DP 组内的各个 GPU。反向传播结束后，各卡通过 Reduce-Scatter 汇聚自己负责分片的参数梯度，并仅更新维护属于自己的那部分模型参数与优化器动量。在前向计算前，各卡通过 All-Gather 同步完整参数。与标准 DP 相比，**完全不增加通信量**，但可将优化器显存占用降低至原来的 $1/N_{DP}$。
* **ZeRO-2 与 ZeRO-3**：ZeRO-2 进一步切分梯度缓存；ZeRO-3 则在前向与反向传播中临时拉取与销毁参数本身。ZeRO-3 虽然显存压缩彻底，但每次前向与反向均需触发参数通信，通信开销增加约 50%。

#### 贯穿示例的 3D 并行拓扑配置
对于 1024 卡 A100 集群训练 130B 模型：
* 节点内配置 **TP = 8**（单机 8 卡利用 NVLink 消化每层矩阵切分）；
* 节点间配置 **PP = 8**（跨 8 个节点切分层数，利用 1F1B 隐藏通信延迟）；
* 剩余维度配置 **DP = 16**（$1024 / (8 \times 8) = 16$），并开启 **ZeRO-1**：
  模型参数与优化器状态经 TP=8 与 PP=8 共同切分（共 $8 \times 8 = 64$ 个模型分片），单卡对应切片的优化器状态显存基数为 $1560\text{ GB} / 64 = 24.375\text{ GB}$。开启 ZeRO-1 后在 DP=16 维度进一步分片，单卡优化器显存降至 $24.375\text{ GB} / 16 \approx 1.52\text{ GB}$（相当于全量优化器状态由 1024 卡集群均分）。加上单卡参数与梯度各约 $4.06\text{ GB}$，静态显存仅约 $9.64\text{ GB}$，为前向激活值与通信缓冲区留出了超过 70GB 的充裕空间。关于单机显存开销的详细理论拆解，可进一步参考 [/interview/llm-interview/transformer-memory.md](/interview/llm-interview/transformer-memory.md)。

## 集群故障与断点续训（Checkpoint）

在数千张 GPU 持续运行数月的预训练任务中，光模块损坏、网络闪断或单卡 ECC 硬件错误属于常态事件。预训练框架必须建立严密的容灾恢复机制。

![分布式训练容灾闭环：心跳检测、节点隔离与数据状态精准对齐的断点续训流](/images/content-rebuild/64d08fbdcda30fef/fig-5.png)

### 1. 为什么“只保存模型权重”会导致续训严重劣化？
若在检查点中仅持久化模型权重 $\theta$，重新加载训练时会导致训练不稳定甚至完全发散：

1. **AdamW 优化器动量丢失**：优化器中的一阶动量 $m_t$ 和二阶动量 $v_t$ 记录了历史梯度的滑动平均值。若重置为 0，相当于从冷启动状态直接以当前的较大更新步长计算更新量，极易引发 Loss 突刺（Loss Spike）和数值溢出（详见梯度裁剪机制说明 [/interview/llm-interview/gradient-clipping.md](/interview/llm-interview/gradient-clipping.md)）。
2. **学习率调度进度错位**：若丢失当前的全局执行步数（Global Step），学习率退火策略（如 Cosine Decay）与 Warmup 状态将回到初始状态，导致学习率异常激增。
3. **随机数生成器（RNG）状态偏差**：若不恢复 PyTorch、CUDA 及 Python 内部的 RNG 种子状态，在包含 Dropout 或动态数据增强的分支中，计算的确定性将被破坏。
4. **DataLoader 游标偏移量丢失**：预训练语料往往切分为数万个分卷文件（Shards）。若恢复时不恢复精确的数据读取游标（Dataset Index & Token Offset），训练将从头重新读取数据，破坏全局语料的无偏分布并引发过拟合。

### 2. 异步检查点（Async Checkpointing）机制
千亿模型全量状态（权重 + 梯度 + 优化器）体积达数 TB。若采用常规同步写入磁盘，每次保存需导致数千张 GPU 挂起停机 15~30 分钟，大幅压低有效算力利用率（MFU）。

* **显存到内存影子拷贝（D2H Copy）**：触发保存时，系统在显卡显存与主机内存（Host RAM）之间发起异步非阻塞内存复制，仅需几秒钟即可将当前步的权重与优化器切片搬移至 CPU 内存中。
* **计算立即恢复**：显存拷贝完成后，GPU 立即继续下一步迭代计算，停顿时间降低至秒级。
* **后台进程异步落盘**：CPU 主机通过后台独立线程，将内存中的快照数据以流水线方式推送到分布式共享存储（如 Lustre、GPFS 或高吞吐 S3 对象存储）中。

### 3. 故障处理与节点替换流程
当某张 GPU 发生不可恢复的硬件故障时，集群编排系统执行以下转移流程：

1. **心跳超时判定**：NCCL 通信库在检测到节点无响应或通信超时后抛出异常，监控系统捕获信号并终止当前训练作业。
2. **故障节点隔离**：调度器自动将故障物理机标记为不可用，移出算力调度池。
3. **热备节点替换与拓扑重组**：从预留的热备节点池中调入相同数量的健康主机，重新分配 MPI 进程 rank 并初始化通信拓扑。
4. **状态对齐与无损加载**：所有节点读取上一个已完整落盘的分布式检查点文件，严格对齐模型参数、优化器状态与数据游标，恢复训练。

## 典型工程陷阱与避坑指南

![典型工程陷阱对比：Packing 未隔离 Mask 与跨机 TP 通信阻塞的失效机理](/images/content-rebuild/64d08fbdcda30fef/fig-6.png)

| 常见错误实现 | 潜在风险与失效现象 | 正确工程实现建议 |
| :--- | :--- | :--- |
| **将 TP（张量并行）跨机器多节点部署** | 跨机通信带宽受限于网络交换机（如 400Gbps InfiniBand），比节点内 NVLink（900GB/s~3.2TB/s）慢 1~2 个数量级。TP 每层包含 2 次强同步 All-Reduce，跨机会导致 GPU 长期处于通信等待状态，集群整体吞吐断崖式下跌。 | **TP 严格限制在单机节点内（通常 TP $\le 8$）**。跨机器的规模扩展应当优先交给流水线并行（PP）与数据并行（DP/ZeRO）。 |
| **Sequence Packing 时沿用标准因果掩码** | 排在同一行后方的短文档，会通过标准下三角 Attention 矩阵计算看到前面毫不相关文档的全部 Token，导致严重的**跨样本注意力穿透与语义污染**。 | 必须构造**分段因果掩码（Block-diagonal Mask）**，或在底层直接调用传入 `cu_seqlens` 边界数组的 FlashAttention 变长算子实现物理级注意力阻断。 |
| **Packing 拼接后 Position ID 单调连续递增** | 拼接在后方的文档获得了很大的绝对位置偏移，打破了相对位置编码（如 RoPE）的局部空间不变性，导致推理时短上下文泛化表现变差。 | **每个拼接子文档的 Position IDs 必须独立从 0 开始重新递增**。 |
| **断点恢复时重置 DataLoader 遍历位置** | 语料规模达到万亿 Token 时，若每次恢复训练都从数据文件头开始读，模型会反复学习头部数据，破坏全局配比分布，引发过拟合。 | Checkpoint 中必须持久化保存当前 DataLoader 的 **分卷文件索引（Shard Index）与样本内 Token 偏移量（Token Offset）**。 |
