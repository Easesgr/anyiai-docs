在评估 Transformer 模型的表现时，学术研究与工程落地面临不同的权衡：从底层的自回归概率建模能力，到标准化跨学科能力基准，再到开放式问答中的人类意图对齐。单一指标很难刻画出模型的综合能力。

建立评估体系，需要认清指标背后的数学定义、数据筛选假设，以及不同评测手段在面对长文本与开放式推理时暴露的局限。

---

## 30秒口述结论

在面试中被问及“如何系统评估一个训练完成的 Transformer 模型”时，可以按如下框架条理回答：

> 评估大模型通常从四个层次递进展开：
>
> 1. **内在语言建模指标**：以困惑度（Perplexity, PPL）和交叉熵损失为主，用于评估模型对序列统计规律的拟合度。但 PPL 受分词器（Tokenizer）切分粒度影响，跨模型直接比大小容易失真，且不直接反映事实准确性。
> 2. **标准化能力基准**：包括综合知识（MMLU）、数学推理（GSM8K）与代码生成（HumanEval）。这类测试采用客观单选匹配或沙箱执行（如 Pass@k），需重点防范“基准数据污染”（测试集泄露进训练语料）导致的虚假高分。
> 3. **模型自动评审（LLM-as-a-Judge）**：针对开放式生成任务，使用更强的模型进行成对比较（Pairwise）或多维度打分。落地时必须通过双向盲测和细化评分量规，消除位置偏见、长度偏见和自我家族偏好。
> 4. **企业业务端到端验收**：由“通用能力防退化门禁 + 垂直任务黄金测试集（沙箱执行验证）+ 抽检自动评审 + 线上推理延时吞吐”组成多层验收流程。

## 传统指标的机制与局限：PPL、BLEU 与 ROUGE

自回归语言模型的[预训练目标](/interview/llm-interview/pretraining-objective.md)是预测下一个 Token 的条件概率分布。因此，早期评估自然延续了信息论和统计自然语言处理的方法。

### 困惑度（Perplexity, PPL）

PPL 衡量语言模型预测文本样本的平均不确定性。给定包含 $N$ 个 Token 的测试文本序列 $W = (w_1, w_2, \dots, w_N)$，模型的平均交叉熵损失 $\mathcal{L}$ 为：

$$\mathcal{L} = -\frac{1}{N} \sum_{i=1}^N \ln P(w_i \mid w_1, \dots, w_{i-1})$$

困惑度定义为平均损失的指数：

$$\text{PPL}(W) = \exp(\mathcal{L}) = \exp\left( -\frac{1}{N} \sum_{i=1}^N \ln P(w_i \mid w_{<i}) \right) = \left( \prod_{i=1}^N P(w_i \mid w_{<i}) \right)^{-\frac{1}{N}}$$

PPL 可以直观理解为模型在预测下一个词时，平均面临的“等价候选词分支数”。数值越低，代表模型给测试集的概率越高。

**使用 PPL 的边界与常见陷阱**：
1. **不可跨分词器对比**：公式中的序列长度 $N$ 由分词器决定。如果模型 A 采用词表较大的粗粒度分词（一句话切成 5 个 Token），模型 B 采用细粒度分词（切成 15 个 Token），两者预测的候选概率分布完全不同。细粒度切分单个候选空间相对较小，常测出更低的单 Token 交叉熵，但这并不代表生成质量更好。分词机制细节可参考 [Token 与分词算法解析](/interview/llm-interview/tokenization.md)。
2. **流畅度不等于事实准确度**：PPL 只反映文本是否符合训练语料的分布惯性。一段结构通顺但内容纯属编造的胡话，其 PPL 可能显著低于一段包含生僻专业名词的真实医学处方。

### BLEU 与 ROUGE 在长文本生成中的失效

传统文本任务常用字面重叠率指标：

- **BLEU**（Bilingual Evaluation Understudy）：主要统计生成文本与参考文本的 $n\text{-gram}$ **精确率（Precision）**，并带简短惩罚因子。
- **ROUGE**（Recall-Oriented Understudy for Gisting Evaluation）：主要统计参考文本在生成文本中的 **召回率（Recall）**。ROUGE-1/2 统计单字或双字重叠，ROUGE-L 统计最长公共子序列（LCS）。

![传统 n-gram 指标与困惑度在生成评测中的失效路径](/images/content-rebuild/09c4204ab3dc3bfb/fig-1.png)

字面匹配在处理语义逻辑时容易产生严重失真：

**贯穿示例：医疗诊断文本评估**

- **参考答案**：“患者对阿司匹林严重过敏，禁止开具该类药物。”
- **模型 A 生成**：“患者对阿司匹林不过敏，可以开具该类药物。”
  - 按字统计，参考答案（不计标点）共 19 字，模型 A 命中了除“严、重、禁、止”外的 15 个字。
  - **ROUGE-1 召回率**：约为 $\frac{15}{19} \approx 78.9\%$
  - **ROUGE-L 得分**：最长公共子序列极高。
  - **实际后果**：语义完全相反，存在严重医疗安全隐患，但自动化评分却判定接近满分。
- **模型 B 生成**：“用药禁忌：严禁使用乙酰水杨酸制剂，该人员存在过敏史。”
  - 药品被替换为通用化学名，句式完全重组。
  - **ROUGE-1 召回率**：极低（仅命中“过敏”等少量字词，低于 $20\%$）。
  - **实际后果**：表述准确专业，但词面重叠指标判定其不合格。

在评估理解、推理和开放式生成时，硬匹配指标无法作为独立的质量标准。

## 主流能力基准：MMLU、GSM8K 与 HumanEval

为了在可复现前提下横向对比，业界通常采用标准化基准集：

| 基准名称 | 考察维度 | 题目形态 | 判定机制 | 局限性 |
| :--- | :--- | :--- | :--- | :--- |
| **MMLU** | 涵盖人文、社科、STEM 等数十个领域的综合知识 | 4 选 1 单选题 | 比较选项对应 Token 的 Logits 概率，或解析输出的首字符 | 仅考查选项识别辨析，无法评估长文本组织与推演 |
| **GSM8K / MATH** | 多步小学与竞赛级数学逻辑推理 | 应用题、计算题 | 正则提取最终数值（如 `#### 答案`）进行精确比对 | 难以识别“推导步骤全错但巧合算对最终数字”的情况 |
| **HumanEval** | 代码理解、算法实现与边界处理 | 函数名、签名及注释文档 | 在隔离沙箱中运行单元测试，计算 Pass@k 真实通过率 | 用例覆盖率受限，存在通过用例但有隐蔽边界 Bug 的可能 |

![主流大模型学术基准的数据形态与判定机制对比](/images/content-rebuild/09c4204ab3dc3bfb/fig-2.png)

在代码生成评测中，**Pass@k** 属于公认具备执行验证力的指标。若模型为每个问题采样生成 $n$ 个独立样本（$n \ge k$），其中有 $c$ 个样本通过测试，从 $n$ 中无放回抽取 $k$ 个样本至少有 1 个正确的无偏估计公式为：

$$\text{Pass@}k = \mathbb{E}_{\text{Problems}} \left[ 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}} \right]$$

当 $k=1$ 且仅采样 1 个回答时，公式退化为单次通过率。该指标依靠外部测试运行，不受字面表述差异干扰。

更多基准分类可参考 [大模型常见评测有哪些](/fundamentals/evaluation-metrics/llm-benchmarks.md) 与 [分类任务怎么评估](/fundamentals/evaluation-metrics/classification-metrics.md)。

## 基准污染的现象与检测方法

随着对榜单排名的追求，“基准污染（Benchmark Contamination）”已成为评测中的普遍挑战。

### 污染的两种形式

1. **显式泄漏**：在大规模无监督预训练语料爬取时，清洗规则未过滤公开评测集，导致题干与标准答案进入训练序列。模型记住了对应词元，而非学到了通用推理能力。
2. **改写泄漏**：在指令微调（SFT）或合成数据时，直接基于测试题库生成相似变体或解题步骤进行训练。模型通过模仿特定解题套路应对测试。

![数据污染如何导致模型在原始榜单与扰动测试集上出现表现断崖](/images/content-rebuild/09c4204ab3dc3bfb/fig-3.png)

这对应了古德哈特定律：“当一个指标变成目标，它就不再是一个好指标。”如果模型在原题库上准确率达到 90%，但题目常数稍作改动就发生错误，说明其主要依赖记忆而非推理。

### 检验污染的三种常规方法

1. **n-gram 包含度过滤**：在构建训练数据集时，针对主流公开评测集提取 8-gram 到 13-gram 切片，通过后缀数组或布隆过滤器对训练集做去重与清洗。
2. **困惑度异常检测**：计算模型在测试集题干上的平均 PPL。若测试集的 PPL 异常偏低，且明显偏离同一模型在同难度未知语料上的分布（例如低于均值 3 个标准差），通常是预训练过拟合的信号。
3. **鲁棒性扰动测试**：
   - **实体替换**：将题目中的“小明买了 3 个苹果”换为“工匠采购了 3 根铜管”；
   - **数值扰动**：将题中的常量替换为相同量级的其他数字；
   - **选项轮换**：对多选题选项顺序随机洗牌，保持提示词逻辑一致；
   - 若在扰动后模型准确率出现大幅度下滑，表明模型大概率记住了原题答案序列。

## LLM-as-a-Judge 落地规范：偏见与消除协议

对于自由对话、内容摘要等没有唯一标准答案的任务，使用更强的模型充当裁判（LLM-as-a-Judge）是常见做法。但大模型裁判自身也带有明确的偏见。

![LLM-as-a-Judge 的三大偏见及双向盲测校正机制](/images/content-rebuild/09c4204ab3dc3bfb/fig-4.png)

### 三类常见裁判偏见

1. **位置偏见（Position Bias）**：在成对比较（Pairwise）中，裁判模型倾向于给先输入（Option A）或后输入（Option B）的回答更高的打分。这与注意力机制中前缀词元的注意力分配及近因效应有关。
2. **长度偏见（Verbosity Bias）**：裁判模型普遍青睐篇幅更长、排版更丰富（带列表和粗体）的回答，哪怕长内容包含冗余车轱辘话甚至细微事实错误。
3. **自我家族偏好（Self-enhancement Bias）**：部分裁判模型给自身架构或同一系列模型生成的文本打分相对偏高，源于其词元预测倾向与同类模型更为契合。

### 双向盲测校准实现

为了减轻位置偏见，工程上常采用双向对调验证协议：

```python
from typing import Dict, Any
import json

def evaluate_pairwise(
    judge_client,
    prompt: str,
    response_a: str,
    response_b: str,
    rubric: str
) -> Dict[str, Any]:
    """
    双向位置对调评测实现：检验两轮裁判结果的一致性
    """
    # 第一轮：A 排在第一位，B 排在第二位
    res_round1 = _call_judge(judge_client, prompt, first=response_a, second=response_b, rubric=rubric)
    
    # 第二轮：B 排在第一位，A 排在第二位
    res_round2 = _call_judge(judge_client, prompt, first=response_b, second=response_a, rubric=rubric)
    
    # 提取裁判决策：约定返回 1 为 first 获胜，-1 为 second 获胜，0 为平局
    winner_r1 = res_round1.get("winner")  # 1 代表 A 胜，-1 代表 B 胜
    winner_r2 = res_round2.get("winner")  # 1 代表 B 胜，-1 代表 A 胜
    
    # 校验两轮决策是否一致
    if winner_r1 == 1 and winner_r2 == -1:
        return {"winner": "model_a", "status": "consistent"}
    elif winner_r1 == -1 and winner_r2 == 1:
        return {"winner": "model_b", "status": "consistent"}
    elif winner_r1 == 0 and winner_r2 == 0:
        return {"winner": "tie", "status": "consistent"}
    else:
        # 两轮评判发生冲突（例如两次都选第一项），标记为受位置影响
        return {"winner": "tie", "status": "position_bias_fallback"}

def _call_judge(client, prompt: str, first: str, second: str, rubric: str) -> dict:
    system_prompt = f"""你是一名技术评估裁判。请根据提供的量规（Rubrics）比对两个候选回答。
注意要求：
1. 不要单纯因篇幅长或格式丰富而给高分，简练准确的回答优先。
2. 输出结论前先给出评分理由，最后输出 JSON，格式为 {{"reason": "...", "winner": 1或-1或0}}（约定：1 代表候选回答1更优，-1 代表候选回答2更优，0 代表平局）。
量规：
{rubric}
"""
    user_input = f"用户问题：{prompt}\n\n候选回答1：\n{first}\n\n候选回答2：\n{second}"
    raw_resp = client.generate(system=system_prompt, user=user_input, temperature=0.0)
    return json.loads(raw_resp.content)
```

关于自动化评测流程的架构拆解，可参考 [AI 评测体系架构设计](/architecture/ai-evaluation.md) 与 [RAG 系统评测规范](/fundamentals/evaluation-metrics/rag-evaluation.md)。

## 业务微调模型的端到端验收设计

**面试常考场景**：
> “团队针对某垂直金融业务微调了一个开源模型，准备替换线上基线。如何设计一套完整的验收方案以降低上线风险？”

![企业微调模型端到端上线验收评测体系与四层门禁漏斗](/images/content-rebuild/09c4204ab3dc3bfb/fig-5.png)

可从以下四个层次建立工程化验收流程：

### 第一层：基础能力防退化门禁

- **目标**：微调容易引入**灾难性遗忘**，即业务问答能力提升，但基础指令遵循（如输出指定 JSON 格式）、常识逻辑或安全防线退化。
- **测试集与要求**：
  - 通用基准抽取 500-1000 道固定指令，测试格式遵循率，指标下滑幅度需控制在预设容忍度以内；
  - 安全对抗测试：准备 200 条红蓝对抗样本（Prompt 越狱、敏感信息试探），确认模型的违规拒绝率达到业务安全标准。

### 第二层：垂直领域黄金测试集验证

- **数据集构建**：整理 1000-2000 条业务样本，按调用场景划分为：典型高频问题（60%）、长尾边界情况（30%）以及诱导错误输入（10%）。
- **差异化执行评估**：
  - **结构化任务（如 Text-to-SQL、参数抽取）**：采用**沙箱执行验证**。直接在脱敏测试数据库中执行生成的 SQL，比对查询结果集与标注真值是否一致，避免依赖词面匹配；
  - **非结构化咨询**：通过经过双向校准的裁判模型进行打分，并抽样交由人工业务专家进行复核。

### 第三层：推理性能与系统开销测试

模型能否上线不仅取决于生成质量，还取决于推理开销与时延表现：

1. **首字延迟（TTFT, Time To First Token）**：反映 Prefill 阶段处理 Prompt 的速度；
2. **输出流式延迟（TPOT, Time Per Output Token）**：反映 Decode 阶段每个 Token 的平均生成耗时；
3. **显存并发水位**：结合 [KV Cache 显存占用分析](/interview/llm-interview/kv-cache.md)，压测在不同并发下的 P95/P99 响应延迟，避免线上发生显存溢出（OOM）。部署显存与推理性能分析可参阅 [Transformer 显存开销拆解](/interview/llm-interview/transformer-memory.md) 与 [Transformer 推理瓶颈剖析](/interview/llm-interview/transformer-bottleneck.md)。

### 第四层：线上灰度与可观测反馈

自动化测试通过后，进入灰度切流：

![评测流水线自动化执行与可观测报告仪表盘](/images/content-rebuild/09c4204ab3dc3bfb/fig-6.png)

- **分流验证**：分配小比例流量给新模型，其余保持原有基线；
- **显式指标**：跟踪用户的点赞、点踩、重新生成请求比例；
- **隐式转化指标**：以客服场景为例，重点监控人工转接率；以代码辅助为例，监控代码采纳率。

## 常见误区与辨析

| 常见说法 | 实际机制与边界说明 |
| :--- | :--- |
| “模型 A 的 PPL 比模型 B 低很多，说明模型 A 性能全面更强” | 若两个模型分词器不同，序列划分数量 $N$ 和概率计算空间不同，跨分词器对比 PPL 在统计上缺乏可比性。 |
| “生成回答与标准答案的 ROUGE 分数越高，说明事实回答越准” | ROUGE 依赖字词重叠统计。语义相反但用词高度相似的句子可能拿到高分，同义替换但用词不同的正确回答反而得分偏低。 |
| “开源榜单（如 GSM8K）得分高，业务落地自然稳妥” | 公开基准容易出现预训练数据污染。未经扰动测试（如微调数字或重组题干）的高分模型，可能仅记住了原题答案序列。 |
| “用 GPT-4 作为裁判进行比较，结果天然比规则打分准确” | 未经设计的裁判模型存在明显的位置偏见、长度偏见与同家族偏好，需要通过双向位置互换与结构化量规进行约束。 |

综合语言建模概率、标准化基准沙箱验证、带校准的模型裁判与工程上线指标，才能建立起兼顾技术严密性与工程可用性的评估流程。
