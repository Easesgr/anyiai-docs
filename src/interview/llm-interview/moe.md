![MoE架构原理封面图](/images/content-rebuild/2b0816d76b0b9a41/cover.png)

在稠密 Transformer 中，模型每增加一倍参数，每次推理的前向计算量和能耗就会同步增加一倍。混合专家模型（Mixture of Experts, MoE）改变了这种绑定关系：它把模型参数扩充到原来的数倍，但对每个处理的 Token，仅动态挑选其中一小部分参数参与计算，从而在保持单步低延迟的同时扩充参数容量。

本文先给出面试标准的口述答案，再以具体数据和公式拆解门控路由的计算过程、路由崩溃的发生机制，以及落地部署中的真实瓶颈。

---

## 面试 30 秒口述答案

被问及“什么是 MoE 及其工作原理”时，可按以下三点回答：

1. **结构改动**：MoE 保留了 Transformer 块中的多头自注意力层，只把前馈网络（FFN）替换为一组结构相同、权重独立的前馈子网络（专家，Experts），并在输入端增加一个参数量极小的门控网络（Router）。
2. **稀疏激活**：门控网络对每个 Token 动态打分，仅选出得分最高的 $k$ 个专家（如 Top-2）进行前向计算，其余专家完全闲置，最终将选中专家的输出加权汇总。这让**模型的总参数容量与单步前向计算量（FLOPs）解耦**。
3. **核心代价**：
   - **显存不缩减**：推理时无法预知下一个 Token 会路由到哪台机器上的哪个专家，因此所有专家的权重必须全量常驻显存，显存占用取决于总参数量而非激活参数量；
   - **路由崩溃风险**：门控网络容易因早期训练的微弱优势而把所有 Token 都派给少数专家，需引入负载均衡辅助损失（Auxiliary Loss）来强制打散；
   - **分布式通信开销**：在跨卡采用专家并行（EP）时，需要在节点间派发和汇聚 Token，引入高昂的 All-to-All 集体通信耗时。

## 结构改动：MoE 改变了 Transformer 的什么

在标准 Transformer 解码器块中，每个 Token 都会经过两个主要组件：多头自注意力层（MHA）和前馈网络层（FFN）。详细的 FFN 内部结构可参考 [/interview/llm-interview/ffn-swiglu.md](/interview/llm-interview/ffn-swiglu.md)。

![稠密 Transformer 与 MoE 结构演化对比](/images/content-rebuild/2b0816d76b0b9a41/fig-1.png)

MoE 的改动集中在 FFN 区域：
- **注意力层保持共享**：所有 Token 依然经过同一套注意力参数矩阵（$W_q, W_k, W_v, W_o$），模型并没有为每个专家复制注意力层；
- **FFN 替换为专家池**：原本单一的稠密 FFN 被替换为 $N$ 个独立的 FFN，每个 FFN 称为一个“专家”（$E_1, E_2, \dots, E_N$）；
- **新增门控路由矩阵**：在进入专家池前，添加一个轻量级线性矩阵 $W_g$。每个 Token 计算完自注意力后，先经过门控打分，再决定进入哪 $k$ 个专家，非选中的 $N-k$ 个专家跳过计算。

## 门控路由机制与逐步算例

门控路由决定了一个 Token 应该派给谁、分配多少权重。

![Top-k 门控路由机制计算流](/images/content-rebuild/2b0816d76b0b9a41/fig-2.png)

### 1. 门控计算步骤

设输入 Token 经过自注意力层后的隐层表示为向量 $x \in \mathbb{R}^d$，门控网络参数矩阵为 $W_g \in \mathbb{R}^{d \times N}$，其中 $N$ 为专家总数：

1. **计算原始专家得分（Logits）**：
   $$H(x) = x \cdot W_g \in \mathbb{R}^N$$
   这里直接用向量点积衡量当前 Token 隐层特征与各专家向量的匹配度。

2. **筛选 Top-$k$ 专家**：
   从 $H(x)$ 中挑出数值最大的前 $k$ 个得分对应的专家下标，构成激活集合 $\mathcal{T} = \text{Top-}k(H(x))$。对于集合之外的专家 $i \notin \mathcal{T}$，其权重强制记为 0。

3. **对选中的专家做局部 Softmax**：
   为了让激活专家的权重和为 1，仅在集合 $\mathcal{T}$ 内部进行 Softmax 归一化：
   $$G_i(x) = \begin{cases} \frac{\exp(H(x)_i)}{\sum_{j \in \mathcal{T}} \exp(H(x)_j)}, & i \in \mathcal{T} \\ 0, & i \notin \mathcal{T} \end{cases}$$

4. **输出加权汇总**：
   MoE 层的最终输出 $y$ 是被选取的 $k$ 个专家输出的加权求和：
   $$y = \sum_{i \in \mathcal{T}} G_i(x) \cdot E_i(x)$$

### 2. 逐步数值算例

设专家总数 $N=4$，激活专家数 $k=2$。某 Token 经过门控矩阵线性变换后得到打分向量：
$$H(x) = [2.2, \; 0.4, \; 3.1, \; -1.5]$$

- **挑选 Top-2**：对比数值，第 3 位最大（$3.1$），第 1 位次大（$2.2$），因此被选专家集合 $\mathcal{T} = \{1, 3\}$。
- **计算指数与局部归一化**：
  - $\exp(2.2) \approx 9.025$
  - $\exp(3.1) \approx 22.198$
  - 分母总和 $= 9.025 + 22.198 = 31.223$
  - 归一化权重：
    $$G_1(x) = \frac{9.025}{31.223} \approx 0.289$$
    $$G_3(x) = \frac{22.198}{31.223} \approx 0.711$$
    $$G_2(x) = 0, \quad G_4(x) = 0$$
- **前向计算**：该 Token 只输入专家 1 和专家 3 的 FFN，最终输出为 $y = 0.289 E_1(x) + 0.711 E_3(x)$。专家 2 和专家 4 在这一步不分配任何浮点乘加运算。

## 路由崩溃与负载均衡辅助损失

门控网络在没有任何外部约束时直接参与端到端反向传播，容易陷入严重的**路由崩溃（Routing Collapse）**。

![路由崩溃与专家饥饿现象示意](/images/content-rebuild/2b0816d76b0b9a41/fig-3.png)

### 1. 为什么会发生路由崩溃？

在模型随机初始化阶段，各个专家的能力并无本质差别。但由于初始化随机性，某个专家（如 Expert 1）的打分可能偶然略高于其他专家。

反向传播的机制决定了：**只有被选中的专家才能接收到梯度更新**。
- Expert 1 接收到的 Token 略多，更新步数更多，模型主任务损失下降得更快；
- 门控网络学习到了“把 Token 分配给 Expert 1 能降低损失”，因而在后续训练中进一步加大对 Expert 1 的打分；
- 导致 Expert 1 承受越来越多的 Token，其他专家则长期接收不到数据与梯度，陷入“专家饥饿”；
- 最终，门控网络退化为恒定把所有数据分发给同 1~2 个专家，其余专家参数完全废弃，模型退化成实际参数量很小的稠密模型，失去了多专家的容量价值。

### 2. 负载均衡辅助损失（Load Balancing Loss）的实现方式

为了强制门控网络均衡派发任务，Switch Transformer、GShard 和 Mixtral 等模型都引入了辅助损失 $\mathcal{L}_{aux}$。

![负载均衡辅助损失数学构成解析](/images/content-rebuild/2b0816d76b0b9a41/fig-4.png)

设一个批次（Batch）内共有 $T$ 个 Token。辅助损失通过两个向量的点积来约束分配均匀度：

1. **实际分发频次占比向量 $f$**：衡量在当前 Batch 中，专家 $i$ 获得的派发次数占全部 $k \cdot T$ 个分配槽位的比例：
   $$f_i = \frac{1}{k \cdot T} \sum_{t=1}^T \mathbb{I}(\text{Token } t \text{ 的 Top-}k \text{ 包含专家 } i)$$
   因为 Top-$k$ 是硬挑选操作，不可求导，所以 $f_i$ 无法把梯度传回门控权重。

2. **门控预测概率均值向量 $P$**：衡量门控网络在整个 Batch 上给专家 $i$ 分配的平均 Softmax 概率倾向（在所有 $N$ 个专家上求 Softmax）：
   $$P_i = \frac{1}{T} \sum_{t=1}^T \text{Softmax}(H(x_t))_i$$
   $P_i$ 是连续变化的平滑概率，**对门控参数矩阵 $W_g$ 完全可导**。

3. **辅助损失公式**：
   $$\mathcal{L}_{aux} = \alpha \cdot N \sum_{i=1}^N f_i \cdot P_i$$
   其中 $\alpha$ 为超参数（通常取 $0.01$ 到 $0.001$ 之间），$N$ 为专家总数。

**为什么点积能促成均匀分布？**
向量 $f$ 和 $P$ 各自分量和均为 1（$\sum f_i = 1$ 且 $\sum P_i = 1$）。根据向量内积性质，当各专家被完全均匀选中且预测概率均等时（$f_i = \frac{1}{N}, P_i = \frac{1}{N}$），内积取得最小值 $\sum f_i P_i = \frac{1}{N}$，乘以 $N$ 后的基准值为 1；而当流量极度倾斜、门控概率与实际分配高度同向重叠时（如全部扎堆单一专家，使 $f_1 \approx 1, P_1 \approx 1$），点积取得最大值 1，乘以 $N$ 后辅助损失放大为 $N$ 倍，从而对倾斜路由施加严厉惩罚。

反向传播时，如果某个专家的实际分发量 $f_i$ 过高，辅助损失就会通过 $P_i$ 对门控网络施加惩罚，迫使门控网络降低对该专家的打分，把后续 Token 分流给其他专家。

## 工程实操代价：显存驻留与跨卡通信

评估 MoE 架构必须兼顾算力收益与分布式系统的额外开销，相关理论可参考 [/interview/llm-interview/transformer-memory.md](/interview/llm-interview/transformer-memory.md) 与 [/interview/llm-interview/transformer-bottleneck.md](/interview/llm-interview/transformer-bottleneck.md)。

![专家并行与 All-to-All 集体通信拓扑](/images/content-rebuild/2b0816d76b0b9a41/fig-5.png)

### 1. 显存开销：全量参数必须常驻 GPU
“MoE 只激活 2 个专家，所以显存只需要装 2 个专家”是常见的理解偏差。

门控路由是在每个 Token 上实时动态计算的。模型无法在生成开始前预测后续 Token 会命中哪个专家。因此，**所有专家的全量权重必须提前完整装入显存**。一个 47B 参数的 MoE 模型，使用 16 位半精度（FP16/BF16）载入时，仅权重本身就需要消耗约 $47 \times 2 = 94\text{ GB}$ 显存，硬件显存门槛与同等规模的稠密模型相同。

### 2. 通信瓶颈：专家并行（EP）下的 All-to-All
当专家数量增多、单张 GPU 无法容纳所有专家参数时，通常使用**专家并行（Expert Parallelism, EP）**：把不同的专家切分存放在不同的 GPU 节点上。

此时每前向计算一个 MoE 层，就会触发两次跨卡集群通信：
1. **Token 分发（Dispatch）**：GPU 0 上的 Token 计算完注意力后，门控指出它需要由 GPU 3 上的专家计算，GPU 0 必须通过集群网络把 Token 向量发送到 GPU 3；
2. **All-to-All 通信**：由于所有卡上的 Token 都在随机派往不同卡上的目标专家，卡间形成全对全的网状数据交换；
3. **Token 聚合（Combine）**：各卡专家计算完成后，再次执行一次 All-to-All 通信，把专家输出的向量发送回原卡进行残差连接。

若集群跨卡互联带宽较低（如无 NVLink 支持的跨节点网络），通信等待时间可能会超过计算节省的时间，削弱稀疏激活带来的吞吐优势。

## 典型案例：Mixtral 8x7B 的参数算术题

> **面试常考题**：Mixtral 8x7B 包含 8 个专家，每个专家的规模与 Mistral-7B 相当。为什么它的总参数量不是 $8 \times 7\text{B} = 56\text{B}$ 而是约 47B？为什么每次推理计算量约相当于 13B 稠密模型？

![Mixtral 8x7B 共享与稀疏参数构成拆解](/images/content-rebuild/2b0816d76b0b9a41/fig-6.png)

### 算术分解

#### 1. 为什么总参数量约为 47B？
在标准的 7B 稠密模型中，参数分布大约为：
- **共享模块**（Token 嵌入层、所有层的自注意力矩阵、归一化层和输出分类头）：约占 $1.5\text{B} \sim 1.7\text{B}$；
- **FFN 模块**（升采样、门控投影、降采样矩阵）：占总参数量的约 2/3，约 $5.6\text{B}$。

Mixtral 8x7B 并没有把包含自注意力的完整 7B 模型复制 8 遍：
- **自注意力层在所有专家之间共享**，总共只有 1 份；
- **仅 FFN 层被复制了 8 份**，形成 8 个互不干扰的独立专家。

总参数量计算为：
$$\text{Total} = \text{共享参数} + 8 \times \text{单个 FFN} \approx 1.7\text{B} + 8 \times 5.6\text{B} \approx 46.5\text{B} \approx 47\text{B}$$
因此总参数量不是 56B。

#### 2. 为什么计算量约等于 13B 稠密模型？
Mixtral 采用 **Top-2 路由**，即每个 Token 在每一层仅唤醒 2 个专家参与计算。单步前向传播激活的参数量为：
$$\text{Active Parameters} = \text{共享参数} + 2 \times \text{单个 FFN} \approx 1.7\text{B} + 2 \times 5.6\text{B} \approx 12.9\text{B} \approx 13\text{B}$$

因此，该模型在推理时：
- 静态显存需求等同于约 47B 稠密模型；
- 单步前向乘加运算量（FLOPs）等同于约 13B 稠密模型。

## 常见认知误区

| 常见误区 | 实际机制说明 |
| :--- | :--- |
| **“MoE 激活参数少，能在单张 16GB 消费级显卡上跑 47B 模型”** | 错误。每个 Token 选中的专家动态变化，必须全量常驻显存。47B 半精度模型仍需 90GB 以上显存放置静态权重，除非使用量化或 CPU 内存卸载（Offloading）。 |
| **“门控路由是按整篇文档或整句话分发的”** | 错误。主流大模型均采用**逐 Token 路由**。一句话中的相邻词语，甚至同一个单词的不同分词片段，都可能被派发给不同的专家。 |
| **“不同专家会自动学会人类理解的业务分工（如专攻数学、专攻代码）”** | 与实测现象不符。实证研究显示，专家分工主要体现在浅层句法结构、标点符号、高频语法模式或特定上下文分布上，极少呈现整齐的人类宏观学科分类。 |
| **“辅助损失系数越大，模型表现越好”** | 错误。辅助损失过大时，门控网络会为了强求“完全平分 Token”而牺牲语义匹配度，破坏专家的专业化学习能力，导致主任务损失上升。 |
