在大模型应用开发与系统优化中，**Token** 是一个绕不开的基础单位。无论是上下文窗口管理、商业 API 计费预估，还是部署推理引擎时的显存排布，度量标准都是 Token 数量。很多初学者常把 Token 误当成“汉字”或“英文单词”，这在工程核算中往往会造成较大偏差。

本文从大模型分词机制出发，通过一个贯穿示例讲清自然语言如何变为离散 Token，梳理中英文换算规律、特殊标记的作用，以及 Token 膨胀对显存和推理时延的连锁影响。

## 30 秒面试口述答案

如果在面试中被问到“Token 是什么，如何核算与控制”，可以这样回答：

> **口述要点：**
>
> 1. **定义**：Token 是大语言模型分词器（Tokenizer）处理文本时的**最小离散符号单元**。神经网络无法直接计算不定长的字符串，必须通过词表和子词分词算法（如 BPE、Unigram）把文本切分为 Token 序列。每个 Token 对应词表里的一个整型编号（Token ID），模型再通过词嵌入矩阵把 ID 映射为连续向量送入网络计算。
> 2. **换算规律**：英文文本中 1 个 Token 大致对应 4 个字符（约 0.75 个英文单词）。中文由于没有天然空格分隔，消耗量取决于词表设计：在以英文为主的旧词表（如早期 LLaMA）中，由于触发字节回退，1 个汉字可能消耗 2 到 3 个 Token；而在针对多语言或中文优化的大词表（如 Qwen、LLaMA-3）中，1 个汉字平均仅消耗 0.6 到 0.8 个 Token。
> 3. **工程控制**：Token 数量直接决定 KV Cache 显存占用与 Prefill/Decode 延迟。控制手段包括选择合适压缩比的词表、精简 System Prompt、压缩或截断历史上下文、监控并强制捕获 EOS 终止标记，以及在网关层设置动态 `max_tokens` 阈值防止自回归死循环。

## 一个贯穿示例：一句话是如何变成向量的？

为了直观理解从字符串到模型输入的完整流转，我们来看一句话在现代多语言分词器中的处理过程：

$$\text{“AI 助手正在加速学习 transformer 架构。”}$$

系统并不是一次性把整句话读入模型，而是经历以下四个明确阶段：

1. **预分词（Pre-tokenization）**：
   分词器按照预定规则（如空白字符、标点符号或特定语言切分正则）将原始句子切分为粗粒度片段：
   `["AI", " ", "助手", "正在", "加速", "学习", " ", "transformer", " ", "架构", "。"]`

2. **子词切分（Subword Tokenization）**：
   根据训练好的分词算法（例如基于 BPE 或 WordPiece）与固定词表进行匹配。
   - 英文单词 `transformer` 并非生僻词，可能整体被识别为 1 个 Token；如果是极少见的组合词，则会被切分成更小的词根词缀。
   - 中文常用词如 `架构`、`正在`、`学习` 在优化过的词表中可能直接作为单独的 Token 收录；而若词表未收录，则会回退为单字甚至 UTF-8 字节。

3. **词表查表转换为整型索引（Token ID）**：
   每个切分后的 Token 对应词表中固定的非负整数索引。例如：
   `["AI" -> 9552, " 助手" -> 48312, "正在" -> 1928, "加速" -> 33104, "学习" -> 3512, " transformer" -> 28416, " 架构" -> 15982, "。" -> 1777]`
   （注：以上 ID 为原理示意，不同分词器的映射映射表各不相同）。

4. **查表映射为连续向量（Embedding Lookup）**：
   模型维护一个大小为 $V \times d_{\text{model}}$ 的词嵌入矩阵（其中 $V$ 为词表容量，$d_{\text{model}}$ 为模型隐藏层维度）。Token ID 作为行索引，从中提取出对应的浮点数向量，传入 Transformer 堆叠层展开注意力计算。详细映射过程可参考 [Embedding 在大模型中起什么作用？](/interview/llm-interview/embedding.md)。

## 中英文字符与 Token 数量的换算规律

在做容量规划和 API 成本核算时，开发者常犯的错误是用“字数”直接等价于“Token 数”。不同语言以及不同分词器之间，实际的字符压缩比有着巨大差异。

### 1. 英文文本的换算关系
大多数大模型分词器在构建基础词表时，英文语料占据了较大权重。高频的词缀、短词以及基础单词都被直接收入词表中：
- **字符比例**：通常满足 $1\text{ Token} \approx 3.5 \sim 4\text{ 个英文字符}$（包含空格与常见标点）。
- **单词比例**：通常满足 $100\text{ 个英文单词} \approx 130 \sim 135\text{ 个 Token}$，折算约为 $1\text{ Token} \approx 0.75\text{ 个英文单词}$。

### 2. 中文文本的分词压缩比与“字节回退”
中文文本缺乏自然的空格定界，模型切分中文依赖词表中收录的字、词序列分布。

- **以英文为主的旧词表（如早期 LLaMA-1/LLaMA-2）**：
  这类分词器的词表规模较小（约 32,000），训练数据以英文为主，几乎没有收录多字中文词，甚至没有收录大量中文单字。当遇到不在词表内的中文字符时，分词器触发 **Byte-fallback（字节回退）** 机制——将单个中文字符（在 UTF-8 编码下占 3 个字节）拆散成 2 到 3 个独立的字节 Token。这就导致：**输入 1 个汉字，模型需要消耗 2~3 个 Token**，序列长度被严重拉长。
- **针对多语言/中文优化的大词表（如 Qwen 系列、LLaMA-3 等）**：
  此类分词器将词表扩充到 100,000 以上（如 128k 或 152k），不仅覆盖了常用单字，还收录了大量中文两字词、成语及专业术语（如“人工智能”、“机器学习”直接作为一个 Token）。此时，**1 个汉字平均仅消耗 0.6 到 0.8 个 Token**，或者说 **1 个 Token 能表示 1.3~1.6 个汉字**。

| 模型分词器 | 典型词表大小 | 1,000 汉字预估消耗 Token 数 | 1,000 英文单词预估消耗 Token 数 |
| :--- | :--- | :--- | :--- | :--- |
| **LLaMA-2** | 32,000 | 约 2,000 ~ 2,800 个 | 约 1,300 个 |
| **LLaMA-3** | 128,256 | 约 1,200 ~ 1,400 个 | 约 1,300 个 |
| **Qwen-2.5** | 152,064 | 约 600 ~ 750 个 | 约 1,250 个 |

分词算法本身的合并机制与细节推导，可参考 [分词算法有什么区别？](/interview/llm-interview/tokenization.md)。

## 特殊 Token 的作用：控制自回归与交互边界

在日常文本词汇之外，分词器还保留了一组用于系统控制的特殊标记（Special Tokens）。它们不代表文本字面语义，而是用来指示生成边界和引导结构化控制。

### 1. BOS (Beginning of Sequence)
- **常见写法**：`<s>`、`<|begin_of_text|>`。
- **作用机制**：标识序列的起始位置。在 Decoder-only 架构的自回归推理中，模型需要一个初始输入来启动第一个词的预测，BOS 起到了明确的启动标记作用。

### 2. EOS (End of Sequence)
- **常见写法**：`</s>`、`<|end_of_text|>`、`<|im_end|>`。
- **作用机制**：**自回归循环的停止判断条件**。模型在 Decode 阶段逐个 Token 生成。当采样输出包含 EOS 时，推理框架（如 vLLM、TGI）判定当前回答完成，停止向前计算并返回结果。若因训练或模板拼接错误导致 EOS 丢失，模型会陷入复读或胡言乱语，直到触碰最大长度硬性截断。

### 3. PAD (Padding Token)
- **常见写法**：`<pad>`、`[PAD]`。
- **作用机制**：在批处理（Batching）阶段，不同样本的文本长度往往不一致。系统在短序列后面拼接 PAD 标记，使其对齐到当前 Batch 的最大长度 $S_{\max}$。
- **注意点**：必须配合注意力遮蔽（Attention Mask）使用。PAD 所在位置的 Mask 为 0，在计算自注意力时被加上负无穷大偏移量，使 Softmax 后的权重归零，避免无效填充干扰语义。原理细节见 [注意力遮蔽（Attention Masking）的工作原理是什么？](/interview/llm-interview/attention-masking.md)。

### 4. 轮次与角色分隔符（Turn Tokens）
- **常见写法**：`<|im_start|>`、`<|im_end|>`（ChatML 规范），或者 `[SEP]`（BERT 时代）。
- **作用机制**：在多轮对话中划分 `system`、`user` 与 `assistant` 的边界。分词器会将这些角色标记转化为专有 Token，模型借此区分哪部分是开发者约束、哪部分是用户提问。

### 5. 工具调用标记（Tool Call Tokens）
- **常见写法**：`<tool_call>`、`</tool_call>` 等自定义扩展标记。
- **作用机制**：当模型决定使用外部工具时，会输出预训练约定好的结构化标记。推理系统捕获到这些标记后，暂停流式生成，将标签内部的参数提取为 JSON 执行函数调用。

## 工程核算：分词膨胀对显存与时延的实际影响

在系统工程中，Token 绝不仅是计费数字，它直接左右着系统的吞吐上限与硬件显存边界。

### 1. KV Cache 显存占用推算
在大模型逐字生成的 Decode 阶段，为了避免历史 Token 在注意力层重复计算，必须将每一步计算出的 Key 和 Value 矩阵缓存到显存中，这就是 KV Cache。
在常见的 FP16/BF16 精度（每个参数 2 字节）下，每个 Token 带来的 KV Cache 显存开销公式为：

$$\text{Memory}_{\text{KV}} = 2 \times n_{\text{layers}} \times n_{\text{heads\_kv}} \times d_{\text{head}} \times S \times b_{\text{bytes}}$$

其中 $S$ 为 Token 数量，$n_{\text{layers}}$ 为网络层数，$n_{\text{heads\_kv}}$ 为 KV 注意力头数（采用 GQA 结构时远小于 Query 头数），$d_{\text{head}}$ 为单头维度，$b_{\text{bytes}}=2$。

**具体算例**：
以一个常见的 70B 模型为例（80 层，$n_{\text{heads\_kv}}=8$，$d_{\text{head}}=128$，BF16 精度）：
每个 Token 在整个网络中生成的 KV Cache 显存为：

$$2 \times 80 \times 8 \times 128 \times 1 \times 2 \text{ 字节} = 327,680 \text{ 字节} = 320 \text{ KB}$$

现在输入一段长度为 **2,000 汉字**的文档：
- **采用中文优化大词表**（约生成 **1,200 个 Token**）：
  该请求对应的 KV Cache 显存占用为 $1,200 \times 320\text{ KB} = 384,000\text{ KB} = 375\text{ MB}$。
- **采用中文未优化的英文主导词表**（膨胀产生约 **4,500 个 Token**）：
  该请求对应的 KV Cache 显存占用激增至 $4,500 \times 320\text{ KB} = 1,440,000\text{ KB} = 1,406.25\text{ MB} \approx 1.37\text{ GB}$。

仅仅由于分词膨胀，单请求的显存占用就翻了近 3.7 倍。这意味着在有限的显存资源下，系统能够支持的并发批次（Batch Size）会断崖式下降，极易导致高并发时爆显存（OOM）。关于显存构成的完整拆解，请参考 [KV Cache 是什么？](/interview/llm-interview/kv-cache.md) 与 [Transformer 的哪个部分最占用显存？](/interview/llm-interview/transformer-memory.md)。

### 2. 对 Prefill 与 Decode 延迟的双重放大
- **Prefill 阶段（首字延迟 TTFT）**：
  虽然 Transformer 中的前馈网络（FFN）对输入长度 $S$ 是线性依赖的，但核心自注意力机制中的 $Q K^T$ 矩阵乘法以及乘以 $V$ 的计算量与序列长度呈二次方关系 $\mathcal{O}(S^2 \cdot d)$。当文本因为分词不当导致 Token 数量膨胀数倍时，注意力层计算量与中间激活值显存占用成倍增加，显著拉长首字响应时间。
- **Decode 阶段（逐字生成延迟）**：
  大模型输出是严格串行自回归的。如果生成相同一段中文文本，膨胀率高的分词器需要进行更多步的前向传播迭代（Forward Pass），生成耗时成比例增加，使得终端用户感知的输出吞吐率（按汉字/秒计算）大幅下滑。

在网关层面控制调用开销与延时的落地方案，可进一步阅读 [Token 成本控制](/architecture/token-cost.md)。

## 面试追问：为什么不用纯单词或纯字符作为输入？

面试官常通过反向设问来考察分词设计的权衡逻辑：

> **追问 1：为什么不能像传统自然语言处理那样，直接用“空格切分的单词（Word-level）”？**

- **未登录词（OOV, Out-Of-Vocabulary）爆炸**：自然语言存在大量的构词衍生（时态、复数、大小写变体）、生僻人名、拼写错误以及新词。纯单词切分无法穷尽所有词汇。遇到未收录词只能标记为 `<unk>`，导致模型丢失信息。
- **词表与模型参数无法承受**：如果要尽量覆盖常用英文单词，词表规模需要达到数百万级。模型的输入 Embedding 层与输出线性层（LM Head）参数量均为 $V \times d_{\text{model}}$。当词表 $V$ 达数百万时，仅这两层就要消耗几十 GB 显存，且在全词表上计算 Softmax 的开销会严重拖慢推理速度。

> **追问 2：为什么不走另一个极端，纯粹使用“字符级别（Character-level）”？比如英文只保留 26 个字母加标点，中文只保留单字。**

- **序列长度成倍增加**：一个平均包含 5~6 个字符的英文单词，若采用字符级切分，Token 数量直接扩大 5 倍以上。这会快速消耗有限的上下文窗口（详见 [上下文窗口是什么？](/interview/llm-interview/context-window.md)），并在长文本时引发自注意力计算开销的大幅增加。
- **自回归解码步数剧增**：自回归生成每步只能吐出一个字符，输出一段话需要成百上千步模型前向计算，响应速度慢到无法满足交互需求。
- **单字符语义密度过低**：单字母（如 `t`、`e`、`r`）本身不具备明确语义，模型必须分配大量注意力头和网络深度来拼凑语义片段，增加了网络学习与收敛的负担。

**结论**：
当前广泛使用的**子词分词法（Subword Tokenization）**，正是在“词表参数体积（显存制约）”与“切分后序列长度（注意力计算与延迟制约）”之间取得的平衡折中方案。

## 常见误区与工程排坑

在面试与系统设计中，有三个关于 Token 的典型认知误区需要澄清：

### 误区 1：认为输入 Token 比输出 Token 便宜单纯是商业促销策略
**事实分析**：API 定价由模型服务商结合商业策略与运营成本公布。虽然服务商通常把输出 Token 价格定得更高，其背后反映了底层硬件执行特征的差异，但单价并非单凭物理机制唯一决定，实际开销还取决于并发批量（Batch Size）和硬件环境：
- **输入阶段（Prefill）**：Prompt 的全部 Token 可一次性并行输入，张量计算单元利用较充分，通常更容易达到计算密集型（Compute-bound）的高吞吐状态。
- **输出阶段（Decode）**：大模型自回归串行逐字生成。在小 Batch 或单并发场景下，每生成 1 个 Token 都需将全量模型权重从显存（HBM）搬运至计算核心，此时常受限于显存带宽（Memory-bound），算力利用率偏低；而在极高并发大 Batch 下，权重搬运被均摊，瓶颈特征也会变化。输出单价偏高既折射了低并发时硬件资源的占用成本，也受服务商调度与商业策略调控。

### 误区 2：认为“词表越大越好，压缩率越高越好”
**事实分析**：词表并非越大越好。
词表扩充确实能提高中英文文本的压缩率，减少 Token 数量，但有其边际递减效应和负面影响：
1. 词表变大后，长尾低频 Token 获得的训练机会极少，Embedding 层容易欠拟合；
2. 最终输出层（LM Head）在投影到词表维度并进行 Softmax 归一化时，计算开销与显存分配成正比上升。开源主流模型（如 LLaMA-3、Qwen）将词表控制在 100k~150k 之间，正是综合权衡了压缩率与解码层性能的结果。

### 误区 3：忽视自回归过程中的 EOS 丢失故障
**事实分析**：在微调（SFT）大模型或构造长上下文 Prompt 时，如果数据集中遗漏了结束标记（如 `<|im_end|>` 或 `</s>`），模型在生成完目标回答后将**无法主动触发停止信号**。
这会导致模型继续生成训练集中的幻觉内容，或陷入“死循环复读”，直到耗尽 `max_tokens` 阈值才被推理引擎强制截断。这种故障不仅拖垮单次请求的时延，还会产生大量无效的 Token 计费。工程上必须在推理参数中严格配置 `stop` 终止符列表，并对流式输出进行内容截断监测，详见 [Loop Engineering 的坑：无限循环、烧 Token、越改越差](/frontier/loop-engineering/Loop_Engineering_的坑_无限循环_烧_Token_越改越差.md)。
