当面对需要多步协作、跨系统调用和工具交互的复杂目标时，如果大语言模型仅依赖单步自回归生成，很容易在多轮调用后偏离最初目标、陷入无效重试或在长上下文中迷失方向。任务规划（Task Planning）是让智能体能够分解目标、判断当前执行进度，并在遇到异常时调整后续动作的控制机制。

## 面试标准口述：任务规划的核心价值与解决的问题

如果在面试中被问到：“为什么 Agent 系统需要显式任务规划？它的核心工作原理是什么？”，可以直接按照以下结构回答：

> **面试口述参考回答：**
>
> “任务规划是 Agent 将用户的非结构化、长周期目标，拆解为具有执行顺序和依赖关系的子任务清单或有向无环图（DAG），并根据环境反馈动态调控执行轨迹的机制。
>
> 它主要解决大模型在长流程中容易出现的两个问题：**单步贪婪决策导致的短视**，以及**多步执行中的复合错误累积**。如果没有显式规划，模型往往走一步看一步，一旦某一步工具调用偏离预期，整条链路就会逐渐脱轨。
>
> 在工程落地中，显式规划主要提供三项价值：
> 1. **解耦拆解与执行**：由规划模块负责宏观目标分解，执行模块专心调用工具，降低单步执行时的上下文负担；
> 2. **明确依赖与剪枝**：前置理顺前置条件，避免盲目试探无关工具；
> 3. **提供检验基准**：规划中的子目标和预期产出，为运行时的状态校验、错误归因以及局部重规划提供了对照依据。”

在深入规划机制前，如果需要回顾底层智能体循环与基础工具调用，可参考 [Agent 的核心流程](/interview/agent-interview/agent-loop.md) 与 [ReAct 的原理与循环](/interview/agent-interview/react-principle.md)。

## 贯穿示例：跨系统财报合并与风险排查

为了清晰说明各种规划模式的区别，我们以一个具体的工程任务贯穿后文：

*   **总目标**：分析指定企业近三年的经营现金流与供应链负债数据，识别潜在财务风险，生成合规报告，并在通过风控校验后通过邮件推送给审计人员。
*   **执行条件与状态**：
    *   依赖两个内部 API（`query_financial_db` 读取财务库，`audit_risk_rules` 进行合规规则检查）；
    *   依赖一个通知工具 `send_audit_email`（具备外部写操作的副作用）；
    *   数据可能存在缺失（如第三方库因数据延迟只提供近两年的部分摘要）。

在这个任务中，是每查一步决定下一步，还是一开始定好全部步骤，抑或是分层按里程碑推进？这就是不同规划范式的选择。

## 主流规划范式对比：单步贪婪、前置拆解与动态分层

根据对环境变化与不确定性的不同预期，工程实践中主要演化出三种规划方式：

![三种主流任务规划范式对比图](/images/content-rebuild/ec853cb697534d62/fig-1.png)

### 1. 单步贪婪规划（Reactive / Step-by-Step）

以经典 ReAct 为代表。系统在每一步接收上一动作的环境观测，在提示词中追加“思考（Thought）”，然后直接生成当下的“动作（Action）”：

$$\text{Action}_t \sim \pi_{\theta}(\cdot \mid \text{Goal}, \text{History}_{1:t-1}, \text{Observation}_t)$$

*   **运行过程**：不维护长远的全局步骤表。例如执行上述财报任务时，第一步先调 `query_financial_db(year=2024)`，拿到数据后思考“接下来还要看 2023 年”，再执行下一步。
*   **适用场景**：先验信息极少、需要根据前一步结果进行发散式探索的任务（例如排查未知的线上故障日志）。
*   **工程局限**：随着轮数增加，对话历史迅速膨胀。由于缺乏显式的全局里程碑，模型容易在重复报错时陷入死循环，或者在上下文变长后逐渐遗忘核心目标。

### 2. 前置一次性拆解（Plan-and-Solve / Plan-and-Execute）

将任务严格划分为两个阶段：规划器（Planner）在最开始分析目标，生成完整的固定步骤列表 $P = [s_1, s_2, \dots, s_n]$；执行器（Executor）随后按照拓扑顺序依次调度 [工具调用](/interview/agent-interview/tool-calling.md) 完成执行。

*   **运行过程**：规划器一次性生成：1. 抓取三年财报；2. 计算比率指标；3. 执行规则校验；4. 生成报表；5. 发送邮件。执行器按部就班分发调度。
*   **适用场景**：流程高度标准化、环境确定性强、每一步输出预期明确的工作流。
*   **工程局限**：对初始假设的脆弱性。如果在步骤 1 发现财务库中 2022 年数据缺失，原先计划好的步骤 2（对比三年数据）就会失去前置条件。若没有容错分支，整条静态流水线就会直接中断。

### 3. 动态分层规划（Hierarchical & Dynamic Planning）

在复杂业务工作流（如基于 [LangGraph 状态机编排](/interview/agent-interview/agent-frameworks.md)）中广泛采用。系统划分为高层规划者与底层执行者：

![动态分层规划与状态回传结构](/images/content-rebuild/ec853cb697534d62/fig-2.png)

*   **运行过程**：高层规划者仅定义核心阶段（里程碑）和阶段验收断言（如“阶段一：完成基础数据对齐，断言要求记录数大于等于2”）。底层执行者在每个阶段内部以轻量级动作闭环完成细节。阶段执行完毕后，由高层控制器根据产出校验结果决定推进或调整后续计划。
*   **适用场景**：长周期、包含外部易变环境、步骤间存在阶段性依赖的企业级业务系统。

| 维度 | 单步贪婪规划（ReAct） | 前置一次性拆解（Plan-and-Execute） | 动态分层规划（Hierarchical） |
| :--- | :--- | :--- | :--- |
| **决策视野** | 单步决策，无长远步骤视图 | 初始阶段生成全量步骤 | 宏观规划里程碑，微观动态自适应 |
| **单次推理负载** | 上下文逐轮累加，后期显存与Token增加 | 规划与执行解耦，单步上下文较小 | 分层维护上下文，状态按阶段归集 |
| **对意外阻断的韧性** | 依靠即时提示词修正，容易跑偏 | 初始假设打破后通常无法自愈 | 阶段断言拦截偏离，支持局部更新 |
| **适用场景特征** | 探索排查、开放域检索 | 确定性流程、数据转换批处理 | 跨系统集成、多阶段长链路业务 |

## 反思与自修正机制：错误的因果归因与处理

在规划执行过程中，报错和偏离是常态。未经分析的无脑重试（Retry）往往只会浪费 Token。自修正（Self-Refine）的核心在于：**捕获观测异常后，判断失败原因，再决定采取哪级修复动作**。

![自修正闭环与因果归因判定树](/images/content-rebuild/ec853cb697534d62/fig-3.png)

执行过程中遇到的异常主要可以分为三类，具体处置策略也可参考 [Agent 执行失败时的恢复方案](/interview/agent-interview/agent-error-handling.md)：

1. **格式与协议级错误（Protocol Failure）**
   *   *现象*：模型输出的 JSON 格式缺失闭合括号，或缺少 API 必填字段。
   *   *原因*：生成格式偏离，并不影响整体业务路线。
   *   *处理*：无需修改任务规划，将错误提示作为输入直接要求模型重新格式化输出。
2. **前提条件不满足（Precondition Failure）**
   *   *现象*：调用 `query_financial_db` 返回 404 或权限缺失。
   *   *原因*：规划器最初假设该数据直接可读，但现实环境缺少前置凭据或资源。
   *   *处理*：触发局部修补（Plan Patching）。保留已生成的计划骨架，在当前步骤前动态插入前置探针动作（例如“请求临时只读凭证”）。
3. **业务语义冲突（Semantic Conflict）**
   *   *现象*：接口调用成功，但计算出的风险评分与输入的基础资产负债率出现严重逻辑矛盾（例如资产为负但评级为极佳）。
   *   *原因*：子任务的业务假设或中间推理出现幻觉。
   *   *处理*：将当前生成的数据标记为不可信，通知高层规划器，回滚到上一个经过验证的状态快照并重新规划。

以下是基于归因分流的反思调度代码实现：

```python
# 规划执行中的状态校验与调度分发示例
from dataclasses import dataclass
from typing import Optional, Dict, Any

@dataclass
class SubTask:
    id: str
    description: str
    expected_field: str

class PlanController:
    def __init__(self, plan: list[SubTask]):
        self.plan = plan
        self.current_step = 0
        self.context: Dict[str, Any] = {}

    def execute_and_reflect(self, observation: Dict[str, Any]) -> str:
        current_task = self.plan[self.current_step]
        
        # 1. 验证产出是否符合断言
        if current_task.expected_field not in observation:
            return self._handle_failure(current_task, observation, error_type="MISSING_SCHEMA")
        
        # 2. 验证业务数值有效性
        if observation.get(current_task.expected_field) is None:
            return self._handle_failure(current_task, observation, error_type="PRECONDITION_UNMET")
        
        # 3. 验证业务语义一致性（检测是否存在矛盾）
        if observation.get("semantic_conflict", False):
            return self._handle_failure(current_task, observation, error_type="SEMANTIC_CONFLICT")
        
        # 校验通过，推进状态
        self.context[current_task.id] = observation
        self.current_step += 1
        return "PROCEED"

    def _handle_failure(self, task: SubTask, obs: Dict[str, Any], error_type: str) -> str:
        if error_type == "MISSING_SCHEMA":
            # 局部修复格式，不改动任务计划
            return f"RETRY_STEP: 补充参数 {task.expected_field} 后重试"
        elif error_type == "PRECONDITION_UNMET":
            # 插入前置补丁任务
            patch_task = SubTask(id=f"{task.id}_patch", description="检索备用数据源", expected_field=task.expected_field)
            self.plan.insert(self.current_step, patch_task)
            return "PATCH_PLAN: 已插入备用探针步骤"
        else:
            # 触发宏观重规划
            return "TRIGGER_REPLAN: 无法调和的业务冲突"
```

## 动态重规划的触发条件与防震荡设计

如果在每一次工具调用出现微小扰动时都全面推翻计划，会导致系统陷入反复重排的“震荡”状态，造成大量延迟与计算浪费。因此必须设立清晰的触发条件和防护边界。

![动态重规划触发矩阵与状态流转机](/images/content-rebuild/ec853cb697534d62/fig-4.png)

### 明确的重规划触发条件

1. **硬性阻断且局部重试耗尽**：
   下游接口返回不可恢复的错误（如实体不存在），且单步修复次数达到上限（如重试 2 次均失败）。
2. **运行预算阈值告警**：
   累计的 Token 消耗或请求耗时达到预设预算的警戒线（如 80%），规划器必须放弃深度探索，切换为精简备用方案。
3. **核心假设被实质性证伪**：
   例如在财报场景中，用户要求分析近三年数据，但实际发现仅有一年数据公开。此时即使每一步工具都调用成功，由于前提缺失，原计划的“多年度增长对比分析”也必须调整为“单年度深度分析与免责说明”。

### 避免频繁推翻计划的防震荡机制

*   **冻结已验证节点（Node Freezing）**：
    重规划只针对失败节点及其有直接依赖关系的下游节点。上游已经通过断言验证并产出数据的步骤必须锁定，不得重复执行。
*   **硬性重规划预算（Replanning Budget）**：
    在系统状态中显式维护 `replan_count`，为单次任务设定上限（属于可配置的防震荡策略，工程实践中常按业务容忍度设为 2~3 次）。达到阈值仍无法通过时，降级为返回部分成果并交由人工介入（Human-in-the-loop），防止死循环。
*   **状态快照与回滚（State Checkpointing）**：
    重规划前保存当前上下文镜像。如果重规划生成的新步骤执行依然失败，系统可安全回滚到上一个稳定快照，避免脏数据污染后续分析。关于复杂分析与检索规划的更多结合，可参考 [Agentic RAG 的查询规划与多步检索](/frontier/agentic-rag/complex-query-planning.md)。

## 工程权衡：规划深度与系统成本算例

在引入规划器时，需要评估其额外的模型调用开销是否能够换取更高的成功率。

![规划深度与系统开销的边际效益分析](/images/content-rebuild/ec853cb697534d62/fig-5.png)

### 教学估算对比

假设我们面对一个标准流程包含 5 个关键步骤的任务（提取、清洗、规则计算、排版、通知）。我们设定一组相同的单步基准开销进行教学测算：

*   **参数假设**：单次宏观或局部规划处理基准消耗 800 Input Tokens + 400 Output Tokens；单步执行器处理消耗 500 Input Tokens + 150 Output Tokens；动态分层规划中的阶段状态汇聚带来约 150 Tokens 上下文开销；在单步 ReAct 中，每前进一步都会将上一轮的历史追加到输入中，假设输入 Token 随步数 $k$ 递增：$\text{Input}(k) = 400 + 300 \times k$。
*   **开销与表现对比（教学示意）**：

| 指标（示意估算） | 单步贪婪（ReAct） | 前置一次性（Plan-and-Execute） | 动态分层规划（含 1 次局部修补） |
| :--- | :--- | :--- | :--- |
| **模型调用总次数** | 5 次（顺利）至 8 次以上（反复纠偏） | 1 次规划 + 5 次执行 = 6 次 | 1 次宏观规划 + 5 次执行 + 1 次局部调整 = 7 次 |
| **处理过程的总输入与输出** | 随步数累积，约 7,000 ~ 9,000 Tokens | 步骤独立分发，约 4,450 Tokens | 阶段性汇集上下文，约 5,800 Tokens |
| **假设失效时的表现** | 在历史中持续挣扎，可能偏离目标 | **直接中断**：后续步骤完全依赖前序数据，需全盘重跑 | **局部修补**：仅重跑受损步骤，保留已完成阶段 |

### 规划深度的边际效应

为什么不能在一开始就把任务细化到几十个操作原子？

随着初始规划深度的增加，模型的有效预测能力会受到外部环境不确定性的影响。超前拆解过细的步骤，本质上是将大量未经证实的先验假设固化下来。一旦第三步的真实返回值与最初预期稍有不同，后面规划好的十几步动作就会全线失效，造成更严重的**复合错误扩散**。

因此，合理的工程策略是：**高层宏观规划只锁定关键里程碑与验收标准，微观具体执行由底层工具或小范围动作链动态推进**。

![生产级 Agent 规划与执行引擎工程架构](/images/content-rebuild/ec853cb697534d62/fig-6.png)

对于业务规则明确的通用步骤，更适合沉淀为由代码预定义控制路径的函数或专用工具（可参考 [Agent Skills 的任务封装与复用](/frontier/agent-skills/skill-encapsulation.md)），仅将关键决策点交给大模型规划。

## 面试高频追问

### 追问 1：在什么场景下前置一次性拆解优于 ReAct？什么场景下会完全失效？

> **参考回答：**
>
> “前置拆解适用于**业务规则明确、步骤间依赖清晰且环境相对静态**的场景，比如根据模板从已清洗的数据中生成分析报告或固定的 ETL 处理。在这些场景中，预先规划可以避免多轮 ReAct 带来的上下文冗余，减少 Token 浪费并提高运行稳定性。
>
> 但在**强依赖未知环境探索**的场景下会迅速失效，比如排查未知的网络渗透漏洞或在线故障定位。由于下一步的决策完全取决于上一步返回的未知变量，任何前置生成的长步骤清单都会在第一轮意外反馈后直接作废。”

### 追问 2：如果规划生成的任务图（DAG）包含可以并行的分支，执行引擎需要注意什么？

> **参考回答：**
>
> “核心需要解决**状态写入竞争、上下文隔离与异常终止**三个问题：
> 1. **状态隔离**：并行执行的两个子任务应只读取其所需的最小上下文子集，产出的结果以增量补丁（Delta）形式返回，而不能直接并发修改同一个全局状态对象；
> 2. **汇聚点合并（Join Node）**：在并行分支汇聚处，通过显式的合并函数或规则校验数据一致性，防范不同分支产出相互矛盾的字段；
> 3. **异常快速短路（Early Exit）**：若分支 A 发生致命异常导致后续任务必然无法完成，执行引擎应通过异步取消信号立即终止还在运行的分支 B，避免无效的计算与外部计费。”

### 追问 3：为什么说遇到错误时，不可逆副作用是规划与重规划的最大挑战？

> **参考回答：**
>
> “只读操作（如查询、计算）失败后，系统随时可以安全回滚并重新规划；但具有**外部副作用的操作**（如发送邮件、扣款、删除数据）一旦执行便无法在物理上自动撤销。
> 如果重规划引擎在未做拦截的情况下重新跑整个流程，就会造成重复扣款或重复发信等事故。因此工程上必须做到：具有破坏性或写操作的节点前，强制设置确定性的审批拦截门禁（Human-in-the-loop），或者要求底层工具提供幂等性保证。”

---

## 常见误区与辨析

*   **误区一：把硬编码的条件判断代码当成“Agent 规划”**
    *   *辨析*：根据 Anthropic 在构建有效智能体中的定义，按预设代码路径编排模型与工具的属于工作流（Workflows）；只有当大模型能够根据任务上下文动态生成后续动作并控制执行过程时，才属于智能体（Agents）。两者结合的实现策略可参考 [AI Agent 是什么？](/interview/agent-interview/what-is-agent.md)。
*   **误区二：拆解的步骤越多越细，系统执行越稳定**
    *   *辨析*：规划过细会导致对先验条件的过度依赖。外部环境的一点点微小偏差都会让长链条失效。最佳实践是粗粒度里程碑规划搭配局部动态执行。
*   **误区三：重试和自修正只要提示词写好就能解决所有问题**
    *   *辨析*：提示词反思只能纠正模型认知范围内的输出逻辑。针对第三方接口宕机、网络超时、鉴权失败等工程基础设施问题，必须依赖宿主程序中的重试预算、熔断机制以及幂等控制来提供可靠保障，不可盲目交由大模型自由发挥。
