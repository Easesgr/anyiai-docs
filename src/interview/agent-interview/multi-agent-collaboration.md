在开发基于大语言模型的智能体时，很多团队起初都尝试用单个 Agent 解决所有问题：给它注入系统提示词，挂载十几个工具，让它自主规划和调用。但随着任务链路变长，单 Agent 会迅速撞上上下文膨胀、注意力被试错日志稀释、意图漂移以及工具越权等现实瓶颈。子智能体（Subagent）模式通过将复杂长任务拆分为独立的执行沙箱，实现上下文隔离与权限收窄。本文从面试口述出发，拆解父子 Agent 的派发时序、隔离机制、生命周期控制及边界条件。

## 面试标准口述：子智能体模式的核心价值与实现原理

面试中遇到“什么场景下需要多 Agent 协作而不是单个 Agent 解决？父子 Agent 是怎么实现的？”时，建议先给出明确的工程判断，再展开架构设计：

### 基础口述（60 秒紧凑版）

> 引入多 Agent 协作而不是单个 Agent，核心是为了解决两个问题：**上下文信噪比退化**与**工具决策混乱**。
>
> 当单 Agent 面临需要多步检索、代码试错或网页抓取的复杂深层任务时，大量中间临时日志会堆积在同一个上下文窗口中，导致模型注意力分散，甚至遗忘最开始的目标；同时挂载过多工具也会显著增加模型调错工具的概率。
>
> 父子 Agent（Subagent）的实现机制可以概括为三步：
> 1. **任务分派**：父 Agent 通过结构化工具调用（Tool Calling）向宿主系统发起子任务委托，指明执行目标和约束。
> 2. **沙箱隔离**：宿主拦截调用后，为子 Agent 创建独立的会话环境（独立 Session ID、专用提示词与受限工具集）。子 Agent 的中间探索、报错重试都在子环境中消化。
> 3. **结果汇总**：子 Agent 完成后，将符合数据契约的精简结果返回给父级。父 Agent 的上下文只新增一条工具返回消息，保护了主流程的上下文干净度。

### 进阶追问（架构细节版）

如果面试官深入追问“如何在工程上防止子 Agent 失控与越权”，可以从以下三点回答：

> - **权限单向收窄**：子 Agent 的工具权限必须受到白名单限制，通常是父级或系统授权范围的严格子集，且底层资源凭证应按最小特权原则降级（例如只读数据库连接、局部工作空间挂载）。
> - **生命周期受控**：子 Agent 必须设置硬性超时时间（Timeout）、单次调用 Token 配额和最大交互轮数熔断，防止陷入死循环。
> - **结构化契约汇聚**：子 Agent 退出前，宿主使用强类型 Schema（如 Pydantic）校验其返回内容，校验通过才将结果以 `ToolMessage` 格式写回父 Agent，避免自然语言回复带来的格式歧义。

## 贯穿案例：代码安全审计流水线

为了直观理解这套机制，本文以一个具体的工程任务贯穿始终：**自动审计代码仓库的安全漏洞并输出技术报告**。

- **父 Agent（审计总调度）**：负责阅读用户需求、检视项目全局目录、协调分析步骤，并编写最终的安全建议汇总。
- **子任务（深层探索）**：深入排查 `services/order` 模块中的 SQL 注入风险。这需要子 Agent 调取 AST 解析工具、反复搜索调用链、查找测试用例并执行片段模拟。

如果把排查过程中的上百行抽象语法树片段、搜索失败的重试日志全都留在父 Agent 窗口中，父 Agent 在写最终报告时就极易受到中间垃圾信息的干扰。接下来我们将看到系统如何优雅地隔离这一过程。

## 任务拆解与分派时序：父级指令如何实例化独立子 Agent

大语言模型自身是无状态的文本计算引擎，它无法主动创建系统线程或进程。父 Agent 派生子 Agent 的过程，本质上是**模型按照契约发出 Tool Calling 指令，由外层宿主系统（Host Runtime）拦截并编排执行实例**。

完整的分派时序包含以下四个步骤：

1. **意图决策与参数组装**：父 Agent 规划分析链路，判定模块审计需要大量的工具试错，于是调用内置的委派工具（如 `dispatch_subagent`）。调用参数包含：子任务类型、输入背景、目标说明及期望返回格式。
2. **宿主拦截与环境初始化**：框架运行时（如基于 LangGraph 编排的应用层）拦截该工具调用，挂起父 Agent 会话。宿主为子 Agent 生成独立的会话上下文（Session ID / Checkpoint），避免变量污染。
3. **运行时参数装配**：宿主为子 Agent 注入专用的系统提示词、分配最小特权工具包（仅给代码检索与语法分析工具，不给部署或发送邮件工具），并设定计算配额。
4. **子任务推进与生命周期闭环**：子 Agent 独立运行自己的推理与工具调用循环。执行完毕后由宿主收集最终摘要，作为父 Agent 本次工具调用的返回内容，唤醒父级继续向下推进。

```python
# 代码实现示意：宿主环境拦截派生指令并初始化子 Agent 沙箱
from typing import Dict, Any, List
from pydantic import BaseModel

class SubagentTaskSpec(BaseModel):
    task_id: str
    task_description: str
    allowed_tools: List[str]  # 限制子级可调用的工具白名单
    max_tokens_budget: int    # 消耗硬限制
    timeout_seconds: int      # 物理超时时间

def host_dispatch_subagent(parent_session_id: str, spec: SubagentTaskSpec) -> Dict[str, Any]:
    # 1. 权限校验：子 Agent 的工具白名单必须属于当前任务的系统授权范围
    system_allowed_tools = get_task_allowed_tools(parent_session_id)
    if not set(spec.allowed_tools).issubset(set(system_allowed_tools)):
        raise PermissionError("派生失败：工具超出任务授权范围")

    # 2. 隔离运行时上下文与状态存储
    sub_session_id = f"{parent_session_id}_sub_{spec.task_id}"
    sub_context = init_isolated_context(session_id=sub_session_id)
    
    # 3. 装配降权后的工具集与专属系统提示词
    sandboxed_tools = bind_tools(spec.allowed_tools)
    sub_agent_runner = create_agent_runner(
        context=sub_context,
        tools=sandboxed_tools,
        system_prompt=f"你是专项安全扫描执行器。当前目标: {spec.task_description}"
    )
    
    # 4. 在受限沙箱中运行（带超时与 Token 配额监控）
    return run_with_guardrails(
        runner=sub_agent_runner,
        timeout=spec.timeout_seconds,
        token_limit=spec.max_tokens_budget
    )
```

## 上下文隔离与信息阻断：防止试错噪点污染主流程

在单 Agent 串行架构中，所有的检索文档片段、工具调用报错、正则匹配重试都在主历史中线性追加。这种上下文无限堆积会带来严重的负面效应：

1. **有效注意力稀释**：上下文越长，模型在庞大文本中精准提取关键事实的能力越容易退化；
2. **意图污染**：子任务执行过程中的临时纠错指令（如“上一行语法错误，请重新匹配引号”）可能会干扰模型后续的全局分析，导致父级在后续生成中把局部约束当成全局规则。

### 噪声阻断机制

父子架构的核心价值在于**上下文阻断（Context Firewall）**。子 Agent 在排查 SQL 注入时，可能执行了 15 次正则匹配、读了 8 个函数实现、重试了 3 种语法解析方案：

- **子沙箱内**：保留完整的工具调用与反馈历史，支撑子 Agent 完成局部自我纠错与长链路探索。
- **父上下文内**：所有子任务内部的中间推理与错误日志被彻底隔绝在沙箱内。任务完结后沙箱销毁，只有一份提炼出的结构化发现（例如“在 `OrderRepo.kt:42` 发现未转义拼接”）输入回父级。

### 上下文开销算例对比（教学示意）

我们设定一个典型的审计场景参数（数据为便于理解机制的教学算例假设）：
- 主 Agent 全局对话与规划基底上下文：$2,000$ Token；
- 子任务排查 SQL 注入：阅读代码与中间检索返回累计 $5 \times 4,000 = 20,000$ Token 内容；经过 6 轮交互与修正，产生推理与请求约 $6 \times 300 = 1,800$ Token；子任务内部中间数据体量合计：
  $$20,000 + 1,800 = 21,800\text{ Token}$$
- 提取后的结构化漏洞判定结论：$500$ Token。

| 对比维度 | 单 Agent 模式（未隔离） | 父子 Agent 模式（沙箱阻断） |
| :--- | :--- | :--- |
| **主流程最终上下文开销** | $2,000 + 21,800 + 500 = 24,300$ Token | $2,000 + 500 = 2,500$ Token |
| **主上下文中的信噪比** | 低（充斥大量冗余 AST 输出与试错代码） | 高（仅包含规划步骤与结构化审计结论） |
| **注意力受干扰风险** | 高（主模型容易受代码报错提示词误导） | 低（局部试错历史随子沙箱销毁被物理抛弃） |
| **并行执行多个子任务** | 难（多任务日志交叉串行累积，极易撑爆窗口） | 易（多个子任务在各自独立的 $21,800$ Token 沙箱内并发） |

## 子 Agent 的生命周期控制：超时熔断与结构化汇总

子 Agent 绝不能脱离宿主环境无休止运行。如果子任务因为模型决策漂移或工具反复报错而陷入死循环，会白白消耗配额。宿主系统必须为其建立清晰的状态机与监控机制。

### 运行时状态变迁

子 Agent 的生命周期包含明确的五种状态：

1. **Pending（待初始化）**：宿主校验参数合法性，配置独立的上下文存储区和工具白名单。
2. **Running（运行中）**：子 Agent 在独立循环中自主决策。宿主在此期间挂载资源监控，统计经过的时间（Wall-clock Time）和 Token 消耗量。
3. **Suspended（挂起状态）**：若子 Agent 遇到需要高危确认的操作，可暂时持久化状态并中断执行，等待人机协同（Human-in-the-loop）确认。
4. **Completed（正常完结）**：子 Agent 达成预设目标并输出结果，触发格式校验。
5. **Terminated / Failed（异常熔断）**：若超过超时时间阈值、达到 Token 消耗上限或工具连续报错超出重试阈值，宿主强制终止沙箱，并向父级回传标准失败错误码。

### 输出契约与格式校验

子 Agent 不能随意输出自由文本，否则父 Agent 依然需要花费推理算力去解析格式：

- **强类型 Schema 验证**：宿主使用预定义的 Pydantic 类或 JSON Schema 校验子 Agent 的最终输出。如果字段缺失，宿主可以在子沙箱内部自动提示模型修复，而不需要惊动父 Agent。
- **资源释放（Tear Down）**：数据校验完成后，子 Agent 分配的临时文件目录和网络连接被即时释放，确保系统资源不发生泄漏。

## 权限受控继承：限制子 Agent 的能力边界

在智能体安全设计中，子 Agent 往往是越权风险的高发点。如果父 Agent 只有代码阅读权限，而子 Agent 在执行分析时却能调用代码提交或远程部署工具，系统的安全边界就会彻底被击穿。

### 权限单向收窄原则（Subsetting）

工程架构上必须强制实现**工具权限单向收窄**：

$$\text{Tools}_{\text{child}} \subseteq \text{Tools}_{\text{allowed}}$$

子 Agent 绝不能申请超出当前流程授权范围之外的高敏工具。宿主在拦截派生请求时，必须校验其工具请求白名单。一旦发现子 Agent 试图申请未授权工具，宿主应立刻拒绝派生并向父级返回鉴权异常。

```
当前任务授权池: [File_Read, AST_Search, Terminal_Exec, Deploy_Prod]
                     │
                     ├─ 合规派生: [File_Read, AST_Search] (严格受限子集，安全)
                     │
                     └─ 越权拦截: [File_Read, Deploy_Prod] (生产环境部署工具禁止委派给探针)
```

### 凭证作用域降级

除了工具名称维度的控制，工具底层的访问凭证也必须进行物理隔离：

1. **目录只读挂载**：在代码审计场景中，父 Agent 即使有全局文件系统访问权，传给排查子 Agent 的也只能是特定目录的只读镜像，防止其意外修改源码。
2. **短期临时 Token**：若子 Agent 必须调用外部 API，宿主应当为其签发具有短过期时间（如 5 分钟）、限制仅访问单个接口的临时凭证，避免长期密钥暴露。
3. **网络沙箱隔离**：限制子 Agent 的网络请求出口，禁止其向未列入白名单的外部服务器发送 HTTP 请求，防止被检索到的代码片段中隐藏的 Prompt 注入指令把数据外发。

## 递归派生陷阱与调用深度控制

如果系统允许子 Agent 继续创建更下一级的子 Agent（“孙子 Agent”），一旦缺乏全局硬性约束，极易引发**派生爆炸**。例如：父 Agent 拆出 4 个子任务，每个子任务遇到不确定的点又各拆出 4 个任务，调用树呈指数级裂变，几分钟内就会耗尽团队的 API 额度与系统连接池。

### 防控工程策略

1. **最大递归深度限制（Max Depth Guard）**：
   在会话元数据中注入深度计数器 `depth`。根父级为 `depth=0`，第一级子 Agent 为 `depth=1`。宿主设置全局硬性上限（通常设为 $D_{\max} = 1$ 或 $2$）。当 `depth >= D_{max}` 时，宿主从工具列表中直接移除 `dispatch_subagent`，强制当前 Agent 必须自行调用基础工具完成任务。
2. **并发度信号量（Concurrency Semaphore）**：
   为单个根任务维护全局并发子 Agent 计数器。例如同一时刻最多允许 3 个子 Agent 处于 Running 状态，超出者排队等待，平抑峰值算力与网络压力。
3. **任务树预算池（Global Budget Pool）**：
   预算不能由各层级 Agent 自行随意申报。必须由父级从全局总预算（如 $50,000$ Token）中划分一部分（如 $8,000$ Token）硬性配额给子 Agent。子 Agent 达到该配额上限即被宿主熔断结算，杜绝无限透支。

## 避坑指南：识别多 Agent 架构的常见误区

在架构评审与面试交流中，需要区分真实工程实践与概念炒作：

### 误区 1：只要任务稍微复杂，就必须上多 Agent 协作
**纠偏**：多 Agent 协作意味着更多的网络通信开销、更高的延迟和复杂的编排逻辑。根据 Anthropic 在《Building effective agents》中的实践总结，在绝大多数结构化较强的业务场景中，优先使用由预定义代码路径串联的**工作流（Workflows）**，往往比让模型自主调度子 Agent 具有更高的可预测性与经济性。代码控制执行分支不代表工作流内部模型调用或外部状态 100% 确定，但相比自主 Agent 显著减少了决策漂移。只有在子任务具有高度不确定性、需要长程试错，且必须与主流程做上下文与权限物理隔离时，引入 Subagent 才是划算的权衡。

### 误区 2：子 Agent 必须把所有执行日志完整交回父 Agent 审计
**纠偏**：这种做法直接破坏了上下文隔离的初衷。如果子 Agent 把执行中的 20 轮控制台打印信息原封不动传给父 Agent，父 Agent 的上下文依然会被海量低价值字符淹没。父 Agent 只需要结构化的结论、置信度以及核心引用证据（如文件行号或证据文本切片）。

### 误区 3：子 Agent 必然是独立的操作系统进程或微服务容器
**纠偏**：在主流 Agent 运行时（如 LangGraph 等框架）中，子 Agent 绝大多数情况下只是同一应用进程内的**独立状态图（Subgraph）**或**独立线程会话（Thread Session）**。它们拥有独立的内存上下文和状态检查点，并不必然绑定笨重的容器化基础设施。过早将 Subagent 映射为微服务容器会徒增系统运维成本。
