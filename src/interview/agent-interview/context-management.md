在开发基于大模型的自主智能体（Agent）时，开发者常遇到类似现象：一个在 3 到 5 步内表现出色的 Agent，一旦执行链条拉长到 15 步以上，就会出现响应变慢、忘记初始指令约束、甚至在工具调用之间打转的异常状态。

以一个“排查线上数据库慢查询”的运维 Agent 为例：初始指令明确要求“严禁执行写操作，仅分析并输出建议”。第 1 步它查询慢日志，工具返回了包含数百条 SQL 的冗长数据；第 3 步它调取监控指标；到了第 10 步，累积的上下文已超过几万 Token，模型在生成下一步操作时，把最初的“严禁写操作”约束抛在脑后，甚至尝试创建临时表来加速查询。

这种失败并非大模型推理能力突然退化，而是运行时缺乏上下文管理的必然结果。理解上下文管理，是构建多步长可靠 Agent 的基础。

## 一、面试标准口述：Agent 上下文管理的核心逻辑

在面试中被问及“Agent 的上下文管理为什么重要？有哪些具体治理方案？”时，建议从**无状态机制、膨胀风险、三层治理策略**三个层面紧凑作答：

> **核心口述回答：**
>
> 上下文管理是保证 Agent 长程任务可用性与成本可控的运行时控制机制。大语言模型本质上是无状态的单次调用函数，Agent 的连续决策依赖宿主程序在每一步把此前的系统指令、历史对话、工具调用和环境返回拼接成完整的输入序列送回模型。如果不加管控，随着执行步长增加会带来三大风险：
> 1. **Prefill 计算与账单成本累增**：模型每轮调用都要对全量历史重新计算 Key-Value 向量，输入 Token 随步数增加呈平方级累加，不仅延迟上升，计费也迅速扩大；
> 2. **关键指令衰减（如 Lost in the Middle）**：模型在长输入中间区域的注意力权重和事实提取能力往往低于首尾，历史中杂乱的中间结果会冲淡最初的核心规则；
> 3. **工具输出污染**：API 或数据库返回的大量冗余字段（如原始日志、大列表 JSON）会迅速挤占有限的有效窗口。
>
> 工程落地上通常采用三层手段：
> - **输入截断与引用**：对工具输出做字段投影，大体量数据存入外部存储并向上下文返回存储句柄（Pointer）；
> - **动态历史压缩**：通过高低水位线机制控制长度，近期消息保留原始细节，超限的旧消息由轻量模型分段压缩为增量摘要；
> - **分层隔离与缓存**：将上下文划分为静态系统区、全局状态区、检索记忆区与动态工作栈，保证静态前缀稳定以最大化利用 Prompt Caching（前缀缓存）降低延迟。

## 二、上下文膨胀带来的成本累加与注意力衰减

要解决长上下文问题，需要理清无管控状态下系统面临的具体开销与模型表现退化。

### 1. Prefill 阶段的 Token 累加算例
在 [Agent 的核心流程](/interview/agent-interview/agent-loop.md) 中，Agent 依靠循环（Loop）不断交替执行“模型思考/行动”与“环境返回观察”。

在生成每个输出 Token（Decode 阶段）之前，模型必须先读取全部已有输入并计算其键值对表示，这一过程称为 **Prefill（前填）阶段**。假设一个任务中：
- 系统指令与工具声明固定占用 $S = 2{,}000$ Tokens；
- 每一轮模型输出的思考与工具调用参数平均占用 $g = 200$ Tokens；
- 外部工具返回的结果平均占用 $o = 3{,}000$ Tokens。

在没有压缩机制的情况下，第 $N$ 轮模型调用时单次输入的 Token 数量为：
$$T_N = S + \sum_{k=1}^{N-1} (g_k + o_k) = 2000 + (N-1) \times 3200$$

我们计算前 20 步中每次调用的输入长度与累积处理的 Prefill Token 总量：

| 执行步数 ($N$) | 单步环境返回 ($o$) | 当前调用输入长度 ($T_N$) | 累计 Prefill 输入 Tokens |
| :--- | :--- | :--- | :--- |
| 第 1 步 | 0 | 2,000 | 2,000 |
| 第 5 步 | 3,000 | 14,800 | 42,000 |
| 第 10 步 | 3,000 | 30,800 | 164,000 |
| 第 20 步 | 3,000 | 62,800 | 648,000 |

*注：上表计算基于每步恒定增长假设，用于说明 Prefill 总开销随步数呈二次方累积的趋势。实际工程中工具返回大小会有波动。*

从数据可以看出：到第 20 步时，单次输入的长度已超过 6.2 万 Tokens，而宿主程序为该任务向模型服务商支付的 Prefill Token 总量已经突破 64 万（达到 64.8 万 Tokens）。即使模型单价不高，多步长任务的计费也会迅速失控；同时，输入序列变长直接拖慢了首字生成时间（TTFT, Time To First Token）。

### 2. 中间位置信息丢失（Lost in the Middle）
长上下文模型标称的物理支持长度（如 128K 或 1M Tokens）仅代表窗口容纳上限，不等于在长序列任意位置都具有相同的检索与理解精度。

大量长文本问答与长程注意力评测表明，大模型对位于输入序列**开头（Primacy）**和**结尾（Recency）**的信息关注度通常高于中间区域。当关键约束（如第 1 步设定的安全边界、第 2 步获取的鉴权凭证）被后续数万 Token 的工具输出推挤至序列中部（例如 40%–70% 相对位置）时，模型在自注意力分配中对该区域的关注往往会被大量稀释，进而导致指令遵循失败。更多关于长序列衰减的实验分析可参考 [长上下文应用的陷阱与位置衰减](/frontier/long-context-app/long-context-pitfalls.md)。

## 三、工具输出数据的修剪策略

在 [Tool Calling](/interview/agent-interview/tool-calling.md) 场景下，上下文激增的主要来源通常不是用户的短文本提问，而是外部系统返回的未过滤数据。例如数据库查询返回的几千行数据表，或接口报错时附带的几百行调用栈。

针对工具输出，工程上常用三种递进处理方式：

### 1. 字段投影（Field Projection）
下游决策通常只需要几项核心指标，并不需要全部原始元数据。例如查询容器状态时，仅需要容器 ID、镜像名、运行状态与重启次数，可主动过滤掉包含大量配置明细的字段。

### 2. 数量截断与分页提示（Pagination & Guardrail Truncation）
在工具执行层设定输出长度的硬性阈值。截断时必须显式告知模型真实数据的总量，并提供明确的获取下一页参数的方法，避免模型做出错误的外推。

### 3. 外部存储与句柄引用（Pointer-based Offloading）
当后续流程可能需要用到全量数据时，工具层应将大体量数据写入对象存储或临时文件，只把生成的数据文件路径（句柄/URI）与简要统计信息放入上下文中。

```python
# 工具输出裁剪与引用化存储处理示例
import json
import uuid

MAX_INLINE_ITEMS = 5

def sanitize_tool_output(raw_records: list[dict], storage_client) -> str:
    total_count = len(raw_records)
    
    # 1. 字段过滤：仅保留关键诊断字段
    projected = [
        {"id": r.get("id"), "status": r.get("status"), "name": r.get("name")}
        for r in raw_records
    ]
    
    # 2. 数量小于阈值，直接内联返回
    if total_count <= MAX_INLINE_ITEMS:
        return json.dumps({"count": total_count, "items": projected}, ensure_ascii=False)
    
    # 3. 超过阈值：落盘外部存储，返回引用句柄
    file_key = f"spool/query_{uuid.uuid4().hex[:8]}.json"
    storage_client.save(file_key, json.dumps(raw_records, ensure_ascii=False))
    
    inline_sample = projected[:MAX_INLINE_ITEMS]
    return json.dumps({
        "warning": f"结果集过大，共 {total_count} 条记录。已截断内联显示前 {MAX_INLINE_ITEMS} 条。",
        "storage_pointer": file_key,
        "sample_items": inline_sample,
        "action_guidance": "如需全局聚合分析，请调用专用数据分析工具并传入 storage_pointer。"
    }, ensure_ascii=False)
```

## 四、历史交互压缩：滑动窗口与增量状态摘要

在控制住单步工具输出后，多轮对话历史本身的累积仍需算法来周期性清理。

### 1. 基于规则的滑动窗口（Sliding Window）
- **做法**：维护一个消息队列，仅保留最近 $K$ 轮（或最近 8,000 Tokens）的消息。超出预算时，将最早的消息弹出队列。
- **适用场景**：短平快任务或各步骤之间相对独立的场景。
- **局限**：早期用户输入的重要参数或全局约束会被直接丢弃，容易出现前后逻辑脱节。

### 2. 基于轻量模型的增量状态摘要（Incremental State Summarization）
- **做法**：当历史长度达到设定上限时，调用低成本的小模型，将需要被移出活跃窗口的历史交互整理为一份精炼的文字摘要，保存在系统提示词后方。
- **为什么不能每轮都摘要**：频繁摘要会引入三大问题：一是每步增加一次额外模型调用，增加延迟与费用；二是大模型摘要存在信息损耗，多次反复重写会导致**传话筒效应**，早期细节在反复转述中容易失真甚至产生虚构；三是破坏缓存前缀命中。

### 3. 高低水位线控制（Watermark Trigger）
为了兼顾准确性与成本，工程中通常使用双水位线机制：
- **高水位线（如 12,000 Tokens）**：当当前上下文总长度触及高水位时，触发压缩流程；
- **低水位线（如 4,000 Tokens）**：压缩器将较旧的消息块合并压缩为摘要，使剩余上下文长度回落至低水位线附近；
- **近轮活跃保留区**：无论何时，强制保留最近 $M$ 步（例如最近 3 步）的原始交互记录，确保模型对眼下正在执行的因果逻辑具备清晰的感知。

## 五、上下文四层隔离布局与 Prompt Caching

上下文不仅关乎内容多少，其结构顺序对模型的注意力和推理性能同样有直接影响。不合理的顺序打乱会导致推理引擎的缓存频繁失效。

推荐将上下文划分为四个独立逻辑层级：

| 区域划分 | 内容组成 | 变动频率 | 缓存友好性 |
| :--- | :--- | :--- | :--- |
| **1. 静态系统指令区 (System Core)** | 身份设定、行为准则、可用工具声明 (Tool Schemas) | 静态固定 | 高度复用（Prefix Cache 命中） |
| **2. 任务全局状态区 (Global State)** | 当前目标拆解、已归档历史摘要、核心环境变量 | 低频更新 | 局部增量复用 |
| **3. 长期记忆插槽 (Memory Slots)** | 针对当前步骤按需检索注入的相关知识（参考 [Agent 中的 Memory](/interview/agent-interview/agent-memory.md)） | 中频按需更新 | 视检索结果而定 |
| **4. 活动执行工作栈 (Scratchpad)** | 最近几步的思考、工具调用及工具返回明细 | 高频动态追加 | 末尾变化，不破坏前置缓存 |

```text
+-------------------------------------------------------------+
| [静态系统区 - 绝对置顶]                                     |
| System Instructions: "You are an autonomous DB Engineer..." |
| Tool Schemas: [query_sql, inspect_table, run_migration...]  |
+-------------------------------------------------------------+
| [任务全局状态区]                                           |
| Task Status: Step 3/5 Completed                             |
| History Summary: Successfully connected to replica host...  |
+-------------------------------------------------------------+
| [长期记忆与检索插槽]                                       |
| Recalled Rules: "Production table alterations require VIP"  |
+-------------------------------------------------------------+
| [活动执行工作栈 - 最近 N 轮滑动明细]                        |
| Turn N-1: Assistant(call=inspect_table) -> Tool(columns...) |
| Turn N: Thought -> Next Action                              |
+-------------------------------------------------------------+
```

现代主流大模型 API（如 Anthropic Claude、OpenAI）以及开源自建推理引擎（如 vLLM）普遍支持 **Prompt Caching（前缀缓存）**。前缀缓存要求输入序列的开头部分必须保持严格的字节级一致。将固定不变的 System Prompt 和工具 Schema 放在最前端，动态消息追加在末尾，可使前缀部分的 Prefill 耗时大幅减少、计费显著降低。关于上下文编排的系统设计，可参阅 [高质量上下文构建指南](/frontier/context-engineering/high-quality-context.md)。

## 六、面试高频追问与常见认知误区

### 追问 1：如果工具输出的大数据集必须完整分析才能得出结论，不能截断，该如何设计？
**口述要点：**
1. **子 Agent 分治（推荐）**：主 Agent 不直接将海量数据读入自身上下文，而是派发子任务给专门的数据分析子 Agent（Subagent）。子 Agent 在独立的短生命周期上下文中分批次加载、汇总数据，最后仅把结构化的聚合结论返回给主 Agent；
2. **代码沙箱执行**：让 Agent 生成数据处理代码（如 Pandas 或 SQL 过滤逻辑），直接在工具宿主环境或代码沙箱中运行，只将计算后的统计指标或异常行返回模型。

### 追问 2：使用 Prompt Caching 时，对上下文管理逻辑有什么具体限制？
**口述要点：**
- 前缀匹配具有严格的从左到右依赖性。只要前面有一个字符变动，其后所有的缓存均告失效；
- 服务商通常设有最小缓存门槛（如 Claude 要求前缀通常不低于 1,024 Tokens）与生存时间（TTL），静态前缀过短或调用间隔过长无法触发命中；
- 严禁在静态 System Prompt 中插入动态变化的时间戳、动态生成的请求 UUID 或随机顺序的工具定义；
- 易变的状态变量（如当前重试计数器、动态时间）应封装在静态区之后的消息体内，确保静态前缀长效稳定。

![动态变量干扰导致 Prompt Caching 失效对比图](/images/content-rebuild/413545d6a71beed1/fig-6.png)

### 常见认知误区辨析

* **误区一：“模型已经支持 1M 上下文，直接把所有历史全塞进去就行，没必要费力管理。”**
  * **事实**：长序列会显著增加 Prefill 耗时与 Token 账单；更关键的是，中间堆积的大量非关键数据会冲淡模型的注意力分配，导致在复杂任务中的指令遵循与多步推理准确度下降。
* **误区二：“每一步都调用摘要模型压缩上一轮对话，能最大限度节省 Token。”**
  * **事实**：频繁摘要不仅额外增加了调用次数和响应延迟，还会因为多层连续摘要引发累积性信息失真与虚构。合理做法是结合高低水位线与活跃保留区进行分段处理。
* **误区三：“接入向量检索（RAG）就可以替代上下文管理。”**
  * **事实**：RAG 解决的是从外部大规模非结构化知识库中检索相关静态事实的问题；而上下文管理解决的是 Agent 运行时的任务工作状态、执行轨迹与决策因果链的动态维护，二者分工不同，不可相互替代。

## 读者自测思考

1. 在一个代码生成 Agent 中，某次编译报错输出了 2,000 行包含大量第三方库跟踪的堆栈日志。应采用何种策略将其修剪后再输入上下文？
2. 为什么在 Prompt Caching 生效的系统中，每次调用动态更新工具列表（Tool Schemas）的顺序会导致严重的性能退化？
3. 当使用增量摘要替换旧历史后，如果后续某一步骤确实需要回溯第 2 步中某个具体配置参数的原始字段，架构上应如何提供回溯能力？
