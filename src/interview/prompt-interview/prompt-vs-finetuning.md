在生成式 AI 应用开发中，“调 Prompt 还是微调模型”是技术方案评审和高频面试中最核心的技术选型问题。很多初学者容易陷入两个误区：一是认为微调是解决所有 Prompt 效果不佳的终极手段；二是认为写长 Prompt 是完全零成本的捷径。

实际上，两者的差异根植于计算架构与模型机制的不同：Prompt 优化是在模型参数固定的前提下，依赖注意力机制建立临时上下文；微调则是通过反向传播算法，将特定知识或行为模式写入神经网络权重。

## 面试标准口述回答

如果面试官要求用两分钟讲清楚 Prompt 优化与微调的区别与选型，可以按以下层次回答：

> **核心机制**：Prompt 优化保持基座模型权重冻结，将指令、约束和示例编码进输入序列，依赖 Transformer 的自注意力机制在上下文窗口内进行推理，属于“运行时的临时记忆引导”；微调（如全量 SFT 或 LoRA）则通过反向传播，将领域数据分布、特定任务格式或专业语气转化为参数增量，固化在神经网络权重中。
>
> **工程优劣**：Prompt 优化的优势是零前期训练成本、更新即时生效、支持快速迭代；缺点是每次请求都要消耗前置 Prefill 计算量与 KV Cache 显存，且长上下文对复杂指令的遵循存在概率性漂移。微调的优势是大幅压缩输入序列长度、输出格式一致性高、显著降低单次推理延迟与显存占用；缺点是需要前期数据清洗和算力投入，且不适合处理频繁变动的动态事实。
>
> **选型准则**：处理高频更新的动态事实（如商品价格、实时库存）优先使用 RAG + Prompt 优化；如果需要严格锁定垂直领域的结构化输出（如非标 JSON、专用文书格式）或面对高并发极低延迟要求，则应通过微调将能力内化到小模型中。

## 贯穿案例：电商智能工单处理

为了直观理解两者的运作机制，我们以一个电商智能工单系统为例。业务要求：接收用户的退换货描述，提取出“问题类别、订单号、涉及商品、责任判定”，并输出严格符合内部系统格式的 JSON。

### 机制一：Prompt 优化的运行时开销
在 Prompt 优化方案中，模型参数保持不变。为了让模型输出稳定的 JSON 并理解特定的分类标准，开发者通常会在输入中加入系统说明、字段定义以及 3 到 5 个完整的输入输出示例（Few-shot）。关于基础提示词的设计方法，可参考 [Prompt 工程是什么](/interview/prompt-interview/what-is-prompt.md) 与 [Prompt 基本结构](/interview/prompt-interview/prompt-structure.md)。

在推理执行时，大模型会经历两个阶段：
1. **Prefill（预填充阶段）**：推理引擎计算输入 Prompt 中所有 Token 的 Key 和 Value 向量，并写入显存中的 KV Cache。如果 5 个示例让输入序列膨胀到 2,500 Token，每次请求无论多么简单的用户输入，都必须先对这 2,500 Token 进行全量注意力计算，导致首字生成延迟（TTFT, Time to First Token）显著上升。
2. **Decode（自回归生成阶段）**：模型逐字生成输出 JSON。在此期间，显存必须持续驻留对应 2,500 Token 的 KV Cache，直到本次请求彻底结束。当线上并发量从 10 增至 100 时，KV Cache 显存占用呈线性增长，容易导致 GPU 显存耗尽（OOM）。

### 机制二：微调的参数固化机制
在微调方案中，系统使用数千条标注好的“用户输入-标准 JSON 输出”工单数据，通过反向传播计算损失函数并更新权重。在参数高效微调（如 LoRA）中，基座模型权重 $W_0$ 保持冻结，仅训练低秩矩阵 $A$ 和 $B$（参数增量 $\Delta W = B \times A$），详见 [微调基础与 LoRA](/fundamentals/llm-basics/finetuning-sft-lora.md) 及 [LoRA 与 QLoRA 原理](/fundamentals/training-and-finetuning/lora-qlora.md)。

训练完成后，格式要求和分类规则已经以内生概率分布的形式固化在权重中。线上推理时：
* 输入 Prompt 不再需要塞入冗长的 5 个示例，仅需包含当前用户的 200 Token 描述和极短的指令。
* Prefill 计算量缩减 90% 以上，首字延迟显著降低，并发场景下的 KV Cache 显存开销同步大幅下降。

## 选型决策：四类业务场景划分

技术选型不能脱离业务的具体约束。我们可以从“事实动态性”与“时延/格式规范要求”两个维度评估选型路径：

![任务类型与系统约束的选型四象限决策模型](/images/content-rebuild/de66f4bade8ca2e3/fig-2.png)

### 1. 高频动态事实更新（优先选择 RAG + Prompt）
* **典型场景**：电商实时库存、秒杀价格变动、物流节点追踪、财经即时资讯。
* **为什么微调不合适**：微调后参数属于黑盒概率分布。如果每天重新微调价格数据，不仅存在训练时延，模型还可能在回答时混淆新旧参数，产生不可预测的幻觉；同时微调无法提供确定性的数据对账与审计溯源能力。
* **推荐解法**：保持模型权重固定，通过检索系统（如 Elasticsearch 或向量数据库）获取实时真实数据，以 Context 形式拼接在 Prompt 中，结合 [RAG 中的 Prompt 组织](/interview/prompt-interview/rag-prompt.md) 要求模型严格基于材料回答。

### 2. 严格输出结构与特定语法（优先选择 SFT / LoRA）
* **典型场景**：企业内部专用 DSL 语言生成、复杂多层嵌套 JSON 提取、特定法律合规文书结构化。
* **为什么长 Prompt 会遇瓶颈**：当目标 Schema 包含大量嵌套字段或复杂约束时，单纯依靠 Few-shot 示例容易受上下文长度与密集规则干扰，导致模型对长指令的依从度下降，生成过程中容易出现标点缺失、键名拼写错误或字段遗漏。
* **微调收益**：通过几百至几千条清洗干净的结构化样例进行 [SFT 监督微调](/fundamentals/training-and-finetuning/sft.md)，可以让模型对特定语法的下一个 Token 预测概率高度集中，显著提升格式合法率。

### 3. 固定业务语气与垂直领域角色（优先选择 SFT / DPO）
* **典型场景**：特定品牌风格的客服话术、心理咨询共情对话、游戏 NPC 角色扮演。
* **为什么微调表现更优**：在系统提示词中写“请使用亲切幽默的语气”往往只能提供弱约束，不同基座模型的理解参差不齐。使用经过人工偏好标注的对话对进行指令微调或偏好对齐（如 DPO），可以从根本上改变模型输出文本的风格偏好。

### 4. 严苛 SLA 与高吞吐并发（优先微调小模型）
* **典型场景**：在线搜索重排序、内容即时风控机审、边缘网关意图识别。当接口的 P99 响应时间要求在 200ms 以内，且需要承载数千 QPS 时，大模型加长 Prompt 方案的首字延迟与显存开销直接超标，必须微调 0.5B 到 7B 级别的小模型来提供高吞吐服务。

## 全生命周期成本核算模型

选型时必须算清楚全生命周期成本（TCO）。不能只看单次 API 调用的价格，也不能忽视私有部署微调模型的运维基建成本。

![全生命周期成本核算：前期启动成本与长尾推理成本推移曲线](/images/content-rebuild/de66f4bade8ca2e3/fig-3.png)

### 测算设定
* **场景**：每月处理 100 万次用户工单分类与抽取任务。
* **单次请求**：包含 200 Token 用户描述，模型输出 100 Token 结构化结果。
* **周期**：连续稳定运营 6 个月（总计 600 万次请求）。

### 方案 A：通用商用大模型 API + Few-shot Prompt
* **输入输出长度**：Prompt 包含任务说明与 5 个 [Few-shot 示例](/interview/prompt-interview/shot-types.md)，单次请求输入达 2,500 Token；输出 100 Token。
* **计费假设**（以常见商用 API 输入 ¥0.01/千 Token、输出 ¥0.03/千 Token 测算，假设按全量输入计费且未计入厂商的 Prompt 缓存优惠）：
  * 单次输入成本：$(2,500 / 1,000) \times 0.01 = 0.025$ 元
  * 单次输出成本：$(100 / 1,000) \times 0.03 = 0.003$ 元
  * 单月开销：$1,000,000 \times (0.025 + 0.003) = 28,000$ 元
  * **6 个月总运营成本**：$28,000 \times 6 = 168,000$ 元。

### 方案 B：微调开源 8B 模型并自建部署
* **前期投入**：
  * 数据整理与清洗：2,000 条高质量标注工单样例，人工审核与清洗成本约 8,000 元。
  * 训练算力：使用单卡 A100 (80GB) 进行 LoRA 训练数小时，算力租用约 100 元。
  * 研发与调优调试：工程师调优、验证和部署上线约 10 人天，研发成本折合约 20,000 元。
  * 前期固定投入小计：约 28,100 元。
* **持续运营投入**：
  * 输入输出长度：微调内化了示例，单次请求仅需输入 200 Token 用户描述，输出 100 Token。
  * 资源开销：100 万次/月（平均 QPS 约为 0.38，按波峰预留 10 QPS），单张 24GB 显存 GPU（如 A10 或 RTX 4090）配合 vLLM 即可承载，实例月租金约 2,000 元。（注：测算未计入跨机房多副本高可用灾备与专属运维人力；商用 API 包含全托管免运维特性）。
  * 6 个月算力租赁费用：$2,000 \times 6 = 12,000$ 元。
  * **6 个月总成本**：$28,100 + 12,000 = 40,100$ 元。

### 成本对比结论
在调用量较小（如每月几千次验证原型）或业务需求尚未固化的阶段，方案 A（Prompt 优化）具备零前期成本与极高的调整灵活性；但随着业务量突破百万级且输入格式高度固定时，方案 B 通过消除长 Prompt 带来的输入 Token 与 KV Cache 负担，能在数月内收回前期工程与标注投资。

## 混合演进路径：从 Prompt 原型到小模型微调

在实际工程中，团队通常遵循循序渐进的四阶段演进路径，而不是一开始就做非此即彼的决定：

![工程落地演进飞轮：Prompt 原型验证到小模型微调蒸馏](/images/content-rebuild/de66f4bade8ca2e3/fig-4.png)

1. **冷启动与可行性验证（第 1 - 2 周）**：
   * 直接使用大参数商用模型，编写详尽的 Prompt（包含角色定义、推理逻辑与 Few-shot 反例），快速跑通产品原型，验证业务逻辑可行性。
2. **生产日志收集与金标数据沉淀（第 3 - 6 周）**：
   * 系统上线小流量，记录真实用户的 Prompt 输入和模型回复。
   * 建立数据质检机制：将优秀的生成样例标记为正样本，对格式漂移或意图识别错误的案例进行人工修正，清洗沉淀出 1,000 到 3,000 条高质量垂直领域金标数据集。
3. **轻量模型微调与评测（第 7 - 8 周）**：
   * 选择轻量开源模型（如 7B/8B 级别），基于金标数据集执行 SFT 监督微调或偏好对齐，重点学习格式一致性与专业领域推理步骤。
4. **线上灰度降级与精简 Prompt 部署（第 9 周起）**：
   * 剥离冗长的示例内容，将轻量微调模型切入生产，以极短的指令承接线上流量，兼顾系统敏捷性、响应速度与推理成本。更多宏观选型框架可参考 [Prompt、RAG 与微调选型](/fundamentals/training-and-finetuning/prompt-rag-finetuning.md)。

## 高频面试追问解析

![电商频繁变动价格更新的架构对比：微调的滞后幻觉与 RAG 解耦](/images/content-rebuild/de66f4bade8ca2e3/fig-5.png)

### 追问 1：为什么电商每天波动的商品价格不能通过每天微调模型来更新？

**考点分析**：考查对参数知识存储特性的认知与生产环境可行性边界。

**参考回答**：
1. **时效性与计算成本**：微调需要经历数据采样、分词（Tokenization）、反向传播与权重发布，具备明显的时间延迟。电商价格变动秒级生效，不可能对每次改价触发一次训练流水线。
2. **黑盒存储与不可解释性**：神经网络权重通过参数间的连续概率关联存储知识，缺乏关系数据库的精确索引机制。即便微调，也无法保证模型每次回答都稳定输出最新值，当出现价格错误时无法判定是训练未收敛还是注意力偏差，难以做审计与业务对账。
3. **灾难性遗忘与泛化破坏**：对模型高频灌入离散、高密度的实体价格键值对，容易导致模型在前馈网络中产生概率过拟合，甚至破坏原有的通用对话和逻辑推理能力。确定性的高频事实必须由数据库承载，在推理时动态注入 Prompt。

![高并发场景下长 Prompt 引发的 Prefill 延迟与显存瓶颈](/images/content-rebuild/de66f4bade8ca2e3/fig-6.png)

### 追问 2：什么情况下，持续优化 Prompt 会遇到瓶颈，促使团队转向微调？

**考点分析**：考查候选人在生产性能排障与方案重构时的判断标准。

**参考回答**：
当系统遇到以下三类工程瓶颈时，表明 Prompt 优化已达边际收益极限：
1. **首字延迟（TTFT）突破 SLA 限制**：为了确保复杂任务的准确性，Prompt 中加入了长篇业务规则与多个完整示例，导致 Prefill 阶段消耗数百毫秒甚至数秒，无法满足低延迟交互要求。
2. **KV Cache 显存打满限制系统并发**：高并发场景下，长上下文导致的 KV Cache 显存占用直接卡死并发上限，单卡吞吐量极低，扩容服务器成本剧增。
3. **规则冲突与注意力负迁移**：当 Prompt 越来越长，针对边缘 Case 补充的自然语言规则开始出现冲突，出现“修改了一条规则解决场景 A，却导致场景 B 准确率下降”的恶性循环。此时通过微调在特定数据集上建立明确的梯度惩罚，能够更稳定地约束模型行为。

### 追问 3：微调之后是不是就可以完全抛弃 Prompt 了？

**考点分析**：考查微调与推理运行时交互的实际工程细节。

**参考回答**：
并不是。微调消除了冗长的 Few-shot 示例和复杂背景说明，但推理时依然需要基本的指令引导（Zero-shot Prompt）。在模型训练与推理的最佳实践中，推理输入需要与微调时采用的对话模板（Chat Template）保持一致格式；若采用了条件调用序列等特殊适配器设计，还需匹配对应的调用标记。微调后精简的“薄 Prompt”能够以最小的序列开销激活微调权重中的能力，二者是相互配合的工程组合，而非完全对立替换。
