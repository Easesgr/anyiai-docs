在大语言模型开发与提示工程（Prompt Engineering）中，为提示词提供示例（Demonstrations）是最常见的调优手段。根据提示词中包含示范输入输出对的数量，通常分为 **Zero-shot（零样本）**、**One-shot（单样本）** 与 **Few-shot（少样本）**。

在实际生产中，示例并不是“越多越好”。示例会直接增加输入序列长度，推高推理首字延迟（TTFT）与计费成本；如果示例挑选不当，还会诱发分类偏差或格式僵化。本文先给出面试可直接口述的简洁总结，再通过一个贯穿前后的工单分类实例，拆解其背后的计算开销、选型阶梯与常见错误。

## 面试速答：三类 Shot 的定义与口述模板

> **面试口述参考**：
> “三者的核心区别在于提示词中是否包含示范性的输入输出对：
> - **Zero-shot**：只有任务要求和待处理输入，不给任何示例。
> - **One-shot**：在指令后附带 1 个完整的输入与标准输出样例。
> - **Few-shot**：通常附带 2 到 5 个具有代表性的正反示例。
>
> 从底层机制来看，示例并没有改变模型微调权重，而是利用自注意力机制，将后续生成首字及后续内容的概率分布锚定在期望的轨道上。示例主要发挥两层作用：一是**规范输出格式与风格**，二是**厘清模糊的业务规则与决策边界**。
>
> 工程选型遵循‘**默认 Zero-shot，格式漂移用 One-shot，逻辑歧义上 Few-shot，严控延迟与上下文膨胀**’：
> 1. 通用常识、标准摘要和已有良好指令微调支持的任务，首选 Zero-shot，推理首字延迟（TTFT）最低，Token 成本最小。
> 2. 当模型输出字段名不稳定、需要特定风格或特殊文本标记时，1 个典型的 One-shot 即可消除绝大部分格式歧义。
> 3. 遇到业务私有分类标准、易混淆边缘用例时，用 2~5 个正反均衡的 Few-shot 进行边界标定。
> 4. 若在实时低延迟场景下使用 Few-shot，应固定示例前缀，借助服务端的 Prompt Caching（前缀缓存）减少重复计算。”

| 维度 | Zero-shot（零样本） | One-shot（单样本） | Few-shot（少样本，典型 2~5 个） |
| :--- | :--- | :--- | :--- |
| **输入组成** | 系统指令 + 待测输入 | 指令 + 1 个输入输出样例 + 待测输入 | 指令 + N 个输入输出样例 + 待测输入 |
| **核心作用** | 验证模型基础能力与指令遵循 | 快速锁定输出格式、特定 JSON 结构或语气 | 标定模糊业务规则、解歧多分类边界 |
| **首字延迟（TTFT）** | 最短（无额外示例 Token） | 略有增加（增加单次示例 Prefill 计算） | 明显增加（Prefill 计算开销随输入序列长度增加，标准自注意力复杂度呈平方阶） |
| **计费与吞吐** | Token 消耗最少，并发承载力高 | 适度增加输入 Token 成本 | 显著增加输入计费，强依赖前缀缓存复用 |
| **常见工程风险** | 复杂格式易偶发漂移、长尾指令失真 | 容易过度拟合单一输出模板 | 标签分布偏置（Label Bias）、近因偏差（Recency Bias） |

## 一个贯穿例子：工单自动分派任务

为了直观理解这三者的差异，我们以一个电商平台售后工单分类场景贯穿下文：系统需要将用户的自然语言报障分配到 `[系统故障]` 或 `[业务咨询]`，并输出统一的 JSON 格式。

### 1. Zero-shot 形态
只提供任务指令，不提供示范样例：

```text
你是一个售后工单分派员。请分析用户的输入，判断分类是 [系统故障] 还是 [业务咨询]，并以 JSON 格式输出，包含 category 和 reason 两个字段。

用户输入：点击“导出报表”按钮变灰无法点击，没有任何错误提示。
输出：
```
- **特点**：输入极为精炼，没有任何示例开销。
- **可能问题**：模型可能把按钮变灰误判为“系统故障”（前端 Bug），也可能输出 `{"type": "...", "detail": "..."}` 等非预期键名。

### 2. One-shot 形态：锚定格式与字段名
为了防止输出字段名乱跳，加入 1 个格式示范：

```text
你是一个售后工单分派员。请分析用户的输入，判断分类是 [系统故障] 还是 [业务咨询]，并以 JSON 格式输出，包含 category 和 reason 两个字段。

【参考示例】
输入：登录时提示“密码错误超过上限，账号已锁定”。
输出：{
  "category": "业务咨询",
  "reason": "属于安全策略锁定，需引导用户走自助找回密码流程。"
}

【待处理任务】
输入：点击“导出报表”按钮变灰无法点击，没有任何错误提示。
输出：
```
- **特点**：模型通过模式模仿，几乎可以稳定输出 `category` 和 `reason` 这两个字段，不再需要多轮提示调整。

### 3. Few-shot 形态：标定业务决策边界
“按钮变灰”在公司业务规则中通常是因为“用户没有开通对应权限”，属于业务咨询，并非代码异常或后端报错。为了让模型分清边界，提供涵盖正例与反例的 Few-shot：

```text
你是一个售后工单分派员。请分析用户的输入，判断分类是 [系统故障] 还是 [业务咨询]，并以 JSON 格式输出，包含 category 和 reason 两个字段。

【参考示例 1：业务咨询 - 权限与流程】
输入：在员工管理页面点击“批量删除”，按钮呈灰色无法点击，没有报错提示。
输出：{
  "category": "业务咨询",
  "reason": "功能按钮置灰且无报错通常属于未配置操作权限，需引导走权限申请流程。"
}

【参考示例 2：系统故障 - 服务端或接口异常】
输入：在员工管理页面点击“批量删除”后，页面弹出红框报错 500 Internal Server Error。
输出：{
  "category": "系统故障",
  "reason": "服务端明确返回 5xx 状态码，属于接口运行异常，需流转研发排查。"
}

【待处理任务】
输入：点击“导出报表”按钮变灰无法点击，没有任何错误提示。
输出：
```
- **特点**：保持待处理输入与前述 Zero-shot、One-shot 一致。通过正反两组同类业务场景对比，明确了“置灰无报错属于权限咨询”与“明确返回 5xx 属于系统故障”的决策边界，辅助模型在相同待测输入上做出符合私有业务规则的准确判定，同时避免将测试用例直接泄露到示范样例中。

## 示例生效的两种机制：格式对齐 vs 规则解歧

在大模型自回归生成过程中，输出是以输入序列为条件计算下一个 Token 的概率分布。提示词中追加示例，本质上是丰富了自注意力机制在生成初始 Token 时的上下文信息。

![示例对模型输出概率分布的锚定机制](/images/content-rebuild/15b918278e9c803a/fig-1.png)

在工程实践中，示例带来的收益分为两个完全不同的层次：

### 1. 表面格式与风格对齐
自然语言描述存在理解偏差。例如要求“给出精炼诊断结论”，不同模型的理解从单字到两百字不等。加入 1 个完整的示范（One-shot），模型在自注意力计算中会参照上文的格式框架，大幅提升预期语法结构对应 Token 的生成概率。

对于纯粹的格式统一（如 JSON 键名、输出语调、每行一条的分隔符），**通常 1 个最具代表性的示例就足够了**。此时增加到 5 个示例，格式收益基本不再增加，反而浪费计算资源。

### 2. 任务规则与分类边界解歧
当业务逻辑属于公司私有规则、行业术语或者存在重叠边界时，纯指令很难将所有边界条件阐明。通过 2 至 5 个正反交替的示例，上下文中的对比特征能够引导自注意力头聚焦于关键判定词（如错误码、置灰状态等）。

关于大模型在多层注意力结构中如何依据上下文进行模式匹配与归纳推理，可参考 [什么是 Few-shot Learning？Zero-shot、One-shot、Few-shot 有什么区别？](/interview/prompt-interview/few-shot-learning.md)。

## 系统性能与开销权衡：TTFT、KV Cache 与计费

提示词工程的改动直接对应后端基础设施的计算量。大模型推理通常分为两个阶段：
1. **Prefill（预填充）阶段**：推理引擎将输入的全部提示词 Token 并行计算自注意力，生成对应的 Key/Value 向量并写入显存（KV Cache），输出首个 Token。该阶段耗时直接决定了**首字延迟（Time to First Token, TTFT）**。
2. **Decode（逐字解码）阶段**：在已缓存的 KV 向量基础上，串行生成后续 Token，决定系统吞吐速率（Tokens/s）。

![示例数量对Prefill计算量与TTFT延迟影响的权衡算例](/images/content-rebuild/15b918278e9c803a/fig-2.png)

### 延迟与成本对比算例
假设一个工单分类服务，平均每次待测用户输入为 100 Tokens，系统任务指令为 200 Tokens，每个标准示例为 150 Tokens。我们对比不同策略的系统开销（注：以下为单次请求 Token 规模与理论计算趋势示意，实际物理延迟受服务器排队、并发 Batch 及显卡架构影响）：

| 指标 | Zero-shot | One-shot (1-shot) | Few-shot (5-shot) |
| :--- | :--- | :--- | :--- |
| **单次输入 Token 总数** | $200 + 100 = 300$ | $200 + 150 + 100 = 450$ | $200 + (150 \times 5) + 100 = 1050$ |
| **输入规模相对倍数** | $1.0\times$（基准） | $1.5\times$ | $3.5\times$ |
| **输入端 KV Cache 显存占用** | 基准水平 | 增加约 $50\%$ 显存（与输入 Token 数正比） | 增加约 $250\%$ 显存（与输入 Token 数正比） |
| **每天 10 万次调用的输入计费** | 3000 万 Tokens | 4500 万 Tokens | 1 亿 500 万 Tokens |
| **无缓存时的首字延迟（TTFT）** | 最优 | 略微上升 | 显著拉长，在线交互易有停顿感 |

### Prompt Caching（前缀缓存）的关键作用
现代推理框架（如 vLLM 的 Prefix Caching）及商业 API（如 Claude Prompt Caching、OpenAI Prompt Caching）支持前缀缓存技术：
- **静态共享示例**：如果将 Few-shot 示例固定在系统提示词开头，并且后续请求共享完全相同的前缀，推理引擎可以直接读取显存中已计算好的 KV Cache，省去重复的 Prefill 计算。此时 Few-shot 的首字延迟可大幅下降，且服务商通常对命中缓存的 Token 提供折扣。
- **动态检索示例（如 RAG 动态注入 Few-shot）**：如果每个请求根据用户输入临时从向量库召回 3~5 个不同示例，由于每个请求前缀都不相同，**前缀缓存将完全失效**。在高并发在线场景下，动态 Few-shot 会使显存带宽与算力迅速吃紧，成为系统扩容瓶颈。

## 渐进选型决策流

提示词优化应遵循渐进迭代原则，避免起手就拼接大量示例。在设计提示词前，建议先阅读 [Prompt 中如何设计角色、任务、约束、输出格式和示例？](/interview/prompt-interview/prompt-design.md)。

![提示策略工程选型阶梯决策树](/images/content-rebuild/15b918278e9c803a/fig-3.png)

### 阶段 1：首选 Zero-shot 验证任务基线
对于标准文本摘要、通用语言翻译、提取显式实体、常见代码补全等通用任务，当前主流大模型本身已有充足的先验知识，应优先使用清晰的 Zero-shot。

### 阶段 2：输出格式不稳定时，优先考虑替代技术
如果遇到格式偶尔漂移、漏字段或输出带闲聊废话，**先不要急着堆砌示例**，优先评估以下方式：
1. **受控解码（Structured Outputs / JSON Schema）**：在 API 或推理引擎层配置固定的 JSON 校验结构。解码器在每一步会屏蔽不合法的 Token，在解码阶段保证语法符合 Schema。详见 [结构化输出 Prompt 应该怎么写？](/interview/prompt-interview/structured-output.md)。
2. **回复预填充（Assistant Prefill）**：在支持的 API 中，预先在模型回复起点填入 `{"category":`，引导模型顺着 JSON 语法输出。
3. **1 个标准的 One-shot**：若需要输出非标准的自定义分隔符文本（如 `ID:::STATUS`），补充 1 个标准 One-shot 即可稳定。

### 阶段 3：规则逻辑有歧义时，引入 2~5 个 Few-shot
只有当遇到以下本质性业务障碍时，才必须使用 Few-shot：
1. **私有映射规则**：公开语料中不存在的特定错误码或业务状态映射。
2. **边缘分类混淆**：规则叙述难以覆盖两可之间的模糊情形，需要正例、反例对照定界。
3. **特定专业领域的推理风格**：如特定合规审查、医疗或法律判例分析范式。

## 工程陷阱：Few-shot 的常见失效与排查

引入 Few-shot 并不保证准确率必然上升。在评测中，多示例提示词常见以下三类问题：

![Few-shot工程偏差与排错机制](/images/content-rebuild/15b918278e9c803a/fig-4.png)

### 1. 标签分布偏置（Label Bias）
模型对示例中的类别比例很敏感。如果在 4 个示例中，有 3 个是“业务咨询”，仅 1 个是“系统故障”，模型倾向于提高“业务咨询”的预测倾向，导致真故障被漏判。
- **防御手段**：Few-shot 示例的类别比例必须**严格保持平衡**。二分类任务应正反各半，多分类任务各类示例数量尽量均等。

### 2. 近因偏差（Recency Bias）
注意力计算往往对位置靠近待测输入的上下文赋予更高的关联权重。模型容易无意识地模仿最后一个示例的结构、长度乃至输出标签。
- **防御手段**：测试时打乱示例顺序，评估模型输出的稳定性。若改变示例顺序导致分类大幅波动，说明存在近因偏置。

### 3. 表面模仿与伪逻辑（Surface Mimicry）
模型完整输出了规范的 JSON 键值，但内容为空洞套话。这是因为示例过强地锚定了格式注意力，削弱了对待测文本具体内容的深入分析。
- **防御手段**：在示例中引入思维链（Chain-of-Thought, CoT），示例不仅给出输入和标签，还示范简明推理步骤。详见 [Chain-of-Thought 是什么？](/interview/prompt-interview/chain-of-thought.md)。

```python
# 验证示例排列顺序对模型稳定性影响的测试伪代码
import itertools

def evaluate_prompt_order_sensitivity(test_cases, demonstrations, call_llm):
    """
    测试不同示例排列顺序下，模型预测结果的一致性
    """
    demo_orders = list(itertools.permutations(demonstrations))
    inconsistent_cases = 0
    
    for case in test_cases:
        predictions = []
        for order in demo_orders:
            prompt = build_prompt(demos=order, user_input=case["input"])
            response = call_llm(prompt)
            predictions.append(parse_category(response))
        
        # 若调换示例顺序导致预测类别不唯一，记录为不稳定样本
        if len(set(predictions)) > 1:
            inconsistent_cases += 1
            
    instability_rate = inconsistent_cases / len(test_cases)
    print(f"示例顺序敏感度（抖动率）: {instability_rate:.2%}")
    return instability_rate
```

## 面试追问与攻防推演

![面试追问推演与攻防示意图](/images/content-rebuild/15b918278e9c803a/fig-5.png)

### 追问 1：在低延迟实时交互（如语音助手、实时补全）场景中，加 5-shot 会带来什么影响？该如何优化？
- **回答要点**：
  1. **首字延迟拉长**：输入 Token 数量成倍增加，直接放大服务端的 Prefill 计算时间，用户等待首字的时间变长；
  2. **并发容量下降**：每个并发请求占用的 KV Cache 显存增加，导致单张 GPU 能同时承载的请求数（Batch Size）降低，易引发排队；
  3. **工程优化路径**：避免动态检索式 Few-shot。若必须使用，应将示例沉淀为**静态系统前缀**以充分命中前缀缓存（Prompt Caching）；若延迟要求达到极致（如百毫秒级），应通过监督微调（SFT）将格式与规则直接注入模型权重中，在线调用完全切回 Zero-shot。关于微调与 Prompt 的权衡，可参考 [微调与 Prompt 怎么选？有什么区别？](/interview/prompt-interview/prompt-vs-finetuning.md)。

### 追问 2：如果在 Zero-shot 下输出格式不稳定，除了加示例，还有哪些更轻量的工程解法？
- **回答要点**：
  1. **结构化标记划分**：使用清晰的 XML 标签（如 `<instructions>`、`<context>`、`<format>`）组织输入，减少自然语言叙述歧义；
  2. **受控解码约束**：配置 JSON Schema 约束，利用底层推理引擎进行语法引导生成，无需消耗上下文 Token 即可确保输出符合语法规范；
  3. **输出预填（Prefill）**：在请求的 Assistant 角色开头预填起始字符（如 `{`），锁定生成轨道；
  4. **两阶段流水线**：一阶段专注无格式约束的自由语义推导，二阶段通过轻量正则或极小模型转换格式。

### 追问 3：为什么有时在提示词中增加了示例，模型的准确率反而下降了？
- **回答误区**：“因为示例占满了上下文窗口，模型注意力不够用导致遗忘。”（现代模型窗口通常很大，三五个示例通常只占数百 Token，远未达到窗口上限）。
- **合理原因分析**：
  1. **样本类别失衡（Label Bias）**：示例中某类标签过多，破坏了模型原有的先验平衡；
  2. **示例引入误导性噪声**：示例可能涵盖了过于特殊的个案，或人工标注存在错误，干扰了模型的正常推理；
  3. **注意力稀释与模板固化**：示例过长或包含过多无关背景，分散了模型对待测输入的注意力，导致模型直接套用示例模版而忽略待测输入的独特细节。
