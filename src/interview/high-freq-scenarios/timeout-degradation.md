在生产环境中调用大语言模型（LLM）与传统微服务有很大不同。传统微服务调用的耗时通常在几十毫秒到几百毫秒之间，而大模型推理受到提示词预填充（Prefill）计算量、自回归解码（Decode）序列长度、GPU 显存并发上限以及服务商排队队列的影响，端到端耗时常常在数秒到数十秒之间波动。

面对这种高延迟和剧烈抖动，如果网关依然采用传统的“固定超时加直接报错”策略，系统不仅会频繁超时，还会因为盲目重试导致 GPU 算力挤兑。本文以一个典型的“智能客服知识库问答”为贯穿案例，从面试口述答案出发，详解细粒度超时预算、复合断路器、阶梯降级以及流式断流的落地做法。

## 面试标准口述：四步防御体系

当面试官提问“大模型接口变慢或超时，系统应该如何降级”时，切忌直接罗列零散的重试参数，建议按“预算分段、复合熔断、阶梯降级、断流清理”四个层次进行口述：

> **面试口述参考**：  
> “大模型服务出现延迟或超时，不能沿用传统 RPC 的统一超时逻辑，应建立全链路的分级防护：  
> 1. **分段超时预算**：将统一超时拆解为建连耗时、首字耗时（TTFT）与字间间隔（ITL）。防止请求长时间卡在推理排队阶段，霸占网关连接。  
> 2. **复合断路器**：大模型的故障常表现为‘HTTP 200 已返回，但排队极长或吐字卡死’。断路器不能只看 5xx 状态码，必须把 TTFT 的 P95 延迟和字间停顿率纳入跳闸判定，指标恶化时及时换路到备用模型。  
> 3. **阶梯降级策略**：按任务容忍度逐级回退——高频问题优先命中语义缓存；主模型异常时切换到小参数模型；在 RAG 场景下，超时直接展示前置检索已召回的资料原文，跳过慢速生成；重型任务转入异步后台任务。  
> 4. **断流补偿与算力释放**：对于已经发出 HTTP 200 的流式响应（SSE），网关需通过协议级错误事件帧通知前端优雅结束；同时在前端取消或超时断开时，网关必须向上游推理集群发送 Abort 信号，及时释放 GPU 上的 KV Cache 资源。”

## 细粒度超时预算：打破单一体积超时

传统 HTTP 客户端习惯配置一个全局的 `timeout = 30s`。在大模型推理场景下，这种设置存在两个常见问题：
1. **首字饥饿**：如果模型因为推理集群排队或 Prefill 阶段超载，等了 28 秒才吐出第一个字，剩下 2 秒根本无法完成后续几十个词的解码生成，白白浪费了 30 秒的连接等待。
2. **静默挂死**：如果在流式输出第 20 个字后，后端解码线程卡死或网络静默中断，客户端只能干等满 30 秒才会抛出异常，前端用户会面对长达数十秒的无响应冻结。

### 耗时拆解与计时器设计

调用大模型时，应将单次调用划分为三个独立的计时阶段：

* **建连超时（Connect Timeout）**：通常设置为 $1 \sim 3\text{ 秒}$。仅检测 TCP 握手与 TLS 协商，若超时说明网络路由断开或服务网关宕机。
* **首字耗时（TTFT, Time to First Token）**：指从请求完整发送到接收到第一个数据块（Chunk）的时间。该指标直接反映了推理集群的排队深度与 Prefill 算力负荷。在在线交互中，通常建议设在 $3 \sim 5\text{ 秒}$。
* **字间延迟（ITL, Inter-Token Latency）**：流式输出中相邻两个 Chunk 之间的时间间隔。该指标反映单步自回归解码（Decode）的执行情况，通常设定为 $1 \sim 2\text{ 秒}$。一旦超过该阈值，即可认定为上游解码挂起或网络失联。

```python
# 示例：流式调用的细粒度超时控制（TTFT 与 ITL 双重预算）
import asyncio
import httpx

async def stream_with_budget(client: httpx.AsyncClient, request_payload: dict):
    ttft_budget = 3.0       # 首字预算 3.0 秒（覆盖排队与 Prefill 计算）
    chunk_budget = 1.0      # 字间间隔预算 1.0 秒（监控 Decode 阶段）
    
    # 1. 建立流式连接：read 必须配置首字预算，防止上游在排队返回响应头阶段无限挂起
    async with client.stream(
        "POST", 
        "/v1/chat/completions", 
        json=request_payload, 
        timeout=httpx.Timeout(connect=2.0, read=ttft_budget, write=5.0, pool=5.0)
    ) as response:
        if response.status_code != 200:
            raise RuntimeError(f"上游服务返回异常状态码: {response.status_code}")
            
        stream_iter = response.aiter_bytes().__aiter__()
        first_token = True
        
        while True:
            # 动态选择当前阶段的超时预算（首字到达后切换为字间间隔预算）
            current_budget = ttft_budget if first_token else chunk_budget
            try:
                # 使用 wait_for 挂载异步超时，防止 socket 读操作在底层无限制阻塞
                chunk = await asyncio.wait_for(stream_iter.__anext__(), timeout=current_budget)
            except (asyncio.TimeoutError, httpx.ReadTimeout):
                if first_token:
                    raise TimeoutError(f"首字生成超时（>{ttft_budget}s），上游排队过深或Prefill过载")
                else:
                    raise TimeoutError(f"流式字间间隔超时（>{chunk_budget}s），模型解码停滞")
            except StopAsyncIteration:
                # 数据流正常结束
                break
            
            first_token = False
            yield chunk
```

## 复合熔断机制：为什么不能只看 HTTP 状态码

当某个模型供应商的推理集群过载时，报错率可能并不高，而是表现为排队时间从 800 毫秒飙升到 20 秒以上。所有请求堆积在业务网关的连接池中，最终耗尽文件描述符和内存。

![大模型断路器状态机与双重健康探测机制](/images/content-rebuild/b45a88ffb1b2bf59/fig-2.png)

### 典型失效模式与指标设计

传统断路器通常依赖 HTTP 5xx 或 429 比例进行统计。但大模型服务的典型失效特征是：**网关早已返回 HTTP 200 并成功建立了 SSE 流式连接，但首字延迟极长，或者吐出几个字符后长时间无响应**。如果只看状态码，断路器会误判服务正常，继续把流量灌入过载节点。

专用于大模型的断路器需要引入结合延迟与停滞率的复合判定公式：

$$\text{Trip} = (P_{95}(\text{TTFT}) > \tau_{\text{ttft}}) \lor (\text{Rate}_{5xx+429} > \tau_{\text{err}}) \lor (\text{Rate}_{\text{stall}} > \tau_{\text{stall}})$$

* **关闭状态（Closed）**：流量正常通行。在滑动窗口（如最近 100 次请求）内统计 TTFT 的 P95 延迟、首字超时率、字间中断率与 HTTP 错误码。
* **打开状态（Open）**：当滑动窗口内 TTFT 超标或中断率突破阈值（例如首字超时率超过 20%），断路器跳闸。新进入的请求直接切换至备用路由（如备用供应商、小参数模型或降级方案），保护主集群降压。
* **半开状态（Half-Open）**：冷却时间（如 15 秒）结束后进入半开状态。网关放行极少量真实流量（如 5%），或发起指定输入和长度的探测请求（Synthetic Probes）。当连续数次探测的 TTFT 与字间生成均恢复正常，断路器才切回关闭状态。

## 四级阶梯降级：维持业务可用

降级的目标是当主力模型出现性能瓶颈时，以较低的保真度或更确定的方式，保证核心业务流程不中断。

![四级阶梯降级策略漏斗与对应开销](/images/content-rebuild/b45a88ffb1b2bf59/fig-3.png)

以智能客服问答场景为例，系统可以设计四层降级机制：

### 一级降级：语义缓存（Semantic Cache）
在请求到达大模型之前，先与向量缓存库比对。若用户提问与库中已有高频问答的相似度高于设定阈值（如余弦相似度 $>0.96$），直接提取既有回答返回。该策略适用于低时效性、无私有数据隔离要求的高频公共 FAQ；在接口过载或熔断时，亦可通过临时启用缓存或微调阈值快速拦截流量。缓存查询耗时通常在数十毫秒以内，既能屏蔽上游推理服务的不稳定，也能在突发流量下减轻算力负荷。

### 二级降级：模型降级（Model Downgrade）
从高阶推理模型（如 70B 参数大模型）无缝切换至备用轻量模型（如 8B 参数模型或端侧轻量模型）。
* **适用场景**：意图分类、总结摘要、标准信息抽取。
* **注意事项**：轻量模型对复杂指令的遵循能力较弱。网关在切换时，需要配合使用结构化输出约束（如 JSON Schema 校验）或更具约束力的 Few-Shot 提示词，避免格式混乱。

### 三级降级：复用检索切片原文（Direct Snippet Fallback）
在检索增强生成（RAG）系统中，如果模型在最终整理答案时变慢或超时，**切忌在捕获异常后再去发起一次耗时的向量检索**。正确做法是**直接复用在生成前就已经召回并缓存好的 Top-K 知识切片原文**。系统直接将高相关度段落组装成参考资料卡片展示给用户，并提示：“AI 助手繁忙，已直接为您调取相关参考资料”，用确定性的检索结果替代不确定的慢速生成。

### 四级降级：异步任务排队（Async Handover）
对于报表整理、长文分析、代码审查等计算量较大的任务，前端不再同步等待流式结果。网关在识别到过载或超时后，返回生成的任务 ID，提示用户“任务已转入后台处理”。请求放入消息队列中，由后台工作线程以较低的并发速度拉取执行，并在完成后通过站内信或消息推送通知用户。

## 流式响应中的断流补偿与前端约定

在 Server-Sent Events (SSE) 场景下，降级面临一个协议层限制：**网关通常在接收到上游响应头时，就已经向前端发送了 `HTTP 200 OK` 和 `Content-Type: text/event-stream`**。若随后推理集群超时断开，网关无法再通过修改 HTTP 状态码来报告失败。

![SSE流式输出中断与优雅截断补齐时序图](/images/content-rebuild/b45a88ffb1b2bf59/fig-4.png)

### 协议级显式错误帧

网关必须与前端建立统一的流式帧规范，避免直接掐断 TCP 连接导致前端页面停在“半截话”而没有任何反馈。

```text
// 正常文本数据帧
data: {"type": "chunk", "delta": "退换货政策规定，自签收之日起"}

// 心跳保活帧（防止中间反向代理如 Nginx 超时关闭连接）
: keep-alive

// 发生异常时推送的结构化错误帧
event: error
data: {"code": "upstream_timeout", "message": "[系统检测到响应超时，已为您保留当前生成内容]", "can_retry": true}
```

### 客户端处理与补偿策略

1. **心跳保活**：在模型等待排队或 Prefill 阶段，网关定时（如每秒）向下游发送 SSE 注释行（`: ping

`），防止反向代理的 `proxy_read_timeout` 误判为链路断开。
2. **断点保留与操作引导**：前端收到 `event: error` 后，保留当前已经打字渲染出来的文本，并在文字末尾以弱提示形式标明中断原因，同时展示“继续生成”或“转人工客服”按钮。

## 并发反压：为什么必须按连接数限流

模型接口变慢往往是突发并发打满 GPU 显存引发的。GPU 显存中能容纳的 KV Cache 槽位数决定了能同时处理的请求上限。

![基于并发槽位感知的分级限流与反压架构](/images/content-rebuild/b45a88ffb1b2bf59/fig-5.png)

传统 Web 系统常根据 QPS（每秒请求数）配置限流。但在大模型网关中，**基于活跃并发连接数的控制比单一 QPS 更加关键**。  
假设每个请求平均生成耗时 15 秒，即使限制 QPS 为 10，10 秒内涌入的 100 个请求将全部驻留在内存与 GPU 显存中。如果显存最大只能承载 30 个并发生成的 KV Cache，剩余 70 个请求就会在底层排队，拖垮所有请求的 TTFT。

网关的防护做法是维护全局并发连接槽位：
* **软限制与排队**：当并发数达到设定阈值时，触发反压，将新进入的请求按优先级放入有限容量的等待队列中；
* **快速失败（Fail-Fast）**：当预计排队等待时间超过设定的首字预算（TTFT Budget）时，直接拒绝新请求并返回 429 或触发降级方案，阻止无效请求继续堆积。

## 资源回收：防止客户端取消引发算力泄漏

在大模型系统中，经常出现**孤儿请求（Orphan Requests）**导致的算力泄漏：当用户在界面上点击“停止生成”，或者客户端因网络中断关闭了页面，如果网关没有把取消动作传递到上游，推理集群仍会持续执行解码，计算完剩下的数百个 Token。

![客户端连接断开时向推理引擎传播中断信号的时序图](/images/content-rebuild/b45a88ffb1b2bf59/fig-6.png)

### 中断信号的下发机制

业务网关必须监听客户端的连接状态（例如在 Python 中检查 `request.is_disconnected()`，在 Go 中监听 `r.Context().Done()`）：
1. 一旦捕获到客户端主动断开，网关立即中断向上游推理服务的请求流；
2. 对于私有化部署的推理服务（如 vLLM、TGI、TensorRT-LLM），调用其取消接口或关闭流连接，提示引擎立即注销对应的推理任务，释放显存中占用的 KV Cache 显存块。

及时回收算力，能避免无效计算抢占资源，防止系统延迟进一步恶化。

## 面试高频追问与应对

### 追问 1：大模型调用超时后，客户端能否直接原地自动重试？
**风险回答**：“超时了就在客户端配置重试 3 次，保证请求最终成功。”  
**采分点回答**：大模型调用消耗的算力很大，盲目重试会引发重试风暴，加速集群崩溃。正确的重试原则是：  
1. **首字吐出后不重试**：如果模型已经输出了部分 Token，严禁整段重新发起请求，应走流式断流处理；  
2. **重试需换路**：仅在建连失败或明确收到 429/503 时重试，且重试时必须采用带随机抖动的指数退避（Exponential Backoff with Jitter），并优先切换到备用服务商节点，避免对原过载实例重复施压。

### 追问 2：在多 Agent 协作链路中，中间某一个 Agent 超时怎么处理？
**采分点回答**：在多 Agent 工作流中，必须采用**全局编排超时预算**与**执行状态检查点机制**（可参考 [Agent 调用工具失败与循环处理](/interview/high-freq-scenarios/agent-failure.md)）。不能让链路上的第一个 Agent 耗尽全局时间。工作流引擎在每个 Agent 步骤完成后保存状态；当某个下游 Agent 超时时，可以根据业务属性采用预设默认值代替、跳过该辅助步骤，或触发人工确认机制，避免整个工作流从头重跑。

### 追问 3：从大模型降级到小模型后，输出格式损坏怎么办？
**采分点回答**：小参数模型对于纯自然语言的 Prompt 结构约束理解能力较弱。在实施降级时，网关不仅要替换模型名称，还要同步切换为针对该小模型适配的提示词模板（如增加明确的 Few-Shot 输入输出示例）；在推理服务侧，开启受限解码（Guided Decoding / JSON Schema 语法树掩码），从词表采样阶段直接过滤非法符号，确保返回合规的 JSON 结构。

## 常见认知误区

* **误区一：大模型接口超时后，在异常处理里重新执行一次向量检索**。在模型接口已经超时的场景下，若在异常捕获逻辑中重新发起向量计算与数据库查询，会引入新的 I/O 开销与不可控延迟。正确的做法是就地复用：直接展示进入模型前就已经召回并缓存在上下文中的知识切片。
* **误区二：只要配置了熔断器就高枕无忧**。如果不监控 TTFT 首字耗时和字间中断率，单纯监控 HTTP 状态码，当模型因显存满载在排队队列中长时间等待时，因流式连接已建立，HTTP 状态码仍为 200，传统断路器完全不会跳闸。
* **误区三：降级直接等同于“抛出友好的错误信息”**。降级的核心是维持可用性。应尽可能优先尝试语义缓存、备用轻量模型或参考资料卡片，只有在完全没有可用替代方案时，才回退到提示话术或异步任务。
