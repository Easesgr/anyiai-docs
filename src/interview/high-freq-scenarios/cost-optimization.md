大模型应用的计费主要由输入 Token 数量、输出 Token 数量以及所选模型的单价共同决定。在业务规模扩张阶段，如果所有请求都直接调用高规格的旗舰大模型，账单会随调用量线性甚至超线性上升。降本的核心不是简单地删减提示词，而是在请求接入、上下文组织、模型调度以及云厂商计费机制四个环节综合优化。

以一个典型的企业智能助手为例：员工每天会提交数万次查询，内容涵盖“公积金缴纳比例”等固定制度问答、“帮我润色这段周报”等日常文本处理，以及“排查分布式锁死锁日志”等复杂技术分析。如果每类问题都直接发送给旗舰模型，就会产生大量不必要的开销。

![成本优化三维框架封面图](/images/content-rebuild/1d2bd75b4fbdf063/cover.png)

## 面试口述标准回答

在面试中被问及“如何降低大模型调用的 API 成本”时，建议分层口述：

> **口述模板**：
> “降低大模型 API 成本可以围绕计费公式展开。单次调用的费用等于‘输入 Token 数 × 输入单价 + 输出 Token 数 × 输出单价’，工程落地通常分为四个步骤：
> 
> 1. **少调请求（接入层缓存）**：建立精确哈希缓存与向量语义缓存。完全相同的重复提问由哈希缓存直接返回；高频的标准制度问答由语义缓存拦截，避免调用模型。
> 2. **少发输入与输出（上下文瘦身）**：在输入端，通过多轮对话滑动窗口、提炼历史状态摘要，以及 RAG 阶段用 Rerank 截断多余文档块来缩短输入；在输出端，通过严格约束返回格式与设置 `max_tokens`，减少高单价的输出 Token。
> 3. **用便宜模型（梯级路由）**：在网关层部署轻量分类规则或微调的小模型，将日常闲聊、信息提取等简单任务分流给低成本轻量模型，仅把复杂代码排查和多步推理交给旗舰模型。
> 4. **吃透计费特性（厂商机制）**：静态长文本严格前置以命中供应商的 Prompt Caching（前缀缓存），离线非实时任务接入厂商提供的 Batch API 批量接口，通过异步排队换取费率折扣（具体折扣与交付时限以各厂商公布为准）。”

## 成本拆解：计费杠杆与硬件执行瓶颈

大模型商用 API 的标准计费公式如下：

$$\text{Cost} = N_{\text{in}} \times P_{\text{in}} + N_{\text{out}} \times P_{\text{out}}$$

其中 $N_{\text{in}}$ 为输入 Token 数量，$P_{\text{in}}$ 为输入单价；$N_{\text{out}}$ 为输出 Token 数量，$P_{\text{out}}$ 为输出单价。在各大厂商的定价表中，输出单价 $P_{\text{out}}$ 通常是输入单价 $P_{\text{in}}$ 的 3 到 5 倍。

![大模型调用成本构成与计费杠杆分解图](/images/content-rebuild/1d2bd75b4fbdf063/fig-1.png)

这种价格差异既包含云厂商的商业定价策略，也与底层推理执行特征密切相关：
1. **Prefill（预填充）阶段**：处理输入 Prompt 时，通常可以一次性将所有 Token 输入矩阵并行计算，更容易充分利用硬件的张量计算单元，多数场景下更偏向计算密集（Compute-bound）。
2. **Decode（解码）阶段**：自回归生成输出文本时必须逐 Token 串行生成。在单请求或较小并发批量下，每生成一个 Token 都要反复加载权重与对应的 KV Cache，极易受显存带宽限制（Memory bandwidth-bound），硬件算力利用率相对偏低。

需要注意，实际执行瓶颈还受并发批量（Batch Size）、序列长度和部署硬件影响，API 定价终由供应商官方公布，但这一硬件特征为厂商拉大输入与输出单价差距提供了底层物理依据。

因此，**压制生成长度（$N_{\text{out}}$）的单位经济收益明显高于压缩输入**。在 Prompt 中通过 JSON Schema 限制字段、明确要求“只给出答案，不写多余客套话”，能显著遏制高单价 Token 的产生。

## 接入层拦截：精确匹配与语义缓存

降低总成本最彻底的方法是减少到达大模型的请求数量。网关层通常设计两级缓存：

![精确匹配缓存与语义缓存分层过滤流程图](/images/content-rebuild/1d2bd75b4fbdf063/fig-2.png)

### 1. 精确哈希缓存（Exact Match Cache）
- **工作机制**：将用户请求的完整要素（包含 System Prompt、对话上下文、用户问题、模型名称以及 Temperature 等超参数）进行标准化序列化后，计算 SHA-256 哈希值，直接在 Redis 中查询是否有已缓存的答案。
- **适用条件**：温度参数为 0 或接近 0 的确定性任务（如结构化抽取、标准问答）。
- **优势与局限**：精确匹配相同请求要素，查询耗时仅几毫秒，不消耗额外模型算力；但只要输入多打一个标点或空格就会未命中。同时哈希相等不等于业务答案绝对正确，仍需结合数据时效（TTL）、模型版本、工具状态更新与权限范围做失效管理。

### 2. 向量语义缓存（Semantic Cache）
- **工作机制**：使用轻量 Embedding 模型将用户的 Query 转为向量，在向量数据库中与历史已被采纳的标准问答进行余弦相似度比对。若相似度超过预设阈值 $\tau$（如 0.95），则直接返回历史答案。
- **边界与风险**：
  - **语义漂移与张冠李戴**：若阈值设置过于宽松（例如降至 0.85），“公司年假有多少天？”与“婚假有多少天？”可能被混淆，导致系统返回错误信息。
  - **租户与权限隔离**：语义缓存不能做全租户无差别共享。涉及用户私有数据或特定权限的查询，必须把用户角色或租户 ID 编码进缓存键，防止越权数据泄露。
  - **额外开销**：生成 Embedding 和向量比对同样消耗计算资源与时间。只有当向量比对的成本与延迟明显低于大模型时，该方案才有收益。

## 模型层梯级路由：分流简单任务

并非所有请求都需要旗舰级大模型。通过模型路由器（Router）进行分流，是拉低单次请求平均成本（Blended Cost）的核心手段。

![轻量模型意图分类与复杂大模型梯级路由架构图](/images/content-rebuild/1d2bd75b4fbdf063/fig-3.png)

### 常见路由策略
1. **规则路由**：根据请求特征直接判断。例如：输入长度小于 30 字且不带复杂指令的日常问候，直接走微型模型；需要复杂代码解释的，分流给旗舰模型。
2. **轻量分类器路由**：在网关处部署一个极小参数的模型（如几千万参数的分类器或小语言模型），将输入意图划分为：信息提取、文本润色、常识问答、复杂代码与推理。简单任务走低成本模型，复杂任务升级给旗舰模型。
3. **级联尝试（Cascade Routing）**：先尝试由低成本轻量模型回答，通过轻量验证规则（如输出格式是否合规、置信度是否达标）进行判断。若未通过，再提升至大模型重新生成。需要注意：如果轻量模型失败率过高，反而会导致“小模型开销 + 大模型开销”的双重费用以及响应延迟增加（超时与降级处理可参考 [/interview/high-freq-scenarios/timeout-degradation.md](/interview/high-freq-scenarios/timeout-degradation.md)）。

### 示意算例与收益推演
假设某系统日均处理 100,000 次请求，平均每单输入 1,000 Token，输出 500 Token。设定两档公开 API 参考价格（推演示意）：
- 旗舰大模型：输入 15 元/百万 Token，输出 60 元/百万 Token。
- 轻量小模型：输入 1 元/百万 Token，输出 2 元/百万 Token。

**基准方案（全量直连旗舰模型）**：
$$\text{单次成本} = 1,000 \times 1.5 \times 10^{-5} + 500 \times 6.0 \times 10^{-5} = 0.015 + 0.030 = 0.045 \text{ 元}$$
$$\text{日总成本} = 100,000 \times 0.045 = 4,500 \text{ 元/天}$$

**梯级路由方案**：
假设轻量意图分类器部署在本地或单次分类开销极低（忽略不计），且分流准确率满足预期，无级联重试；75% 的简单任务分流给轻量模型，25% 的复杂任务交由旗舰模型：
- 轻量模型部分（75,000 次）：
  $$75,000 \times (1,000 \times 1.0 \times 10^{-6} + 500 \times 2.0 \times 10^{-6}) = 75,000 \times 0.002 = 150 \text{ 元}$$
- 旗舰模型部分（25,000 次）：
  $$25,000 \times 0.045 = 1,125 \text{ 元}$$
- **混合日成本**：$150 + 1,125 = 1,275 \text{ 元/天}$（在上述理想假设下，较全量方案降低约 71.6%）。

## 上下文瘦身：精简、滑动与切片摘要

输入上下文的隐性膨胀是账单激增的常见诱因。在多轮对话中，如果未经处理直接把历史消息全量拼接，输入 Token 会呈二次方增长。

![多轮对话上下文滑动窗口与提取式摘要压缩机制图](/images/content-rebuild/1d2bd75b4fbdf063/fig-4.png)

### 1. 提示词剪枝（Prompt Pruning）
- **清理空泛修饰**：去除 System Prompt 中无实质约束作用的冗余客套话，改用紧凑的 Markdown 列表或 YAML 结构明确边界规则。
- **动态注入 Few-Shot**：不要硬编码数十个 Few-Shot 示例到系统提示词中。平时保持零示例（Zero-Shot），仅在检测到特定边缘边界或通过向量检索发现当前问题与特定疑难案例高度相似时，才动态插入 1~2 个针对性示例。

### 2. 对话历史压缩
- **滑动窗口（Sliding Window）**：只保留最近 $K$ 轮（如最近 3~4 轮）完整的用户与模型对话。超出窗口的早期原始对话直接移出输入。
- **提取式状态摘要**：对于必须记住长期状态的场景，周期性调用低成本小模型，将滑动窗口之外的历史信息压缩为简短的事实列表（例如：“用户身份：财务；正在处理：4月份发票；当前诉求：报销流程”），作为上下文前置输入，替代原本数千 Token 的原始对话流。

### 3. RAG 召回链路截断
在检索增强生成场景中，召回环节往往为了防止漏检而从向量库拉取数十个文档切片。如果把 Top-20 全部塞进 Prompt，既增加 Token 消耗，又容易让模型在冗长材料中产生事实偏差（参考 [/interview/high-freq-scenarios/rag-answer-wrong.md](/interview/high-freq-scenarios/rag-answer-wrong.md)）。

标准做法是在向量初检后接入轻量重排序模型（Reranker），基于相关性打分严格截断，仅向模型上下文输入 Top-3 到 Top-5 的核心切片（切片清洗与特征管理可参考 [/interview/high-freq-scenarios/doc-cleaning.md](/interview/high-freq-scenarios/doc-cleaning.md)）。

## 供应商计费特性：前缀缓存与异步批处理

主流云厂商针对底层推理架构提供了配套的计费优惠特性，合理编排调用格式能够直接降低单价。

![供应商 Prompt Caching 前缀匹配与 Batch API 批量调度机制图](/images/content-rebuild/1d2bd75b4fbdf063/fig-5.png)

### 1. 前缀缓存（Prompt Caching）
- **机制原理**：多个请求若具有完全相同的输入前缀（从第 1 个 Token 开始连续匹配），服务端在显卡上可以直接复用已经计算好的 KV Cache，无需对相同前缀重新执行 Prefill 计算。
- **计费特征**：命中前缀缓存的输入 Token，单价通常比全量输入单价低 50% 到 80%。
- **上下文编排要求**：
  - **静态内容严格前置**：必须把完全不变的内容（如大型系统规则、工具定义、固定知识库背景）置于最前；动态变化的内容（如当前时间、随机变量、用户新问题）严格放在末尾。
  - **杜绝前置动态干扰**：如果在 System Prompt 的第一行就拼入当前时间戳，会导致整个请求的前缀哈希彻底改变，造成前缀缓存穿透。
  - **注意最小长度门槛**：各云厂商通常对前缀缓存设有最小长度门槛（例如通常需达到 1024 Token 才会触发缓存机制）。

```python
# 错误示例：动态时间戳置顶，导致后续 1500 Tokens 的制度规则无法命中前缀缓存
bad_messages = [
    {"role": "system", "content": f"当前时间: {current_time}\n企业管理制度规范...[1500 tokens]"},
    {"role": "user", "content": user_query}
]

# 正确示例：静态长文本严格前置，动态变量下沉至请求末尾
good_messages = [
    {"role": "system", "content": "企业管理制度规范...[1500 tokens]"},
    {"role": "user", "content": f"[参考上下文：时间={current_time}]\n用户问题: {user_query}"}
]
```

### 2. 离线异步批处理（Batch API）
对于不需要即时响应的场景（如离线知识库解析、批量日志摘要、评测数据集跑分），可接入厂商提供的 Batch API 异步提交任务。作为错峰平衡闲置算力的对价，厂商通常会提供较为可观的单价折扣（各厂商折扣比例与交付时限不同，例如部分厂商提供约 50% 折扣并承诺 24 小时窗口，具体须以对应供应商官方定价与 SLA 为准）。

## 降本措施的边界与质量退化权衡

过度优化 Token 消耗会带来质量与稳定性的退化。降本必须建立在评测基线之上，权衡各项措施的边界：

![成本缩减与生成质量退化权衡雷达与边界图](/images/content-rebuild/1d2bd75b4fbdf063/fig-6.png)

| 降本措施 | 潜在工程风险 | 失效表现 | 缓解与防护手段 |
| :--- | :--- | :--- | :--- |
| **语义缓存（Semantic Cache）** | 细粒度意图混淆 | 相似度阈值偏低时，把否定句或不同主体的提问误判为同一问题 | 结合关键词提取过滤；仅对只读公共制度类问答开启缓存 |
| **上下文滑动截断** | 关键实体与指代信息丢失 | 历史窗口过小，模型无法理解“它”、“上面提到的第三点”指的是什么 | 引入提取式状态摘要，把关键实体保留在独立上下文字段中 |
| **轻量模型路由** | 复杂指令遵循能力不足 | 生成的 JSON 缺少必填字段，或复杂逻辑推断出现幻觉 | 在网关处执行 Schema 校验；校验失败触发级联升级至大模型重试 |
| **削减 Few-Shot 示例** | 边界场景输出格式漂移 | 结构化输出未按预期枚举值生成 | 优先使用模型供应商提供的结构化输出约束语法（Structured Outputs） |

## 面试高频追问

### 追问 1：语义缓存（Semantic Cache）如果命中率极低，可能是什么原因？如何排查？
**口述要点**：
1. **Query 分布呈长尾特征**：如果业务本身是专业代码排查或创意写作，用户提问天然离散，重复度极低，此时语义缓存不适用。
2. **通用向量模型对业务词区分度不足**：通用的语义嵌入模型对业务特有缩写或术语不敏感，即使表达同一意图，向量余弦相似度也达不到阈值。可以考虑微调领域专用的 Embedding 模型，或采用“关键词检索粗筛 + 语义计算精筛”的组合机制（参考 [/fundamentals/embedding/embedding-optimization.md](/fundamentals/embedding/embedding-optimization.md)）。
3. **缓存键包含了动态杂质**：排查在计算向量前是否错误地将动态 Session ID、用户昵称、未经标准化的首尾无用字符混合了进去，导致表征偏离。

### 追问 2：为什么控制输出 Token 往往比压缩输入更具经济价值？
**口述要点**：
1. **硬件执行瓶颈导致的单价非对称**：自回归解码（Decode）阶段是逐 Token 串行生成的，显存带宽利用效率低，硬件成本高，因此供应商的输出定价普遍是输入定价的 3 到 5 倍。
2. **工程控制确定性高**：输入端需要兼顾背景知识与提问完整性，压缩过多容易损失关键信息；而输出端可以通过 Prompt 明确约束格式（如“仅输出 2 位代码，不输出解释”），或直接设置合理的 `max_tokens` 阈值，以更低的工程代价避免模型生成冗余说明。

## 常见认知错误与避坑指南

- **错误 1：为了省钱把 System Prompt 删到最少，让模型自行理解**
  - *后果*：System Prompt 缺乏约束会导致模型输出格式不稳定，客户端反序列化失败率增加，频繁触发重试，反而消耗更多 Token。
- **错误 2：认为开启了供应商的 Prompt Caching 费用就自动减半**
  - *后果*：没有将静态规则与动态变量分离。哪怕长文本前仅仅动态插入了一个毫秒级时间戳，都会彻底破坏前缀哈希，导致缓存完全未命中。
- **错误 3：试图用小参数模型全面替代旗舰模型**
  - *后果*：小模型在严格指令遵循、复杂多步推理和防范提示词注入方面与旗舰模型仍有明确差距（安全防护细节可参考 [/interview/high-freq-scenarios/prompt-injection-defense.md](/interview/high-freq-scenarios/prompt-injection-defense.md)）。合理的做法是“梯级分流”，而非“全量平替”。
