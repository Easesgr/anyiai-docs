在对话系统与 AI 应用中，用户输入的提问往往残缺不全。如果系统盲目猜测并输出长篇内容，既浪费计算资源，又容易给出不相干的答案；如果无论什么问题都机械反问，又会让用户感到繁琐、失去耐心。

面对模糊提问，系统应该在什么时候直接回答，什么时候停下来追问？这是面试中考察对话交互设计与状态管理的核心问题。

---

## 面试口述标准答案

在面试中回答此问题时，应避免给出“必须追问”或“直接回答”的单一结论，建议采用**“先查上下文，再依风险与信息量三路分流”**的框架口述：

> **建议口述表达：**
> “面对模糊提问，系统不应该单向偏向盲猜或机械反问，而是采取分流决策：
> 1. **前置反查上下文**：在打扰用户之前，先检查当前页状态、登录身份或历史会话。如果系统已知缺失参数（例如当前用户只有一张待出行车票），优先将追问简化为直接确认，不发起多余提问。
> 2. **低风险直接回答加提示**：对于只读型的通用知识咨询（如‘怎么排查死锁’），即便缺少技术栈细节，也优先给出最常见场景的解答，并在结尾补充其他分支提示。
> 3. **有限分支直接概括**：当提问命中 2 到 3 个明确方向时，直接给出结构化对比，并附带可点击的快捷选项，让用户选择。
> 4. **高风险动作阻断追问**：对于退票、转账、删除数据等写操作，只要核心参数缺失，必须挂起执行，向用户发起追问；追问时尽量提供单选按钮，降低用户的输入成本。”

## 模糊提问的四种常见形态

在分析处理方案前，先区分提问模糊的具体原因。原因不同，系统的处理方式也完全不同：

![意图模糊的四种典型模式与成因对比](/images/content-rebuild/bcd39c0c31eaf9ae/fig-2.png)

- **槽位（Slot）缺失**：槽位指完成某个动作所必需的关键参数。例如用户说“帮我退票”，动作是退票，但缺少订单号、乘车人或车次。没有这些参数，后端接口无法执行真实操作。
- **代词指代不清（Coreference Ambiguity）**：例如“把刚才那个发给他”。“刚才那个”是前文生成的文件还是某条记录？“他”是谁？这类问题需要结合上下文的实体消歧逻辑来补全。
- **同名术语多义（Domain Polysemy）**：例如用户问“如何排查死锁”。在 MySQL 关系数据库中死锁是行锁与事务等待，在 Go 语言中可能是 channel 阻塞，在操作系统中是多线程资源竞争。用户意图清晰，但上下文领域未指定。
- **过于宏观宽泛（Overly Broad Query）**：例如“我想学人工智能”。这种问题并不缺少某个具体参数，而是涵盖范围过大，无法在单轮对话中穷尽。

## 触发追问的判定逻辑与代码实现

在工程实践中，不能完全依赖模型自由发挥来决定是否追问。通常由网关或流程控制器根据**操作风险等级**与**参数完备度**做结构化判定。

以客服与操作助手为例，系统判断的流程如下：

```
用户输入 Query
       |
       v
[1. 反查上下文 (用户ID/页面状态/历史记录)] -- 命中全部参数 --> 直接执行并反馈
       |
     仍有缺失
       v
[2. 风险与意图判定]
       |-- 高风险操作 且 缺失核心槽位 ------> 阻断追问 (提供快捷选项)
       |-- 命中 2~3 个明确分支 ----------> 输出分支概括 + 选项引导
       +-- 只读问答 / 仅缺修饰细节 --------> 默认假设回答 + 文末补充说明
```

![澄清追问的触发逻辑与系统门控](/images/content-rebuild/bcd39c0c31eaf9ae/fig-3.png)

下面是用 Python 与 Pydantic 表达的分流决策逻辑示例：

```python
from typing import Optional, List
from pydantic import BaseModel, Field

class IntentCheckResult(BaseModel):
    intent_name: str = Field(description="识别出的核心意图，如 refund_ticket, explain_concept")
    confidence: float = Field(description="意图识别置信度，0.0 到 1.0")
    is_write_action: bool = Field(description="是否为修改数据、调用支付等写操作")
    required_slots: List[str] = Field(default_factory=list, description="执行所需参数列表")
    branch_candidates: List[str] = Field(default_factory=list, description="意图覆盖的分支列表")

def decide_next_action(
    user_query: str,
    session_state: dict,
    check: IntentCheckResult
) -> str:
    # 步骤 1：优先尝试从会话状态或系统上下文中补齐槽位
    missing_slots = []
    for slot in check.required_slots:
        if slot not in session_state:
            missing_slots.append(slot)

    # 步骤 2：写操作且核心参数完整，进入执行或二次确认流程
    if check.is_write_action and not missing_slots:
        return "CONFIRM_AND_EXECUTE"

    # 步骤 3：写操作且存在未补齐参数，必须阻断追问
    if check.is_write_action and missing_slots:
        return "BLOCK_AND_ASK_SLOT"

    # 步骤 4：多义词且存在有限候选分支，输出分支摘要让用户选择
    if len(check.branch_candidates) in [2, 3] and check.confidence < 0.75:
        return "SHOW_BRANCH_SUMMARY"

    # 步骤 5：只读查询或低风险场景，按默认常见场景直接回答
    return "DIRECT_ANSWER_WITH_HINT"
```

这段代码的核心在于：**追问的目的是保障操作安全与交互效率，而不是推卸回答责任。**只要可以通过系统状态自动补充的参数，就不需要向用户发起追问。

## 追问交互设计：选项化与降低输入负担

当系统决定追问时，提问的方式直接决定了交互体验。常见的设计缺陷是向用户抛出开放式大问题，例如：“请问您的业务场景是什么？数据规模有多大？使用的是什么数据库版本？”这种提问会显著增加用户的输入成本。

![开放式哲学盘问与选项化降阻追问对比](/images/content-rebuild/bcd39c0c31eaf9ae/fig-4.png)

在人机交互设计中，**点击选择的认知负担远低于从头回忆并打字**。好的追问应遵循以下原则：

1. **选项化（Option Chips）**：追问时直接附带 2 到 4 个高频选项按钮。例如用户询问“死锁怎么排查”，追问气泡下方直接提供：“MySQL 数据库”、“Java 多线程”、“Go 协程”。
2. **单轮只聚焦最关键参数**：即使缺失多个参数，也不要像问卷一样一次性提出 3 个以上问题。先追问对决策影响最大的顶层参数，次要参数可在后续环节默认推荐或逐步补齐。
3. **给出带默认值的建议**：追问时可以附带默认推荐，例如：“您是想了解个人退票还是团体退票？（默认为您展示个人退票流程）”。

## 状态机维护与多轮槽位填充

在多轮对话中，用户对追问做出的回复往往非常简短（例如只回一个选项或一串数字）。对话引擎需要依托有限状态机（Finite State Machine, FSM）来维护上下文，将新输入与上一轮挂起的目标合并：

![槽位填充与多轮对话状态机演进流](/images/content-rebuild/bcd39c0c31eaf9ae/fig-5.png)

状态迁移通常包含以下节点：
- **空闲态（IDLE）**：等待用户发起新请求。
- **收集态（COLLECTING）**：识别出目标意图，但核心参数缺失，系统抛出追问控件，任务标记为挂起等待（Pending）。
- **就绪态（READY）**：用户选定或输入了参数，系统将新参数填入对应槽位，移交后端执行模块。

在实现状态机时，必须支持**意图抢占（Topic Preemption）**：如果系统正在追问“请问您的车次是哪一趟”，用户突然说“先不退了，帮我查查明天的天气”，系统必须能够识别出用户切换了意图，及时释放当前挂起任务，转入新的查询流程，而不是继续追问车次。

## 追问轮次上限与降级兜底

多轮追问的容忍度很低。如果用户连续两轮都没能给出系统需要的参数，继续追问通常只会让体验恶化。因此需要建立兜底机制：

![防盘问轮数计数器与兜底降级决策环](/images/content-rebuild/bcd39c0c31eaf9ae/fig-6.png)

1. **最大追问轮数限制（例如设为 2 次）**：对同一意图连续追问达到上限后，不再发起第三轮追问，转为直接给出常见问题列表、搜索链接或转接人工客服。
2. **提供跳出通道**：追问气泡下方应常置“换个问题”或“人工协助”按钮，允许用户随时退出追问流程。
3. **只读场景坚持回答先行**：对于涉及概念解释的场景（如 [/interview/high-freq-scenarios/inaccurate-answer.md](/interview/high-freq-scenarios/inaccurate-answer.md) 中提到的通用技术问题），坚持“先基于高频假设给出 80% 大众方案，文末留出延展说明”，避免阻断式追问。

## 面试考题拆解与常见误区

### 追问 1：用户只输入“帮我退票”，没有任何订单号，系统应如何处理？

**参考回答要点：**
1. **前置反查业务库**：根据当前用户的登录信息，查询数据库中处于“待出行/可退票”状态的有效订单。
2. **依据反查结果分流**：
   - **仅有 1 笔有效订单**：不需要追问车次，直接调出该订单详情并给出确认卡片：“为您找到明天 G101 次车票，退票手续费为 5%，是否确认退订？”将“追问参数”降级为“二次确认”。
   - **存在多笔有效订单**：弹出卡片展示这几笔订单，提供单选按钮供用户点选。
   - **无任何有效订单**：直接回复“当前账户下未查询到可退订的车票”，结束流程。

### 追问 2：为什么不直接在系统 Prompt 里写“遇到不确定的问题请向用户追问”，让大模型全权决定？

**参考回答要点：**
1. **模型倾向强行作答**：主流大模型经过指令微调和人类偏好对齐训练，天然倾向于给出详尽完整的回答。在仅靠自然语言提示约束时，模型很容易自行脑补一套假设直接输出，策略稳定性不足。
2. **开放式盘问难以控制**：一旦模型触发追问倾向，往往会一次性抛出多个开放式反问，导致交互体验变差。
3. **工程与安全解耦**：涉及写操作的权限校验、参数提取和反查逻辑属于系统控制流（可参考 [/frontier/agentic-rag/complex-query-planning.md](/frontier/agentic-rag/complex-query-planning.md) 中关于规划与控制流的解耦思路）。这类确定性逻辑应当由程序代码控制，模型主要负责语义理解和槽位提取，不能把业务安全完全寄托在模型的单次生成上。

### 常见错误说法辨析

- **误区 1：“为了回答准确，遇到任何信息不全的问题都必须先追问清楚。”**  
  *纠错*：低风险只读问答过度追问会导致极高的跳出率。正确的做法是“直接给主干、末尾注分支”，只有写操作或核心主键缺失才进行阻断追问。
- **误区 2：“意图识别必须用大模型跑多步推理。”**  
  *纠错*：高频且模式明确的意图，通常采用规则或轻量分类模型前置过滤，既能降低端到端延迟与推理开销（可参考 [/interview/high-freq-scenarios/cost-optimization.md](/interview/high-freq-scenarios/cost-optimization.md)），又能避免大模型在简单意图分类时的随机抖动。

## 总结与延伸阅读

决定直接回答还是先追问，本质是在**用户交互成本**与**误操作风险代价**之间寻找平衡。通过上下文反查减少不必要提问、对只读问答先行作答、对高风险写操作以选项化形式精确追问，并配合状态机管理，才能构建既安全又顺畅的对话系统。
