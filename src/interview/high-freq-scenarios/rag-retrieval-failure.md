在检索增强生成（RAG）系统中，模型回答错误或答非所问，很大一部分并非大语言模型本身的推理缺陷，而是上游检索器根本没有把正确文档送入上下文窗口。我们在前置讨论[/interview/high-freq-scenarios/inaccurate-answer.md](/interview/high-freq-scenarios/inaccurate-answer.md)中把 RAG 链路拆分为检索、增强与生成三个阶段，本篇专门聚焦第一阶段——**如何排查与解决检索未命中问题**。

为了让排查步骤落地，我们用一个贯穿全篇的技术排障场景作为示例：
* **用户提问**："服务报错 `ERR_CONNECTION_TIMED_OUT`，怎么排查？"
* **知识库目标文档**：包含一段针对 Windows 系统的网络错误码记录，正文记述为"系统错误代码 10060 表示连接尝试因目标主机在一段时间内未正确响应而超时失效，对应常见客户端报错 ERR_CONNECTION_TIMED_OUT..."。

## 口述标准框架：检索未命中的三阶段排查

面试中遇到"RAG 检索不到正确文档，你怎么排查"这类问题，切忌零散背诵参数，应按照数据在检索系统中的流动阶段组织回答：

> "排查 RAG 检索未命中，通常按数据流动的三个关键节点逆向排查：
>
> 1. **检索度量与截断阶段（搜不出）**：首先检查是否有过紧的硬过滤。包括 ANN 索引的搜索范围参数（如 HNSW 的 `ef_search`）设置过小导致提前终止、相似度固定截断阈值（Score Threshold）设得过高，或者向量度量方式配置不一致（例如未做模长归一化却使用了点积索引）。同时需检查租户隔离、环境标签等元数据过滤是否发生误杀。
> 2. **向量编码与语义对齐阶段（转不对）**：检查查询与文档使用的 Embedding 模型版本是否严格一致；分析专有名词与技术代码（如 `ERR_CONNECTION_TIMED_OUT`）是否因词表切分而导致向量表征偏离；对于简短疑问句与长陈述句之间的非对称语义鸿沟，排查是否缺乏适配。
> 3. **数据分块与索引构建阶段（存不进）**：回溯原始切分。分块过大导致核心错误码被整段无关信息稀释；分块过小或机械按字符硬切，导致主语、代词与解决方案跨块断裂，使单个文本块失去独立语义。
>
> 排查时，工程上遵循'**放开过滤与阈值验证原始打分 $\to$ 对比向量与关键词命中 $\to$ 校验原始分块质量**'的逆向定位顺序，并视情况引入 BM25 混合检索、查询改写与 Cross-Encoder 重排完成优化。"

## 阶段一：文档切分与索引过滤排查

如果数据在进入向量数据库前就已经丢失了上下文，后续任何检索算法都无法召回正确结果。

### 1. 分块粒度失衡
* **分块过大（例如单块 > 1500 tokens）**：常见双塔 Embedding 模型输出固定维度的稠密向量，对整段文本的全局语义进行压缩。如果一个文本块同时包含网络配置、内存调优和错误码解释，核心名词 `ERR_CONNECTION_TIMED_OUT` 在向量中的权重会被周围无关内容稀释，导致余弦相似度排名被更专注的小文档挤出 Top-K。
* **分块过小（例如单块 < 64 tokens）**：分块会破坏句义的完整性。例如切分把"故障代码 10060 说明"放在前一块，而"解决方案是检查防火墙出站规则"切到了后一块。用户询问排障方案时，无论命中哪一块，送入生成模型的上下文都缺乏完整因果链条。

### 2. 机械断句导致的指代悬空
纯按固定字符数暴力滑动切分，极易在从句或代词处切断。例如原文：
> "系统错误代码 10060 是底层网络握手超时的典型体现。**该问题**通常由网关策略阻断或端口未监听引起，对应上层应用的 `ERR_CONNECTION_TIMED_OUT`。"

若切分边界恰好落在第二句前，生成的第二个块仅包含："该问题通常由网关策略阻断或端口未监听引起..."。由于缺失前置主语，模型和检索器都无法推断"该问题"指向哪个具体错误。对于此类情况，工程中通常采用带有重叠区间的滑动窗口（如设置 Chunk Overlap 为分块大小的 10%~20%），或采用父子文档切分策略（小块用于检索，大块用于喂给模型）。

### 3. 元数据过滤的静默误杀
向量数据库（如 Qdrant、Milvus、Elasticsearch）普遍支持在向量相似度计算前或计算后执行布尔过滤（Metadata Filtering）。
* **常见排查点**：检查查询请求中携带的过滤条件，例如环境标（`env = 'prod'`）、租户 ID（`tenant_id`）、状态标识（`status = 'published'`）以及软删除标记（`is_deleted = false`）。
* **验证方法**：**临时移除所有布尔过滤条件**，仅传入用户 Query 向量执行全量 Top-K 检索，确认目标文档是否确实存在于索引中。如果在无过滤状态下能搜到，说明是上游过滤规则存在逻辑偏差。

## 阶段二：向量表征质量排查

文档切分完整且确认入库后，如果仍然漏召回，需排查向量空间中的几何对齐状态。

### 1. 领域专有名词与编码分词偏移
通用的预训练 Embedding 模型主要在通用语料上进行对比学习。当遇到垂直领域特有的复合标识符、错误代码或系统配置项（如 `ERR_CONNECTION_TIMED_OUT`）时：
* 词表（Tokenizer）通常没有收录该词，会将其拆解为多个子词片段（Subwords），如 `ERR`、`_`、`CONNECT`、`ION` 等。
* 缺乏先验训练的子词组合，编码出的向量往往会偏离真实语义聚类，无法与文档中的"网络连接超时"建立高相似度联系。

### 2. 非对称检索的语义鸿沟
RAG 场景下的检索普遍属于**非对称检索（Asymmetric Search）**：
* 用户提问是短文本、疑问语态，词汇量少；
* 知识库目标文档是长文本、陈述语态，带有具体的技术参数与操作规程。

在未经非对称任务微调的向量空间中，疑问句倾向于同其他疑问句聚在一起，陈述句同陈述句聚在一起。当用户输入疑问句检索时，系统更容易召回"社区中其他人提出的相似问题"，而非给出答案的操作指南。

![非对称检索语义空间分布示意图](/images/content-rebuild/677543f74f220c48/fig-3.png)

### 3. 模型版本与环境配置漂移
这是一个常见但易被忽视的工程失误：离线批处理构建知识库索引时使用的是模型版本 A（例如某一 Embedding 模型的 v1 版本，或带有某种输入前缀指令），而在线服务升级后，Query 端使用了更新后的 v2 模型，或者遗漏了模型要求的专用 Prompt 前缀（例如某些模型在检索时要求对 Query 添加 `Represent this sentence for searching relevant passages:`）。向量空间基准不一致，相似度计算将彻底失效。

## 阶段三：检索计算与参数度量陷阱

即使向量表征合理，检索阶段的数学度量配置或索引剪枝参数不当，也会导致正确文档被系统截断。

### 1. 度量方式与模长归一化
向量数据库支持的度量方式通常包括余弦相似度（Cosine）、内积（Dot Product / IP）与欧氏距离（L2）。
* **数学关系**：余弦相似度定义为：
  $$\text{Cosine}(A, B) = \frac{A \cdot B}{\|A\|_2 \|B\|_2}$$
  向量若经过 L2 归一化（即单位化，$\|A\|_2 = 1, \|B\|_2 = 1$），内积与余弦相似度在数值上完全相等：$A \cdot B = \text{Cosine}(A, B)$。
* **故障现象**：若向量写入数据库前未做 L2 归一化，而检索索引却配置为内积（IP），模长较大的文本块（通常是词数较多、信息杂糅的块）内积计算值会天然偏高，直接压制模长较小但语义高度匹配的短文本块。

### 2. 硬编码相似度阈值的截断风险
部分系统在检索器后置了固定的得分过滤逻辑，例如只保留相似度得分大于 0.8 的文档。
* **问题根源**：向量在空间中的分布并不均匀。常见的高频意图相似度往往能达到 0.85 以上，但冷门专业术语或带复杂约束的查询，最相关文档的得分可能天然落在 0.70 左右。
* **排查方法**：将 Score Threshold 临时置为 0，查看 Top-K 返回结果中目标文档的真实得分与位次分布。

### 3. ANN 索引的参数提前剪枝
为了在海量向量中保证检索延迟，系统通常采用 HNSW 等近似最近邻索引。在 HNSW 算法中，`ef_search` 参数控制在线遍历图时的动态候选集队列大小。
* 如果并发升高或资源吃紧时将 `ef_search` 设得过小，图遍历算法在跳跃搜索时更容易陷入局部极值点并提前终止，导致原本全局距离最近的正确节点未能进入候选列表。

## 进阶优化方案：混合检索、查询增强与两阶段重排

单靠调整分块与阈值有时无法完全解决特定字符匹配与语义表达的矛盾。生产系统中常引入以下组合方案。

### 1. BM25 与稠密向量的混合检索（Hybrid Search）
针对 `ERR_CONNECTION_TIMED_OUT`、错误代码 `10060` 这类字符明确但语义抽象的技术词，倒排索引（BM25）具备确定性的字面命中优势；而稠密向量则负责理解"连接中断"、"网络不通"等自然语言语义。关于检索机制对比可参考[/llm-100/rag/retrieval-methods.md](/llm-100/rag/retrieval-methods.md)。

两路检索召回的结果，常用**互惠排名融合（Reciprocal Rank Fusion, RRF）**进行无量纲合并。RRF 不依赖绝对相似度分数，而是利用各自返回的名次计算融合得分：

$$\text{RRF\_Score}(d) = \sum_{m \in M} \frac{w_m}{k + r_m(d)}$$

其中 $M$ 为检索器集合，$r_m(d)$ 为文档 $d$ 在检索器 $m$ 中从 1 开始的排位名次，$k$ 为平滑常数（经验值常取 60），$w_m$ 为各通道权重系数（默认可设为 1.0）。若某文档在某通道未上榜，该通道对应项记为 0。

#### 贯穿示例：RRF 融合算例
假设以 `ERR_CONNECTION_TIMED_OUT` 为查询，平滑常数 $k=60$，等权重 $w=1.0$，两路检索结果如下：

| 文档编号 | 文档主题 | 稠密向量排位 ($r_{\text{dense}}$) | BM25 排位 ($r_{\text{bm25}}$) | RRF 计算过程 | 最终得分 | 融合后位次 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Doc-A** | 错误码 10060 与 ERR_CONNECTION_TIMED_OUT 排障 | 2 | 1 | $\frac{1}{60+2} + \frac{1}{60+1} = 0.01613 + 0.01639$ | **0.03252** | **第 1 位** |
| **Doc-B** | 客户端常见连接异常类型盘点 | 1 | 未上榜 | $\frac{1}{60+1} + 0 = 0.01639$ | 0.01639 | 第 3 位 |
| **Doc-C** | Windows Socket 网络错误代码汇总 | 12 | 2 | $\frac{1}{60+12} + \frac{1}{60+2} = 0.01389 + 0.01613$ | 0.03002 | 第 2 位 |

纯向量检索中位列第 2 的 `Doc-A`，依靠 BM25 对精准错误码的第一命中，在 RRF 融合后跃居第一，成功纠正了单一通道的排序不足。

### 2. 假设性文档嵌入（HyDE）与查询改写
若用户提问过于简略，可在检索前调用轻量模型执行预处理：
* **HyDE（Hypothetical Document Embeddings）**：提示大模型针对提问生成一段模拟的回答段落。即使该虚构段落事实未必完全准确，但其陈述句文风和专业术语分布更贴近知识库文档。用该虚构段落生成 Embedding 去向量库检索，能拉近与陈述性文档的空间距离。
* **多步改写与分解**：对于复合问题，可将单次提问拆解为多个子查询分头检索，细节可参考[/frontier/agentic-rag/multi-step-retrieval.md](/frontier/agentic-rag/multi-step-retrieval.md)。

### 3. 两阶段重排：Bi-Encoder 粗排 + Cross-Encoder 精排
* **Bi-Encoder（双塔结构，初筛）**：Query 和 Document 分别经过独立的 Transformer 编码得到两个定长向量，各自注意力计算复杂度为 $O(L_q^2)$ 与 $O(L_d^2)$。由于两端没有跨序列的逐字全注意力交互，文档向量可离线预先编码并建立索引；在线查询时只需对 Query 进行一次编码，再通过 ANN 索引做向量近邻检索，适合在百万级候选库中做毫秒级初筛。
* **Cross-Encoder（交叉编码结构，重排）**：将 Query 与 Document 拼接为单个序列输入模型：
  $$\text{[CLS]} \circ \text{Query} \circ \text{[SEP]} \circ \text{Document} \circ \text{[SEP]}$$
  模型内部所有层级进行全自注意力计算，每个查询词都能直接与文档词进行交互，匹配精度显著提高。但其计算复杂度为 $O((L_q + L_d)^2)$，且无法离线预存分数，每次必须在线计算。
* **级联工作流**：初筛阶段用双塔向量与 BM25 召回 Top-100，再交由 Cross-Encoder 重排模型打分，截取前 3~5 篇送入大语言模型。既保证了召回覆盖率，又兼顾了线上响应延迟。

## 离线评测体系：量化检验检索调优

检索排查与优化必须基于可复现的离线量化指标，不能依赖零散单例的主观体验。

构建评测集时，准备一组测试查询 $Q$，每个查询 $q$ 标注了标准答案文档集合 $G_q$。设检索系统返回的前 $K$ 个候选文档为 $R_q@K$。

### 常用指标定义

1. **命中率（Hit Rate@K）**：前 $K$ 个结果中只要包含至少一个正例文档即算命中（值为 1，否则为 0）：
   $$\text{Hit@K} = \frac{1}{|Q|} \sum_{q \in Q} \mathbb{I}(|R_q@K \cap G_q| > 0)$$
2. **平均倒数排名（MRR, Mean Reciprocal Rank）**：关注**首个**正确文档在候选列表中的排位名次 $\text{rank}_q$。名次越靠前，分值越高；前 $K$ 个结果中未命中则计为 0：
   $$\text{MRR@K} = \frac{1}{|Q|} \sum_{q \in Q} \frac{1}{\text{rank}_q}$$
3. **召回率（Recall@K）**：前 $K$ 个结果中命中的正例数量占该查询全部正例的比例：
   $$\text{Recall@K} = \frac{1}{|Q|} \sum_{q \in Q} \frac{|R_q@K \cap G_q|}{|G_q|}$$

#### 评测算例（假设 $K=3$）

| 查询编号 | 标准正例集合 $G_q$ | 检索给出的 Top-3 预测序列 ($R_q@3$) | 首个正例位次 ($\text{rank}_q$) | $\text{Hit@3}$ | 倒数排名 (RR) | $\text{Recall@3}$ |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| $q_1$ | $\{d_1, d_2\}$ | $[d_3, \mathbf{d_1}, d_5]$ | 第 2 位 | 1 | $1/2 = 0.50$ | $1/2 = 0.50$ |
| $q_2$ | $\{d_8\}$ | $[\mathbf{d_8}, d_4, d_6]$ | 第 1 位 | 1 | $1/1 = 1.00$ | $1/1 = 1.00$ |
| $q_3$ | $\{d_9, d_{10}\}$ | $[d_2, d_7, d_{11}]$ | 未命中 | 0 | $0.00$ | $0/2 = 0.00$ |
| **平均表现** | - | - | - | **0.67** | **0.50** | **0.50** |

根据上表统计：
* 系统在 $K=3$ 时的平均 $\text{Hit@3} = (1 + 1 + 0) / 3 \approx 0.67$
* 平均倒数排名 $\text{MRR@3} = (0.50 + 1.00 + 0) / 3 = 0.50$
* 整体平均 $\text{Recall@3} = (0.50 + 1.00 + 0) / 3 = 0.50$

每次对切分粒度、索引参数或重排模型做调整后，通过对比评测集上的指标浮动，即可验证优化方案的实际增益。

## 面试追问与深度探讨

### 追问 1：遇到生僻的技术缩写或错误码，稠密向量检索往往漏召回，原因是什么？混合检索又是如何解决的？
**口述要点**：
1. **失效原因**：通用 Embedding 模型的词表中没有这类生僻专有名词，分词时会被拆分成多个 Subwords。在 Transformer 的自注意力计算中，这些缺乏共现统计的子词无法聚合成具备明确指向的语义向量，导致其向量坐标向通用均值漂移，与文档中的对应代码无法紧密对齐。
2. **混合检索作用**：引入基于倒排索引的 BM25。BM25 是字面精准匹配，计算词频（TF）与逆文档频率（IDF），对这类全局低频、局部出现的专有名词和错误代码有极高的区分权重。通过 RRF 将 BM25 与稠密向量的排位结果加权融合，可以确保专有字面匹配的文档在排序中稳定上浮。

### 追问 2：为什么 Cross-Encoder 重排模型效果更好，却不能直接替代 Bi-Encoder 用于全库初筛？
**口述要点**：
1. **计算复杂度限制**：Bi-Encoder 在预处理阶段就能离线计算并存储全库文档向量，在线查询只需计算一次 Query 向量并通过 HNSW 索引做向量近邻搜索，耗时在毫秒级。而 Cross-Encoder 要求将 Query 与候选 Document 拼接，每次打分都需要完整的自注意力前向计算，复杂度随候选文档量线性增长（$O(N \cdot (L_q+L_d)^2)$）。
2. **工程折中**：如果直接对百万级文档做全量 Cross-Encoder 推理，延迟和显存开销在生产环境中不可承受。因此工业界普遍采用"Bi-Encoder 粗筛出 Top-50~100 $\to$ Cross-Encoder 精排至 Top-3~5"的级联分层结构。

## 常见认知错误与避坑清单

* **错误 1：一遇到检索未命中，立刻微调（Fine-tune）Embedding 模型**。微调成本高、周期长，且容易引起模型在其他通用领域的遗忘。排查应优先检查元数据过滤误杀、分块代词截断以及 ANN 搜索参数，这些在实际工程中占比极高且极易修复。
* **错误 2：认为稠密向量可以彻底淘汰 BM25 等传统全文检索**。向量检索擅长模糊意图与近义对齐，但在处理人名、手机号、UUID、错误枚举值等强确定性文本时存在结构性盲区，混合检索是目前成熟系统的标准选择。
* **错误 3：为了提高召回率无节制放大最终喂给 LLM 的 Top-K**。把检索的 Top-K 从 5 直接放宽到 30 并全量拼接进 Prompt，不仅急剧增加 API 成本与首字生成延迟，还会引发模型注意力在过长无关上下文中分散（Lost in the Middle），导致生成质量显著恶化。正确思路是放大初筛候选池，并在最终输入生成模型前通过重排模型做精准剪裁。
