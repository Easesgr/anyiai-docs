在检索增强生成（RAG）应用中，检索不准或大模型答非所问，问题往往并不出在 Embedding 模型或大模型本身，而是发生在最前端的环节：**数据抽取与清洗（ETL）**。

如果将未经清洗、排版错乱的双栏 PDF、冗余的 HTML 或带有复杂样式的 DOCX 直接切块入库，向量数据库中就会充斥着乱码、被截断的半句话以及脱离章节上下文的文本碎片。排查检索质量问题的方法可参考 [/interview/high-freq-scenarios/rag-retrieval-failure.md](/interview/high-freq-scenarios/rag-retrieval-failure.md)。本文梳理一套经过工程验证的文档清洗与入库流水线设计。

## 一、口述标准回答（可用于面试）

> **面试官提问：如果企业知识库有数万篇格式混乱、包含乱码和排版杂乱的文档，你会如何设计从解析、清洗到入库的完整流程？**

**口述要点（约 60 ~ 90 秒）：**

“处理混乱且批量的企业文档，核心是建立一条**分阶段、带质检门禁的离线数据流水线**，主要分为四个环节：

1. **格式差异化解析与版面分析**：区分流式排版（HTML、DOCX）与物理绘图排版（PDF）。针对 PDF，不使用无版面感知的线性文本抽取，而是通过版面分析识别文本块的二维坐标（Bounding Box），区分单双栏与表格，按照人类阅读顺序重构正文流。
2. **规则规整与跨页缝合**：基于 Y 坐标分布和跨页重复模式剔除固定页眉、页脚与页码；通过标点和连字符规则，识别换页处被中断的自然段落与单词，拼回连贯文本，并过滤控制字符和非法编码。
3. **语义结构化分块与父子索引**：优先利用 Markdown 标题树或段落边界切分，并在每个分块前拼入章节路径作为上下文补充；采用父子块（Parent-Child）策略，切分 200 Token 左右的小块用于计算向量并做精准检索，命中后根据映射关联提取 1000 Token 的完整父块供大模型生成使用。
4. **入库门禁质检**：入库前设置长度过滤、乱码检测（结合不可见字符与信息熵）以及基于 MinHash / SimHash 的高频模板公文去重。通过质检后，携带文档来源、更新时间、标题路径等元数据分别写入全文和向量索引。”

## 二、贯穿案例与多格式源文档解析

以处理一份包含 500 页的《分布式存储运维手册》为例，该文档在企业内部存在三种副本：原始扫描与电子排版的 PDF（带双栏与页眉）、内部 Wiki 导出的 HTML、以及各团队修改的 DOCX。

不同格式的数据组织方式存在根本区别：

* **HTML**：基于 DOM 树，标签语义清晰（`<h1>`、`<p>`、`<table>`）。清洗重点是剔除 `<script>`、`<style>`、导航栏和弹窗容器，提取主体文本标签。
* **DOCX**：基于 OpenXML 规范，由段落（Paragraph）、样式运行块（Run）与表格构成，天然包含章节树状结构。
* **PDF**：本质是基于打印指令的绘图文件。它只记录字符字形在当前页面的绝对二维坐标 $(x, y)$，本身没有“行”、“段落”或“双栏”的数据结构。

![PDF、DOCX 与 HTML 解析机制与版面分析（Layout Analysis）对比](/images/content-rebuild/45bbb6e776751b9f/fig-1.png)

如果在解析双栏排版的 PDF 时使用基础文本抽取库（如未配置分栏规则的早期工具），解析器会按从上到下的物理 Y 坐标逐行读取，把左右两栏同一水平高度的文字拼成一行，导致语义彻底错乱。

因此，处理物理排版文档必须引入**版面分析（Layout Analysis）**：
1. **字符到文本块聚类**：利用字符坐标间距（横向字符间距与纵向行间距），将散落字形聚合为文本行，再聚合成带矩形坐标框（Bounding Box）的段落块。
2. **分栏检测与阅读顺序还原**：通过投影分析或几何规则判定页面是否存在垂直中线分割。确认双栏后，优先遍历左栏从上到下的所有文本块，再遍历右栏，还原人类自然阅读顺序。

## 三、文本清洗：去除噪声与跨页断句缝合

在将解析后的文本交给分块器前，需要通过规则管道消除版面产生的机械噪声。

![页眉页脚过滤与跨页断句拼接机制流程](/images/content-rebuild/45bbb6e776751b9f/fig-2.png)

### 1. 页眉、页脚与页码过滤
* **坐标边界裁剪**：统计整篇文档的元素分布。页面顶部 5%~8% 与底部 5%~8% 区域内的单行文本，通常属于页眉、页脚或页码。
* **跨页频次比对**：若某段固定文字（如“内部机密·请勿外传”）在多个连续页面相同坐标区间内高频重复出现，或在页脚区域匹配到递增页码模式，可直接从文本流中剥离。

### 2. 编码与不可见字符规范化
* 依据源文件的实际编码正确解码，再统一保存为 UTF-8。遇到 Unicode 替换字符（U+FFFD）时，先检查源文件编码与抽取日志，尽量回源恢复；无法恢复时保留错误标记，不直接删除以掩盖数据丢失。
* 移除无需保留的 ASCII 控制字符，保留换行符 `\n` 和制表符 `\t`。
* 将 3 个及以上的连续换行符规范化为双换行 `\n\n`，保留段落区分标记的同时避免占用多余 Token。

### 3. 跨页断句缝合
PDF 分页常导致同一句话或同一个单词被截断在两页，中间还夹着页眉页脚。在移除了页眉页脚之后，需根据标点与词法状态进行拼接：

```python
import re

def stitch_cross_page_blocks(cleaned_pages: list[str]) -> list[str]:
    """
    处理已去除页眉页脚的单页文本列表，修复因换页导致的截断段落。
    """
    terminal_punctuations = {"。", "！", "？", ".", "!", "?", "；", ";"}
    stitched_blocks = []
    
    for current_page in cleaned_pages:
        text = current_page.strip()
        if not text:
            continue
        if not stitched_blocks:
            stitched_blocks.append(text)
            continue
            
        prev_text = stitched_blocks[-1]
        last_char = prev_text[-1]
        
        # 情况 1：前一页以西文连字符结尾（例如：distri-\n buted）
        if prev_text.endswith("-") and len(prev_text) > 1 and prev_text[-2].isalpha():
            stitched_blocks[-1] = prev_text[:-1] + text
        # 情况 2：前一页末尾不是句子终结标点，说明句子被跨页截断
        elif last_char not in terminal_punctuations:
            # 中文字符之间直接无缝拼接；西文字符之间补一个空格
            separator = "" if '\u4e00' <= last_char <= '\u9fff' else " "
            stitched_blocks[-1] = prev_text + separator + text
        else:
            stitched_blocks.append(text)
            
    return stitched_blocks
```

## 四、分块策略：从固定窗口到结构化分块

清洗后的连贯文本需要切分为离散的片段（Chunks）。分块策略直接决定了检索匹配的信噪比。

![固定分块、滑动窗口与按文档结构切分的切块效果对比](/images/content-rebuild/45bbb6e776751b9f/fig-3.png)

### 1. 固定长度与滑动窗口的局限
* **机械固定长度（Fixed Token Size）**：如每 500 Token 强制截断。切割点可能正好落在一段代码、数学公式或关键因果句中间，造成语义生硬割裂。
* **带重叠的滑动窗口（Overlap）**：如窗口 500 Token、步长 400 Token（100 Token 重叠）。重叠区能缓解边界截断，但带来了数据冗余与存储膨胀；同时它依然无法感知章节层级，容易把二级标题与它的正文拆分到两个块中。

### 2. 结构化切分与章节路径补全
更合理的做法是将解析后的文档统一归一化为 Markdown 树状结构，按语法层级递归分块：
1. **标题层级下钻**：优先在 `#`、`##`、`###` 边界切分，确保同级章节的聚合度。
2. **段落级回退**：若某个子章节内容仍超出设定的 Token 阈值，退回在自然段落（`

`）处切分；若段落仍超长，再按句子终结符（句号、问号、叹号）切分。
3. **注入章节路径（Breadcrumb Injection）**：
   孤立的切块常丢失主语。例如正文写道：“将参数设置为 3 以启动集群同步。”在没有上下文时，检索模型无法获知这是哪个组件的参数。在切块文本开头拼接其所属的完整路径：
   ```text
   [所属章节: 分布式存储运维手册 > 第三章 存储节点配置 > 3.2 同步超时机制]
   将参数设置为 3 以启动集群同步。
   ```
   通过在切块头部注入面包屑路径，为 Embedding 和关键字检索补齐了实体与上下文，同时代价仅增加少量 Token。

## 五、父子块（Parent-Child）架构设计

切块长度的设计常面临矛盾：
* **短分块（如 150~250 Token）**：语义集中，检索时与用户提问的短查询向量重合度高；但片段过短，缺乏充足推导过程，大模型生成时容易信息不全。
* **长分块（如 1000~1500 Token）**：包含完整背景，但文本内混杂多个子话题，生成的稠密向量（Dense Vector）各主题特征相互稀释，导致检索阶段相似度得分被拉低。

![父子分块（Parent-Child）架构检索与生成拓扑机制](/images/content-rebuild/45bbb6e776751b9f/fig-4.png)

**父子分块（Parent-Child Chunking）**将检索单元与生成单元解耦：

1. **切分与关联**：按较大粒度切分出包含完整逻辑的“父块”（如 800~1200 Token）；在每个父块内部，进一步细切成若干高密度的“子块”（如 150~250 Token）。
2. **差异化存储**：仅对子块计算 Embedding 并存入向量数据库，子块元数据中记录对应的 `parent_id`；父块全文存入文档数据库或对象存储（如 PostgreSQL、MongoDB、Redis）。
3. **检索与还原**：检索时用子块匹配用户的 Query；拿到 Top-K 个子块后，通过 `parent_id` 查出对应的父块，父块去重后组装成上下文发给大模型。

```python
import uuid
from typing import Dict, List

class ParentChildIndexer:
    def __init__(self):
        self.vector_index: List[Dict] = []      # 存检索子块与向量
        self.child_to_parent: Dict[str, str] = {} # 子块到父块映射，保证 O(1) 检索
        self.doc_store: Dict[str, str] = {}     # 存完整父块正文

    def add_document(self, parent_text: str, child_texts: List[str]):
        parent_id = f"parent_{uuid.uuid4().hex[:8]}"
        # 存储大上下文父块
        self.doc_store[parent_id] = parent_text
        
        # 为子块建立索引
        for child in child_texts:
            child_id = f"child_{uuid.uuid4().hex[:8]}"
            self.child_to_parent[child_id] = parent_id
            self.vector_index.append({
                "child_id": child_id,
                "parent_id": parent_id,
                "text": child,
                # 生产环境调用真实 Embedding 模型生成向量：
                # "vector": embedding_model.embed(child)
            })

    def retrieve_parents(self, matched_child_ids: List[str]) -> List[str]:
        """
        命中子块后，按 matched_child_ids 相似度排序提取父块并保序去重
        """
        hit_parents = []
        seen_parents = set()
        for cid in matched_child_ids:
            pid = self.child_to_parent.get(cid)
            if pid and pid in self.doc_store and pid not in seen_parents:
                seen_parents.add(pid)
                hit_parents.append(self.doc_store[pid])
                
        return hit_parents
```

## 六、入库质量门禁（Quality Gate）

入库前必须设置程序化的检验过滤网，防止脏数据污染索引库。

![入库质检门禁（Quality Gate）的三道过滤防线](/images/content-rebuild/45bbb6e776751b9f/fig-5.png)

### 1. 长度门禁
* **超短碎片过滤**：去除字数小于 20 字且不含有效知识的片段（如单纯的“目录”、“版权所有”、“（完）”），避免污染检索召回列表。
* **超长溢出拦截**：单块字数超出目标模型最大输入窗口的，拦截打入报警队列，防止被客户端自动截断导致信息丢失。

### 2. 乱码与低质内容识别
乱码文本（如二进制文件解析错误、字体映射表丢失或未经解码的 base64 字符串）具有异常的字符特征。

* **不可打印字符比例**：统计控制字符和不可见字符占比，超过 5% 即丢弃。
* **字符香农信息熵（Shannon Entropy）检测**：

$$H(X) = -\sum_{i=1}^{n} P(x_i) \log_2 P(x_i)$$

当一段文本长度超过 50 个字符时：
* **熵极低**（例如 $H < 1.5$）：通常是无意义的机械重复字符（如 `==============` 或 `AAAAAAA`）。
* **乱码特征**：对于含有大量无意义随机符号、解码错误的乱码片段，不仅熵值分布偏离自然语言，且会伴随大量未知 Unicode 字符。过滤时应结合**特定无意义符号比例**与**信息熵**做联合判断，不能仅凭高熵就误判正常汉字文本（因为多字不重复的正常中文长句，其字级熵本身就偏高）。

### 3. 内容去重（Deduplication）
在企业文档中，法律免责声明、页脚版权、公文抬头往往反复出现。若每一份都计算向量入库，向量检索列表中会出现大量同质噪声。
* **局部敏感哈希（MinHash / SimHash）**：离线对每个切块计算 64 位 SimHash 签名。若新切块与已有模板库的汉明距离小于阈值（例如 $\le 3$），判定为模板段落，只保留首次出现的块或打上降权标签。

## 七、面试追问与反模式拆解

![数据入库清洗的三大常见反模式与避坑分析](/images/content-rebuild/45bbb6e776751b9f/fig-6.png)

### 追问 1：既然很多大模型已支持 32k 甚至 128k 上下文，为什么不直接把切分窗口设成 2000 Token 大块，免去父子块映射的复杂度？

**回答要点**：
大模型上下文窗口变大，解决的是“单次能吃下多少内容”，并没有解决“向量检索如何精准召回”。
1. **语义稀释**：当文本块达到 2000 Token 时，它往往涵盖了背景介绍、具体配置、排障流程等多个不同主题。基于双塔的 Dense Embedding 输出的是固定维度（如 1024 维）的向量，多主题混杂会导致该向量成为各个主题的折中表示，面对用户具体而精准的短查询（如“同步超时重试几次？”），向量相似度得分会被平均化拉低，导致首轮召回失败。
2. **存储与计算成本**：大窗口分块若做 Overlap，会显著增加向量库的体积与每次计算相似度的开销。
因此，小块负责空间对齐与检索召回，父块负责提供生成所需的完整上下文，这种解耦在长上下文时代仍然有效。

### 追问 2：如果在清洗阶段遇到大量扫描版文档或不可选中的纯图片，应该如何接入流水线？

**回答要点**：
工程落地中避免对所有 PDF 页面一律调用昂贵的多模态大模型或全图 OCR，应设计**分级过滤漏斗**：
1. **首选原生文本流**：利用解析库探测 PDF 是否内嵌文字层。若页面有效字符数大于设定阈值（如每页大于 50 个非空字符），说明是正常电子版，走轻量版面解析。
2. **无文字层路由到 OCR**：仅当页面内嵌文字过少或不存在时，才将该页转为图像，调用 OCR 引擎（如 PaddleOCR、Tesseract 或云端接口）。
3. **区域级精准识别**：先通过轻量版面分析模型（如识别文字框、表格框、插图框），只对文字框和表格框提取图片送入 OCR，跳过纯装饰性底图或图标，降低 OCR 调用量与算力消耗。
4. **置信度校验**：对 OCR 输出的平均置信度进行检查，低于阈值（如 0.6）的页面转入人工复核或告警队列，避免低质识别文本污染知识库。

### 常见反模式清单

| 常见反模式 | 产生后果 | 正确工程做法 |
| :--- | :--- | :--- |
| **无脑设置 50% Overlap** | 向量库体积翻倍，Top-K 召回结果被同义且几乎完全重叠的相邻切块占满 | 优先使用 Markdown 语法树与自然段落分块，配合父子块架构解耦检索与生成 |
| **丢弃元数据（Metadata）** | 切块只存文本，无法进行多租户隔离、时间过滤、版本剔除，大模型回答无法给出精准引用源 | 切块时显式保留并写入 `doc_id`、`page_no`、`title_path`、`source_url` 和更新时间戳 |
| **仅依据文件后缀判定类型** | 上传改了扩展名的文件（如将损坏的 zip 改为 `.txt`）导致解析脚本异常崩溃 | 基于二进制文件头部魔数（Magic Number，如 `python-magic`）识别真实 MIME 类型后再分发解析器 |
