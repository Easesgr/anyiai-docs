当用户反馈“模型回答不准确”时，很多开发者的第一反应是去改提示词（Prompt）或者直接换更大的模型。这种做法往往费时且无法定位根因。大模型的最终输出由整个应用链路共同决定，任何一个前置节点的输入变形或数据缺失，都会导致回答跑偏。

排查这一问题的标准工程方法，是沿着数据流向，将整条链路拆解为可观测、有日志记录的分层漏斗进行逐级定位。

为了便于理解，我们用一个电商智能客服的具体场景贯穿全文：
> 用户在对话中询问：“**退货运费谁来出？**”
> 实际业务规则为：“**商品质量问题商家承担运费；七天无理由退货由买家自行承担。**”
> 线上模型却错误回答：“**所有退货运费均由平台全额垫付。**”

---

## 面试标准回答：分类界定与四层漏斗排查法

在面试中被问及“如何排查和优化模型回答不准确”时，建议先给分类标准，再口述排查漏斗，最后说明如何防止二次退化：

> **面试口述参考**：
> “排查模型回答不准确，我会分为三步：
> 1. **错误类型分类**：先将问题区分为**事实性错误**（与既有事实或参考文档冲突）、**逻辑推理错误**（计算颠倒或条件推导中断）和**指令遵循违背**（未遵守指定格式或输出限制）。
> 2. **四层漏斗定位**：沿着请求链路自上而下排查：
>    - **意图层**：检查多轮对话上下文污染、代词指代不明与意图漂移；
>    - **知识检索层（RAG）**：查看日志中的召回切片，排查检索未命中、切片冲突或引入高噪无关内容；
>    - **上下文组装层**：检查是否有静默超长截断、系统指令与上下文规则冲突，以及关键信息深埋导致的中间遗忘；
>    - **模型解码层**：固定随机种子并将 Temperature 降至 0，排除随机采样干扰，判断是否达到基座模型自身的能力上限。
> 3. **沉淀回归用例**：将确认的 Bad Case 补充进基准测试集（Golden Dataset），在后续优化提示词或检索策略时运行自动化回归测试，避免‘修好一个引入三个’。”

![大模型错误输出的三大类型与排查优先级](/images/content-rebuild/4b83820290da88d1/fig-1.png)

如图所示，排查前先明确问题类型。如果用户反馈的是“没有按要求输出 JSON 格式”，这属于指令遵循违背，直接去改知识库检索策略就找错了方向。

## 第一层排查：用户输入与意图解析

排查的第一站，必须是**系统实际接收到的原始输入**，而不是终端用户看到的那句话。

在电商客服例子中，如果这是单轮对话，用户直接问“退货运费谁来出？”，问题本身是清晰的。但如果是多轮会话：
- 第一轮：用户说“我收到的衣服袖子脱线了”。
- 第二轮：用户问“退货运费谁来出？”

如果系统缺少多轮改写模块，直接把“退货运费谁来出？”作为独立查询词去检索，检索系统无法得知“衣服脱线（属于质量问题）”这一前提，导致下游检索召回了“七天无理由退货说明”，从而给出了错误答案。

### 常见意图层缺陷
1. **代词与省略指代不清**：输入包含“它”、“这款商品”、“上一笔订单”，缺乏前置的 Query 改写（Query Rewriting）模块进行指代消解。
2. **多轮历史过度堆叠**：直接将历史 10 轮对话全量拼接入模型输入，历史中用户过去的错误陈述、废弃纠错内容变成了当前推理的干扰噪声。
3. **意图漂移**：多轮对话过长，导致初始系统设定的角色任务与边界被后续会话内容冲淡。

```python
# 意图层排查示例：检查多轮改写是否丢失关键条件
def inspect_intent_rewrite(raw_query: str, chat_history: list[dict]) -> dict:
    # 1. 检查当前输入是否存在依赖上下文的代词或省略
    pronouns = ["它", "这个", "运费", "上一件"]
    needs_rewrite = any(p in raw_query for p in pronouns)
    
    # 2. 模拟改写逻辑
    rewritten_query = rewrite_query(raw_query, chat_history)
    
    # 验收准则：改写后的句子必须是自包含的事实查询
    return {
        "raw_query": raw_query,
        "rewritten_query": rewritten_query,
        "is_independent": "质量问题" in rewritten_query if "脱线" in str(chat_history) else True
    }
```

![用户输入与多轮对话意图污染排查流程](/images/content-rebuild/4b83820290da88d1/fig-2.png)

若排查发现改写后的 Query 确实丢失了“衣服质量问题”的前置条件，问题根因就定位在意图解析层，无需变动底座模型或检索向量库。

## 第二层排查：外部知识注入与 RAG 链路

如果系统接入了知识库（RAG 架构），绝大多数事实性错误都出自知识检索环节。

排查时，应调取该次请求在系统后台落盘的 **Trace 日志**，直接核对组装进 Prompt 的 `context` 字段，核查检索器究竟给模型喂了什么资料：

1. **检索未命中（Retrieval Miss）**：知识库里确实有运费规则，但因为分块切分过大、向量相似度计算偏差或关键词未覆盖，召回的前 Top-K 个切片全是“商品包装规范”、“发货时效”，根本没有运费规则。关于检索召回失效的专门定位，可参考 [/interview/high-freq-scenarios/rag-retrieval-failure.md](/interview/high-freq-scenarios/rag-retrieval-failure.md)。
2. **切片冲突与版本未清理**：知识库中同时并存着《2021年平台运费补贴规则》（旧规则：平台垫付）和《2024年退换货规范》（新规则：商家或买家承担）。检索把新旧两个版本都塞进了上下文，且未标注版本时间，模型无法判断真伪，只能根据内部先验偏好随机挑选一条。
3. **切片粒度过碎（Chunking Defect）**：文档被机械按每 200 字切块，正好把“若因质量问题产生的运费”切在块 A 尾部，把“由商家全额承担”切在块 B 开头，导致单块内容失去完整逻辑因果。

![RAG检索链路故障分流决策树](/images/content-rebuild/4b83820290da88d1/fig-3.png)

如决策树所示：如果日志中 `context` 没有任何相关规则，责任在检索系统；如果 `context` 已经给出了正确的运费规则，但模型依然回答“平台垫付”，排查流程才继续向下流动至组装与解码层。相关分流可参考 [/interview/high-freq-scenarios/rag-answer-wrong.md](/interview/high-freq-scenarios/rag-answer-wrong.md) 与 [/llm-100/rag/rag-wrong-answers.md](/llm-100/rag/rag-wrong-answers.md)。

## 第三层排查：提示词与上下文组装

当知识检索成功返回了正确段落，这批段落如何组装进最终的提示词，直接影响模型的注意力分布与阅读结果。

1. **静默截断（Silent Truncation）**：系统通常会设置单次请求的最大输入 Token 阈值。如果代码实现为“从后往前截断”或未做超长告警，当检索内容与历史会话过多时，正好把末尾的关键运费规则切除了，导致送给模型的内容里缺少该规则。
2. **指令与文档规则冲突**：系统提示词中写了“请严格根据常识判断”，文档里写了“请忽略其他常识，按本平台特例规则执行”，互相打架的指令会显著降低小参数量模型的指令遵循率。
3. **中间遗忘效应（Lost in the Middle）**：长文本评测实证表明，当关键证据位于上下文开头或末尾时，模型提取并正确回答的概率更高；当核心切片深埋在长上下文正中间时，问答任务的准确率往往呈现明显的 U 型下降。这是一种实证观察到的位置偏差现象，而非自注意力机制在物理上对中间位置失去权重。

![上下文组装中的截断与中间遗忘效应机制图](/images/content-rebuild/4b83820290da88d1/fig-4.png)

排查这一层时，务必导出**网关最终发送给大模型 API 的完备 Payload 字符串**。检查截断发生在哪一个位置，关键事实是否被夹杂在冗余文档正中间。

## 第四层排查：模型参数与解码配置

如果排查确认前三层均正常：用户意图清晰、检索切片准确无冲突、组装后的上下文完整且未被截断，但模型给出的结论依然南辕北辙，此时必须进入模型与解码层排查。

### 排除随机采样干扰
线上推理通常会设置采样参数，如 $Temperature = 0.7$ 或 $Top\text{-}P = 0.9$。在这些设置下，自回归模型每一步不是取概率最高（argmax）的 Token，而是依照概率分布进行多项式采样。
- 这意味着：同一句话输入进去，10 次调用可能有 8 次回答正确，2 次由于随机采样选到了概率较低的词，进而引发连锁推导偏差。
- **排查动作**：将参数强制调整为 $Temperature = 0$（在绝大多数框架中退化为确定性的贪心解码，Greedy Search），并固定随机种子（Seed）。在相同的输入下运行排查，消除采样发散。

![固定解码参数排查随机性的实验对比](/images/content-rebuild/4b83820290da88d1/fig-5.png)

如果在 $Temperature = 0$ 下模型能够稳定输出正确答案，说明错误来自过高的采样温度导致的发散，应当针对需要精确事实的问答场景下调线上温度；如果在 $Temperature = 0$ 下模型依然生成错误内容，则说明系统触碰到了**基座模型自身的能力瓶颈**（例如逻辑推理步数过长、多约束冲突处理失败，或基座预训练知识与上下文证据发生严重先验冲突）。

## 建立 Bad Case 分流与自动化回归防护

单次定位修复并不意味着工作结束。大模型系统最常见的工程陷阱是：为了修好“退货运费”的提示词，微调了指令模板，结果导致另外十个原本正常的业务提问发生格式错乱或拒答。

防止系统退化的标准做法是建立回归评测闭环：

1. **Bad Case 结构化入库**：每个线上投诉 case 必须记录原始输入、检索快照、当时模型参数、错误回答，并打上排查后的归因标签（如 `Intent_Drift`、`Retrieval_Miss`、`Context_Truncated`、`Sampling_Variance`）。
2. **构建基准金标集（Golden Dataset）**：筛选涵盖各业务分支的典型 Case，由人工或严谨的业务规则标定标准答案（Ground Truth），包含事实判定与格式判定标准。
3. **更新后的门禁回归**：每当调整提示词结构、更新检索召回算法、更换 Embedding 模型或更新切分策略时，在金标集上自动化批量执行评估，核验核心指标（如准确率、格式遵循率）是否发生劣化。

## 面试追问与深度辨析

### 追问 1：如果模型给出的答案里包含外部知识库完全没有的实体或结论，如何判定是模型本身“产生幻觉”，还是由于上下文截断导致的“知识先验脑补”？

**回答要点**：
核对该请求**实际发送给模型 API 的最终 Payload 日志**：
- 如果日志显示正确的知识切片在组装阶段因为 Token 限制被截断丢弃了，模型由于缺少约束，只能调用自身预训练参数里的记忆去回答，这属于**截断诱发的先验补齐**，修复手段是优化前端截断规则和精简 Prompt。
- 如果日志确认完整、无矛盾的事实切片已经喂给了模型，且提示词中明确说明了“仅依据所给资料回答”，模型依然输出了外部实体，这属于**上下文约束下的模型事实性幻觉**或**基座先验反噬**，需通过增强提示词约束权重、调整解码温度或更换推理能力更强的基座模型来解决。

### 追问 2：为什么很多团队一遇到回答不准就急于去微调（SFT）模型，这种做法有哪些风险？

**回答要点**：
将回答不准简单归咎于“模型没有微调过”是常见的工程误区：
1. **更新知识的成本极高且容易过拟合**：业务规则（如退换货政策、商品价格）具有高频变动特性。微调模型需要准备标注数据、重新训练、评测与部署，周期以天或周计；而更新 RAG 知识库只需更新切片索引，秒级生效。
2. **微调无法保证 100% 事实准确**：微调主要改变的是模型的表达风格、输出格式以及领域推理习惯，很难精确修正参数权重内部的事实记忆，甚至可能诱发灾难性遗忘。
3. **最佳实践分工**：事实性更新优先使用知识库（RAG）；只有当任务涉及特定的输出格式（如限定的 DSL）、独特的推理链路模式，或小参数模型经过详细提示词仍无法遵循指令时，才考虑采用微调手段。
