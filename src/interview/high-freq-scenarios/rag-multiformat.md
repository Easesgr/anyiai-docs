在知识库系统中，真实的技术文档、财务报告和系统规范很少是纯文本。一份典型的《支付网关重构与对账系统设计文档》，通常同时包含跨页的商户交易清算表格、微服务鉴权架构图以及处理退款的核心代码片段。

如果直接沿用纯文本的固定长度切分（例如每 500 字符切一段），表格的表头会与数据脱节，架构图中的箭头流向无法进入文本向量，代码则会被从循环或条件分支中间截断。面试官考察这一问题时，重点在于评估应聘者能否针对不同模态数据的组织特点，设计出兼顾解析准确率与计算成本的处理流程。

## 面试速答：两分钟口述回答

面试中遇到“混排文档如何处理”时，可以按照以下三个层次口述：

![多格式混排文档的三大物理结构破坏与对应解析流水线](/images/content-rebuild/3f4160648c5d1fc2/fig-1.png)

1. **核心矛盾**：常规纯文本切分会破坏非连续文本的内在逻辑——表格丢失行列对应关系，图片丢失视觉拓扑与流程走向，代码丢失缩进和作用域依赖。
2. **针对性处理方案**：
   - **表格**：解析为 HTML 或 Markdown 格式，把合并单元格还原；单行切分时采用“列名: 单元格内容”的键值拼接，让每一行自包含上下文；对大表做全局摘要供向量检索，针对统计汇总类问题路由到 Text-to-SQL 或代码计算引擎。
   - **图片**：按类型分流。扫描版文字和单据走轻量 OCR；系统架构图和流程图调用视觉大模型（VLM）生成包含节点、调用链和异常分支的结构化文本摘要（Caption），并将摘要与原图位置一同存入向量库。
   - **代码**：使用抽象语法树（AST）工具按函数或类完整切分，并在切片头部补齐文件路径、类声明和依赖引入（Import），防止变量与调用关系脱节。
3. **检索与融合**：采用多路检索。对精确符号和函数名用词法检索（BM25），对概念解释和架构流程用稠密向量，通过加权倒数排名（Weighted RRF）融合打分，避免单一检索方式在混合内容中失准。

## 复杂表格处理：表头补齐与双路检索

在《每日商户交易清算明细表》中，如果表格跨页或者行数超过单个分块上限，第 30 行可能只显示 `2024-03-01 | 商户B | 120,000 | 0.006 | 已结算`。若直接截断，文本中没有列名，向量模型无法识别 `120,000` 是交易金额、退款金额还是流水号。

![复杂表格的提取、表头补齐与双路表征机制](/images/content-rebuild/3f4160648c5d1fc2/fig-2.png)

针对表格数据，通常采用结构化还原、单行键值序列化与双路处理机制：

### 1. 结构化解析与单元格还原
利用版面分析工具（如基于规则的 pdfplumber、或开源表格识别模型）提取表格边界，将其转为 HTML `<table>` 或标准 Markdown 表格。对于具有 `rowspan`（跨行）或 `colspan`（跨列）的合并单元格，在内存中将父级表头的文字复制并填充到下属的每一个子单元格中，确保每个单元格在底层都有明确的属性归属。

### 2. 行级键值序列化
当表格无法完整放入单个分块时，需要拆解为行。拆解时不能只保留原始数值，而应将列名与字段值拼成自解释的文本行：

```text
[清算明细记录 - 行 30]
结算日期: 2024-03-01 | 商户名称: 优选生鲜 | 交易结算额(元): 120,000 | 手续费率: 0.6% | 结算状态: 已结算
```

这样即使单行被切开，文本向量模型也能根据完整的字段名匹配到用户的查询意图（如“优选生鲜 3 月 1 日结算额”）。

### 3. 定位检索与统计计算分流
表格问答存在两种常见类型：
- **单点定位类**：“优选生鲜 3 月 1 日的手续费率是多少？”这类问题依靠上述序列化文本做向量或词法检索即可命中。
- **计算聚合类**：“所有商户中 3 月份结算总额最高的前三家总计多少钱？”如果仅靠检索文本段落塞给大语言模型，模型在长上下文下容易发生算术计算错误。

针对计算类问题，工程上推荐配置**双路表征**：
- 离线时提取表格元数据并生成文字摘要（例如“2024年3月商户结算明细表，含结算额、费率、状态等指标”），将摘要存入向量库用于召回该表。
- 将原始表格数据同步转存为结构化数据库（如 SQLite 或 DuckDB 表）。当用户意图被识别为计算汇总时，由大模型生成 SQL 语句在数据库中执行，返回精确计算结果。

## 图像与图表处理：分类路由与结构化描述

文档中的图像信息密度差异极大。一份发票扫描件需要提取文字，而案例中的《支付核心服务请求鉴权与分布式事务时序图》则需要理解连线方向与调用步骤。

![图像双轨分流处理管道：OCR 与视觉模型协同表征](/images/content-rebuild/3f4160648c5d1fc2/fig-3.png)

生产中通常通过分类器对图像进行双轨分流：

### 1. 纯文字截图与扫描单据走 OCR
对于资质证明、合同扫描件或纯文字截图，直接调用轻量级 OCR 工具提取文本。提取时保留文字坐标（Bounding Box），按自然阅读顺序拼接成文字段落，直接并入主文本切片中。

### 2. 流程图与系统架构图走视觉模型描述（Captioning）
架构图中的文字通常只有“网关”、“Redis”、“500ms 超时”，文字本身无法体现先后顺序和条件分支。

对于此类图表，在离线构建阶段调用视觉模型（如 Qwen-VL 等多模态模型），输入图片及其在正文中的上下文（如正文中的“图 3 所示为鉴权熔断机制”），生成遵循固定格式的结构化描述：

```markdown
【图表名称】支付核心服务请求鉴权与事务时序图
【核心模块】客户端、API 网关、Redis 鉴权中心、支付核心系统
【调用步骤】
1. 客户端发起 HTTPS POST 请求至 API 网关；
2. API 网关向 Redis 校验令牌，超时阈值设为 200ms；
3. 校验通过后，网关向支付核心系统发起 RPC 调用；
4. 若 Redis 超时未响应，网关触发本地降级，向客户端返回 504 错误。
```

将上述描述文本作为该图片的检索代理存入向量库，并在元数据中关联原图的存储链接（OSS URL）。当用户询问“网关连不上 Redis 会怎样”时，检索阶段命中该段描述，模型生成答案的同时还可以把原图链接提供给用户查阅。

## 代码块处理：基于 AST 的语义范围保护

在处理案例中的 `RefundService` 代码时，若按字符数硬切，可能会将一个包含事务处理的 `try...except` 块拦腰切断，下半段只剩下变量赋值，丢失了前置的函数名和参数类型定义。

![基于抽象语法树（AST）的代码语义分块与上下文补全机制](/images/content-rebuild/3f4160648c5d1fc2/fig-4.png)

针对代码文件，推荐使用抽象语法树（如利用 `tree-sitter`）识别代码的语法结构，按逻辑单元切分：

### 1. 语法作用域分块
优先将独立的函数（Function）或类（Class）作为最小切分单元。如果某个函数内部逻辑过长，确实超出单块上限，切分点应选在顶层的分支语句（如主 `if-elif` 边界）之间，避免在嵌套表达式或循环体内部截断。

### 2. 上下文头部补充
被切开的代码切片需要补充必要的前置信息。在切片生成时，解析器可以提取文件路径、所属类名以及相关的导入语句，作为切片头部前缀：

```python
# [文件路径: services/payment/refund.py] 
# [所属模块: RefundService] 
# [依赖引用: from core.errors import InvalidStatusError; import stripe]

async def execute_refund(self, order_id: str, amount_cents: int) -> bool:
    """执行商户退款，校验当前订单状态"""
    order = await self.repo.get(order_id)
    if order.status != "SETTLED":
        raise InvalidStatusError("未结算订单不支持直接退款")
    return await self.gateway.refund(order.channel_id, amount_cents)
```

通过补充头部信息，当用户检索“RefundService 哪些状态不支持退款”时，切片即使不包含整个文件的全部代码，也能精准匹配类名与业务逻辑。

## 检索阶段：加权倒数排名（Weighted RRF）融合

混排文档处理完毕后，候选片段分布在不同的索引中：代码片段包含大量特定标识符（如 `InvalidStatusError`），架构图描述包含长句自然语言，表格摘要则指向结构化数据。

![混合多路检索路由器与加权倒数排名（Weighted RRF）融合架构](/images/content-rebuild/3f4160648c5d1fc2/fig-5.png)

如果单纯使用稠密向量，对精确定位报错类符号的效果有限；而单纯使用词法匹配（BM25），又无法理解架构图的语义描述。常见做法是采用多路检索配合加权倒数排名（Weighted RRF）：

在支持多路混合检索的系统中，加权倒数排名（Weighted RRF）的通用打分公式如下：

$$RRF\_Score(d) = \sum_{m \in M} w_m \cdot \frac{1}{k + r_m(d)}$$

其中：
- $M$ 是检索通道集合（例如稀疏词法通道与稠密向量通道）；
- $r_m(d)$ 是文档 $d$ 在通道 $m$ 中的检索排名（从 1 开始计数）；
- $k$ 是平滑常数（经典文献通常取 60，用于平滑各通道靠前名次的分值差距；若引擎实现未配置平滑项或 $k=0$，则退化为纯排名倒数）；
- $w_m$ 是赋予通道 $m$ 的相对权重（如 Qdrant v1.17+ 支持通过预取数组为不同检索分支配置权重系数）。

**权重调节示例**：
当检测到用户问题包含驼峰命名、报错代码或函数关键词（如 `execute_refund` 报错）时，可以将 BM25 通道的权重 $w_{\text{sparse}}$ 从 1.0 提高到 2.5；当用户询问“系统降级逻辑是什么”等概念性问题时，将稠密向量通道权重 $w_{\text{dense}}$ 设为更高，从而自适应地融合排名前列的候选结果。

## 工程落地：性能、成本与降级设计

全量调用视觉大模型和深层解析工具会带来显著的离线构建耗时与调用开销。工程落地需要根据内容特征做阶梯式降级：

![多模态 RAG 解析的工程时延、成本矩阵与降级分支决策树](/images/content-rebuild/3f4160648c5d1fc2/fig-6.png)

| 文档元素 | 默认低成本路径 | 深度解析路径 | 触发深度解析的条件 |
| :--- | :--- | :--- | :--- |
| **常规表格** | 基于规则提取为 Markdown / 键值序列 | VLM 表格重构 + 结构化转存 | 存在复杂嵌套合并单元格或版面识别错位 |
| **文档配图** | 轻量本地 OCR 识别文字 | 多模态大模型生成拓扑 Caption | 图像长宽比较均衡、文字密度低且包含几何连线框 |
| **程序代码** | 基于缩进与空行的规则切分 | 基于 Tree-sitter 的 AST 节点切分 | 规则切分导致缩进不匹配或语法解析失败 |

通过此分类机制，仅有真正复杂的图表和嵌套代码会触发高开销模型，大部分常规文本与扁平表格均在本地轻量解析完成，从而在保持多模态信息提取质量的同时控制索引构建成本。

## 面试追问深度准备

### 追问 1：跨页表格导致表头丢失，在工程上如何稳定拼接？
**回答思路**：
1. **坐标对齐校验**：利用 PDF 解析工具获取表格边界矩形（Bounding Box）。若第 N 页底部的表格横向边界与第 N+1 页顶部的表格横向边界重合度高于阈值，判定二者属于同一张连续表格。
2. **重复表头检测**：检测次页首行文本是否与首页表头文本完全一致。如果是，直接去除次页冗余表头；如果次页直接紧接着数据行，则把首页保存的列名集合主动补入次页数据的头部，再执行后续的序列化操作。

### 追问 2：视觉大模型在给架构图生成 Caption 时产生幻觉，如何防范？
**回答思路**：
1. **引入正文图注做上下文约束**：调用视觉模型时，必须将该图片在文档正文中前后对应的解释段落一并传入，要求模型仅根据正文提及的名词和图中可见箭头进行概括。
2. **名词白名单校验**：提取 Caption 中的技术组件名，校验其是否在正文词表或系统词典中出现。若出现大量陌生实体，降低置信度并回退到仅使用 OCR 提取到的纯文字。

### 追问 3：为什么不直接把几百页 PDF 原生塞进长上下文多模态大模型？
**回答思路**：
1. **首字延迟与吞吐受限**：多页高分辨率图像会消耗巨量 Vision Tokens，导致首字响应延迟（TTFT）显著增加，并发成本过高。
2. **注意力分散与细节丢失**：多模态模型在超长上下文中对微小文字或嵌套数字的关注度会下降，容易出现长文本位置偏差（Lost in the Middle）。
3. **缺乏精细权限管理**：企业级知识库往往需要对不同部门控制特定表格或代码模块的查阅权限。端到端直接塞全量文档无法做到段落级的权限过滤与引用溯源。
