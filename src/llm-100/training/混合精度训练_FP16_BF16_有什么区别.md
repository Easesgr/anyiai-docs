### 学习目标与实验设计

在大模型训练中，“混合精度训练”（Mixed Precision Training）是指在前向计算和反向传播中使用 16 位浮点数（FP16 或 BF16）来降低显存占用并提升计算速度，同时在优化器更新阶段维护 32 位浮点数（FP32）权重以保证参数更新精度的方法。

很多开发者在配置训练参数时都会面临选择：该用 FP16 还是 BF16？为什么 FP16 必须配合 `GradScaler` 才能训练，而 BF16 通常不需要？如果在旧显卡上强行开 BF16 会发生什么？

本讲通过一个可以在单卡运行的 PyTorch 实验，贯穿解决以下三个具体问题：
1. 动手构建一个包含连续微弱梯度的模型，观察 FP16 浮点格式下的数值下溢（Underflow）与梯度归零现象。
2. 接入 PyTorch 的 `torch.cuda.amp.GradScaler`，观察其在检测到溢出时的“跳过更新”与“缩放因子回退”状态流转。
3. 将精度切换为 BF16，对比梯度保留情况，解释显卡架构对精度的硬件限制，并梳理训练中突发 NaN/Inf 时的排查流程。

### 浮点格式差异与 FP16 梯度下溢复现

要理解为什么会有下溢，首先需要明确 FP16 与 BF16 的结构差异：
- **FP16（半精度浮点）**：由 1 位符号位、5 位指数位和 10 位尾数位组成。因为指数位只有 5 位，其正数表示范围较窄，规格化数约为 $6.10 \times 10^{-5}$ 到 $65504$。当数值小于规格化下限时，会进入次规格化数区间（最小约 $5.96 \times 10^{-8}$），而在 GPU 计算中为了保证执行速度，通常会采用刷零（Flush To Zero, FTZ）策略，导致微小数值极易直接被截断为 `0.0`。
- **BF16（Bfloat16 脑浮点）**：由 1 位符号位、8 位指数位和 7 位尾数位组成。它的指数位与 FP32 完全相同，因此动态表示范围与 FP32 一致（下限可达约 $1.18 \times 10^{-38}$，上限约 $3.39 \times 10^{38}$），代价是尾数位从 10 位缩减为 7 位，相对精度稍低。

我们构造一个简单的“深度缩放网络”。网络由 8 个连续线性层构成，权重初始化故意偏小，反向传播时链式法则会使梯度逐层衰减，最终让输入层的梯度落在 $10^{-6}$ 到 $10^{-8}$ 之间。

```python
import torch
import torch.nn as nn

assert torch.cuda.is_available(), "本练习需要 CUDA 设备以支持硬件浮点与 AMP 特性"
device = torch.device("cuda")

class UnderflowProbeNet(nn.Module):
    def __init__(self, depth=8):
        super().__init__()
        self.layers = nn.ModuleList([
            nn.Linear(64, 64, bias=False) for _ in range(depth)
        ])
        # 初始化较小权重，使前向与反向逐层衰减
        for layer in self.layers:
            nn.init.orthogonal_(layer.weight, gain=0.35)

    def forward(self, x):
        for layer in self.layers:
            x = layer(x)
        return x

model = UnderflowProbeNet(depth=8).to(device)
x = torch.randn(32, 64, device=device)
```

在不使用任何损失缩放（Loss Scaling）的情况下，直接在 FP16 精度上下文中运行反向传播：

```python
model.zero_grad()
with torch.autocast(device_type="cuda", dtype=torch.float16):
    out = model(x)
    loss = (out ** 2).sum() * 1e-4  # 微弱损失信号

loss.backward()

first_layer_grad = model.layers[0].weight.grad
print("未缩放下 FP16 输入层梯度范数:", first_layer_grad.norm().item())
print("输入层梯度是否完全为零:", torch.all(first_layer_grad == 0).item())
```

运行上述代码后，终端输出：
```text
未缩放下 FP16 输入层梯度范数: 0.0
输入层梯度是否完全为零: True
```

![图1：FP16梯度在深度缩放算子下的逐层衰减与下溢为零](/images/content-rebuild/cf6e5dd1fd384dbc/fig-1.png)

如图 1 所示，在链式传播过程中，梯度随着网络深度逐层缩小。当梯度数值穿透 FP16 的表达区间后，硬件将其直接舍入为零。这会导致靠近输入的浅层网络完全接收不到梯度更新信号，在大模型训练中表现为浅层参数更新迟缓甚至停滞。

### 观察 PyTorch GradScaler 的动态调整过程

为了解决 FP16 的下溢问题，业界普遍采用“动态损失缩放”（Dynamic Loss Scaling）。PyTorch 提供了 `torch.cuda.amp.GradScaler` 工具，其工作过程分为三个阶段：
1. **前向放大**：在反向传播前将损失乘以缩放系数 $S$（默认初始值为 $2^{16} = 65536.0$），反向传播计算出的梯度也会放大 $S$ 倍，从而避开 FP16 的下溢区间。
2. **梯度还原（Unscale）**：在优化器执行更新前，将参数梯度除以 $S$ 还原为真实大小。
3. **溢出检测与动态调整**：检查还原后的梯度中是否存在 `Inf` 或 `NaN`。
   - 若存在非法值（说明 $S$ 设得过大导致 FP16 上溢），则**跳过当前步的参数更新**，并将缩放因子 $S$ 乘以退避因子（默认 `backoff_factor=0.5`，即数值减半）。
   - 若连续若干步（默认 `growth_interval=2000` 步）所有梯度均正常，则将 $S$ 乘以增长因子（默认 `growth_factor=2.0`，即数值翻倍），尝试寻找更大的数值表达空间。

我们通过以下代码追踪 `GradScaler` 的内部状态流转。为了在短时间内观察到调整，我们将 `growth_interval` 设为 3，并在第 4 步人为注入一个极大的损失，制造溢出：

```python
from torch.cuda.amp import GradScaler

model = UnderflowProbeNet(depth=8).to(device)
optimizer = torch.optim.SGD(model.parameters(), lr=0.01)
scaler = GradScaler(init_scale=65536.0, growth_interval=3, backoff_factor=0.5)

print("=== 开始观察 GradScaler 行为 ===")
for step in range(1, 8):
    optimizer.zero_grad()
    
    with torch.autocast(device_type="cuda", dtype=torch.float16):
        out = model(x)
        factor = 1e6 if step == 4 else 1e-4  # 第 4 步注入极大损失
        loss = (out ** 2).sum() * factor

    # 1. 放大损失并反向传播
    scaler.scale(loss).backward()
    current_scale = scaler.get_scale()
    
    # 2. scaler.step 内部执行 unscale 并探测 Inf/NaN
    scaler.step(optimizer)
    
    # 3. 更新缩放因子状态
    scaler.update()
    new_scale = scaler.get_scale()
    
    probe_grad = model.layers[0].weight.grad
    grad_norm = probe_grad.norm().item() if probe_grad is not None else 0.0
    
    print(f"Step {step} | 初始Scale: {current_scale:<8.1f} | "
          f"更新后Scale: {new_scale:<8.1f} | 梯度范数: {grad_norm:.6e}")
```

运行后输出轨迹记录：
```text

Step 2 | 初始Scale: 65536.0  | 更新后Scale: 65536.0  | 梯度范数: 1.428290e-06
Step 3 | 初始Scale: 65536.0  | 更新后Scale: 131072.0 | 梯度范数: 1.428268e-06
Step 4 | 初始Scale: 131072.0 | 更新后Scale: 65536.0  | 梯度范数: inf
Step 5 | 初始Scale: 65536.0  | 更新后Scale: 65536.0  | 梯度范数: 1.428245e-06
Step 6 | 初始Scale: 65536.0  | 更新后Scale: 65536.0  | 梯度范数: 1.428223e-06
```

![图2：GradScaler 动态探测梯度异常并调整缩放因子的状态流转](/images/content-rebuild/cf6e5dd1fd384dbc/fig-2.png)

结合代码输出与图 2 可以看出：
- 在 Step 1 和 Step 2，损失被放大 65536 倍后，输入层梯度从下溢区间被拉入有效浮点范围，梯度还原后成功获得非零值（约 $1.428 \times 10^{-6}$），模型正常更新。
- Step 3 满足连续 3 步正常的条件，`scaler.update()` 将缩放因子增加到 `131072.0`。
- Step 4 出现梯度上溢，数值变为 `inf`。`scaler.step(optimizer)` 探测到异常后，直接跳过了当前的参数更新，`scaler.update()` 将缩放因子减半回退到 `65536.0`，并重置正常步数计数器。

**当训练出现持续异常时的现象**：
若模型出现持续梯度爆炸，在连续步数中均检测到 `Inf` 或 `NaN`，系统会发生以下连锁反应：
1. 权重更新持续跳过，模型停止学习。
2. 缩放因子在每一步都被乘以 0.5，数值呈指数级下降（$65536 \to 32768 \to \dots \to 1.0 \to 2^{-n}$）。
3. 当缩放因子小于 1.0 时，不仅无法防范上溢，反而会人为压缩梯度，导致正常的微小梯度重新发生下溢截断，训练彻底失去推进能力。

### 对比实验：切换 BF16 与硬件适用条件

接下来在相同的网络和微弱损失条件下，将精度切换为 `torch.bfloat16`。

由于 BF16 拥有与 FP32 完全相同的 8 位指数位，其表示下限可达 $1.18 \times 10^{-38}$，在常规训练中几乎不会发生下溢，因此无需使用 `GradScaler`：

```python
model_bf16 = UnderflowProbeNet(depth=8).to(device)
optimizer_bf16 = torch.optim.SGD(model_bf16.parameters(), lr=0.01)

print("=== 开始观察 BF16 行为 ===")
for step in range(1, 5):
    optimizer_bf16.zero_grad()
    
    with torch.autocast(device_type="cuda", dtype=torch.bfloat16):
        out = model_bf16(x)
        loss = (out ** 2).sum() * 1e-4

    # BF16 不需要调用 scaler.scale()
    loss.backward()
    optimizer_bf16.step()
    
    probe_grad = model_bf16.layers[0].weight.grad
    print(f"BF16 Step {step} | 梯度范数: {probe_grad.norm().item():.6e} | "
          f"梯度是否为零: {torch.all(probe_grad == 0).item()}")
```

控制台输出：
```text
=== 开始观察 BF16 行为 ===
BF16 Step 1 | 梯度范数: 1.427982e-06 | 梯度是否为零: False
BF16 Step 2 | 梯度范数: 1.427958e-06 | 梯度是否为零: False
BF16 Step 3 | 梯度范数: 1.427931e-06 | 梯度是否为零: False
BF16 Step 4 | 梯度范数: 1.427909e-06 | 梯度是否为零: False
```

![图3：FP16与BF16在极端小梯度区间的数值保留与梯度有效性对比](/images/content-rebuild/cf6e5dd1fd384dbc/fig-3.png)

对比图 3 中的数据表现：
1. **动态范围**：BF16 无需任何外部放大逻辑，就能直接保留 $10^{-6}$ 的梯度值，避免了跳步与维护缩放因子的开销。
2. **精度损失**：对比 Step 1 中 FP16 的 `1.428312e-06` 与 BF16 的 `1.427982e-06`，两者存在微弱的尾数差异。这是因为 BF16 只有 7 位尾数（十进制约 2~3 位有效数字），低于 FP16 的 10 位尾数（十进制约 3~4 位有效数字）。但在依赖大批量样本均值与动量统计的深度学习训练中，模型对尾数精度的微小偏差较为不敏感，反而对数值是否越界更加脆弱，因此 BF16 成为当前主流大模型训练的首选。

**硬件支持边界**：
BF16 依赖显卡硬件架构的指令支持。NVIDIA 从 Ampere 架构（如 A100、RTX 30 系列，计算能力 8.0 及以上）才开始提供硬件级 BF16 Tensor Core。
如果在不支持 BF16 的旧架构显卡（如 V100、T4 或更早的显卡）上强制指定 `torch.bfloat16`，会遇到两类工程问题：
1. **速度大幅下降**：底层驱动无法调用硬件原生乘加单元，只能通过软件将 BF16 数据转回 FP32 计算后再转回，带来显存读写与格式转换开销，速度往往慢于纯 FP32 训练。
2. **底层算子报错**：现代高效算子库（如 FlashAttention）直接依赖特定硬件架构的指令编译。在旧硬件上执行涉及 BF16 的定制算子时，会直接抛出运行期错误（如 `CUDA error: no kernel image is available for execution on the device`）。因此在旧卡上，混合精度仍需选择 FP16 配合 `GradScaler`。

### 训练出现 NaN 或 Inf 时的排查步骤

即使使用混合精度，在训练过程中也可能因为初始化不当、学习率过大或输入脏数据导致数值崩溃。遇到 `NaN` 或 `Inf` 时，可按以下步骤排查。

![图4：训练中数值异常发生点的快速定位排查树](/images/content-rebuild/cf6e5dd1fd384dbc/fig-4.png)

#### 步骤一：定位发生阶段与具体算子
1. **判断前向还是反向**：
   - 若在 `loss.backward()` 之前，打印的 `loss.item()` 就已经是 `NaN`，说明前向计算已经溢出或发生除零。
   - 若前向 `loss` 数值正常，而在反向传播后参数梯度 `param.grad` 出现 `NaN/Inf`，说明问题出在反向传播或梯度计算。
2. **使用异常检测定位报错代码**：
   在复现阶段，可以开启 PyTorch 提供的自动求导异常检测上下文：
   ```python
   with torch.autograd.detect_anomaly():
       out = model(inputs)
       loss = criterion(out, targets)
       loss.backward()
   ```
   该工具会在产生非法浮点数的节点处直接抛出异常调用栈，指示出错的代码行（注意：开启该功能会大幅拖慢训练速度，仅用于单步调试排查，不可留在生产脚本中）。

#### 步骤二：排查常见代码陷阱

##### 1. 注意力 Softmax 的数值稳定性
计算注意力矩阵时需采用减去行最大值的数值安全写法（Safe Softmax）：
$$\text{Softmax}(z_i) = \frac{e^{z_i - \max(z)}}{\sum_j e^{z_j - \max(z)}}$$
若未做减最大值处理，在输入数值较大时，$e^{z}$ 会极快超过 FP16 的上限 65504，产生 `Inf`，进而导致后续运算全盘变成 `NaN`。

##### 2. 归一化层的微小常数 Epsilon
LayerNorm 或 RMSNorm 内部需要加上常数 $\epsilon$ 防止分母为零：
$$\text{RMSNorm}(x) = \frac{x}{\sqrt{\frac{1}{d}\sum_{i=1}^d x_i^2 + \epsilon}} \odot \gamma$$
在 FP32 中常设 $\epsilon = 10^{-12}$。但在 FP16 下，$10^{-12}$ 会发生下溢直接变成 `0.0`。一旦输入方差极小，分母就可能变为零导致除零错误。在混合精度训练中，归一化层的 $\epsilon$ 通常需要调大至 $10^{-5}$，或者让归一化算子强制运行在 FP32 精度下。

##### 3. 梯度裁剪的时序错误
如果使用 FP16 与 `GradScaler`，且代码中包含梯度裁剪（`clip_grad_norm_`），必须确保裁剪发生在**梯度还原（unscale）之后、参数更新（step）之前**。

![图5：梯度裁剪在 Scaler 梯度反缩放之后的正确调用时序](/images/content-rebuild/cf6e5dd1fd384dbc/fig-5.png)

时序对比如下：

```python
# ❌ 错误做法：在放大后的梯度上做裁剪
scaler.scale(loss).backward()
torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0) # 梯度仍处于放大 S 倍的状态
scaler.step(optimizer)
scaler.update()

# ✅ 正确做法：显式还原尺度后再裁剪
scaler.scale(loss).backward()
scaler.unscale_(optimizer)  # 将优化器管理的梯度除以 S 还原为真实数值
torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0) # 在真实尺度上裁剪
scaler.step(optimizer)      # 内部检测到已 unscale，直接执行检验与更新
scaler.update()
```
如果在还原前执行裁剪，由于当前梯度被人为放大了 $S$ 倍（如 65536 倍），计算得到的梯度范数会严重超标，导致所有参数梯度被过度压缩数万倍，模型将失去正常的参数更新能力。

### 本讲小结与练习

本讲通过动手实验梳理了混合精度训练中的核心数值机制：
- **FP16**：指数位较短（5 位），容易发生数值下溢，必须借助 `GradScaler` 进行动态放大与还原；但在旧卡上具备更好的原生兼容性。
- **BF16**：具备与 FP32 相同的指数位（8 位），原生避开了绝大多数下溢风险，免去了维护缩放因子的开销；但需要 Ampere 及以上架构显卡的硬件支持。
- **工程调试**：遇到 `NaN/Inf` 时，需根据发生阶段排查 Softmax 减最大值、归一化层的 $\epsilon$ 大小，以及 `unscale_` 与梯度裁剪的调用顺序。
