在学习了 [Agent 的核心组成：模型、记忆、工具和规划](/llm-100/agent-basics/Agent_的核心组成_模型_记忆_工具和规划.md) 与 [Agent 的 Memory 应该怎么设计？](/llm-100/agent-basics/Agent_的_Memory_应该怎么设计.md) 后，我们已经能够构建一个包含工具调用与状态记忆的独立智能体。但在处理链路长、工具多、输入数据量大的复杂任务时，单一 Agent 往往会出现准确率明显下降、选错工具或遗忘规则等现象。

多 Agent 系统（Multi-Agent System）常被通俗地比喻为“团队开会分工”。从工程实现看，多 Agent 的核心作用并非模拟社交行为，而是通过**切分上下文窗口与工具集合**，降低单个模型调用在单次推理中承担的信息负荷。本讲以一个线上运维排障的任务为贯穿案例，拆解单 Agent 的性能瓶颈，对比多 Agent 的上下文隔离收益，并分析其引入的通信延迟与级联错误风险。

![多 Agent 协作模式概览：从单实体过载到多实体职责解耦](/images/content-rebuild/8980b37fbdbabf3b/cover.png)

## 贯穿案例与单 Agent 的运行瓶颈

以一个典型的运维故障排查任务为例：系统收到服务器告警后，需要排查过去 1 小时内数万行的访问日志，找出恶意攻击的来源 IP，比对内部白名单库，决定是否调用防火墙封禁接口，并最终生成一份结构化的处理报告。

如果用一个单 Agent 独立完成全流程，它的运行环境通常由一个主循环构成：每次调用大模型时，把系统提示词、所有候选工具定义、当前对话历史和中间执行日志全部拼接到同一个上下文内。

```
+--------------------------------------------------------------+
| 单 Agent 运行栈                                               |
| 1. System Prompt (角色、合规准则、报告格式、安全红线...)     |
| 2. Tool Schemas (日志检索、白名单对比、防火墙配置、告警发送...) |
| 3. Message History (多轮交互、数万字原始日志、中间报错...)   |
+--------------------------------------------------------------+
                                |
                                v
             [LLM 面对过长输入：注意力分散、选错工具、遗忘初始约束]
```

随着任务推进，单 Agent 往往会在以下三个环节遇到限制：

### 1. 提示词膨胀与规则冲突
单个 Agent 如果要兼顾日志分析、合规审查、网络安全和文档排版，其系统提示词（System Prompt）就需要塞入每个环节的角色约束。当提示词过长且规则互有侧重时，大语言模型的指令遵循能力容易下降，出现忽略输出格式约束或放宽安全限制的情况。

### 2. 工具定义过多导致选择混淆
在 [Tool Calling 是什么？大模型如何调用工具？](/llm-100/agent-basics/Tool_Calling_是什么_大模型如何调用工具.md) 中我们讨论过，工具的名称、描述与参数模式（JSON Schema）会在每次调用前完整拼接至 Prompt 中。若挂载了十几个甚至数十个工具：
- 每次请求的输入 Token 开销显著增加；
- 功能接近的工具（例如“按时间段过滤日志”与“按关键字检索日志”）容易出现语义混淆，导致模型传入错误参数或调错工具。

### 3. 上下文污染与有效信息稀释
在 [Agent 为什么容易陷入死循环？](/llm-100/agent-basics/Agent_为什么容易陷入死循环.md) 与 [为什么记忆系统不能什么都存？](/frontier/agent-memory-system/memory-risks.md) 中提到，工具返回的观测值（Observations）常夹杂冗余数据。一万多行的服务器日志直接灌入会话历史后，用户最初下达的指令和核心约束在整个上下文中的比例急剧缩水，容易让模型在后续循环中出现目标漂移。

## 上下文隔离：多 Agent 的核心收益

应对上述问题的一种工程手段是**上下文隔离（Context Isolation）**：不再由一个 Agent 独占所有信息，而是按职责把任务拆分成独立的执行域，由不同的子代理（Subagent）在各自专属的上下文中运行。

### 上下文隔离的执行逻辑
在多 Agent 架构下，每个子任务被分配给特定职责的 Subagent：
- **独立的提示词**：每个 Subagent 只加载当前步骤需要的规则和指令，避免全局规则互相干扰。
- **最小权限工具集**：子 Agent 只绑定当前任务必需的少数工具（例如日志 Subagent 只挂载日志检索工具，封禁 Subagent 只挂载防火墙接口），减少工具定义对注意力的争夺。
- **过程数据就地消化**：日志检索返回的大段日志仅在子 Agent 内部流转。完成分析后，子 Agent 仅提炼出几条核心结论（如异常 IP 列表及判断依据）上报给调度器，海量中间日志随子 Agent 会话结束而释放。

![上下文隔离机制：子 Agent 独立吞吐中间日志并向调度器返回紧凑结论](/images/content-rebuild/8980b37fbdbabf3b/fig-2.png)

### 算例对比：日志排查任务下的 Token 消耗特征
为直观说明上下文隔离的效果，我们设定一个具体的处理场景：一段 15,000 Token 的服务器日志，需要先进行异常扫描，再由安全策略完成封禁校验。

> **注：以下数据为机制示意算例。实际 Token 数量与模型分词器、具体提示词写法及工具定义相关。**

#### 方案 A：单 Agent 连续执行
1. **第 1 轮**：System Prompt（2,000 Token）+ 20 个通用工具描述（3,000 Token）+ 初始日志（15,000 Token）= 输入约 20,000 Token。模型分析后调用正则提取工具。
2. **第 2 轮**：前文全部保留（20,000 Token）+ 工具返回的 5 个可疑 IP（200 Token）= 输入约 20,200 Token。模型分析后调用防火墙封禁工具。
3. **第 1~2 轮累积输入 Token**：$20,000 + 20,200 = 40,200$ Token。如果后续还需要进行报告编写、通知发送等步骤，这 15,000 Token 的原始日志仍会持续驻留在上下文窗口中，每一轮都要重复参与前向计算。

#### 方案 B：Subagent 委派执行
1. **主调度器分发**：调度 Prompt（800 Token）+ 委派工具（300 Token）+ 任务指令（200 Token）= 输入 1,300 Token。调度器决定调起“日志分析 Subagent”。
2. **日志 Subagent 独立运行**：分析专有 Prompt（500 Token）+ 扫描工具（200 Token）+ 原始日志（15,000 Token）= 输入 15,700 Token。Subagent 提取出 5 个异常 IP，生成 100 Token 的结构化结果后结束会话。
3. **主调度器二次决策**：接收到 100 Token 摘要，主调度器当前上下文约 1,450 Token。调度器将该结果派发给“安全策略 Subagent”。
4. **安全 Subagent 独立运行**：安全规则 Prompt（400 Token）+ 封禁工具（200 Token）+ 传入的 5 个 IP 摘要（100 Token）= 输入 700 Token。完成封禁操作。

| 维度 | 单 Agent 连续执行 | 多 Agent 上下文隔离 | 机制差异归因 |
| :--- | :--- | :--- | :--- |
| **单次最大输入窗口** | 20,200 Token | 15,700 Token | 原始日志被局限在日志 Subagent 内 |
| **调度器后续上下文** | 随轮次持续膨胀（20,000+） | 保持轻量（~1,500 Token） | 原始噪声数据在子节点完成汇总后释放 |
| **单节点可选工具数** | 20 个工具同时竞争注意力 | 各节点仅挂载 1~2 个工具 | 减小工具模式描述对注意力的稀释 |

## 协作拓扑：主从层级、对等网络与集中式状态图

多 Agent 系统的运行方式由其拓扑结构决定。[LangGraph 官方文档](https://docs.langchain.com/oss/python/langgraph/overview) 与 [Anthropic Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents) 对常见的协作与编排形态进行了系统性归纳：

![多 Agent 协作拓扑对比：主从层级、对等网络与集中式黑板系统](/images/content-rebuild/8980b37fbdbabf3b/fig-3.png)

### 1. 主从层级模式（Supervisor / Subagents）
- **结构形态**：树状拓扑。
- **运行机制**：存在一个中央调度器（Supervisor）。调度器解析用户意图，按步骤调用不同的 Subagent；Subagent 之间不直接建立通信链路，完成各自子任务后将结果统一返回给 Supervisor。
- **适用场景**：流程可拆分为明确子任务、需要集中把控状态与风险的工程系统。链路清晰，易于单点排查与增加断点审查。

### 2. 对等网络模式（Peer-to-Peer / Decentralized）
- **结构形态**：网状拓扑。
- **运行机制**：没有固定中心节点，多个 Agent 平铺于同一层级，通过相互传递消息进行协作（如代码编写 Agent 与代码评审 Agent 反复多轮推敲）。
- **适用场景**：方案推演、交叉质询或特定角色的模拟实验。随着节点增多，消息链路呈现全连接倾向，状态收敛难度和死循环风险会随之增大，通常需要对交互轮次设置硬性上限。

### 3. 集中式黑板系统（Blackboard / Shared State System）
- **结构形态**：星形或图状状态中心。
- **运行机制**：Agent 之间不通过自由对话进行私信，而是共同读写一个集中式的状态存储（State）。例如在 LangGraph 中，各节点接收图状态（State），执行后返回状态增量更新；图运行时依据条件边（Conditional Edge）判定下一步激活哪一个 Agent 节点。
- **适用场景**：复杂状态机系统。各节点实现无状态化，仅依赖当前共享状态输入，适合与持久化（Persistence）和断点恢复机制结合。

## 通信载体：自然语言对话 vs 强类型结构化消息

在多个 Agent 节点之间流转数据时，载体的选择直接影响系统的稳定性。

![自由自然语言通信与强类型结构化 JSON 消息的数据流对比](/images/content-rebuild/8980b37fbdbabf3b/fig-4.png)

### 1. 自由自然语言对话
早期多 Agent 框架常让模型直接发送非结构化的自然语言文本。这种方式有两点主要隐患：
- **解析不确定**：下游 Agent 必须额外耗费推理能力去从上游的叙述中提取关键事实，可能引入二次幻觉；
- **控制困难**：纯文本无法让宿主程序方便地利用 `if/else` 校验状态，错误容易直接穿透到后续业务流程中。

### 2. 强类型结构化消息（JSON / Pydantic）
在工程实践中，推荐使用结构化的模式（Schema）约束节点间的消息传递：

```python
from pydantic import BaseModel, Field
from typing import List, Literal

class SubagentTaskResult(BaseModel):
    task_id: str = Field(description="当前子任务的唯一标识")
    status: Literal["success", "failed", "blocked"] = Field(description="执行状态")
    detected_ips: List[str] = Field(default_factory=list, description="分析提取出的异常 IP 列表")
    summary: str = Field(description="核心发现摘要，控制在 100 字内")
    suggested_action: Literal["block", "ignore", "escalate"] = Field(description="建议下一步动作")
```

采用结构化消息后，下游既可以由调度模型做进一步语义决策，也可以由宿主代码直接读取 `status` 和 `suggested_action` 执行确定性分支，一旦格式校验失败，可在运行时边界由程序直接发起重试，避免错误扩散。

## 多 Agent 的工程代价与风险边界

拆分出多个 Agent 并非零成本。随着系统实体增多，以下三项工程代价会显现出来：

![多 Agent 系统中的错误级联放大机制](/images/content-rebuild/8980b37fbdbabf3b/fig-5.png)

### 1. 响应延迟累加
在单 Agent 场景中，完成一次交互通常需要 1~2 次模型推理。而在层级化多 Agent 系统中，完成一次端到端任务需要串行经过：主调度规划 $\rightarrow$ 子 Agent 推理与工具调用 $\rightarrow$ 主调度汇总。整体首字延迟（TTFT）与端到端响应时间会明显拉长，通常不适合对毫秒级响应有刚性要求的高频交互场景。

### 2. 调用开销与 Token 总量反弹
虽然单个 Subagent 的上下文得到了裁剪，但每个 Subagent 在启动时都需要挂载独立的 System Prompt；加上主从之间的调度指令、JSON 包装开销以及多次 API 调用的网络握手，系统的整体调用频次与综合 Token 消耗往往高于简单单任务实现。

### 3. 错误级联与偏差累积
在链式执行中，上游 Agent 输出的任何事实偏差都会成为下游 Agent 的推理基准。

> **注：以下公式仅为说明“串行依赖下成功率随链路拉长而衰减”的理论示意，计算基于“各节点错误发生相互独立且概率相同”的理想化假设。现实系统的错误往往存在上下游关联，且受校验策略影响。**

若一条依赖链包含 $n$ 个按序执行的 Agent 节点，且假定各节点独立产出正确结论的概率均为 $p$（例如 $p = 0.9$）：
- 2 节点协作链路的整体可靠性理论示意：$P = 0.9^2 = 0.81$；
- 4 节点协作链路的整体可靠性理论示意：$P = 0.9^4 \approx 0.656$。

如果在节点交接处缺乏宿主程序的断言校验，上游产生的细微幻觉可能在后续节点中被当成已知事实继续推导，从而导致最终输出偏离目标。

## 架构选型参考：何时不需要多 Agent？

Anthropic 在 [Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents) 中建议：**从最简单的方案开始，仅在复杂度确有必要时才引入更复杂的模式。**

![多 Agent 架构选型决策树与工程红线](/images/content-rebuild/8980b37fbdbabf3b/fig-6.png)

在以下场景中，通常优先考虑单 Agent 或确定性工作流，而非多 Agent：

1. **逻辑路径高度固定的任务**：如果任务可以通过固定分支语句（如 `if error: retry`）、状态机或标准 DAG 图完成，应使用确定性代码编排（Workflows），而不是让大语言模型动态协商下一步走法。
2. **工具数量较少且上下文较短的任务**：当工具总数在 3~5 个以内，且环境返回的数据量适中时，配合标准的 [ReAct 框架](/llm-100/agent-basics/ReAct_框架是什么_为什么适合_Agent.md) 即可稳定工作，拆分子 Agent 只会平白增加通信延迟。
3. **缺乏追踪与调试设施的系统**：多 Agent 系统运行路径更动态。如果项目中尚未接入链路追踪（如 LangSmith Trace）与结构化日志系统，排查多节点状态漂移将变得极其困难。

## 读者自测

1. **上下文隔离检验**：为什么在日志排障任务中，让 Subagent 仅向主调度器返回“提取出的 5 个异常 IP”，比直接把原始日志传递给主调度器更能提升系统的长期稳定性？
2. **通信模式分析**：在多 Agent 协作中，使用 Pydantic 强类型消息传递相比于纯自然语言对话，在错误拦截上有何具体差异？
3. **选型思考**：假设有一个“根据用户身份证号查询征信，符合条件则发短信，不符合则记录日志”的业务，应该选择由两个 Agent 协作完成，还是用普通代码编写 Workflow？请结合延迟与确定性说明理由。

### 参考答案提示
- **第 1 题**：原始日志包含大量与后续决策无关的冗余字符。若驻留在主调度器上下文中，不仅每一轮推理都要重新消耗 Prefill 算力，还会稀释系统指令和合规边界的权重。通过 Subagent 就地消化并仅上报结构化摘要，保持了主调度器上下文的整洁。
- **第 2 题**：纯自然语言对话必须依赖下游 LLM 再次进行文本理解与提取，若存在语义歧义或幻觉容易直接顺延；强类型消息由宿主程序的反序列化代码在节点边界进行校验，一旦字段缺失或类型不符可直接阻断并就地重试，无需下游模型猜测意图。
- **第 3 题**：应使用 Workflow 编排。该任务的流转逻辑完全基于预定义的业务规则（布尔判断、接口调用），不存在开放式探索或需要动态规划的步骤。用普通代码编排无需大模型推理费用，控制流由代码路径直接决定；虽然网络与外部接口仍可能发生超时或故障，但可通过标准错误捕获与重试机制进行可控处理，引入多 Agent 反而平白增加模型推理延迟、非确定性决策与出错点。
