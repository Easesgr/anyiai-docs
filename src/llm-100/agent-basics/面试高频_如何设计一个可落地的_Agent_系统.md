在很多面试或技术讨论中，讨论到“如何设计一个 Agent 系统”时，常见的回答往往是列举“LLM 规划 + 记忆 + 工具”三要素，再画一个让模型反复自主推理与调用工具的循环。然而在实际工程交付中，如果把控制权完全交给大语言模型，系统容易遇到三个现实阻碍：**任务在多轮调用中偏离预期或死循环、外部写操作缺乏阻断机制可能误改数据、缺乏链路排查手段导致定位故障困难**。

要让 Agent 稳定运行在生产环境，核心工程原则不是追求完全无人工干预的自主运行，而是**在确定性的代码控制流与模型的动态推理能力之间建立清晰的分工**。本讲以一个具体的电商售后维权工单处理系统为贯穿案例，拆解系统边界定义、混合控制架构、权限隔离沙盒、人机协同（Human-in-the-loop）机制、分布式链路监控以及核心量化验收指标。

## 贯穿案例与需求拆解：输入规格、行动空间、边界约束与验收标准

为了让讨论保持具体，我们设定一个贯穿全篇的业务场景：**电商售后争议赔付 Agent**。用户输入一条诉求：“我上周买的生鲜水果严重腐烂，商家拒绝退款，请帮我核实并赔偿 50 元代金券。”

如果直接把这段文字连同所有系统 API 扔给大模型让其自由发挥，模型可能会自行调用转账或发券接口，甚至被恶意提示词诱导造成资损。在编写代码之前，必须首先确定四个工程边界：

![Agent 业务解题四要素分解图](/images/content-rebuild/2b73d1a2612e523c/fig-1.png)

1. **输入规格（Input Specification）**：非结构化的自然语言输入不能直接进入决策核心，必须提取并校验结构化元数据。例如：当前登录用户的身份（`user_id`）、租户隔离标识（`tenant_id`）、目标订单号（`order_id`）以及操作人权限范围。参数缺失时应先触发澄清流程，而非让模型自行猜测。
2. **行动空间（Action Space）**：系统允许调用的工具集合必须封闭且语义明确。每个动作必须显式标注其副作用属性：
   - **无副作用（只读）**：如 `get_order_detail`（查询订单详情）、`get_logistics_status`（获取物流轨迹）、`fetch_policy_rules`（检索赔付规则库）。
   - **有副作用（写入/资产变动）**：如 `issue_coupon`（发放代金券）、`update_order_status`（修改订单状态）。这类工具不能由模型单方面直接触发。
3. **边界约束（Guardrails）**：为防止模型陷入推理震荡或被恶意消耗，必须在程序中配置硬性边界：
   - 单任务模型交互步数上限 $N_{\max}$（例如最多 5 轮交互）；
   - 单任务累计消耗 Token 上限；
   - 单任务全局执行超时时间（例如 60 秒）；
   - 工具调用失败的最大重试次数（例如最多重试 2 次且使用指数退避）。
4. **验收标准（Acceptance Criteria）**：任务结束的判据必须基于系统的状态变更，而不能依赖模型说出的自然语言回复。例如验收标准是：“数据库中工单状态扭转为 COMPLETED，补偿流水记录写入成功且附带审核人签名”。

关于单次对话与具备工具行动空间系统的差异，可参考 [/llm-100/agent-basics/Agent_是什么_它和普通_ChatBot_有什么区别.md](/llm-100/agent-basics/Agent_是什么_它和普通_ChatBot_有什么区别.md)。

## 控制架构选型：确定性代码主干与局部模型决策

根据 Anthropic 在《Building effective agents》中的总结，AI 驱动的系统主要分为两类：
- **工作流（Workflows）**：执行路径由预先编写的代码分支与状态机编排，模型仅在特定节点执行分类、摘要或结构化提取；
- **智能体（Agents）**：模型动态决定自身的执行步骤和工具调用时机。

在生产环境中，纯粹由模型全权控制的智能体很难保证行为一致性。更稳妥的做法是采用**混合架构（Hybrid Architecture）**：由确定性的代码图负责主干路由、状态持久化和权限门禁，仅在需要理解非结构化证据、裁定赔付责任等环节，交由模型进行局部动态决策。

![工作流与 Agent 控制架构选型对比](/images/content-rebuild/2b73d1a2612e523c/fig-2.png)

在混合架构中，我们可以把执行逻辑组织为一个有向图状态机。常规的前置取数和参数验证走固定代码路径，当所有事实数据收集完毕后，再由模型给出一份决策建议。这样既能利用模型对复杂证据的理解能力，又规避了 [/llm-100/agent-basics/Agent_为什么容易陷入死循环.md](/llm-100/agent-basics/Agent_为什么容易陷入死循环.md) 中分析的模型在工具调用间反复震荡的问题。

<ReadMoreLock />

下面给出一个基于 Python 伪代码的简化状态机控制示例，展示确定性检查与模型决策节点的切分逻辑：

```python
# 混合状态机控制逻辑示例（伪代码）
from typing import Dict, Any, Literal

class AgentState(dict):
    order_id: str
    user_claim: str
    evidence_data: Dict[str, Any]
    decision_proposal: Dict[str, Any] | None
    pending_write_action: Dict[str, Any] | None
    step_count: int
    is_finished: bool

def collect_data_node(state: AgentState) -> AgentState:
    """确定性节点：通过标准只读接口获取订单与物流数据，不消耗模型 Token"""
    state["evidence_data"] = {
        "order": fetch_order_api(state["order_id"]),
        "logistics": fetch_logistics_api(state["order_id"])
    }
    return state

def evaluate_claim_node(state: AgentState) -> AgentState:
    """模型决策节点：由 LLM 综合对比证据与规则，提出赔偿方案"""
    state["step_count"] += 1
    proposal = call_llm_for_adjudication(
        claim=state["user_claim"],
        evidence=state["evidence_data"]
    )
    state["decision_proposal"] = proposal
    
    # 若模型建议赔偿金额大于 0，生成待审批写动作，不直接调用发券 API
    if proposal.get("compensation_amount", 0) > 0:
        state["pending_write_action"] = {
            "tool": "issue_coupon",
            "amount": proposal["compensation_amount"],
            "reason": proposal.get("reason")
        }
    else:
        state["is_finished"] = True
    return state

def route_next_step(state: AgentState) -> Literal["human_approval", "finalize"]:
    """确定性路由分支"""
    if state.get("pending_write_action") is not None:
        return "human_approval"
    return "finalize"
```

## 安全与权限隔离：读写分离、参数校验与运行沙盒

模型根据输入概率采样生成输出，可能会受到外部不可信内容触发间接提示词注入。如果模型生成的工具调用可以直接写入生产数据库或触发退款接口，系统将面临越权与资损风险。关于大模型如何发起工具调用，可参考 [/llm-100/agent-basics/Tool_Calling_是什么_大模型如何调用工具.md](/llm-100/agent-basics/Tool_Calling_是什么_大模型如何调用工具.md) 与 [/llm-100/agent-basics/Function_Calling_和_MCP_有什么区别.md](/llm-100/agent-basics/Function_Calling_和_MCP_有什么区别.md)。

![安全与权限隔离机制及沙盒架构](/images/content-rebuild/2b73d1a2612e523c/fig-3.png)

在工程上，防御模型误操作必须依靠外部系统机制，而不是依赖“请严格遵守安全规则”的系统提示词：

1. **读写权限隔离**：
   - **只读操作**：查询类接口配置为只读数据库账号或只读 HTTP API，允许在设定的步数预算内由模型自动调用。
   - **写操作门禁**：涉及资产变动、数据删除、状态修改的接口，严禁挂载为无需确认的自动工具。模型仅能输出“操作申请”，由后续网关或人工审核通过后由系统执行。
2. **强类型与边界校验**：模型输出的 JSON 参数必须经过 Pydantic 或 JSON Schema 严格校验。对于金额、ID、枚举值等关键字段，需设置硬性业务断言（例如：单笔补偿金额必须大于 0 且小于等于 50 元）。超出边界时直接报错返回，不执行下游调用。
3. **动态代码执行沙盒**：如果 Agent 拥有运行生成的 Python 代码或 Shell 脚本的能力（例如数据分析场景），必须将执行环境限制在隔离容器或轻量虚拟机（MicroVM）中，禁用外网访问权限，以只读方式挂载宿主目录，并严格限制内存与 CPU 配额。

## 人机协同（Human-in-the-loop）：检查点持久化与状态干预

人机协同（HITL）常被误解为在对话框中让模型向用户提问“你确定要执行吗”，然后等待下一句回复。这种方式在工程上存在漏洞：模型可能被下一轮对话诱导绕过确认，而且在长会话中容易丢失上下文。

如 LangGraph 等编排框架所示，成熟的人机协同机制依赖于**状态机级别的中断（Interrupt）与检查点持久化（Checkpointer Persistence）**：

![人机协同状态挂起与恢复时序图](/images/content-rebuild/2b73d1a2612e523c/fig-4.png)

整个中断与恢复流程包含四个环节：

1. **检测到敏感动作并触发中断**：当路由逻辑检测到存在待执行的敏感操作（例如 `pending_write_action` 存在）时，状态机暂停执行，不再向模型发起调用。
2. **状态快照持久化**：系统将当前的完整会话状态（包括历史消息、收集的证据、待执行动作参数）序列化存储至数据库（如 PostgreSQL 或 Redis），生成唯一的 `checkpoint_id`，并向审批平台发送待办通知。
3. **人工审查与状态修改**：客服主管或运营人员在管理后台打开该检查点。审批人可以执行三种操作：
   - 直接批准执行；
   - 驳回请求并附带理由；
   - **直接修改状态中的参数**（例如将模型建议的 50 元补偿金修改为 30 元）。
4. **携带新状态恢复执行（Resume）**：审核完成后，状态机从数据库加载更新后的状态，从中断节点继续向下运行。系统由固定代码执行实际发券动作，并将执行结果写回上下文。

关于多轮交互中状态与记忆的持久化管理，读者可参考 [/llm-100/agent-basics/Agent_的_Memory_应该怎么设计.md](/llm-100/agent-basics/Agent_的_Memory_应该怎么设计.md) 以及 [/frontier/agent-memory-system/memory-design.md](/frontier/agent-memory-system/memory-design.md)。

## 链路可观测性：分布式 Trace 与状态重放

由于模型具有概率输出特性，一旦用户反馈“为什么我的工单被误判”，仅仅依靠打印系统最终输出是无法排查问题的。生产级 Agent 必须接入分布式链路追踪（Distributed Tracing），以树状 Span 的形式捕获每一次状态转换与外部交互：

![Agent 完整 Trace 链路与监控时序图](/images/content-rebuild/2b73d1a2612e523c/fig-5.png)

一个完整的 Trace 树需要按层级记录以下核心数据：

- **Root Run（全局任务节点）**：记录任务开始时间、结束时间、端到端耗时、输入原始 Query、最终工单状态以及整个生命周期消耗的总 Token。
- **LLM Span（模型调用节点）**：记录请求到达模型的确切上下文、当前使用的提示词模板、模型输出的思维链或原始文本、使用的解码参数（Temperature 等），以及准确的 Prefill 与 Completion Token 消耗数。
- **Tool Span（工具执行节点）**：记录调用的工具名称、由模型生成的实参、工具执行耗时、HTTP 状态码以及接口返回的原始数据。
- **State Transition（状态变迁快照）**：在状态图的每个关键节点流转前后，保存当前状态字典的差异对比（Diff），便于回溯哪一步修改了特定变量。

## 生产评估指标与对比算例

评估 Agent 系统是否能够上线，需要量化的服务等级目标（SLO），通常围绕以下四个指标建立监控看板：

![生产级 Agent 核心评估指标雷达](/images/content-rebuild/2b73d1a2612e523c/fig-6.png)

1. **端到端任务完成率（Task Success Rate）**：在测试集或线上样本中，工单最终达到正确业务状态（而非仅仅模型生成完文本）的比例。
2. **平均执行步数与有效比（Average Steps）**：完成单项任务经历的工具调用与模型交互轮数。步数持续偏高通常意味着模型陷入反思循环，ReAct 的内部原理可参见 [/llm-100/agent-basics/ReAct_框架是什么_为什么适合_Agent.md](/llm-100/agent-basics/ReAct_框架是什么_为什么适合_Agent.md)。
3. **单任务综合成本与延迟（Cost & Latency per Task）**：单次任务消耗的模型 API 费用和端到端 P95 延迟。
4. **人工干预率（Human Intervention Rate）**：触发中断需要人工复核或手动修改参数的任务占比。

### 教学对比算例：纯自主 ReAct vs 混合受控架构

为了直观展示架构选型对成本和稳定性的影响，我们设定一个具体的工单处理算例。

**算例假设条件（仅作教学机制对比示意）**：
- 处理 1,000 个售后争议工单，其中 800 个为常规无货/退款查询（可通过规则直接判断），200 个涉及复杂争议赔偿。
- 模型 API 单价设定：输入 $0.002$ 元 / 1k tokens，输出 $0.006$ 元 / 1k tokens。
- 单次模型调用：平均输入上下文 2,000 tokens，输出 200 tokens。单次调用成本约为 $0.002 \times 2 + 0.006 \times 0.2 = 0.0052$ 元。

**方案对比设定**：
- **方案 A（纯自主 ReAct 架构）**：所有工单均从第一步开始由大模型自主决策，自主选择调用查询订单、查询物流、查询政策、发起赔偿等工具。设定最大步数阈值为 8 步。由于缺乏固定流程约束，常规工单平均调用 3 次模型，复杂工单平均调用 6 次模型，且有部分长尾任务陷入步数打满失败。
- **方案 B（混合受控架构）**：前置由固定代码走标准 API 查询订单和物流信息（不调用模型，成本为 0）。800 个常规工单由确定性规则代码直接结单（调用 0 次模型）；200 个复杂争议工单仅由模型进行 1 次责任判定，写操作进入审批。平均每个复杂任务调用模型 1.1 次（含极少量重试）。

| 评估指标 | 方案 A：纯自主 ReAct 架构 | 方案 B：混合受控架构（推荐） |
| :--- | :--- | :--- |
| **模型调用总次数** | $800 \times 3 + 200 \times 6 = 3,600$ 次 | $800 \times 0 + 200 \times 1.1 = 220$ 次 |
| **1,000 任务总模型成本** | $3,600 \times 0.0052 = 18.72$ 元 | $220 \times 0.0052 = 1.144$ 元 |
| **常规任务完成率** | 约 $85\%$（存在模型调用工具格式错误或振荡） | $\approx 99\%$（由成熟后端接口保证） |
| **资损防护机制** | 依赖 Prompt 软约束，存在越权调工具风险 | 写操作在代码层被拦截挂起，由人工确认 |
| **故障定位难度** | 难以排查，每一步都是自由文本推理链 | 容易排查，只读流水走标准日志，决策点独立归档 |

算例说明：**对大部分能够通过规则或传统代码解决的流程，不应盲目引入大模型循环调用**。将确定性业务逻辑沉淀在状态机代码中，只在真正的语义理解和模糊裁决环节引入模型，能大幅降低系统调用成本并提升稳定性。

## 常见面试追问与回答要点

在面试或系统架构评审中，关于 Agent 落地常有以下深度追问：

### 追问 1：如何防止 Agent 在生产中执行越权或破坏性操作？
- **错误回答**：“在系统提示词里严格写明‘严禁删除数据’、‘调用前必须复核’。”
- **推荐思路**：
  1. **模型输出不等于系统执行**：大语言模型仅能生成调用意图（Action Proposal），不能直接持有生产数据库的写权限；
  2. **读写接口物理切分**：只读工具自动执行，破坏性写操作必须映射为“待审批工单”，并触发中断保存当前检查点；
  3. **运行沙盒与入参断言**：代码解释器放在隔离容器中运行，所有工具参数通过强类型校验库做上下限边界检查。

### 追问 2：什么时候该用预定义 Workflow，什么时候该用 Agent？
- **错误回答**：“简单逻辑用 Workflow，复杂系统都要升级为 Agent。”
- **推荐思路**：
  1. 核心判断标准是**业务路径是否具备先验确定性**；
  2. 如果业务规则清晰、分支条件可以明确枚举（如根据用户会员等级匹配固定补偿金额），优先使用确定性工作流，其延迟低、开销小、稳定性高；
  3. 只有当任务输入高度非结构化、需要根据外部环境的不确定反馈动态选择工具次序时，才在局部环节采用 Agent。大部分成熟系统采用“外层确定性工作流 + 局部 Agent 节点”的组合模式。

### 追问 3：多 Agent 协作系统是否一定优于单 Agent？
- **错误回答**：“分工越多越好，设计产品、研发、测试多个 Agent 模拟人类团队，效果更好。”
- **推荐思路**：多 Agent 协作虽然可以拆分长上下文、实现提示词关注点分离，但会带来网络往返延迟叠加、Token 消耗倍增以及跨 Agent 传递信息失真等新问题。工程架构应遵循奥卡姆剃刀原则：能用单次 Prompt 解决的不用工具调用，能用单 Agent 加工具解决的不用多 Agent，仅在上下文存在物理权限隔离或必须由异构系统配合时才拆分多智能体。具体权衡可参考 [/llm-100/agent-basics/多_Agent_协作到底解决什么问题.md](/llm-100/agent-basics/多_Agent_协作到底解决什么问题.md)。
