在很多大模型应用讨论中，“ChatBot”、“工作流（Workflow）”和“Agent（智能体）”三个名词经常被混为一谈。不少开发者将“接了知识库的问答窗口”或“调用了外部天气接口的脚本”直接称为 Agent。这种概念混淆会导致选型偏差：要么给规则固定的业务强行引入不确定的自主循环，导致高延迟与调用失控；要么在需要灵活试错的复杂任务中写死代码分支，导致系统无法应对预期外的输入。

要理清它们的关系，核心在于看**系统的控制权（Control Flow）在谁手里**：是程序员用代码锁定了每一步跳转，还是由大模型根据环境反馈动态决定下一步做什么？

以一个排查线上故障的场景为例：**“线上数据库连接数激增，请找出原因”**。
*   **普通 ChatBot**：只能给出通用的文字排查建议（如“请检查慢查询和连接池配置”），它无法查看真实的线上指标，也无法执行任何排查动作。
*   **硬编码工作流（Workflow）**：由程序员写死执行步骤，代码先调用接口查慢查询日志，再把日志传给大模型总结。如果这次连接激增恰好不是慢查询引起的，而是网络丢包，由于代码没有写其他分支，流程便直接终止，给出“未发现慢查询”的无效排查结果。
*   **Agent 系统**：程序员给模型提供一组工具（查慢查询、查网络连接分布、查连接池指标）。模型先查慢查询，发现日志正常；它看到这个返回结果后，自主决定调用下一个工具查网络连接分布，发现某台微服务实例建立了异常多的空闲连接，最终定位到连接池泄露。

![Agent 与 ChatBot 的范式差异与控制权流转](/images/content-rebuild/e4d43e99d944c3cc/cover.png)

上图展示了从固定应答到自主循环的演进逻辑。左侧是单向生成的对话模型，中间是规则固定的代码工作流，右侧则是将控制权交给模型决策循环的 Agent 系统。接下来我们将沿着运行方式、架构差异、循环机制、能力边界与工程代价展开说明。

## 普通 ChatBot 的运行方式：单向输入与文本补全

传统对话机器人（ChatBot）的核心运行机制是自回归语言模型的文本补全。无论接入了多么精巧的提示词模板或多轮对话历史，它在处理链路上都是“开环”的。

在每一轮交互中，系统执行的过程非常直观：

1. 用户在前端输入问题；
2. 宿主程序将系统提示词（System Prompt）、多轮对话历史和当前输入拼装成完整的提示词；
3. 模型进行推断并流式输出文本响应；
4. 生成结束，等待下一次用户输入。

![ChatBot 的开环生成交互机制](/images/content-rebuild/e4d43e99d944c3cc/fig-1.png)

在图 1 中可以看到，ChatBot 处理链路中外部环境对模型是只读或不可见的。即使接入了 RAG（检索增强生成），检索步骤也是在模型推理前由代码写死的：用户提问 $\to$ 检索向量库 $\to$ 拼装上下文 $\to$ 模型生成回答。模型在这个过程中**不能决定要不要检索、向哪里检索，检索结果不理想时也无法自主换个关键词重新查**。它负责生成答案，但没有参与达成目标的过程控制。

## 控制权之争：预定义工作流与 Agent 的架构差异

Anthropic 在《Building effective agents》中对这两类架构给出了明确界定：
*   **工作流（Workflows）**：通过预定义的代码路径编排大模型和工具的系统。
*   **Agent**：由大模型动态主导执行流程、自主决定工具调用的系统。

区分两者的关键，不是“是否调用了大模型”或“是否使用了外部 API”，而是**下一步跳转的决定权在代码还是在模型的推理输出中**。

![硬编码工作流与 Agent 动态流转的拓扑对比](/images/content-rebuild/e4d43e99d944c3cc/fig-2.png)

如图 2 所示，两者的执行拓扑截然不同：

*   **工作流（Workflows）**：执行路径是一张预先确定的有向图（DAG）或带有显式规则的状态机。系统所有可能的分支走向和判定规则在代码中预先固化。即使分支条件依赖大模型的分类输出或外部 API 返回值，程序也只能在写好的代码路径中流转，不能自主创造或选择未定义的路径；同时需要注意，代码控制分支不等于整个工作流 100% 确定，模型波动、网络 I/O 和外部状态变化仍会影响执行结果。
*   **Agent 系统**：执行路径在运行前无法完全确定。程序员向模型注册一组可用工具和目标说明，**模型在循环中根据当前状态和上一步工具返回的结果，自主决定是继续调用某个工具、更换参数重试，还是结束任务输出结果**。

以下两段最小伪代码展示了两者的控制逻辑差异：

```python
# 示例 A：硬编码工作流（控制权在代码）
def workflow_pipeline(user_query: str):
    # 1. 固定的意图分类
    intent = call_llm(f"分类用户意图: {user_query}")
    
    # 2. 固定的代码分支判断
    if intent == "check_order":
        order_info = query_order_db(user_query)
        return call_llm(f"根据数据生成回复: {order_info}")
    elif intent == "refund":
        policy = get_refund_policy()
        return call_llm(f"根据规则解答: {policy}")
    else:
        return call_llm(f"自由回答: {user_query}")
```

```python
# 示例 B：Agent 决策循环（控制权在模型推理与环境反馈）
def agent_loop(user_goal: str, tools: dict, max_steps: int = 5):
    state_history = [{"role": "user", "content": user_goal}]
    
    for step in range(max_steps):
        # 模型根据历史状态与观察，自主决定下一步动作
        decision = call_llm_with_tools(state_history, tools.specs())
        
        # 模型自主判断任务是否完成
        if decision.is_final_answer:
            return decision.answer
            
        # 宿主系统执行工具，并将结果回填为观察（Observation）
        tool_result = tools[decision.tool_name](**decision.tool_args)
        state_history.append({"role": "tool", "content": str(tool_result)})
        
    return "达到最大步数限制，任务未收敛"
```

在工作流中，如果分类模型把未见过的网络丢包问题误判进其他分支，程序就会在预设路径里直接报错或退出；而在 Agent 架构中，模型可以根据工具返回的报错信息，在下一次循环中自主决定调整参数或切换调用其他工具。

关于大模型输出结构化参数并调用工具的具体协议规范，可以参阅本栏目的专讲：[/llm-100/agent-basics/Tool_Calling_是什么_大模型如何调用工具.md](/llm-100/agent-basics/Tool_Calling_是什么_大模型如何调用工具.md)。

## 动态决策循环：感知、决策、行动与观察

Agent 能够处理开放式任务的关键，在于其内嵌的**动态反馈控制循环**。这一循环通常由感知（Perceive）、决策（Reason）、行动（Act）和观察（Observe）四个环节构成，业界最典型的实现即 ReAct 循环。

有关该运行模式的详细解析，详见 [/llm-100/agent-basics/ReAct_框架是什么_为什么适合_Agent.md](/llm-100/agent-basics/ReAct_框架是什么_为什么适合_Agent.md)。

![Agent 动态决策四步闭环交互细节](/images/content-rebuild/e4d43e99d944c3cc/fig-3.png)

如图 3 所示，决策循环的每一次迭代都包含四个明确的状态交接阶段：

1.  **感知与状态组装（Sense & State Formulation）**：
    宿主程序收集用户任务目标、历史对话轨迹以及上一轮工具执行返回的结果（Observation），拼装成符合模型接口规范的 Prompt 上下文。
2.  **评估与决策（Evaluate & Plan）**：
    模型评估当前已掌握的信息是否足以回答用户需求。如果足够，生成最终回答；如果不足，决定下一步调用的工具名及参数。
3.  **行动下发（Action Dispatch）**：
    模型输出符合规范的结构化调用请求（如包含函数名与参数的 JSON）。这里需要明确：**大模型本身不具备网络通信和代码执行能力**，它只是输出调用指令，必须由宿主程序验证权限、检查参数并真正向目标 API 发送网络请求。
4.  **环境观察与反馈回填（Observation Feedback）**：
    宿主程序将工具调用的结果（无论是数据返回值、网络超时还是异常报错堆栈）回填进上下文记忆。模型在下一轮循环中将这些结果作为新的环境事实进行下一步分析。

这种机制打破了单次生成“落子无悔”的局限。普通 ChatBot 一旦开始生成，中途遇到错误只能等用户在下一轮对话中纠正；Agent 则利用中间观察数据的不断注入，在将最终结果交付给用户前完成多轮自发验证与分支重试。

## 三者能力与边界对比

我们可以从行动空间、状态持久化方式和错误应对能力三个维度，对 ChatBot、工作流与 Agent 进行横向对比。

![ChatBot、工作流与 Agent 的三维工程能力对比](/images/content-rebuild/e4d43e99d944c3cc/fig-4.png)

| 对比维度 | 普通对话机器人 (ChatBot) | 硬编码工作流 (Workflow) | 自主智能体 (Agent) |
| :--- | :--- | :--- | :--- |
| **控制权主体** | 用户输入单向驱动 | 宿主代码业务逻辑驱动（DAG / 状态机） | 大模型根据反馈动态驱动 |
| **行动空间** | 仅输出语言文本 | 代码预设的固定 API 调用序列 | 开放的工具集，由模型自主挑选组合 |
| **状态管理** | 短暂维护对话历史 | 依赖业务数据库记录流程节点 | 依赖持久化状态机、执行检查点与工作记忆 |
| **执行路径确定性** | 高（流程固定，仅文本措辞波动） | 较高（可选路径集合由代码预先限定，但若节点包含模型判定或外部状态，分支走向与输出仍受其影响） | 低（路径动态生成，不同运行可能出现差异） |
| **错误应对表现** | 无法自主纠错，依赖用户提醒 | 依赖人工预先埋设的 `try-catch` 或重试规则 | 可读取工具报错，自主尝试修改参数或更换工具 |

需要指出的是，**Agent 的错误纠正能力有严格边界**。在生产实践中，Agent 的自主调整通常只能应对局部异常：
*   工具参数格式不合规（Pydantic 报错回传后，模型重新生成格式正确的参数）；
*   查询关键词返回空数据（模型根据反馈更换近义词重试）；
*   接口返回临时业务权限提示（模型换用备选查询工具）。

如果任务目标本身自相矛盾、依赖的底层服务彻底不可用，或者模型对观察结果产生严重理解偏差，Agent 容易陷入无休止的无效尝试。关于如何识别并防范死循环，参见 [/llm-100/agent-basics/Agent_为什么容易陷入死循环.md](/llm-100/agent-basics/Agent_为什么容易陷入死循环.md)。

## 工程落地权衡：延迟、费用与不确定性

虽然 Agent 展现了极强的自适应能力，但在实际工程中，自主性往往伴随着明显的系统代价。

![技术选型权衡决策树：ChatBot、Workflow 还是 Agent](/images/content-rebuild/e4d43e99d944c3cc/fig-5.png)

如图 5 所示，引入动态决策循环会带来三方面的成本增加：

### 1. 响应延迟累加（Latency Accumulation）
普通问答只需要一次模型推断，端到端延迟通常在几百毫秒到两三秒之间；而一个包含 4 步工具调用的 Agent 任务，至少需要 4 到 5 次模型完整推断加上 4 次工具 API 的网络 I/O。总延迟通常会上升到 10 秒到 30 秒以上，无法用于对实时性要求苛刻的场景。

### 2. 上下文膨胀与 Token 消耗（Context Growth）
在循环过程中，工具返回的数据（例如一段数百行的监控日志）必须塞入上下文作为下一次推断的依据。第 $N$ 次循环的 Prompt 包含前面所有步骤的调用记录与工具返回值。如果没有清洗和修剪机制，Token 消耗会随循环轮数快速增加，带来昂贵的调用账单。

关于如何合理管理 Agent 的短期工作记忆与长期存储，可参考 [/llm-100/agent-basics/Agent_的_Memory_应该怎么设计.md](/llm-100/agent-basics/Agent_的_Memory_应该怎么设计.md) 以及进阶专题 [/frontier/agent-memory-system/README.md](/frontier/agent-memory-system/README.md)。

### 3. 不确定性与审计困难（Non-deterministic Risks）
在财务结算、核心权限审批、医疗合规等场景下，业务对稳定性和可复现性有硬性要求。Agent 具有探索性，面对相同的输入可能走出不同的工具调用路径；一旦缺少防护规则，模型还可能产生非预期的外部操作（例如误调用批量退款接口）。

因此，在系统设计时建议遵循**最简可用原则**：
1.  **纯文本总结与信息咨询**：使用标准 ChatBot 或单轮 Prompt；
2.  **业务逻辑固定、分支条件明确**：使用预定义代码路径的工作流（Workflow），仅在需要内容抽取的特定节点调用 LLM；
3.  **排查路径事先无法枚举、需要基于环境观察多轮动态试错**：才考虑使用 Agent。

## 贯穿案例复盘：告警排查的两种实现路径

回到开头的数据库告警排查案例，我们对比两种系统的实际执行表现：

![排查运维告警场景下 Workflow 与 Agent 的失败表现对比](/images/content-rebuild/e4d43e99d944c3cc/fig-6.png)

图 6 清晰展示了两者的分歧：

*   **工作流实现**：代码固定串联 `获取告警详情` $\to$ `查询慢日志 Top 10` $\to$ `模型分析并输出报告`。如果根因是慢查询，该系统耗时短、消耗低且极为可靠。但当根因是网络丢包或连接池配置错误时，工作流查完慢日志就退出了，得出“慢日志正常，未见异常”的空结论，无法继续深入排查。
*   **Agent 实现**：提供 `查询慢日志`、`查询系统连接IP分布`、`查询主机网络状态` 三个工具。模型第一步调用慢日志，得到“查询耗时均在 5ms 以内”的反馈；模型据此判断并非慢查询导致，第二步自主触发 `查询系统连接IP分布`，发现某一服务实例占用了 90% 的长连接；最终输出排查推断。但若网络监控接口报错超时且未设上限，模型可能会反复重试，造成资源浪费。

在现代工程中，主流的落地方案通常不是非此即彼，而是 **“以预定义代码路径的工作流为主干骨架，在局部需要探索的环节接入 Agent”**。例如在 LangGraph 等框架中，主流程用预定义分支图保证合规与审计，局部复杂子任务交由模型进行自主决策试错。

更多关于模型、工具、记忆与规划四大模块的协同运作原理，将在下一讲 [/llm-100/agent-basics/Agent_的核心组成_模型_记忆_工具和规划.md](/llm-100/agent-basics/Agent_的核心组成_模型_记忆_工具和规划.md) 中展开。

## 思考与检验

请尝试完成以下两个具体练习，检验对本讲内容的掌握程度：

### 练习 1：判断架构类型
某团队开发了一个客服助手，当用户发消息时，系统执行以下逻辑：
1. 用正则判断用户是否询问“退款”；
2. 若命中，调用退款流程接口并让模型生成一句礼貌用语返回给用户；
3. 若未命中，直接将消息转发给大模型自由回答。

**问题**：该系统属于普通 ChatBot、硬编码工作流还是 Agent？控制流的决定权在代码还是模型？

### 练习 2：编写最小决策验证代码
编写一个最小 Python 脚本，定义两个简单的本地工具函数：
1. `query_weather(city: str) -> str`：若传入 `"北京"` 返回 `"晴天"`，若传入其他城市返回 `"错误: 暂无该城市数据"`。
2. `query_mock_db(item: str) -> str`：返回对应物品的库存。

模拟一段模型决策逻辑（可用硬编码返回模拟模型的工具调用输出）：
*   第一次调用 `query_weather(city="上海")`，观察工具返回报错；
*   根据工具报错，系统进入第二轮循环，改为调用 `query_weather(city="北京")`；
*   第三轮循环根据成功结果生成最终回答并终止。

**检验标准**：代码中必须包含明确的状态累加列表、步骤计数器（防死循环上限）以及基于工具返回值决定是否退出的判断条件。
