把单次大模型 API 调用做成一个可供多人稳定使用的业务系统，面临的工程问题会发生明显改变：单次计算耗时从传统的数十毫秒拉长至数秒甚至数分钟，模型输出具有一定随机性，每次请求受上下文窗口和预算约束，并且外部模型服务存在调用频次限制与宕机风险。

大模型应用系统并非简单地由前端直接向模型提供商发送请求，而是由交互层、业务编排层、模型网关层与持久存储层组成的协作体系。本讲以一个典型的“知识库客服助手”为贯穿示例，梳理各组件的分工、数据在链路中的流转路径，以及应对长耗时和网络抖动的工程解法。

本讲作为 [大模型应用系统篇](/llm-100/app-system/README.md) 的基础，帮助读者建立系统全局视角，后续可进一步学习 [前端、后端与模型协同](/llm-100/app-system/frontend-backend-model.md) 和 [接口调用生命周期](/llm-100/app-system/model-api-request-lifecycle.md)。

### 传统 Web 系统与大模型应用系统的差异

以用户查询“我的订单能否无理由退货”为例：

* **传统 Web 架构**：客户端发起请求，后端服务读取关系型数据库中的订单创建时间和退货规则字典，经过确定性条件判断（例如 `当前时间 - 支付时间 <= 7天`），在数十毫秒内直接返回固定格式的 JSON 数据。网络连接即开即关，服务端容易做无状态水平扩展。
* **大模型应用架构**：用户输入的是自然语言，系统需要从向量库或文档库检索售后政策，将政策文本与用户历史提问组合成提示词（Prompt），再发给大语言模型进行推断，最后将生成的自然语言或提取的结构化参数逐字返回给用户。

![传统 Web 架构与现代大模型应用架构对比](/images/content-rebuild/4de0e8a38419373e/fig-1.png)

这一过程给系统带来了四个主要的工程差异：

1. **高延迟与流式传输依赖**：大模型生成文本依赖自回归解码，逐个生成 Token。生成一段完整回答通常需要数秒至数十秒。如果采用传统的同步阻塞 HTTP 请求，客户端长时间等待容易超时，用户体验也很差。因此，系统接入层通常需要支持 Server-Sent Events（SSE）等流式传输方式，让用户即时看到前序字符。
2. **上下文即动态输入状态**：大模型本身是无状态的，不会自动记住上一次对话。系统每次推断前，都必须在编排层主动把会话历史、背景知识和系统设定拼接进输入上下文。上下文长度受模型硬件显存与算法设计约束，越长的上下文消耗的推理算力和费用越高，必须受到系统预算控制。
3. **输出的非确定性与防御验证**：大模型返回的内容并非预定义的数据库字段，即使设置低采样温度，也不能假设输出格式绝对固定。当系统需要用模型输出驱动后续业务逻辑时，必须经过格式校验（如 JSON Schema 校验）与安全合规过滤，并在解析失败时配置重试逻辑。
4. **受限的外部依赖与计费**：模型调用通常存在每分钟请求数（RPM）和每分钟 Token 数（TPM）配额限制，且单次调用计费明确。系统不能让外部请求无节制地直通模型，必须在网关层设置限流、鉴权与用量审计。

### 应用系统的四个核心分层

为了清晰界定职责，生产环境中的大模型应用通常划分为以下四层：

![大模型应用的四层架构拓扑与交互关系](/images/content-rebuild/4de0e8a38419373e/fig-2.png)

#### 1. 交互展示层（Client / UI Layer）
直接面向终端用户，承载网页、桌面客户端或移动端界面。其核心职责包括：
* 维持与后端的流式长连接，接收增量文本块（Chunk）并在界面上实现平滑打字机渲染。
* 解析 Markdown、代码块、LaTeX 公式与图表等富文本内容。
* 提供中断机制（如通过前端 `AbortController` 取消请求并在服务端联动中止上游调用），当用户主动点击“停止生成”时及时截断后续推流与生成，减少无效算力开销（需注意已完成的输入处理与已输出 Token 通常已产生计费）。

#### 2. 业务编排层（Application & Orchestration Layer）
负责承载核心业务逻辑，处理提示词组装和流程协调，不直接与硬件模型绑定：
* **身份与配额管理**：验证用户权限，检查租户的调用余额与可用额度。
* **提示词组装**：结合 [Prompt 模板系统](/llm-100/app-system/prompt-template-system.md)，将静态规则、业务参数与用户输入拼接为结构化的输入文本。
* **上下文管理**：从缓存或数据库获取历史对话，并根据 [上下文预算控制](/llm-100/app-system/context-budget.md) 策略执行截断、丢弃或摘要压缩。
* **知识与工具协调**：在需要补充背景信息或执行特定操作时，协调向量检索（RAG）或调用本地业务函数。

#### 3. 模型网关层（Model Gateway Layer）
位于业务后端与底层具体模型提供商之间的代理中介，主要职责是抹平差异和保障调用稳定：
* **统一协议转换**：把业务层发送的标准请求转换为不同提供商（如 OpenAI、Anthropic、本地部署的 vLLM 服务等）所要求的接口格式。
* **凭据与密钥管理**：集中维护各供应商的 API Key，避免凭据散落在各业务服务或暴露给前端。
* **流量控制与故障转移**：实施全局与租户级的 RPM/TPM 限流；在主模型提供商返回 429（限流）或 5xx 错误时，执行退避重试或自动路由至备用模型，具体方案见 [多模型路由](/architecture/multi-model-routing.md) 与 [模型网关设计](/architecture/model-gateway.md)。

#### 4. 数据持久与状态存储层（Data & Persistence Layer）
为系统提供长期记忆和基础数据支持：
* **关系型/文档数据库**：持久化存储用户资料、订单记录、对话归档和审计日志。
* **会话缓存（如 Redis）**：低延迟暂存近期活跃的对话上下文，支持高效的 [多轮对话历史管理](/llm-100/app-system/conversation-history.md)。
* **向量数据库**：存储文档切片及其稠密向量索引，用于语义检索与知识召回。
* **语义/结果缓存**：对于高频重复的提问或相同上下文，缓存模型输出以降低成本并加快响应，详见 [大模型应用缓存设计](/llm-100/app-system/llm-application-caching.md)。

### 请求处理的全流程

以用户向客服助手提问“跨国退货运费谁承担？”为例，请求从进入系统到返回结果，依次流经四个处理阶段：

![大模型应用核心请求处理管道时序与状态](/images/content-rebuild/4de0e8a38419373e/fig-3.png)

#### 阶段一：入站拦截与安全检查
用户的 HTTP POST 请求到达业务后端。系统首先校验 JWT 鉴权凭证与租户剩余调用额度，随后执行基础的前置安全防御，检测输入文本中是否包含恶意注入或违规内容。如果判定输入命中安全拦截规则，系统会直接返回预设的友好提示，不再向下游发起模型调用。

#### 阶段二：上下文检索与动态装配
通过安全检查后，业务编排层执行准备工作：
1. 读取当前 `session_id` 对应的最近几轮历史对话。
2. 将用户问题转成向量，在向量数据库中检索“跨境退换货政策”相关的条款切片。
3. 将系统角色设定、参考条款和历史对话拼装成规范的输入结构，并统计预估 Token 数。如果超过模型限制，按照预定策略裁剪更早的历史记录。

```json
// 业务编排层组装完成的标准调用结构示例
{
  "model": "qwen-max",
  "stream": true,
  "temperature": 0.3,
  "messages": [
    {
      "role": "system",
      "content": "你是官方售后助手。请根据以下参考资料回答，如果资料未提及，请说明无法确定。\n[资料: 跨国退货在非质量问题下由买家承担国际运费]"
    },
    {
      "role": "user",
      "content": "跨国退货运费谁承担？"
    }
  ]
}
```

#### 阶段三：网关中继与模型调用
业务层将装配好的载荷发送至模型网关。网关附加供应商认证凭据，向模型服务的接口发送请求（带有 `"stream": true` 参数）。模型服务在计算完输入上下文（Prefill 阶段）后，生成首个 Token，随后以流式数据包的形式逐步回传后续生成的文字碎片（Delta Token）。

#### 阶段四：流式解析与出站推流
模型网关将接收到的 Server-Sent Events（SSE）数据帧传递给业务编排层。业务层在推流过程中实时检测文本合规性，并通过长连接把 Token 逐字推送至前端界面，通信机制对比可参考 [SSE 与 WebSocket 的选择与实现](/llm-100/app-system/sse-vs-websocket.md)。若模型判定需要调用外部工具查询订单状态，系统会暂停向前端输出，执行本地函数后再将查询结果喂回模型继续生成。

### 长耗时任务处理：同步流式与异步队列的选型

对于一两百字的短对话，客户端与服务端维持一条数十秒的 SSE 同步连接即可满足需求。但在文档批量处理、大型代码库跨文件重构或多步 Agent 推理场景中，模型生成或链式调用可能持续数分钟甚至数小时。

![长耗时任务的同步与异步架构处理模式对比](/images/content-rebuild/4de0e8a38419373e/fig-4.png)

如果在长耗时场景下仍使用同步长连接，会带来明显的工程风险：
1. **网络超时与断连脆弱**：反向代理（如 Nginx）通常默认配置数十秒的读取超时。移动端弱网抖动或网络切换也极易造成 TCP 连接中断，导致服务端进程在客户端掉线后仍在空转扣费。
2. **服务端连接资源占用**：每个同步请求都需要操作系统占用文件描述符和内存缓冲，大量挂起的长连接会限制系统的并发承载能力。

针对不同耗时与场景，架构上通常做如下划分：

| 对比维度 | 同步流式连接 (Sync Streaming) | 异步任务队列 (Async Job Queue) |
| :--- | :--- | :--- |
| **典型通信协议** | HTTP / Server-Sent Events (SSE) | HTTP 提交作业 + 轮询状态 / WebSocket 通知 |
| **适用耗时范围** | 建议在网络代理超时阈值以内（常见为数十秒内） | 允许数分钟至数小时（无硬性网络连接限制） |
| **网络中断影响** | 客户端掉线容易导致结果丢失或难以恢复 | 任务状态持久化于队列和数据库中，重连后可拉取结果 |
| **服务端状态** | 依赖维持长连接的进程上下文 | 任务由独立的 Worker 进程异步拉取执行，支持水平伸缩 |
| **典型业务场景** | 网页即时问答、短文本润色、辅助代码补全 | 深度文档分析、全仓代码扫描、批量离线评测 |

异步长任务的具体调度与状态同步可深入阅读 [异步任务处理](/architecture/async-tasks.md) 与 [长任务执行系统](/architecture/long-task-execution.md)。

### 系统的工程稳定性与安全保障

把原型推进至生产环境时，需要在网关和编排层增加以下三项保护措施：

![生产级模型网关的限流、熔断与动态降级拓扑](/images/content-rebuild/4de0e8a38419373e/fig-5.png)

#### 1. 凭据隔离与权限边界
前端代码运行在用户可控的环境中，若直接在前端存放模型 API Key，用户可以通过浏览器控制台轻松提取凭据，导致账户被盗刷。必须由独立的后端服务或模型网关持有 API Key，前端仅持有业务系统发放的有时效性 Token，以此保证细粒度的租户计费核算和系统提示词（System Prompt）的安全隔离。

#### 2. 分布式链路追踪（Tracing）
一次用户提问背后可能包含向量化、知识库多路召回、重排以及多次模型调用。链路监控需要记录以下几个针对大模型场景的关键指标：
* **首字延迟（Time to First Token, TTFT）**：从发起请求到收到第一个 Token 的耗时，反映模型对输入上下文的预填充计算（Prefill）速度以及排队情况。
* **生成吞吐率（Tokens Per Second, TPS）**：衡量模型自回归解码（Decode）阶段的生成速度。
* **Token 消耗统计**：分别记录 Prompt Token 与 Completion Token，作为成本核算和限额审计的依据，详见 [日志与 Trace 设计](/architecture/logging-trace.md)。

#### 3. 限流、重试与熔断降级
云端模型服务常因瞬时并发过高返回 HTTP 429（Rate Limit Exceeded）或发生服务抖动。模型网关应内置保护策略：
* **退避重试**：遇到 429 或瞬时网络超时错误时，采用指数退避并叠加随机抖动（Jitter），防止所有客户端在固定间隔同时发起重试导致二次冲击。
* **断路器熔断**：在特定时间窗口内，若主模型错误率达到预设阈值，断路器自动跳闸，将流量临时切往备用模型或降级为简要规则输出，避免全业务链路挂起，具体容灾策略见 [高可用设计](/architecture/high-availability.md)。

### 验证实验：网关退避重试与备用降级

下面提供一段可运行的 Python 验证脚本。代码模拟了当主模型服务频繁返回限流（429）异常时，网关如何通过指数退避机制重试，并在重试耗尽后平滑切换至备用模型。

![模型网关备用路由降级实验流程](/images/content-rebuild/4de0e8a38419373e/fig-6.png)

```python
# 验证模型网关重试与备用路由降级逻辑（单机模拟示意）
import time
import random

class ModelRateLimitError(Exception):
    pass

def call_primary_provider(prompt: str) -> str:
    # 模拟主模型服务有 70% 的概率抛出 429 限流错误
    if random.random() < 0.7:
        raise ModelRateLimitError("HTTP 429: Rate Limit Exceeded")
    return f"[主模型正常响应] 用户提问: {prompt[:15]}"

def call_backup_provider(prompt: str) -> str:
    # 模拟备用模型稳定响应
    return f"[备用模型降级响应] 用户提问: {prompt[:15]}"

def gateway_dispatch(prompt: str, max_retries: int = 2) -> dict:
    start_time = time.time()
    
    # 1. 尝试主模型并在遇到限流时执行指数退避重试（初始调用 1 次 + 最多重试 max_retries 次）
    for attempt in range(max_retries + 1):
        try:
            output = call_primary_provider(prompt)
            return {
                "status": "success",
                "provider": "primary",
                "output": output,
                "elapsed": round(time.time() - start_time, 3)
            }
        except ModelRateLimitError as err:
            if attempt < max_retries:
                # 仍有重试配额，计算退避时间并附加微量随机抖动
                wait_time = 0.1 * (2 ** attempt) + random.uniform(0, 0.05)
                print(f"主模型调用失败（第 {attempt + 1} 次）: {err}，等待 {wait_time:.3f} 秒后重试...")
                time.sleep(wait_time)
            else:
                # 重试耗尽，不再无谓休眠等待，准备切换
                print(f"主模型调用失败（第 {attempt + 1} 次）: {err}，重试超限，平滑切至备用提供商...")
            
    # 2. 激活备用模型
    fallback_output = call_backup_provider(prompt)
    return {
        "status": "fallback",
        "provider": "backup",
        "output": fallback_output,
        "elapsed": round(time.time() - start_time, 3)
    }

if __name__ == "__main__":
    query = "跨国退货国际运费由谁承担？"
    result = gateway_dispatch(query)
    print("\n网关最终返回结果:", result)
```

运行上述代码多次可以观察到：即使底层主模型频繁产生限流故障，网关层通过局部重试和备用路由接管，对上层调用方始终返回可用结果，从而保障了业务可用性。
