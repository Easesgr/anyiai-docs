在调用大语言模型（LLM）构建业务系统时，每次模型请求通常需要消耗数百毫秒到数秒的时间，并且大多按 Token 数量产生直接计费。在前面[《上下文长度不够怎么办？》](/llm-100/app-system/context-budget.md)中，我们通过切分和压缩控制了单次请求的上下文预算；但如果大量用户反复询问相同或高度相似的问题，重复调用底层模型依然会带来延迟和预算压力。

解决这个问题的直接手段是在应用层引入缓存。我们先来看一个贯穿本文的具体例子：一家公司的企业内部问答助手，每天会收到成百上千条员工提问。

* 员工 A 提问：“公司的餐补标准是多少？”
* 员工 B 随后提问：“公司的餐补标准是多少？”（字面完全相同，适合精确匹配）
* 员工 C 提问：“请问员工每天餐费补贴多少钱？”（字面不同但意图一致，需要语义缓存）
* 员工 D 提问：“我昨天提交的报销单什么时候能批？”（包含强时效性与个人身份，不能随意走通用缓存）

大模型应用的缓存设计，就是要判断哪些问题可以直接返回历史结果，哪些需要模糊匹配，哪些必须穿透给模型。

## 概念区分：应用层缓存与推理引擎的 KV Cache

许多开发者容易将“应用层缓存”与“模型显存中的 KV Cache”混淆。这两者位于完全不同的技术层级，解决的问题也不一样：

1. **显存 KV Cache（推理层）**：运行在 GPU 显存与推理框架（如 vLLM、TensorRT-LLM）内部。自回归模型在逐个生成 Token 时，历史所有 Token 计算出的 Key 和 Value 向量保持不变。推理引擎将它们缓存在显存中，避免每生成一个新词就重新计算一遍整段前文。它优化的是**单次推理任务内部的解码速度**，依然会执行完整的计算流程。
2. **应用层缓存（网关与服务层）**：运行在应用的后端服务或 API 网关中（如 Redis、向量数据库）。它将用户的提问或提示词作为键（Key），将模型之前生成的整段文本作为值（Value）。当系统判定当前请求命中历史记录时，直接将旧答案返回给客户端，**完全不发起对大模型 API 的调用**，从而将耗时从数秒降低到数十毫秒，并将该次调用的模型 Token 成本降为零。

![大模型应用缓存架构全景](/images/content-rebuild/166e3550871e720a/cover.png)

在应用层，缓存实现通常分为两大类：基于哈希比对的**精确匹配缓存（Exact Match Cache）**，以及基于向量近邻检索的**语义缓存（Semantic Cache）**。

## 精确匹配缓存：哈希比对与确定性边界

精确匹配缓存采用传统的键值存储（如 Redis）。核心逻辑是：当新请求的输入参数、系统提示词以及模型配置与历史请求完全一致时，直接读取历史输出。

### 缓存键的构造原则

在普通的 Web 系统中，API 路径加请求参数往往就能构成缓存键。而在[大模型接口调用流程](/llm-100/app-system/model-api-request-lifecycle.md)中，影响模型输出的因素远不止最终那句提问。一个可靠的精确缓存键，至少需要包含以下几项序列化内容：

1. **渲染后的完整提示词**：经过[Prompt 模板系统](/llm-100/app-system/prompt-template-system.md)渲染后的 System Prompt，以及当前 User Query。
2. **历史上下文**：经过[多轮对话历史管理](/llm-100/app-system/conversation-history.md)裁剪后的整段历史消息列表。
3. **模型名称、版本与超参数**：例如具体模型版本、`temperature`、`top_p` 以及声明的工具配置（`tools`、`tool_choice`）。不同参数与工具定义会直接改变模型的分支走向与输出结构。
4. **租户与权限标识**：多租户系统下的企业 ID（Tenant ID）或用户权限范围，防止跨租户或越权读取缓存。

```python
import hashlib
import json
from typing import Any, Dict, List, Optional

def generate_exact_cache_key(
    model: str,
    messages: List[Dict[str, Any]],
    temperature: float,
    tenant_id: str,
    tools: Optional[List[Dict[str, Any]]] = None
) -> str:
    """
    将影响模型生成结果的关键参数统一序列化，生成 SHA-256 哈希键
    """
    payload = {
        "tenant_id": tenant_id,
        "model": model,
        "temperature": temperature,
        "messages": messages,
        "tools": tools or []
    }
    # 必须指定 sort_keys=True，避免 Python 字典键遍历顺序不一致导致哈希改变
    serialized = json.dumps(payload, sort_keys=True, ensure_ascii=False)
    return hashlib.sha256(serialized.encode("utf-8")).hexdigest()
```

### 适用条件与温度参数（Temperature）

精确匹配能够成立的工程前提不仅包含**输出的可复现性**，还取决于**业务状态的时效性与无外部副作用**：

* **采样温度与一致性**：当业务场景将 `temperature` 设置为 `0`（或接近 0 的极低值）时，模型采用贪心解码，相同的输入在绝大多数情况下会输出高度一致的文本，此时建立缓存收益很高；而在创意写作等设置 `temperature >= 0.7` 的场景，用户期望多样化回复，强行缓存会损害体验。
* **哈希相等不等于业务答案正确**：即使输入参数完全一致且 `temperature=0`，哈希命中也仅代表当前发给模型的静态请求体相同。如果任务涉及外部工具调用（如查实时汇率、库存）、包含实时时间等动态变量、底层知识库已更新，或者服务端静默升级了模型小版本权重，直接返回旧答案就会引发业务错误。因此，精确匹配必须配合数据时效（TTL）、依赖版本指纹，或仅用于无外部动态状态依赖的纯静态任务中。

因此，精确匹配缓存通常用于制度问答、静态代码检测、标准化结构解析等对一致性要求高且依赖数据相对固定的场景。

## 语义缓存：基于向量嵌入的相似度匹配

自然语言往往“同义不同词”。在公司问答助手中，“电脑补贴怎么申请？”和“请问如何领取电脑补贴？”在字符上完全不同，精确哈希必然不命中。为了拦截这类同义表达，系统需要引入**语义缓存（Semantic Cache）**。

### 向量检索与阈值判定机制

语义缓存通过文本嵌入模型（Embedding Model）将用户的提问转为稠密向量，并存入支持向量近邻检索的存储引擎（如 Redis VSS、Qdrant、Milvus）。当收到新提问时，系统先在向量库中寻找距离最近的历史问题。

常用的度量方式是余弦相似度（Cosine Similarity）。对于当前提问向量 $\mathbf{v}_q$ 与缓存中的历史问题向量 $\mathbf{v}_i$：

$$\text{Sim}(\mathbf{v}_q, \mathbf{v}_i) = \frac{\mathbf{v}_q \cdot \mathbf{v}_i}{\|\mathbf{v}_q\| \|\mathbf{v}_i\|}$$

如果历史库中最大的相似度 $\max_i \text{Sim}(\mathbf{v}_q, \mathbf{v}_i) \ge \tau$（$\tau$ 为预设阈值），系统判定语义命中，直接取出与该历史提问绑定的模型回答返回。

![语义缓存的向量检索与阈值判定机制](/images/content-rebuild/166e3550871e720a/fig-2.png)

下面是语义缓存核心判断逻辑的代码示意：

```python
import numpy as np
from typing import Optional, List, Dict

class SemanticCache:
    def __init__(self, similarity_threshold: float = 0.88):
        self.threshold = similarity_threshold
        self.records: List[Dict] = []  # 实际工程中对应向量数据库

    def query(self, query_vector: np.ndarray) -> Optional[str]:
        if not self.records:
            return None
        
        # 归一化后点积即为余弦相似度（此处做单条遍历示意）
        q_norm = query_vector / np.linalg.norm(query_vector)
        best_score = -1.0
        matched_answer = None

        for item in self.records:
            c_norm = item["vector"] / np.linalg.norm(item["vector"])
            sim = float(np.dot(q_norm, c_norm))
            if sim > best_score:
                best_score = sim
                matched_answer = item["answer"]

        if best_score >= self.threshold:
            return matched_answer
        return None

    def store(self, query_vector: np.ndarray, answer: str):
        self.records.append({"vector": query_vector, "answer": answer})
```

需要注意的是，语义缓存本身需要先调用一次 Embedding 模型，再执行一次近邻搜索。这两步耗时通常在 20~80 毫秒之间。相比大模型生成整段回答所需的数百毫秒至数秒，这几十毫秒的开销是划算的，但它绝非零成本。

## 语义缓存的落地陷阱与边界

语义缓存虽然扩大了拦截范围，但向量空间的连续性也带来了典型的错误匹配风险。在生产落地时，常见以下三类问题。

### 1. 关键实体与反义词误命中

通用的 Embedding 模型侧重于捕捉全局主题，对于局部单字的改变往往不够敏锐：

* **时间与数值实体**：“帮我查**明天**的会议安排”与“帮我查**昨天**的会议安排”。两句话仅相差一个时间词，在通用向量模型计算下，余弦相似度可能高达 0.92。如果直接走语义缓存，用户会拿到昨天的会议记录，引发业务错误。
* **否定句与反义词**：“这个合同**可以**盖章吗”与“这个合同**不可以**盖章吗”，两者的语义主题高度重合，向量空间距离往往极其接近。

![实体与反义词引发的语义缓存误命中陷阱](/images/content-rebuild/166e3550871e720a/fig-3.png)

**应对方案**：
不能单凭向量相似度做决定。在进入向量比对前或比对后，增加**关键槽位校验（Slot Checking）**。例如先通过轻量规则或命名实体识别（NER）提取出时间、金额、人名或否定词。只有在“实体槽位一致”且“向量相似度超过阈值”的联合条件下，才允许命中缓存。

### 2. 多轮对话中的指代缺失

在多轮对话中，用户往往会使用代词或省略句。例如：

* 用户：“请问公司买 MacBook Pro 有补贴吗？”
* 模型：“有，每年最高补贴 3000 元。”
* 用户继续问：“那 ThinkPad 呢？”

如果直接把最后一句话“那 ThinkPad 呢？”单独拿去算向量并写进缓存，下一次若有另一个用户在讨论公积金时问“那 ThinkPad 呢？”，系统就会错误取出电脑补贴的回复。

![多轮对话中上下文缺失导致的缓存失效](/images/content-rebuild/166e3550871e720a/fig-4.png)

**应对方案**：
多轮对话不能直接缓存单句。进入语义缓存的提问文本，必须是结合前序上下文经过[多轮对话历史管理](/llm-100/app-system/conversation-history.md)改写后的“独立提问”（例如自动改写为“请问公司买 ThinkPad 有补贴吗？”）；或者将前序会话摘要与当前提问拼装后再参与检索。

### 3. 相似度阈值的两难选择

相似度阈值 $\tau$ 的调节直接决定系统的准确率与覆盖率：

* 阈值过高（如 0.98）：只有错别字或微小的虚词变化能命中，语义缓存基本退化为拼写纠错器，命中率过低。
* 阈值过低（如 0.80）：命中率明显提升，但大量语意有细微差异的问题（如“年假怎么休”与“事假怎么休”）会混淆，导致答非所问。

在实际工程中，不能直接沿用开源工具的默认阈值。应当收集业务场景下几百组真实同义句与易混淆非同义句，计算模型打分分布，确定兼顾准确率与命中率的阈值切分点。

## 生产防护与多级缓存架构

在实际的[大模型应用系统架构](/llm-100/app-system/llm-app-architecture.md)中，通常将不同开销的缓存技术分层组合，形成阶梯式的拦截管道。

### 阶梯式多级缓存设计

按照检索延迟由低到高，典型架构分为四层：

1. **L1 进程内存精确缓存**：在单机服务内存中使用 LRU 缓存（如 Python 的 `cachetools`）。拦截极短时间内（如数秒内）完全相同的重复请求，耗时处于微秒级。
2. **L2 分布式精确缓存**：在 Redis 集群中存储全局哈希键，支持跨多实例共享，耗时在数毫秒级。
3. **L3 向量语义缓存**：在前置过滤通过后，调用 Embedding 模型并在向量库中做近邻匹配，耗时约数十毫秒。
4. **Fallback 真实模型调用**：当以上三层均未命中时，才将请求真正转发给底层模型网关。

### 缓存更新与主动失效机制

大模型系统常常依赖外部知识库，例如[企业知识库问答系统](/llm-100/app-system/enterprise-knowledge-qa.md)。一旦制度变更或文档更新，旧缓存必须能够同步失效：

* **版本号注入**：将知识库的数据版本号（如 `doc_v2.1`）直接编入精确缓存键或作为语义缓存的过滤元数据（Metadata Filter）。当知识库重建或文档发布新版时，版本号递增，旧版本关联的缓存自动失去检索资格。
* **生存时间（TTL）**：为所有缓存记录设置兜底有效时间，例如 24 小时或 7 天，避免脏数据长期驻留。
* **事件驱动删除**：在内容管理系统删除或修改文档时，通过消息队列主动向向量库和 Redis 下发删除指令。

### 击穿与雪崩的工程防范

大模型单次调用的计算开销极大，并发穿透时对后端造成的压力比传统 Web 系统更剧烈：

* **缓存击穿（Breakdown）**：某个极高频的热点问题（如全员通知发布时引发的集中提问）在缓存失效的瞬间，几十上百个并发请求同时到达。如果所有请求同时穿透到底层模型网关，会导致 API 额度超限或产生高额账单。
  * **防范方案**：采用**单飞互斥锁（Singleflight）**机制。在当前实例或全局内，只允许排在第一位的请求去调用模型 API，其余等待该请求完成后，共享写入的缓存结果并返回。
* **缓存雪崩（Avalanche）**：大量缓存设置了完全相同的固定过期时间，到期时同时失效，瞬间将流量全部压向模型网关。
  * **防范方案**：采用**带抖动的过期时间（Jittered TTL）**。在设定的基准时间（例如 24 小时）基础上，叠加一段均匀分布的随机偏移（例如 $\pm 15\%$），打散失效时间点。
