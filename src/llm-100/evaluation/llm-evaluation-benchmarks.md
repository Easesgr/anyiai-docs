评估传统分类模型时，准确率、精确率、召回率或 F1 值能给出明确的度量。但是面对大语言模型（LLM）时，这项工作变得复杂许多。

以一个电商客服助手为例：若用户提问“我买的衣服尺码偏小，发票抬头开错了，能换货并重开发票吗？”，模型可能回答“可以换货，发票也可以重新开具”，也可能回答“支持更换尺码，请将原商品与原发票一并寄回，我们在收到后为您办理重开与换货”。两段回答字面完全不同，但业务处理逻辑均正确；而如果模型回答“可以换货，发票丢失不影响”，字面流畅度极高，业务规则上却是错的。单纯使用传统的字符匹配算法（如 BLEU、编辑距离）很难反映这种实际质量差异。

业内通常使用公开基准（Benchmark）来横向对比不同模型的能力，但公开跑分并不能直接等同于业务落地的效果。

### 自由文本评测的核心难点

自回归语言模型的输出空间是开放的自然语言文本，这种开放性带来了三个具体的评测难题：

1. **多解性与语义等价**：同一个问题存在多种字面完全不同但逻辑等价的表达形式。对于数学题，输出“8”、“答案是 8”、“最终计算结果为八”或经过长篇推理后在末尾总结“8”，业务语义完全一致，但字符重叠率差异明显。
2. **中间过程与最终结果的解耦**：在复杂的推理任务中，模型可能每一步推导逻辑都正确，却在最后一步抄错数字；或者推理过程胡言乱语，最后偶然猜中了正确数字。若仅通过抓取最终答案进行判断，会掩盖模型的真实推理鲁棒性。
3. **自动化评分器的主观偏差**：人工打分成本高昂且标注一致性难以长期保持；若引入大模型作为裁判（LLM-as-a-judge），评判模型自身也存在系统性偏差：
   - **位置偏差**：在对比两个候选回答时，倾向于给排在前面的回答打高分。
   - **长度偏差**：倾向于给字数更多、排版更丰富（带列表、加粗）的回答打高分，即使内容包含套话或废话。
   - **自我偏好**：倾向于给自己生成的文本或风格相近的模型打更高分。

![传统分类评估与大模型自由文本评估的决策与验证路径对比](/images/content-rebuild/243f1f5f9c4c7269/fig-1.png)

上图对比了传统分类评估与生成式评估的路径差异。传统模型输出受限于离散类别空间，验证逻辑确定；而生成式模型输出的是连续自由文本，必须借助对数似然映射、规则抽取或模型打分等中间层进行验证。

### 常见公开基准（Benchmark）解析

为了衡量大模型的通用能力，学术界与工业界构建了一系列标准测试集，覆盖知识储备、逻辑推理与代码生成三个主要方向。

```
                                  ┌── MMLU (57个学科/单选题/Log-likelihood或生成抽取)
              ┌── 知识与通识理解 ──┼── C-Eval / CMMLU (中文学科与综合常识)
              │                   └── HELM (多维度标准化评测集合)
              │
              ├── 数学与符号推理 ──┬── GSM8K (小学应用题/多步链式推理)
主流基准体系 ──┤                   └── MATH (竞赛级数学题/LaTeX公式推导)
              │
              ├── 代码生成与执行 ──┬── HumanEval (Python函数单元测试 pass@k)
              │                   └── SWE-bench (真实 GitHub Issue 修复)
              │
              └── 人类交互与对战 ──── LMSYS Chatbot Arena (众包双盲 Elo 评分)
```

#### 1. 知识理解：MMLU

**MMLU（Massive Multitask Language Understanding）** 包含 57 个学科领域（如初等数学、计算机科学、法律、临床医学等），题型为四选一单选题。它主要测试预训练过程中沉淀的知识广度与常识关联能力。中文场景下的同类基准包括 C-Eval 和 CMMLU。

#### 2. 数学推理：GSM8K 与 MATH

- **GSM8K（Grade School Math 8K）**：包含 8500 道小学级数学文字应用题，通常需要 2 到 8 步的四则运算。该基准用于检验模型的逐步推理（Chain-of-Thought, CoT）能力和中间状态维护能力。
- **MATH**：包含 12,500 道高中及竞赛难度的数学题，涉及代数、数论与微积分，要求输出包含 LaTeX 复杂公式的推导步骤，题目难度远高于 GSM8K。

#### 3. 代码生成：HumanEval

由 OpenAI 推出的代码评测基准，包含 164 道手写 Python 编程题。每道题由函数签名、文档描述、函数实现和平均 7.7 个单元测试用例组成。评测时将模型生成的代码放入沙箱中运行，以 **pass@k** 指标度量：

$$\text{pass@k} = \mathbb{E}_{\text{Problems}} \left[ 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}} \right]$$

其中 $n$ 为对单道题目生成的总代码候选数（要求 $n \ge k$），$c$ 为通过全部单元测试的样本数。工业界最常报告的是 **pass@1**（生成一次即通过的概率）。该基准不使用字符匹配，直接以代码的可执行性与测试通过率作为验收依据。

![典型基准测试形式、考察目标及校验机制对比](/images/content-rebuild/243f1f5f9c4c7269/fig-2.png)

上图梳理了三种典型基准的验证机制演进：从静态选项的概率比对，到逐步推理的文本抽取，再到动态沙箱环境的代码执行，评测客观性逐步增强，但运行环境和计算成本也依次上升。

### 评测执行机制：对数似然打分与自由生成抽取

在执行选择题类基准（如 MMLU）时，评测方式的选择会显著影响最终得分。业内主要存在两种执行机制。

#### 方式 A：对数似然打分（Log-likelihood Scoring）

该机制常见于开源白盒评测框架（如 EleutherAI 的 lm-evaluation-harness）。模型并不进行逐字采样生成，而是将题目 Prompt 分别与候选项（A、B、C、D）拼接，计算模型预测该选项 Token 序列的条件对数似然值，选取得分最高的选项：

$$\hat{y} = \arg\max_{i \in \{A, B, C, D\}} \sum_{t=1}^{|T_i|} \log P\left(w_{i,t} \mid \text{Prompt}, w_{i,<t}\right)$$

- **前置条件**：评测程序必须能获取模型输出层完整的词表对数几率（Logits），因此适用于开源白盒基础（Base）模型。
- **技术局限**：对指示微调（Instruct/Chat）模型不够友好。经过对齐微调的模型习惯于输出连贯的对话解答，在首字输出单一选项 Token 的对数几率分布往往会发生偏移；另外，选项本身的词频偏差也会干扰判断。

#### 方式 B：自由生成与规则抽取（Generative Evaluation）

通过少样本提示（Few-shot）或指令约束，让模型通过自回归采样自由输出一段文本，随后评测程序使用正则表达式抽取其中的选项或最终数字（如抽取 `答案是：(A|B|C|D)` 或 `#### (\d+)`）。

- **前置条件**：适用于黑盒 API 模型与白盒对话模型，允许模型先输出思维链（CoT）推导过程，再得出结论。
- **技术局限**：强依赖正则匹配规则。如果模型推理正确，但回复格式写成了“综上所述应该选A”，而规则只匹配“答案是：A”，则会被误判为错误。这种方式评测的是“推理能力 + 严格遵循格式指令能力”的复合表现。

![选择题对数似然计算与自回归生成正则抽取两种路径流程图](/images/content-rebuild/243f1f5f9c4c7269/fig-3.png)

从上图可以看出，对数似然打分是单次前向传播的概率统计，绕过了采样解码；而自由生成评测包含完整的自回归生成与后处理抽取流程。

#### 代码实现：两种评测机制的逻辑对比

下面这段 Python 代码直观展示了两种评测机制在工程实现上的核心区别：

```python
import re
import numpy as np

prompt = "问题：中国的首都是哪里？\nA. 上海\nB. 北京\nC. 广州\nD. 深圳\n答案："
choices = ["A", "B", "C", "D"]

# ---------------------------------------------------------
# 方案 A：对数似然打分机制（需要模型底层 Logits 输出）
# ---------------------------------------------------------
def evaluate_by_loglikelihood(mock_token_probs, choices_list):
    """
    根据给定 prompt 下候选 token 的条件概率计算 log-likelihood
    此处以单 token 选项为例进行示意
    """
    choice_log_probs = {}
    for c in choices_list:
        prob = mock_token_probs.get(c, 1e-12)
        choice_log_probs[c] = float(np.log(prob))
    
    # 选取条件对数概率最大的选项
    selected_choice = max(choice_log_probs, key=choice_log_probs.get)
    return selected_choice, choice_log_probs

# 模拟模型输出层对于首个 token 的预测概率分布
mock_logits_probs = {"A": 0.04, "B": 0.85, "C": 0.06, "D": 0.05}
pred_choice, scores = evaluate_by_loglikelihood(mock_logits_probs, choices)
print(f"[Log-likelihood 机制] 选定项: {pred_choice}, 分布得分: {scores}")

# ---------------------------------------------------------
# 方案 B：自回归自由生成与正则抽取机制（针对 API / Chat 模型）
# ---------------------------------------------------------
def evaluate_by_generation(generated_text):
    """
    使用预定义正则表达式从自由生成的自然语言中提取答案标记
    """
    patterns = [
        r"答案是[：:\s]*([A-D])",
        r"(?:选|选项)[：:\s]*([A-D])",
        r"\b([A-D])\b(?=[^A-D]*$)"  # 匹配末尾单独出现的选项字母
    ]
    for pattern in patterns:
        match = re.search(pattern, generated_text)
        if match:
            return match.group(1)
    return "PARSE_ERROR"  # 格式未匹配，提取失败

# 模拟模型输出了推导过程与结论
generated_answer = "经过地理与政治常识分析，中国的首都是北京。因此选：B。"
parsed_result = evaluate_by_generation(generated_answer)
print(f"[自由生成抽取机制] 提取结果: {parsed_result}")
```

如果模型输出“我认为应该去北京看升旗”，方案 B 的正则将返回 `PARSE_ERROR` 判为错误，尽管模型的地理认知是正确的；而方案 A 则完全依赖首个 Token 的词表几率。因此，对比公开论文的分数时，必须确认其执行机制是否相同。

### 公开基准的现实局限

基准跑分并不能完整等同于模型的真实能力，开发者需要注意以下两个常见偏差。

#### 1. 数据污染（Data Contamination）

现代大语言模型的预训练数据包含数万亿 Token，大多抓取自公开互联网。GSM8K、MMLU、HumanEval 的题干与答案已在各类网页、技术文章与仓库中广泛传播。若数据清洗过滤不严密，测试样本就可能混入训练数据中：

- **完全重合**：测试题目与答案逐字出现在预训练语料中，模型只需记忆复现即可得分。
- **语义改写**：题目中的数字或实体名称被替换，但题型框架已被模型记忆过拟合。

![训练集与测试集污染途径及检验策略机制图](/images/content-rebuild/243f1f5f9c4c7269/fig-4.png)

上图展示了污染排查的两种常用工程方法：
- **n-gram 重叠度分析**：计算测试题与预训练数据之间的 8-gram 或 13-gram 字符级重叠率。若测试集长句的出现比例显著高于常态，存在语料泄露风险。
- **时间切片对比（Time-split Evaluation）**：选取模型知识截断日期（Cut-off Date）**之前**发布的 Benchmark 题目，与知识截断日期**之后**同等难度的全新私有题目进行比对。若模型在旧题上能拿 85 分，在同难度新题上降至 50 分左右，说明其在旧数据集上存在记忆过拟合现象。

#### 2. 提示词敏感性（Prompt Sensitivity）

自由生成式评测对 Prompt 的微调非常敏感。下表整理了在同一模型上仅微调提示词格式时，GSM8K 准确率出现的变动范围（数据为实验示意区间）：

| 提示词变体形式 | 模板构造示例 | GSM8K 准确率变动（示意区间） |
| :--- | :--- | :--- |
| 标准 8-shot CoT | `Q: ... A: Let's think step by step ... Output: #### X` | 基准基线（假设 72.0%） |
| 改变少样本示例顺序 | 保持 8 个示例不变，打乱先后排列次序 | $\pm 2.0\% \sim 3.0\%$ 波动 |
| 调整引导词前缀 | 将 `Answer:` 替换为 `The result is:` | $\pm 3.0\% \sim 4.5\%$ 波动 |
| 移除分隔空行 | 去掉题目与答案之间的换行符 `\n\n` | $\pm 1.0\% \sim 2.0\%$ 波动 |

由于不同评测框架使用的 Prompt 模板并不一致，直接拿不同技术报告中的公开分数作横向判断往往会失真。

### 评测基准与方法的演进

为了缓解静态单选题与简单生成题的局限，评测基准正朝着多维化、动态化与环境交互方向发展。

![评测体系从静态离散单选题到动态闭环智能体执行的演化阶梯](/images/content-rebuild/243f1f5f9c4c7269/fig-5.png)

上图展现了评测维度的递进方向：

1. **HELM（Holistic Evaluation of Language Models）**：由斯坦福大学提出，不再仅看单一准确率指标，而是从准确性（Accuracy）、鲁棒性（Robustness）、偏见程度（Bias）、毒性（Toxicity）与响应延迟（Latency）等多维度进行综合画像。
2. **LMSYS Chatbot Arena（众包双盲对战）**：引入国际象棋的 Elo 积分算法。用户输入任意自定义 Prompt，系统隐去模型名称，调用两个不同模型同时作答，由用户盲测投票。这引入了大量动态且贴近真实需求的长尾 Query，降低了刷分风险。其局限在于普通用户的投票存在主观偏好（例如更偏向文字工整、语气客气的回答）。
3. **SWE-bench 与智能体任务**：从问答转向复杂工程执行。SWE-bench 从 GitHub 开源项目中收集真实 Issue，要求模型在完整的代码仓库中定位 Bug、编辑跨文件代码，并确保单元测试通过，用于衡量长上下文和动态环境下的代码工程能力。

关于文本生成的具体量化指标（如 ROUGE、BLEU 的统计匹配与人工校验协议），可参阅 [/llm-100/evaluation/generation-quality-metrics.md](/llm-100/evaluation/generation-quality-metrics.md)；若需了解检索增强场景的专业评估方案，可参考 [/fundamentals/evaluation-metrics/rag-evaluation.md](/fundamentals/evaluation-metrics/rag-evaluation.md)。

### 业务私有评测集的构建流程

公开 Benchmark 主要用于宏观粗筛，模型在具体业务中的表现，必须基于私有评测集进行闭环验证。

![企业自建专属业务评测集的四步工程闭环体系](/images/content-rebuild/243f1f5f9c4c7269/fig-6.png)

结合上图的工程流水线，构建业务私有评测集通常包含以下四个步骤：

#### 第一步：构建业务代表性测试样本库

不要直接把未清洗的全部线上日志塞进评测集，应该按业务逻辑分层采样：
- **意图与实体覆盖**：按高频业务分类（如换货咨询、发票疑问、物流催单）和实体分布（品牌、商品型号）进行按比例抽样。
- **边界与异常样本注入**：正向业务样本占主体的同时，主动加入 15%~20% 的边缘 Case（如模糊提问、越权指令输入、乱码或无关长文本），检验系统容错能力。

#### 第二步：确立严密的评分细则（Rubrics）

根据任务类型选择度量方式：
- **结构化信息抽取**：使用字段级精准匹配率（Exact Match）或 F1 值。
- **开放性问答与总结**：制定明确的打分细则（Rubric）。如果引入大模型裁判进行绝对评分（参考 Ragas 等框架的评估机制），Prompt 需设置具体的 1 至 5 分参考锚点，并要求“先输出判定依据，再输出分数”以提高评分稳定性；若采用成对对比（Pairwise Comparison），则应交换两个候选回答的呈现顺序（Swap Position）分别调用，通过比对两次结果缓解位置偏差。

#### 第三步：版本冻结与防污染隔离

业务评测集审定后，需使用版本控制系统锁定（如通过 Git LFS 保存不可变文件）。严格禁止业务测试数据流入任何训练集群的微调（SFT）语料库或 RAG 检索知识库。开发调优集合（Dev Set）必须与最终评测集合（Test Set）做好物理隔离。

#### 第四步：CI/CD 自动化回归集成

将评测脚本接入开发流水线。当底层模型更换、系统 Prompt 微调、RAG 检索参数变更或本地微调权重更新时，自动化触发回归测试并生成差异对比报告，只有在关键业务指标不发生负向回归的情况下才允许上线。关于系统层面的整体评测架构，可参阅 [/architecture/ai-evaluation.md](/architecture/ai-evaluation.md)。

### 本讲小结与练习

- 公开 Benchmark（MMLU、GSM8K、HumanEval）反映了模型在通识、数学推理和代码编写上的基线水平，但其绝对分数受对数似然打分与自由生成抽取等执行机制的直接影响。
- 数据污染与 Prompt 敏感性是公开静态榜单的主要缺陷，不能仅凭排行榜高低作为选型依据。
- 业务落地需建立私有评测集：通过分层抽样、明确评分细则、隔离测试集以及自动化回归，形成可重复验证的工程护栏。

#### 可检验练习

**练习目标**：实现一个具有“消解位置偏差”能力的 LLM 裁判比对函数。
