在开发大语言模型应用时，团队经常面临方案选型难题：遇到专业术语和固定格式，是用微调还是写 Prompt？业务数据频繁更新，该建 RAG 检索库还是定期增量训练？面对多步查询和比对校验，什么时候才真正需要引入 Agent 编排？

选型的关键在于明确两件事：**信息究竟应该保存在模型权重里还是在外部存储中**，以及**任务执行是单次前向推理还是多轮环境交互**。

在上一讲[/llm-100/evaluation/reducing-hallucinations.md](/llm-100/evaluation/reducing-hallucinations.md)中，我们分析了抑制模型幻觉的技术手段。本讲以一个贯穿全文的“企业财务合规质检系统”为例，梳理检索增强生成（RAG）、模型微调（Fine-Tuning）与智能体（Agent）各自的运行机理与技术边界，给出工程决策矩阵与组合架构设计。

## 一个贯穿场景：企业合规质检系统

为了让每项技术的职责和取舍更加具体，我们设定一个典型的业务系统：

*   **业务目标**：自动审查企业财务合同与各季度财报，检查是否违反最新监管规定。
*   **数据特征**：监管合规条款每月甚至每周都有增补与局部调整；上市公司每季度披露新财报。
*   **输出要求**：必须输出字段严格对齐的审计 JSON 报告，包含条款编号、违规原文摘录和风险定级，格式不允许解析失败。
*   **分析逻辑**：部分复杂审计需要对比“目标公司 Q3 财报”与“行业龙头 Q3 财报”在同口径下的毛利率与应收账款，需要多步查询与交叉求证。

接下来，我们借助这个场景，看三种技术方案如何各自发挥作用，又在何处遇到瓶颈。

## 三类技术路线的机理与边界

![三类技术路线机理对比](/images/content-rebuild/2467d22eea9c55aa/fig-1.png)

### 1. 外部证据检索注入（RAG）

**工作原理**：模型的网络参数在推理时保持不变。系统在外部建立索引（如向量数据库、BM25 全文检索或关系数据库）。当用户发起请求时，系统检索出相关的切片文档，拼入当前 Prompt 的上下文窗口，模型再根据输入内容阅读并生成回答。

*   **在质检场景中的表现**：合规条款随时修改，只需在知识库中更新对应切片，模型在下一次查询时就能看到最新条款，且能在回答中明确标注引用的条款原文位置。
*   **适用条件**：数据变动频繁（小时级到周级）；需要明确的原文依据；需要严格按用户角色隔离文档访问权限。
*   **边界与代价**：
    *   依赖检索质量：如果检索召回阶段漏掉了关键条款，模型即使推理能力再强也无法得出正确结论。
    *   上下文与延迟开销：检索出的文本切片越多，Prompt 占用的 Token 越多。超长的输入会显著增加首字生成时间（TTFT，Time to First Token）和 Prefill 阶段的计算开销。

### 2. 权重参数调整（微调）

**工作原理**：通过在标注样本上进行反向传播训练（如全参数微调或 LoRA 低秩适配），修改模型的注意力投影层与前馈网络连接权重，调整模型输出特定 Token 序列的条件概率分布。

*   **在质检场景中的表现**：微调非常适合让模型掌握特定审计报告的输出格式、专业缩写词以及符合监管规范的说话口吻。微调后的模型无需在 Prompt 中堆砌大量冗长的 Few-shot 样例，就能稳定输出结构化内容。
*   **适用条件**：任务的形式、语气、专业语法或输出 Schema 高度固定；需要将特定领域先验直接内化，减少输入 Prompt 长度。
*   **边界与代价**：
    *   事实更新滞后：训练模型需要经过数据清洗、参数微调、评估验收和上线部署，无法做到秒级同步业务事实。
    *   黑盒记忆不可靠：模型参数是高维统计关联，无法精确定位某条合规条款具体写在哪个权重参数中；直接用微调强记长尾动态事实容易导致模型在回答不确定信息时生成误导性极强的幻觉，甚至引起通用推理能力下降（灾难性遗忘）。
    *   格式遵循仍有随机性：微调能显著提升输出符合 JSON 语法的概率，但单靠采样依然存在极低概率的格式畸变，对于系统间严格对接，仍需结合受限解码（如 JSON Schema 结构化输出）或程序校验兜底。

### 3. 多轮环境交互（Agent）

**工作原理**：模型不仅做单次输入到输出的映射，而是作为循环控制器。模型根据当前任务和上下文做出决策（决定调用哪个工具、传入什么参数），执行环境运行工具并返回结果，模型观察结果后决定下一步行动，直到任务完成。

*   **在质检场景中的表现**：面对“对比 A 公司与 B 公司 2024Q3 毛利率与负债率差异”这类复杂复合问题，一次检索无法命中所有跨文档证据。Agent 可以将任务拆解为两步：先检索 A 公司的财报，再检索 B 公司的财报，若发现财报口径不一致，再调用会计准则换算工具进行折算，最后整合输出。
*   **适用条件**：任务无法通过一次检索或单次前向生成解决；依赖动态分支规划；工具执行结果可能失败并需要主动重试。
*   **边界与代价**：
    *   延迟倍增：每增加一轮工具调用，就多一次模型推理和网络 I/O，端到端耗时显著拉长。
    *   错误级联风险：多轮推理中，若某一步工具调用的参数推断偏差未被捕获，后续步骤会基于错误的事实继续推导，导致最终结果严重偏离预期。因此，工具调用、幂等性与状态检查必须由工程程序严格把关，不能假设模型绝对不会犯错。

## 四维选型评估矩阵与推演算例

在工程实践中，判断应该使用 RAG、微调还是 Agent，可以通过四个维度来衡量：

1.  **数据更新时效**：知识生命周期是月级相对稳定，还是日级/秒级实时变动？
2.  **格式与规范严苛度**：业务系统对专业术语、私有协议与 JSON Schema 格式的容错率有多高？
3.  **多步推理复杂度**：输入到输出是一步直达，还是需要依赖中间结果进行多步拆解与外部交互？
4.  **工程与计算成本**：包括训练计算成本、存储与检索维护成本、推理 Prefill 与 Decode 延迟预算。

### 成本与可行性推演算例

以合规质检场景为例：**系统每月处理 100,000 次审查请求，涉及 1,000 份随时更新的合规条款，质检结果要求符合标准审计 JSON 结构。**

假设每次审查实际只需参考 3 篇相关条款（平均每篇 1,500 Tokens，共 4,500 Tokens），审计模板与字段约束约 1,200 Tokens，用户输入的质检材料约 800 Tokens。我们对比三种独立方案的运行特征（数据为示意估算）：

| 方案类型 | 知识与格式注入方式 | 单次请求输入 Token 规模 | 每月知识更新维护机制 | 格式遵循稳定性 | 事实更新及时性与追溯 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **全量长上下文 Prompt** | 每次将全部 1,000 份条款（150 万 Tokens）放入 Prompt | 约 1,500,000 Tokens | 无需训练，直接更新 Prompt 输入文本 | 依靠 Prompt 约束，长文本下对局部指令遵循容易出现注意力分散 | 秒级更新；但单次请求 Prefill 耗时极长，显存占用极大，吞吐量极低 |
| **纯增量微调（LoRA）** | 每周将新条款与格式训练进模型权重 | 仅需输入质检文本（约 800 Tokens） | 需定期收集样本、清洗、重训 LoRA 并做全量回归测试 | 较高，格式已内化在先验中，但无受限解码时单靠采样仍有低概率畸变 | 存在发布周期滞后；无法直接向审计人员给出条款原文精确段落出处 |
| **RAG 检索方案** | 向量+全文检索命中 Top-3 条款（4,500 Tokens）+ 格式 Prompt（1,200 Tokens） | 4,500 + 1,200 + 800 = 6,500 Tokens | 条款变更时，对局部切片更新索引库，通常数秒生效 | 良好，结合结构化输出模式即可稳定解析 | 秒级生效；回答能够附带精确的条款引用出处，便于合规复核 |

算例说明：面对持续变更的事实，将所有条款一次性塞入长上下文或者频繁重新微调模型都不是经济可行的路线。**由检索系统（RAG）负责提供最新事实与溯源依据，由微调或受限解码负责保障输出格式与领域表达**，是系统开销和准确率之间更平衡的解法。

## 典型组合架构落地实践

在真实的生产系统中，通常会将这三项技术组合使用，各司其职。

### 模式一：微调基座 + RAG（专业术语适配与外部最新知识注入）

通用开源大模型直接面对专业场景（如医药病理、海关税号、合规法条）时，常因分词器切词碎片化或未见专有名词分布，导致专业术语理解偏离。

![微调基座结合 RAG 架构流程](/images/content-rebuild/2467d22eea9c55aa/fig-3.png)

*   **工作分工**：微调并不用来记忆下周可能会改动的条文，而是通过特定领域的语料对模型做 LoRA 微调，让模型熟悉行业的专业词汇缩写、推演逻辑与 JSON 输出结构。RAG 则作为外挂证据库，持续检索最新的条款切片注入上下文。
*   **推理优化协同**：在系统层面上，如 Hugging Face PEFT 中的 aLoRA 架构所示，通过在基座模型与适配器之间实现调用前的 KV Cache 共享，可以在基座模型与专用微调适配器切换时避免重复进行上下文的前置计算（Prefill），显著降低端到端响应延迟。
*   **异常防御**：当外部检索库没有命中相关条款或返回空集时，微调模型必须具备标准的拒答能力（如在微调数据集中包含“根据已知材料无法得出结论”的样本），防止模型退回使用参数记忆编造陈旧事实。

### 模式二：RAG + Agent（将单次检索升级为多步分析与交叉验证）

标准的 RAG 是一条单向流水线：`输入问题 -> 单次检索 -> 拼接生成`。当用户提出复合问题时，单次检索往往无法兼顾所有关联实体。

![Agent 驱动的多跳动态检索架构](/images/content-rebuild/2467d22eea9c55aa/fig-4.png)

*   **查询解构**：Agent 首先分析主问题，将其拆分为多个有依赖关系的子任务。例如：先调用检索工具查询“A 公司 2024Q3 研发费用”，得到数据后再调用检索工具查询“B 公司 2024Q3 研发费用”。关于多步规划的详细算法，读者可参考[/frontier/agentic-rag/complex-query-planning.md](/frontier/agentic-rag/complex-query-planning.md)。
*   **检索重试与自愈**：如果第一轮检索召回的内容相关性得分过低（例如用户使用了不规范的简称），Agent 可以结合工具返回的错误信息或摘要，改写检索关键词重新发起搜索。
*   **交叉比对**：Agent 将多篇财报或条款提取的数据进行逻辑校验，确认无矛盾后，才汇总生成最终答复。

### 模式三：微调 Agent 决策策略（精简 Prompt 长度与提升工具调用准确率）

在复杂的 Agent 框架中，通常需要在 System Prompt 中附带多个工具的名称、参数类型和入参说明（JSON Schema）。当工具数量较多时，System Prompt 会占用大量 Token，既增加了每轮对话的 Prefill 计算耗时，又容易在长多轮对话中引起模型漏传关键参数。

![微调决策策略的 Agent 架构](/images/content-rebuild/2467d22eea9c55aa/fig-5.png)

*   **决策行为微调**：通过构建工具调用的对话轨迹数据集，对轻量级模型进行指令微调（SFT）或偏好对齐（DPO，Direct Preference Optimization）。在训练中，将“在对应场景下选择正确工具且入参合规”作为正向样例，将“选错工具或参数格式错误”作为负向样例。
*   **工程收益**：模型权重内化了工具路由的条件反射后，System Prompt 中不必每次都携带繁复的参数说明与 Few-shot 样例，能直接减少输入 Token 规模，从而缩短端到端时延并降低由于格式解析失败引发的重试次数。关于标准工具与能力的定义设计，读者可参阅[/frontier/agent-skills/reusable-skill.md](/frontier/agent-skills/reusable-skill.md)。

## 生产实践中的典型认知误区

在系统设计与面试交流中，有两个流传较广的误区需要从运行机制层面进行辨析。

![认知误区与真实因果机制剖析](/images/content-rebuild/2467d22eea9c55aa/fig-6.png)

### 误区一：“大模型上下文窗口越来越大，RAG 很快会被淘汰？”

**辨析与事实机制**：
1.  **显存与并发瓶颈**：自注意力的全量计算在 Prefill 阶段通常随序列长度呈二次方增长，而在生成解码阶段，为了避免重复计算历史序列的 Key 和 Value，系统需要将它们缓存在显存中（KV Cache）。KV Cache 的显存占用随上下文长度呈线性增加。当并发请求增多、且每个请求都输入数十万 Token 时，KV Cache 会迅速占满 GPU 显存，导致单机并发能力断崖式下降。
2.  **注意力稀释与位置偏差（Lost in the Middle）**：模型在超长序列下的注意力分配并非完全均匀。当关键信息被夹杂在数十万字的中间段落时，模型提取该细节的准确率往往低于信息位于开头或结尾的情况。通过检索系统预先筛选出 Top-K 相关片段，能显著降低长上下文中的噪声干扰。
3.  **多租户数据权限隔离**：在企业生产环境中，不同员工对文档具有不同的读取权限。如果在检索层完成权限过滤，未授权文档甚至不会离开数据库；若直接把海量企业数据塞入一个公用的大上下文，系统的权限控制就必须依赖模型的“口头保密”，这在安全上是无法验收的。

### 误区二：“为了让大模型学习最新业务数据，应该每天做持续 SFT 微调？”

**辨析与事实机制**：
1.  **灾难性遗忘**：高频、小批量的增量监督微调（SFT）使用的样本分布通常高度局限。当模型权重反复在小规模非均匀数据上更新时，模型原本在预训练中建立的通用推理、指令遵循与代码能力很容易发生退化。
2.  **事实存储缺乏精确引用**：微调改变的是概率生成倾向，而不是向关系数据库写表。模型无法保证在任何 Prompt 诱导下都能准确无误地背出某一条款，更无法在回答时像检索系统一样给出精确到段落和页码的证据指针。
3.  **加剧确定性语气的幻觉**：强行通过微调让模型记忆超出容量的长尾实体，往往会导致模型遇到模棱两可的问题时，依然以极其自信的语气输出错误的混合事实。关于幻觉的深入归因，见[/llm-100/evaluation/hallucination-causes.md](/llm-100/evaluation/hallucination-causes.md)。

## 系统选型调度工程实现示意

在工程落地中，网关路由层可以根据任务的属性（数据时效、输出严苛度、推理步骤）来动态编排底层管道：

```python
# 系统选型调度示意伪代码
from dataclasses import dataclass
from typing import Dict, Any, Optional

@dataclass
class TaskProfile:
    task_id: str
    data_volatility: str     # "static"(静态), "daily_update"(每日更新), "realtime"(实时)
    format_strictness: float # 0.0 ~ 1.0 (例如 0.8 以上需要严格校验 JSON)
    reasoning_steps: int     # 1 为单步推理, >1 为多步复合分析

class ExecutionRouter:
    def __init__(self, base_model: str, adapters: Dict[str, str], rag_engine: Any):
        self.base_model = base_model
        self.adapters = adapters
        self.rag_engine = rag_engine

    def build_pipeline(self, profile: TaskProfile, query: str) -> Dict[str, Any]:
        plan = {
            "model": self.base_model,
            "adapter": None,
            "use_rag": False,
            "agent_mode": False,
            "constrained_decoding": False
        }

        # 维度 1：格式与领域表达要求高，挂载专用微调 Adapter 并启用受限解码
        if profile.format_strictness >= 0.8:
            plan["adapter"] = self.adapters.get("audit_format_lora")
            plan["constrained_decoding"] = True
        
        # 维度 2：涉及动态或外部业务事实，启动知识库检索
        if profile.data_volatility in ["daily_update", "realtime"]:
            plan["use_rag"] = True

        # 维度 3：多步关联任务，交由 Agent 状态机循环执行
        if profile.reasoning_steps > 1:
            plan["agent_mode"] = True
            # RAG 将作为 Agent 可调用的工具之一提供，而非一次性前置拼接
            return {"type": "agentic_workflow", "plan": plan, "query": query}
        
        # 单步直接推理流水线
        return {"type": "linear_pipeline", "plan": plan, "query": query}
```

## 读者自测与验收练习

学完本讲后，请尝试回答以下两个工程设计问题，检验选型思路：

1.  **架构分工题**：
    *   *题目*：某电商平台需要搭建一个商品售后仲裁助手，要求：每天处理上千起纠纷；依据最新商户服务协议做出裁定；输出符合工单系统规范的结构化记录；必要时需要分别调取买家聊天记录、物流轨迹和商家资质做综合比对。请画出 RAG、微调与 Agent 的职责划分。
    *   *参考思路*：买家聊天记录、物流轨迹与最新商户协议由 RAG/API 检索系统动态提供，确保数据实时与权限隔离；工单格式规范与平台仲裁术语可由微调 Adapter 结合受限解码约束；买卖双方证据的多步调取与交叉校验由 Agent 编排推进。
2.  **长上下文与微调边界题**：
    *   *题目*：团队中有人建议：“我们直接购买支持 2M 上下文的商用模型 API，把所有的公司规章制度和业务手册直接拼在 System Prompt 里，省去 RAG 向量库与微调流程。”从系统吞吐、成本和准确率三个角度，列举该建议存在的工程隐患。
    *   *参考思路*：每次请求都输入海量静态规则会导致 Prefill Token 费用暴增；长文本中间的细则容易被注意力稀释（Lost in the Middle）；多租户权限难以在统一的超长 Prompt 中实现物理隔离。
