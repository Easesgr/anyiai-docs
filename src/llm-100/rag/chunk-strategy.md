在检索增强生成（RAG）系统中，文档切分（Chunking）是将原始长文本转为检索索引单元的预处理步骤。如果切分方式破坏了句意或丢失了表格结构，后续无论选用多大参数量的向量模型，检索模块都难以向大模型提供准确的事实依据。

在上一讲 [/llm-100/rag/what-is-rag.md](/llm-100/rag/what-is-rag.md) 中，我们梳理了 RAG 系统的两个基本阶段：离线构建索引与在线检索生成。本文以一份真实的《存储集群运维手册》为例，讲解如何将非结构化文档切分成长度适中、语义聚焦且保留层级结构的文本块。

![文档切分工程全景架构](/images/content-rebuild/67789ec85795216d/cover.png)

上图展示了文档切分的基础处理流程：原始长文档在进入向量化模块前，先经过分词器（Tokenizer）长度校验、滑动重叠切分，并结合文档语法树注入层级元数据，使切分出的每一个文本块都能独立表达明确事实。

### 块大小（Chunk Size）权衡：语义稀释与碎片化

切分块的长度并非越长越好，也不是切得越碎越准。稠密嵌入模型（Dense Embedding）会将一段变长文本压缩成一个固定维度的向量（如 768 或 1024 维）。这种降维压缩决定了切分粒度存在明确的工程折中。

![切分粒度两极权衡机制](/images/content-rebuild/67789ec85795216d/fig-1.png)

如上图所示，切分块过大或过小都会影响检索表现：

1. **块过大（例如单块超过 1000 Tokens）导致的语义稀释**：
   - 如果一个切分块内同时包含“集群网络拓扑”、“磁盘写入只读阈值”、“扩容收费方案”和“历史更新记录”，模型生成的单一向量需要同时涵盖多个主题。
   - 用户的检索词通常针对具体问题（例如“磁盘剩余多少会触发只读保护”）。大块向量由于包含了过多无关主题的信息，其与专一检索词的余弦相似度往往会被拉低，导致排序靠后。
   - 即便该大块被成功召回，未经过滤的长段落也会占用生成模型的上下文窗口，分散注意力的集中度。
2. **块过小（例如单块少于 50 Tokens）导致的语义碎片化**：
   - 自然语言中的因果判断、执行条件和限定主语往往跨越多句话。
   - 若切分过细，容易出现类似“阈值不得低于 5%”的孤立片段，而前置主语“主节点可用磁盘容量”被截留在前一个切片，后果“否则触发全局只读”被切到后一个切片。
   - 检索阶段可能命中该短句，但送入大模型后，大模型因缺乏主语和上下文判定条件，容易给出错误判断或提示信息不足。

因此，切分粒度需在“向量针对特定问题的聚焦度”与“单块内逻辑自洽的上下文长度”之间寻找平衡。在常规技术文档检索中，工程实践通常先以 256 到 512 Tokens 作为切分测试的初始基准，再根据问答评测集进行调整。

### 字符计数与 Token 计数的计算差异

很多初学者在编写切分脚本时，习惯直接调用编程语言的字符串截断（例如 Python 中的 `text[i:i+500]`）。这种“按字符截断”与嵌入模型实际处理的“Token 序列”在计数上并不对齐。

![字符切分与Token切分的对齐差异](/images/content-rebuild/67789ec85795216d/fig-2.png)

嵌入模型不直接处理原始字符，而是通过分词器（Tokenizer，如基于 BPE 或 WordPiece 算法）将文本切分成词元（Token）序列。字符数与 Token 数之间不存在固定的 1:1 比例关系：
- 纯英文常见单词可能 1 个单词对应 1 个 Token，但生僻词、缩写或编程变量会被拆分成多个子词。
- 在中文、代码或包含特殊数学符号的技术文本中，常用汉字可能占 1 到 2 个 Token，特殊符号甚至占用更多。

设输入文本字符长度为 500。如果文本中包含密集的代码、日志格式或生僻术语，经分词器转换后可能产生 750 个 Tokens。若下游嵌入模型的最大处理长度为 512 Tokens，超出该上限的 238 个 Tokens 将在模型内部被**尾部静默截断**。段落后半部的结论或关键参数因此未能参与向量生成，导致向量无法代表被截断的内容，而系统运行通常不会抛出任何报错。

此外，按字符硬截断容易将完整的英文变量（如 `min_disk_free_limit` 截成 `min_disk_` 与 `free_limit`）从中间截断，破坏词根结构。因此，切分长度计算必须使用与目标嵌入模型配套的 Tokenizer。

### 重叠窗口（Overlap）的作用与成本

为了避免关键陈述刚好落在切分分界线两侧而丢失语义，通常会在相邻的切分块之间设置滑动重叠窗口（Overlap）。

![重叠窗口机制与冗余权衡](/images/content-rebuild/67789ec85795216d/fig-3.png)

#### 1. 缓解边界断句问题
如上图左侧所示，考虑手册中的一条告警规则：“**当主节点磁盘空间低于 5% 时，集群将自动切换为只读保护模式以防止元数据损坏**”。如果切分边界刚好切在“5% 时”后面：
- 块 A 得到：“当主节点磁盘空间低于 5% 时……”（仅包含前置诱因，缺失动作结果）。
- 块 B 得到：“集群将自动切换为只读保护模式……”（仅包含动作，缺失具体的量化阈值）。

当用户提问“集群在什么磁盘条件下会进入只读保护？”时，块 A 缺少“只读保护”关键词，块 B 缺少“低于 5%”这一限制条件，两块在检索阶段的相似度打分都会下降。

通过配置重叠窗口，使块 B 的起始位置回退一定数量的 Token，整条因果语句就能完整落在块 B 的前部，保障了核心逻辑的连续性。

#### 2. 重叠率的计算与召回冗余
设文档总 Token 数为 $L$，单块目标大小为 $S$，相邻块重叠大小为 $O$（满足 $0 \le O < S$）。在均匀滑动切分且不丢弃尾部余量的前提下，切出的文本块总数 $N$ 满足：

$$N = \max\left(1, \left\lceil \frac{L - O}{S - O} \right\rceil\right)$$

重叠量并非越大越好，设置过高会带来两项负面效应：
- **索引存储与计算开销上升**：若设置 $S = 500, O = 250$（重叠率 50%），切片总数接近翻倍，向量存储体积与离线向量化调用的开销也同步翻倍。
- **Top-K 结果聚集冗余**：如上图右侧所示，若切片之间重合度过高，检索返回的前 3 个结果可能是同一段原始文本在不同滑动窗口下的微调版本（内容重合达 70% 以上）。这会挤占检索配额，导致其他包含不同有效信息的段落无法被展示给大模型。

常规工程实践中，重叠率多控制在 $10\% \sim 20\%$。例如对于 $S = 512$ 的切分块，重叠量通常配置为 $50 \sim 100$ Tokens。

### 结构感知切分：Markdown 标题与表格对齐

在很多技术文档中，段落含义依附于其所在的层级标题和表格排版。脱离上下文层级的纯线性切分往往导致信息失真。

![结构感知切分与元数据注入流程](/images/content-rebuild/67789ec85795216d/fig-4.png)

#### 1. Markdown 标题层级注入
如果在文档中看到这样一句话：“超时时间默认设为 15 秒”。脱离章节层级，读者无法得知这是客户端连接超时、事务提交超时还是元数据同步超时。

结构感知切分会先解析 Markdown 的标题标记（`#`, `##`, `###`）构建文档树，并对叶子节点的文本块实施元数据注入：
- 将父级标题链提取出来，例如 `运维规范 > 存储节点 > 客户端连接池`。
- 将标题链以文本前缀形式追加到块头部，或写入该块的元数据属性中。
- 这样在向量匹配或关键词检索时，文本块便天然携带了归属领域的上下文信息。

#### 2. 表格切分与单元格对齐保护
表格是按字符或按行盲切的重灾区。二维表格依赖顶部的“列名”和左侧的“行属性”共同界定每个单元格的含义：
- **表头丢失**：如果表格有 20 行，按行数硬切为两个块，后半部分的数据行将失去顶部的列名定义。大模型看到孤立的一行数据（如 `| node-01 | 64GB | 8TB |`），无法分辨数字分别对应的是内存、缓存还是数据盘容量。
- **合并单元格（Rowspan/Colspan）错位**：在 HTML 或富文本表格中，若某个单元格设置了跨行（`rowspan`），该单元格通常仅在第一行显式声明，后续行在数据结构上会跳过该列。如果切分时直接在中间某行切断，被截断的下半部分行就会发生“列偏移”，原本属于第 3 列的数值会被错位排到第 2 列。
- **处理方案**：在切分包含表格的内容前，先将合并单元格解包还原，将跨行内容广播复制到对应单元格中；切分拆行时，必须为拆分后的每个子块强制重新补充完整的表头行。

### 语义切分（Semantic Chunking）原理与开销边界

对于没有层级标题、缺少排版标记的纯文本（如会议速记、电话录音听写），显式规则切分往往难以捕捉自然段落的主题转换。此时可采用**基于相似度突变点的语义切分**。

![语义切分相似度突变点检测](/images/content-rebuild/67789ec85795216d/fig-5.png)

#### 1. 相似度突变点检测
语义切分的基本假设是：**讨论同一话题的连续句子，其句向量在语义空间中的余弦相似度较高；当话题切换时，相邻句子间的相似度会出现明显下降。**

其算法流程包括：
1. **断句**：使用分句工具将长文档拆分成有序句子列表 $s_1, s_2, \dots, s_M$。
2. **向量编码**：使用轻量嵌入模型计算每句话（或由前后若干句组成的局部滑动窗口）的向量 $v_1, v_2, \dots, v_M$。
3. **计算相邻相似度**：计算句子转移过程中的余弦相似度 $d_t = \text{CosineSim}(v_t, v_{t+1})$。
4. **判定切分点**：设定分割阈值 $\tau$。阈值可以结合全篇相邻相似度的均值 $\mu$ 与样本标准差 $\sigma$ 动态设定：
   $$\tau = \mu - k \cdot \sigma$$
   其中 $k$ 为调节参数。当转移相似度 $d_t < \tau$ 时，判定此处发生主题切换，将其设定为切分点。

#### 2. 算力开销与适用范围
语义切分能自适应捕捉主题边界，但计算成本显著高于规则切分：
- 规则切分（基于正则与标点符号）仅涉及字符串扫描，耗时通常在毫秒级。
- 语义切分需要为全篇所有单句逐一调用嵌入模型进行前向推理，计算开销与网络/硬件延迟呈线性增加。

因此，语义切分主要用于缺乏格式排版的纯文本内容；对于技术手册、API 文档等具有良好标题和段落排版的结构化材料，优先采用结合语法树与层级标记的结构感知切分性价比更高。

### 动手验证：固定字符切分 vs 结构感知切分

通过一段包含层级标题与参数表格的测试文档，对比直接截断与结构感知切分的实际输出差异。

![切分策略对表格检索上下文影响对比](/images/content-rebuild/67789ec85795216d/fig-6.png)

上图对比了两种策略的处理效果：固定长度切分将表格截断，丢失了列属性与章节从属；而结构感知切分保留了层级路径与表格表头。

运行以下 Python 验证代码：

```python
from typing import List, Dict

raw_doc = """# 存储节点运维规范
## 硬件配置参数
以下为生产集群建议的节点规格参数：

| 节点型号 | CPU规格 | 内存容量 | 系统盘配置 | 数据盘配置 |
| :--- | :--- | :--- | :--- | :--- |
| Storage-A | 32 Core | 128 GB | 2x 480G SSD | 8x 3.84TB NVMe |
| Storage-B | 64 Core | 256 GB | 2x 960G SSD | 16x 7.68TB NVMe |
| Storage-C | 16 Core | 64 GB | 2x 240G SSD | 4x 1.92TB NVMe |

注：所有数据盘均需配置为硬件 RAID 10。"""

# 策略 1：固定字符长度切分（模拟每块 130 字符硬截断）
def naive_fixed_chunk(text: str, chunk_size: int = 130) -> List[str]:
    chunks = []
    for i in range(0, len(text), chunk_size):
        chunks.append(text[i:i + chunk_size])
    return chunks

# 策略 2：结构感知切分（提取 Markdown 标题前缀，表格切分时保留表头）
def structure_aware_chunk(text: str) -> List[Dict[str, str]]:
    chunks = []
    lines = text.strip().split("\n")
    current_h1, current_h2 = "", ""
    table_header = ""
    table_rows = []
    in_table = False
    
    def flush_table():
        nonlocal table_rows, in_table
        for row in table_rows:
            # 为每一条表格数据行补充标题上下文及完整表头
            content = f"[{current_h1} > {current_h2}]\n{table_header}{row}"
            chunks.append({"content": content, "type": "table_row"})
        table_rows = []
        in_table = False

    for line in lines:
        if line.startswith("# "):
            current_h1 = line.replace("# ", "").strip()
        elif line.startswith("## "):
            current_h2 = line.replace("## ", "").strip()
        elif line.startswith("|"):
            if not in_table:
                in_table = True
                table_header = line + "\n"  # 记录列名
            elif ":---" in line:
                table_header += line + "\n" # 记录分隔线
            else:
                table_rows.append(line)     # 记录数据行
        else:
            if in_table:
                flush_table()
                
    # 边界保护：若文本末尾以表格结尾，清空缓冲区残留
    if in_table and table_rows:
        flush_table()
        
    return chunks

# 执行验证
naive_res = naive_fixed_chunk(raw_doc, chunk_size=130)
aware_res = structure_aware_chunk(raw_doc)

print("=== 策略 1：固定截断的第 2 块 ===")
print(repr(naive_res[1]))
print("\n=== 策略 2：结构感知切分的第 1 个表格块 ===")
print(aware_res[0]["content"])
```

#### 运行结果解析

1. **策略 1（固定截断）的输出片段**：
   ```text
   ' 32 Core | 128 GB | 2x 480G SSD | 8x 3.84TB NVMe |\n| Storage-B | 64 Core | 256 GB | 2x 960G SSD | 16x 7.68TB NVMe |\n| Storage-C '
   ```
   由于刚好切在 130 字符处，该切片不仅完全丢失了顶部的列名定义（`CPU规格`、`内存容量` 等），第一行甚至连节点型号 `Storage-A` 都在上一块被截断（开头直接以 `' 32 Core'` 起始），且末尾行数据在 `| Storage-C ` 处被截断。若大模型仅依据此切片回答问题，既无法断定 `128 GB` 属于哪个配置项，也无法确定其对应的完整节点型号。
2. **策略 2（结构感知切分）的输出片段**：
   ```text
   [存储节点运维规范 > 硬件配置参数]
   | 节点型号 | CPU规格 | 内存容量 | 系统盘配置 | 数据盘配置 |
   | :--- | :--- | :--- | :--- | :--- |
   | Storage-A | 32 Core | 128 GB | 2x 480G SSD | 8x 3.84TB NVMe |
   ```
   每个表格子块均继承了所属的章节标题，并绑定了完整的列属性。送入检索系统后，不仅能够依靠关键词同时召回章节名与字段名，大模型在阅读该上下文时也能做出确定性推断。
