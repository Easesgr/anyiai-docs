在开发基于大语言模型的企业应用时，团队经常会在两条路线之间犹豫：是搭建检索增强生成（RAG），还是收集一批业务数据做监督微调（SFT）？

一种常见尝试是把企业内部几百页的规章制度做成问答对直接微调模型，期望模型把条款“记住”。上线后却发现，模型遇到生僻条款依然会编造内容，且每当业务规则修改时，重新训练与验证的周期过长。另一种极端是试图完全依靠提示词与 RAG 来规范复杂的输出结构（例如上百行嵌套的固定格式 JSON），结果每次请求都要拼接冗长的格式规则与示例，导致输入 Token 数量暴涨、首字延迟增加，且长文本下偶尔仍会破坏结构。

**结论先行**：
* **RAG 解决的是“知识从哪里来”的问题**。它不改变模型本身的参数，而是在用户提问时，先通过检索程序从外部知识库找到相关参考片段，再把片段拼接到提示词中供模型阅读。适合**高频更新、需要查阅依据、强溯源**的事实类任务。
* **微调（SFT）解决的是“模型如何表达与行动”的问题**。它通过计算损失函数并更新模型权重（或额外的适配层权重，如 LoRA），改变模型生成词元的条件概率。适合**固定输出格式、特定行文风格、执行特定任务范式**（如代码生成、数据抽取、固定工作流分类）。

为了清晰理解这一权衡，本文以一个贯穿示例展开：假设我们要为一家商业银行搭建“信贷合规助手”，用户会询问“个人消费贷款审批上限是多少？根据哪项制度执行？”，同时系统需要以严格的内部风控 JSON 结构输出审核结论。

![RAG 与微调在上下文注入与参数修改路径上的对比](/images/content-rebuild/431af968cda63a05/cover.png)

### 1. 机制区别：提示词上下文注入 vs 内部权重更新

理解两者的适用场景，首先需要区分二者在模型推理时所依赖的信息载体。

#### 概念定义
* **检索增强生成（RAG, Retrieval-Augmented Generation）**：在推理阶段，先利用用户的查询（Query）在外部向量数据库或全文检索引擎中找出最相关的 $K$ 个文档切片，将切片和问题组装到上下文窗口（Context Window）中，直接作为大模型的输入。大模型的参数在整个过程中没有任何改动。
* **监督微调（SFT, Supervised Fine-Tuning）**：在已有预训练模型参数 $\theta$ 的基础上，准备一批由提示词输入 $x$ 和理想回复 $y$ 构成的标注样本，通过反向传播算法调整模型权重（或低秩适配层权重），使模型在给定输入时的预测分布尽可能接近标注答案：

$$\mathcal{L}_{\text{SFT}}(\theta) = -\sum_{t=1}^{T} \log P_\theta(y_t \mid x, y_{<t})$$

其中 $y_t$ 是第 $t$ 个标记，$y_{<t}$ 是前文已生成的标记。

![监督微调参数更新与自回归生成的隐式激活机制](/images/content-rebuild/431af968cda63a05/fig-1.png)

#### 为什么微调不适合作为精确事实库？

在上述信贷合规助手中，若想让模型记住“《个人贷款管理办法》第 28 条规定个人消费贷款单笔最高不超过 30 万元人民币”，微调会遇到以下阻碍：

1. **参数存储具有弥散性**：Transformer 模型内部没有类似关系型数据库的独立单元格。一个事实信息在经过梯度更新后，被分散记录在注意力投影矩阵（$W_q, W_k, W_v, W_o$）和多层感知机（MLP）的数十亿参数中。模型学到的是标记之间的统计共现概率，而非确定的键值对应关系。
2. **低频长尾事实容易幻觉**：通用事实在数万亿 Token 的预训练语料中反复出现，激活路径稳固；而企业内部私有的条款、规章通常只在微调集的几十或几百个样本中出现。在推理采样阶段，稍微改变提问句式，模型就很可能沿预训练时的高概率通用模式采样，输出看似合理却张冠李戴的数字。
3. **遗忘风险**：当通过增量微调强行灌入大量长尾事实时，更新方向可能干扰模型原有的指令遵循与通用推理能力。详细机制可参考 [/fundamentals/training-and-finetuning/finetuning-pitfalls.md](/fundamentals/training-and-finetuning/finetuning-pitfalls.md)。

因此，**参数适合内化技能与行为规范，上下文适合呈现事实依据**。

### 2. 知识更新成本：即时索引写入 vs 周期性再训练

在真实业务中，规章制度和产品手册经常修编。当总行下发通知将个人消费贷款额度从 30 万元临时调整为 20 万元时，两套架构的处理方式存在明显的维护成本差异。

![RAG 知识增量更新链路与微调再训练全周期的耗时对比](/images/content-rebuild/431af968cda63a05/fig-2.png)

#### 增量更新全流程对比算例

假设银行内部有 200 份信贷文件发生修订，变动内容总计 50 万 Token。两者的处理流程如下：

| 评估维度 | RAG 检索管线更新 | SFT / LoRA 增量微调更新 |
| :--- | :--- | :--- |
| **数据准备** | 文本解析 $\rightarrow$ Chunk 切分 $\rightarrow$ 计算 Embedding 向量 | 必须组织、清洗并生成成对的问答或指令样本集（需要人工标注或大模型合成审核） |
| **计算工作量** | **单次前向推理与文本建库**：对 50 万 Token 执行单次前向推理计算稠密向量，倒排索引仅需分词构建 | **多轮前向 + 反向传播**：通常需迭代 3~5 个 Epoch，计算梯度并更新优化器状态 |
| **更新耗时** | **秒级至分钟级**：向量与文本写入数据库后即可命中 | **小时级至天级**：需经历训练、损失收敛观察、下游测试集回归评估、服务上线 |
| **回滚与撤回** | **低风险**：在向量库中按文档 ID 或版本标签执行删除即可立即失效 | **高风险**：无法直接从权重中单独剥离某些样本的影响，需回滚权重检查点重新训练 |
| **计算资源** | 少量 CPU 或单卡 GPU 计算 Embedding 即可 | 需保留完整的微调显卡算力，且需要保留用于回归评测的校验算力 |

在 RAG 架构中，知识的更新与模型解耦。文档切分并写入向量数据库（如 Qdrant、Milvus，详见 [/llm-100/rag/vector-db-in-rag.md](/llm-100/rag/vector-db-in-rag.md)）后，下一次检索即可直接引用最新条文。

### 3. 可解释性与可审计性：显式参考片段 vs 概率采样黑盒

在金融、法务等合规要求极高的场景中，系统给出的结论必须附带可核实的依据。

![RAG 基于文本块的显式引用与微调隐式记忆输出的审计对比](/images/content-rebuild/431af968cda63a05/fig-3.png)

#### 两种方案的审计机制区别

* **RAG 能够提供显式证据链**：检索模块返回文档切片时，每个切片都包含来源元数据（文档编号、文件名、页码、段落哈希）。组装后的输入形如：

```text
请根据以下参考资料回答用户问题，并在回答中用 [Doc ID] 标注依据。

参考资料：
[Doc-01] 《个人消费信贷实施细则（2024版）》第 14 条：普通个人消费贷款单笔上限为 30 万元人民币。
[Doc-02] 《高净值客户特批办法》第 3 条：符合 A 类资产认证的高净值客户，经分行审核，特批上限为 100 万元人民币。

问题：普通个人消费信贷最高审批额度是多少？
```

当模型生成回答并打上 `[Doc-01]` 标记后，质检程序或合规审计员可直接提取该文本切片与原始合同做逐字比对。如果模型答错，排查逻辑非常明确：
1. 是检索阶段没查出来（切片未召回）？
2. 还是检索已给出正确切片，模型没遵循上下文生成（生成阶段遵循失败）？

* **纯微调模型难以完成事实溯源**：如果把上述细则作为训练语料让模型微调，即便在指令数据中强制模型输出形如“根据《细则》第 14 条...”，该条款名称和序号依然是模型自回归采样生成的。微调后的模型容易以笃定的语气生成看似专业、实则由统计混淆捏造的条款（例如输出《个人信贷指引》第 88 条）。更关键的是，我们无法从模型权重反推这一句究竟由哪一条具体训练数据直接推导而来。

### 4. 结构控制与风格固定：微调的实际价值

尽管 RAG 在事实更新和溯源上具备显著优势，但如果任务目标是**严格遵循复杂格式、特定的领域行文语气或极低的首字延迟**，微调则是更为高效的手段。

![针对特定领域语法和严格输出格式的微调行为控制结构](/images/content-rebuild/431af968cda63a05/fig-4.png)

#### 为什么仅靠 RAG 与长 Prompt 规范格式有时不够理想？

1. **上下文冗余与成本上升**：若业务要求模型每次必须输出包含数十个嵌套字段的风控检查报告（JSON 结构），使用纯 Prompt 方案时，每次请求都必须附带完整的 JSON Schema 和数个 Few-Shot 样例。单次提示词可能额外消耗 2,000~3,000 Token。这不仅增加 API 调用成本，还会显著延长首字生成延迟（TTFT, Time To First Token）。
2. **长序列格式稳定性问题**：大模型仅依靠上下文提示生成复杂嵌套结构时，随着输出变长，容易发生尾部字段缺失或括号未闭合的情况。微调能调整输出标记的转移概率，使模型内化该任务的语法骨架，在短提示词下也能高概率输出合规结构。当然，若工程上需要完全保证 JSON 格式无语法错误，生产环境通常还会配合语法约束解码（Grammar-constrained Decoding 或 JSON 模式）作为双重保障。
3. **减少提示词争抢**：若提示词中同时包含海量参考切片和极其冗长的格式说明，模型对两者的兼顾能力可能会受到影响。通过微调将输出格式固化为模型的默认行为模式，提示词就可以专注于容纳事实切片。

#### 示例配置：使用 Hugging Face PEFT 定义针对结构化输出的 LoRA 适配器

在参数高效微调（PEFT）中，LoRA（Low-Rank Adaptation）通过在预训练权重旁增加低秩分解矩阵来拟合新任务，无需更新全量参数。以下展示针对文本结构化抽取任务的典型配置：

```python
from peft import LoraConfig, TaskType

# 针对指令遵循与特定语法格式微调的 LoRA 配置示例
peft_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    inference_mode=False,
    r=16,           # 秩大小：根据任务复杂度一般取 8~32
    lora_alpha=32,  # 缩放系数，通常设置为 r 的 1~2 倍
    lora_dropout=0.05,
    # 同时作用于注意力投影矩阵与全连接层（MLP），有助于改善词汇选择与结构遵循
    target_modules=[
        "q_proj", "k_proj", "v_proj", "o_proj",
        "gate_proj", "up_proj", "down_proj"
    ],
    bias="none"
)
```

关于 LoRA 的显存计算原理与训练步骤，可参考 [/fundamentals/training-and-finetuning/lora-qlora.md](/fundamentals/training-and-finetuning/lora-qlora.md)。

### 5. 选型评估与协同架构

在实际工程设计中，RAG 与微调并非对立的单选项。团队可以依据**知识时效性**与**格式/行为专用性**两个维度来制定选型决策。

![企业级大模型应用技术选型评估决策流](/images/content-rebuild/431af968cda63a05/fig-5.png)

#### 选型判断清单

* **适用纯 RAG 的场景**：
  * 核心需求是企业知识库、客服手册、政策法规问答。
  * 业务事实变动频繁（每天、每周或每月都有更新）。
  * 需要严格的用户数据隔离（不同权限员工只能检索其有权限的文档）。
  * 必须提供显式引文链接供人工核验。
* **适用纯微调（SFT）的场景**：
  * 核心需求是文本转换、代码辅助补全、特定领域专有名词翻译。
  * 所需知识相对静态，但对输出格式（如特定的 DSL 或严格 JSON）有极高要求。
  * 对推理首字延迟与 Token 成本非常敏感，希望输入提示词保持极短。
* **适用“微调 + RAG”协同的场景**：
  * 专业业务领域系统（如信贷审查助理、医疗分诊建议助手）：一方面需要依据最新更新的业务制度与外部案例作答（由 RAG 检索最新切片注入），另一方面要求输出必须满足固定的医学/金融分析模版并具备严谨专业口吻（由 SFT 调整模型的行文风格与生成格式）。

![领域微调模型配合 RAG 检索管道的端到端生产架构](/images/content-rebuild/431af968cda63a05/fig-6.png)

#### 协同落地的具体分工

在协同落地架构中，两个组件各司其职：
1. **离线微调（SFT）**：使用一批清洗过的脱敏业务样本微调基座模型。微调的目标**不是**让模型死记硬背条款数字，而是训练它两项能力：
   * **阅读理解与抽取能力**：学会严格依据所提供的参考资料回答，当下文没有依据时，输出统一的标准话术（如“参考资料未提及相关内容，无法核实”），减少无根据的自由发挥；
   * **规范化格式输出**：学会按指定的 JSON 模板组织回答，并把依据标记放置在特定字段。
2. **在线检索（RAG）**：用户发起提问，检索模块从向量库和全文索引中召回与问题最相关的 $K$ 个段落，并经过重排序（Rerank，详见 [/llm-100/rag/rerank-importance.md](/llm-100/rag/rerank-importance.md)）选出最优切片。
3. **组合生成**：将切片输入给经过微调的模型。模型以精简的提示词驱动，输出格式合规、附带事实切片引用的可靠回复。

### 6. 检验练习

为了检验对两者技术边界的理解，请尝试回答以下两个工程问题：

1. **练习 1**：某电商平台有 1000 万种商品，商品的价格和库存每分钟都在变化。如果需要搭建一个能回答“某商品当前是否有货、价格多少”的智能客服，应该选择微调模型还是 RAG 方案？为什么？
   * *思考方向*：从数据写入频率、训练时间、显存与参数存储机理考虑。
2. **练习 2**：某团队开发了一套自动化运维系统，需要将用户的自然语言运维指令翻译为该团队自定义的内部脚本语言（包含 40 种自定义语法规则）。初始使用通用大模型加 Prompt 方案，由于语法手册长达 3000 Token，导致每次调用延迟高且频繁出现标点与关键字错误。该团队应该如何优化？
   * *思考方向*：该任务属于事实检索还是特定语法形式的模式转换？能否利用微调将语法树先验固化在模型中？
