在构建检索增强生成（RAG）系统时，基础原型搭建往往只需要几行代码：读取文档、按固定长度切块、调用向量模型生成嵌入、存入向量库，最后按相似度取 Top-K 拼入 Prompt。然而，当文档规模增长、业务问题变复杂时，这种朴素方案（Naive RAG）常常出现两类典型问题：**检索端没找对或没找全信息（召回率低）**，以及**生成端拿到了片段却答非所问或产生幻觉（准确率低）**。我们在[/llm-100/rag/rag-wrong-answers.md](/llm-100/rag/rag-wrong-answers.md)中讨论过 RAG 答非所问的常见故障原因。

解决这些问题不能靠盲目更换模型或随意调试提示词，而需要针对检索链路的三个关键环节做针对性优化，并通过可量化的指标形成验证闭环：

1. **查询端**：解决用户输入表达模糊、问答空间不对齐的问题；
2. **索引端**：解耦“用于向量检索的文本粒度”与“提供给模型阅读的上下文粒度”；
3. **评测端**：将端到端表现拆解为定位精准度、生成忠实度与回答相关性三个独立指标，指导定向调优。

本文通过一个贯穿始终的运维知识库查询场景，拆解各环节的优化方法与工程边界。

### 贯穿场景：集群升级超时排查

假设我们正在为内部基础设施团队搭建一套技术文档问答系统。用户在聊天窗口中输入：

> “2.4 版本集群升级如果超时该改哪个参数？默认值是多少？”

知识库中存放着两份相关文档：
- **文档 A（《平台部署与升级运维指南 v2.4》）**：包含段落“……在执行集群升级任务时，若节点拉取镜像较慢触发等待限制，可通过修改配置项 `upgrade_timeout_seconds` 增加超时容忍。该参数默认值为 300 秒，大规模节点场景建议调整至 600 秒……”。
- **文档 B（《旧版升级参考 v1.8》）**：包含段落“……升级超时时间由 `timeout_sec` 控制，默认 120 秒……”。

在朴素 RAG 流程下，系统常在这里失效：
- 用户提问是问句形式（“如果超时该改哪个参数”），文档里是声明句陈述（“修改配置项 `upgrade_timeout_seconds`”），向量相似度计算可能不够突出；
- 如果切块尺寸很小（例如 128 Token），命中了“默认值为 300 秒”，但缺少段落开头“执行集群升级任务”和“适用于 v2.4”的上下文，模型拿到的证据不完整；如果切块尺寸过大（例如 1024 Token），整块文字混杂了节点调度、网络配置等其他说明，向量语义被稀释；
- 如果未指定版本进行过滤，向量检索可能误召回《旧版升级参考 v1.8》，导致模型给出了已废弃的配置项 `timeout_sec`。

### 查询端重构：Query 改写、HyDE 与多查询分解

用户输入的原始查询通常带有口语化表述、代词或多重复合意图。查询端处理的目标是在向量比对前，将输入转换为更适合检索的形式。

#### 1. 查询重写（Query Rewriting）
在多轮对话中，用户常使用省略句或代词，如“它的默认值呢？”。查询重写利用轻量语言模型，结合对话历史补齐上下文，输出独立的单句：
- 输入：“它的默认值呢？”（结合上文关于 v2.4 集群升级超时的讨论）
- 改写输出：“v2.4 版本平台集群升级超时参数 `upgrade_timeout_seconds` 的默认值是多少？”

重写消除了代词歧义，使检索器能直接匹配目标实体。

#### 2. 假设性文档嵌入（HyDE）
用户的问题与知识库中的答案，在语法结构和词汇分布上往往存在差异。问题通常由疑问词、条件从句构成，而技术文档是规范陈述句。**HyDE（Hypothetical Document Embeddings）**改变了直接用问题向量检索文档的模式，其运行步骤如下：

1. 接收用户问题 $q$；
2. 让 LLM 在不查阅外部知识库的前提下，根据自身语言先验生成一段假设性的答案段落 $\hat{d}$；
3. 对假想段落 $\hat{d}$ 计算嵌入向量 $E(\hat{d})$，以此向量在知识库中匹配相似文档。

```python
# HyDE 查询变换示例
def hyde_query_transform(query: str, generator_llm, embedding_model) -> list[float]:
    # 步骤 1: 让大模型生成与问题对应的假想段落
    prompt = (
        f"请针对以下技术问题，写一段可能出现在官方文档中的陈述性回答：\n"
        f"问题：{query}\n"
        f"要求：直接给出配置参数名称、作用说明与默认取值，使用规范技术文档风格。"
    )
    hypothetical_doc = generator_llm.generate(prompt, temperature=0.0)
    
    # 步骤 2: 对假想文档向量化，实现“文档到文档”的表征对齐
    query_vector = embedding_model.get_text_embedding(hypothetical_doc)
    return query_vector
```

在我们的贯穿场景中，模型生成的假想文本虽然可能猜错具体参数名，但其生成的句式（如“在配置中调整升级超时时间参数，默认值为……秒”）在向量空间中与文档 A 的陈述句高度靠近，从而提升相关段落的召回概率。

**适用边界**：HyDE 的效果依赖生成模型的先验质量。如果查询涉及完全私有的特殊错误码、随机哈希串或模型先验未涵盖的冷门内部标识符，模型虚构的假想文本可能产生严重的主题漂移，反而干扰检索。

#### 3. 多查询分解（Multi-Query Decomposition）
针对由多个子问题复合而成的复杂提问，单一向量难以同时覆盖所有语义焦点。例如：
> “v2.4 集群升级超时改什么参数？升级失败后回滚命令是什么？”

多查询分解模块将该问题拆解为两个正交的子查询：
- 子查询 1：“v2.4 集群升级 超时 配置参数 默认值”
- 子查询 2：“v2.4 集群升级失败 回滚操作 命令”

两个子查询分别执行独立检索，合并召回候选集并去重，确保每个子意图都有对应的文档片段被命中。

### 索引端层次化设计：Parent-Child（父子块）策略

在切分文档时，固定尺寸切块面临“颗粒度冲突”：切块太小（如 128 Token），语义聚焦、向量相似度计算精准，但塞入 Prompt 时信息支离破碎；切块太大（如 1024 Token），单块包含多个子主题，向量计算时关键信息被稀释，检索命中率下降。关于切块大小与滑动窗口的底层分析可参考[/llm-100/rag/chunk-strategy.md](/llm-100/rag/chunk-strategy.md)。

**父子块（Parent-Child / Small-to-Big）切分策略**将“用于检索的单元”与“用于生成的单元”分离开来：

1. **索引阶段**：
   - 首先将文档按自然段落或层级切分成较大的文本块，作为**父块（Parent Chunk）**，例如 1024 Token；
   - 再将每个父块切细为若干小段落，作为**子块（Child Chunk）**，例如 128 Token；
   - 仅对**子块**计算向量嵌入并写入向量库，子块的元数据中包含所属父块的唯一标识 `parent_id`；
   - 将**父块**的完整正文存储在文档存储（Docstore 或 Key-Value 存储）中。
2. **检索阶段**：
   - 检索器使用查询向量在向量库中寻找最相似的**子块**；
   - 获取命中子块的 `parent_id` 并进行去重；
   - 根据 `parent_id` 直接从 Docstore 中读取完整的**父块**文本，拼接送入生成模型的上下文窗口。

在贯穿例子中，文档 A 的“默认值为 300 秒”子块被精准匹配，但最终送给模型的是包含前置条件“针对集群升级任务”、“v2.4 版本”的完整父块，模型由此能够完整回答前提与具体数值，避免信息断章取义。

![父子块索引与组装机制](/images/content-rebuild/c74b6eebab470d3f/fig-2.png)

上图展示了存储与检索的双层分离机制：底层的向量库只索引高区分度的子块，而顶层的生成上下文直接装配包含完整上下文的父块文本。

### 元数据提取与预过滤（Pre-filtering）

纯向量检索依赖向量间的空间距离，无法对确定性属性（如系统版本、发布日期、所属部门、密级）提供硬性约束。在贯穿场景中，提问包含“2.4 版本”，但旧版文档 B 的文字描述可能与问题在语义上同样接近，导致旧版配置被误召回。

解决办法是在数据入库阶段提取元数据，并在查询阶段执行结构化过滤。

```python
from pydantic import BaseModel, Field

class DocumentMetadata(BaseModel):
    doc_category: str = Field(description="文档类型，例如：操作手册、配置参考、故障排查")
    target_version: str = Field(description="适用的软件或系统版本号，如 v2.4，通用填 common")
    component: str = Field(description="关联的核心组件，如 etcd, apiserver, worker")
```

入库管道通过规则或小模型将每个切块提取出元数据，随同向量一起写入支持元数据过滤的向量引擎（如 Qdrant、Milvus 等）。

在检索时，查询路由模块先解析提问中的属性约束：

$$\text{Query} \rightarrow \begin{cases} \text{Filter: } \{\text{target\_version} \in [\text{'v2.4'}, \text{'common'}]\} \\ \text{Vector: } E(\text{Query}) \end{cases}$$

**过滤方式的工程选择**：当业务存在租户隔离、版本限制等硬性约束且目标子集占比较小时，通常建议优先采用**预过滤（Pre-filtering）**，而非后过滤（Post-filtering）。
- **后过滤（Post-filtering）**：先按向量距离在全库中检索出 Top-K，然后再根据元数据剔除不合规项。如果符合版本条件的文档在库中占比很低，Top-K 结果过滤后可能只剩下极少甚至 0 条数据，导致召回不足。
- **预过滤（Pre-filtering）**：检索前先由存储引擎利用标量索引圈定候选集合，只在该子空间内执行向量距离计算，确保最终返回的 Top-K 结果全部符合属性约束。

### 自动化评测：Context Precision、Faithfulness 与 Answer Relevancy

为了脱离主观抽查，建立可回归的评测流程，行业主流评测体系（如 LlamaIndex 与 Ragas 规范）将 RAG 系统表现拆解为三个正交的核心指标：

| 指标名称 | 评测输入 | 度量问题 | 对应排查环节 |
| :--- | :--- | :--- | :--- |
| **Context Precision**<br>（上下文精准度） | 用户问题 + 检索上下文 + 参考答案 | 检索到的上下文片段中，真正相关的部分是否排在靠前位置？ | 检索器 / Rerank 重排层 |
| **Faithfulness**<br>（忠实度） | 检索上下文 + 生成回答 | 回答中的每一处陈述，是否都能在检索出的上下文中找到证据？ | 提示词约束 / 模型事实幻觉 |
| **Answer Relevancy**<br>（回答相关性） | 用户问题 + 生成回答 | 回答是否正面回应了用户的问题，是否存在跑题或多余回答？ | 生成模型的指令遵循能力 |

#### 指标计算机制

1. **Context Precision**：度量排序质量。假定检索返回了 $K$ 个文档块，由裁判模型或基准标签判断第 $k$ 个片段是否相关，记指示变量 $r_k \in \{0, 1\}$：
   $$\text{Context Precision@K} = \frac{\sum_{k=1}^K (\text{Precision@}k \times r_k)}{\sum_{k=1}^K r_k}$$
   其中 $\text{Precision@}k = \frac{\sum_{j=1}^k r_j}{k}$。若检索结果中不包含任何相关文档（即分母 $\sum_{k=1}^K r_k = 0$），指标直接计为 0。若相关文档排在第 1 位，得分显著高于相关文档沉在第 5 位的情况。

2. **Faithfulness**：度量幻觉程度。评测模型先将最终回答拆分为 $m$ 个独立的原子命题集合 $C = \{c_1, c_2, \dots, c_m\}$，随后逐一校验每个命题能否被检索上下文推导：
   $$\text{Faithfulness} = \frac{\sum_{i=1}^m \mathbb{I}(c_i \text{ 能由上下文支持})}{m}$$
   若评测显示 Context Precision 很高而 Faithfulness 很低，表明**检索端已找到正确材料，问题出在模型未能严格依据上下文生成，产生了无依据的推论**。

3. **Answer Relevancy**：度量回答是否切题。评测系统让评估模型根据当前生成的回答，反向推导可能对应的问题，并计算反推问题与真实问题的 Embedding 余弦相似度均值。如果模型输出大量客套话或答非所问，相似度会显著下降。

### 评测集构建与评估器校准

自动化评测的有效性取决于测试集质量与评估模型（LLM-as-a-Judge）判定的稳定性。

#### 1. 问答基准集（LabelledRagDataset）
工业实践中通常结合**合成数据生成**与**人工复核**来构建评估数据集：
- **文档采样**：从技术文档库中抽取具有代表性的核心段落；
- **生成问题**：利用能力较强的模型提取段落关键信息，逆向生成自然语言提问；
- **标注基准**：记录生成回答所需的黄金参考答案（Reference Answer）与对应的文档块 ID（Reference Contexts）。

```python
# 评测样本的核心数据结构
eval_sample = {
    "query": "v2.4 版本集群升级超时应该修改哪个参数？默认值是多少？",
    "reference_contexts": ["doc_chunk_v24_upgrade_guide"],
    "reference_answer": "应修改 upgrade_timeout_seconds 参数，该参数在 v2.4 中默认值为 300 秒。"
}
```

#### 2. 评估器校准（LabelledEvaluatorDataset）
以大模型作为裁判打分时，裁判模型本身可能存在打分偏置。因此需要准备 100 左右包含人工正误标注的样本集，运行评测 Prompt，计算评估模型的打分与人工判定之间的一致性（例如准确率或二分类 F1-Score）。一致性达到可用阈值后，才能将自动化评测指标作为流程发布的门禁。

### 优化消融调优：从 Baseline 到加权 RRF

为了展示各优化方案的调优机制与改善趋势，以下基于包含 200 条技术问答的合成评估场景，展示一组消融对比示意数据。

#### 优化演进配置
- **Phase 0（Baseline 朴素 RAG）**：固定 512 Token 切块，纯向量检索（Top-K=5），无查询变换；
- **Phase 1（+ HyDE）**：在查询端增加假想文档生成，拉近问答空间距离；
- **Phase 2（+ Parent-Child）**：索引端采用 128 Token 子块建库向量，命中后映射回 1024 Token 父块作为生成上下文；
- **Phase 3（+ 加权 RRF 混合检索）**：引入 BM25 稀疏检索与密集向量检索并行，通过加权倒排排名融合（Weighted Reciprocal Rank Fusion）合并排位。关于稀疏与密集检索的机制差异详见[/llm-100/rag/bm25-in-rag.md](/llm-100/rag/bm25-in-rag.md)与[/llm-100/rag/retrieval-methods.md](/llm-100/rag/retrieval-methods.md)。

加权 RRF 公式如下：
$$RRF\_Score(d) = w_{dense} \cdot \frac{1}{k + r_{dense}(d)} + w_{sparse} \cdot \frac{1}{k + r_{sparse}(d)}$$
其中平滑常数 $k$ 通常取 60，$r(d)$ 为文档在对应列表中的排名（从 1 开始计；若文档未出现在某一路结果列表中，则对应项得分计为 0）。在技术术语密集场景下，本例将稀疏权重设为 $w_{sparse}=1.5$，向量权重设为 $w_{dense}=1.0$。

#### 消融实验数据对比（合成测试集，样本数 $N=200$，示意算例）

| 阶段 | 策略调整 | Context Precision | Faithfulness | Answer Relevancy | 平均端到端延迟 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Phase 0** | Baseline 朴素方案 | 0.62 | 0.71 | 0.73 | ~850 ms |
| **Phase 1** | + 查询端 HyDE | 0.71 | 0.74 | 0.84 | ~1650 ms |
| **Phase 2** | + 索引端 Parent-Child | 0.83 | 0.89 | 0.86 | ~1750 ms |
| **Phase 3** | + 加权 RRF 混合检索 | **0.91** | **0.93** | **0.92** | ~1820 ms |

*注：上表指标与延迟为特定测试集与硬件环境下的实验记录示意。不同模型、硬件规格与语料复杂度会导致实际绝对数值变化。*

从指标变化可以看出：
- **引入 HyDE 后**：Answer Relevancy 与 Precision 显著提高，但因为检索前增加了一次 LLM 生成，端到端延迟增加了约 800 ms；
- **引入 Parent-Child 后**：Faithfulness 明显上升（0.74 $\rightarrow$ 0.89）。这是因为父块保留了完整的段落逻辑，解决了小切块上下文缺失导致的推断臆测；
- **引入加权 RRF 后**：BM25 弥补了向量检索对技术专有名词（如配置参数名）匹配不精准的问题，使相关文档排在前面的概率进一步提升。如果需要对召回结果做进一步精细打分，可参考两阶段重排机制：[/llm-100/rag/rerank-importance.md](/llm-100/rag/rerank-importance.md)。

### 边界与工程权衡

上述优化方案在带来准确率收益的同时，也伴随着系统资源和延迟开销，落地时需要评估以下权衡：

1. **首字延迟（TTFT）与算力开销**：
   HyDE 需要在向量比对前由模型先生成一段伪文档，直接增加数百毫秒至一秒以上的延迟；多查询拆解则会导致并发检索请求倍增。在对延迟要求极苛刻的实时交互场景，应优先使用低开销的规则改写或单句改写。
2. **存储与索引膨胀**：
   采用父子块策略后，文档被切分为密集的微小文本块，向量数量会增加数倍，直接扩大了向量索引的内存占用与磁盘开销。子块尺寸不宜切分过小（例如小于 64 Token），否则过碎的文本会导致大量弱相关子块被检索命中，增加无效父块的去重负担。
3. **融合权重的环境依赖**：
   加权 RRF 中的权重配比取决于特定数据集的特征。如果业务语料更偏向自然语言长句，向量检索权重应占优；若语料包含大量缩写、版本号、API 签名，则需提高关键词检索比重。权重参数需要在验证集上定期标定，不可直接当作通用常数。

### 可检验练习

#### 练习 1：手算加权 RRF 排名融合
已知候选文档池中有文档 $d_1$ 和 $d_2$：
- 密集检索结果排名：$d_1$ 排名第 1（$r_{dense}=1$），$d_2$ 排名第 3（$r_{dense}=3$）；
- 稀疏检索（BM25）结果排名：$d_1$ 排名第 4（$r_{sparse}=4$），$d_2$ 排名第 1（$r_{sparse}=1$）。

设定平滑常数 $k=60$，检索权重为 $w_{dense}=1.0$，$w_{sparse}=1.5$。

**计算步骤与检验**：
1. 计算 $d_1$ 的得分：
   $$RRF(d_1) = 1.0 \times \frac{1}{60 + 1} + 1.5 \times \frac{1}{60 + 4} = \frac{1}{61} + \frac{1.5}{64} \approx 0.016393 + 0.023438 = 0.039831$$
2. 计算 $d_2$ 的得分：
   $$RRF(d_2) = 1.0 \times \frac{1}{60 + 3} + 1.5 \times \frac{1}{60 + 1} = \frac{1}{63} + \frac{1.5}{61} \approx 0.015873 + 0.024590 = 0.040463$$
3. **结论**：因为稀疏检索赋予了更高权重，$d_2$ 的最终得分高于 $d_1$，融合排序中 $d_2$ 位列第一。

#### 练习 2：计算 Context Precision@5
假设检索返回了 5 个文档块，经与标准答案对照，命中的相关性序列为 $r = [1, 0, 1, 0, 0]$（第 1、3 块与提问相关，其余不相关）。
- $k=1$：$r_1=1$，$\text{Precision@}1 = \frac{1}{1} = 1.0$
- $k=2$：$r_2=0$
- $k=3$：$r_3=1$，$\text{Precision@}3 = \frac{1 + 0 + 1}{3} = \frac{2}{3} \approx 0.667$
- $k=4, 5$：$r_k=0$

命中相关文档总数 $\sum_{k=1}^5 r_k = 2$。
$$\text{Context Precision@5} = \frac{1.0 \times 1 + 0.667 \times 1}{2} = \frac{1.667}{2} \approx 0.833$$
