搭建好一套检索增强生成（RAG）系统后，线上最常遇到的问题往往不是系统报错崩溃，而是模型给出的回答“答非所问”或“看似言之成理却与事实不符”。

例如，用户询问：“安逸商城生鲜订单破损，物流赔付上限是多少？”系统却回答：“生鲜订单不支持退货，请联系快递员确认。”或者输出了“单次最高赔付 30 元”，但业务最新规则明明是 50 元。

出现这种异常时，不能笼统归咎于大模型的“幻觉”，也不能盲目认为只要换一个更大的向量模型就能解决。RAG 系统的处理流程包含两步：先从外部知识库检索相关文本，再将文本拼进提示词（Prompt）让大模型阅读并生成回答。排查问题的关键，是先确定故障究竟发生在检索环节，还是生成环节。

## 故障分类：检索端失效与生成端失效

排查线上问答异常的第一步，是查看实际送入大语言模型提示词中的上下文片段（Context）。根据上下文是否包含推导答案所需的客观依据，可以将异常分为两类：

```text
                           用户提问 Query
                                 │
                 ┌───────────────┴───────────────┐
                 ▼                               ▼
     【检索端失效：缺少正确证据】           【生成端失效：包含正确证据】
     ├─ 词表未命中：专业术语匹配不上        ├─ 位置衰减：证据在中段被忽略
     ├─ 切分断裂：主体与结论被硬拆截断      ├─ 噪声干扰：无关片段误导生成
     └─ 语义不对称：问答句式相似度偏低      ├─ 版本冲突：多份文档相互矛盾
                                            └─ 先验覆盖：依赖自身记忆答错
```

1. **检索端失效**：送入模型提示词的候选文档中，在客观上缺少推导出正确答案所必需的信息。此时无论大模型的阅读理解能力多强，都无法仅凭给定的参考资料得出结论。如果提示词未做严格拒答约束，模型往往会退回依赖预训练记忆，从而产生虚构陈述。
2. **生成端失效**：候选文档中完整包含了所需的全部事实，但模型输出仍然错误。常见原因包括关键信息被夹在长文本中段受到忽略、提示词中塞入的无关段落造成干扰，或者知识库中存在多个矛盾版本导致模型拼接了错误事实。

将排查路径拆分为这两大方向，可以避免在检索漏召回时盲目调试模型生成提示词，也能避免在上下文位置偏差或冲突干扰时盲目更换向量模型。

## 检索端未命中：为什么模型拿不到正确依据？

当最终提示词里没有包含正确答案的片段时，说明问题出在知识库构建或召回链路。以下是三种最常见的工程成因：

### 1. 切分断裂导致的语义孤立
很多系统采用固定字符数（例如每 300 字硬切一刀）进行机械分块。这种切法很容易把一个完整逻辑事实拆分到两个相邻的块（Chunk）中。

以下面这段生鲜赔偿规则为例：

```text
原始文档片段：
“安逸商城跨境生鲜退货均由冷链专线承运。因保温箱破损导致的商品变质，单次最高赔付标准为 50 元。”

机械切分后的结果：
【Chunk A】：安逸商城跨境生鲜退货均由冷链专线承运。因保温箱破损导致
【Chunk B】：的商品变质，单次最高赔付标准为 50 元。
```

当用户提问“安逸商城跨境生鲜破损赔付上限是多少”时：
- **Chunk A** 包含主体“安逸商城跨境生鲜”，但缺少赔付金额；
- **Chunk B** 包含了“单次最高赔付标准为 50 元”，但句首的主语残缺，变成了一个缺乏归属的孤立从句。

在向量检索中，Chunk B 很难与带有明确主体名称的提问建立强匹配；即使 Chunk A 被召回，模型也无法根据它算出赔偿金额。要避免切分断裂，切分策略应结合标点段落边界，或在重叠窗口（Chunk Overlap）、文档层级解析（如按 Markdown 标题层级）上下功夫。具体切分策略可参考 [文档切分 Chunk 应该怎么做？](/llm-100/rag/chunk-strategy.md)。

### 2. 专业专名与词表失配
纯稠密向量检索（Dense Retrieval）依靠预训练嵌入模型将文本映射为高维向量。但遇到生僻型号、专用缩写或内部规范代号（例如单号前缀 `FS-COOL-2024` 或特定芯片型号）时，若模型在预训练时未充分见过该词，分词器会将其拆解为多个子词碎片，计算出的向量表征容易退化为宽泛的泛化语义，难以拉开与其它文档的距离。

此时，依靠统计字词精确匹配的传统算法（如 BM25）往往能准确命中包含该代号的文档。这也是为什么生产系统通常使用稠密向量与稀疏关键词结合的混合检索。相关对比可查阅 [BM25 为什么还能在 RAG 中发挥作用？](/llm-100/rag/bm25-in-rag.md) 以及 [相似度检索、关键词检索、混合检索有什么区别？](/llm-100/rag/retrieval-methods.md)。

### 3. 问答句式不对称的语义距离
用户提问通常是简短疑问句（“生鲜坏了赔多少？”），而知识库正文则是长句陈述（“关于冷藏包装破损导致损耗的责任认定及限额细则”）。

若使用的嵌入模型未在不对称问答任务上做过针对性微调，疑问句与陈述句在向量空间内的余弦相似度可能并不高，甚至不如某些字面重合度高但回答无关问题的陈述句。模型选型可参考 [Embedding 模型如何选择？](/llm-100/rag/embedding-selection.md)。

## 低相关性噪声注入：Top-K 放大带来的生成干扰

为了防止漏掉正确信息，很多开发者习惯在初筛阶段放大召回数量（例如将 Top-K 直接设为 10 甚至 15 个分块）。然而，盲目将低相关度片段拼进提示词，会直接对生成质量产生负面影响。

大语言模型基于自注意力机制依次处理整个上下文。提示词中混入的大量弱相关内容（例如搜出了“普通商品退货流程”、“运费险购买指南”等），并非完全不被模型关注，其中的词汇、实体与数值会与核心问题产生竞争：

1. **混淆实体与数值**：例如用户问生鲜破损赔付，检索带进来了运费险说明中的“单次赔付 15 元”。模型可能将运费险的限额张冠李戴，作为生鲜破损的赔付答案输出。
2. **削弱拒答边界**：系统提示词通常会要求“如材料未提及请说明无法回答”。但当提示词中充斥着多篇与该领域相关的低置信度段落时，模型更容易产生“这里面一定有答案”的倾向，转而从弱相关段落中推导虚构结论。

防止噪声干扰的常规工程手段是在向量检索后增加重排序（Rerank）环节，使用交叉编码器对初筛结果进行打分，并设置分数阈值剔除低相关候选。具体机制请参阅 [Rerank 重排序为什么重要？](/llm-100/rag/rerank-importance.md)。

## 上下文位置偏差：中段信息容易被忽略

在很多失败案例中，排查日志发现正确的事实分块确实被召回了，且排在召回列表的第 3 位或第 4 位，但模型回答时却对其视而不见，甚至声称“知识库未提及该项信息”。

这种现象与大语言模型处理长序列时的**上下文位置偏差**（Lost in the Middle）密切相关。测试表明，当关键证据处于上下文两端（靠近开头的系统指令区，或靠近结尾的提问区）时，模型成功提取并利用该证据的概率较高；而当证据被夹在长文本的中段时，模型忽略该证据的概率会明显升高。

```text
      关键证据在 Prompt 中所处物理位置与回答正确率变化趋势（示意）
      高 ┌──────────────────────────────────────────────┐
         │  ███                                    ███  │
         │  ███                                    ███  │
         │  ███  ███                          ███  ███  │
         │  ███  ███                          ███  ███  │
         │  ███  ███  ███                ███  ███  ███  │
         │  ███  ███  ███  ███      ███  ███  ███  ███  │
         │  ███  ███  ███  ███  ███ █▄█  ███  ███  ███  │
      低 └──────────────────────────────────────────────┘
            开头前缀            中段区域            结尾后缀
```

*注：上图呈现的是长序列基准评测中观察到的典型性能变化趋势，用于指导上下文排版，并非所有模型的固定准确率绝对值。*

在拼接提示词时，需要注意以下工程要点：
- **控制上下文总量**：只保留经过重排序筛选后的高置信度片段（通常 3 到 5 个），避免无节制堆叠长文本。
- **关键片段排布**：若包含多条相关度不同的证据，可将得分最高的片段放在最靠近结尾提问的位置，或紧跟在系统提示词之后，降低中段被忽略的风险。

## 多版本冲突：相互矛盾的内容如何引发错误？

在长期维护的知识库中，常常同时沉淀着旧版规则与新版规范。如果数据入库时未做版本隔离，检索很可能同时命中不同时期的文档。

例如，知识库中同时存在：
- **文档 A（2022 年规则）**：“生鲜破损单次赔付上限为 30 元。”
- **文档 B（2024 年新规）**：“生鲜破损单次赔付上限已调整至 50 元。”

大语言模型本身没有真实世界的物理时钟感知，看到两份平铺直叙但结论相悖的文本，通常会出现以下两类错误行为：

1. **结论缝合**：将两段话拼凑成从未存在过的伪规则，例如输出“单次赔付标准为 30 元，但在特定调整后最高可达 50 元”。
2. **非确定性摇摆**：受采样随机性影响，同一次提问时而回答 30 元，时而回答 50 元。

解决版本冲突不能单靠在提示词里加上“请依据最新规范回答”。大模型无法准确推断哪一段文字是最新颁布的。可靠的做法是在数据入库（Ingestion）时，为每篇文档提取版本号、生效日期和失效状态作为元数据（Metadata），存入向量数据库；检索时通过元数据过滤（Metadata Filtering），在检索阶段直接排除已失效的历史版本。

## 基于 Trace 日志的全链路排查实操

排查线上 Bad Case 时，切忌只对着最终模型输出猜测原因。可复现、可定位的排查必须依赖全链路结构化日志（Trace）。一次标准的 RAG 请求日志应包含以下各阶段状态：

```json
{
  "trace_id": "rag_trace_20250518_0102",
  "query": "安逸商城跨境生鲜破损单次赔付上限是多少？",
  "retrieval_stage": {
    "dense_matches": [
      {"chunk_id": "chunk_102", "score": 0.81},
      {"chunk_id": "chunk_809", "score": 0.65}
    ],
    "sparse_matches": [
      {"chunk_id": "chunk_102", "score": 7.82},
      {"chunk_id": "chunk_305", "score": 5.12}
    ],
    "fused_candidates": ["chunk_102", "chunk_809", "chunk_305"]
  },
  "rerank_stage": {
    "ranked_chunks": [
      {"chunk_id": "chunk_102", "score": 0.93, "version": "2024-v2"},
      {"chunk_id": "chunk_305", "score": 0.42, "version": "2022-v1"}
    ]
  },
  "prompt_assembly": {
    "assembled_chunks": ["chunk_102"],
    "prompt_token_count": 520
  },
  "generation_stage": {
    "response": "根据2024年生鲜售后规范，因保温箱破损导致商品变质的，单次最高赔付标准为50元。",
    "finish_reason": "stop"
  }
}
```

拿到异常日志后，遵循如下两步排查树进行定位：

```text
                  用户反馈回答错误 / 出现异常
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
      检查 Prompt 中的 Context        Prompt Context 中
      包含推导所需的完整依据？         缺少必要依据或内容残缺？
              │                               │
      【排查生成端】                  【排查检索端】
      ├─ 关键证据是否处于中段？       ├─ 知识库底层是否存在该条内容？
      ├─ 是否存在冲突版本并存？       ├─ 切分分块是否打断了主谓宾结构？
      ├─ 是否注入过多无关噪声分块？   ├─ 关键词/单号是否未被检索命中？
      └─ 采样参数（Temperature）过高？ └─ 重排序模型是否将正确分块过滤？
```

### 决策推演顺序
1. **优先确认实际投喂的 Context**：在日志中调出 `prompt_assembly` 字段。如果人工阅读这些段落确认已包含推导正确答案所需的充分事实，**即可基本排除正确证据漏召回的问题**，排查重点转向生成阶段的呈现与干扰因素（检查关键信息排布位置、是否存在多版本或无关片段干扰、系统提示词约束与采样参数）。若发现混入了过期版本或大量无关噪声，再针对性回溯元数据过滤规则或重排序阈值。
2. **逆向核对召回与重排序阶段**：若 Context 中没有正确内容，对比 `rerank_stage` 与 `retrieval_stage`。如果初筛列表中存在正确 Chunk，但重排序后被裁减，说明重排序打分阈值过高或领域适应不足；若初筛中完全没有正确 Chunk，则需要核查知识库原文收录情况、分块边界切分质量与向量匹配度。

关于召回率与准确率的系统性评估指标，可继续阅读 [如何优化 RAG 的召回率和准确率？](/llm-100/rag/optimize-rag.md)。如果是在面试准备中遇到该类题型，可查阅 [RAG 检索到了正确内容，但模型回答仍然错误，可能是什么原因？](/interview/high-freq-scenarios/rag-answer-wrong.md)。

## 检验与思考

请结合本讲知识，分析以下两个工程场景：

1. **某系统在 Trace 中确认：推导答案所需的事实片段排在检索结果的第 1 位，并成功拼接进 Prompt 的开头，但模型依然给出了与该片段相悖的错误结论。在排除模型预训练先验覆盖的前提下，还应当检查哪些生成环节的设置？**
   *提示：检查是否存在生成采样参数（如 Temperature）过高导致发散、系统提示词中是否有更强硬的格式或拒答指令产生逻辑冲突。*

2. **知识库中存在同款产品在不同年份的多份迭代说明，经常导致回答中混用新旧参数。为什么“在系统提示词中加上‘请只参考最新文档’”通常无法稳定根治该问题？工程上更稳妥的处理手段是什么？**
   *提示：从大模型对物理时间感知能力的局限性，以及向量数据库元数据过滤（Metadata Filtering）的确定性角度进行分析。*
