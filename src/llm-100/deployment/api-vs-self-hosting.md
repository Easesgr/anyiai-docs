在大模型技术落地时，技术团队面临的首要工程决策不是微调参数怎么调，而是底座算力采用哪种模式：**直接调用第三方商业云端 API，还是采购/租赁 GPU 硬件自建私有化推理集群？**

这一抉择不仅决定了前期的资金投入方式，还直接绑定了系统的数据合规边界、扩展弹性以及后续的团队运维负担。如果缺乏精确的财务与流量测算，盲目自建容易陷入硬件闲置折旧与驱动运维泥潭；而完全依赖外部 API，则可能面临数据出域合规风险、公网延迟抖动以及调用量放大后的费用失控。

本讲基于 [本地部署大模型需要哪些硬件？](/llm-100/deployment/hardware-estimation.md) 的显存与算力核算规则，推导 API 与自建部署的财务平衡点模型，分析流量潮汐对真实成本的影响，并给出兼顾安全与弹性的混合架构实现方案。

学习目标：
1. 掌握大模型全生命周期总拥有成本（TCO）的核算方法与平衡点公式。
2. 理解并发潮汐如何改变硬件利用率与单 Token 履约成本。
3. 能根据合规要求与业务流量波形，设计“稳态自建 + 峰值 API”的混合路由架构。

## 贯穿案例与决策矩阵总览

为了让工程概念落地，我们以一家正在落地大模型的金融科技公司为例。该公司计划上线一套“信贷业务助手”，主要承接两类任务：
1. **合规敏感任务**：审查用户征信流水、身份信息与风控评级；
2. **通用咨询任务**：解答用户关于信用卡权益、营业网点地址及常见贷款政策的咨询。

公司需要决定是全部采购商业 API、全部自建 8 卡 GPU 服务器，还是采用混合架构。评估通常基于以下五个维度：

| 评估维度 | 商业云端 API | 私有化自建推理集群 |
| :--- | :--- | :--- |
| **资金支出结构** | 纯运营支出（OPEX），按实际消耗 Token 弹性计费 | 包含资本性支出（CAPEX）折旧与机房/电费固定运营成本（OPEX） |
| **资源弹性与扩展性** | 几乎无需维护扩容，分钟级承接突发并发峰值 | 算力上限由本地卡数锁定，扩容受硬件采购周期与集群搭建限制 |
| **数据合规与主权** | 数据需传输至第三方供应商云端，依赖服务商数据协议 | 数据物理闭环不出内部局域网，可部署在内外物理隔离网络 |
| **模型定制与控制力**| 仅开放预设 HTTP 接口，无法直接获取隐藏层激活或修改底层算子 | 支持任意量化算子替换、白盒微调权重加载与动态批处理调度定制 |
| **工程运维负担** | 由云厂商承担底层 SLA，内部零硬件与驱动维护工作量 | 需内部维护机柜散热、网络拓扑、CUDA 驱动、故障迁移与推理服务监控 |

这五个维度互为约束条件。如果数据合规是硬性法律红线，即使自建成本更高也必须私有化；而在产品立项初期、日请求量波动巨大时，灵活性与零固定资产投入则是首要考量。

## 财务平衡点（Break-even Point）量化计算模型

评估采购还是自建，首先需要量化全生命周期总拥有成本（Total Cost of Ownership, TCO）。

![CAPEX与OPEX在不同吞吐量下的成本平衡曲线](/images/content-rebuild/ed9f27620ddc82eb/fig-1.png)

### 1. 成本函数定义

调用商业 API 的月度成本 $C_{\text{API}}$ 取决于实际调用的输入、输出 Token 总量与供应商定价：

$$C_{\text{API}} = \sum_{i} \left( T_{\text{in}, i} \times P_{\text{in}} + T_{\text{out}, i} \times P_{\text{out}} \right)$$

其中 $T_{\text{in}}, T_{\text{out}}$ 为月度输入与输出 Token 数量，$P_{\text{in}}, P_{\text{out}}$ 为单位 Token 单价。

自建私有集群的月度实际总成本 $C_{\text{Self}}$ 则由固定折旧、基础设施运营和运维人力三部分构成：

$$C_{\text{Self}} = \text{CAPEX}_{\text{amortized}} + \text{OPEX}_{\text{infra}} + \text{OPEX}_{\text{labor}}$$

*   $\text{CAPEX}_{\text{amortized}}$：计算节点服务器、交换机与高速线缆的购置折旧。数据中心服务器通常按 36 个月直线折旧（月折旧率约为 $1/36$）。
*   $\text{OPEX}_{\text{infra}}$：数据中心机柜机位租赁费、电力消耗（含机房能源效率指标 PUE 乘数）以及出口保底带宽网络费用。
*   $\text{OPEX}_{\text{labor}}$：维护集群运转所需的运维或算法工程师薪酬分摊工时。

### 2. 70B 级别开源模型平衡点算例

我们设定一个基准算例（数值用于示范逻辑计算，实际采购请以当期硬件与云服务报价为准）：

1.  **目标模型与硬件配置**：70B 参数开源模型，使用 FP8 精度部署。单台服务器配备 8 张 80GB 显存加速卡，通过 NVLink 互联，由 [vLLM 为什么推理速度快？](/llm-100/deployment/vllm-inference.md) 提供并发服务。
2.  **商业 API 价格**：同级别开源模型商业 API 综合加权价格设定为：每 100 万 Token（按典型输入输出比例加权）5 元人民币，即单 Token 成本 $P = 5 \times 10^{-6}$ 元。
3.  **自建硬件折旧（CAPEX）**：整机采购成本约为 360,000 元，按 36 个月直线折旧，月均折旧 $\text{CAPEX}_{\text{amortized}} = 10,000$ 元。
4.  **机房与电费（OPEX）**：单台整机满载与待机综合平均功耗取 2.5 kW，机房 PUE 取 1.3，月耗电量为：
    $$2.5\text{ kW} \times 1.3 \times 24\text{ 小时} \times 30\text{ 天} = 2,340\text{ kWh}$$
    电价按 0.8 元/kWh 计算得 1,872 元；加上高保密机房机柜机位费 3,000 元/月，基础设施月费用 $\text{OPEX}_{\text{infra}} = 4,872$ 元。
5.  **运维人力成本分摊（OPEX）**：按运维工程师 0.2 个人月维护该节点，分摊月度工时成本 $\text{OPEX}_{\text{labor}} = 6,000$ 元。

此时，单台自建节点的保底月度总支出为：

$$C_{\text{Self}} = 10,000 + 4,872 + 6,000 = 20,872\text{ 元/月}$$

**平衡点 Token 总量推导**：

$$N_{\text{break-even}} = \frac{C_{\text{Self}}}{P} = \frac{20,872}{0.000005} \approx 41.74\text{ 亿 Token / 月}$$

折合日均 Token 产出需达到 **1.39 亿 Token**。也就是说，只有当业务月度稳定吞吐超过 41.7 亿 Token，且单台服务器性能能够承接该吞吐时，自建才开始在纯财务核算上体现出单价优势。

### 3. 硬件吞吐上限物理核验

核算平衡点时，必须核验硬件的物理极限：**单台 8 卡服务器在一个月内能否产出 41.74 亿 Token？**

*   一个月按 30 天计算，共有 $30 \times 86,400 = 2,592,000$ 秒。
*   维持月产 41.74 亿 Token，要求系统 30 天 24 小时不间断输出，平均生成速度必须达到：
    $$\frac{4,174,000,000}{2,592,000} \approx 1,610\text{ Token/s}$$
*   根据主流推理引擎在 8 卡 80GB（FP8 精度）上的实测基准，70B 密集模型在 Continuous Batching 达到较大 Batch Size（如 64 以上）且 Prefill 与 Decode 混合打满时，系统吞吐可达到 1,200~1,800 Token/s。但在真实并发受限或短请求场景下，吞吐往往难以全天候维持在 1,600 Token/s 以上。如果单机吞吐上限无法覆盖平衡点，就必须采购第 2 台服务器，导致自建固定成本翻倍（达到约 41,744 元/月），平衡点也将后移至 83.5 亿 Token/月。

## 流量潮汐效应与资源利用率陷阱

在上述推导中，隐含了一个脱离生产实际的假设：**请求是 24 小时绝对均匀到达的**。工程实践中，企事业单位的真实业务流量通常呈现剧烈的“潮汐现象”。

![潮汐流量下实际有效吞吐与硬件闲置折旧对比](/images/content-rebuild/ed9f27620ddc82eb/fig-2.png)

### 1. 为什么“日均 Token 量”会制造财务假象？

在信贷业务场景中，用户咨询高度集中于工作时段（09:00 至 18:00），夜间流量通常接近于零。

*   **自建系统的容量刚性**：自建系统不能按照“日均吞吐量”采购硬件，而必须按照**峰值并发需求（Peak RPS）**配置算力。根据 [大模型推理为什么慢？瓶颈在哪里？](/llm-100/deployment/inference-bottlenecks.md) 中的分析，推理服务的延迟受 Memory Bandwidth 和 KV Cache 容量约束。如果白天的峰值并发是全天平均值的 3 倍，企业就必须配置承载峰值的硬件，否则队列排队会导致延迟急剧增加甚至请求超时。
*   **低谷期的固定损耗**：在夜间低谷期，服务器折旧、机房供电与制冷费用并不会停止。硬件利用率（Utilization Ratio）下跌，会直接拉高每一张实际生成 Token 的综合成本。

### 2. 有效利用率公式

定义真实有效单 Token 履约成本 $P_{\text{effective}}$：

$$P_{\text{effective}} = \frac{C_{\text{Self}}}{T_{\text{actual}}} = \frac{C_{\text{Self}}}{\eta \times T_{\text{max}}}$$

其中 $T_{\text{max}}$ 为服务器 24 小时满载下的理论产出量，$\eta$ 为实际利用率（$0 \le \eta \le 1$）。

假设自建单机 24 小时跑满的月产出为 30 亿 Token。如果受白天峰值、夜间低谷的潮汐影响，实际月交付量仅为 7.5 亿 Token（$\eta = 25\%$），则单 Token 履约成本实质上升为基准的 **4 倍**：

$$P_{\text{effective}} = \frac{20,872\text{ 元}}{750,000,000\text{ Token}} \approx 2.78 \times 10^{-5}\text{ 元/Token} = 27.83\text{ 元 / 百万 Token}$$

这一单价远高于商业 API 的 5 元 / 百万 Token。此时，自建看似省下了 API 采购费，实则在为闲置折旧买单。

## 数据安全与监管合规边界

在部分严肃业务场景中，即使自建核算成本高于 API 调用，私有化部署依然是必选项。根本原因在于**数据主权与法务合规刚性门槛**。

![企业数据流动合规审查与出域边界判定流程](/images/content-rebuild/ed9f27620ddc82eb/fig-3.png)

### 1. 刚性法律与网络物理隔离

*   **金融与关键信息基础设施**：金融监管对用户征信信息、借贷流水有明确的驻留要求，禁止将用户明文身份及敏感资产信息上传至公有云多租户模型服务接口。
*   **医疗个人健康信息保护**：病患完整病历与诊断记录属于极度敏感个人数据，明文出域调用公网 API 存在法律合规风险。
*   **机要与内网物理隔离**：政务专网或工业涉密控制系统通常运行在物理隔离（Air-gapped）网络中，外部公网 API 在网络拓扑上物理不可达。

### 2. 商业 API 的合规协议及其审计边界

部分主流云厂商提供了“企业级合规方案”，例如签署数据零留存协议（Zero Data Retention，承诺请求数据不写入磁盘、不参与二次训练），甚至支持专线（VPC Direct Connect）接入。

但从法律管辖权与合规审计角度看，数据明文只要离开企业自主控制的物理服务器，在第三方租户算力节点解密处理，就构成了合规意义上的“数据对外提供”。企业无法穿透审计第三方公有云机房内部的内存隔离与固件漏洞。因此，在合规红线明确的场景下，私有化方案具备“一票否决权”。

## 隐藏的运维与工程成本

只看显卡硬件标价而决定自建的团队，往往低估了大模型分布式推理服务的工程维护难度。

![自建推理服务全生命周期中软硬件运维故障树](/images/content-rebuild/ed9f27620ddc82eb/fig-4.png)

自建集群需要团队承担以下四层技术损耗：

1.  **硬件与网络故障率**：GPU 加速卡在高负载推理下长期发热，显存 ECC 错误、板卡掉卡（GPU Drop-off）、PCIe 降速以及跨节点 RDMA 网络抖动属于常见硬件故障。在张量并行（Tensor Parallelism）模式下，单卡掉线会导致整台服务器的推理进程崩溃退出，需要配置自动健康检查与容灾重启机制。
2.  **推理引擎技术栈依赖维护**：主流推理框架（如 vLLM、TensorRT-LLM）涉及底层 CUDA 驱动、PyTorch 版本、FlashAttention 内核编译与 Triton 算子。升级任何一个基础库，都有可能导致算子编译失败或长文本 Attention 精度截断。
3.  **模型架构演变与适配成本**：当模型从传统的 Dense 架构演进为 MoE（混合专家）架构时，通信拓扑与显存分配机制发生变化，团队需要重新进行通信算子调优与内存编排。相比之下，商业 API 用户只需调整调用参数即可平滑升级。
4.  **模型量化与精度损失压测**：如 [量化是什么？INT8、INT4、GPTQ、AWQ 有什么区别？](/llm-100/deployment/quantization-methods.md) 所述，为了在有限显存内承载更大模型，团队必须自行压测 PTQ 量化后的下游任务准确率与困惑度（Perplexity），这会持续占用算法工程师的人力工时。

## 混合部署架构（Hybrid Strategy）

在商业 API 的高弹性与私有化部署的高安全之间，并不一定是非此即彼的选择。工业界主流架构常采用**混合分流模式**：用私有化硬件承接稳态基线与敏感数据，用商业 API 消化潮汐峰值并兜底。

![稳态底仓走私有化与突发潮汐走云端API的混合路由拓扑](/images/content-rebuild/ed9f27620ddc82eb/fig-5.png)

### 1. 混合分流网关设计

在客户端与模型之间设立统一的“模型接入网关（Gateway）”，实现两级路由逻辑：

```python
from typing import Dict, Any
import time

class HybridModelGateway:
    def __init__(self, local_cluster_client, cloud_api_client):
        self.local_client = local_cluster_client
        self.cloud_client = cloud_api_client
        # 队列深度警戒水位
        self.MAX_LOCAL_QUEUE_DEPTH = 50

    def route_request(self, prompt: str, metadata: Dict[str, Any]) -> str:
        """
        混合调度路由：安全检查 -> 队列容量检查 -> 动态分流
        """
        # 1. 安全合规检查（一票否决）
        if metadata.get("contains_pii") or metadata.get("is_sensitive"):
            return self.local_client.generate(prompt)
        
        # 2. 本地集群负载状态检查
        current_queue_depth = self.local_client.get_waiting_queue_depth()
        
        # 3. 峰值分流逻辑：本地队列饱和且任务非敏感时，突发流量外溢给云端 API
        if current_queue_depth > self.MAX_LOCAL_QUEUE_DEPTH:
            try:
                return self.cloud_client.generate(prompt)
            except Exception as e:
                # 云端降级回退至本地排队
                return self.local_client.generate(prompt)
        
        # 4. 常态流量由本地底仓消化
        return self.local_client.generate(prompt)
```

### 2. 混合架构的运维策略

*   **基线流量走自建（Base Load）**：将私有化集群规模定在业务的**常态低谷水位**（例如保证 80%~90% 的日间稳态运行），确保本地硬件折旧被高利用率充分摊薄。
*   **潮汐突发走云端（Burst Load）**：对于非敏感的咨询类通用流量，在业务高峰期通过网关分流至商业 API，避免为了应对每天 2 小时的瞬时峰值而超额采购硬件。
*   **双向容灾兜底**：当公网链路中断或云端 API 遭遇 429 限流时，非核心业务降级为异步排队；若本地服务器发生硬件故障，在脱敏合规允许的前提下可临时调用备用 API 兜底，具体高并发工程设计可参考 [面试高频：大模型推理服务如何做高并发？](/llm-100/deployment/high-concurrency-serving.md)。

## 选型决策流程与落地清单

项目启动前，可通过以下决策路径进行技术选型核查：

![企业选型最终决策流程与评估清单](/images/content-rebuild/ed9f27620ddc82eb/fig-6.png)

1.  **合规审查**：业务处理的数据是否包含法律法规禁止出域的敏感信息，或处于内网物理隔离环境？
    *   **是** $\to$ **选型私有化自建部署**（或合规专属云私有节点）。
    *   **否** $\to$ 进入下一步。
2.  **流量波形与规模预估**：业务是否处于早期探索期？日均请求是否极小或波动极大？
    *   **是（探索期/高脉冲）** $\to$ **首选商业云端 API**。按量计费，快速验证业务，避免固定资产沉没。
    *   **否（业务稳定/流量持续）** $\to$ 进入下一步。
3.  **财务平衡点试算**：基于前文公式测算，自建节点利用率达到 60% 以上时，月度产出是否稳定超过平衡点 Token 数？
    *   **否** $\to$ **维持商业 API 采购**。
    *   **是** $\to$ 进入下一步。
4.  **工程技术储备**：团队是否具备 Linux 内核调试、GPU 集群网络、CUDA/PyTorch 编译以及推理引擎调优的专职运维能力？
    *   **否** $\to$ **采购商业 API 或第三方全托管算力服务**。
    *   **是** $\to$ **实施“私有化稳态底仓 + 商业 API 弹性削峰”的混合架构**。

选型确立后，关于如何进一步压低本地硬件或 API 调用的开销，可继续参考 [如何降低大模型应用成本？](/llm-100/deployment/llm-cost-optimization.md)。

## 课后检验练习

### 练习目标
根据给定的业务流量与成本参数，计算财务平衡点，并为业务设计合理的部署形态。

### 场景设定
某在线教育公司计划引入 14B 参数模型为学生提供作业答疑。已知条件如下：
1.  **合规属性**：学生输入的问题均为公开教材习题，不含个人隐私与保密信息。
2.  **商业 API 单价**：该 14B 模型的商业 API 综合单价为每 100 万 Token 1.5 元（即 $1.5 \times 10^{-6}$ 元/Token）。
3.  **自建成本**：搭建 1 台双卡专业 GPU 服务器即可承载 14B 模型运行。整机采购价格 60,000 元（按 36 个月直线折旧）；机房机位与用电月度支出 1,500 元；工程维护人力月分摊 3,000 元。
4.  **业务流量**：当前处于业务冷启动期，预计前 3 个月日均 Token 产出约为 1,000 万 Token。

### 检验问题
1.  计算单台自建服务器的月度总拥有成本（TCO）。
2.  计算该场景下自建与 API 调用的月度财务平衡点 Token 量。
3.  根据当前日均 1,000 万 Token 的流量，说明当前阶段应该选择“商业 API”还是“自建私有化”，并给出量化依据。

### 参考答案与验收标准
*   **问题 1**：
    $$\text{CAPEX}_{\text{amortized}} = \frac{60,000}{36} \approx 1,666.67\text{ 元/月}$$
    $$C_{\text{Self}} = 1,666.67 + 1,500 + 3,000 = 6,166.67\text{ 元/月}$$
*   **问题 2**：
    $$N_{\text{break-even}} = \frac{6,166.67}{0.0000015} \approx 4,111,113,333\text{ Token / 月} \approx 41.11\text{ 亿 Token / 月}$$
    折合日均 Token 生成量约为：$41.11\text{ 亿} / 30 \approx 1.37\text{ 亿 Token / 天}$。
*   **问题 3**：
    当前日均 1,000 万 Token，月度总量约为 $1,000\text{ 万} \times 30 = 3\text{ 亿 Token}$。远低于 41.11 亿 Token 的财务平衡点。
    *   商业 API 月支出：$3\text{ 亿} \times 0.0000015 = 450\text{ 元/月}$。
    *   自建月支出：$6,166.67\text{ 元/月}$。
    结论：当前处于冷启动期，且数据无刚性合规出域限制，选择**商业云端 API**，月度成本可降低 92% 以上，且无硬件沉没风险。
