评估大模型本地部署或私有化部署方案时，很多开发者容易陷入一个误区：以为显存需求仅仅等于“模型权重文件的大小”。例如，一个 70B（700 亿参数）的模型用 4-bit 量化后文件约为 35 GB，不少人便认为两张 24 GB 显存的消费级显卡（共 48 GB）就能轻松承载。

然而一旦服务上线并接入真实并发请求，系统就会迅速因显存溢出（OOM, Out of Memory）崩溃。原因在于：大模型推理在运行时除了需要存放**静态权重**，还会产生动态增长的 **KV Cache（键值缓存）**、算子前向传播的**中间激活值**，以及系统通信与框架运行时预留开销。在高并发场景下，KV Cache 占用的显存甚至会超过量化后的模型权重本身。

![显存容量与显存带宽的双重约束看板](/images/content-rebuild/58d85b94283eb5af/cover.png)

从上面的看板可以看出，大模型硬件选型受物理容量与传输带宽双重约束。本文以主流开源模型 **Meta-Llama-3-70B** 为贯穿案例，拆解显存构成的四个部分，推导数学计算公式，并给出严谨的硬件选型决策流程。

## 推理显存的四个组成部分

在大模型推理服务引擎（例如 vLLM）中，单卡或多卡集群的可用显存主要被划分为以下四个区域：

$$M_{\text{total}} = M_{\text{weights}} + M_{\text{kv}} + M_{\text{act}} + M_{\text{runtime}}$$

这四个组成部分的生命周期和占用机制完全不同：

1. **静态模型权重显存（$M_{\text{weights}}$）**：服务启动时载入显存的神经网络参数矩阵。其大小在整个推理服务运行期间恒定不变，取决于模型参数总量与量化精度位宽。
2. **动态键值缓存显存（$M_{\text{kv}}$）**：在自回归生成过程中，为了避免每步解码重复计算前面 Token 的注意力表示，系统将历史 Token 的 Key 和 Value 向量保存在显存中（详见 [KV Cache 是什么？为什么能加速推理？](/llm-100/deployment/kv-cache.md)）。显存占用随并发请求数、上下文长度的增加而线性膨胀，是长文本和高并发场景下的显存消耗主力。
3. **运行时激活值显存（$M_{\text{act}}$）**：模型执行前向传播计算时产生的临时张量（例如注意力分数矩阵、层归一化与投影中间值）。激活值在 Prefill（输入提示词处理）阶段随序列长度增加而增大，在 Decode（逐字生成）阶段则相对较小。
4. **系统与运行时预留显存（$M_{\text{runtime}}$）**：包含 CUDA 上下文初始化开销（通常 0.5 GiB 至 1.5 GiB）、PyTorch 显存分配器碎片预留、多卡通信中间缓冲区（NCCL 环形缓冲区）以及 CUDA Graphs 预捕获所占用的显存。

![显存开销四部曲分解结构](/images/content-rebuild/58d85b94283eb5af/fig-1.png)

如图 1 所示，静态权重是基础底座，运行时预留是固定成本，而并发流量真正竞争的是 KV Cache 和动态激活值空间。若未提前规划足够的 KV Cache 显存池，突发并发请求就会耗尽显存引发 OOM 崩溃。

## 静态权重显存计算与进制换算

### 理论基线推导与进制区分

静态模型权重所需显存由模型参数总量 $P$ 和每个参数占用的存储位宽（Bit-width）$b$ 决定：

$$M_{\text{weights}} = P \times \frac{b}{8} \text{ (Bytes)}$$

在工程计算中，必须区分十进制的 **GB**（$10^9$ 字节）与二进制的 **GiB**（$1024^3 = 1,073,741,824$ 字节）。硬件厂商标称的显存容量通常采用十进制 GB，而操作系统内核与 PyTorch 分配器均按二进制 GiB 进行寻址。转换为 GiB 的理论公式为：

$$M_{\text{weights\_(GiB)}} = \frac{P \times b}{8 \times 1024^3}$$

不同量化精度对应的每个参数存储位宽及理论字节如下（量化算法细节可参考 [量化是什么？INT8、INT4、GPTQ、AWQ 有什么区别？](/llm-100/deployment/quantization-methods.md)）：
* **FP32（单精度）**：$b = 32$，每个参数占用 4 字节。
* **FP16 / BF16（半精度）**：$b = 16$，每个参数占用 2 字节。
* **INT8 / FP8（8 位精度）**：$b = 8$，每个参数占用 1 字节。
* **INT4（4 位精度，如 AWQ、GPTQ）**：$b = 4$，每个参数理论占用 0.5 字节。

### 静态显存加载冗余

在真实服务中，显存占用往往高于纯数学计算值，主要原因包括：
1. **量化元数据开销**：在 INT4 或 INT8 量化中，除了量化后的权重外，还需要存储量化分组（Group）的反量化缩放因子（Scales）与零点（Zero Points），这通常会额外增加 5% 至 10% 的显存。
2. **未量化模块保留高精度**：为了保证生成质量，部分关键层（如输入词嵌入层 `embed_tokens`、输出投影层 `lm_head` 以及 LayerNorm 层）通常在量化模型中依然保持 FP16/BF16 精度。
3. **内存对齐与填充**：底层算子为了保证访存对齐，可能会对张量尺寸做微小的补齐。

**建议预留系数**：
* **原生 FP16/BF16**：建议乘以 $1.05 \sim 1.08$ 的安全系数。
* **INT4/INT8 量化模型**：建议乘以 $1.12 \sim 1.18$ 的安全系数，以覆盖量化元数据与高精度层。

## 并发 KV Cache 显存容量模型

### 单 Token 的 KV Cache 显存推导

对于自回归 Transformer 模型，每个序列中的每个 Token 都在每一层产生对应的 Key 向量与 Value 向量并缓存下来。

设：
* $L$ 为 Transformer 模型的层数（Layers）；
* $n_{\text{kv}}$ 为 Key/Value 注意力头数（在采用分组查询注意力 GQA 的架构中，$n_{\text{kv}}$ 小于 Query 头数 $n_{\text{q}}$）；
* $d_{\text{head}}$ 为每个注意力头的维度；
* $b_{\text{kv}}$ 为 KV Cache 存储的位宽（默认 FP16 为 16-bit，使用 FP8 缓存时为 8-bit）。

单个 Token 在单个解码层内保存 Key 和 Value 所产生的元素总量为：

$$\text{Elements}_{\text{layer}} = 2 \times n_{\text{kv}} \times d_{\text{head}}$$

跨越全部 $L$ 层，单个 Token 在整个模型中累计固化的 KV Cache 物理内存字节数为：

$$S_{\text{token}} = 2 \times L \times n_{\text{kv}} \times d_{\text{head}} \times \frac{b_{\text{kv}}}{8} \text{ (Bytes)}$$

![并发 KV Cache 显存模型](/images/content-rebuild/58d85b94283eb5af/fig-3.png)

如图 3 所示，KV Cache 随着并发请求数和序列长度的增加呈立体扩展。若不加以规划，长上下文场景下的缓存开销将呈倍数递增。

### 系统并发显存计算

设推理系统需要同时支撑的最大并发请求数为 $B$，每个请求达到的最大上下文长度（输入 Prompt 长度 + 输出生成长度）为 $S$。

在传统的连续内存分配中，为了避免动态重分配发生中断，系统往往需要按照每个请求的最长上下文预留显存：

$$M_{\text{kv\_native}} = B \times S \times S_{\text{token}}$$

而在引入虚拟内存分页机制的现代引擎中（如利用分页管理物理显存块的机制，详见 [PagedAttention 解决了什么问题？](/llm-100/deployment/paged-attention.md)），显存按物理块动态分配，消除了外部内存碎片，但仍需承载峰值 Token 驻留量：

$$M_{\text{kv\_actual}} = \sum_{i=1}^{B} s_i \times S_{\text{token}} + \text{Internal\_Fragmentation}$$

其中 $s_i$ 是第 $i$ 个请求当前的实际上下文长度。内部碎片由未完全填满的物理块引起（例如块大小为 16 时，末尾块平均存在闲置），通常占用比例小于 4%，在工程测算中预留 $1.05$ 倍系数即可覆盖。

## 激活值显存与多卡并行开销

### Prefill 与 Decode 阶段的激活值差异

激活值是指算子在前向传播时生成的临时张量，显存在推理的不同阶段表现出不同特征：

1. **Prefill 阶段（首字计算）**：用户的整段输入 Prompt 一次性传入网络。若采用传统自注意力算子，中间注意力权重矩阵形状为 $[B, n_{\text{q}}, S_{\text{in}}, S_{\text{in}}]$，显存占用与输入序列长度呈平方关系。而在使用 FlashAttention 等算子融合技术后，计算过程在片上 SRAM 中分块完成，不需要将完整的中间注意力矩阵写回全局显存，激活值显存降为与序列长度线性相关。但在长 Prompt 批处理时，激活值仍会占用数 GiB 的临时显存。
2. **Decode 阶段（逐字生成）**：每次只计算一个新 Token，单步计算输入长度为 1，批次大小为并发数 $B$。此时临时张量体积较小，通常仅占用几十到几百兆字节。

在规划高吞吐服务时，激活值显存通常取决于分块 Prefill（Chunked Prefill）的单批次上限配置。一般建议单卡预留 $M_{\text{act}} = 2 \sim 4 \text{ GiB}$ 作为中间计算缓冲区。

![多卡张量并行显存分摊与通信缓冲](/images/content-rebuild/58d85b94283eb5af/fig-4.png)

### 张量并行（TP）显存分摊与通信代价

当单张 GPU 显存不足以容纳模型时，通常采用张量并行（Tensor Parallelism, TP）将模型参数横向切分到 $N$ 张 GPU 上（详见 [vLLM 为什么推理速度快？](/llm-100/deployment/vllm-inference.md)）。如图 4 所示，在 TP 集群中显存并非均匀除以 $N$：

* **模型权重**：线性层被均匀切分，每张卡承担 $M_{\text{weights}} / N$。
* **KV Cache 的整除性约束**：GQA 架构的 KV 头数 $n_{\text{kv}}$ 被平均分配给各张卡，即每卡负责 $n_{\text{kv}} / N$ 个头。**硬性工程约束：KV 头数 $n_{\text{kv}}$ 必须能被张量并行度 $N$ 整除（代码断言 `assert n_kv % N == 0`）**。分摊后每张卡的单 Token KV 缓存大小也变为 $S_{\text{token}} / N$。
* **非切分部分**：LayerNorm 层、词嵌入部分算子以及 CUDA 上下文无法被切分分摊，每张卡都需要完整驻留一份。
* **NCCL 通信缓冲区**：多卡之间进行 All-Reduce 同步必须开辟通信环形缓冲区。并行卡数越多，通信缓冲占用的显存越多，通常每张卡额外占用 $1 \sim 2 \text{ GiB}$ 专用显存。

## 典型卡型规格与选型矩阵

进行硬件选型时，不能只看标称显存容量（GB）。大模型推理受到硬件物理特性的约束：

* **Prefill 阶段是计算受限（Compute-Bound）**：GPU 的半精度浮点算力（TFLOPS）决定了首字延迟（TTFT）。
* **Decode 阶段是内存带宽受限（Memory-Bound）**：显存带宽（Bandwidth）决定了后续每个 Token 的吐字速度（TPS）。关于底层机理可参考 [大模型推理为什么慢？瓶颈在哪里？](/llm-100/deployment/inference-bottlenecks.md)。

### 单请求 Decode 阶段的吐字物理极限

在 Batch Size 为 1 的极小负载下，每生成一个 Token，模型全部权重参数就必须从 GPU 显存完整读取到计算核心一次。此时理论最高吐字速度直接受限于显存带宽：

$$\text{Max\_Tokens\_per\_Second} \le \frac{\text{Memory\_Bandwidth (GB/s)}}{M_{\text{weights}} \text{ (GB)}}$$

当并发批次增大时，读取一次权重可同时为多个请求计算输出，计算密度提升，性能瓶颈会逐步从显存带宽向算力瓶颈转移（有关并发调度机制可参考 [面试高频：大模型推理服务如何做高并发？](/llm-100/deployment/high-concurrency-serving.md)）。

## 贯穿案例测算：Llama-3-70B 的 50 并发硬件选型

以 **Meta-Llama-3-70B** 为例，完整演练生产级硬件容量的精算过程。

### 1. 模型架构参数

查阅模型配置文件可知：
* 参数总量：$P \approx 70.6 \times 10^9$
* 模型层数：$L = 80$
* 隐藏层维度：$d_{\text{model}} = 8192$
* Query 头数：$n_{\text{q}} = 64$
* Key/Value 头数：$n_{\text{kv}} = 8$（GQA 架构，8 组 KV 头复用）
* 单头维度：$d_{\text{head}} = d_{\text{model}} / n_{\text{q}} = 8192 / 64 = 128$

### 2. 业务需求目标
* 目标并发请求数：$B = 50$
* 最大上下文长度规划：$S = 4096$ Tokens（平均输入 3000 Tokens + 输出 1096 Tokens）
* KV Cache 存储精度：FP16（$b_{\text{kv}} = 16$）

### 3. 分步容量精算

#### 第一步：静态权重显存计算

* **FP16 原生精度**：
  $$M_{\text{weights}} = \frac{70.6 \times 10^9 \times 2}{1024^3} \approx 131.5 \text{ GiB}$$
  加上 8% 的工程冗余（包含 Norm 与未切分模块）：$131.5 \times 1.08 \approx 142.0 \text{ GiB}$。

* **INT4 量化精度（AWQ/GPTQ）**：
  $$M_{\text{weights}} = \frac{70.6 \times 10^9 \times 0.5}{1024^3} \approx 32.9 \text{ GiB}$$
  加上反量化 Scales 与未量化层开销（预留 15% 冗余）：$32.9 \times 1.15 \approx 37.8 \text{ GiB}$。

#### 第二步：KV Cache 显存计算

代入 Llama-3-70B 的 GQA 参数，计算单 Token 的 KV Cache 大小：
$$S_{\text{token}} = 2 \times 80 \text{ (层)} \times 8 \text{ (KV头)} \times 128 \text{ (维度)} \times 2 \text{ (Bytes)} = 327,680 \text{ Bytes} = 320 \text{ KiB}$$

单个 Token 在模型中累计占用 $0.3125 \text{ MiB}$。

在 50 并发、每请求 4096 长度的峰值负载下：
$$\text{总 Token 驻留量} = 50 \times 4096 = 204,800 \text{ Tokens}$$
$$M_{\text{kv}} = \frac{204,800 \times 327,680}{1024^3} \approx 62.5 \text{ GiB}$$

考虑分页管理的内部碎片预留（乘以 1.05）：
$$M_{\text{kv\_actual}} \approx 62.5 \times 1.05 \approx 65.6 \text{ GiB}$$

*可以看到：在 50 并发长文本场景下，仅 KV Cache 就需要 65.6 GiB 显存，这已经接近单张 80GB 卡的可用上限（74.5 GiB），并且显著超过了 INT4 量化后的模型权重本身（37.8 GiB）。*

#### 第三步：激活值与系统运行时预留
* 激活值显存预留（分块 Prefill 缓冲区）：$M_{\text{act}} \approx 4.0 \text{ GiB}$
* 运行时系统与通信缓冲区预留：$M_{\text{runtime}} \approx 2.0 \text{ GiB} \times N$（$N$ 为卡数）

![实操测算案例与集群部署拓扑](/images/content-rebuild/58d85b94283eb5af/fig-6.png)

### 4. 选型落地决策

如图 6 所示，将各部分显存汇总以确定最终硬件方案：

* **方案 A（FP16 原生精度部署，支持 50 并发 4k 窗口）**：
  $$M_{\text{total}} = 142.0 \text{ (权重)} + 65.6 \text{ (KV)} + 4.0 \text{ (激活)} + 8.0 \text{ (4卡运行时)} \approx 219.6 \text{ GiB}$$
  *决策结果*：单张或双张 80GB 卡（双卡可用显存 $2 \times 74.5 = 149.0 \text{ GiB}$）均无法容纳。**必须选用 4 张 80GB GPU（如 4 $\times$ A100-80GB 或 4 $\times$ H100-80GB，总可用显存 $4 \times 74.5 = 298.0 \text{ GiB}$）**。设置张量并行度 $\text{TP}=4$（$N=4$ 能整除 $n_{\text{kv}}=8$），每卡平均承载约 $54.9 \text{ GiB}$，显存利用率处于 $219.6 / 298.0 \approx 73.7\%$ 的安全水位。

* **方案 B（INT4 量化部署，支持 50 并发 4k 窗口）**：
  $$M_{\text{total}} = 37.8 \text{ (权重)} + 65.6 \text{ (KV)} + 4.0 \text{ (激活)} + 4.0 \text{ (2卡运行时)} \approx 111.4 \text{ GiB}$$
  *决策结果*：两张 80GB GPU（换算可用显存 $2 \times 74.5 = 149.0 \text{ GiB}$）即可完整承载。设置张量并行度 $\text{TP}=2$（$N=2$ 能整除 $n_{\text{kv}}=8$），每卡分摊显存约 $55.7 \text{ GiB}$，显存利用率处于 $111.4 / 149.0 \approx 74.8\%$ 的健康区间，硬件成本比 FP16 降低一半。

### 练习 1：多头注意力（MHA）模型的显存膨胀推导
假设有一个 14B 参数模型，采用传统的多头注意力（MHA）架构：
* 模型层数 $L = 40$
* 隐藏层维度 $d_{\text{model}} = 5120$
* Query 头数与 KV 头数相同：$n_{\text{q}} = n_{\text{kv}} = 40$
* 单头维度 $d_{\text{head}} = 128$
* 缓存精度为 FP16（2 字节）

**问题**：
1. 计算单 Token 占用的 KV Cache 字节数 $S_{\text{token}}$。
2. 若将该模型以 INT4 量化（预估静态显存约 8.5 GiB），在 32 并发、8192 上下文长度的峰值负载下，KV Cache 显存是多少？单张 24GB 显卡（可用 22.4 GiB）能否支撑？瓶颈发生了什么转移？

<details>
<summary>查看练习 1 解析与答案</summary>

1. **单 Token KV Cache 计算**：
   $$S_{\text{token}} = 2 \times 40 \text{ (层)} \times 40 \text{ (KV头)} \times 128 \text{ (维度)} \times 2 \text{ (Bytes)} = 819,200 \text{ Bytes} = 800 \text{ KiB} \approx 0.78125 \text{ MiB}$$
   *对比提示*：由于该模型采用 MHA（$n_{\text{kv}}=40$），其单 Token 产生的 KV Cache 是采用 GQA 的 70B 模型（$n_{\text{kv}}=8$ 为 320 KiB）的 2.5 倍。

2. **并发显存测算**：
   总 Token 驻留量 $= 32 \times 8192 = 262,144$ Tokens。
   $$M_{\text{kv}} = \frac{262,144 \times 819,200}{1024^3} = 200 \text{ GiB}$$
   加上 5% 分页内部碎片：$200 \times 1.05 = 210 \text{ GiB}$。

   **结论**：即使静态权重经过 INT4 量化缩小到 8.5 GiB，但 32 并发 8k 上下文产生的 KV Cache 高达 210 GiB，单张 24GB 显卡完全无法支撑。此时**显存开销的主导因素彻底从模型静态权重转移到了 KV Cache 动态缓存**，需要采用更激进的 KV Cache 量化（如 FP8/INT4 KV），或者选择多卡并行提供更大的显存池。
</details>

### 练习 2：多卡互连与并发瓶颈分析
现有两套备选硬件方案用于部署同一套量化模型并承载高并发长文本服务：
* **方案甲**：4 张 RTX 4090（标称总显存 $24 \times 4 = 96 \text{ GB}$，换算可用约 $89.6 \text{ GiB}$，PCIe 4.0 互连）
* **方案乙**：1 张 A100-SXM4-80GB（标称显存 80 GB，可用约 $74.5 \text{ GiB}$，显存带宽 2039 GB/s）

**问题**：从显存容量看，方案甲的总容量大于方案乙。但在真实高并发自回归推理中，方案甲的吐字吞吐与端到端延迟往往明显弱于方案乙。请从显存带宽与互连通道两个物理维度解释原因。

<details>
<summary>查看练习 2 解析与答案</summary>

1. **多卡张量并行（TP）互连瓶颈**：
   方案甲采用 4 张 4090 组成张量并行。在自回归生成每个 Token 的前向计算中，每层 Transformer 内部的注意力模块和 MLP 模块都需要至少一次跨卡 All-Reduce 集合通信。4090 没有硬件 NVLink 支持，通信必须经过主板的 PCIe 4.0 插槽（单向理论带宽仅 32 GB/s，实际有效传输更低）。高频跨卡同步导致计算核心长时间处于等待数据的“通信气泡”中，大幅拉高延迟并降低并行效率。而方案乙是单卡执行，完全不存在跨卡通信开销。

2. **通信开销对有效显存带宽的阻断与显存池瓶颈**：
   方案甲 4 卡张量并行时理论聚合显存带宽虽达 $4 \times 1008 = 4032 \text{ GB/s}$，且每卡仅需并行读取 $1/4$ 权重，但自回归每步生成都需要高频跨卡 All-Reduce 同步。PCIe 4.0 通信延迟高且单向带宽仅 32 GB/s，导致计算核心频繁处于等待同步的空转状态，显存控制器无法维持满负荷吞吐，实际有效显存带宽利用率极低。此外，单张 4090 可用显存仅 22.4 GiB，扣除切分权重与运行时后单卡 KV Cache 空间不足 10 GiB，极大压制了并发批次上限；而 A100 单卡具备 2039 GB/s 的纯净本地 HBM 带宽与充足连续显存池，无需跨卡通信阻断，在高并发扩展下能够维持极高的有效带宽利用率与吐字吞吐。
</details>
