在上一讲[PagedAttention 解决了什么问题？](paged-attention.md)中，我们了解了 vLLM 如何通过类似操作系统的分页内存管理，解决大模型自回归生成时 KV 缓存（KV Cache）的显存碎片问题。

然而，光有高效的显存数据结构还不够。大语言模型推理通常分为两个阶段：
1. **预填充（Prefill）阶段**：处理用户输入的提示词（Prompt），计算所有输入 Token 的注意力与前向传播。在常规输入长度与批次下，多 Token 的矩阵乘法更容易并行打满 GPU 计算核心，通常偏向**计算受限**（Compute-bound，但极短 Prompt 时也受算子发射与访存影响）。
2. **解码（Decode）阶段**：每一步自回归生成 1 个新 Token，需要读取之前所有 Token 的历史 KV 缓存。在常见中小批量下，每步针对单 Token 计算强度较低，主要受限于从显存搬运庞大历史 KV 缓存的速度，通常偏向**显存带宽受限**（Memory-bandwidth-bound；只有当并发批次极大时，累积计算量才可能使系统转向计算受限）。

如果调度策略不当，GPU 要么在等待输入，要么在 Decode 时算力闲置。本讲的学习目标是：理解 vLLM 如何通过持续批处理（Continuous Batching）、显存耗尽抢占、分块预填充（Chunked Prefill）、自动前缀缓存（APC）与 CUDA Graph，在保证低延迟的同时提升吞吐量，并能推演调度器在不同并发状态下的动作。

### 静态批处理的缺陷：长尾等待与执行气泡

在传统的深度学习模型推理（如图像分类或 BERT 文本分类）中，输入和输出的张量大小固定，通常采用**静态批处理（Static Batching）**：调度器攒齐 $N$ 个请求组成一个 Batch，执行一次前向传播，全部算完后统一返回。

但在大语言模型的生成任务中，每个请求的 Prompt 长度不同，模型输出的生成长度也各不相同，直到模型输出终止标记（如 `<|endoftext|>`）或达到长度上限才会停止。

![静态批处理的长尾气泡与持续批处理迭代级调度的对比图，展示静态批处理的长尾气泡与持续批处理迭代插入的无缝衔接](/images/content-rebuild/17d89d9f6dfbf8d6/fig-1.png)

设想一个静态批处理包含 3 个并发请求：
* 请求 A：生成 20 个 Token 即结束；
* 请求 B：生成 100 个 Token 结束；
* 请求 C：生成 512 个 Token 结束。

在静态批处理逻辑下，整个批次的前向步数必须对齐到最长的请求 C（512 步）。请求 A 在第 20 步就已经完成了，但在接下来的 492 步中，它对应的槽位必须填充无意义的 Padding Token 继续参与前向计算；请求 B 也是如此。这种由于等待长请求而产生的算力浪费，被称为**执行气泡（Execution Bubble）**。

### 持续批处理：单步迭代级调度

为了消除气泡，vLLM 采用了迭代级调度（Iteration-level Scheduling），通常称为**持续批处理（Continuous Batching）**。其核心是将调度的粒度从“请求生命周期”缩小到“单步 Token 生成（Iteration）”。

调度器不再维护固定的批次容器，而是维护几个队列构成的状态流转：

```
[新请求进入] --> WAITING 队列
                     |
             (显存块充裕，分配块)
                     v
                 RUNNING 队列 <=====> (显存不足) SWAPPED / PREEMPTED
                     |
               (输出终止标记)
                     v
                  FINISHED (释放显存块，返回响应)
```

在每次模型前向传播开始前，调度器都会重新组织当前迭代的执行批次：
1. **动态移出**：在第 $t$ 步中，只要有请求输出了终止标记或达到长度上限，该请求立即标记为完成，退出 `RUNNING` 队列，释放它占用的 PagedAttention 显存物理块，并通过流式接口返回。
2. **动态插入**：只要当前 GPU 还有空闲物理块，调度器就可以在第 $t+1$ 步从 `WAITING` 队列中拉取新请求的 Prompt 加入批次，直接开始计算。

调度周期被缩短到几十毫秒以内的单步迭代，短请求完成后立刻让出槽位，新请求立刻填充进来，消除了静态批处理中的等待气泡。

### 显存耗尽时的调度抢占策略

自回归生成中，每个请求最终要生成多少个 Token 事先无法确知。当请求处于 `RUNNING` 状态并不断吐字时，每生成一个块大小（例如 16 个 Token），就必须申请一个新的物理块。

在突发的高并发下，GPU 的空闲物理块可能在某一解码步彻底耗尽。为了避免程序崩溃（OOM），调度器必须主动干预。vLLM 默认按照先来先服务（FCFS）的逆序，即优先抢占最晚到达的请求，强制收回其持有的物理块，将资源让给更早到达的请求。

![显存耗尽时的调度抢占与处理路径图，对比重计算与 CPU 换出的流向与开销权衡](/images/content-rebuild/17d89d9f6dfbf8d6/fig-3.png)

对被抢占的请求，系统有两种恢复路径：

1. **重计算（Recomputation / Drop）**：
   * **机制**：直接释放该请求持有的所有 GPU 显存块，将请求放回 `WAITING` 队列头部。待显存空闲时，把该请求原始的 Prompt 与之前已经生成的内容拼在一起，重新执行一次 Prefill 恢复 KV 状态，随后继续解码。
   * **权衡**：以 GPU 运算时间换取显存空间。对于生成长度较短的请求，重新执行 Prefill 的矩阵计算速度很快（几毫秒到几十毫秒），代价很低。

2. **换出（Swap to CPU）**：
   * **机制**：抢占发生时，通过 PCIe 总线将该请求在 GPU 显存中的 KV 缓存复制到主机内存（CPU RAM）中，释放 GPU 块。待显存空闲后，再从 CPU 内存换入 GPU 恢复解码。
   * **权衡**：以 PCIe 传输带宽换取 GPU 算力。当请求已经生成了数千个 Token 时，重新做一次超长 Prefill 的注意力计算开销很大，此时利用空闲的 PCIe DMA 将缓存移到 CPU 内存可以避免重复计算。

在纯线上 API 服务中，由于长文本换出容易引起多卡 PCIe 带宽竞争，状态机也更复杂，大多数追求高吞吐的集群通常将重计算作为默认抢占方案。

### 分块 Prefill：消除长 Prompt 的队头阻塞

在基础持续批处理中，Prefill 和 Decode 在常见运行负载下的特点存在冲突：
* Prefill 通常一次性处理大批 Token，在输入充足时更容易并行占满计算核心；
* Decode 在常见中小并发下每步只处理 1 个 Token，计算强度较低，主要依赖显存带宽读取历史缓存。

如果不做特殊处理，当一个长达 8k Token 的长请求进入系统时，调度器若一次性执行完整的 Prefill，会独占整张 GPU 数百毫秒。这会导致两个问题：
1. 正在进行 Decode 的其他请求被卡住数拍，逐字吐字间隔（ITL, Inter-token Latency）发生剧烈抖动；
2. 排在后面的短请求无法开始，首字延迟（TTFT, Time To First Token）大幅增加，形成队头阻塞。

为了解决这个问题，vLLM 引入了**分块预填充（Chunked Prefill）**机制：

![分块 Prefill 与多请求 Decode 混合打包单步执行的时序示意图](/images/content-rebuild/17d89d9f6dfbf8d6/fig-4.png)

1. **设定单步 Token 预算**：调度器设定每个前向步允许处理的最大 Token 总数 $T_{\text{budget}}$（例如 512）。
2. **拆分长提示词**：若新到的 Prompt 有 2048 个 Token，调度器将其切成 4 个大小为 512 的块。第 1 步先计算前 512 个 Token 的 KV 缓存并保存；后续步中逐步计算剩余块。
3. **混合打包执行**：在同一个迭代批次中，调度器把一个 Prefill 块（如 480 个 Token）与若干个正在 Decode 的请求（如 32 个请求各 1 个 Token）打包进同一个批次，总 Token 数为 $480 + 32 = 512$。

这种混合打包让 Decode 的访存操作和 Prefill 的矩阵乘法同时进行，既打满闲置的浮点运算单元，又避免了长 Prompt 对硬件的长时间独占。

### 自动前缀缓存：跨请求复用公共 Prompt

许多业务场景中，不同请求的前半部分高度重合：
* Agent 每次调用都会携带相同的 System Prompt 和工具定义；
* RAG 应用围绕同一篇背景资料进行多轮提问；
* 多轮对话中包含完全相同的历史上下文。

如果每个请求都从头计算这部分前缀，会造成大量的重复计算和显存占用。vLLM 提供了**自动前缀缓存（Automatic Prefix Caching, APC）**。

![自动前缀缓存原理图，展示基于 Token 块哈希链表的前缀树与跨请求零拷贝共享](/images/content-rebuild/17d89d9f6dfbf8d6/fig-5.png)

#### 链式哈希与块复用逻辑

APC 依赖 PagedAttention 的定长块（例如 16 个 Token 为一个 Block）：
1. **哈希链计算**：第 $i$ 个物理块的哈希值由前一个块的哈希值与当前块内的 16 个 Token 共同计算：
   $$\text{Hash}_i = \text{Hash}(\text{Hash}_{i-1}, \text{Token}_{(i \times 16) \dots (i \times 16 + 15)})$$
   引入前驱哈希后，即使两段文本包含相同的 16 个 Token，只要在上下文中的位置或前置文字不同，哈希值也不同，确保了因果注意力的严格正确。
2. **匹配与共享**：新请求到达时，调度器先计算其各个 Token 块的哈希值。若哈希表命中已存在的块，该物理块的引用计数（Ref Count）加 1，新请求的虚拟块直接指向该物理块，**跳过该块的 Prefill 计算**。
3. **LRU 淘汰**：当请求完成时，对应块的引用计数减 1。引用计数降为 0 的块不会立即抹除，而是留在 LRU 淘汰队列中。后续请求若再次命中可直接复用；只有显存不足需要开辟新块时，这些冷数据才会被覆盖。

### CUDA Graph 协同：消除 Decode 小算子发射开销

即便上层调度做好了分块与批次拼装，底层硬件执行仍有一道阻碍：**CPU 发射开销（Kernel Launch Overhead）**。

在 Decode 阶段，每个请求每步只产生 1 个 Token。在数十层的 Transformer 中，每一层都有 RMSNorm、RoPE、PagedAttention、SwiGLU 激活等小算子。每个算子在 GPU 上的执行时间可能只有几微秒，但 CPU 通过驱动发射一个 Kernel 到 GPU 的开销也需要数微秒。当批次较小时，GPU 常常在几微秒内执行完毕，随后处于空闲状态等待 CPU 发射下一个算子。

![CPU 算子发射开销与 CUDA Graph 预捕获批量重放的时序流水线对比图](/images/content-rebuild/17d89d9f6dfbf8d6/fig-6.png)

#### CUDA Graph 分桶机制与适用条件

CUDA Graph 技术允许把一整串连续执行的 Kernel 调用、显存指针和依赖关系打包固化为一张静态图。执行时，CPU 只需要向 GPU 发送一次启动指令，GPU 内部即可连续流水线执行整张图，消除了中间的驱动发射间隔。

但 CUDA Graph 要求图内张量的显存地址和形状（Shape）保持不变。因此它主要适用于：
* **纯 Decode 迭代**：每个序列固定只输入 1 个 Token，张量形状由 Batch Size 决定。
* **分桶预捕获（Batch Bucketing）**：vLLM 在服务启动阶段，预先对一组离散的 Batch 大小（如 1, 2, 4, 8, 16, 32 等）捕获好对应的 CUDA Graph。运行时若有 13 个纯 Decode 请求，调度器向上对齐至 16，空余槽位补齐虚拟 Padding，然后直接重放 16 维度的执行图。
* **Prefill 动态降级**：当批次中包含 Prefill 或 Chunked Prefill 时，由于序列长度不固定，无法直接应用固定的 CUDA Graph，引擎会自动降级为常规的 Eager 模式（逐个发射算子）或使用分段图执行。

### 调度全流程算例推演

我们以一个具体场景跟踪一步调度的完整决策过程：

* **系统配置**：Block Size = 16 Token；最大单步 Token 预算 $T_{\text{budget}} = 64$。
* **当前状态**：
  * `RUNNING` 队列：请求 A（Decode 阶段，消耗 1 Token 预算）、请求 B（Decode 阶段，消耗 1 Token 预算）。合计占用预算 2。
  * `WAITING` 队列：请求 C，输入长度共 80 个 Token，其中前 32 个 Token 恰好命中全局 APC 缓存（对应已有的 2 个物理块）。

**调度器决策过程**：
1. **扣除缓存**：请求 C 命中 32 Token 缓存，这部分不需要做 Prefill，剩余待计算 Token 长度为 $80 - 32 = 48$。
2. **检查预算**：当前剩余预算为 $64 - 2 = 62$。由于 $48 \le 62$，调度器决定在本步接纳请求 C 的全部未计算部分，不需要再次切分分块。
3. **组装批次**：本步总计输入 Token 为 $1 + 1 + 48 = 50$。其中包含 Decode 请求（A、B）与 Prefill 请求（C）。
4. **后端选择**：由于批次中混有 48 Token 的 Prefill 输入，张量维度非固定，系统绕过纯 Decode 的 CUDA Graph，通过常规模式执行本次前向传播。
5. **步末结算**：若请求 B 在本步生成终止标记，释放其物理块退出；请求 C 完成 Prefill，进入下一步的 `RUNNING` 队列参与后续的 Decode。

### 可检验练习

请根据本讲介绍的调度规则，独立完成以下推演：

**场景假设**：
* 调度器单步 Token 预算 $T_{\text{budget}} = 128$，物理显存 Block 大小为 16 Token。
* 当前 `RUNNING` 队列有 6 个正在进行自回归生成的请求（纯 Decode）。
* 当前 `WAITING` 队列首位为请求 X，总输入长度为 300 Token，其中前 64 Token 命中了 APC 缓存。

**问题**：
1. 本次迭代中，调度器最多能为请求 X 分配多少个 Prefill Token？
2. 请求 X 在本步之后是否能完成全部 Prefill？若不能，还剩多少 Token 待计算？
3. 本次迭代组装完毕后，后端执行引擎能否直接使用纯 Decode 的 CUDA Graph？为什么？

**推导与解答**：
1. `RUNNING` 队列中的 6 个 Decode 请求每步各消耗 1 个 Token，共占用 $6 \times 1 = 6$ Token 预算。因此本步剩余给 Prefill 的预算为 $128 - 6 = 122$ Token。请求 X 命中 64 Token 缓存后，剩余待 Prefill 长度为 $300 - 64 = 236$ Token。由于 $236 > 122$，调度器触发分块 Prefill，本步最多只能计算 122 个 Token。
2. 本步计算 122 个 Token 后，请求 X 剩余待计算 Token 为 $236 - 122 = 114$ 个，因此尚未完成全部 Prefill，下一拍仍需继续作为分块排队计算。
3. 不能。因为该迭代的批次中混入了 122 个 Prefill Token，存在非固定形状的动态矩阵输入，不满足纯 Decode 静态张量维度的条件，调度器会降级执行而非直接使用纯 Decode 的 CUDA Graph。

### 部署配置建议与注意事项

在生产环境中部署 vLLM 时，调度参数需要根据实际负载权衡：

| 业务场景 | 核心参数配置 | 说明与权衡 |
| :--- | :--- | :--- |
| **长文本 / 知识库 RAG** | `--enable-chunked-prefill=True`<br>`--max-num-batched-tokens=512` | 拆分长 Prompt，平抑逐字生成时延（ITL）抖动，消除队头阻塞。 |
| **固定模板 Agent 集群** | `--enable-prefix-caching=True` | 对重复使用的 System Prompt 与工具 Schema 实现零拷贝复用，降低首字延迟。 |
| **高并发短文本问答** | `--gpu-memory-utilization=0.90`<br>`--swap-space=4` (GB) | 留出部分显存用于 CUDA Graph 捕获和临时激活；配置少量 CPU Swap 作为突发显存高峰的缓冲。 |

**部署排查要点**：
* **显存利用率（gpu-memory-utilization）切忌设为 1.0**：vLLM 启动时会预先划拨指定比例的显存作为 KV 块池。若设为 0.98 或更高，留给 CUDA Graph 捕获、模型临时激活值（Activation）的显存过少，极易引发不可恢复的 CUDA OOM 崩溃。通常建议设置在 0.85 到 0.92 之间。
* **超短 Prompt 场景分块预算不宜过大**：若业务请求的 Prompt 普遍在几十个 Token 内，过大的 `max-num-batched-tokens` 会让单个批次过度偏向长张量，增加组装调度开销，应结合压测进行微调。

在掌握了内存分页、迭代级调度、分块预填充与前缀缓存的协同运作后，单机的推理吞吐潜力已基本释放。接下来在[量化是什么？INT8、INT4、GPTQ、AWQ 有什么区别？](quantization-methods.md)中，我们将进一步学习如何通过权重与 KV 缓存量化压缩，在同等显存条件下容纳更大的批次与模型。
