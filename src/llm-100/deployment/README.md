大模型训练的目标是更新权重让损失函数收敛，而部署与推理的目标则是在硬件显存和算力受限的前提下，以尽可能低的延迟和计算成本，承接尽可能高的并发访问。与传统的 Web 服务或卷积神经网络推理相比，自回归大语言模型在生成文本时具有独特的两阶段执行特征，这使得显存分配和计算调度变得格外复杂。

![部署与推理优化模块全景导读封面](/images/content-rebuild/eebbb3a7822db5d2/cover.png)

本模块将带你建立从底层硬件性能瓶颈到上层分布式推理集群的完整工程认知。

## 一、贯穿场景：一张显卡如何承接高并发

为了理解为什么大模型推理需要一系列专门的优化技术，我们来看一个具体的工程场景：

假设我们有一张 24GB 显存的 GPU，计划部署一个 7B（70 亿参数）的开源对话模型。在未做量化、以 16 位半精度浮点（FP16/BF16）加载时，每个参数占用 2 字节，模型本身的静态权重就需要占用约：

$$7\times 10^9 \times 2 \text{ 字节} \approx 14 \text{ GB}$$

显卡还剩下约 10GB 显存。当多个用户同时发起请求时，系统会经历两个计算特征完全不同的阶段：

1. **首字计算阶段（Prefill）**：模型需要一次性读取用户输入的提示词（假设为 2048 个 Token），并行计算所有输入位置的注意力与前馈网络。此时 GPU 的矩阵乘法计算单元（如 Tensor Core）处于高负荷运转状态，系统瓶颈主要在于**浮点计算能力（Compute-bound）**。
2. **逐字生成阶段（Decode）**：模型每生成一个新词，都要依赖之前所有已生成的词。如果每次生成新词都把前面 2000 多个词重新计算一遍，算力开销将随长度呈二次方暴增。因此工程上必须把历史 Token 的 Key 和 Value 向量暂存在显存中（即 **KV Cache**）。但在生成阶段，若处于单请求或中小批大小并发下，每次前向传播只为每个序列处理 1 个新增 Token，矩阵计算量相对访存量极小，GPU 却必须把整份 14GB 的模型权重以及不断变长的 KV Cache 从显存重新搬运到计算芯片一次。此时计算单元大部分时间在等待数据传输，系统瓶颈主要在于**显存带宽（Memory-bound）**。

当并发请求数增加时，每个请求的 KV Cache 随生成长度动态膨胀。如果像传统系统那样预先为每个请求分配最大可能长度（如 4096）的连续显存，显卡在承接 3 到 4 个并发请求时就会耗尽显存发生溢出（Out of Memory, OOM）。

围绕“如何减少显存搬运”、“如何消除显存碎片”、“如何压榨计算核心利用率”这三个核心物理制约，大模型推理衍生出了完整的工程优化技术栈。

## 二、推理优化的协同体系

大模型推理优化并非单点算法，而是硬件特性、计算算子、运行时引擎与系统网关相互配合的结果。

![大模型推理技术栈四层架构图](/images/content-rebuild/eebbb3a7822db5d2/fig-1.png)

在实际工程实现中，这四个组成部分各司其职又紧密配合：

* **硬件物理层**：提供算力基石。决定性能的关键参数不仅是显存容量（决定能装下多大的模型和并发 Cache），还有显存带宽（HBM/GDDR 带宽决定逐字生成阶段的读写上限）以及卡间通信总线（NVLink/PCIe 决定多卡张量并行时的同步延迟）。
* **底层算子层**：负责具体矩阵运算的极速执行。例如 FlashAttention 通过分块计算把注意力运算限制在 GPU 片上高速缓存（SRAM）中，减少高延迟的显存全局读写；针对低精度量化（INT8、INT4、FP8）的专用 GEMM 算子则在减少访存量的同时加速矩阵乘法。
* **推理引擎层**：整个推理系统的调度中枢（以 vLLM、TensorRT-LLM 为代表）。它向下管理显存虚拟分页（PagedAttention），消除内存碎片；向上实现动态批处理（Continuous Batching）与 Chunked Prefill，在时间线上灵活交织处理不同用户的长短请求。
* **服务网关层**：负责生产环境的工程化封装。处理流式传输协议（SSE）、OpenAI 兼容接口转换、请求级排队优先级管理、多实例负载均衡与健康检查。

## 三、优化技术的递进脉络

本模块的十讲内容按照技术演进的依赖关系组织，解决从单请求延迟到大规模集群吞吐的连续问题：

![推理技术递进因果链条](/images/content-rebuild/eebbb3a7822db5d2/fig-2.png)

1. **定位瓶颈**：通过 Roofline 性能模型量化 Prefill（计算瓶颈）与 Decode（显存带宽瓶颈）的物理特征，明确后续优化的切入方向（详见 [01 篇：拆解 Prefill 与 Decode 瓶颈](/llm-100/deployment/inference-bottlenecks.md)）。
2. **状态缓存**：引入 KV Cache 消除逐字生成时的历史重复计算，推导显存随批大小与序列长度增长的定量公式（详见 [02 篇：KV Cache 原理与显存占用分析](/llm-100/deployment/kv-cache.md)）。
3. **显存分页**：针对动态长度造成的严重内部与外部显存碎片，借鉴操作系统虚拟内存思想，引入逻辑块与物理块解耦的动态管理机制（详见 [03 篇：PagedAttention 显存分页机制](/llm-100/deployment/paged-attention.md)）。
4. **调度革新**：基于显存细粒度分配能力，抛弃传统静态批处理等待机制，在 Token 生成步之间实现动态插入新请求与退出结束请求（详见 [04 篇：vLLM 持续批处理与调度](/llm-100/deployment/vllm-inference.md)）。
5. **参数压缩**：通过量化技术（AWQ、GPTQ、FP8 等）压缩模型权重与 KV Cache，成倍降低显存占用与访存带宽需求，使消费级硬件或单卡承载更大模型成为可能（详见 [05 篇：模型量化方法对比](/llm-100/deployment/quantization-methods.md)）。
6. **容量规划**：建立严格的显存与吞吐估算模型，结合张量并行（TP）与流水线并行（PP）完成硬件选型测算（详见 [06 篇：推理硬件配置与显存测算](/llm-100/deployment/hardware-estimation.md)）。
7. **单机实践**：对比 Ollama、vLLM、llama.cpp、LM Studio 等工具在本地单机与轻量生产下的设计取舍与配置（详见 [07 篇：本地推理工具对比与选型](/llm-100/deployment/local-serving-tools.md)）。
8. **并发服务化**：架构多副本实例集群，配合反向代理、动态队列排队与分块预填充，保障服务高可用与低抖动（详见 [08 篇：高并发推理服务架构](/llm-100/deployment/high-concurrency-serving.md)）。
9. **成本决策**：建立公有云商业 API 与私有化自建集群的总体拥有成本（TCO）核算模型，推导盈亏平衡点（详见 [09 篇：自建推理与云端 API 决策权衡](/llm-100/deployment/api-vs-self-hosting.md)）。
10. **系统级控本**：综合运用前缀缓存（Prefix Caching）、模型级联路由与输入压缩技术，进一步压降调用成本（详见 [10 篇：大模型推理成本综合优化](/llm-100/deployment/llm-cost-optimization.md)）。

## 六、可检验练习与验收标准

在阅读完本导读并进入后续篇目学习前，请通过以下两个基础推演检验对概念的理解：

### 练习 1：显存类型区分与估算推演
**问题**：某同学说：“一个 14B 参数的模型用 FP16 加载占用 28GB 显存，我们租一张 32GB 显存的显卡，刚好能跑起来并且支持任意长文本对话。”请指出这句话中的漏洞，并列出推理时显存消耗的组成部分。

> **检验标准与分析**：
> 1. 推理阶段的显存不仅仅包含**模型权重显存**（14B $\times$ 2 字节 $\approx$ 28GB）。
> 2. 还必须包含随并发数和序列长度动态增加的 **KV Cache 显存**，以及少量前向传播所需的**激活值显存（Activation）**与框架运行开销。
> 3. 32GB 显卡减去 28GB 权重后仅剩约 4GB 显存。一旦输入较长（例如 4096 Token）或存在多个并发请求，4GB 显存会在瞬间被 KV Cache 填满并触发 OOM，因此绝不可能“支持任意长文本对话”。必须考虑降低精度（如 4 位量化）或者使用更大显存的显卡。

### 练习 2：首字延迟（TTFT）与每字延迟（TPOT）归因
**问题**：用户反馈在线问答服务出现性能异常，现象为：“发送请求后，界面转圈等待 4 秒才开始吐出第一个字；但一旦开始吐字，后续字符以每秒 50 字的高速流畅输出。”请分析问题最可能出现在哪个推理阶段？应从哪些技术方向进行排查？

> **检验标准与分析**：
> 1. 首字等待时间被称为 **TTFT（Time to First Token）**，对应推理的 **Prefill 阶段**；后续逐字生成耗时通常以 **TPOT（Time Per Output Token）** 衡量（对应生成速率的倒数，例如每秒 50 字对应 TPOT 约为 20 毫秒/Token），对应 **Decode 阶段**。
> 2. 现象表明 Decode 阶段吞吐正常（显存带宽与单步推理未受阻），而 Prefill 阶段消耗了整整 4 秒。
> 3. 排查方向包括：用户输入文本过长导致矩阵计算量大、当前请求在队列中等待前面批次调度耗时过长（排队延迟）、或者未命中前缀缓存（Prefix Cache）导致长系统提示词重复计算。可通过引入分块预填充（Chunked Prefill）或开启系统提示词缓存来优化首字响应。
