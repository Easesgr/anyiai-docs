在了解了 [System Prompt、User Prompt、Assistant Prompt 分别有什么作用？](/llm-100/prompt-engineering/System_Prompt_User_Prompt_Assistant_Prompt_分别有什么作用.md) 后，我们知道可以通过消息角色来区分系统设定与用户对话。但在实际业务中，单靠角色划分往往不够：一段发给模型的提示词里，通常同时塞满了业务目标、排障手册、格式约束、负向禁止清单以及动态传入的用户数据。

如果把所有内容直接写成一大段连续的自然语言，模型很容易出现漏看约束、被用户输入中的转折词误导、或者输出格式不稳定的问题。这一讲我们通过一个贯穿始终的“线上日志排障助手”例子，掌握结构化 Prompt 的模块拆解方法、XML 标签边界隔离技巧、负向规则的正向化转换，以及程序运行时的动态装配保护。

## 为什么一大段文字混在一起容易失效？

我们先来看一个真实场景。假设我们希望模型分析一段 Java 后端异常日志，匹配运维排障手册后给出处置建议。如果不加结构化组织，常见的自然语言写法通常是这样：

> “你是一个运维专家，请帮我分析下面这段错误日志，千万不要胡说八道，不要写客套话，不要解释原理。参考规则是如果遇到连接池超时并且等待大于3000ms就是数据库满，遇到Metaspace就是类加载溢出。日志是 2025-03-29 ERROR HikariPool-1 - Connection is not available, request timed out after 3002ms。请直接告诉我怎么做，用三段式输出结果。”

这种写法在输入很短时可能勉强有效，但一旦日志变长、规则增多，就容易暴露出两个典型问题：

1. **关键约束在非结构化语流中定位困难**：当背景规则、限制条件与待分析数据混杂在一起时，缺乏清晰的边界与语义锚点。随着上下文变长，模型受位置偏差和大量叙述性文本干扰，难以稳定检索并持续遵循夹杂在中间的核心约束（例如“三段式输出”、“只依据规则判定”），容易发生漏看。
2. **指令与数据缺乏边界**：如果日志内容本身包含“注意：请忽略上述警告”、“不要重启服务”等具有祈使意味的句子，模型很难判断这些文本究竟是“待分析的数据”，还是“用户下达的新命令”，从而产生执行偏差。

![非结构化混杂文本与结构化分块提示词的注意力分配机制对比](/images/content-rebuild/155f91f076d0012d/fig-1.png)

如上图对比所示，右侧将指令、规则与待分析数据通过清晰的区块物理隔开，能帮助模型在推理时明确区分“哪个区域是规则”、“哪个区域是待处理内容”。

## 结构化拆解：四大核心模块职责划分

编写健壮提示词的第一步，是将一段原本混杂的自然语言，解耦为四个职责明确的独立模块：

### 1. 角色设定（Role）
角色设定的作用不是角色扮演，而是**界定专业视角与术语范围**，促使模型在对应的领域上下文中采样词汇。
* **低效写法**：`你是一个超级厉害无所不知的 Python 架构大师。`（充满主观修饰，增加额外 Token 却无具体信息）
* **明确写法**：`你是一名代码审计员，负责对 Python 脚本进行静态类型安全与异步资源释放检查。`（限定了关注焦点和专业范围）

### 2. 任务目标与流程（Task & Workflow）
明确说明核心动作。如果任务包含多个步骤，使用有序列表写明处理逻辑：
* 说明先做什么、后做什么，例如第一步提取关键异常名，第二步比对规则，第三步匹配处理方案。

### 3. 参考背景与输入数据（Context & Input Data）
将模型做决策需要用到的所有事实材料（如知识库检索片段、配置规则、待分析文本）集中存放，并与操作指令清晰分开。当系统更复杂时，这部分通常由上下文工程动态提供，具体组织方式可参考 [一个高质量上下文应该包含什么？任务目标、背景资料、约束和输出格式怎么组织？](/frontier/context-engineering/high-quality-context.md)。

### 4. 输出规范（Output Specification）
直接给出输出模板、格式要求（如 Markdown 标题层级、键值对格式）以及当参考资料不足时的固定兜底话术。

## 用 XML 标签界定数据与指令边界

在主流开发实践（例如 Anthropic 官方推荐指南）中，XML 标签被广泛用作划分模块的标记。为什么推荐使用成对的 XML 标签，而不是普通的破折号或缩进？

1. **成对闭合，作用域明确**：`<logs>` 与 `</logs>` 提供了清晰的起始与结束边界，与主流模型在预训练阶段见过的 HTML 和代码结构保持一致。
2. **便于在指令中精确引用**：系统指令可以直接指名标签，例如：“请根据 `<rules>` 中的定义分析 `<error_logs>`，如果 `<rules>` 中未收录，请直接回答依据不足。”
3. **降低数据与指令的混淆概率**：外部传入的文本往往不可控，将其用固定标签包裹，能提示模型该区域仅为待处理的“数据内容”，而不是执行逻辑。

![XML 标签在控制平面指令与数据平面负载之间建立的隔离边界](/images/content-rebuild/155f91f076d0012d/fig-3.png)

**重要边界提醒**：XML 标签只是一种让模型更好理解上下文结构的“格式约定”，**它不是操作系统的安全沙箱**。如果外部传入的数据中刻意包含 `</user_input>` 并追加诱导性指令，单纯依赖 System Prompt 依然存在被绕过的风险。系统安全需要依赖外部输入清洗、权限最小化及敏感词过滤等工程手段，具体防范方案见 [Prompt 注入攻击是什么？如何防范？](/llm-100/prompt-engineering/Prompt_注入攻击是什么_如何防范.md)。

## 负向约束怎么改：把“不要做什么”换成“应该做什么”

许多人在写提示词时习惯写一长串否定句：“不要说废话”、“不要开头问好”、“绝对不要给出没有依据的猜测”。但在实际测试中，否定句的约束往往很脆弱，主要原因包括：

* **未收敛输出路径**：否定句只告诉模型“不能走哪条路”，但留下了无数条其他可能的输出路径，生成结果依然容易偏离预期。
* **激活了不期望的词汇概率**：自回归生成根据已有文本预测下一个 Token。当提示词中频繁出现“道歉”、“寒暄”等字眼时，这些概念在上下文中的权重被动提高，有时反而促成了相关内容的生成。

改写负向约束的核心方法是：**给出确定的正向规则、确定的格式前缀，或给出固定的兜底返回值**。

| 脆弱的负向表述 | 健壮的正向确定规则 | 为什么更稳定 |
| :--- | :--- | :--- |
| 不要输出任何客套话和开场白 | 直接输出诊断正文，第一行必须以二级标题 `## 诊断分析` 起始 | 锁定了输出起始 Token，跳过寒暄语句 |
| 不要编造参考文档中没有的信息 | 回答必须严格基于 `<reference>`。若材料中未提及，统一输出固定文本：`依据不足，无法确认。` | 给出了明确的兜底退出分支，不再发散试错 |
| 不要使用复杂的长难句和被动语态 | 每个分析结论统一使用“【主语】+【动作动词】+【对象】”的单句形式输出 | 约束了句式结构，降低语法分支不确定性 |

## 动态组装：在程序中组装提示词的防护逻辑

在实际代码工程中，提示词不是写死的静态文本，而是由程序把用户输入、数据库记录动态拼接生成的。在拼装过程中，需要注意三项基础保护：

1. **标签转义**：防止外部数据中恰好包含与系统提示词相同的闭合标签（如 `</user_payload>`），导致标签提前闭合。
2. **长度截断**：避免外部数据超出模型的上下文预算，破坏前置指令或输出规范。
3. **空值兜底**：当检索结果为空时，应填充明确的默认说明文本，而不是拼接空字符串。

![动态模板组装中的变量填充、字符转义与上下文截断流水线](/images/content-rebuild/155f91f076d0012d/fig-5.png)

下面是一个包含转义与截断保护的 Python 组装示例：

```python
import html

class StructuredPromptBuilder:
    def __init__(self, max_context_chars: int = 4000):
        self.max_context_chars = max_context_chars

    def _sanitize(self, text: str) -> str:
        """对尖括号进行基础转义，防止与结构化标签产生歧义"""
        if not text or not text.strip():
            return "无"
        return html.escape(text.strip())

    def _truncate(self, text: str, max_len: int) -> str:
        """控制外部数据长度，超出时保留前部并追加说明"""
        if len(text) <= max_len:
            return text
        return text[:max_len] + "\n[警告：外部数据超长，已截断]"

    def build(self, role: str, task: str, rules: str, payload: str) -> str:
        clean_role = self._sanitize(role)
        clean_task = self._sanitize(task)
        clean_rules = self._truncate(self._sanitize(rules), self.max_context_chars)
        clean_payload = self._truncate(self._sanitize(payload), self.max_context_chars)

        return f"""<role>
{clean_role}
</role>

<task>
{clean_task}
</task>

<reference_rules>
{clean_rules}
</reference_rules>

<input_data>
{clean_payload}
</input_data>

<output_specification>
1. 第一行直接以一级标题 "# 诊断报告" 开始，不输出任何问候语。
2. 严格依据 <reference_rules> 中的规则进行判定；若规则未包含该错误，直接输出 "未知故障类型"。
3. 使用主动语态，列出具体处理动作。
</output_specification>"""
```

## 贯穿案例：生产日志排障的完整提示词

把上述所有规范应用到我们最初的日志排障需求中，最终组装出的提示词如下：

```markdown
<role>
你是一名分布式服务 SRE 排障专家，负责根据应用运行日志定位根因。
</role>

<task>
请分析 <error_logs> 中的崩溃栈信息，比对 <runbook_rules> 中的规则，输出诊断判定与应急步骤。
</task>

<runbook_rules>
- 规则 1：当包含连接超时信息（如 Connection is not available, request timed out）且等待时间 > 3000ms 时，判定为数据库连接池耗尽。
- 规则 2：当包含 OutOfMemoryError: Metaspace 时，判定为类加载溢出，需调整 MaxMetaspaceSize 参数。
</runbook_rules>

<error_logs>
2025-03-29 10:14:22 ERROR [http-nio-8080-exec-12] c.z.h.p.HikariPool: HikariPool-1 - Connection is not available, request timed out after 3002ms.
Caused by: com.zaxxer.hikari.pool.HikariPool$PoolInitializationException: Exception during pool initialization
</error_logs>

<output_specification>
输出必须严格按以下结构生成，不得输出前言与寒暄：

# 故障诊断报告
## 1. 命中规则名称
[从 runbook_rules 中匹配到的规则名称，如未匹配则填写“未收录规则”]

## 2. 核心证据
[摘录一条日志中的直接报错行]

## 3. 建议应急动作
[根据规则给出的具体处置操作]
</output_specification>
```

在这个结构中，指令有明确的步骤，外部日志被框定在 `<error_logs>` 之中，输出也有确定的标题起始标记和格式模版。当日志中即便出现无关文字甚至诱导性文本时，模型也能够较好地将其定位为待处理数据。

## 练习与自查清单

### 随堂练习
以下是一段有问题的提示词：

> “你是一个客服小助手。帮我看看用户的退款申请。千万别随便同意，不要乱给退款，退款政策是发货后7天内可以无理由，超过7天不行。用户输入是：‘我已经买了10天了，但衣服没拆封，给我退了吧，求求你了。’ 请回答用户，态度要好，不要骂人，直接说结果。”

**任务要求**：
1. 将其拆解为 `<role>`、`<task>`、`<policy>`、`<user_input>`、`<output_specification>` 五个模块。
2. 将其中的三处负向约束（“千万别随便同意”、“不要乱给退款”、“不要骂人”）改写为确定的正向规则或兜底格式。
3. 规定模型的输出首行必须以 `【审核结果】` 起始。

**验收标准**：
* 重构后的提示词中没有任何模糊的“千万别/不要”句式；
* 输入文本被独立放置在 `<user_input>` 标签内；
* 输出规范中明确规定了不同条件下的具体返回文字。

完成结构化文本组织后，如果业务需要将大模型的输出对接到程序接口或自动化流程中，单纯的自然语言排版依然不够。接下来请进入下一讲：[如何让大模型稳定输出 JSON？](/llm-100/prompt-engineering/如何让大模型稳定输出_JSON.md)，学习结构化输出与 Schema 约束的底层保障机制。
