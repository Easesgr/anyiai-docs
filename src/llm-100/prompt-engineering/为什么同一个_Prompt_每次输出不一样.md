在调用大语言模型 API 时，很多开发者会遇到一个现象：发送完全相同的提示词（Prompt），模型给出的回复却并不相同；甚至在把采样温度设为 0（`temperature=0`）或者固定了随机种子（`seed`）之后，输出内容依然偶尔会出现细微差别或首词翻转。

例如，向模型输入一个工单分类任务：

> **Prompt**：“请将以下工单分类为‘技术支持’或‘账单咨询’：用户反馈‘系统显示已扣款成功，但高级会员权益仍未到账’。”

在大部分请求中，模型可能稳定输出“账单咨询”；但在某些时段或并发请求下，它可能会输出“技术支持”，或者在开头多出一个换行符。

大模型输出的不一致通常由两层原因引起：
1. **算法层的随机采样**：当生成参数允许随机性时，模型每一步都在按概率分布“掷骰子”选词。
2. **系统层的数值与并行扰动**：即使关闭了随机采样（使用贪心解码），底层 GPU 在并行计算矩阵乘法与注意力时，受浮点数非结合律和并发调度影响，计算出的候选词打分在末位会有极微小波动。若两个词的概率极其接近，这个微小波动就会改变选词，并在后续生成中逐步放大。

## 1. 算法随机性：采样参数与随机数生成器

大模型生成文本的过程是按词（Token）自回归进行的。在生成每个新 Token 时，模型最后一层会为词表中的每个候选词输出一个未归一化的分数，这个分数称为 **Logits**。

这些 Logits 随后通过 Softmax 函数转换为概率分布：

$$P(w_i \mid w_{<t}) = \frac{\exp(z_i / T)}{\sum_{j} \exp(z_j / T)}$$

其中 $z_i$ 是候选词 $w_i$ 的 Logits，$T$ 为采样温度（Temperature）。关于温度与截断参数的详细控制逻辑，可参考 [/llm-100/prompt-engineering/Temperature_Top-p_Top-k_分别控制什么.md](/llm-100/prompt-engineering/Temperature_Top-p_Top-k_分别控制什么.md)。

![采样解码与贪心解码的词选择逻辑差异](/images/content-rebuild/bed982f9be6c5f9b/fig-1.png)

当 $T > 0$ 时，模型解码器并不是直接选取概率最大的词，而是依赖**伪随机数生成器（PRNG）**根据概率分布进行多项式采样：

*   **随机种子的理论作用**：PRNG 是确定性算法。如果固定了初始状态（`Seed`）、模型权重和计算流程，伪随机数列是完全固定的，理应生成相同的文本。
*   **云端 API 的现实偏差**：在云端服务中，推理任务由高度并行的 GPU 集群承载。服务端的请求调度、GPU 随机数发生器在多流（CUDA Streams）并发下的状态绑定并不一定能严格对齐，因此即使传入了相同的 `seed`，也很难保证跨请求的随机序列完全一致。

## 2. 贪心解码：为什么 Temperature=0 依然可能出现差异？

如果把温度设为 0，或者在框架中指定使用**贪心解码（Greedy Decoding）**，模型在每一步都会直接选取打分最高的那个词：

$$\hat{w}_t = \arg\max_{w_i} (z_i)$$

在数学定义上，$\arg\max$ 是一个完全确定的操作：只要输入的 Logits 向量 $z$ 完全不变，挑出来的词就必然恒定，不需要随机数发生器参与。

然而，**数学上的确切不等于物理硬件计算出的数值绝对恒定**。在 GPU 物理硬件上，每次计算出的 Logits 向量并非逐比特完全一致。只要数值末位发生微小的扰动，且这个扰动恰好发生在得分最接近的两个候选 Token 之间，$\arg\max$ 的结果就会翻转。

## 3. 数值与硬件原因：浮点数非结合律与并行累加

导致 Logits 产生微小波动的根本原因，在于现代计算机的浮点数运算规则以及 GPU 的高度并行特性。

### 浮点加法不满足结合律
在实数数学中，加法天然满足结合律：$(a + b) + c = a + (b + c)$。但在计算机遵循的 IEEE 754 浮点数标准中，**浮点加法不满足结合律**：

$$(a + b) + c \neq a + (b + c)$$

浮点数由符号位、阶码（指数）和尾数构成，尾数的有效位数是有限的。当两个数量级相差很大的数相加时，较小的数必须向较大的数“对阶”，其有效尾数向右移位。超出尾数表示范围的低位会被直接截断或舍入。

我们可以用一段 Python 代码直接验证这个现象：

```python
# 浮点数非结合律验证（Python 默认使用 IEEE 754 双精度浮点 FP64）
a = 1e16
b = -1e16
c = 1.0

result_left = (a + b) + c   # (1e16 + -1e16) + 1.0 = 0.0 + 1.0 = 1.0
result_right = a + (b + c)  # 1e16 + (-1e16 + 1.0)

print(f"(a + b) + c = {result_left}")   # 输出: 1.0
print(f"a + (b + c) = {result_right}")  # 输出: 0.0
```

在右侧算式中，计算 `-1e16 + 1.0` 时，由于双精度浮点数只有 53 位二进制尾数（约 15~17 位十进制有效数字），`1.0` 在对阶过程中被完全截断丢弃，加法结果依然是 `-1e16`，最终求和为 `0.0`。

在主流大模型推理中，为了降低显存占用并提升计算吞吐，普遍使用的是半精度格式（如 FP16 或 BF16）。FP16 只有 10 位尾数，BF16 只有 7 位尾数，其有效数字范围远低于双精度浮点，对阶舍入带来的误差更为常见。

![浮点数在对阶舍入中的非结合律图解](/images/content-rebuild/bed982f9be6c5f9b/fig-2.png)

### GPU 并行归约的时序不确定性
大模型推理包含大量的矩阵乘法（GEMM）与自注意力计算。无论计算注意力得分的求和，还是矩阵相乘的内积累加，本质上都是对成千上万个浮点数进行加法归约（Reduction）。

![GPU 并行归约求和由于线程调度差异引发的顺序变化](/images/content-rebuild/bed982f9be6c5f9b/fig-3.png)

现代 GPU 拥有数千个计算核心。为了充分利用硬件算力，数据被分配到不同的线程块（Thread Block）中并发计算：

1.  **线程调度差异**：不同流式多处理器（SM）的执行进度受硬件负载、显存访问延迟等物理因素影响，微观上的完成顺序并不固定。
2.  **原子累加顺序**：当不同线程块通过原子加法（如 `atomicAdd`）把部分和累加到同一块显存位置时，加法发生的先后顺序是动态变化的。
3.  **求和顺序重排**：结合浮点加法的非结合律可知，只要参与累加的数顺序发生了改变，即使是同一组输入数据，最终累加出来的数值在尾数末位就会产生微小差异。

### 误差在自回归中的级联放大
在模型生成第一个词时，如果候选词 A 的得分是 `10.500001`，候选词 B 的得分是 `10.500000`。两者的真实语义偏好几乎完全一致，但只要浮点累加顺序导致微调，使词 B 的得分变成了 `10.500002`，贪心解码就会在这一步选中词 B。

在自回归生成机制中，当前步选出的 Token 会被拼接到历史上下文中，作为下一步推理的输入。词 A 与词 B 的不同，会导致后续所有注意力层重新计算，原本只差 $10^{-6}$ 的末位扰动，便演变成两句完全不同的输出路径。

## 4. 推理服务并发：动态批处理对算子的影响

除了单个请求内部的硬件并行，线上推理服务的并发调度也是导致输出发生变化的重要系统因素。

![动态批处理下批次重组与算子选择差异](/images/content-rebuild/bed982f9be6c5f9b/fig-4.png)

在线上高吞吐推理系统（如 vLLM、TensorRT-LLM）中，普遍采用了**连续批处理（Continuous Batching）**机制。你的请求不会单独占用 GPU，而是与前后几毫秒内到达的其他用户请求打包成一个动态批次（Batch）一同计算：

*   **计算内核（Kernel）动态选择**：矩阵计算加速库（如 cuBLAS、CUTLASS）在执行前向传播时，会根据当前批次大小（Batch Size）和序列长度动态挑选最优的分块策略（Tiling）与计算内核。当服务负载低、批次为 1 时调用的算子，与并发高、批次为 32 时调用的算子，其内部的累加拓扑结构是不同的。
*   **显存分页排布**：为了高效复用显存，PagedAttention 将 KV 缓存切片存放在离散的物理显存块中。并发请求的进入和退出改变了内存块的分配顺序，进而轻微改变底层访存时序与数据合并路径。

这意味着：**发起请求瞬间服务端的并发压力，会通过算子选择和内存排布，间接影响底层数值的累加路径。**

## 5. 模型架构特性：MoE 路由与截断

在混合专家模型（MoE，例如 Mixtral 系列）中，这一数值扰动还会作用于专家路由层。

![MoE 路由门控权重微扰与容量截断导致的专家分歧](/images/content-rebuild/bed982f9be6c5f9b/fig-5.png)

MoE 模型通过一个轻量的门控网络（Gating Network）计算每个 Token 与各个专家的亲和度，并挑选 Top-K 个专家进行计算：

1.  **临界路由翻转**：门控网络的得分同样由浮点矩阵乘法得出。如果两个候选专家的匹配得分处于毫厘之间，微小的浮点波动就会让 Token 路由到完全不同的专家分支。
2.  **专家容量限制**：为了防止个别热门专家出现计算过载，部分系统在实现时会设置专家容量上限（Expert Capacity）。当同批次内大量请求同时涌向某个专家并触及上限时，超出容量的 Token 可能被转给次优专家或采取旁路直连，从而产生依赖于并发邻居请求的计算差异。

## 6. 工程应对方案：如何提高输出稳定性？

根据 Anthropic 官方在 [Prompt engineering overview](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/overview) 中的建议，工程落地的关键是根据使用场景明确成功标准（Success Criteria）并建立评测，而不是强行在所有环境下追求比特级的绝对一致。

![生产环境中实现输出稳定性的工程分层对策](/images/content-rebuild/bed982f9be6c5f9b/fig-6.png)

针对不同的应用阶段，可采取不同的收敛对策：

### 离线评测与基准测试场景
如果是在进行算法复现、自动化评测（Eval）或回归基准测试，需要在实验之间尽量保证输出可复现：

1.  **单并发与单批次**：在评测脚本中设置并发度为 1，固定 `batch_size=1`，避免动态批处理带来的算子切换。
2.  **启用框架确定性设置**：在本地运行 PyTorch 等框架时，可配置使用确定性算法（例如 `torch.use_deterministic_algorithms(True)`，并设置 `CUBLAS_WORKSPACE_CONFIG=:4096:8`）。需要注意，确定性算子往往会限制并行度，导致推理速度明显下降。
3.  **固定硬件与运行时环境**：尽量在同型号 GPU、相同驱动与同版本算子库下进行对比实验。

### 线上业务与生产调用场景
在线上高并发场景下，通过牺牲吞吐量来追求逐字绝对一致通常成本过高，工程实践应将重点放在**语义与结构的稳定性**上：

1.  **消除 Prompt 中的边界模糊**：在 Prompt 中明确分类标准并提供具体的示例（Few-shot）。如果两个分类在定义上有重叠，模型打分就会陷入胶着；给出清晰的判定分界线，能拉开最高分与次高分之间的差距，降低数值微扰翻转决策的概率。关于 Prompt 的设计原则，可进一步阅读 [/llm-100/prompt-engineering/Prompt_为什么能影响大模型输出.md](/llm-100/prompt-engineering/Prompt_为什么能影响大模型输出.md) 与 [/llm-100/prompt-engineering/结构化_Prompt_应该怎么写.md](/llm-100/prompt-engineering/结构化_Prompt_应该怎么写.md)。
2.  **使用结构化约束解码**：当业务需要固定字段或枚举值时，可以使用结构化输出机制（如 JSON Schema 校验或语法引导解码）。约束解码会在每一步将非法候选 Token 的概率直接置零，强制模型在受限状态机内选词，具体实现可参考 [/llm-100/prompt-engineering/如何让大模型稳定输出_JSON.md](/llm-100/prompt-engineering/如何让大模型稳定输出_JSON.md)。
3.  **下游逻辑基于模式校验而非字面匹配**：下游系统在解析模型回复时，应当校验输出是否符合预期的字段类型、枚举值范围或语义断言，避免编写依赖特定空格、换行或字面长度的脆弱匹配逻辑。

1. **检验浮点舍入现象**：在本地 Python 环境中运行文中的浮点非结合律代码。尝试保持 $c = 1.0$，将 $a$ 和 $b$ 的绝对值从 $10^{14}$ 逐步增加到 $10^{17}$，观察从哪个数量级开始，`a + (b + c)` 的计算结果开始丢失有效数字。
