在提示工程中，开发者最常接触的三种基础范式是：零样本提示（Zero-shot）、少样本提示（Few-shot）与思维链提示（Chain-of-Thought, CoT）。许多初学者容易把它们看作“不给例子”、“给几个例子”与“加一句逐步思考”的文本拼凑技巧。

实际上，这三种范式改变了自回归语言模型处理任务的计算路径。承接上一讲 [Prompt 为什么能影响大模型输出？](/llm-100/prompt-engineering/Prompt_为什么能影响大模型输出.md) 中关于条件概率分布塑造的讨论，本文通过一个统一的“退款工单审核”场景贯穿全篇，横向对比三种范式的工作机制、Token 开销与潜在偏置，并给出清晰的工程选型路径。

![Zero-shot、Few-shot 与 Chain-of-Thought 原理对比与选型实践封面图](/images/content-rebuild/cf75ca4820ee7158/cover.png)

> **阅读提示**：封面展示了三种范式在输入构建、注意力引导与推导路径上的差异。理解它们的核心在于观察模型究竟是直接输出判定，还是依赖示例锚定格式，亦或是借助中间步骤作为计算缓冲。

## 一个贯穿场景：退款申请审核

为了直观展示三者的区别，我们设定一个具体的业务场景：**电商售后退款审核**。
审核规则如下：
1. 商品送达未超过 7 天支持无理由退货；
2. 生鲜食品拆封后不支持无理由退货；
3. 质量问题退款必须附带图片凭证。

待测工单内容：*“用户购买的进口车厘子已签收 3 天，反馈底部发霉腐烂，附带了 2 张开箱照片，申请全额退款。”*

面对这一工单，三种提示方式的运作方式截然不同：

- **Zero-shot（零样本）**：只给出审核规则和工单，要求模型直接输出 `{"approved": true, "reason_code": "QUALITY_ISSUE"}`。模型直接依赖预训练与指令对齐时学到的通用语义来做判断。
- **Few-shot（少样本）**：在给出规则之前，先提供 2 到 3 个已审核过的工单样例（包含工单描述与对应的 JSON 结果），最后拼接当前待测工单。模型通过示例在上下文中快速锚定字段命名与分类边界。
- **Chain-of-Thought（思维链）**：要求模型不能一步得出判定，必须先按“商品类型核验 -> 签收时限核验 -> 凭证完整性核验”逐项推导，最后输出 JSON。模型利用自己生成的推导文本作为后续解码的计算上下文，降低跳步导致的逻辑遗漏。

## Zero-shot：依靠指令对齐的基线模式

### 工作机制

零样本提示在输入中仅包含任务指令与当前输入文本，不提供任何参考示例。其序列输入为：

$$\text{Input} = [\text{Instruction}, X_{\text{test}}]$$

模型根据前置指令计算当前输入的条件概率：

$$P(Y_{\text{test}} | \text{Instruction}, X_{\text{test}}) = \prod_{t=1}^{T} P(y_t | \text{Instruction}, X_{\text{test}}, y_{<t})$$

![Zero-shot 指令唤醒机制与基线确立流程](/images/content-rebuild/cf75ca4820ee7158/fig-1.png)

> **阅读提示**：图 1 展示了 Zero-shot 的直接映射路径。指令文本作为前置上下文，直接引导模型预测测试输入的输出分布。

Zero-shot 之所以能够理解未见过的任务，前提是模型在训练过程中经过了充分的指令微调（Instruction Tuning）与对齐训练。模型已经学习到了“提取”、“分类”、“总结”等高频动词的行为模式。当系统输入“请判断以下工单是否合规”时，模型能够沿用对齐先验直接进行解码。

### 优势与局限

1. **首字延迟（TTFT）最低**：提示词简短，Prefill 阶段的计算量和显存占用极小，能以最低的计算开销返回结果。
2. **零样本维护成本**：无需提前筛选、清洗与校验高质量示例。
3. **局限与边界**：如果任务涉及内部私有状态码、特殊的字段层级或非通用的业务定义（例如特定风控标签），模型缺少上下文线索，容易出现格式漂移或生成通用但错误的标签。

## Few-shot：利用上下文学习锚定格式与分布

### 上下文学习的生效方式

少样本提示通过在提示词中提供 $K$ 个标注好的输入-输出示例，引导模型处理新样本：

$$\text{Input} = [\text{Instruction}, (X_1, Y_1), (X_2, Y_2), \dots, (X_K, Y_K), X_{\text{test}}]$$

Few-shot 并不更新模型参数，它完全依靠自注意力机制在上下文窗口内建立关联：

1. **约束输出空间**：如果在 3 个示例中，输出标签均严格为 `REJECT` 或 `APPROVE`，模型注意力头会把预测概率显著集中在这些特定 Token 上，压制“驳回”、“同意”、“不通过”等同义泛化词的概率。
2. **锚定数据格式**：示例展示了精确的标点、缩进和 JSON 键名，模型在生成时能直接对齐示例的格式特征，减少语法解析错误。
3. **明确判断粒度**：示例能直观展示边界案例。例如“外包装轻微挤压”是否算作“质量问题”，文字规则难以穷举，但示例可以直接传递这种判别尺度。

![Few-shot 上下文注意力重分配与偏置产生机制](/images/content-rebuild/cf75ca4820ee7158/fig-2.png)

> **阅读提示**：图 2 展示了在提供多个示例时，自注意力机制如何将测试样本与前面的示例相连，同时标出了示例排布顺序可能引发的注意力倾斜。

### 潜在的统计偏置与陷阱

Few-shot 提高了格式稳定性，但也容易引入提示词诱导的偏差：

- **多数类偏置（Majority Label Bias）**：如果示例中 4 个是“同意退款”，仅 1 个是“拒绝退款”，模型会倾向于提高“同意退款”的先验概率，导致在真实类别平衡的数据上假阳性率上升。
- **近因偏置（Recency Bias）**：因果语言模型的注意力权重容易向靠近序列末尾的内容倾斜。排在最后一个示例的类别与风格，对 $X_{\text{test}}$ 的影响往往大于排在最前面的示例。
- **表面模式绑定**：若示例中所有“拒绝退款”的案例刚好都提到了“生鲜”，模型可能会误以为“生鲜”就等于“拒绝”，从而削弱对规则本身的综合判定。

工程对策：保持示例的类别数量均衡；随机打乱示例顺序；确保示例的多样性，避免所有正例都具备某种非关键共性。

## Chain-of-Thought：展开中间推导的计算草稿纸

### 为什么需要展开推导步骤？

标准提示（无论是 Zero-shot 还是 Few-shot）都要求模型完成从输入直接到结果的映射：

$$X \to Y$$

自回归模型在生成每一个 Token 时，其计算深度受限于网络层数与固定容量的前向计算。对于包含多个前置条件检查、多步数学运算或多跳逻辑关联的任务，单步前向传播往往难以直接锁定最终目标 Token 的概率分布，容易出现结论错误。

思维链（Chain-of-Thought, CoT）通过显式引入中间推导序列 $C = [c_1, c_2, \dots, c_M]$，将复合映射拆解为条件联合分布的逐步自回归过程：

$$P(C, Y | X) = P(C | X) \cdot P(Y | X, C) = \left(\prod_{m=1}^{M} P(c_m | X, c_{<m})\right) \prod_{t=1}^{T} P(y_t | X, C, y_{<t})$$

![标准直接映射与思维链状态展开路径对比](/images/content-rebuild/cf75ca4820ee7158/fig-3.png)

> **阅读提示**：图 3 对比了直接映射与思维链的推导差异。左侧直接跳步映射容易因计算容量受限而出现逻辑断裂；右侧显式输出中间推导 Token，充当了推理计算的草稿纸。

生成的每一个中间 Token 都会进入后续生成的计算上下文（写入 KV 缓存），后续步骤可以注意力回溯前面的推导结论，从而降低逻辑跳步导致的判断失误。

### 常见实现方式

1. **Zero-shot CoT（启发式诱导）**：在指令后追加“请按步骤分析各规则是否满足，再给出最终结论”。调用简单，但推导的规范性取决于模型自身能力。
2. **Few-shot CoT（显式范例约束）**：在上下文示例中提供完整的推导链范式：
   $$(X_1, C_1, Y_1), \dots, (X_K, C_K, Y_K), X_{\text{test}}$$
   这种方式不仅提示模型展开思考，还严格统一了中间步骤的颗粒度与推导格式。

关于思维链计算特性的详细论述，请参阅：[CoT 思维链提示为什么有效？](/llm-100/prompt-engineering/CoT_思维链提示为什么有效.md)。

## 核心指标对比与资源开销测算

在实际生产中，选择哪种范式需要综合权衡准确率与计算成本：

| 对比维度 | Zero-shot 提示 | Few-shot 提示 | Chain-of-Thought 提示 | 工程含义 |
| :--- | :--- | :--- | :--- | :--- |
| **输入构造难度** | 低（编写指令与数据占位） | 中（需筛选代表性样本） | 较高（需编写连贯的推导步骤） | 提示词构建与维护的人力成本 |
| **Prefill 开销** | 极小（通常数十至数百 Token） | 较大（数个示例增加数百至数千 Token）| 大（示例包含推导过程） | 影响首字延迟（TTFT）与服务并发上限 |
| **Decode 开销** | 小（直接生成最终答案） | 小（直接按模板生成结果） | 很大（输出数十至数百字推导过程） | 影响生成总耗时与每秒吞吐量（TPS） |
| **端到端延迟** | 短 | 较短 | 较长（生成时间随 Token 线性增加）| 用户端感知的完整响应耗时 |
| **格式遵循度** | 容易受指令理解偏差影响 | 极高（注意力机制对齐示例结构） | 中等（中间文本过长可能干扰结构） | 生成严格符合 JSON/模式定义的稳定性 |
| **复杂逻辑表现** | 条件交叠时容易漏判 | 对复杂因果推理提升有限 | 多步骤逻辑判定准确率提升显著 | 面对需要组合分析任务时的可靠性 |
| **典型失效表现** | 格式幻觉、生僻标签乱选 | 多数类偏置、近因偏置 | 逻辑逐步偏离（滚雪球错误）、无效废话 | 线上调优的重点排查方向 |

![三种提示范式多维工程权衡矩阵](/images/content-rebuild/cf75ca4820ee7158/fig-4.png)

> **阅读提示**：图 4 直观对比了三种范式在 Prefill 输入量、Decode 生成延迟、标注维护成本及复杂逻辑可靠性上的取舍关系。

### 控制变量测算示例

以开头的“退款工单审核”为例，待测输入约 80 个 Token，包含 3 条核验规则。在相同模型下对三种范式的资源占用进行估算（数值为标准 Tokenizer 下的控制示意）：

```text
[场景设定] 电商退款审核（待测工单长度=80 Tokens）

1. Zero-shot 方案：
   - 输入 (Prefill): 规则说明 + 待测工单 ≈ 140 Tokens
   - 输出 (Decode): JSON 结果 ≈ 20 Tokens
   - 运行特征: 首字延迟低，总耗时最短；面对多条件交叠时容易漏判生鲜属性。

2. Few-shot 方案 (K=3 样本)：
   - 输入 (Prefill): 规则说明 + 3 个标准样本 + 待测工单 ≈ 480 Tokens
   - 输出 (Decode): JSON 结果 ≈ 20 Tokens
   - 运行特征: Prefill 计算量约为零样本的 3.4 倍，首字延迟略增，但 Decode 耗时与零样本几乎一致；JSON 字段与状态码完全符合预期。

3. Few-shot CoT 方案 (K=3 包含推导过程样本)：
   - 输入 (Prefill): 规则说明 + 3 个含检查步骤样本 + 待测工单 ≈ 860 Tokens
   - 输出 (Decode): 逐步核验分析 + JSON 结果 ≈ 130 Tokens
   - 运行特征: Prefill 显著增大，Decode Token 量扩大约 6.5 倍。大模型生成阶段逐 Token 自回归，在常见交互与中小批量场景下通常受显存带宽限制（Memory Bandwidth Bound），总响应耗时显著拉长，但条件遗漏率明显下降。
```

## 生产落地选型决策路径

系统设计应遵循**“先轻后重、根据评估结果递进”**的原则，避免不加分析就直接引入复杂的长提示。

![生产落地选型决策路径图](/images/content-rebuild/cf75ca4820ee7158/fig-5.png)

> **阅读提示**：图 5 给出了从业务目标评估到范式确立的递进判定树。依据延迟要求、格式容忍度与推理深度逐步选择合适方案。

### 三步递进法

#### 第一步：用清晰的 Zero-shot 建立评估基线
对于常规分类、简短摘要、提取常见实体等任务，首先通过 Zero-shot 建立性能与准确率基线。参考 [结构化 Prompt 应该怎么写](/llm-100/prompt-engineering/结构化_Prompt_应该怎么写.md) 与 [System Prompt、User Prompt、Assistant Prompt 分别有什么作用？](/llm-100/prompt-engineering/System_Prompt_User_Prompt_Assistant_Prompt_分别有什么作用.md) 编写清晰的分块提示词。如果指标符合业务要求，应优先采用该方案以获得最低延迟与调用成本。

#### 第二步：遭遇格式错误或标签模糊时升级为 Few-shot
如果评测发现模型逻辑判断基本正确，但存在以下问题，应升级为 Few-shot：
- **输出格式不稳定**：生成的 JSON 字段时有时无，或缩进异常（配合 [如何让大模型稳定输出 JSON](/llm-100/prompt-engineering/如何让大模型稳定输出_JSON.md) 实践）；
- **专用标签分类**：业务有特殊的枚举定义（如内部错误码 `ERR_BIZ_402`）。
- **实施细节**：准备 2 到 4 个覆盖不同类别的代表性示例，保持正反例数量相当，且正负样本交替排列。

#### 第三步：面临多步条件与逻辑组合时升级为 CoT
只有当评估数据明确出现**“漏看规则”**、**“计算失误”**或**“前后结论矛盾”**时，才引入思维链：
- **适用场景**：多条件风控决策、数值与时间比对、代码分析。
- **延迟控制**：对于在线实时交互接口，过长的思维链会损害用户体验；可以通过限制输出步骤长度，或者在后台离线审核中采用该策略。

## 可检验练习与边界排查

![Few-shot 顺序偏置与 CoT 格式冗余故障排查图](/images/content-rebuild/cf75ca4820ee7158/fig-6.png)

> **阅读提示**：图 6 展示了练习涉及的两个常见工程故障：示例不均衡导致的判定倾斜，以及简单提取任务强加思考链导致的延迟劣化。

### 练习 1：排查样本顺序与比例偏置
**场景**：某团队使用 Few-shot 检查商品图片是否侵权。Prompt 中配置了 5 个示例：前 4 个都是侵权样例（`VIOLATION`），第 5 个是非侵权样例（`NORMAL`），紧接着输入待测商品图信息 $X_{\text{test}}$。
**现象**：在实际灰度测试中，边界模糊的轻微相似案例几乎全部被判为 `NORMAL`；而删除第 5 个示例后，模型又将绝大多数待测样本判为 `VIOLATION`。

**检验任务**：
1. 结合上下文学习机制，分别解释上述两种现象的原因。
2. 给出重新设计这批示例的排布方案，使其能够进行更客观的分类。

```text
[排查参考思路]
1. 前者受近因偏置（Recency Bias）主导：最后一个示例紧挨待测输入，其注意力权重被放大；后者受多数类偏置（Majority Label Bias）主导：示例全为违规，拉高了该类别的先验概率。
2. 方案：挑选 4 个典型示例（2 个违规、2 个合规），按“违规 - 合规 - 违规 - 合规”交替排布，消除近因与类别不均衡。
```

### 练习 2：简单抽取任务中的范式错配
**场景**：业务需求是从用户反馈中抽取 `用户手机号`、`故障设备类型` 和 `发生城市`。某开发人员为了“保证准确度”，在 Prompt 中加入了：“请详细分析用户的表达意图，逐步推理设备特征与所在地区，写出分析过程，再输出 JSON”。
**现象**：系统每秒处理并发量（TPS）大幅下降，且下游 JSON 解析器频繁报错。

**检验任务**：
1. 从计算特性的角度，分析该做法为何导致吞吐量下降？
2. 为什么该任务加入推理链反而更容易让 JSON 解析失败？

```text
[排查参考思路]
1. 实体抽取属于直接模式匹配，不包含多步因果逻辑。引入思维链使输出 Token 增加了数倍，在常规服务批量下解码受显存带宽瓶颈制约，单次调用生成耗时大幅延长，拖垮并发吞吐。
2. 模型在自由输出长段推导文本时，容易遗忘包裹最终结果的代码围栏，或在 JSON 前后混入推导总结，导致下游反序列化失败。此类任务应改用标准 Few-shot 配合结构化约束。
```
