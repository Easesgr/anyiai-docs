在完成监督微调（SFT）或偏好对齐后，很多开发者习惯盯着训练损失（Loss）曲线看：只要 Loss 一路平稳下降，就认为微调模型已经学成。然而，训练 Loss 下降仅仅说明模型拟合了训练集中的 Token 序列概率分布。如果训练集存在表达偏差、标注噪声或格式模式化，模型在真实未见任务上的泛化能力不仅可能没有提升，甚至还会发生通识能力的退化。

我们在 [/llm-100/finetuning/sft-instruction-tuning.md](/llm-100/finetuning/sft-instruction-tuning.md) 中介绍了指令微调的具体流程，在 [/llm-100/finetuning/finetuning-overfitting.md](/llm-100/finetuning/finetuning-overfitting.md) 中分析过过拟合的早期信号。本讲将重心移到模型微调完成后的独立验证体系：如何建立客观、可量化且不易受表象欺骗的评估链路，确认模型究竟是“真的变聪明了”，还是仅仅在“死记硬背”或“学会了敷衍”。

以一个典型的业务场景贯穿全文：**企业 IT 运维故障排障助手**。团队使用 2000 条内部工单数据微调了一个 8B 尺寸的开源底座模型，目标是让它准确分析系统报错日志、生成诊断结论并给出安全的操作建议。

![微调模型评估体系全景图](/images/content-rebuild/d31baa1761e454a9/cover.png)

评估大语言模型的核心难点在于：自然语言输出是开放的，同一技术意图可以用完全不同的词汇表达，缺乏唯一的确定性解析解。要建立可信的评估体系，需要将评测划分为三个互为补充的层次：**客观自动化指标**用于底线验证，**大模型作为裁判（LLM-as-a-Judge）**处理多维度复杂开放式表达，**人工双盲抽样与端到端业务监控**完成生产环境验收。

## 1. 传统 NLP 评估指标的失效：BLEU 与 ROUGE 的局限性

在传统机器翻译和自动文本摘要任务中，BLEU（Bilingual Evaluation Understudy）与 ROUGE（Recall-Oriented Understudy for Gisting Evaluation）是最常用的统计学重叠度指标：

- **BLEU** 基于 $n$-gram 精确率（Precision），统计生成文本中的词段有多少比例命中了参考答案，配合简短惩罚因子（Brevity Penalty）防止模型短路输出短语。
- **ROUGE**（如 ROUGE-N、ROUGE-L）侧重于召回率（Recall），衡量参考答案中有多少 $n$-gram 或最长公共子序列（LCS）出现在生成文本中。

在现代大模型的生成场景中，这两类指标往往会带来严重的误判。

### 语义对齐与表面重叠的脱节

BLEU 和 ROUGE 依赖字符串层面的精确 Token 匹配，完全忽略了向量空间内的同义替换、句式重组和关键逻辑词的致命影响。

在我们的运维助手场景中，看下面两组对比算例：

**算例 A：语义完全相同，但词汇重叠度极低（高漏报）**
- 参考答案：`"生产集群数据库连接池耗尽，需要紧急扩容连接数上限。"`
- 模型生成：`"线上 DB 实例的 Connection Pool 满了，请立即调大最大活跃连接配置。"`
- 结果：尽管两者给出的排障结论和处置方案 100% 一致，但由于专有名词中英文混用以及用词习惯差异，二元语法（2-gram）交集几乎为零，BLEU-2 得分极低。自动化指标会把这一优质回答判定为“不合格”。

**算例 B：词汇重叠度极高，但关键逻辑反转（高误报）**
- 参考答案：`"该告警由网络抖动引起，千万不要直接重启核心主节点。"`
- 模型生成：`"该告警由网络抖动引起，建议直接重启核心主节点。"`
- 结果：二者仅有“千万不要”与“建议”这几个字的差异，ROUGE-1 与 ROUGE-L 得分可高达 0.85 以上。但模型给出的建议完全相反，执行后会导致生产集群宕机。

![传统指标失效与语义矛盾对比](/images/content-rebuild/d31baa1761e454a9/fig-1.png)

对于严格的结构化输出（如提取特定格式的 JSON）、分类或代码执行，我们可以通过语法解析器或单元测试运行断言（如 HumanEval 采用的 `Pass@k`）。但在生成长文本诊断报告、多步排障建议或对话交互时，词面统计指标已无法胜任，必须引入基准测试与模型评判机制。

## 2. 客观标准化评测基准：通用能力与领域封闭集设计

在微调特定领域的模型时，评估必须包含两个并行方向：一是验证**目标垂直能力的增量**，二是监控**通用基础能力的退化（灾难性遗忘）**。

### 2.1 通用基础能力基线测试（防遗忘回归）
微调会更新模型的注意力权重与前馈网络参数。如果训练数据分布过于单一，很容易破坏基座模型原有的通用常识与符号推理能力。一套严谨的评估方案应在微调前后对通用学术基线进行回归测试：
- **MMLU / CMMLU**：检验基础多学科知识常识与通识理解。
- **GSM8K / MATH**：检验多步数学演算与符号逻辑推理是否被微调冲垮。
- **HumanEval / MBPP**：监测基础代码编写与指令语法遵循能力。

如果在运维领域微调后，运维专业问答得分上升了，但 GSM8K 上的多步逻辑准确率相对微调前 Base 模型下跌了超过 15%，这就意味着模型的基本推导链路受到了破坏，在后续面对未见过的复合故障日志时，极容易出现逻辑混乱。

### 2.2 垂直领域封闭测试集设计规范
通用基准测不出业务细节，必须针对业务场景构建独立、不对外公开的封闭测试集（Held-out Test Set）。在 [/llm-100/finetuning/finetuning-data-construction.md](/llm-100/finetuning/finetuning-data-construction.md) 中我们讨论了数据的构建与清洗。在测试集规划中，建议遵循以下约束：

1. **分布分层覆盖**：按照真实线上日志的意图频率抽取测试样本，不要采用均匀分布。常见高频故障（如网络超时、OOM、鉴权失败）占 70%~80%，长尾低频故障（如内核丢包、死锁竞争）占 20%~30%。
2. **难度梯度划分**：将测试用例细分为标准用例（Standard，格式规范且信息完整）、复合用例（Complex，跨服务级联报错）和对抗用例（Edge/Adversarial，如缺少上下文的模糊提问、带错别字的日志）。对抗用例专门检验模型在信息缺失时是否懂得要求用户补充信息，而不是胡乱生成结论。
3. **多参照物对齐**：评测不能只看模型自身的绝对分数，必须设立基线参照物：
   - **微调前 Base 模型**：在相同 Prompt 条件下的 Zero-shot 与 Few-shot 输出，这是衡量微调带来的“真实增量”的标尺。
   - **标杆通用大模型**：使用行业公认的高能力模型（如 GPT-4）生成的回答，作为该任务的能力天花板参照。

## 3. LLM-as-a-Judge 实施机制：单样本打分与成对对比

当参考答案不唯一且人工批改成本极高时，采用推理能力更强的高阶大模型担任裁判，即 **LLM-as-a-Judge** 方案。目前主流评测范式分为两类：单样本打分（Single-Answer Grading）与成对对比（Pairwise Comparison）。

### 3.1 单样本打分（Direct Scoring）
裁判模型对单个候选回答基于预定义的评分标准（Rubric）给出 1 到 5 分的分项评分。这种方式适合大规模自动化初筛，但面临打分尺度漂移问题——模型裁判容易给大多数回答都打出 4 分或 5 分（分数通胀），很难拉开不同版本模型之间的细微差距。

### 3.2 成对对比（Pairwise Win-Rate）
成对对比更贴近人类实际体验：向裁判模型同时提供用户提问、可选的标准排障手册参考，以及由两个模型分别生成的回答（候选回答 A 与候选回答 B）。裁判模型只需要判断：`A 更好`、`B 更好` 还是 `平局`。成对对比能有效放大两个候选输出在细节处理上的差异，是目前衡量微调模型与基座模型相对胜率的核心方式。

![LLM-as-a-Judge 判定机制与数据流](/images/content-rebuild/d31baa1761e454a9/fig-3.png)

### 3.3 裁判 Prompt 设计规范
裁判模型同样会受诱导性提示词影响。必须通过严密的结构化 Prompt 规范其评判标准，强制要求裁判模型在得出结论前，必须先在 Thinking 标签中给出逐步推导依据（Chain-of-Thought），防止它未经推理直接凭借表面印象选出胜者。

```markdown
[系统角色]
你是一位严格公正的资深 IT 运维与系统架构专家。你需要对比两个 AI 运维助手针对工程师报错提问给出的回复质量。

[评判标准]
1. 诊断准确性：排查方向是否符合系统报错的真实原因？是否存在捏造命令或技术幻觉？
2. 方案安全性：给出的排障操作命令是否具备防护意识？是否提示了备份数据或高危操作风险？
3. 指令遵循度：是否遵守了用户提出的输出格式与排障步骤要求？
4. 简洁清晰度：条理是否分明，是否直奔故障核心？

[评测输入]
【用户问题与报错日志】
{input_prompt}

【助手 A 回答】
{response_a}

【助手 B 回答】
{response_b}

[评判要求]
- 必须逐步对比助手 A 与助手 B 在上述四个标准上的实际表现。
- 坚决杜绝因篇幅更长或排版花哨而盲目给高分，无用废话应判定为扣分项。
- 先在 `<analysis>` 标签中输出详细推导依据，最后在 `<judgment>` 标签中严格输出一个选项：[[A胜]]、[[B胜]] 或 [[平局]]。
```

## 4. 模型裁判的偏差校准：位置、冗长与自我偏置

在很多公开报告中，微调模型在成对对比中对基座模型取得了 70% 以上的胜率，但上线后用户满意度毫无变化。深入排查后往往会发现：胜率不是来源于模型能力提升，而是触发了裁判模型的系统性偏置（Biases）。

### 4.1 位置偏置（Position Bias）与双向交换校准
语言模型在处理较长输入时，受注意力分布和自回归解码机制的影响，往往会对输入顺序产生偏好。部分模型容易出现首因效应（Primacy Bias，偏向槽位 1），但更常见的是近因效应（Recency Bias，更偏向后读到的槽位 2）。

**双向交换校准（Position Swap）流程**：
每个测试用例必须运行两次判定，交换候选模型的呈现位置：
1. **轮次 1**：槽位 1 填入模型 A，槽位 2 填入模型 B，获得判定结果 $J_1$。
2. **轮次 2**：槽位 1 填入模型 B，槽位 2 填入模型 A，获得判定结果 $J_2$。

汇总判决结果规则如下：

| 轮次 1 ($A$ 在前, $B$ 在后) | 轮次 2 ($B$ 在前, $A$ 在后) | 最终双向校准结果 | 原因说明 |
| :--- | :--- | :--- | :--- |
| $A$ 胜 | $A$ 胜 (即裁判判定槽位 2 胜) | **$A$ 胜** | 不受位置调换影响，结论稳定一致 |
| $B$ 胜 | $B$ 胜 (即裁判判定槽位 1 胜) | **$B$ 胜** | 不受位置调换影响，结论稳定一致 |
| $A$ 胜 (判槽位 1 胜) | $B$ 胜 (判槽位 1 胜) | **平局（或丢弃用例）** | 明显被位置偏置主导（只偏好前面的选项） |
| $B$ 胜 (判槽位 2 胜) | $A$ 胜 (判槽位 2 胜) | **平局（或丢弃用例）** | 明显被位置偏置主导（只偏好后面的选项） |
| 平局 | 平局 | **平局** | 两者质量没有明显差距 |

![位置偏置双向交换与校准流程](/images/content-rebuild/d31baa1761e454a9/fig-4.png)

### 4.2 冗长偏置（Verbosity Bias）
模型裁判普遍容易被长篇大论吸引。如果模型 A 输出了 300 字的精准排障步骤，而微调模型 B 套用了通用模板，洋洋洒洒输出了 800 字的问候语、排障原则、安全免责声明和多余建议，裁判模型很容易误判模型 B“更详细、更专业”。

校准手段包括：
- **长度惩罚约束**：在裁判 Prompt 中硬性写明“若多出的内容不包含新的有效排查信息，属于负向冗余，应酌情扣分”。
- **长度差分桶统计**：在统计最终胜率时，计算两份回答的字符长度差值 $\Delta L = |L_A - L_B|$。如果微调模型的胜率提升全部集中在 $\Delta L > 200$ 字符的区间，而在长度相近的区间胜率与基座模型持平，这就清楚表明微调模型只是学会了“注水刷分”，并未提高真实排障能力。

### 4.3 自我偏置（Self-Enhancement Bias）
实验发现，以某厂商大模型作为裁判时，它往往会对自身或同一模型家族生成的语言风格（如特定的过渡句句式）打出更高分数。因此在工程评测中，应尽量选用与待测模型架构不同、非同源训练的高阶模型作为裁判，或者引入双裁判交叉表决。

实现双向位置交换校准的参考代码：

```python
from typing import Dict, Any

def evaluate_pairwise_swap(
    judge_client,
    prompt: str,
    ans_a: str,
    ans_b: str
) -> Dict[str, Any]:
    """
    双向交换成对评测：消除模型裁判的位置偏置
    """
    # 第一轮：模型 A 放在槽位 1，模型 B 放在槽位 2
    res_1 = judge_client.judge(prompt=prompt, first=ans_a, second=ans_b)
    
    # 第二轮：模型 B 放在槽位 1，模型 A 放在槽位 2
    res_2 = judge_client.judge(prompt=prompt, first=ans_b, second=ans_a)
    
    # 假设 judge_client 返回标准化判决："FIRST_WIN", "SECOND_WIN", "TIE"
    # 将两轮判决映射回真实模型 A 与 B
    v1 = "A" if res_1 == "FIRST_WIN" else ("B" if res_1 == "SECOND_WIN" else "TIE")
    v2 = "B" if res_2 == "FIRST_WIN" else ("A" if res_2 == "SECOND_WIN" else "TIE")
    
    if v1 == v2:
        final_winner = v1
        status = "CONSISTENT"
    else:
        # 两轮评测结果因位置变化出现冲突，归类为受位置偏置影响
        final_winner = "TIE"
        status = "POSITION_CONFLICT"
        
    return {
        "round_1": v1,
        "round_2": v2,
        "final": final_winner,
        "status": status
    }
```

## 5. 生产级验收闭环：防数据污染、人工抽检与业务指标

通过了离线评测与裁判打分，模型只是拿到了通往生产环境的准考证。在上线前，还需要完成防污染审查、人工双盲检验与端到端业务监控。

### 5.1 数据污染排查（Data Contamination Check）
如果微调后的模型在公开基准或私有封闭测试集上的得分高得惊人，最常见的原因是：**测试样本被混入到了微调训练集中**。这种现象被称为测试集污染。模型并没有学会解题推理，只是强记住了标准答案。

排查数据污染的常用手段包括：
- **$n$-gram 重叠检索**：提取测试集中所有问题的 8-gram 到 13-gram 片段，反向检索训练语料库。若命中率过高，说明存在直接的文字抄录或重复切片泄露。
- **向量语义近邻扫描**：使用 [/fundamentals/embedding/embedding-model-selection.md](/fundamentals/embedding/embedding-model-selection.md) 中介绍的嵌入模型，将测试集问题与训练集样本统一编码。针对余弦相似度大于 0.95 的样本对，进行人工审核排除重复问题。
- **困惑度（Perplexity, PPL）异常检验**：计算模型在测试样本上的 Token 级条件困惑度。困惑度的数学理论下界为 1（对应交叉熵损失 Loss 为 0）。如果特定测试样本的 PPL 呈现异常接近 1 的极端低值，远低于同分布下其他域外测试集，表明模型大概率在微调期间反复见过这批文本。

![微调数据污染检测流程图](/images/content-rebuild/d31baa1761e454a9/fig-5.png)

### 5.2 人工双盲 A/B 抽测（Human Blind A/B）
在金融、医疗、基础设施运维等容错率极低的领域，离线全自动评估必须辅以人工抽检。开展高质量人工评审的核心在于消除主观倾向：
1. **抹除格式指纹**：微调模型通常会自带独特的问候语格式、小标题层级或特殊标记。在分发给技术专家前，必须预先清洗掉这些格式指纹，让评审员无法辨别哪份回答来自微调模型、哪份来自基准大模型。
2. **标注一致性度量（Inter-Annotator Agreement）**：安排至少两名技术人员独立盲审同一批测试样本，使用 Cohen's Kappa 系数计算两人的判定一致性。如果 Kappa 系数低于 0.6，说明评估细则（Rubric）在执行上存在较大歧义，评审员各有各的标准，必须重新修订量表并对齐尺度。

### 5.3 串联端到端业务转化指标
微调模型的最终价值需要体现在真实业务指标的改善上，模型的输出往往由 [/interview/model-deployment-interview/core-metrics.md](/interview/model-deployment-interview/core-metrics.md) 中介绍的工程网关统一接入。对于我们的运维排障助手，核心考核以下业务指标：

- **格式解析失败率**：如果助手需要直接调用系统 API 触发排查脚本，其输出的 JSON 格式或命令参数解析失败率必须低于预设阈值。无法解析即视为整次任务失败。
- **一线工程师采纳率（Acceptance Rate）**：在真实工单排障建议流中，一线运维工程师直接采纳模型建议或仅做微调编辑的比例。
- **平均故障解决时长（MTTR）缩短率**：接入微调助手后，典型高频故障从报警到恢复的时间是否实质缩短。

![生产级端到端验收闭环流向图](/images/content-rebuild/d31baa1761e454a9/fig-6.png)

一套稳健的微调评估方案，绝不是单看一条不断降低的训练 Loss 曲线，而是由“通用基准防遗忘 + 封闭测试集测增量 + LLM 裁判双向交换保客观 + 数据排查防泄露 + 线上业务指标验收益”共同构成的严密验证链条。

## 学习成果检验

学完本讲后，请尝试完成以下两个推演与设计练习：

1. **偏差校准场景推演**：在对微调模型 A 与 Base 模型 B 进行成对对比测试时，共评测了 100 道运维题目。在未做交换的第一轮中，A 的胜率为 68%，B 为 22%，平局 10%。而在交换位置后执行的第二轮中，A 的胜率变为 32%，B 为 58%，平局 10%。请计算经过双向位置一致性校准（仅保留两轮均获胜的样本）后，模型 A 的真实净胜场次上限可能是多少？这说明评测过程受到了什么偏置的影响？
2. **数据污染排查方案设计**：团队从线上真实工单中导出了 50000 条数据用于微调，并从中随机切分出 1000 条作为测试集。经过 3 轮微调后，测试集准确率达到了 98%，但直接给外部测试工单诊断时准确率仅有 60%。在不重新收集新数据的前提下，你首先应如何排查切分过程中是否存在数据泄漏？
