在构建大模型系统时，调用 API 的 Demo 往往只需几十行代码。但当服务推向生产环境时，开发团队常常遭遇吞吐骤降、首字延迟过高、显存溢出（OOM）或硬件采购成本失控等问题。这些瓶颈不是常规的 Web 并发锁或网络 I/O 延迟，而是直接受制于 GPU 计算核心算力、显存容量与显存访问带宽之间的物理平衡。

本路线承接 [AI 工程师入门学习路线](/learning-path/ai-engineer.md) 的基础认知，通过一个贯穿全程的 70B 模型私有化部署案例，剖析自回归 Transformer 的双阶段计算特征、推理与训练的显存真实构成，以及这些底层限制如何直接决定连续批处理、KV Cache 管理与硬件选型。

## 贯穿案例：一个 70B 问答系统的落地指标

为了避免抽象讨论，我们设定一个具体的企业私有化部署任务：
* **模型规格**：开源 70B 参数密集型模型，采用分组查询注意力（GQA），层数 $L=80$，KV 头数 $H_{kv}=8$，每个注意头维度 $d_k=128$；
* **业务负载**：支持峰值并发 $C=16$；平均输入长度 2048 Tokens，期望输出长度 512 Tokens，单请求总序列长度为 2560 Tokens；
* **核心诉求**：评估需要几张 80GB 显存的 GPU，并推导单请求在不同阶段的时延上限。

后续各节将围绕这个具体任务，逐步拆解为什么单卡装不下、显存如何被吞噬，以及吞吐瓶颈落在哪里。

## 阶段一：自注意力计算的双阶段与硬件物理瓶颈

大模型在生成回答时分为两个截然不同的阶段：**Prefill（预填充）** 与 **Decode（逐字解码）**。两个阶段对硬件资源的诉求完全不同。

标准多头自注意力计算公式为：

$$\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V$$

对于长度为 $N$ 的输入序列，矩阵乘法 $Q K^T$ 的维度是 $(N, N)$，理论计算量与中间张量随序列长度呈现平方级增长。但在推理的不同阶段，这一计算表现出不同的硬件制约。

![Prefill 计算受限与 Decode 访存受限机制对比](/images/content-rebuild/86522adfe61616ed/fig-1.png)

上图展示了自回归生成的两大阶段差异：左侧 Prefill 阶段由矩阵乘法主导，GPU 算力利用充分；右侧 Decode 阶段由矩阵向量乘主导，耗时受制于显存读取速度。

### 1. Prefill 阶段：计算受限（Compute-Bound）
当用户提交长度为 $N$ 的提示词时，模型需要一次性计算所有输入 Token 的注意力分布以建立初始上下文。此时的计算形式为矩阵乘矩阵（GEMM）。
* **硬件特征**：算力利用率高（FLOPs / Byte 很高）。GPU 的张量核心（Tensor Cores）全速运转，耗时主要取决于 GPU 的峰值浮点计算能力；
* **指标影响**：直接决定了**首字延迟（Time to First Token, TTFT）**。输入提示词越长，Prefill 的计算量增长越快；如果输入达到上万 Token，即便采用 FlashAttention 减少显存读写，注意力计算本身的算术运算量依然随序列长度显著上升。

### 2. Decode 阶段：访存受限（Memory-Bandwidth Bound）
模型吐出第一个字后，进入自回归循环：每一步仅将上一轮生成的这 1 个 Token 作为新输入，计算其输出概率。此时的计算形式退化为矩阵乘向量（GEMV）。
* **硬件特征**：为了计算最新这 1 个 Token 的输出，GPU 在每一步都必须将全量模型权重（例如 70B 参数）以及之前积累的所有历史 Key/Value 缓存，完整地从显存（HBM）搬运到计算芯片的片上高速缓存（SRAM）中。因为计算量仅对应 1 个 Token，计算强度极低，GPU 计算单元大部分时间都在“等待数据从显存搬运过来”；
* **指标影响**：直接决定了**每个输出 Token 的耗时（Time Per Output Token, TPOT）**。在单并发或小批次场景下，单纯提升 GPU 浮点算力对加快 Decode 速度几乎没有帮助，决定流速的是显存读取带宽。

## 阶段二：推理显存构成与 KV Cache 动态膨胀

许多开发者误以为只要显卡显存大于模型权重体积就能顺利部署。实际上，推理节点显存包含四部分：

$$\text{Total Memory} = \text{Memory}_{\text{Model}} + \text{Memory}_{\text{KV Cache}} + \text{Memory}_{\text{Activations}} + \text{Memory}_{\text{Workspace}}$$

![LLM 推理显存切片与 KV Cache 随并发扩张机制](/images/content-rebuild/86522adfe61616ed/fig-2.png)

上图拆解了推理节点的显存结构。静态权重奠定了显存底座，而动态 KV Cache 随并发数与上下文长度不断累加，是引发服务 OOM 的主要原因。

### KV Cache 显存核算推导
为了避免在生成第 $t$ 个 Token 时重新计算前 $t-1$ 个 Token 的 Key 和 Value，系统必须把每层的 Key/Value 张量驻留在显存中。对于采用分组查询注意力（GQA）的模型，单个 Token 在模型全层中占用的 KV Cache 显存为：

$$\text{Size}_{\text{per\_token}} = 2 \times L \times H_{kv} \times d_k \times \text{BytesPerElement}$$

以我们的 70B 案例模型为例（$L=80, H_{kv}=8, d_k=128$），在 FP8 精度存储下（每个元素占 1 字节）：
$$\text{Size}_{\text{per\_token}} = 2 \times 80 \times 8 \times 128 \times 1 \text{ 字节} = 163,840 \text{ 字节} = 160 \text{ KiB}$$

当系统承载 16 个并发，单请求上下文长度达到 2560 Tokens 时：
$$\text{Total KV Cache} = 16 \times 2560 \times 160 \text{ KiB} = 6,553,600 \text{ KiB} = 6.25 \text{ GiB}$$

如果并发数扩大到 64，且采用未量化的 FP16（每个元素 2 字节）存储，KV Cache 将直接膨胀至：
$$64 \times 2560 \times 320 \text{ KiB} = 52,428,800 \text{ KiB} = 50 \text{ GiB}$$
此时仅上下文缓存的显存开销就高达 50 GiB，已占满单张 80GB 显卡的一大半，逼近了 FP8 模型权重自身的体积。

### 显存优化策略
为了防止显存耗尽并提升吞吐，工程上有两类核心解法：
1. **权重量化与 KV Cache 量化**：将 FP16/BF16 权重压缩至 FP8、INT8 或 INT4，大幅减小静态权重和 Decode 阶段每步的显存数据读取量；同时启用 FP8 KV Cache，将单个 Token 的缓存体积直接减半；
2. **分页显存管理（PagedAttention）**：传统连续显存分配必须预先为每个请求分配最大长度（如 4096）的空间，导致大量未写满的显存碎片无法被其他请求使用。PagedAttention 借鉴操作系统虚拟内存分页思想，将 KV Cache 划分为固定大小的物理块（Block），按需动态分配，消除外部碎片并允许多个请求共享部分前缀缓存（Prompt Cache）。

## 阶段三：参数调整与模型对齐的资源边界

当基础模型输出不符合业务要求时，团队常常需要在微调、对齐与外挂知识库之间进行抉择。

![全量微调、LoRA 与 DPO 的显存开销与更新机制拓扑](/images/content-rebuild/86522adfe61616ed/fig-3.png)

上图对比了三种训练与对齐方式的显存开销。全量微调因优化器状态导致显存需求呈数倍放大，LoRA 大幅降低了梯度与优化器开销，而 DPO 则避免了在线采样的调度负担。

### 训练显存的严格构成
推理阶段只保留权重和少量激活值，而训练阶段必须维护优化器状态与梯度。以 16 位混合精度训练结合标准 AdamW 优化器为例，显存开销如下（设参数量为 $\Phi$）：
* **模型权重（FP16/BF16）**：$2 \Phi$ 字节；
* **梯度（FP16/BF16）**：$2 \Phi$ 字节；
* **AdamW 优化器状态（FP32）**：包含 FP32 主权重副本（$4 \Phi$）、一阶动量（$4 \Phi$）、二阶动量（$4 \Phi$），合计 $12 \Phi$ 字节。

仅参数、梯度与优化器这三项静态开销就达到 $16 \Phi$ 字节。如果对 70B 模型进行全量微调，静态显存需求直接达到 $70 \times 16 = 1120 \text{ GB}$，这还没包含前向传播保存的中间激活值（Activations），必须依赖大规模张量并行与 ZeRO 分片集群。

### LoRA 与 DPO 的工程权衡
* **LoRA（低秩自适应）**：固定原始权重 $W_0$，仅训练低秩分解矩阵 $\Delta W = B \cdot A$（秩 $r \ll \min(d, k)$）。参与反向传播的参数量通常低于原始参数的 1%，使得梯度和 AdamW 状态占用的显存从上千 GB 降至数 GB（若进一步结合 4-bit 量化的 QLoRA 压缩冻结权重，即可在普通工作站上调优 70B 模型）；
* **DPO（直接偏好优化）**：传统 RLHF 依赖 PPO 算法，需要同时在显存中维护策略模型、价值模型、参考模型和奖励模型，并在训练中执行在线采样，调度复杂且显存开销极高。DPO 将偏好损失推导为基于参考模型的隐式概率对齐，直接使用离线标注的偏好数据对更新策略模型，免去了在线采样生成与独立奖励模型的维护。

### 机制澄清：为什么不能用微调替代知识库？
很多团队希望通过微调直接把企业规章或专业资料“背诵”进模型参数中，这在工程上存在显著风险：
1. **知识的概率化存储不可控**：微调更新的是高维连接权重，模型学习的是文本的分布、语法和推理风格，难以严格保证对具体事实性数字、日期的精确记忆；
2. **灾难性遗忘与知识冲突**：参数注入容易导致模型遗忘通用能力，且一旦企业业务规则更新，无法单点修改参数；
3. **缺乏事实可溯源与权限控制**：生产级系统要求每项结论提供出处切片以供审计。微调输出无法提供确定性的引用来源，也无法按用户权限动态隔离数据。

因此，事实性知识必须交由检索增强系统（RAG），微调则用于约束输出格式、领域专业术语表达与特定推理规范。相关落地细节可参考 [RAG 实战学习路线](/learning-path/rag-practice.md)。

## 阶段四：调度机制演进与并发吞吐优化

显存容量与读写带宽的限制，直接推动了推理引擎架构从早期静态批处理走向迭代级调度。

![传统静态批处理与连续批处理调度时序对比](/images/content-rebuild/86522adfe61616ed/fig-4.png)

上图展示了连续批处理如何消除由于请求输出长度不一带来的“气泡等待时间”，从而大幅提升推理硬件的吞吐效率。

### 连续批处理（Continuous Batching）
* **传统静态批处理**：一组请求必须等待该批次中最长的请求生成完毕后才能统一退出。如果一个请求只需生成 20 个字，而另一个请求需要生成 500 个字，短请求完成后其占用的显存和算力将被长时间锁死（产生气泡时间 Bubble）；
* **连续批处理**：推理引擎在每个生成步（Iteration-level）介入调度。当某个请求生成结束标识符（EOS）时，引擎立即释放该请求占用的 KV 块，并将等待队列中的新请求加入进来，同时执行新请求的 Prefill 与旧请求的 Decode。硬件流水线因此保持高度饱和。

在应用层，如果无视显存上限而让多轮对话无限增长，任何先进调度引擎都会触发显存溢出。必须在上层进行主动的上下文预算管理与剪枝：
* 依照 [上下文工程是什么？为什么它比单纯写 Prompt 更重要？](/frontier/context-engineering/what-is-context-eng.md) 建立 Token 预算管控；
* 参考 [一个高质量上下文应该包含什么？](/frontier/context-engineering/high-quality-context.md) 剔除冗余历史；
* 在复杂执行任务中，结合 [Loop Engineering 到底是什么？](/frontier/loop-engineering/Loop_Engineering_到底是什么.md) 与 [Loop 的灵魂不是执行，而是验证](/frontier/loop-engineering/Loop_的灵魂不是执行_而是验证.md) 拆解长链条，防止对话轮数无限膨胀。

## 阶段五：交付物实操——70B 问答系统选型与推导验收

现在回到文章开头的贯穿案例，依据前面推导的物理限制与公式，完成系统的硬件与性能选型核算。

![基于显存公式与并发吞吐要求的推理部署选型决策漏斗](/images/content-rebuild/86522adfe61616ed/fig-5.png)

上图展示了从业务并发与长度指标，通过显存与带宽核算，最终推导出所需 GPU 配置与理论时延上限的决策漏斗。

### 1. 显存总需求核算
* **模型权重（采用 FP8 格式）**：
  $$\text{Mem}_{\text{Model}} \approx 70 \times 10^9 \times 1 \text{ 字节} \approx 70 \text{ GB}$$
* **KV Cache 显存（16 并发，单请求 2560 Tokens，FP8 格式）**：
  $$\text{Mem}_{\text{KV}} = 16 \times 2560 \times 160 \text{ KiB} \approx 6.25 \text{ GiB}$$
* **运行缓存与激活值预留**（CUDA Graphs、PagedAttention 内存池管理开销）：预留约 $8 \text{ GB}$；
* **系统总显存需求**：
  $$\text{Mem}_{\text{Total}} = 70 + 6.25 + 8 = 84.25 \text{ GB}$$

### 2. GPU 卡数与并行策略
* 单张 80GB 显卡（如 A100-80G 或 H800-80G）即便在 FP8 量化下也无法容纳 84.25 GB；
* 选型结论：必须采用**双卡张量并行（Tensor Parallelism, TP=2）**，总显存容量为 $160 \text{ GB}$；
* 显存余量：部署完成后占用约 $84.25 / 160 \approx 52.7\%$，剩余显存空间可供动态扩展最大并发至 64 以上。

### 3. Decode 阶段理论单流流速上限推算
假定 2 张 80GB GPU 的聚合显存带宽为 $2 \times 2.0 \text{ TB/s} = 4000 \text{ GB/s}$：
在 Decode 阶段，单请求独占系统时，每生成 1 个 Token 都需要遍历加载一遍 70GB 权重。单步纯访存最低耗时为：
$$t_{\text{step}} \approx \frac{70 \text{ GB}}{4000 \text{ GB/s}} = 0.0175 \text{ 秒} = 17.5 \text{ 毫秒}$$
对应单请求的最高理论生成流速为：
$$v \approx \frac{1}{0.0175} \approx 57 \text{ Tokens/s}$$
*注：该数值为单请求独占整组显存带宽时的极限基准值，未计入卡间通信延迟与算子调度开销；当 16 个并发同时 Decode 时，模型权重在每次前向传播中被多请求复用，系统总吞吐（Tokens/s）会成倍提高，但受制于单批次显存读取与计算调度，每个请求的单字流速会有所下降。*

### 阶段自测标准
在推进后续专项前，确保能够独立回答并推演以下两个问题：
1. **自测题 1**：为什么相同的 70B 模型，在长提示词的 Prefill 阶段主要消耗 GPU 算力，而在短输入的自回归 Decode 阶段却主要消耗显存带宽？
2. **自测题 2**：给定一个 13B 密集模型（$L=40, H_{kv}=40, d_k=128$），在 FP16 精度、单请求上下文 4096 Tokens 下，单并发时的 KV Cache 显存是多少？全量微调与 LoRA 微调在静态显存需求上有何量级差异？
