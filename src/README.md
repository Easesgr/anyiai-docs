<summary>阅读指南</summary>

大模型工程是一门结合了概率采样、张量计算、宿主系统调度与业务容错的综合技术。本站旨在帮助开发者拆解从 Transformer 底层计算、应用状态机设计到生产级服务调度的完整链路。

为了让抽象概念落地，我们以一个贯穿全站的具体工程案例作为线索：**构建一个自动化“电商订单与退款处理助手”**。
* 在最简单的阶段，我们直接向模型发送提示词要求退款，模型可能由于无法连接数据库而编造订单状态；
* 引入工具调用（Tool Call）后，模型可以输出查询数据库的参数，由宿主程序代为执行；
* 当退款涉及“检查物流状态 -> 校验退款金额 -> 写入退款单 -> 发送短信通知”等多步骤时，单靠单一提示词往往难以稳定保障分支流转与状态一致，工程上通常引入由代码约束的状态机或工作流来管理步骤转移与重试边界；
* 当助手推向多用户并发访问时，系统需要处理首字延迟（TTFT）、解码吞吐瓶颈、显存溢出（OOM）以及多租户鉴权隔离。

本站的全部模块，均围绕解决此类真实系统问题而展开。

## 五层研发进阶阶梯

学习大模型技术并非只有“调用 API”和“从零训练基座”两个极端。本站将工程与算法认知拆解为五个层级：

1. **L1 基础认知（输入输出与概率分布）**：理解文本如何通过分词器（Tokenizer）转换为离散的 Token 编号，理解向量嵌入（Embedding）在高维空间中的相对几何关系，掌握模型如何基于未归一化对数概率（Logits）配合温度（Temperature）和 Top-p 进行随机采样。
2. **L2 机制原理（张量流动与计算开销）**：深入 Transformer 内部的注意力矩阵计算。理解输入阶段并行计算（Prefill）与逐字吐字阶段（Decode）在显存读取与算力需求上的差异；推导键值缓存（KV Cache）的显存占用公式；理解参数高效微调（如 LoRA）的低秩分解逻辑与直接偏好对齐（DPO）的目标函数设计。
3. **L3 应用工程（工具调用与状态编排）**：掌握检索增强生成（RAG）的切块分块、多路召回与重排序；理解模型函数调用中 Schema 校验与宿主执行的职责划分；通过代码定义有限状态机（FSM）或有向无环图（DAG）限制流程分支；使用模型上下文协议（MCP）标准化连接外部数据源，理解提示规范与执行脚本的分离。
4. **L4 系统架构（并发调度与服务治理）**：面对生产流量，设计带有排队机制的模型网关；配置 Prefill 与 Decode 分离部署策略以降低首字等待；针对多租户实现会话隔离与配额控制；管理长时间运行任务的异步分发与状态持久化；为所有生成请求配置基于 Trace ID 的全链路监控。
5. **L5 验证复盘（评测指标与故障定位）**：区分 RAG 评测中的上下文相关度、召回率、忠实度与答案相关度指标；建立自动化基准评测流水线；复盘线上常见的显存 OOM、超时堆积、状态机死循环与提示注入问题，形成严密的排障因果链。

![五层研发认知演变阶梯与阶段交付产物示意图](/images/content-rebuild/b335630551682c19/fig-1.png)

上图展示了 L1 至 L5 的递进关系。需要说明的是，这五级并非单向绝缘，当我们在 L4 遇到解码阶段显存暴涨时，往往需要回到 L2 重新计算 KV Cache 的显存开销；当 L3 工具调用出错时，也需要回到 L1 检查提示词输入是否触发了分词异常。

## 专栏矩阵与内容职责分工

为了让每篇文章职责清晰、不杂糅无关概念，本站划分为六大核心专栏：

* **基础原理（Fundamentals）**：专注概念定义、直觉推导与基础小实验。解释机制“因何而生”、“数学与物理约束是什么”，避免将工程表象包装为伪原理。
* **LLM-100 体系课**：按照由浅入深的节奏，系统讲解从底层计算、预训练目标、微调对齐到端侧优化的渐进主线，每篇聚焦一个核心技术点。
* **[前沿专题](/frontier/README.md)**：覆盖工程实践中演进迅速的专门方向：
  * [文档解析](/frontier/document-parsing/README.md)：分析版面分析、表格提取与 OCR 混合输入的精度边界；
  * [上下文工程](/frontier/context-engineering/README.md)：讨论长序列注意力分布衰减、中间信息丢失与提示压缩；
  * [Agent 记忆系统](/frontier/agent-memory-system/README.md)：解析对话上下文窗口、外部数据库持久化与用户画像检索的设计权衡；
  * [Agent Skills](/frontier/agent-skills/README.md)：明确将业务规范文档（SKILL.md）与宿主具体执行脚本解耦，强调 Skill 是由模型与宿主程序协作解析的说明组织形式，而非单一函数调用；
  * [Agentic RAG](/frontier/agentic-rag/README.md) 与 [AI Workflow](/frontier/ai-workflow/README.md)：比较模型自主规划与程序代码约束的工作流边界，探讨何时该让模型自由决策，何时该由程序代码硬性约束状态转移；
  * [AI Coding Agent](/frontier/ai-coding-agent/README.md)：分析自动化代码生成、安全沙箱隔离与测试报错反馈循环的设计要点。
* **[AI 工程架构](/architecture/README.md)**：聚焦工程基础设施。涵盖统一网关代理、流式响应截断、会话缓存（Prefix Caching）命中策略与全链路 Trace 可观测性。
* **工程项目（Projects）**：提供可运行的代码仓库与完整的配置文件，侧重网络重试、环境恢复与接口边界处理等真实细节。
* **面试与学习路径（Interview & Path）**：提炼严谨的技术口述与系统排障复盘，帮助工程师在系统设计与技术评审中准确表达系统选型权衡。

## 面向不同技术背景的学习动线

不同角色的工程师在进入大模型领域时，面临的技术挑战差异很大。以下是三条推荐的学习路径：

### 1. 应用开发工程师（偏重业务逻辑与 API 落地）
* **核心目标**：开发稳定可控的业务应用，避免模型产生无法处理的幻觉或失控跳转。
* **推进路径**：从 L1 建立对 Token 和采样的直觉，直接进入 L3 学习工具调用格式验证；研读 [AI Workflow](/frontier/ai-workflow/README.md) 掌握状态转移代码写法；参考 [Agentic RAG](/frontier/agentic-rag/README.md) 优化退款场景下的知识召回；随后了解 [AI 工程架构](/architecture/README.md) 中的基础重试与网关流控配置。

### 2. 算法研发工程师（偏重模型调优与表征极限）
* **核心目标**：理解模型内部注意力分配、微调权重更新与上下文长度扩展机理。
* **推进路径**：以 L2 机制层为核心，掌握 Transformer 矩阵计算与注意力掩码设计；推导混合精度训练显存分配与 KV Cache 的增长模型；深入 [上下文工程](/frontier/context-engineering/README.md) 分析长窗口信息检索损耗；结合 [Agent 记忆系统](/frontier/agent-memory-system/README.md) 探索语义向量的有效召回。

### 3. 系统架构师（偏重集群吞吐、成本与高可用）
* **核心目标**：搭建高可用模型推理网关，在有限算力下保障并发吞吐与 SLA。
* **推进路径**：深入 L4 架构层，系统研读 [AI 工程架构](/architecture/README.md)；对比 Prefill 阶段的高算力消耗与 Decode 阶段的高显存带宽占用，评估分离部署方案；针对多租户设计安全的沙箱隔离与状态缓存，参考 [AI Coding Agent](/frontier/ai-coding-agent/README.md) 规划企业级代码执行环境。

### 跨模块穿透示例：在退款助手里安全集成 MCP 与工作流

如果直接让模型自主调用退款接口，一旦模型产生参数幻觉，就可能引发误退款。标准的多层穿透落地流程如下：

```text
步骤 1 [机制认知]：理解 Tool Call 的底层事实——模型只负责生成符合 JSON Schema 的文本字符串，没有任何直接操作外部系统的能力。
    ↓
步骤 2 [接口规范]：使用 MCP（模型上下文协议）通过标准传输机制（如 stdio 或 Streamable HTTP）向宿主暴露只读查询工具，工具必须由宿主应用校验权限后再执行。
    ↓
步骤 3 [流程约束]：在 /frontier/ai-workflow/README.md 指引下，使用有限状态机编排关键动作。例如只有在“查到有效退款单”且“金额低于阈值”时，程序才触发退款分支；高风险金额强制转向人工审批节点。
    ↓
步骤 4 [系统防护]：在 /architecture/README.md 指引下，为外部工具调用配置单次超时熔断、失败重试上限，并为每次工具执行打上统一 Trace ID，记录完整出入参用于对账。
```

上图展示了不同角色如何在全站知识地图中穿透协作。模型的生成能力必须被封装在宿主程序的参数校验、状态跳转和超时保护外壳中，才能构成可靠的业务系统。

## 写作与技术验证规范

为确保读者获得真实可验证的知识，本站所有内容均遵循以下写作约定：

1. **杜绝无根据的营销词汇**：不使用无技术定义的形容词，正文直陈输入、处理机制、输出结果与异常条件。
2. **严格区分技术属性**：明确区分概念定义、直觉类比、代码实现、业内实践与数学定理。类比仅用于启发直觉，绝不用作逻辑证明。
3. **拒绝虚构性能数据**：所有延迟、吞吐、召回率算例必须列出软硬件环境与前提假设，不做偷换口径的横向对比。
4. **强调因果关系与失效边界**：讲解系统配置时，既说明正常生效条件，也说明一旦缺乏校验或超出显存时系统会发生何种具体异常（如 OOM、连接池耗尽、步骤漂移）。
5. **代码可运行与降级说明**：提供的示例代码均注重核心调用逻辑，伪代码明确标示；对前沿尚未达成共识的假说做显式说明。
