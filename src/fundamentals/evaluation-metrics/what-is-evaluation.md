在大模型应用开发中，很多人都经历过这样的场景：团队为了解决电商客服助手漏判“生鲜食品不支持七天无理由退换”的问题，在提示词（Prompt）里新增了规则说明，并在后台顺手把生成温度（Temperature）从 0.7 改成了 0.2。

改完后，开发者在对话框里随手试了 3 个生鲜退货问题，模型全都准确拒绝了。大家觉得“效果显著”，立刻推向上线。然而刚过半天，线上监控告警：用户咨询普通服装的正常退货申请被模型大面积误拒，还有用户反映回答语气变得僵硬重复。

这种随手输入几个问题、全凭主观感受做判断的做法，被称为**直觉试用（Vibe Check）**。它没有固定测试集，也没有对照基准，极易被偶发的成功蒙蔽。要想让模型优化具备确定性，必须把评测当作一门严格控制变量的实验科学。

## 科学评测与直觉试用：为什么要控制变量？

评测的目的，是验证某项工程改动与系统表现变化之间的因果关系。当我们提出“增加思维链提示能让客服场景的复杂判决准确率提升”时，这是一个待验证的假设。

为了验证假设，必须设立两组处于相同外部环境的对照分支：

1. **基准组（Control Baseline）**：固定的上下文、固定的温度、固定的测试数据集，使用原版提示词。
2. **实验组（Treatment Group）**：除新增思维链引导语外，模型版本、采样温度、依赖的检索知识库内容均与基准组保持一致。

如果在修改提示词的同时，还顺手更换了底层大模型的版本号，或者调整了检索模块的召回数量，最终的准确率波动就混入了多个变量。统计学上将这些互相交织的干扰因素称为**混杂变量（Confounding Variable）**。一旦存在混杂变量，我们就无法得知分数提升究竟来自提示词，还是来自底层模型更新。

![直觉试用与科学评测对照实验对比图](/images/content-rebuild/db04731e15053235/fig-1.png)

科学评测要求在实验中锁定所有无关变量。只有排除了环境噪声与多变量干扰，指标的升降才能真正反映具体的工程收益。

## 评测系统的四个核心要素

无论是评估简单的文本分类器，还是复杂的复合 Agent 系统，一套规范的评测流水线都由四个相互解耦的组件构成。

```
[1. 测试样本集 (Test Dataset)] ───提供输入数据与预期───┐
                                                         ▼
[2. 系统输入变量 (System Input)] ──> [待测系统 (System Under Test)] ──> [待评测输出 (Output)]
                                                                                 │
[3. 参考标准 (Ground Truth)] ────────────────────────────────────────────────────┼───> [4. 打分器 (Evaluator)] ──> 评测指标
```

### 1. 测试样本集（Test Dataset）
测试集是实验的数据基石。它必须系统性覆盖业务场景中的典型问题，并包含一定比例的边界案例（例如生鲜与普通商品混合退货、特殊格式订单号、恶意试探提问）。测试集必须与训练、调试阶段使用过的样本物理隔离。

### 2. 系统输入变量（System Input）
输入不仅仅是用户发送的问题文本，还包括注入系统的全部上下文环境：系统提示词（System Prompt）、采样参数（Temperature、Top-p、随机种子 Seed）、Few-shot 示范样例，以及知识库检索召回的参考切片。评测时必须完整记录这些参数配置。

### 3. 参考标准（Ground Truth）
参考标准是判断模型输出是否合理的依据，分为两种形式：
* **强参考（Gold Standard）**：有明确唯一的正确答案。例如信息抽取任务中的标准实体标签，或者代码生成任务中必须通过的单元测试套件。
* **弱参考或无参考（Reference-Free）**：在开放式客服解释、文案生成等任务中，不存在唯一标准答案。此时的参考标准转变为质量约束准则（Rubric），例如“回答必须引用参考文档中的退换条款”、“回答不得编造运费险金额”、“语气友好且无攻击性”。

### 4. 打分器（Evaluator / Metric）
打分器负责将待测系统的输出（结合或不结合参考标准）映射为具体的量化分数：
* **规则判定**：使用正则表达式、关键字匹配或 Python 断言进行硬性检查，速度极快且结果确定。
* **启发式统计**：如 BLEU、ROUGE 等指标，通过计算字符或词元的表面重合度打分，适用于翻译等格式高度受限的场景。
* **基于模型的评估器（LLM-as-a-judge）**：让能力更强或经过特定对齐的模型扮演裁判，按照明确的评分规则对回答的逻辑性、事实一致性进行打分。在评估检索增强系统时，诸如 [Ragas](https://docs.ragas.io/en/stable/) 等评测框架广泛采用了这种思路，通过解耦的指标评估上下文相关性与回答真实度。

## 离线门禁与在线监控：测试不能只做一次

系统发布不是评测的终点。一套健壮的 AI 应用工程体系，通常采用“离线门禁”与“在线监控”双轨机制。

| 维度 | 离线评测（Offline Evaluation） | 在线监控（Online Evaluation） |
| :--- | :--- | :--- |
| **核心目标** | 版本发布前的准入把关，防止能力倒退（Regression） | 持续观察生产环境的真实表现，捕获异常故障 |
| **测试数据** | 固定的黄金标注集（Golden Dataset） | 生产环境实时抽样的真实用户请求 |
| **评估延迟** | 容忍较高的耗时（允许跑批数十分钟或数小时） | 要求低延迟，通过异步队列准实时聚合处理 |
| **度量信号** | 任务准召率、约束遵守率、单元测试通过率 | 业务转化率、用户点赞/踩/手动修改、安全拦截告警 |
| **环境状态** | 输入与依赖完全固定，结果易于复现 | 请求分布和外部依赖实时变动，不易单次复现 |

离线评测如同发布前的质检闸门，确保未经测试的改动不会污染生产环境；在线监控则是哨兵，负责捕捉脱离离线数据集范围的新问题。

![离线门禁与在线监控双环结构及数据回流图](/images/content-rebuild/db04731e15053235/fig-3.png)

两个体系通过**数据回流链路（Feedback Loop）**相互强化：在线监控中发现的高频失败案例（例如新上市商品的特殊售后咨询），在经过脱敏、清洗与人工复核后，会作为新测试用例补充进离线的黄金测试集。这样可以保证系统犯过的错误在后续版本中得到持续防护。关于评测体系的整体架构设计，可参考 [AI 评测体系](/architecture/ai-evaluation.md)。

## 高分假象的两个根源：数据泄露与分布漂移

在很多实际项目中，模型在离线榜单或自建测试集上表现优异，上线后却频繁翻车。排除统计误差后，这种反差往往由两类问题引起：**数据泄露**与**分布漂移**。

![数据泄露污染与分布漂移因果机制图](/images/content-rebuild/db04731e15053235/fig-4.png)

### 1. 数据泄露（Data Contamination）
当测试集的答案或特征直接、间接地混入了模型的训练过程或提示词上下文中时，评测就会退化为单纯的“开卷背题”。

常见泄露途径包括：
* 微调训练语料切分时未做物理隔离，同一批用户在相同时段提出的相似问题同时散落在训练集与测试集中。
* 提示词工程中的 Few-shot 示范样例，直接借用了测试集中的代表题。

在数据泄露下，模型只是记住了表层映射关系。一旦遇到表述稍微改变的新样本，指标就会大幅滑落。

### 2. 分布漂移（Distribution Drift）
即便测试集完全独立，静态的测试样本也可能与生产环境的动态流量脱节。常见的漂移包括两种形式：
* **协变量漂移（Covariate Shift）**：输入分布 $P(X)$ 发生变化。离线测试集通常由语法规范、标点完整的书面语组成；而生产环境中的真实用户输入夹杂着大量错别字、倒装句、方言以及网络缩写。
* **概念漂移（Concept Shift）**：输入与正确输出的映射关系 $P(Y|X)$ 发生改变。例如电商平台在年终大促期间临时调整了运费险赔付政策，原本标注为“正确”的标准解答，在现实业务中已经变成了过期的错误回答。

## 样本规模与统计显著性：抽 20 个题测够了吗？

很多研发团队在评估优化效果时，习惯这样汇报：“我们从报错日志里挑了 20 个案例进行对比测试，旧提示词答对了 10 个，新提示词答对了 13 个，胜率达到 65%，优化效果显著。”

这种推断在统计学上是站不住脚的。

### 算例验证：二项分布与假阳性概率

假设新旧提示词在本质上没有任何能力差异，新提示词答对的概率等同于抛掷一枚均匀硬币，胜率参数的零假设为：
$$H_0: p = 0.5$$

我们进行 $N = 20$ 次独立测试。在零假设（即新旧方法完全无差异）成立的前提下，新方法单纯依靠运气命中 $\ge 13$ 次的单侧累计概率计算如下：
$$P(X \ge 13) = \sum_{k=13}^{20} \binom{20}{k} 0.5^{20}$$

逐项计算组合数：
* $\binom{20}{13} = 77,520$
* $\binom{20}{14} = 38,760$
* $\binom{20}{15} = 15,504$
* $\binom{20}{16} = 4,845$
* $\binom{20}{17} = 1,140$
* $\binom{20}{18} = 190$
* $\binom{20}{19} = 20$
* $\binom{20}{20} = 1$

将组合数相加：
$$\sum_{k=13}^{20} \binom{20}{k} = 77,520 + 38,760 + 15,504 + 4,845 + 1,140 + 190 + 20 + 1 = 137,980$$

由于总可能结果数为 $2^{20} = 1,048,576$，因此单侧概率为：
$$P(X \ge 13) = \frac{137,980}{1,048,576} \approx 0.1316$$

双侧假设检验的 $p$-value 约为：
$$p = 2 \times 0.1316 = 0.2632$$

在常规的统计显著性门限 $\alpha = 0.05$ 下，该结果的 $p$-value（0.2632）远大于 0.05。这意味着：即便新旧系统能力完全一致，单纯由于随机抽样波动，在 20 次测试中出现“13 次或以上命中”的概率也高达 26.3% 以上。将这 3 道题的胜出归功于工程优化，存在很大的假阳性风险。

![样本量对二项分布置信区间收敛影响对比图](/images/content-rebuild/db04731e15053235/fig-5.png)

### 样本规模对置信区间的影响

在大样本正态近似下，胜率估计的 Wald 95% 置信区间半宽（误差界限 Margin of Error, MOE）可表示为：
$$\text{MOE} \approx 1.96 \times \sqrt{\frac{\hat{p}(1-\hat{p})}{N}}$$

当观测胜率 $\hat{p} = 0.65$ 时（注：$N=20$ 时样本量较小，此处正态近似主要用于跨数量级宏观趋势示意）：
* 当 $N = 20$ 时，$\text{MOE} \approx 1.96 \times \sqrt{\frac{0.65 \times 0.35}{20}} \approx 0.209$（置信区间宽达 $[44.1\%, 85.9\%]$，完全包含了 $50\%$ 的无差异点）。
* 当 $N = 100$ 时，$\text{MOE} \approx 0.093$（置信区间收缩至 $[55.7\%, 74.3\%]$）。
* 当 $N = 1,000$ 时，$\text{MOE} \approx 0.030$（置信区间精确收窄至 $[62.0\%, 68.0\%]$）。

测试样本量直接决定了实验的最小可检测效应。在小样本下，细微的技术改进会被随机噪声彻底掩盖。没有足够数量且独立分布的测试集，很难得出令人信服的实验结论。

## 搭建一次规范的评测流水线

一套严谨的评测流程应按以下五个阶段推进：

![评测实验设计工程全闭环实施链路图](/images/content-rebuild/db04731e15053235/fig-6.png)

1. **明确假设并控制变量**：确定本次优化的单一独立变量（如仅调整提示词结构），锁定底层模型、温度参数及检索链路。
2. **准备黄金测试集**：收集独立于训练过程的代表性样本，涵盖正面用例与边界异常用例，并建立可靠的判定准则。
3. **选择打分器**：对结构化输出优先使用规则或测试用例进行精确判定；对自然语言解释，可结合针对业务准则对齐的模型评估器或人工双盲复核。
4. **统计显著性验证**：计算指标的置信区间与假设检验指标，避免因小样本随机波动过早得出结论。
5. **灰度发布与监控承接**：离线测试达标后，通过小流量 A/B 测试上线，持续观测业务转化与异常告警，将真实 Bad Case 清洗脱敏后定期回流至黄金测试集。
