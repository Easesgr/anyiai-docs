在评估大语言模型时，字词重合度指标（如 BLEU、ROUGE，参见[《生成任务怎么评估？》](/fundamentals/evaluation-metrics/generation-metrics.md)）只能衡量生成文本和参考答案字面上有多接近。如果模型做数学应用题写了一大堆推理步骤但算错最后一位数字，或者写 Python 代码少了一个闭合括号，字词重合度很高，但结果毫无实用价值。

为了量化模型在学科知识、逻辑推理和代码编写上的能力，学术界推出了各类公开基准测试（Benchmarks）。然而，榜单上的高分经常让人困惑：为什么两个团队测同一个开源模型，MMLU 分数能差 10 分？为什么基准测试跑分极高，上线接真实业务却频繁翻车？

评估基准不仅仅是一套试卷，它包含了一整套输入结构、解码参数与答案提取规则。脱离具体的评测协议看跑分，极易陷入打榜假象。

## 三大主流基准考什么？输入、输出与判定逻辑

主流基准测试针对不同的认知和执行任务，设计了不同的题目形式与判分规则。最具代表性的是考察学科知识的 MMLU、考察多步算术的 GSM8k，以及考察代码正确性的 HumanEval。

![三大基准测试机制分解与判定流程对比](/images/content-rebuild/79d4daeee6843baa/fig-1.png)

### 1. MMLU：多任务学科知识单选

MMLU（Massive Multitask Language Understanding）涵盖初等数学、物理、化学、计算机、法律、医学、人文等 57 个学科领域，共有约 1.4 万道单项选择题。

每道题目由题干（Question）与四个候选项（A、B、C、D）组成：
- **输入示例**：“以下哪个细胞器负责在真核细胞中产生大部分 ATP？ A. 核糖体 B. 线粒体 C. 高尔基体 D. 内质网”
- **标准答案**：`B`

MMLU 考察的是模型通过预训练吸收的事实知识与学科理解。因为是单选题，理论上随机猜测也有 25% 的正确率。

### 2. GSM8k：多步文字算术应用题

GSM8k（Grade School Math 8K）包含 8,500 道小学级别的数学应用题。题目一般包含 2 到 3 句自然语言描述，需要 2 到 8 步四则运算才能得出最终整数答案。

- **输入示例**：“小明买了 3 本笔记本，每本 5 元。他还买了 2 支单价 3 元的钢笔。他给了收银员 30 元，应找回多少元？”
- **预期推导与输出**：
  1. 笔记本花费：$3 \times 5 = 15$ 元；
  2. 钢笔花费：$2 \times 3 = 6$ 元；
  3. 总支出：$15 + 6 = 21$ 元；
  4. 找零：$30 - 21 = 9$ 元。
  最终答案为 9。

GSM8k 考察模型将自然语言拆解为符号计算、维持中间状态并完成多步推演的能力。如果强制要求模型“只输出最终数字”，模型很难在单步自回归中直接预测出多步运算的末尾结果；如果允许模型一步步写出推导过程（思维链，Chain-of-Thought），正确率通常会有明显跃升。

### 3. HumanEval：沙箱环境中的功能正确性

HumanEval 由 164 道手写 Python 编程题组成。每道题包含函数签名、文字描述（Docstring）以及隐藏的单元测试用例。

- **输入示例**：要求实现 `has_close_elements(numbers: List[float], threshold: float) -> bool`，判断浮点数列表中是否存在两数距离小于给定阈值。
- **判定方式**：代码评测不能靠字面比对，唯一标准是把模型生成的代码放入 Python 沙箱运行，执行断言测试（如 `assert has_close_elements([1.0, 2.0, 3.9, 4.0, 5.0], 0.3) == True`）。全部测试用例通过才算正确。

## 评测协议如何改变最终得分

同一个模型在同一个基准数据集上，换用不同的评测协议，分数可能出现几分到十几分的差距。看跑分时，必须连同评测协议一起看。

![评测协议与超参数对基准打分的波动链条](/images/content-rebuild/79d4daeee6843baa/fig-2.png)

### 1. 提示词设置：Zero-shot、Few-shot 与 CoT

- **Zero-shot（零样本）**：只给题干，要求直接答题。这反映模型在没有额外引导下的基础遵循能力。
- **Few-shot（少样本上下文学习）**：在题干前拼入 5 个同类型题目的问答范例（如 5-shot）。这不仅帮模型锚定输出格式，还通过注意力机制激活与该任务相关的上下文表示。在大部分知识单选题上，5-shot 分数通常略高于 0-shot。
- **Chain-of-Thought（CoT，思维链）**：在 GSM8k 等需要中间推导的任务中，提示词中加入分步推导演示或加入“请一步步思考”，让模型先输出推导再给答案。自回归生成推导 Token 时，后续计算可以利用前面的中间结果，把复杂的整体运算拆解为局部的单步推导。需要注意的是，在不需要多步推理的简单单选题上强行加 CoT，反而可能因为格式不稳定或冗余表述导致提取不到选项字母，降低最终统计分数。

### 2. 解码策略：贪心解码与采样解码

- **贪心解码（Greedy Search，Temperature = 0）**：每一步总是选条件概率最高的单个 Token。在客观题（如 MMLU、GSM8k）评测中，贪心解码输出确定、完全可复现，是主流标准。
- **采样解码（Sampling，Temperature > 0）**：每次按概率分布随机采样 Token。如果评测指标允许尝试多次（例如评估 pass@10 需要采 10 份不同解答），就必须开启采样，否则贪心解码生成的 10 份代码将完全相同。

## 输出提取机制：Log-likelihood 评分 vs 正则提取

模型生成的内容如何转换成对错判断？工程上有两种截然不同的实现方式。

![Log-likelihood判定与生成文本正则提取机制对比](/images/content-rebuild/79d4daeee6843baa/fig-3.png)

### 机制一：对数几率评分（Log-likelihood）

在开源评测工具（如 `lm-evaluation-harness`）中，评测四选一单选题时，通常并不真正让模型自回归生成完整段落，而是利用 Teacher-forcing 计算模型在选项位置输出各个候选字符的对数条件概率。

设题干为 $x$，候选项为 $A, B, C, D$。框架分别计算上下文后接各选项字符的概率：

$$\log P(\text{Option} \mid x)$$

概率最高的候选项即判定为模型的预测答案。

- **优点**：计算速度快，只需单次前向传播，无需自回归解码循环；结果确定，不受模型废话（如“我认为选 B”）影响。
- **局限与工程失效**：
  1. **依赖白盒权限**：必须能读取模型词表维度的 Logits，绝大多数商业闭源 API 无法使用此方式。
  2. **分词器（Tokenizer）敏感**：分词器对空格敏感。例如带前导空格的 `" B"` 和不带空格的 `"B"` 在很多分词表中是两个不同的 Token ID。如果评测脚本拼接前缀时少了一个空格，算出来的概率分布就会完全失真。
  3. **无法结合思维链**：对数几率评测要求模型在题干之后立即给出选项概率，无法让模型先写出几十个词的分析再选答案。

### 机制二：自由生成与正则提取（Free-form Generation + Regex）

该机制贴近真实聊天调用：向模型发送提示词，让模型自由生成回复，并要求模型把最终答案放在固定标记中（例如在末尾写 `#### 42` 或 `\boxed{42}`）。评测程序用正则表达式从文本中提取目标值，再与参考答案比对。

- **优点**：通用性强，适用于任何黑盒 API；允许模型完整展开思维链推导。
- **局限与工程失效**：格式依赖极强。如果模型推理完全正确，但没有按规定使用标记包裹（比如写成了“综上所述，结果为 42”），正则未能捕获，该题就会被判为 0 分。此时测出的不是数学推理能力，而是格式遵循度。

### 代码任务的沙箱执行与 pass@k

代码没有标准固定文本，变量名更换或算法实现差异不影响功能正确性，因此字面比对完全无效。

![代码执行沙箱与pass@k判定机制拓扑](/images/content-rebuild/79d4daeee6843baa/fig-4.png)

代码评测必须在受隔离的沙箱中执行。评测代码能力的常用指标是 **pass@k**：对于每个编程题，让模型采样生成 $k$ 个候选代码，只要其中有至少 1 个代码通过全部单元测试，该题就算解决。

如果在评测时真对每个题目仅采样 $k$ 次，结果的方差会很大。学术界通常采用 OpenAI 提出的**无偏估计法**：每个题目采样生成 $n$ 个样本（$n \ge k$，例如 $n=20$），统计其中通过测试的样本数量 $c$。

从 $n$ 个样本中抽取 $k$ 个，全都不通过的组合数是 $\binom{n-c}{k}$，总抽样组合数是 $\binom{n}{k}$。因此至少有 1 个通过的概率为：

$$\text{pass@k} = \mathbb{E}\left[1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}\right]$$

如果未通过的样本数不足 $k$ 个（即 $n - c < k$），无论怎么抽都必然至少包含 1 个通过样本，概率直接记为 1.0。

下面是计算无偏 pass@k 的标准实现：

```python
def calculate_pass_at_k(n: int, c: int, k: int) -> float:
    """
    计算无偏 pass@k 概率估计
    :param n: 每个题目采样的总代码数 (如 n=20)
    :param c: 样本中通过全部单元测试的代码数量
    :param k: 评估指标选取的尝试预算 (如 k=1, k=5)
    :return: 估计的 pass@k 概率
    """
    if n - c < k:
        return 1.0
    if c == 0:
        return 0.0

    # 展开组合数比值，逐步相乘防止大组合数阶乘溢出:
    # comb(n-c, k) / comb(n, k) = prod_{i=1}^k (n - c - i + 1) / (n - i + 1)
    ratio = 1.0
    for i in range(1, k + 1):
        ratio *= (n - c - i + 1) / (n - i + 1)

    return 1.0 - ratio

# 示例算例验证（示意数据）
# 设采样 20 个样本，通过 3 个，分别估算 pass@1 和 pass@5
print(f"pass@1: {calculate_pass_at_k(20, 3, 1):.4f}")  # 3/20 = 0.1500
print(f"pass@5: {calculate_pass_at_k(20, 3, 5):.4f}")  # 约 0.6009
```

## 数据污染：高分背后的虚假繁荣

在看公开榜单时，必须警惕数据污染（Data Contamination）。

![测试集数据污染机制与扰动检验流程](/images/content-rebuild/79d4daeee6843baa/fig-5.png)

基准测试成立的前提，是测试集对模型而言是未见过的样本。然而，GSM8k、HumanEval 等数据集长期公开存放在 GitHub 和各大网站上。大模型在海量网页预训练时，很容易把这些题目和参考答案作为语料吞入模型；更有甚者，部分团队在针对性微调时直接将测试集或变体题目喂给模型。

### 污染的表现形式

1. **死记硬背**：模型在预训练或微调中记住了完全一致的文本，把题目字面与答案概率直接绑定。一旦题干做细微改动，输出立刻错乱。
2. **格式与句式过拟合**：模型学会了针对特定数据集（如 GSM8k 标注风格）的套路句式，但在遇到表述稍有变化的同类问题时推理能力迅速失效。

### 如何识别与检验污染？

- **金丝雀检验（Canary GUID）**：规范的评测集会在数据集中预埋一段随机生成的唯一标识符（例如 BIG-bench 的 Canary 字符串）。评测时输入 GUID 前缀，如果模型能接着把后续预埋串或题目内容背诵出来，可证实测试集已被吸纳进训练集。
- **实体与数值扰动测试**：
  将 GSM8k 题目中的专有名词和数值做等价替换。例如把“小明买了 3 个笔记本每个 5 元”改为“小李买了 7 个 U 盘每个 13 元”，计算逻辑完全相同。
  如果一个模型在原始题上准确率高达 90%，但在数值扰动后的变形题上准确率跌落到 40% 以下，说明高分主要来自记忆，而非掌握了稳健的符号运算逻辑。

## 为什么学术基准高分无法等同于业务实战能力

许多团队在技术选型时仅看基准跑分，结果上线后差强人意。学术基准和真实业务环境之间存在明确的边界差异。

![学术基准与真实业务环境的多维边界差异](/images/content-rebuild/79d4daeee6843baa/fig-6.png)

1. **单轮确定任务 vs 多轮模糊会话**：
   MMLU 和 HumanEval 都是信息完备、格式规整的单轮输入。但真实业务中，用户提问往往充满指代不明（“刚才那个方案再改改”）、口语化表述与多轮上下文依赖，模型需要具备长程上下文理解与纠偏能力。
2. **闭卷死记事实 vs 开卷依据检索（RAG）**：
   MMLU 考察模型参数内部存了多少静态知识。但企业级系统通常依赖外部知识库与检索增强生成（RAG）。在业务中，模型最关键的能力不是背诵知识，而是**严格基于检索到的参考文档回答、不捏造事实、遇到冲突时识别出处**。相关评测指标可参考[《RAG 系统怎么评测？》](/fundamentals/evaluation-metrics/rag-evaluation.md)。
3. **自由生成 vs 严格受控的工具调用**：
   业务系统通常要求模型输出严格符合 JSON Schema 的结构化指令或调用具体 API（如数据库查询、下单接口）。参数字段哪怕错一个逗号或枚举值都会导致后端服务报错。学术基准不评估这种受控环境下的系统集成韧性。关于应用维度的全流程评测体系，可参考[《AI 应用怎么评测？》](/fundamentals/evaluation-metrics/app-evaluation.md)。

公开基准测试是评估模型通用认知水平的参考标尺，但绝不能简单等同于业务选型结论。理解其背后的评测协议、计分机制与数据污染风险，才能看懂各项跑分数字的真实参考价值。
