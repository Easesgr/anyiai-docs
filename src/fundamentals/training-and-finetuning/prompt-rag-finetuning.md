在开发基于大语言模型（LLM）的业务系统时，团队最常面临的决策分歧是：遇到回答不准确、格式不符合要求或缺少内部知识时，到底应该写更长的提示词（Prompt），搭一套检索增强生成（RAG），还是收集数据去做模型微调（Fine-tuning）？

如果选型判断失误，系统很容易陷入两类困境：要么在提示词里塞满冗长的规则与示例，导致首字延迟（TTFT）大幅上升且输出依然偶发格式崩溃；要么盲目投入算力和人力微调模型，试图把频繁变动的业务数据直接“烧录”进模型参数，结果导致维护成本极高，还伴随灾难性遗忘与知识混淆。在前一讲[/fundamentals/training-and-finetuning/training-pipeline.md](/fundamentals/training-and-finetuning/training-pipeline.md)中，我们梳理了预训练、监督微调（SFT）到偏好对齐的流水线。本讲将从因果机制、输入与参数的变化方式、工程开销出发，建立一套清晰可操作的选型依据。

## 一个贯穿场景：售后技术支持与工单生成系统

为了直观理解三种方案的差异，我们设定一个典型的业务场景：构建一个“企业售后技术支持与工单生成系统”。该系统需要满足两项核心诉求：
1. **获取最新业务事实**：准确回答各型号设备的最新保修期限、故障码定义以及当期维修收费标准。这些政策每个月甚至每周都可能有微调。
2. **输出受控结构化数据**：将排障结论转换为企业内部工单系统接收的特定 JSON 报文，要求包含固定的嵌套字段、状态机枚举值，不能输出任何多余的解释性自然语言。

我们将围绕这个贯穿场景，观察三种技术方案在解决“事实更新”与“行为固化”时的实际表现。

## 三种技术方案的作用层级与信息注入机制

从计算图的角度来看，大语言模型可以抽象为一个自回归条件概率生成器 $P(Y \mid X; \theta)$。其中 $X$ 是输入序列，$\theta$ 是静态权重参数，$Y$ 是逐 Token 解码生成的输出序列。提示词工程、RAG 与微调分别作用于这一关系的不同位置。

![三种技术方案在信息注入层级与参数改变上的机制对比](/images/content-rebuild/d36cb96be6bde283/fig-1.png)

### 1. 提示词工程：纯推理态的上下文激活
* **作用层级**：作用于输入序列 $X$，模型权重 $\theta$ 保持冻结。
* **工作机制**：在输入中加入任务指令、边界约束与少量示例（Few-shot）。在前向传播的自注意力计算（Self-Attention）中，模型基于输入的上下文动态调整各层隐状态的注意力分布。所有指令信息仅保存在当次推理的键值缓存（KV Cache）中，推理请求结束后即被释放。
* **在工单系统中的做法**：在每次用户提问前，拼接上“你是一个工单助手”的角色描述、设备故障码说明以及 3 个标准 JSON 工单样例。

### 2. 检索增强生成（RAG）：外挂检索态的上下文动态扩充
* **作用层级**：依然作用于输入序列 $X$，但引入了外部的数据存储与检索链路。
* **工作机制**：系统根据用户的查询 $q$，先在外部数据库（如向量数据库、倒排索引或关系型数据库）中检索出相关度最高的文档片段 $[d_1, d_2, \dots, d_k]$，将其拼装为增强后的上下文 $X' = [q, d_1, \dots, d_k]$，再交给大模型阅读并生成回答。它将“事实知识的存储”与“语言理解与组织能力”解耦。
* **在工单系统中的做法**：把 500 页的《售后维修政策与故障手册》切片存入数据库。当用户询问“Error-404 怎么报修”时，系统检索出包含 Error-404 的特定条款，塞入 Prompt 让模型参考并作答。

### 3. 监督微调（SFT）：训练态的参数内化重塑
* **作用层级**：直接作用于模型权重 $\theta$，将其更新为 $\theta^* = \theta + \Delta \theta$。
* **工作机制**：准备成对的监督微调数据集 $\mathcal{D} = \{(x_i, y_i)\}$，通过反向传播计算自回归交叉熵损失，借助优化器更新全量或部分参数（如 LoRA 低秩适配器）。微调重塑了模型在特定输入分布下的词表发射概率（Logits），把特定的回答结构或推理习惯固化到参数中。后续在[/fundamentals/training-and-finetuning/sft.md](/fundamentals/training-and-finetuning/sft.md)中，我们将展开其损失函数与训练流程。
* **在工单系统中的做法**：收集 5,000 份经过人工核验的标准工单历史样本，使用 SFT 训练一个 7B 或 14B 参数的小模型，让它在看到自然语言故障描述时，自然输出结构严谨的内部 JSON 报文。

| 维度 | 提示词工程 (Prompt) | 检索增强 (RAG) | 监督微调 (Fine-tuning) |
| :--- | :--- | :--- | :--- |
| **主要作用对象** | 输入序列 $X$ | 输入序列扩增 $X' = [X, D_{\text{retrieved}}]$ | 模型参数 $\theta$ |
| **知识更新时机** | 实时，修改提示词即刻生效 | 准实时，更新外部索引即生效 | 离线，需要重新训练、验证并发布权重 |
| **输出格式受控度** | 依赖指令遵循，复杂格式存在概率性漂移 | 依赖输入中的文档格式与示例约束 | 较高，直接拟合特定语法的词表转移概率 |
| **事实依据可查性** | 弱，依赖模型已有先验 | 强，可显式定位召回的文本片段与元数据 | 较弱，知识隐式分布于网络参数中 |
| **主要系统开销** | 每次推理的长上下文 Prefill 算力 | 向量检索与重排服务开销 + 推理算力 | 离线训练算力 + 独立部署模型实例的显存开销 |

## 知识更新维度：动态业务事实与静态领域表征

在技术选型中，一个常见弯路是试图通过微调让模型“记住”频繁变动的业务事实。从深度学习的信息存储机制来看，事实记忆与行为风格的习得存在明显差异。

![动态实时事实与静态领域表征在处理链路上的因果差异](/images/content-rebuild/d36cb96be6bde283/fig-2.png)

### 为什么微调不适合承载高频变动的事实？
1. **参数纠缠与修改代价**：神经网络中的事实并不是以键值对（Key-Value）形式清晰隔离存储的，而是以分布式方式非线性叠加在多层权重中。如果试图通过微调修改一条价格规则（如“零件 A 降价为 80 元”），模型很难保证在所有提问句式下都稳定命中该数值，同时梯度更新可能对其他无关知识产生微弱扰动，甚至引发已有能力的遗忘。
2. **更新流水线的周转延迟**：微调需要经历数据清洗、标注配对、梯度训练、安全评测以及模型热更新部署。这一链条的周期通常以小时或天为单位计算，无法应对分钟级更新的业务变动（如突发停机通知、实时库存或动态排班表）。

### 为什么 RAG 是动态知识的合适载体？
* **存储与计算解耦**：数据库负责做确定性增删改查，语言模型负责提取与表达。当维修手册更新时，只需更新对应文档的切片和索引，耗时在秒级或分钟级，无需重新调用训练集群。
* **证据可追溯**：在技术支持场景中，工单若引发争议，系统必须能定位“该结论依据哪份维修指引第几页”。RAG 检索出的分块附带明确的元数据（如文档名、版本号、章节 ID），能够为生成内容提供明确的事实来源，便于运维审计。

> **边界条件说明**：RAG 并不等于消除了幻觉。如果检索步骤召回了错误的段落，或者多篇参考文档之间存在矛盾，模型依然可能被上下文中相互冲突的信息误导。RAG 解决的是“知识可更新”与“证据可追溯”，其输出质量仍依赖检索召回率与模型自身的阅读理解能力。

## 行为受控维度：结构化语法与私有协议输出

如果任务的核心目标不是查询最新事实，而是要求模型严格遵守复杂的系统通信报文格式（例如私有 DSL、严格嵌套的 JSON Schema 或受控 SQL），提示词方案与微调方案的表现便会显现分界。

![不同复杂度格式遵循任务在提示词工程与微调下的可靠性对比](/images/content-rebuild/d36cb96be6bde283/fig-3.png)

### 提示词工程的局限性
在提示词中提供少样本示例（Few-shot）和结构定义，是早期验证的有效手段。但在复杂长序列生成中，单纯依赖 In-context Learning 存在以下瓶颈：
1. **长输出过程中的约束衰减**：自回归生成是逐 Token 进行的。当输出长度逐渐增加，模型后续生成的 Token 主要依赖前文已经生成的输出，初始提示词中语法格式的权重影响力会相对分散，可能在末尾出现字段缺失、括号未闭合或额外附带解释性废话。
2. **私有标记的先验概率低**：如果输出目标包含企业私有的协议标记或枚举缩写，通用基础模型在预训练阶段极少见过这些组合。仅靠上下文中的两个示例，模型在采样时选择这些特定转移路径的概率相对较低，容易退回到通用的自然语言表达习惯。

### 微调如何重塑输出行为？
* **重塑词表发射概率**：在经过针对性标注的数据集上进行 SFT 后，模型在遇到特定任务前缀时，输出特定结构语法符号的条件概率被直接提升。
* **压缩输入长度**：微调后无需在每次请求中附带数百甚至数千 Token 的 Few-shot 示例，大幅降低了推理阶段 Prefill 的计算量。

> **说明**：在通用 JSON 格式控制上，现代推理框架（如 vLLM、SGLang）广泛支持基于有限状态机（FSM）或语法树（Grammar-guided decoding）的约束采样技术，可以在解码阶段强制输出合规语法。但对于包含私有推理路径、特定字段命名逻辑和业务枚举映射的任务，微调依然是改变生成习惯的有效手段。

## 工程成本与延迟核算：一个量化示例

方案选型不能脱离计算基础设施的成本。我们使用前述工单系统的数据规模进行一组对比算例。

![Prompt、RAG 与微调在端到端系统延迟与算力成本上的结构分布](/images/content-rebuild/d36cb96be6bde283/fig-4.png)

### 假设条件（示意场景）
* **请求量**：每天 10,000 次请求，业务并发约 10~20 QPS。
* **单次请求输入**：用户提问约 100 Tokens。
* **单次输出**：生成的工单报文约 200 Tokens。
* **上下文填充差异（注意工作量前提对齐）**：
  * 纯提示词方案：包含 3 个完整工单示例与排障指引，系统提示词长 2,900 Tokens，总输入为 3,000 Tokens（同时承担动态政策提供与格式规范）。
  * RAG 方案：检索召回 2 个相关手册片段（共 500 Tokens），加上简短指令 100 Tokens，总输入为 700 Tokens（由检索负责事实注入，提示词负责格式规范）。
  * 微调方案：无需 Few-shot 示例，仅保留任务标识与用户输入，总输入为 150 Tokens。**注意前提假设**：该 150 Tokens 测算假定此环节仅承担“将排障结论转换为工单 JSON”的纯格式转换子任务；若在端到端流程中微调模型同样需要依据当期变动政策排障，因高频事实不能固化在参数中，仍需配合 RAG 检索并注入这 500 Tokens 事实片段，此时实际总输入约为 650 Tokens。

### 成本与延迟构成对比

```
纯长提示词方案:
输入: 3,000 Tokens ──────────> [模型 Prefill 耗时较高] ──> [Decode 200 Tokens]
(显存占用随并发线性叠加，若未命中 Prompt Cache，整体吞吐受限)

RAG 方案:
用户输入 ──> [Embedding 编码 (~20ms)] ──> [向量检索+重排 (~40ms)]
          ──> 组合上下文 (700 Tokens) ──> [模型 Prefill 适中] ──> [Decode 200 Tokens]
(增加了检索服务的网络交互，但降低了模型前向计算的 Token 量)

微调专属小模型方案:
用户输入 ──> 极简输入 (150 Tokens) ──> [模型 Prefill 极短] ──> [Decode 200 Tokens]
(端到端延迟低，但前期需要数据标注、训练成本与独立的模型部署实例)
```

#### 1. 纯提示词方案
* **日均输入 Token 量**：$10,000 \times 3,000 = 3 \times 10^7$ Tokens。
* **延迟特性**：Prefill（首字延迟 TTFT）相对较高。如果推理引擎未命中前缀缓存（Prompt Cache），长文本前向计算会占用显著的计算显存。
* **前期投入**：极低。只需编写与调优提示词模板，无需额外基础设施。

#### 2. RAG 方案
* **日均输入 Token 量**：$10,000 \times 700 = 7 \times 10^6$ Tokens（输入 Token 量相比纯提示词方案降低了约 76.7%）。
* **延迟特性**：增加了检索阶段延迟（Embedding 向量化 + 索引搜索 + 重排约 50~80ms），但由于 Prefill Token 显著变短，总体首字延迟可能比未缓存的长 Prompt 方案更低。
* **前期与运维投入**：中等。需要搭建并维护向量数据库、切分清洗管线（ETL）以及检索服务。

#### 3. 监督微调方案（微调 7B / 14B 小模型）
* **日均输入 Token 量**：若按纯报文格式转换子任务测算，为 $10,000 \times 150 = 1.5 \times 10^6$ Tokens；若面向端到端排障需结合 RAG 注入最新政策，则日均输入为 $10,000 \times 650 = 6.5 \times 10^6$ Tokens（相较 RAG 方案省去的是通用格式引导的 Token，而非动态事实 Token）。
* **延迟特性**：若为纯格式转换，Prefill 计算极短，KV Cache 占用小，单卡支持更高并发；若为微调+RAG 协同，则在短 Prefill 基础上增加外挂检索耗时。
* **前期与运维投入**：较高。前期需构建数千条合规工单训练对，消耗 GPU 算力完成微调与评估；上线后需要单独维护专有模型的部署服务。

```python
# 伪代码：评估三种方案在组装与调用环节的流程差异

def generate_support_ticket(user_query: str, pipeline_mode: str):
    if pipeline_mode == "prompt_only":
        # 携带大量少样本示例以保持格式与规则
        system_prompt = load_few_shot_examples()  # ~2900 tokens
        full_input = f"{system_prompt}\n\n用户问题: {user_query}"
        return base_model.generate(full_input)
    
    elif pipeline_mode == "rag":
        # 动态检索关联段落，压缩上下文长度
        query_vector = embed_model.encode(user_query)
        retrieved_docs = vector_store.search(query_vector, top_k=2)  # ~500 tokens
        rag_prompt = format_rag_context(user_query, retrieved_docs)
        return base_model.generate(rag_prompt)
    
    elif pipeline_mode == "finetuned":
        # 模型已通过微调拟合了输出格式与排障行为；若业务涉及最新变动政策，
        # 应走微调+RAG（拼接检索上下文）；此处仅演示纯格式与结构生成子任务
        minimal_input = f"[GENERATE_TICKET]\nQuery: {user_query}"
        return finetuned_model.generate(minimal_input)
```

## 架构协同：工程中的组合模式

在实际生产系统中，Prompt、RAG 与微调并非排他性选择，而是经常协同配合使用。

![RAG 与微调协同落地的端到端工业架构流向](/images/content-rebuild/d36cb96be6bde283/fig-5.png)

### 组合模式一：Prompt + RAG（主流的知识问答组合）
这是目前通用知识问答中最广泛采用的形态：
* **分工**：RAG 负责动态拉取最新、未见过的外部参考资料；Prompt 负责定义输出风格、安全回复边界（如“若参考文档未提及，请回答不知道”）以及引导输出排版。
* **适用场景**：技术文档问答、跨版本产品咨询、HR 制度库助手。

### 组合模式二：微调 + RAG（专业领域的结构化助手）
在严苛的专业场景（如医疗病历整理、金融审计、或本例中的设备故障工单）中，常常将微调与 RAG 结合：
1. **微调解决“表达规范与推理步骤”**：微调一个轻量模型，使其熟练掌握特定领域的技术词汇、意图解析逻辑以及内部工单的严格 JSON 格式。
2. **RAG 解决“事实依据”**：通过 RAG 实时检索设备当前的固件版本更新日志、保修政策变动或特定零件的当期库存。
3. **组合收益**：微调后的模型能够更精准地重写查询（Query Rewriting）并遵循格式，而 RAG 保证了生成的保修结论依据的是当期最新文档，不必为了修改一条保修政策去重新训练模型。

## 选型反面模式与决策矩阵

在方案规划阶段，识别常见的误区有助于避免资源浪费。

![常见技术选型反面模式拦截与正确路径引导](/images/content-rebuild/d36cb96be6bde283/fig-6.png)

### 常见反面模式
* **误区 1：通过微调强行灌入高频变动的价格或库存数据**
  * *现象*：每周训练一次模型试图更新商品价格，结果新旧价格在参数中混杂，生成时经常产生数值混乱，且训练成本居高不下。
  * *建议*：高频变动的数据应交给关系型数据库或检索库，在推理时通过上下文或工具调用（Tool Calling）注入。
* **误区 2：在超长 System Prompt 中堆叠数十个复杂 JSON 示例**
  * *现象*：输入 Token 费用居高不下，且遇到长篇复杂故障描述时，输出的尾部字段仍偶发格式漂移。
  * *建议*：如果输出格式是固定的私有协议，使用高质量数据微调小参数模型，或引入结构化采样解码库（如 Outlines 等基于正则/FSM 的解码工具）。
* **误区 3：认为上了 RAG 就不需要文本切分调优**
  * *现象*：直接将未清洗的 PDF 按固定长度粗暴切分存入向量库，导致检索片段断章取义，大模型根据破碎片段产生严重事实扭曲。
  * *建议*：RAG 的核心瓶颈通常在检索召回与重排质量上，必须结合文档层级切分、混合检索（BM25 + 向量）以及 Reranker 重排。

### 技术选型评估矩阵

| 业务核心诉求 | 推荐优先尝试方案 | 辅助协同手段 | 不推荐的做法 |
| :--- | :--- | :--- | :--- |
| 知识频繁变动（天/周级），要求给出确切参考来源 | **RAG** | 提示词模板约束 | 试图通过频繁微调注入事实 |
| 严格遵循特定的私有结构、DSL 或专用代码风格 | **微调 (SFT)** | 语法约束采样 (Grammar-guided) | 仅靠零样本（Zero-shot）提示词 |
| 概念验证（PoC）阶段，业务逻辑尚在快速探索 | **提示词工程** | Few-shot 少量示例 | 早期投入大量标注与微调算力 |
| 专有领域严苛格式 + 依赖动态实时病历/设备数据 | **微调 + RAG** | 任务意图解析提示词 | 仅依靠通用大模型裸跑 |
| 降低高并发系统的首字延迟（TTFT）与上下文冗余 | **微调专属小模型** | Prompt Cache（前缀缓存） | 在单次请求中堆叠数千 Token 冗余规则 |

明确了三种方案的技术边界后，如果你的业务确实需要通过微调来固化特定的行为、输出语法或推理习惯，就需要进一步掌握有监督微调的数据组织形式与优化过程。下一篇[/fundamentals/training-and-finetuning/sft.md](/fundamentals/training-and-finetuning/sft.md)中，我们将深入有监督微调（SFT）的具体实现细节。
