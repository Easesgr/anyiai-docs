在构建大语言模型应用时，开发者最常遇到的困惑往往不是代码如何编写，而是如何选择技术路线：面对一个新需求，究竟应该写 Prompt、搭建知识检索（RAG），还是收集数据做微调（SFT）？如果决定微调，全量微调、LoRA 和 QLoRA 的显存开销到底该怎么算？模型回答不听指挥时，是该洗数据、改损失函数，还是做 DPO 偏好对齐？

大模型的训练不是单次执行的黑盒算法，而是一条由不同优化目标和数据分布拼接而成的数据处理流水线。本文作为本板块的导读指南，通过一个贯穿始终的业务示例，系统拆解模型从“理解语言”到“执行指令”再到“符合人类偏好”的完整过程，并给出 8 篇专题文章的阅读路线。

## 一个贯穿示例：打造“电商客服工单助手”

为了直观理解各个训练阶段的作用，我们设想这样一个任务：为电商平台打造一个专门的**工单智能助手**。该助手需要满足三个要求：
1. **掌握通用语言与电商常识**：理解什么是退换货、物流单号、运费险以及用户的各种日常表达口吻。
2. **严格遵循任务指令并输出固定格式**：当客服人员输入用户对话记录时，助手必须直接提取出结构化信息，输出合法的 JSON 格式工单，严禁附加多余闲聊。
3. **语气得体并符合业务规范**：面对愤怒投诉的用户，助手不能推卸责任或与用户争吵，必须在安抚情绪的同时严谨核查规则，符合客服合规安全红线。

要实现这三个目标，需要分别依赖三个不同的训练阶段：

- **阶段一：预训练（Pre-training）**。让模型阅读数万亿 Token 的无标注互联网文本，学会因果语言建模（通过上文预测下一个 Token）。在这一步，模型学会了语法、百科事实和常识推理，但它此时只是一个“续写机”，你给它一句“请提取以下退货信息”，它可能会接着续写“并发送给主管签字审核……”，而不会真正停下来执行任务。
- **阶段二：监督微调（Supervised Fine-Tuning, SFT）**。我们准备数万条精标注样本，格式为 `<用户指令, 输入对话, 目标工单JSON>`。在训练中，模型仅在目标 JSON 回答部分计算交叉熵损失（Prompt 掩码机制）。经过这一步，模型从“接话员”变成了“听指令的助手”，学会看到特定指令就输出对应的结构化数据。
- **阶段三：偏好对齐（RLHF / DPO）**。模型虽然会输出工单，但遇到边界情况（如用户恶意诱导其赠送优惠券）可能会产生幻觉或违规承诺。我们构造由成对数据组成的偏好集（一条回答更符合合规规范，另一条回答敷衍或越权），利用强化学习（PPO）或直接偏好优化（DPO），让模型在多种合理表达中更倾向于输出安全合规、语气稳重的回答。

## 关键技术对比与显存机制剖析

在开展模型训练之前，需要准确理解三组经常被混淆的核心技术概念及其物理资源开销：

![训练与微调三对核心技术机制横向对比](/images/content-rebuild/5c8e357c3e0455b6/fig-2.png)

### 1. 训练显存构成的精确量化

许多开发者误以为“能加载 7B 模型的显卡就能训练 7B 模型”，这是混淆了**推理显存**与**训练显存**。

在推理时，显存主要由模型静态权重和自回归生成的动态键值缓存（KV Cache）构成。而在训练时，显存占用包含四个独立部分：
- **模型参数（Model Weights）**：存储当前模型参数。
- **梯度（Gradients）**：反向传播计算出的每个参数的偏导数，尺寸与可训练参数量完全一致。
- **优化器状态（Optimizer States）**：以标准 AdamW 优化器为例，需要为每个可训练参数维护一阶动量（Momentum）和二阶动量（Variance），在混合精度训练中还需要保留一份 FP32 精度的主权重备份。
- **激活值（Activation Memory）**：前向传播过程中各层注意力与 MLP 计算的中间结果，必须保存在显存中以便反向传播时链式求导，激活值大小与序列长度、批次大小（Batch Size）和注意力头数直接正相关。

#### 算例对比：7B 模型全量微调 vs LoRA 微调显存（静态状态开销）

假设采用业界通用的 BF16 混合精度训练，模型参数量为 $N = 7 \times 10^9$（7B）：
- **全量微调（Full Fine-Tuning）**：
  - 模型权重（BF16）：$7 \times 10^9 \times 2 \text{ 字节} = 14\text{ GB}$
  - 梯度（BF16）：$7 \times 10^9 \times 2 \text{ 字节} = 14\text{ GB}$
  - AdamW 状态（FP32）：一阶动量（4 字节）+ 二阶动量（4 字节）+ 主权重备份（4 字节）= $7 \times 10^9 \times 12 \text{ 字节} = 84\text{ GB}$
  - **静态显存合计**：$14 + 14 + 84 = 112\text{ GB}$。这意味着尚未计算激活显存和中间通信缓存，单张 80GB 的 A100/H100 显卡就已经无法容纳，必须使用多卡张量并行（TP）或 ZeRO/FSDP 显存切分技术。
- **LoRA 低秩微调**：
  - 主模型权重冻结（BF16）：仍然占用 $14\text{ GB}$。
  - 假设仅微调注意力层与 MLP 层的部分权重，低秩分支的可训练参数量仅占全模型的 0.2%（约 1400 万参数）：
    - 增量参数与梯度：约 $14 \times 10^6 \times (2 + 2) \text{ 字节} \approx 0.056\text{ GB}$
    - AdamW 优化器状态：约 $14 \times 10^6 \times 12 \text{ 字节} \approx 0.168\text{ GB}$
  - **静态显存合计**：约 $14.23\text{ GB}$。在单张 24GB 显存的消费级显卡（如 RTX 3090/4090）上，配合激活重计算（Activation Checkpointing），即可顺利完成训练。

### 2. 三组核心概念的机制边界

| 对比维度 | 预训练（PT） vs 监督微调（SFT） | 全量微调 vs 低秩微调（LoRA） | 强化学习对齐（RLHF） vs 直接偏好优化（DPO） |
| :--- | :--- | :--- | :--- |
| **核心差异定位** | **训练目标与数据阶段差异** | **参数更新范围与显存占用差异** | **对齐优化算法与架构复杂度差异** |
| **数据形态** | 海量无标注纯文本，滑动窗口切分成连续 Token 序列 | 格式相同：均为 `<Prompt, Response>` 结构化标注对 | RLHF 需单 Prompt 在线 Rollout；DPO 使用静态离线构建的 `<Prompt, Chosen, Rejected>` 对 |
| **参数更新机制** | PT 基于因果掩码对全序列逐位置自回归预测并计算交叉熵；SFT 对 Prompt 施加损失掩码，仅对 Response 部分反向传播 | 全量微调更新全参数 $W$；LoRA 冻结 $W$，仅训练低秩分解外挂分支 $\Delta W = B \times A$ | RLHF 需显式训练 Reward 模型并通过 PPO 策略更新；DPO 将偏好损失直接推导为隐式奖励，直接更新 Policy |
| **显存与算力门槛** | 极高（百卡/千卡集群，以月计），需数万亿 Token 语料 | 全量微调 7B 模型需上百 GB 显存；LoRA 7B 静态显存仅需约 15GB，单卡即可运行 | 经典 RLHF 需在内存中调度或通信 4 个模型（Actor/Critic/Reward/Ref）；DPO 仅需调度当前 Policy 与只读 Reference 模型 |
| **典型失效风险** | 训练发散（Loss Spike）、梯度爆炸、算力开销巨大 | 全量在极小数据集上极易破坏基座泛化能力；LoRA 若秩 $r$ 设过小可能导致表达容量不足 | RLHF 面临强化学习训练超参敏感、奖励黑客（Reward Hacking）；DPO 对数据标注质量敏感，容易偏向过长回复 |

## 业务技术选型指南

面对具体工程任务，盲目启动模型训练往往会增加维护负担。建议按照以下顺序进行评估决策：

![业务场景技术选型决策图](/images/content-rebuild/5c8e357c3e0455b6/fig-3.png)

1. **首选评估：是否必须修改模型参数？**
   - **知识库更新频繁、需要保留权威引用来源**：优先使用 **RAG（检索增强生成）**。例如企业内部政策规章、实时物流状态等，微调无法保证 100% 消除事实幻觉，而检索能提供溯源链接与精确权限隔离。
   - **仅需改变思考逻辑或引导风格**：优先通过 **Few-shot Prompt Engineering** 解决。在 Prompt 中注入格式范例与约束，验证基座模型的原生理解上限。
2. **次级决策：当模型必须微调时，如何选择参数更新策略？**
   - **输出格式强约束、语法严格（如 SQL/JSON/特定代码 DSL）**：执行 **SFT（监督微调）**。当基座模型即便写了详细 Prompt 仍频繁漏字段或语法解析失败时，微调能将格式偏置内化到权重中。
   - **硬件资源充足且需要深度注入特定领域语言习惯**：在拥有大规模高质量语料的前提下，可考虑全量微调。
   - **显存与算力有限（单卡或有限云端实例）**：推荐采用 **LoRA 或 QLoRA**。LoRA 还能通过在同一个冻结底座上切换不同适配器权重（Adapters），低成本服务多业务场景。
3. **最终优化：是否需要偏好对齐？**
   - **模型已经学会遵循指令，但输出语气偏激、存在合规安全隐患或难以在两难回答中做权衡**：引入 **DPO（直接偏好优化）**。DPO 省去了搭建复杂强化学习环境的工程门槛，配合清洗严谨的对比偏好数据，能快速收敛安全边界。
