大语言模型在预训练阶段读过了海量的网页、图书和代码，已经掌握了基础的语言语法和通用的常识关系。在进入监督微调（Supervised Fine-Tuning，简称 SFT）时，训练的目标通常不是让模型硬背全新的百科知识，而是**教会模型理解并服从人类的提示指令、采用符合业务预期的格式与语气进行回复**。这一现象在学术界常被称为“表面对齐假设”（Surface Alignment Hypothesis）。

如果用于微调的数据混乱、充满了格式残缺、事实矛盾或重复模板，模型不仅学不会规范的操作行为，还可能破坏基座原本的语言连贯性与推理能力。本文以一个“金融合规审核助手”的实际构建过程为例，系统梳理 SFT 数据的组织规范、输入掩码原理、四步清洗漏斗、任务配比以及合成数据的验证机制。

## SFT 数据的标准组织规范与字段定义

微调语料在磁盘上通常保存为 `JSON` 或按行读取的 `JSONL` 文件。根据任务复杂度的不同，业界主流微调框架（如 Hugging Face TRL、LLaMA-Factory 等）主要采用两类表示规范：单轮指令格式与多轮消息格式。

### 1. 单轮指令格式（Alpaca Style）

单轮格式适合一次问答即完成交付的任务，例如文本分类、摘要提取、翻译或单轮信息抽取：

```json
{
  "instruction": "根据以下金融理财产品描述，判断其宣传语是否合规，并给出修改建议。",
  "input": "本产品为R2稳健型理财，年化收益保底6%，保本保息，适合追求零风险的投资者。",
  "output": "【审核结果】：不合规。\n【问题说明】：根据资管新规要求，理财产品严禁承诺‘保本保息’、‘保底收益’或‘零风险’。\n【修改建议】：建议修改为‘本产品为R2稳健型理财，业绩比较基准为年化3.5%~4.2%，不保证本金和收益，请审慎投资。’"
}
```

- `instruction`：任务动作定义，告诉模型要扮演什么角色、执行什么规则。
- `input`：待处理的客观输入内容。如果没有额外的输入上下文（例如开放式问答），该字段可以留空。
- `output`：期望模型严格给出的标准回答。

### 2. 多轮对话格式（Messages / ChatML Style）

多轮格式是当前应用更广的标准格式。它用列表结构记录了系统设定、用户输入与模型回复的交替过程，能够保留多轮追问的上下文，也便于融入工具调用（Tool Calling）的记录：

```json
{
  "messages": [
    {
      "role": "system",
      "content": "你是一名严格遵循金融监管法规的合规审查助手，回复需结构清晰，指出违规条款并给出整改意见。"
    },
    {
      "role": "user",
      "content": "业务部门想宣传‘年化保底收益6%’，能过审吗？"
    },
    {
      "role": "assistant",
      "content": "不能过审。资管新规明确禁止金融机构承诺保本保收益。"
    },
    {
      "role": "user",
      "content": "如果加上‘过往业绩表现’的前缀，是不是就可以写了？"
    },
    {
      "role": "assistant",
      "content": "仍然存在合规风险。宣传过往业绩时，必须明确标注‘过往业绩不代表未来收益’，且不得混淆历史业绩与预期收益率，更不可使用‘保底’字样。"
    }
  ]
}
```

### 3. 核心机制：Prompt 损失掩码（Loss Masking）

在自回归语言模型中，前向传播的目标是预测下一个出现的 Token。如果在微调时将用户提示词和期望回复一视同仁地计算交叉熵损失，就会让模型花费梯度更新的开销去学习“用户会怎么提问”，甚至去背诵固定的 System Prompt，这严重偏离了微调的初衷。

![微调输入序列的Prompt掩码与Label映射关系](/images/content-rebuild/572e403a3fa9334a/fig-1.png)

自回归因果语言模型的前向任务是“给定前文预测下一个 Token”（Next Token Prediction，即依据 $x_{<t}$ 预测 $x_t$）。在具体工程实现中（如 Hugging Face CausalLM），计算损失时会将前向输出的 logits 去掉最后一个位置 `logits[:, :-1, :]`，并将 labels 去掉第一个位置 `labels[:, 1:]` 进行错位对齐（Shift）。这意味着是由 Prompt 最后一个 Token 位置的隐藏状态去预测 Assistant 的第 1 个 Token；Assistant 内部各 Token 依次向后预测，直至输出终止符（EOS）。

因此，数据工程中只需构建与 `input_ids` 严格等长的 `labels` 序列，将 System Prompt、User 提问以及前置模板标记位置赋值为 `-100`。在 PyTorch 的交叉熵损失函数中，`-100` 是默认的忽略索引（`ignore_index`），这些位置的前向预测误差不会产生梯度反向传播。

损失函数的数学表达为：

$$\mathcal{L}_{SFT}(\theta) = -\frac{1}{\sum_{t=1}^{T} m_t} \sum_{t=1}^{T} m_t \cdot \log P_\theta(x_t \mid x_{<t})$$

其中 $m_t \in \{0, 1\}$ 是掩码标记：
- 当目标位置 $t$ 属于 System 或 User 文本时，$m_t = 0$，标签设为 `-100`，不参与梯度计算。
- 当目标位置 $t$ 属于模型生成的回复（Assistant）时，$m_t = 1$，模型必须准确预测该位置的 Token 并计算梯度更新参数。

## 高质量微调数据的三要素

微调并不是收集的数据越多越好。低质量或分布单一的数据即使堆叠数万条，也会导致模型输出呆滞甚至过拟合。构建数据集必须兼顾以下三个要素：

![高质量微调数据的三核心要素体系](/images/content-rebuild/572e403a3fa9334a/fig-2.png)

1. **指令多样性（Diversity）**：
   - **句式与表达多样**：用户在提问时不会使用固定模板。针对同一审核需求，数据中应同时存在“帮忙看看这个合规吗”、“请审核如下文案”、“根据合规要求给出评估意见”等多种表达。
   - **难度与长度梯次分布**：训练集应覆盖简短判别、长篇文案整改、跨轮次追问以及边界拒答（例如用户诱导模型违背合规底线时的明确拒绝）。
2. **格式一致性（Format Consistency）**：
   - 如果业务要求输出严格的 JSON 字符串，那么数据集中所有的 Assistant 回复都必须符合统一的 Schema 规范，不能有的样本输出 Markdown 代码块，有的直接输出纯文本，避免破坏客户端解析。
3. **事实正确性（Factuality）**：
   - 监督微调会大幅强化模型对特定陈述的生成概率。若训练集给出的审核结论存在事实性错误，模型在推理时会展现出高度确信的错误幻觉。如果业务需要依靠精准的动态事实支撑决策，应当配合 [RAG 检索增强技术](/fundamentals/training-and-finetuning/prompt-rag-finetuning.md)，而不是让微调参数强行记忆不稳定的静态事实。

## 微调数据清洗漏斗：四步过滤流水线

企业内部沉淀的工单系统记录、客服聊天日志或历史审核单据，通常包含大量的拼写错误、无效占位符与格式垃圾。将原始日志变为可微调的数据集，通常需要经过四步清洗：

![四阶微调数据清洗漏斗流程图](/images/content-rebuild/572e403a3fa9334a/fig-3.png)

### 步骤 1：规则与长度截断（Rule-based Filtering）

- **长度边界过滤**：剔除有效 Token 数过短的样本（如提问只有“在吗”、“测试”，回复只有“好的”），避免无效样本稀释有效梯度；同时剔除超过训练最大上下文窗口（如截断长度 4096）的超长样本，防止模型在推理时产生未闭合的断句。
- **乱码与特殊符号清理**：通过正则表达式清理未解析的 HTML/XML 标签、转义乱码（如 `\x00`、`&nbsp;`）以及无意义的连续重复字符（如连续 20 个问号）。

### 步骤 2：模糊与语义去重（Deduplication）

高频重复的问答会导致模型严重过拟合，使其对微调模式产生路径依赖。

- **精确去重**：通过对整段文本进行哈希计算（如 SHA-256），剔除内容完全一致的重复记录。
- **MinHash + LSH 模糊去重**：对输入指令提取 N-gram 特征，构建 MinHash 签名并利用局部敏感哈希（LSH）将相似文本分桶。对于 Jaccard 相似度高于预设阈值（例如 0.85）的样本对，仅保留质量最高或人工确认过的一条。

### 步骤 3：困惑度（PPL）异常筛查

困惑度（Perplexity, PPL）是语言模型对输入序列概率的预测指标：

$$\text{PPL}(X) = \exp\left(-\frac{1}{N}\sum_{i=1}^{N} \log P(x_i \mid x_{<i})\right)$$

使用一个轻量的开源基座模型（例如 Qwen2.5-0.5B 或 LLaMA3-8B）对候选回复文本计算 PPL：
- **PPL 极高**：文本通常包含严重的语法颠倒、生僻字符拼接或乱码翻译，模型无法按常规语法理解，应直接剔除。
- **PPL 极低**：文本通常是极度单调的机器套话（例如大段重复的免责声明），需做抽检以防降低训练样本的有效信息密度。

### 步骤 4：隐私与敏感信息脱敏（Safety & PII Masking）

利用命名实体识别（NER）工具结合规则匹配，对员工姓名、电话号码、身份证件、银行账户、内部系统密钥（API Key）等个人可识别信息（PII）进行替换占位（如用 `[PHONE_NUMBER]` 占位），防止敏感数据被硬编码进微调权重。

## 任务配比策略与通用回放机制

微调垂直模型时，如果只把几万条垂直场景数据送入模型训练，往往会出现**灾难性遗忘（Catastrophic Forgetting）**：模型虽然学会了当前的业务术语，但基座原本具备的基础对话、逻辑推理以及理解复杂长指令的能力大幅退化。

![垂直任务微调中的通用数据回放混合机制](/images/content-rebuild/572e403a3fa9334a/fig-4.png)

### 1. 通用数据回放（Replay）配比

解决遗忘的有效手段是采用数据回放策略，在业务微调集中混入一定比例的高质量通用指令遵循数据：

- **垂直领域专业数据（70% ~ 85%）**：负责让模型掌握当前业务的操作流程、术语规范与格式要求。
- **通用多轮对话数据（5% ~ 15%）**：维持模型的语言流利度、上下文代词指代和多轮对话状态转移能力。
- **逻辑推理与代码数据（5% ~ 10%）**：维持模型的思维链结构化思考与细致指令遵循能力。
- **安全合规与拒答数据（2% ~ 5%）**：防止业务训练破坏模型基座原有的安全底线，保持边界防御能力。

### 2. 样本随机打散（Shuffle）

在构建数据加载器（DataLoader）时，必须将所有类别的数据彻底随机打散。如果按批次集中训练（例如前三天全训垂直业务，后一天全训通用对话），参数梯度会被集中拉偏。此外，采用 Sequence Packing（将短样本拼接并在注意力中利用特定 Mask 隔离）可以显著减少填充（Padding）所浪费的显存与算力。

## 合成数据与自指令生成（Self-Instruct）闭环

冷启动阶段往往缺乏足够的人工精标样本。利用大模型扩充合成数据（Synthetic Data）已是常见手段，但必须建立确定性的验证闭环，否则模型会学习源模型的幻觉内容。

![Self-Instruct合成微调数据生成与多重校验闭环](/images/content-rebuild/572e403a3fa9334a/fig-5.png)

一套严谨的自指令扩充闭环包含五个环节：

1. **种子指令库构建**：由业务专家人工精选并编写 100~200 条覆盖各类复杂场景的“金标样本”。
2. **指令泛化与扩充**：利用指令遵循能力较强的大模型，根据种子样本生成相似任务但带有不同条件约束的衍生提问与解答。
3. **执行环境检验**：
   - 如果生成的是 SQL、Python 或结构化工具调用，**必须送入沙箱环境运行**。运行报错或结果不符预期的样本直接丢弃。
   - 如果生成的是 JSON 或 XML 格式，必须经过严格的 Schema 验证器，格式校验失败的直接剔除。
4. **模型打分筛查（LLM-as-a-Judge）**：设定结构化打分提示词，从“事实准确性”、“指令完整度”、“格式符合度”三个维度评分，淘汰低分样本。
5. **人工专家抽样复核**：定期对合成数据按比例抽检，并将修改后的高质量样本回流到种子指令库中，迭代修正提示词。

## 小样本与海量数据的权衡：LIMA 效应与前提

Meta 提出的 LIMA（Less Is More for Alignment）实验表明：在基座模型足够强的前提下，仅用 1,000 条高质量的指令数据进行微调，模型就能表现出令人满意的对齐效果。

![表面对齐假设与新知识注入的能力边界权衡](/images/content-rebuild/572e403a3fa9334a/fig-6.png)

### LIMA 效应的适用前提与工程边界

开发者不能把 LIMA 实验误解为“任何垂直场景只要几百条数据就足够”，必须区分其成立的前提：

1. **适用场景：激发已有知识，学习风格与格式**。
   - 基座模型在[预训练阶段](/fundamentals/training-and-finetuning/pretraining-deep.md)就已经学习过相关知识（如金融、法律、常见公文写法）。此时使用 500~1,000 条高标准数据，模型能迅速学会业务指定的段落结构、语气风格与判定逻辑。
2. **失效场景：向模型灌输全新的未知事实**。
   - 如果业务涉及企业内部专有协议、2025 年新修订的内部文件或冷门专业代码，基座模型的预训练权重中完全没有这些词元关联。几百条 SFT 样本只能让模型记住字面模板，在实际推理时面对微小的参数扰动就会胡言乱语。这种场景必须依赖领域持续预训练（Continual Pre-training）或搭配知识库检索（RAG）协同解决。

在工程实践中，推荐优先构建 500~1,000 条高质量验证集跑通微调闭环并评估收益；若模型能较好地遵循格式但缺乏泛化能力，再逐步扩展任务覆盖面，切忌未经清洗就灌入数十万条脏数据。

## 最小工程实验：构建 Token 损失掩码

以下 Python 示例演示了如何基于 Hugging Face 的分词器将标准多轮对话处理为训练所需的 `input_ids` 与 `labels`，并使用 `-100` 将用户提问区域准确遮蔽。

```python
from transformers import AutoTokenizer

# 以开源分词器为例（支持 ChatML 模板）
tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")

messages = [
    {"role": "system", "content": "你是一名金融合规审核助手。"},
    {"role": "user", "content": "宣传材料中写‘年化保底收益6%’是否合规？"},
    {"role": "assistant", "content": "不合规。根据监管要求，资管产品严禁承诺保本保收益。"}
]

# 1. 提取 Prompt 部分并应用 ChatML 模板（带有生成引导符 assistant 前缀）
prompt_messages = messages[:-1]
prompt_text = tokenizer.apply_chat_template(
    prompt_messages,
    tokenize=False,
    add_generation_prompt=True
)
prompt_ids = tokenizer.encode(prompt_text, add_special_tokens=False)

# 2. 提取待学习的 Assistant 回复，并加上终止符
response_text = messages[-1]["content"] + tokenizer.eos_token
response_ids = tokenizer.encode(response_text, add_special_tokens=False)

# 3. 拼接输入序列并构建损失掩码
# Prompt 部分使用 -100 忽略，Response 部分保留真实 Token ID
input_ids = prompt_ids + response_ids
labels = [-100] * len(prompt_ids) + response_ids

print(f"总 Token 数: {len(input_ids)}")
print(f"忽略损失的 Token 数 (Prompt 区域): {labels.count(-100)}")
print(f"参与梯度计算的 Token 数 (Assistant 区域): {len(labels) - labels.count(-100)}")

assert len(input_ids) == len(labels), "input_ids 与 labels 必须严格等长"
```

通过对训练数据进行规范化封装与损失掩码处理，模型能够在梯度反向传播中集中学习回复策略。关于如何在显存受限的硬件上进一步降低参数更新的显存消耗，可阅读 [LoRA 与 QLoRA 参数高效微调](/fundamentals/training-and-finetuning/lora-qlora.md)。
