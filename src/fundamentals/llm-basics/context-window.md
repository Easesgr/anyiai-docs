![上下文窗口的计算机制与物理约束封面图](/images/content-rebuild/932736675f3aa479/cover.png)

在上一讲[大语言模型是怎么理解文本的](/fundamentals/llm-basics/token-to-context.md)中，我们了解了文本如何被切分成 Token，并通过多层自注意力机制转换为语义向量。

实际使用大模型时，你很快会遇到一个直接限制：模型单次能接收的文本长度是有限的。假设你手头有一份 10 万字（约 15 万 Token）的项目工程文档，想让模型从中找出某个具体的接口配置项。不少初学者会想：既然现在的模型标称支持 128K 甚至 1M 上下文，把这 10 万字一次性复制进提示词不就解决了吗？

但在实际测试中，你往往会遭遇两个问题：一是调用耗时极长、显存飙升甚至直接报显存溢出（OOM）；二是模型虽然读了全文，却唯独漏掉了夹在中间那一页的关键配置，给出错误的答案。

大模型的输入范围不是一个可以随意塞入资料的无限容器。模型的“上下文窗口”受到自注意力计算开销、推理显存膨胀以及位置编码外推能力的共同约束。

---

## 上下文窗口的定义与组成

**上下文窗口（Context Window）指的是大语言模型在单次推理过程中，能够同时处理的最大 Token 序列长度**，通常记作 $L_{\max}$。

这个长度是模型单次前向推理的硬性上限，它包含当前请求的所有 Token 总和：

$$L_{\text{total}} = L_{\text{system}} + L_{\text{history}} + L_{\text{prompt}} + L_{\text{generation}} \le L_{\max}$$

各部分的含义非常直观：
- $L_{\text{system}}$：系统提示词（如“你是一个代码助手…”）；
- $L_{\text{history}}$：多轮对话中累积的往返历史记录；
- $L_{\text{prompt}}$：当前用户发送的提问与附带资料；
- $L_{\text{generation}}$：模型接下来逐字生成回答所占用的 Token。

![模型单次推理序列总长度与上下文窗口约束结构图](/images/content-rebuild/932736675f3aa479/fig-1.png)

这里有一个开发者经常忽略的工程细节：**上下文窗口的上限同时约束着“输入”和“输出”**。如果一个模型的窗口上限是 8,192 Token，而你的输入内容已经占满了 8,000 Token，那么模型最多只能输出 192 个 Token 的回答，随后就会因触碰窗口边界而中断。自回归生成每吐出一个新词，留在窗口内供后续生成的额度就会减少一个词。

## 为什么不能直接把窗口设为无限大？

要理解为什么窗口大小受到硬件制约，需要把大模型的推理拆成两个不同阶段来看：处理用户输入的 **Prefill（预填充）阶段**，以及逐字吐出回答的 **Decode（解码）阶段**。

<ReadMoreLock />

### 1. Prefill 阶段：平方级计算开销

当你把一段长文本发给模型时，模型首先要对这批输入的每一个 Token 计算它们之间的相互关系。在标准自注意力计算中：

$$\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V$$

如果输入长度为 $L$，投影得到的查询矩阵 $Q$ 与键矩阵 $K$ 的维度都是 $L \times d_k$。两矩阵相乘得到的注意力分数矩阵 $QK^T$，其维度是 $L \times L$。

![自注意力矩阵计算量随序列长度平方膨胀的示意图](/images/content-rebuild/932736675f3aa479/fig-2.png)

这意味着每个 Token 都要和序列中的其他所有 Token 计算一次关联度：
- **计算复杂度为 $\mathcal{O}(L^2)$**：当输入长度从 4K 扩展到 64K（变为 16 倍）时，注意力矩阵的点积运算量将增长至原来的 $16^2 = 256$ 倍。
- **显存与带宽**：尽管 FlashAttention 等算子通过分块计算避免了把完整的 $L \times L$ 矩阵物化到显存中，节约了显存读写，但总体的理论乘加运算量依然受平方关系制约。输入越长，模型返回第一个字所需等待的时间（Time to First Token, TTFT）就会越长。

### 2. Decode 阶段：KV Cache 带来的显存线性增长

进入生成阶段后，模型每次前向推理只产生一个新 Token。如果每生成一个词，都重新对前面几万个词做一遍全量运算，生成速度会慢到无法使用。

为了避免重复计算，推理框架会采用 **KV Cache（键值缓存）**：把已经计算过的历史 Token 的 Key 和 Value 向量保存在 GPU 显存中。每次生成新 Token 时，只需要计算当前 Token 的 Query，并与显存里缓存的历史 Key 做点积，再对 Value 进行加权汇总。

这一优化避免了重复计算，但代价是**显存占用随着对话或生成长度线性递增**。

在 FP16 或 BF16 精度下（每个参数占 2 字节），KV Cache 的显存开销公式为：

$$\text{显存占用 (字节)} = 2 \times 2 \times n_{\text{layers}} \times n_{\text{heads\_kv}} \times d_{\text{head}} \times L$$

公式拆解如下：
- 第一个乘数 $2$：分别存储 Key 和 Value 两个张量；
- 第二个乘数 $2$：FP16/BF16 格式每个数值占 2 字节；
- $n_{\text{layers}}$：模型的层数；
- $n_{\text{heads\_kv}}$：负责 KV 投影的注意力头数；
- $d_{\text{head}}$：每个注意力头的向量维度；
- $L$：当前的序列总长度。

#### 算例推导：以经典 7B 模型（多头注意力 MHA）为例

假设一个 7B 模型具有 32 层、32 个注意力头（采用 MHA，即 $n_{\text{heads\_kv}} = 32$），每个头的维度 $d_{\text{head}} = 128$。每增加 1 个 Token，KV Cache 需要占用的显存为：

$$2 \times 2 \times 32 \times 32 \times 128 = 524{,}288 \text{ 字节} = 0.5 \text{ MiB/Token}$$

我们对比该模型在承载不同输入长度时，模型权重与单个并发 KV Cache 的显存分配情况（按硬件显存常用的 $1{,}024$ 进制换算）：

| 序列长度 $L$ | 模型静态权重（FP16） | 单并发 KV Cache 显存 | 总显存（不含激活等临时开销） | KV Cache 占比 |
| :--- | :--- | :--- | :--- | :--- |
| **4K (4,096)** | $\approx 14 \text{ GB}$ | $4{,}096 \times 0.5 \text{ MiB} = 2 \text{ GB}$ | $\approx 16 \text{ GB}$ | 约 $12.5\%$ |
| **32K (32,768)** | $\approx 14 \text{ GB}$ | $32{,}768 \times 0.5 \text{ MiB} = 16 \text{ GB}$ | $\approx 30 \text{ GB}$ | 约 $53.3\%$ |
| **64K (65,536)** | $\approx 14 \text{ GB}$ | $65{,}536 \times 0.5 \text{ MiB} = 32 \text{ GB}$ | $\approx 46 \text{ GB}$ | 约 $69.6\%$ |
| **128K (131,072)**| $\approx 14 \text{ GB}$ | $131{,}072 \times 0.5 \text{ MiB} = 64 \text{ GB}$ | $\approx 78 \text{ GB}$ | 约 $82.1\%$ |

注：现阶段许多现代模型采用了分组查询注意力（GQA，如 Llama 3 将 KV 头数缩减为 8 头），KV Cache 显存会缩减至原来的 1/4，但依然与序列长度成正比，且会随着多并发请求线性累加。

![7B模型在不同序列长度下静态权重与KV Cache显存占用对比图](/images/content-rebuild/932736675f3aa479/fig-3.png)

这直观说明了一个现象：**处理短文本时，GPU 显存主要被模型自身的权重占据；但在超长上下文场景下，KV Cache 逐渐反客为主，成为显存消耗的最大头。**

## 标称上下文与有效上下文：“迷失在中间”

在评估长文本能力时，需要区分两个概念：
- **标称上下文（Nominal Context）**：模型在架构和显存限制下，能够跑通推理而不报错的最大长度。
- **有效上下文（Effective Context）**：模型在长输入中，真正能够准确检索出细节并完成推理的长度范围。

一个标称支持 128K 的模型，并不代表在 128K 的任意位置都具备相同的阅读理解精度。

### 为什么中间位置的信息容易被忽略？

长文本问答评测中广泛存在一个现象：**迷失在中间（Lost in the Middle）**。当关键事实位于提示词的开头或结尾时，模型能以较高的准确率将其提取出来；但如果把同样的关键事实放在长文本的中段（如 30% 到 70% 的位置），模型的回答准确率会出现明显下滑。

![关键信息在输入序列不同位置时的召回率U形曲线与注意力弥散图](/images/content-rebuild/932736675f3aa479/fig-4.png)

造成这种现象的主要原因包括：
1. **因果掩码与训练偏置**：在自回归解码中，排在前面的词会被后续所有词计算注意力，更容易成为模型关注的常驻锚点；而排在最末尾的词因为距离输出位置最近，受注意力衰减影响较小。再加上预训练语料中，文章开头通常是背景/摘要、末尾通常是总结，模型学到了对首尾赋予更多关注的倾向。
2. **噪声与注意力稀释**：在长序列中，Softmax 归一化需要对数万个词分配权重。当输入中塞入大量与问题无关的背景材料时，这些无关词汇会分流注意力权重，导致关键证据分配到的注意力被背景噪声稀释，增加了产生[大模型幻觉](/fundamentals/llm-basics/hallucination.md)的概率。

## 为什么不能随意延长位置编码？

如果硬件显存足够大，能否直接让一个在 4K 序列上训练好的模型去处理 32K 的输入？答案是不能。

现代开源大语言模型普遍使用**旋转位置编码（RoPE）**。RoPE 把每个 Token 的绝对位置映射为向量在复数平面上的旋转角度。相邻位置之间的相对距离，转化为两个向量之间的旋转夹角。

如果模型只在 0 到 4,095 的位置范围内训练过，它的注意力层就从未见过旋转角度大于 4,096 的相对相位差。如果直接强行传入位置 8,000 的 Token，未经训练的超限相位差会导致点积计算出现严重偏差，模型输出彻底乱码。

![RoPE直接外推与位置插值频率变换对比图](/images/content-rebuild/932736675f3aa479/fig-5.png)

为了扩展上下文，业界通常使用**位置插值（Position Interpolation, PI）**等方法：
- **位置插值**：不直接往外拓展新的刻度，而是将目标长度（如 8,192）按比例等比缩放回原本的刻度范围（0 到 4,095）。这保证了旋转角度始终在预训练见过的区间内。
- **插值的代价**：等比压缩相当于把刻度盘变得更密集，相邻两个 Token 之间的旋转角度差缩小了，这会导致模型对相邻词序的高频分辨能力下降。后续演化出的 NTK-Aware 插值与 YaRN 等方案，通过对高频特征维持外推、对低频特征进行插值，缓解了这种局部分辨率的损失。

但无论哪种编码调整，如果只在推理期做数学缩放而不进行针对性的长文本微调，模型在处理超长复杂推理时的细节捕捉能力仍会受到影响。

## 长上下文与检索增强（RAG）如何取舍？

随着支持长上下文的模型越来越多，开发[大模型应用系统](/fundamentals/llm-basics/app-system-design.md)时经常需要回答：**既然模型窗口能装下几十万字，还需要搭建检索增强生成（RAG）管道吗？**

长上下文模型与 RAG 并非完全对立，而是针对不同成本与延迟约束的两种方案。

![长上下文与检索增强在延迟、吞吐与显存维度的工程选型权衡图](/images/content-rebuild/932736675f3aa479/fig-6.png)

二者的核心差异如下：

| 评估维度 | 全量长上下文输入 | 检索增强生成（RAG） |
| :--- | :--- | :--- |
| **首字延迟 (TTFT)** | **较高**。需要对几万至几十万 Token 计算 Prefill，等待时间较长。 | **较低**。仅需处理检索出的几千 Token 片段，模型响应迅速。 |
| **GPU 显存与并发** | **开销大**。每个请求长期驻留巨大 KV Cache，单卡支持的并发请求数受限。 | **开销小**。单次请求占用显存小，并发承载能力更强。 |
| **计费成本** | **线性增加**。API 调用通常按输入 Token 数计费，长文本每次请求成本较高。 | **成本更低**。每次只对过滤后的片段付费。 |
| **跨章节宏观理解** | **更优**。自注意力机制能够跨越全篇进行综合归纳、对比和梳理。 | **较弱**。若检索时切分了文档，容易割裂跨段落或跨章节的因果关系。 |
| **抗无关噪声干扰** | **受注意力稀释影响**。无关文本过多时，可能遗漏处于中段的关键细节。 | **取决于检索准确度**。精准召回能有效过滤噪声，但存在漏检风险。 |

### 常见的工程落地策略

在[长文档问答设计](/frontier/long-context-app/doc-qa-design.md)与[长上下文应用](/frontier/long-context-app/what-is-long-context.md)中，更成熟的方案是**先检索粗筛，再利用长窗口精读**：
1. **检索粗筛**：面对庞大的知识库，先通过关键词与向量检索，把范围从数百万 Token 缩小至几万 Token 的相关文档集合；
2. **适度窗口理解**：把粗筛出的多篇关联文档整体喂给具备长窗口的模型，让模型依靠全局注意力完成跨文本对比与归纳。

这样既避免了切片过碎带来的上下文丢失，又避免了无节制堆砌全量内容带来的显存膨胀与延迟恶化。
