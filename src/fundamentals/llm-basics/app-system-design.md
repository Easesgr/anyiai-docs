写一个脚本调用大模型 API 并打印结果只需要几行代码，但在真实业务中使用大模型构建功能时，常常会遇到以下情况：

- 用户多聊了几轮，历史记录超出窗口限制导致接口报错；
- 模型在某一次回复中输出格式损坏，导致下游系统解析崩溃；
- 用户随口一句“我刚刚付款了”，系统若完全相信模型的语义判断，就可能错误推进业务流程；
- 页面等待十多秒才一次性返回文本，期间无响应，容易触发超时断开。

大语言模型本质上是一个按概率预测下一个 Token 的无状态计算单元，而业务系统要求的是确定性的状态流转、严格的数据校验和可预期的响应延迟。将概率模型安全接入传统软件系统，核心在于**用确定性的工程规则约束和编排非确定性的模型输出**。

本文以一个电商售后助手系统为例，讲清楚系统分工、会话状态持久化、职责边界划分、容错降级以及流式传输与缓存优化的具体实现。

## 系统分工：从前端到模型的多层流转

在完整的系统中，前端绝不应该直接携带 API Key 访问大模型。一个通用的后端应用系统通常分为四个组成部分：

1. **接入网关（Gateway）**：负责请求鉴权、多租户配额分配、速率限制（Rate Limiting）和敏感内容拦截。模型 API 计费昂贵且存在并发上限，网关层负责在请求进入后端前过滤非法流量与恶意重放。
2. **业务编排层（Orchestration）**：系统的业务中枢。负责组装 Prompt、调用数据库查询业务数据、协同 [大模型如何调用工具](/fundamentals/llm-basics/function-calling.md)、解析模型输出，并根据校验结果驱动业务状态机。
3. **模型代理与服务层（Model Serving & Proxy）**：统一封装不同厂商的模型接口，提供负载均衡、超时控制和故障切换。当主用模型无响应时，将请求分发给备用模型。
4. **数据与持久化层（Storage & Persistence）**：包括保存会话历史的数据库、临时会话缓存（如 Redis），以及存放企业知识库的检索索引。

![大模型应用系统分层拓扑架构与数据流向图](/images/content-rebuild/1adcc19e6bb480c9/fig-1.png)

客户端发起的每一个请求都必须先经过网关鉴权，再由编排层处理业务逻辑，只有在需要进行自然语言解析或生成时才调用模型服务。这样可以防止前端直接暴露大模型凭证，也能及时拦截非法的状态请求。

## 会话与状态管理：区分上下文记忆与业务真实状态

大模型推理服务是**无状态（Stateless）**的。服务处理完单次请求后，就会释放对应显存中的临时激活值，不会自动记住当前用户上一轮说过什么。为了实现多轮连续对话，应用必须在发起下一次请求时，把历史对话列表作为输入参数重新发送给模型。

<ReadMoreLock />

这种机制带来了一个直接后果：随着对话轮次增加，请求发送的 Token 数量线性增长，端到端延迟变长，最终会触碰模型的[上下文窗口](/fundamentals/llm-basics/context-window.md)上限。

![会话滑动窗口截断策略与外部状态存储拓扑图](/images/content-rebuild/1adcc19e6bb480c9/fig-2.png)

### 上下文截断策略

在编排层中，通常有以下几种方式管理上下文长度：

- **固定轮数滑动窗口**：仅保留最近 $N$ 条消息。实现成本低，但会丢失早期的关键信息（例如用户在第 1 轮表达的诉求）。
- **首尾锚定裁剪**：永久保留开头的系统提示词（System Prompt）和第 1 轮用户诉求，仅对中间的消息进行先进先出（FIFO）丢弃。丢弃时需保证消息对的完整性（例如不能保留工具返回结果却删除了发起调用的工具请求）。
- **异步摘要压缩**：当会话 Token 达到阈值时，在后台启动一个成本更低的小模型，将早期对话压缩成一段事实摘要，替换掉原本冗长的历史消息。

### 业务状态必须落在外部数据库

在售后助手场景中，绝不能依赖模型会话中的自然语言记忆来判断“该订单是否已退款”。如果用户聊了多轮退换货细节，导致早期的关键确认信息被滑出上下文，模型就可能产生[大模型幻觉](/fundamentals/llm-basics/hallucination.md)，给出与真实订单状态矛盾的回答。

**会话上下文只用于语义沟通，权威业务状态必须保存在数据库中。** 用户的订单处于 `待发货`、`申请退款中` 还是 `已退款`，必须由业务数据库中的状态机字段决定。编排层在每次调用模型前，从数据库查出该订单的真实状态并注入 Prompt；在模型生成退款意图后，由后端代码验证订单合法性并修改数据库，模型没有直接修改业务数据的权限。

## 确定性代码与非确定性模型的职责划分

大模型擅长理解口语化、含糊不清的自然语言，但不擅长处理精度要求高的事务与算术计算。

如果在系统设计中把控制权交给模型（例如提示词写：“如果你认为用户满足退款条件，请自行向用户确认退款成功”），一旦模型发生语义漂移或遭到提示词注入（Prompt Injection），就可能引发业务资损。

确定性代码与大模型的分工边界如下：

| 任务维度 | 确定性业务代码负责 | 大语言模型（LLM）负责 |
| :--- | :--- | :--- |
| **权限与安全** | 用户身份校验、接口权限鉴权、计费扣除 | 识别用户自然语言中的退款意图 |
| **数据流转** | 数据库事务提交、状态机条件流转 | 提取非结构化文本中的字段（如退款原因、金额） |
| **业务规则** | 金额比对、库存扣减、是否在7天无理由期限内 | 生成通俗易懂的回复话术 |
| **容错兜底** | 超时控制、模型切换、降级人工客服 | 提供语义分类与提取结果供代码校验 |

![确定性业务代码与非确定性模型调用的边界职责划分图](/images/content-rebuild/1adcc19e6bb480c9/fig-3.png)

在代码实现中，大模型应当处于“叶子节点”的位置，为代码提供参数抽取与语义判断支持，由确定性代码把控状态流转。

以下是一个使用 Python 处理退款意图抽取的简化示例：

```python
from enum import Enum
from pydantic import BaseModel, Field, ValidationError

class OrderState(str, Enum):
    SHIPPED = "SHIPPED"
    REFUND_REQUESTED = "REFUND_REQUESTED"
    CLOSED = "CLOSED"

class RefundIntentSchema(BaseModel):
    intent: str = Field(description="识别出的意图：APPLY_REFUND 或 OTHER")
    order_id: str = Field(description="用户提及的订单编号")
    reason: str = Field(description="退款原因摘要")

def process_user_refund_request(
    current_state: OrderState, 
    user_message: str, 
    actual_order_id: str
) -> OrderState:
    # 1. 确定性前置守卫：已闭环订单不允许发起退款
    if current_state == OrderState.CLOSED:
        raise ValueError("订单已关闭，无法申请退款")
    
    # 2. 调用模型仅作语义抽取（通过工具调用或结构化输出接口）
    # 假定模型返回的 JSON 字符串如下：
    mock_llm_json = '{"intent": "APPLY_REFUND", "order_id": "ORD_100234", "reason": "尺码偏大"}'
    
    # 3. 确定性强类型校验
    try:
        extracted = RefundIntentSchema.model_validate_json(mock_llm_json)
    except ValidationError:
        # 模型输出格式损坏，保持原状态，转入人工或报错重试
        return current_state
    
    # 4. 确定性业务核验与状态流转
    if extracted.intent == "APPLY_REFUND":
        # 校验模型抽取的订单号与当前会话锁定的真实订单是否一致
        if extracted.order_id == actual_order_id:
            # 记录退款原因并推进状态机，模型不能直接修改数据库
            save_refund_reason(actual_order_id, extracted.reason)
            return OrderState.REFUND_REQUESTED
            
    return current_state

def save_refund_reason(order_id: str, reason: str):
    pass
```

## 容错与降级设计：处理输出损坏与模型异常

大模型推理服务的可用性容易受网络抖动、算力排队或并发突发影响，其偶发失败率与尾部延迟通常高于普通后端微服务。因此，构建高可用应用必须设计兜底机制。

![结构化输出校验重试与多级熔断降级流程图](/images/content-rebuild/1adcc19e6bb480c9/fig-4.png)

### 1. 结构化输出损坏的处理三部曲

当系统要求模型返回严格的 JSON 时，模型可能会输出包裹了 Markdown 语法块的文本、缺少必填字段，或者字符串中间被意外截断。处理策略应分为三步：

- **本地清洗与容错解析**：先用正则表达式剥离首尾多余的说明文字与代码块标记；使用容错解析器尝试修复末尾缺失的引号或反括号。
- **携带错误信息的上下文重试**：如果本地解析依然失败，系统截取解析报错信息（例如 `Missing required field: order_id`），放入上下文重新调用模型。模型获知具体报错原因后，纠错重试的成功概率会大幅增加。
- **重试上限限制**：单次任务的自动重试建议控制在 1 到 2 次内，避免死循环消耗额度并加重延迟。

### 2. 多级故障降级（Fallback）

当主用模型接口出现连接超时、服务限流（HTTP 429）或不可用（HTTP 503）时，系统需要启动分级降级：

- **切入备用模型**：调度层迅速将请求路由至备用模型服务。备用模型可以是参数量较小的模型，也可以部署在其他可用区或云服务商处。
- **静态规则保底**：如果多模型调度均失效，系统切入基于关键词或静态模板的兜底逻辑（例如提示：“当前业务繁忙，系统已为您记录工单，请稍后重试或联系人工客服”），保证接口对外始终返回结构清晰的业务响应，而非直接抛出未包装的网关异常。

## 延迟与吞吐优化：流式传输与提示词排布

自回归大模型按 Token 逐个生成，生成一篇完整的答复可能需要耗费数秒甚至数十秒。若采用传统的同步阻塞模式，前端长时间处于白屏等待状态，并且中间网络代理极易因超时主动断开连接。

### SSE 流式响应与网络缓冲

常用的首字优化方案是基于 HTTP 的 **Server-Sent Events（SSE）** 建立单向流式推送。模型每生成一个或几个 Token，服务端就以事件流的形式推给前端渲染，将用户感知到的等待时间降低为首字生成时间（TTFT, Time To First Token）。

![SSE 流式传输时序与网关长连接管理示意图](/images/content-rebuild/1adcc19e6bb480c9/fig-5.png)

引入流式传输后，后端需要注意两项基础设施适配：

1. **保持长连接与并发资源控制**：传统请求通常在几十毫秒到几百毫秒内结束；而 SSE 会话需要持续占用 Socket 描述符和工作线程，直到整个回答生成完毕。高并发时系统需合理配置连接池与协程并发上限，防止耗尽网关文件句柄。
2. **关闭中间代理缓冲**：如果应用前置了 Nginx 等反向代理服务器，默认开启的响应缓冲（`proxy_buffering on;`）会把模型吐出的 Token 积攒成一个大包再一次性发送，破坏打字机效果。生产环境需要显式针对 SSE 路由关闭缓冲（`proxy_buffering off;`），并适当调大读超时参数（如 `proxy_read_timeout`）。

### 提示词排布对 KV 缓存的影响

多数主流推理框架（如 vLLM）和商业 API 支持前缀缓存机制（Prefix / Prompt Caching）。当新请求的前缀 Token 序列与已有请求的前缀一致时，推理引擎可以直接复用此前已经计算好的键值向量（KV Cache），无需重新从头执行全量 Prefill 计算，从而降低服务计算开销并缩短首字延迟。

![Prompt 前缀静态排布对 KV 缓存命中的影响机制图](/images/content-rebuild/1adcc19e6bb480c9/fig-6.png)

在编写 Prompt 模板时，应当遵循**“静态通用内容在前，动态特异变量在后”**的原则：

```text
【低效排布 - 缓存容易失效】
[动态当前时间: 2026-03-31 14:02:11] -> [长达 1500 字的固定角色设定与工具说明] -> [用户输入]
  └─ 动态时间戳位于最前，导致后端推理引擎从第 1 个 Token 开始就无法匹配静态缓存。

【高效排布 - 提升缓存复用率】
[长达 1500 字的固定角色设定与工具说明] -> [动态当前时间] -> [检索出来的上下文] -> [用户输入]
  └─ 前 1500 字保持相对稳定。只要请求被分发至同一推理实例且缓存未被驱逐，就能复用 KV 缓存。
```

需要明确的是，前缀缓存能否命中还取决于推理后端的缓存淘汰策略（如 LRU）以及多实例负载均衡分发策略。将静态前缀靠前排布，是在应用层提升缓存命中概率并降低调用延迟的有效工程实践。

## 总结与工程选型建议

将大模型嵌入软件系统不是单纯替换原有的接口，而是建立一套能够容忍非确定性输出的防御型系统：

1. **控制反转**：由业务代码作为主控制器调度模型，而非将系统控制权全盘交由模型自然语言驱动；
2. **状态分离**：模型上下文仅承载语义交流，业务状态交由数据库状态机管理；
3. **容错重试**：通过格式校验、带报错回传以及备用模型路由，建立防雪崩屏障；
4. **性能调优**：借助 SSE 流式推送改善交互延迟，通过静态前缀排布提高推理缓存复用率。
