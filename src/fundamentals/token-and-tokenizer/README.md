计算机处理器和神经网络只能执行数值运算，无法直接读取人类自然语言中的字符或单词。大语言模型处理文本的第一步，是把连续的字符序列切分成离散的符号单元，再将这些单元映射为数字编号。这个符号单元就是 **Token**，而执行切分与编号转换的程序就是**分词器（Tokenizer）**。

以英文句子 `"Deep learning!"` 为例，分词器不会直接把它当作包含 14 个字符的字符串交给模型，而是经过预处理与子词匹配，切分成类似于 `["Deep", "Ġlearning", "!"]` 的子词单元（其中 `Ġ` 代表前面的空格），并查表映射为一组整数列表，例如 `[38302, 4673, 0]`。只有这串整数进入模型后，神经网络才能通过嵌入矩阵将其转换为高维稠密向量，开始后续的注意力与前向网络计算。

分词机制直接决定了模型的词表大小、序列物理长度、上下文窗口利用率、推理显存开销以及计费成本。本模块通过 5 篇核心教程，带你完整掌握分词器的算法实现、跨语言特性与工程使用边界。

### 模块知识全景与学习路径

本模块包含 5 篇核心文章，按从概念认知、算法推导到工程落地的顺序展开：

![本模块五篇核心主题之间的逻辑演进与依赖关系图](/images/content-rebuild/02bb1649a60ce290/fig-2.png)

1. **概念基础**：[Token 到底是什么？](/fundamentals/token-and-tokenizer/what-is-token.md)
   对比字符级（Character-level）、词级（Word-level）与子词级（Subword）三种文本表示方案。说明为什么现代大模型普遍选用子词分词：字符级虽然词表小但会导致序列极长、注意力计算成本剧增；全词级虽然序列短但词表会膨胀到数百万且无法处理未登录词（OOV）；子词分词则在词表体积与表达效率之间取得了平衡。
2. **算法实现**：[Tokenizer 是怎么工作的？](/fundamentals/token-and-tokenizer/how-tokenizer-works.md)
   拆解主流子词算法的构建逻辑：
   * **BPE（Byte Pair Encoding）**：从基础字符出发，统计数据集中出现频率最高的相邻字符对并迭代合并。
   * **Byte-level BPE**：以 256 个 byte 字节为基底词表，彻底消除未知字符（`<unk>`）风险，被 GPT-2、LLaMA、Qwen 等模型广泛采用。
   * **WordPiece**：类似 BPE 的合并策略，但每次选取能最大化训练数据似然增量（互信息得分）的子词对。
   * **Unigram**：与 BPE 自底向上的合并相反，Unigram 从超大候选词表出发，基于语言模型似然逐步剪除贡献度最低的子词。
   * **SentencePiece**：直接在原始字节或字符流上运行分词算法，将空格显式编码为特殊元符号（如使用 ` ` 标记，Unicode U+2581），原生支持多语言与无空格分界文本。
3. **多语言特性**：[中文分词为什么特殊？](/fundamentals/token-and-tokenizer/chinese-tokenization.md)
   聚焦无空格分界语言。中文单个汉字在 UTF-8 编码下通常占用 3 个字节。如果分词器的词表中缺少常用汉字或中文词汇，Byte-level BPE 会把一个汉字拆成 2 到 3 个独立的字节 Token，导致中文字符串分词后的 Token 数量大幅增加，显著恶化上下文窗口利用率并提高推理成本。
4. **资源核算**：[上下文长度、Token 预算和接口费用到底怎么算？](/fundamentals/token-and-tokenizer/token-budget.md)
   建立大模型运行开销的计算直觉：拆解预填充阶段（Prefill）的全注意力计算开销与自回归生成阶段（Decode）的 KV 缓存增长；说明不同模型提供商如何按照 Prompt Token 与 Completion Token 分开计费；提供容量评估与吞吐量估算方法。
5. **工程实践**：[Tokenization 对 Prompt、RAG 和长文本处理有什么影响？](/fundamentals/token-and-tokenizer/tokenization-impact.md)
   梳理真实业务场景中的分词陷阱：提示词末尾空格引起的 Token 错配与生成漂移、检索增强（RAG）中文档按字符硬截断打碎专有名词与多字节编码的风险，以及代码缩进在不同分词方案下的稳定性防护。

### 运行时数据流：从原始文本到模型输入

分词器在整个大语言模型系统中所处的物理位置如下：

![连续文本经分词器转换为Token ID并映射为嵌入向量的数据流向图](/images/content-rebuild/02bb1649a60ce290/fig-1.png)

在代码调用大模型时，整个流水线经过四个阶段：

1. **规范化与初切分（Normalization & Pre-tokenization）**：
   分词器首先对原始字符串进行标准化（例如 Unicode 标准化 NFKC、清除异常控制字符），然后按照预设规则（如空格、标点或正则模式）切分成初步的离散词元块。
2. **子词编码（Subword Tokenization）**：
   依照分词器训练时生成的静态词表与合并规则，将词元进一步切分为子词。例如常见单词 `"learning"` 保持完整，而罕见词如 `"annoyingly"` 则被拆分成 `["annoy", "ing", "ly"]`。
3. **词表编号映射（ID Mapping）**：
   将切分后的子词按词表（Vocabulary）映射为唯一的整数索引。分词器的输出是纯粹的整数数组，例如输入 `"Hello"` 得到 `[15496]`。**分词器是一个完全独立于神经网络前向计算的前置软件，运行在 CPU 上，不包含任何可学习的浮点神经网络权重。**
4. **嵌入向量查找（Embedding Lookup）**：
   整数数组被传入运行在 GPU 上的模型。第一层是嵌入矩阵 $W_e \in \mathbb{R}^{|V| \times d}$（其中 $|V|$ 为词表大小，$d$ 为隐藏层维度）。模型以 Token ID 作为行索引，取出对应的 $d$ 维稠密向量，加上位置编码后送入 Transformer 层的多头自注意力计算。

分词粒度直接决定了输入给 Transformer 模型的序列长度 $N$。在预填充（Prefill）阶段，标准全注意力的矩阵计算量与序列长度呈二次方关系（$O(N^2)$）；在生成阶段，已生成的上下文键值对（KV Cache）显存占用与长度呈线性关系。分词器对特定语料的压缩比越低，每个有效字符占用的 Token 就越多，推理延迟和显存压力就越大。

### 工程场景中的切分陷阱与边界防御

在构建 RAG 知识库或处理长文本输入时，分词机制如果不加注意，容易引发下游问题：

![分词截断导致的检索关键词断裂与下游自注意力输入映射对照图](/images/content-rebuild/02bb1649a60ce290/fig-3.png)

* **粗暴硬截断破坏编码与子词**：
  如果按照底层固定字节数硬切分文档，切分点可能落在 UTF-8 多字节字符中间导致解码乱码；即使按照固定字符数切分，切分点也容易落在单词内部，把专有名词（例如 `"Transformer"` 拆成 `"Trans"` 和 `"former"`）切分到两个不同的分块（Chunk）中。当检索模型对这两块分别编码时，打碎的子词无法匹配用户查询中的完整词元，导致召回率下降。
* **滑动窗口与 Token 感知切块**：
  生产环境切块时，应使用与模型匹配的分词器进行切块计算，并在相邻块之间保留重叠区域（Overlap，通常保留 10%~20% 的 Token）。这样即便某一个词在边界处被截断，完整的词汇与语境仍能保留在相邻的分块中。
* **提示词结尾的空白字符**：
  许多模型的分词器对带前导空格的词（如 `" world"`）和不带空格的词（如 `"world"`）分配不同的 Token ID。在 Prompt 结尾意外多敲一个空格，会导致原本预期生成的下一个词失去前导空格属性，迫使模型从完全不同的子词分支开始推演，从而引起生成质量的波动。
