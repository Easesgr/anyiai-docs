在搭建检索增强生成（RAG）或知识库系统时，许多开发者常遇到类似困境：用户的提问明明在文档库中有对应内容，系统却召回了不相干的段落，或者把最关键的依据排在很靠后的位置。

面对这种现象，最容易产生的直觉是“换一个参数量更大、跑分更高的 Embedding 模型”。然而在实际工程中，Embedding 模型只是整个检索流水线的一环。一段文本从原始文档转化为向量，再到最终被检索命中，涉及文档解析、分块切分、任务指令、向量召回与重排序等多个环节。盲目更换模型不仅耗时耗算力，而且常常无法解决因数据切分或匹配范式错误导致的根本问题。

![检索优化排查金字塔与级联工作流封面](/images/content-rebuild/ad0b69968ec5652d/cover.png)

调优应当遵循一条清晰的排查路径：**先看数据切分是否完整，再看任务指令是否对齐，接着引入二阶段重排序，最后才评估是否需要领域微调**。本文将围绕一个常见的客服知识库检索场景，拆解检索不准的具体成因与对应的优化方案。

## 检索效果不佳的三种典型根因

为了看清检索质量为何下滑，我们以客服知识库中的一个真实查询为例：

> **用户查询**：“申请退款后多久能到账？”
>
> **知识库原文（售后规约节选）**：
> “……审核通过后，财务将在 1 个工作日内发起原路退款。具体到账时间取决于各发卡行的入账周期，借记卡通常为 1 至 3 个工作日，信用卡为 3 至 7 个工作日。若超过 7 个工作日未到账，请联系人工客服核实交易流水号。”

理想情况下，检索系统应当精准命中上述段落。但如果评测时召回率（Recall）或平均倒数排名（Mean Reciprocal Rank, MRR）偏低，问题通常集中在以下三类机制上：

![检索质量异常的三大归因定位树](/images/content-rebuild/ad0b69968ec5652d/fig-1.png)

### 1. 切片信息破碎（Chunking Fragmentation）
- **现象**：系统召回了包含“退款”字样的句子，但返回的片段是“……通常为 1 至 3 个工作日，信用卡为 3 至 7 个工作日”。它丢失了前句的“财务发起原路退款”以及段落开头的业务前提。
- **成因**：文本切分器按固定字符长度机械切断了句子，导致核心句子的主语、前提条件和补充说明被割裂在不同分块中。Embedding 只能对当前切片内的文字做编码，缺少主谓语和前置条件的孤立片段自然难以与提问建立强相关性。

### 2. 非对称检索失配（Asymmetric Query-Doc Mismatch）
- **现象**：系统没有返回上述长篇说明，反而召回了另一位用户的历史提问：“退款多久到？”或者包含大量字面重合的短句“如何申请退款流程？”。
- **成因**：文本匹配分为**对称匹配**（如判断两句话是否同义）与**非对称检索**（如用短疑问句寻找长陈述句答案）。在没有任何前缀或任务指令引导时，通用双塔模型倾向于将短疑问句映射到与其他短疑问句相近的向量位置，而不是映射到详细陈述答案的知识段落。

### 3. 领域专有名词与词表盲区（Out-of-Domain Failure）
- **现象**：若用户询问内部系统的特定业务词（例如“逆向冲销单时效”），模型召回了完全无关的通用金融文本，甚至将相似拼写的通用词混淆。
- **成因**：通用模型未在特定垂直领域的术语体系上充分训练。模型的分词器（Tokenizer）可能将专有名词切碎成了无意义的子词片段，向量编码器也无法辨识该专业词汇与“退款”之间的强语义关联。

## 数据切分优化：分块大小、重叠窗口与上下文拼接

数据本身的切分质量决定了向量表示的信息上限。在修改模型参数前，应优先检查文本切片是否合理。

![文本分块大小与重叠窗口及元数据拼接机制](/images/content-rebuild/ad0b69968ec5652d/fig-2.png)

### 1. 分块大小（Chunk Size）与重叠（Overlap）的权衡

文本切分的本质是在**语义聚焦度**与**上下文完整度**之间寻找平衡：
- **分块过小（例如 50 到 100 Token）**：向量语义高度集中，但代词指代（如“上述条款”、“该业务”）和因果逻辑极易被截断，使切片失去独立解释能力。
- **分块过大（例如 1500 到 2000 Token）**：虽然保留了完整上下文，但主流开源模型多使用均值池化（Mean Pooling）汇总隐层向量。过长的文本序列使得局部关键信息的特征在求均值过程中被背景信息稀释，难以精准匹配特定细节问题。

工程实践中，通常以 **256 到 512 Token** 作为起步测试区间，并设置 **10% 至 20% 的重叠窗口（Overlap）**。重叠区域的作用是防止长句或核心概念恰好落在截断点上，确保跨边界的关键语义至少完整出现在其中一个切片中。

### 2. 元数据注入（Metadata Enrichment）

许多技术文档和规章制度具有清晰的层级树状结构。孤立看某一个小节，文字往往缺少上下文定位。例如文档中写着：“默认值为 20，数值越大边缘越清晰。”如果脱离了上级章节“图像滤镜配置 -> 锐化算法”，模型无法根据“锐化参数”这个查询命中该段落。

常见做法是在切片文本前显式拼接入父级标题和路径元数据：

```text
[来源: 图像处理接口规范.pdf | 模块: 滤镜配置 > 锐化处理]
默认值为 20，数值越大边缘越清晰。取值范围为 0 到 100，过度调整可能引入高频噪点。
```

这种结构让编码器在进行自注意力计算时，直接将上级语境融合到切片内各词的向量表示中，有效消除切片孤岛现象。

## 提示词与指令前缀：对齐非对称检索

很多开发者在使用支持指令微调的 Embedding 模型时，直接将原始查询传入 `model.encode(query)`，导致非对称问答场景下的表现不及预期。

![指令前缀如何调整非对称检索中的 Query 向量表示](/images/content-rebuild/ad0b69968ec5652d/fig-3.png)

### 机制原理：STS 任务与 IR 任务的差异

- **语义文本相似度（STS, Semantic Textual Similarity）**：对称任务，判断“两句话是否是同一个意思”（例如“天气很好”与“今天晴空万里”）。两侧文本形式对等，直接编码即可。
- **信息检索（IR, Information Retrieval）**：非对称任务，输入是用户的提问（简短、疑问语气、信息不完整），目标是文档切片（详细、陈述语气、结构化）。

现代多任务 Embedding 模型（如 BAAI 的 BGE 系列）通过引入指令（Instruction）区分不同任务。如果不加指令，模型会默认按对称相似度编码；而在 Query 前拼接特定指令后，模型在自注意力层中会针对“检索文档”这一目标重权调整 Query 的特征方向，使其在向量空间中与陈述性答案更靠近。

### 调用示例：使用 Sentence Transformers 规范传参

以下以 `BAAI/bge-base-zh-v1.5` 为例。模型约定：文档端保持原文编码，查询端添加预设指令：

```python
from sentence_transformers import SentenceTransformer

# 加载支持指令的文本嵌入模型
model = SentenceTransformer("BAAI/bge-base-zh-v1.5")

queries = ["申请退款后多久能到账？"]
passages = [
    "审核通过后，财务将在1个工作日内发起原路退款。具体到账时间取决于各发卡行的入账周期，借记卡通常为1至3个工作日，信用卡为3至7个工作日。",
    "修改个人登录密码需进入安全中心，验证原手机号后输入新密码完成重置。"
]

# 非对称检索规范：在 Query 端添加约定的指令前缀
instruction = "为这个句子生成表示以用于检索相关文章："
queries_with_instruction = [f"{instruction}{q}" for q in queries]

# 对向量执行归一化（Normalize）
q_embeddings = model.encode(queries_with_instruction, normalize_embeddings=True)
p_embeddings = model.encode(passages, normalize_embeddings=True)

# 当向量已做 L2 归一化时，点积（Dot Product）计算在数值上等价于余弦相似度，计算效率更高
similarities = q_embeddings @ p_embeddings.T
print(similarities)
```

这一调整在推理时仅增加少量 Token 的前向计算，却能纠正问句在向量空间中的匹配方向。

有关稀疏与稠密特征的组合机制，可进一步参考 [/fundamentals/embedding/sparse-dense-vectors.md](/fundamentals/embedding/sparse-dense-vectors.md)。

## 二阶段级联检索：引入 Cross-Encoder 重排序

如果优化了分块并添加了指令前缀后，相关文档能进入召回列表的前 50 名，但排在第 1、2 名的依然是“表面词汇重合度高、但并未回答问题”的干扰段落，说明单靠双塔向量检索已接近表征精度的上限。

![双塔向量初筛与单塔交叉重排的级联架构](/images/content-rebuild/ad0b69968ec5652d/fig-4.png)

### 1. Bi-Encoder 与 Cross-Encoder 的机制差异

两种架构在交互方式与计算开销上存在根本不同：

| 对比维度 | 双塔模型（Bi-Encoder） | 交叉编码器（Cross-Encoder / Reranker） |
| :--- | :--- | :--- |
| **输入方式** | Query 与 Passage 独立送入编码器，各自输出单向量 | 将 `Query` 与 `Passage` 拼接为一个序列整体输入 |
| **注意力交互** | **无跨文本交互**：Query 的词只能与 Query 交互；Passage 亦然 | **全序列跨注意力交互**：Query 的每个词与 Passage 的每个词共同参与自注意力计算 |
| **离线索引** | **支持**：文档可在入库前全量计算并写入向量数据库 | **不支持**：必须在线对每一个 $(Query, Passage)$ 对实时计算 |
| **在线计算复杂度** | $O(N \cdot d)$ 向量点积（配合近似近邻索引可达亚线性时延） | $O(K \cdot L^2)$ Transformer 前向计算（$K$ 为候选数，$L$ 为拼接长度） |
| **局部语义判别** | 较弱：整段文档被压缩成单个定长向量，局部逻辑容易泛化 | 极高：能逐词比对条件、转折与修饰逻辑 |

### 2. 为什么不能直接用 Cross-Encoder 扫描整个知识库？

假设知识库中有 50 万个切片，每次用户提问时，如果直接用 Cross-Encoder 处理，就需要进行 50 万次多层 Transformer 的前向传播。哪怕使用高性能 GPU，这一过程也会耗费数十秒甚至数分钟，完全无法满足在线交互的时延要求。

### 3. 工程落地方案：两阶段级联

标准方案是将两者级联配合使用：
1. **粗筛阶段（Retrieval）**：使用 Bi-Encoder（可结合 BM25 关键词检索）在全量知识库中执行毫秒级初筛，取出前 $K=100$ 个候选切片。
2. **精排阶段（Rerank）**：使用轻量级 Cross-Encoder 仅对这 100 个切片与 Query 拼接打分，按交互得分重新排序，截取最高的 Top-3 或 Top-5 输出给大模型。

使用 `sentence-transformers` 进行重排序的示例代码如下：

```python
from sentence_transformers import CrossEncoder

# 加载交叉编码重排模型
reranker = CrossEncoder("BAAI/bge-reranker-base")

query = "申请退款后多久能到账？"
candidates = [
    "申请退款前请确保商品未经拆封，包装防伪码完好无损。",
    "审核通过后，财务将在1个工作日内发起原路退款。具体到账时间取决于各发卡行的入账周期，通常为1至3个工作日。",
    "修改密码请在安全中心提交验证码。"
]

# 拼接成 (Query, Passage) 对并预测匹配分值
pairs = [[query, doc] for doc in candidates]
scores = reranker.predict(pairs)

# 降序排列输出
ranked = sorted(zip(candidates, scores), key=lambda x: x[1], reverse=True)
for doc, score in ranked:
    print(f"得分: {score:.4f} | 内容: {doc}")
```

由于 Cross-Encoder 能让提问中的“多久能到账”与候选文档中的“1至3个工作日”产生直接的跨词注意力关联，即使候选段落 1 与提问都包含了“申请退款”四个字，重排模型也能准确将真正回答时效的候选段落 2 排在第一位。

关于重排与基础模型选型的宏观对比，可参阅 [/fundamentals/embedding/embedding-model-selection.md](/fundamentals/embedding/embedding-model-selection.md)。

## 垂直领域微调：优化特征分布与难负例挖掘

如果优化了分块、添加了指令且使用了重排器之后，前 100 个粗选结果中依然完全没有正确文档，说明 **Bi-Encoder 的表征能力在该专业领域存在盲区**，此时需要考虑对 Embedding 模型进行领域微调。

![对比学习三元组与向量拉近推开几何原理](/images/content-rebuild/ad0b69968ec5652d/fig-5.png)

### 1. 样本结构与难负例（Hard Negatives）

微调 Embedding 模型的核心思路是**对比学习（Contrastive Learning）**。训练样本通常组织为三元组：
$$(q, d^+, d^-)$$
其中 $q$ 是查询，$d^+$ 是正确正例文档，$d^-$ 是负例文档。

在构建样本时，**负例的质量决定了微调的效果**：
- **简单负例（Random Negatives）**：随机抽取的无关文本（例如提问是退款时效，负例是红烧肉的做法）。这类负例字面差异巨大，模型无需学习专业语义即可轻易区分，损失函数迅速降低，但模型学不到有效特征。
- **难负例（Hard Negatives）**：与提问在字面上高度相似、甚至能被 BM25 或未微调模型排在前列，但实际未回答问题的文档（例如正例是“退款到账周期”，难负例是“退款申请提交条件”）。只有通过区分难负例，模型才能在向量空间中拉开表面相似、本质不同的文本间距。

### 2. 损失函数机制：MultipleNegativesRankingLoss

开源实践中广泛使用 `MultipleNegativesRankingLoss`。在一个 Batch 大小为 $B$ 的训练批次中，不仅计算显式提供的正负例，还将 Batch 内其他样本的正例文档 $d_j^+ (j \neq i)$ 自动视为样本 $i$ 的负例（In-Batch Negatives）：

$$\mathcal{L} = -\sum_{i=1}^{B} \log \frac{\exp(\text{sim}(q_i, d_i^+) / \tau)}{\sum_{j=1}^{B} \exp(\text{sim}(q_i, d_j^+) / \tau) + \sum_{k} \exp(\text{sim}(q_i, d_{i, k}^-) / \tau)}$$

- $\text{sim}(u, v)$ 通常为两向量的余弦相似度或点积；
- $\tau$ 为平滑概率分布的温度系数（Temperature）；
- $d_{i, k}^-$ 代表为第 $i$ 个样本配置的显式难负例。

通过该优化目标，模型反向传播调整参数，使得正例对的向量距离持续缩短，难负例与不相关对的距离持续拉远。

## 检索调优完整落地流程

当系统检索质量不符合预期时，建议按照从低成本到高成本的次序展开排查：

![检索优化全链路排查与落地工程闭环](/images/content-rebuild/ad0b69968ec5652d/fig-6.png)

1. **数据面诊断（低成本）**：
   - 抽样 30 至 50 个未命中的 Case，观察目标段落是否被切断、是否缺少前置主语或层级标题。
   - 调整切片大小至 256~512 Token，设置 10%~20% 重叠窗口，在切片前拼接入所属章节标题元数据。
2. **调用面诊断（极低成本）**：
   - 核对使用的模型是否要求 Query 携带指令前缀（例如 `BAAI/bge` 系列）。
   - 确保仅在 Query 端添加指令，文档入库端保持原始文本，且检索计算前向量已做归一化。
3. **架构面升级（中等成本）**：
   - 评估 Top-50 或 Top-100 召回池中是否包含正确答案。若包含但排序靠后，接入轻量级 Cross-Encoder 实施重排。
   - 结合 BM25 与稠密向量进行混合检索，避免单一向量对特定编码或缩写的漏检。
4. **模型微调（高成本，兜底手段）**：
   - 若 Top-100 召回率依然低下且专有名词识别严重失真，收集数百至数千条领域问答对。
   - 挖掘 BM25 或旧模型检索出的高分错误切片作为难负例，基于对比学习微调基础模型。

关于 RAG 全链路评估指标与向量在生成系统中的定位，可参阅 [/fundamentals/embedding/embedding-in-rag.md](/fundamentals/embedding/embedding-in-rag.md) 与 [/interview/rag-interview/rag-embedding.md](/interview/rag-interview/rag-embedding.md)。
