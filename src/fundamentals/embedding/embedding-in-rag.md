在[《Embedding 如何表示语义相似度？》](/fundamentals/embedding/embedding-similarity.md)中，我们了解了高维向量如何通过夹角或距离来表达文本之间的语义相关性。在实际开发中，这一技术最典型的应用场景之一就是**检索增强生成（Retrieval-Augmented Generation，简称 RAG）**。

用一句话概括 Embedding 在 RAG 中的核心作用：**它将非结构化的自然语言文本转换成固定长度的稠密数值向量，让计算机能够通过低延迟的数学计算，在海量私域资料中快速找出与用户提问语义最相近的参考段落，再提供给大语言模型作为回答事实依据。**

以企业财务问答为例：员工提问“*公司买软件怎么开专票？*”，而内部制度文件中的原文是“*企业账户增值税专用发票开具需在财务后台提交营业执照与开票资质证明*”。这两句话在字面上几乎没有重叠词汇（“公司/买软件/开专票”与“企业账户/增值税专用发票/资质证明”），传统基于关键词字面匹配的搜索很容易漏掉这条内容；但 Embedding 模型在训练中学习了词语的上下文搭配，能够将它们映射到相近的向量位置，从而被检索系统准确命中。

## RAG 检索流程：离线文档处理与在线查询匹配

大语言模型的上下文窗口容量有限，且输入序列越长，预填充（Prefill）阶段的计算与内存开销就越大。如果把几十万字的公司资料全部塞进输入框，既昂贵又缓慢，还会分散模型的注意力。RAG 的思路是：**先按问题检索出最相关的少量文本片段，再把这些片段与问题拼装后送给大语言模型**。

为了兼顾检索质量与响应速度，现代 RAG 系统通常采用**双塔检索（Bi-Encoder）**思路：文档的向量化与查询的向量化彼此解耦，分别在离线与在线两个阶段运行。

![RAG 双塔架构中离线摄入与在线检索的解耦时序](/images/content-rebuild/74c3848790922db8/fig-1.png)

### 1. 离线文档摄入阶段（Document Ingestion）

知识库建立或更新时，需要提前将文档转换为可检索的数据结构，这个过程不占用用户在线提问的时间：

1. **解析与清洗**：从 PDF、Word、Markdown 等格式中提取纯文本，过滤掉无关排版代码与噪声乱码。
2. **文本切块（Chunking）**：整本文档无法直接生成单一向量。如果将万字长文直接池化为一个向量，局部关键细节会被整体语境稀释，难以精准匹配细小提问；但分块本身也只是工程折中，并不能天然保证语义边界绝对完整。通常工程上会按特定长度（如几百个 Token）并保留一定重叠窗口（Overlap）将其切分为多个片段（Chunk）。
3. **向量化编码**：调用 Embedding 模型，将每个切块分别编码为一个固定维度的数值向量 $\mathbf{d} \in \mathbb{R}^d$（常见维度如 768、1024、1536 等）。
4. **入库与建索引**：将向量及其原始文本、元数据（文档名、章节、页码等）存入向量数据库，并根据数据规模构建向量索引以加速后续搜索。

### 2. 在线查询与检索阶段（Query Serving）

用户在终端发起交互时，系统通常需要在几十至几百毫秒内完成响应：

1. **提问向量化**：系统使用与离线阶段**完全一致**的 Embedding 模型，将用户的提问文本编码为一个查询向量 $\mathbf{q} \in \mathbb{R}^d$。
2. **相似度匹配**：向量检索组件计算 $\mathbf{q}$ 与库中已存文档向量 $\mathbf{d}_i$ 的相似度（常用内积或余弦相似度）。数据量较小时可以直接进行全量暴力比对；数据量达数十万甚至数千万级别时，则利用近似最近邻索引（ANN）以毫秒级延迟捞出最相似的前 $K$ 个文本块（Top-K）。
3. **结果返回与组装**：提取这 $K$ 个文本块的原文，连同用户问题一起组装为完整的 Prompt，交由生成模型推理。

在这一流程中，文档向量只需在入库时计算一次并持久化存储，在线阶段模型只需对用户的单条查询做一次前向计算，有效避免了每次查询都要扫描全量长文本的高额算力消耗。

## 向量匹配计算：从文本输入到 Top-K 召回

理解从文本字符到最终召回候选切片的过程，有助于在检索效果不佳时快速定位问题。

![Query 文本投影至高维隐空间与超球面 ANN 拓扑检索](/images/content-rebuild/74c3848790922db8/fig-2.png)

### 1. 文本到向量的状态转化

当用户提交提问时，计算经过以下步骤：

1. **分词（Tokenization）**：自然语言被分词器映射为整数序列 $T = (t_1, t_2, \dots, t_m)$。
2. **编码器计算**：Transformer 编码器输出每个位置的隐层向量矩阵 $\mathbf{H} \in \mathbb{R}^{m \times d}$。
3. **池化压缩（Pooling）**：通常使用平均池化（Mean Pooling）对整个序列求均值，将矩阵压缩为单个向量 $\mathbf{v}_{raw} \in \mathbb{R}^d$。
4. **$L_2$ 归一化（Normalize）**：
   $$\mathbf{q} = \frac{\mathbf{v}_{raw}}{\|\mathbf{v}_{raw}\|_2}$$
   归一化后向量模长为 1。当库中文档向量 $\mathbf{d}$ 在离线入库时同样完成 $L_2$ 归一化（$\|\mathbf{d}\|_2 = 1$）时，两者的内积在数学上严格等价于余弦相似度：
   $$\mathbf{q} \cdot \mathbf{d} = \cos(\theta)$$
   这省去了在线阶段每次计算余弦相似度时重复计算模长并做除法的开销，大幅简化了向量数据库在大规模召回时的运算步骤。

### 2. 暴力比对（kNN）与近似检索（ANN）的选择

* **暴力比对（Flat / Exact Search）**：对数据库内全部 $N$ 个向量逐一计算内积并排序。其时间复杂度为 $O(N \cdot d)$。当文档切块数量只有数百或数千条时，现代 CPU/GPU 的浮点计算速度足够在几毫秒内算完，此时暴力检索不仅开发简单，而且结果绝对精准，不存在召回率折损。
* **近似最近邻检索（ANN）**：当文档切块达到数十万、数千万规模时，全量比对计算量过大，就需要引入如 HNSW（分层导航小世界图）或 IVF-PQ（倒排聚类与乘积量化）等算法。它们通过预建图拓扑或聚类划分，跳过无关区域，将检索时间复杂度降至次线性级别。代价是牺牲少量极限召回精度（存在微小的漏检几率），换取吞吐的大幅提升。

### 3. 可验证小实验：用 Sentence Transformers 运行检索闭环

下面的 Python 代码演示了一个不依赖外部向量数据库的最小检索逻辑：

```python
import torch
from sentence_transformers import SentenceTransformer, SimilarityFunction

# 1. 加载嵌入模型，并指定使用内积（Dot Product）计算相似度
model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")
model.similarity_fn_name = SimilarityFunction.DOT_PRODUCT

# 2. 准备知识库文本切块
corpus_chunks = [
    "企业账户增值税专用发票开具需在财务后台提交营业执照与开票资质证明。",
    "个人用户购买付费会员后，可在订单中心直接申请普通电子发票，通常于1个工作日内开出。",
    "订单发货周期通常为付款后的24至48小时，遇法定节假日将顺延发货。",
    "增值税发票一经开具不可擅自修改，如抬头错误需联系人工客服发起作废重开流程。"
]

# 对切块进行编码，并开启 L2 归一化
chunk_embeddings = model.encode(corpus_chunks, normalize_embeddings=True)

# 3. 准备用户提问并编码归一化
user_query = "公司买软件怎么开专票？"
query_embedding = model.encode([user_query], normalize_embeddings=True)

# 4. 计算余弦相似度矩阵（归一化后的内积即为余弦相似度）
similarity_matrix = model.similarity(query_embedding, chunk_embeddings)
scores = similarity_matrix[0]

# 5. 提取相似度最高的 Top-2 切块
top_k = 2
top_results = torch.topk(scores, k=top_k)

print(f"用户提问: {user_query}\n")
for rank, (score_tensor, index_tensor) in enumerate(zip(top_results.values, top_results.indices), 1):
    idx = index_tensor.item()
    score = score_tensor.item()
    print(f"第 {rank} 名 [相似度: {score:.4f}] 切块 #{idx}: {corpus_chunks[idx]}")
```

运行上述代码输出示意如下：

```text
用户提问: 公司买软件怎么开专票？

第 1 名 [相似度: 0.6582] 切块 #0: 企业账户增值税专用发票开具需在财务后台提交营业执照与开票资质证明。
第 2 名 [相似度: 0.5411] 切块 #3: 增值税发票一经开具不可擅自修改，如抬头错误需联系人工客服发起作废重开流程。
```

通过该实验可以直观看到：尽管提问中未直接出现“增值税专用发票”，模型依然凭借对“专票”与“增值税专用发票”的语义理解，准确将切块 #0 排在最前。

## 组装生成输入：检索切片如何注入生成模型

Embedding 检索阶段的产物不是答案，而是包含参考文本和相似度分值的离散结构：`[(Chunk_0, Score_0), (Chunk_3, Score_3)]`。系统接下来需要通过结构化模板将其与用户提问拼装成最终提示词。

![检索候选 Chunk 结构化注入 LLM 上下文 Prompt 拼装流程](/images/content-rebuild/74c3848790922db8/fig-3.png)

### 1. 结构化 Prompt 注入

为了避免大模型将检索出的参考内容与用户指令产生混淆，工程实现中通常使用明确的标签或分隔符隔开各区块：

```text
<system>
你是一名严谨的企业助手。请仅根据下方提供的【参考背景信息】回答用户的【当前问题】。
如果参考背景信息未包含推导出答案所需的完整事实，请明确回复“当前资料不足以回答该问题”，不要推测编造。
</system>

<reference_context>
[参考片段 1] 企业账户增值税专用发票开具需在财务后台提交营业执照与开票资质证明。
[参考片段 2] 增值税发票一经开具不可擅自修改，如抬头错误需联系人工客服发起作废重开流程。
</reference_context>

<user_query>
公司买软件怎么开专票？
</user_query>
```

### 2. 职责分工边界

在完整流水线中，两类模型承担不同的分工：
* **Embedding 模型**：负责**空间映射与大范围初筛**。它只计算几何向量相关性，不推演复杂因果，核心目标是从海量数据中把高度相关的候选片段筛选出来。
* **大语言生成模型（LLM）**：负责**上下文理解与语言生成**。它在筛选后的紧凑上下文内，阅读参考事实、辨析条件、综合上下文，并生成符合逻辑的自然语言回答。

两者各自独立，通过输入输出接口协作，互不共享内部参数。

## Embedding 检索的典型失效场景

使用稠密向量检索虽然解决了同义表达匹配的问题，但在特定场景下也会引入新的问题。当 RAG 系统找不到相关内容时，通常需要优先排查以下三类检索失效：

### 1. 切块尺寸不当导致的未命中

切块大小直接影响向量所承载的信息密度：
* **切块过大（例如单块包含数千 Token）**：由池化机制的均值计算特性决定，过长文本的向量会被迫混入整篇文档的所有主题，局部特定的关键条件或细小数值在向量中所占的权重被稀释，导致针对具体细节的提问相似度偏低，无法被 Top-K 召回。
* **切块过小（例如单块仅一二十个词）**：容易生硬切断前后文关联。例如前一个切块写着“该行为将被严肃处理”，而具体违规行为“严禁私自导出生产数据库备份”被切到了后一个切块。前一个切块缺乏完整主谓结构，向量表征漂移，系统便无法通过相关意图召回它。

![切片过长稀释与过短断裂导致检索未命中的因果对比](/images/content-rebuild/74c3848790922db8/fig-4.png)

### 2. 多主题混杂与领域歧义

* **单块混杂多主题**：如果一个切块同时记录了“年假结转规定”与“报销流程”，向量会处于两个语义主题的折中区域。无论是单独搜索年假还是报销，其相似度得分都可能低于单一主题的切块。
* **专业缩写歧义**：例如“ROC”在医学语境下通常指“受试者工作特征曲线（Receiver Operating Characteristic）”，在金融分析语境下则常指“资本回报率（Return on Capital）”。如果通用的 Embedding 模型在训练数据中偏向某一方，在特定专业领域的检索就容易偏航。

### 3. 反义逻辑与否定词钝化

常见通用 Embedding 模型在对比学习训练时，主要依赖上下文共现关系。因此，语义相反但高频出现在相同语境中的词句，其向量距离往往也十分接近：

* 切块 A：“*允许在获得授权后导出生产数据。*”
* 用户提问：“*我可以直接导出生产数据吗？*”
* 切块 B：“*严禁在任何情况下导出生产数据。*”

在很多通用向量模型中，切块 A 与切块 B 与提问的余弦相似度可能相差无几，甚至切块 B 因词汇重合度更高而排在前面。Embedding 无法天然分辨命题的真假与“禁止/允许”这一逻辑反转。如果只依赖相似度，系统容易召回逻辑完全相悖的参考内容。

![反义逻辑与否定句在向量检索中产生高相似度伪召回的失败分析](/images/content-rebuild/74c3848790922db8/fig-5.png)

## 认识 RAG 的边界：检索正确不等于生成完全正确

有些开发者容易产生一种直觉误区：“只要接入了 RAG 知识库，系统就能 100% 杜绝事实错误”。

RAG 改变的只是大模型的输入条件——给它提供了额外的参考资料。但在实际运行中，**即便 Embedding 检索准确命中了相关切块，生成模型依然可能在最终回答时偏离事实**。这主要源于以下四种情况：

![切片命中但 LLM 依然发生生成错误的四种因果场景分解](/images/content-rebuild/74c3848790922db8/fig-6.png)

### 1. 召回切块之间存在事实冲突（Context Contradiction）
当知识库内存在不同历史版本的文件时，系统可能同时召回新旧规则。例如：
* 切块 1（2022 年文件）：“差旅餐补标准为每日 100 元。”
* 切块 2（2024 年文件）：“差旅餐补标准调整为每日 150 元。”

Embedding 检索只看语义相关度，无法自动判断文件版本的生效时间与行政效力，会将两条内容一并召回。生成模型如果缺乏对版本元数据的明确指导，可能会随机采信已废止的规则，甚至综合写出“餐补在 100 到 150 元之间”的错误回答。

### 2. 注意力衰减（Lost in the Middle）
大语言模型处理长上下文时，对输入内容不同位置的关注程度存在差异：通常对开头（首因效应）和结尾（近因效应）的内容保持较高的注意力激活，而对夹在长上下文中间的段落关注度较低。如果正确的事实切片刚好被拼接在 Prompt 的中间位置，模型在自回归解码时有可能忽略该事实，转而依靠自身的内部参数记忆来补齐回答。

### 3. 模型预训练记忆的强行干扰
如果企业私域知识库中的定义与公网通用常识发生冲突，模型自身的预训练权重记忆可能会与输入的上下文发生竞争。例如，企业内部将一个考勤系统命名为“火星计划”，虽然切块明确写着“火星计划负责考勤打卡”，但模型在生成时受预训练知识的强先验影响，仍有概率联想并输出与航天探测相关的胡言乱语。

### 4. 复杂多跳推理断裂（Multi-hop Reasoning）
现实业务问题常需要综合多步信息推导。例如询问“*现任市场部总监毕业于哪所大学？*”：
* 事实 1 记录在组织架构文档：“现任市场部总监是张明。”
* 事实 2 记录在简历库：“张明于 2012 年毕业于浙江大学。”

单次向量检索以原始问题作为 Query，能召回与“市场部总监”相关的切块，但很难在第一轮直接匹配到没有“总监”字样的张明个人学历切块。单步 Embedding 检索无法自主完成跨文档的链式因果推导，这需要借助后续的多步检索或智能体（Agent）工作流来弥补。

## 总结与延伸阅读

在 RAG 架构中，Embedding 负责将非结构化文本映射为高维数值向量，把复杂的自然语言筛选转化为可计算的几何距离比对。它扮演着低延迟、大范围粗筛过滤器的角色。

需要明确的是：**向量相似度高不代表命题逻辑一致，提供参考证据也不等于生成模型能彻底避免偏离事实。**
