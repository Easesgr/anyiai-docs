在企业的技术方案、测试报告和财务白皮书中，关键信息往往不是纯文字，而是系统架构图、业务流转图、带有趋势线的折线图，或者是排版复杂的跨页表格。

如果直接沿用纯文本检索增强生成（RAG）管道，用传统的文本解析器把 PDF 转换成纯字符串，系统往往会答非所问。要让大语言模型看懂并准确引用这些图表，就需要重构从切分、索引到生成的完整流程。理解多模态 RAG 的核心，在于搞清楚两件事：**什么时候把图片转成文字来处理**，**什么时候直接使用原生多模态向量与原图**，以及如何在切分阶段把图片和它的上下文牢牢绑定在一起。

## 贯穿例子：一份带架构图的部署手册

为了直观理解多模态 RAG 的各个环节，我们以一份真实的《支付网关容灾部署手册》作为贯穿示例。这份手册的某一页包含三部分内容：

1. **正文段落**：“……系统在遇到上游渠道超时时，会触发重试分流机制。具体状态转移路径参见图 3-1。”
2. **图 3-1（时序流程图）**：图中包含三个方框组件（网关、重试队列、死信队列）和若干带箭头的连线。其中一条连线上标有明确条件：`[超时 > 3s 且重试次数 >= 3] -> 投递至死信队列`。
3. **图下方表格**：列出了各个队列的容量上限和报警阈值。

当运维人员提问：“系统在什么条件下会把请求送进死信队列？”时，纯文本 RAG 会遇到什么困难？多模态 RAG 又该如何处理？

## 纯文本 RAG 面对图文文档的三种常见断裂

传统的纯文本 RAG 假定文档中的所有有效信息都可以被线性抽成纯文本。当解析器遇到上述手册时，通常会直接丢弃像素，或者简单运行 OCR 提取出孤立字符。这会导致三种常见的信息丢失：

1. **连线与流向断裂**：图 3-1 中的核心逻辑藏在连线的箭头指向和判断分支中。纯文本 OCR 只能扫出文字碎片（如 `网关`、`重试队列`、`死信队列`、`超时 > 3s`），但无法表达“谁连向谁”以及“在哪个条件下流转”。提取出的文字变成了一堆无序词汇。
2. **图表数值与坐标对应关系断裂**：在性能测试折线图中，折线上的拐点和峰值（例如横轴 14:00 对应纵轴 5000 QPS）依赖几何坐标。纯文本提取器通常只能抓取刻度数字，大模型无法反推出哪一个时间点对应哪一个数值。
3. **正文与图表指代悬空（Dangling Reference）**：分块处理（Chunking）如果仅按固定字符数切分，经常把“具体状态转移路径参见图 3-1”切入 Chunk A，而把图 3-1 后续的 OCR 文本或表格切入 Chunk B。检索阶段一旦只召回了 Chunk A，大模型就会因为“看不到图 3-1”而产生幻觉，或者直接回答手册未说明。

![纯文本 RAG 在富媒体文档中的断裂示意图：展示页面解析时文字被抽取而流程图拓扑与表格数值丢失导致的断裂](/images/content-rebuild/7515a1c87cd499ff/fig-1.png)

为了解决这些问题，目前主要有两条架构路线：**图像文本化管道**与**原生多模态向量管道**。

## 路径一：图像文本化管道（OCR + Caption）

图像文本化管道是一种与现有纯文本搜索系统兼容的方案。其思路是：**在预处理阶段，把非文本的图片与图表转成描述性文字，后续继续使用标准的文本向量库和纯文本大语言模型（LLM）**。

### 运作流程

1. **版面解析（Layout Analysis）**：识别 PDF 页面中的正文段落、标题、表格与独立图片区域。
2. **图表转文本**：
   - 表格区域：通过表格解析工具还原为 Markdown 表格或 JSON。
   - 架构图与图表区域：使用 [OCR 与文档理解模型](/fundamentals/multimodal-basics/ocr-doc-understanding.md) 提取图内文字，同时调用轻量多模态模型生成一段说明文本（Caption）。例如针对图 3-1 生成：“图 3-1 展示了支付网关容灾流程，包含网关、重试队列与死信队列，当重试达到3次且超时超3秒时转入死信队列”。
3. **组装与纯文本切分**：将生成的描述文本与 OCR 提取的内容，插入到文档原图所在的位置，与周围正文合并为一个完整的文本块。
4. **文本检索与纯文本生成**：使用通用的文本嵌入模型生成向量并存入数据库。检索召回后，把拼好 Caption 的文本喂给纯文本大模型作答。

![图像文本化管道流向图：展示富媒体切片经由 OCR 与 Caption 模型转换为代理文本，入库至纯文本向量库并最终由 LLM 生成答案的完整流向](/images/content-rebuild/7515a1c87cd499ff/fig-2.png)

### 优缺点与适用边界

* **优点**：
  * 成本低：无需为检索和最终生成部署高成本的视觉大模型。
  * 兼容性好：现有的 Elasticsearch、向量数据库以及分块切分工具可以直接复用。
* **缺点与信息损耗**：
  * **细节压缩不可逆**：百余字的描述文本难以覆盖整张图的所有细节。如果 Caption 模型只总结了“展示了容灾流程”，漏掉了某个旁路分支的端口号或报警条件，下游检索就永远无法找到该细节。
  * **错误被提前固化**：如果前置的轻量多模态模型把折线图拐点“下降 15%”误读为“上升 15%”，这一错误就会硬编码进文本库，后续大模型会基于错误文本给出错误结论。

## 路径二：原生多模态向量管道

原生多模态向量管道不在前置阶段把图像压扁成文字，而是直接提取图片的视觉特征并构建向量索引，生成时把原始图像直接送入视觉语言大模型（VLM）。其理论基础建立在图文联合嵌入（如 [CLIP 是什么？](/fundamentals/multimodal-basics/clip.md)）之上。

### 运作流程

1. **图文原生切片**：解析文档时，正文被切成文本块，图表和重要版面被截取为独立的高保真图像片段，并记录页码与坐标等元数据。
2. **统一多模态向量空间**：使用单向量多模态嵌入模型（例如 CLIP、OpenCLIP 等），分别对文本切片和图像切片进行向量化：
   - 文本切片经过文本编码器得到向量 $v_{\text{text}} \in \mathbb{R}^d$；
   - 图像切片经过视觉编码器得到向量 $v_{\text{img}} \in \mathbb{R}^d$；
   - 文本与图像向量映射在同一共享嵌入空间中，并做归一化处理（若采用 ColPali 等多向量模型，则是对各 Token 与图像 Patch 保留多向量并采用晚期交互 MaxSim 计算，而非单向量余弦）。
3. **跨模态近邻检索**：在单向量架构下，当用户输入文本问题 $q$ 时，多模态模型的文本端将其编码为向量 $v_q$。向量数据库通过余弦相似度计算匹配度：
   $$\text{Score}(q, x) = \frac{v_q \cdot v_x}{\|v_q\| \|v_x\|}, \quad x \in \{ \text{文本块}, \text{图像块} \}$$
4. **VLM 端到端生成**：检索召回的结果不仅包含文字，还包含命中的原始图像。系统把文字与原图一并拼接输入下游的视觉语言大模型（如 GPT-4o 或 Qwen-VL，底层机制参考 [多模态大模型怎么工作？](/fundamentals/multimodal-basics/multimodal-how.md)）完成推理解答。

![原生多模态向量管道机制图：展示文本与图像切片经由跨模态 Embedding 映射至统一向量空间，并在召回后直接将原图输送给 VLM 生成的链路](/images/content-rebuild/7515a1c87cd499ff/fig-3.png)

### 优缺点与工程代价

* **优点**：
  * 细粒度特征保留完整：大模型能直接看到原图中的连线、颜色标注和微小图例，适合精细图表问答。
* **工程代价**：
  * **视觉 Token 开销大**：图像切片切分为图像块（Patches）输入给大模型后，会展开为成百上千个 [视觉 Token](/fundamentals/multimodal-basics/visual-token.md)。如果一次检索返回 3 到 5 张图，上下文中的 [Token](/interview/llm-interview/token-basics.md) 消耗和推理延迟会显著增加。
  * **微小字符检索不敏感**：通用的双塔跨模态嵌入模型擅长抓取宏观构图和物体语义，但对图表内部非常微小的特定设备型号（如 `C5-large`）、寄存器地址等文字的敏感度通常不如 BM25 这类关键词检索。

## 图文混合切分：解决正文与图表绑定的窗口设计

无论选择哪条管道，多模态 RAG 的首要工程约束是：**不能把图片和它周围的说明文字完全割裂**。

如果一张架构图单独作为一个切片，缺少上下文解释；而描述它的正文段落在另一个切片，没有配图，两者在检索时都会丢失必要信息。当前实践中常采用**锚点滑动窗口（Anchor-based Windowing）**结合**父子文档结构（Parent-Child Binding）**来组织切分。

![图文混合切分机制示意图：展示父文档分块、子文本切片、图像对象及锚点引用双向指针的结构关系](/images/content-rebuild/7515a1c87cd499ff/fig-4.png)

### 切片数据结构定义

切分系统中的每个切块单元不仅要保存纯文本，还要包含关联的图片路径与元数据：

```python
from dataclasses import dataclass
from typing import List, Dict, Any

@dataclass
class MultimodalChunk:
    chunk_id: str
    parent_page_id: str               # 关联的父页面或整篇文档 ID
    text_content: str                 # 窗口内的文字（含上下文与段落）
    embedded_images: List[str]        # 关联的图像文件路径或对象存储 URI
    image_captions: List[str]         # 用于文本检索辅助匹配的摘要描述
    metadata: Dict[str, Any]          # 页码、坐标框 (bounding_box) 等元数据
```

### 关联滑动窗口切分逻辑

在切分过程中，遇到图片或表格元素时，算法会将其作为一个锚点，向上和向下截取邻近的正文段落，合并构成一个语义完整的切片：

```python
def build_multimodal_chunks(elements: list, window_radius: int = 2) -> list[MultimodalChunk]:
    """
    elements: 版面分析后的文档元素列表，按自然阅读顺序排列
    window_radius: 遇到图片时，向前向后各捕获的正文段落数量
    """
    chunks = []
    for idx, element in enumerate(elements):
        if element.get("type") in ["Image", "Table"]:
            # 1. 获取图表前后的上下文段落范围
            start_idx = max(0, idx - window_radius)
            end_idx = min(len(elements), idx + window_radius + 1)
            
            context_parts = []
            for i in range(start_idx, end_idx):
                if elements[i].get("type") in ["Paragraph", "Heading"]:
                    context_parts.append(elements[i].get("text", ""))
            
            context_text = "\n".join(context_parts)
            
            # 2. 组装图文绑定切块
            chunk = MultimodalChunk(
                chunk_id=f"chunk_img_{element.get('id')}",
                parent_page_id=element.get("page_id", ""),
                text_content=context_text,
                embedded_images=[element.get("image_path", "")],
                image_captions=[element.get("caption", "")],
                metadata={
                    "page_number": element.get("page_number"),
                    "bbox": element.get("bbox")
                }
            )
            chunks.append(chunk)
        elif element.get("type") == "Paragraph":
            # 常规纯文本段落按标准滑动窗口切分，此处略
            pass
            
    return chunks
```

通过这种绑定，当用户查询“容灾重试分流机制”命中图前的文字时，该图表文件会作为切片的附件一并被检出；反之，若用户的意图通过图像向量命中了该图，周围解释说明的文字也会被一起带入生成阶段。

## 多模态 RAG 的三种典型失效模式

即使切分与向量索引设计完备，在召回与生成阶段仍然需要警惕以下三类失败模式，这些现象与 [多模态模型的固有局限](/fundamentals/multimodal-basics/multimodal-limitations.md) 密切相关。

![多模态 RAG 典型失败模式分析图：并列展示分辨率降采样导致细粒度数字模糊、跨页多图依赖导致时空错位、正文与图表证据冲突导致幻觉的三种失效机制](/images/content-rebuild/7515a1c87cd499ff/fig-5.png)

### 1. 降采样导致的微小信息模糊

主流视觉语言大模型为了控制算力消耗，在接收图像输入时通常有最大分辨率或最大视觉 Token 限制。一张分辨率为 $4000 \times 3000$ 的复杂电路图或宽表格，在送入模型前会被缩小或切分成固定网格。
- **成因**：微小字号的芯片引脚编号或财务报表角标在降采样后变得模糊不清。
- **表现**：大模型无法辨认像素细节，但在 Prompt 要求必须给出答案的情况下，往往会根据先验知识捏造一个看起来合理的数值。

### 2. 跨页依赖与排列次序颠倒

在很多专业文档中，图表的说明文字可能在第 2 页末尾，而图表本身跨到了第 3 页上方。
- **成因**：向量检索通常独立评估各个切块的相似度分数。在召回列表中，第 3 页的图可能因语义匹配排在第 1 位，而第 2 页的背景文字排在第 4 位。
- **表现**：如果未对召回上下文按原始文档的阅读顺序重新排序，直接喂给 VLM，模型容易错位理解因果关系。

### 3. 跨模态证据冲突与文本偏好（Textual Bias）

当正文表述与图表数据产生矛盾时，大模型的表现往往偏离直觉。
- **成因**：例如某报告正文由于笔误写着“Q3 净利润增长 25%”，但下方的折线图明确标出净利润为“-5%”。大语言模型在预训练阶段大部分参数由文本语料驱动，当图文并存且证据矛盾时，模型对文本 Token 的注意力权重往往强于视觉信息。
- **表现**：模型倾向于轻信文本描述中的错误结论，直接忽视原图中正确的负增长曲线。

## 工程选型与加权混合检索设计

在具体工程落地中，通常不需要在“全盘纯文本”和“全盘原生图像”之间做极端二选一，而是依据业务场景做分层权衡：

![多模态 RAG 架构选型与混合路由决策树：展示根据图表复杂度、预算约束与高精度要求选择路径一、路径二或混合检索的决策路径](/images/content-rebuild/7515a1c87cd499ff/fig-6.png)

### 两类架构的关键维度对比

| 评估维度 | 路径一：图像文本化管道（OCR + Caption） | 路径二：原生多模态向量管道（跨模态向量 + VLM） |
| :--- | :--- | :--- |
| **主要索引对象** | 文本稠密向量 + 倒排词频索引（BM25） | 多模态共享向量空间（单向量如 CLIP，或多向量晚期交互如 ColPali） |
| **生成模型类型** | 纯文本 LLM | 视觉语言大模型（VLM） |
| **微观图表特征识别**| 较弱，取决于 Caption 与 OCR 的提取覆盖率 | 较强，保留原始像素特征 |
| **单次检索与推理成本** | 低，文本 Token 价格低且请求延迟短 | 较高，单张图带来数百至数千视觉 Token 显存与计算开销 |
| **基础设施迁移改动** | 小，可直接复用成熟的企业文本搜索系统 | 需支持多模态向量存储与图像对象加载机制 |

### 推荐方案：双路召回与加权倒数排序融合（Weighted RRF）

在同时包含复杂专有名词和图表几何信息的知识库中，通常采用文本支路与视觉支路并行的混合召回设计：

1. **双路并行检索**：
   - **支路 A（文本与 OCR）**：基于正文、OCR 内容和轻量 Caption 进行 BM25 与文本稠密向量检索，确保设备型号、人名、缩写等精确词汇不漏召。
   - **支路 B（跨模态视觉）**：基于跨模态嵌入模型匹配用户查询与图像切片，召回语义或形态相关的图表。
2. **加权融合排序（Weighted RRF）**：参考 Qdrant 等现代检索引擎中支持的加权 RRF 算法，将两路结果按相对排序位置进行打分合并：
   $$RRF\_Score(d) = \frac{w_{\text{text}}}{k + r_{\text{text}}(d)} + \frac{w_{\text{vision}}}{k + r_{\text{vision}}(d)}$$
   其中 $r_{\text{text}}(d)$ 和 $r_{\text{vision}}(d)$ 分别为切片在两路检索中的名次，$k$ 为平滑常数（常见默认值为 60），$w_{\text{text}}$ 与 $w_{\text{vision}}$ 为两路分配的权重。
3. **按需挂载图像像素**：在将最终 Top-K 结果注入上下文时，系统可加入判断：只有当视觉路得分高于设定阈值、或者用户问题带有视觉指代词（如“看图”、“图中流程”）时，才将原始图像作为视觉 Token 传给 VLM；否则只携带纯文本与 Caption。这样可以在控制 API 成本和推理延迟的同时，保留处理复杂图像的能力。

## 验收自测

1. 在图像文本化方案中，如果一份财报折线图里有 10 个关键拐点数值，但前置 Caption 仅概括为“该图展示了平稳波动态势”，该缺陷会对下游检索造成什么具体影响？
2. 为什么在处理多模态图文切分时，不建议把图片切块和正文切块完全拆分成独立不相交的数据实体？
