在了解了[大模型推理是什么？](/fundamentals/inference-and-generation/inference-pipeline.md)以及[KV Cache 是什么？](/fundamentals/inference-and-generation/kv-cache.md)之后，很多开发者在实际部署模型时会遇到一个反直觉的现象：在显卡上运行大模型为单用户生成文本时，GPU 核心计算利用率（Compute Utilization）往往只有 10% 到 20%，但每个 Token 的生成耗时却难以下降；而一旦并发请求增加，系统响应又容易出现明显的排队延迟。

大模型推理并不是单一模式的密集计算，提升推理速度也不能只靠堆叠算力芯片。自回归 Transformer 在处理输入和逐步生成的过程中，会触及截然不同的硬件物理瓶颈。本文以一个具体的 70B 模型贯穿全篇，先拆解 Prefill 与 Decode 两个阶段的物理瓶颈，再逐一分析批处理、权重量化、投机采样与底层算子优化四种主流加速方案的工作原理与适用边界。

## 推理性能评估指标：延迟与吞吐量

评估大语言模型的推理性能，不能直接套用传统 Web 服务的每秒请求数（QPS），因为大模型的输入和输出文本长度各不相同，且输出是逐字生成的。业界通常将推理性能拆分为三个核心指标：

1. **首字延迟（Time To First Token, TTFT）**：从系统接收到用户请求，到模型输出第一个 Token 所经历的时间。这一阶段涵盖网络传输、文本分词以及对完整 Prompt 的前向计算（即 Prefill 预填充阶段）。TTFT 直接决定了用户界面首次给出响应的快慢。
2. **单字解码延迟（Time Per Output Token, TPOT）**：在首字输出后，后续每生成一个 Token 所消耗的平均时间（单位通常为毫秒/Token，其倒数即为单请求流式输出速度 Tokens/s）。TPOT 决定了用户在[流式输出](/fundamentals/inference-and-generation/streaming.md)过程中看到的打字流畅度。
3. **系统吞吐量（System Throughput）**：系统在单位时间内处理并输出的总 Token 数量（通常统计所有并发请求合计的 Total Tokens/s）。该指标决定了在高并发场景下单台服务器所能承载的用户规模与算力成本。

```
用户发送请求 ---> [ Prefill 预填充阶段 ] ---> 输出首字 (TTFT)
                                            |
                                            v
                                      [ Decode 阶段: 第 1 个字 ] -> TPOT 1
                                      [ Decode 阶段: 第 2 个字 ] -> TPOT 2
                                      [ Decode 阶段: 第 3 个字 ] -> TPOT 3
                                            ...
                                      [ 输出结束符 EOS ]
```

在优化系统时，单请求延迟（TTFT、TPOT）与系统吞吐量往往存在取舍。例如，加大批处理规模可以大幅提升显卡的总吞吐量，但因为请求排队和单步计算量增加，每个用户的 TTFT 和 TPOT 通常会有所上升。

## 瓶颈二分法：Prefill 算力受限与 Decode 访存受限

根据硬件计算性能分析模型（Roofline 模型），程序运行速度的上限取决于两个因素：**芯片的峰值计算能力（FLOPs）**与**显存带宽（Memory Bandwidth）**。衡量当前任务受限于哪一方的核心指标是**计算强度（Arithmetic Intensity）**，即每从显存读取 1 个字节的数据，片上计算核心能完成多少次浮点运算（FLOPs / Byte）。

自回归 Transformer 推理天然包含两个物理特征完全对立的计算阶段：

### 1. Prefill 阶段：算力受限（Compute-bound）
在 Prefill 阶段，模型需要一次性处理用户输入的完整 Prompt 序列（设长度为 $L_{in}$）。此时，模型的权重矩阵要与输入序列的全部隐层向量同时进行通用矩阵乘法（GEMM）。

模型权重被从高带宽显存（HBM）加载到片上计算单元（SRAM/寄存器）一次，可以同时被序列中的 $L_{in}$ 个 Token 计算复用。计算量（FLOPs）与输入序列长度及模型参数量成正比。当输入序列较长时，计算强度较高，GPU 的张量计算核心全速运转，此时的主要性能瓶颈在于显卡的**峰值浮点计算能力**。

### 2. Decode 阶段：低并发下的访存受限（Memory-bound）
在逐字生成阶段，由于自回归机制要求上一个 Token 产出后才能作为下一步的输入，模型每一步只能生成 1 个新 Token。虽然维护了 KV Cache 避免了历史 Token 的重复计算，但当前步的输入向量长度缩减为 1。矩阵乘法退化为矩阵-向量乘法（GEMV）。

这意味着：**为了计算这单个 Token 的概率分布，GPU 必须将模型的全部权重参数从显存完整搬运到片上计算核心一次。**

* **贯穿算例**：以一个 70B（700 亿）参数的 FP16 精度模型为例，模型权重体积约为：
  $$70 \times 10^9 \times 2 \text{ 字节} \approx 140 \text{ GB}$$
  在单并发请求下，每生成 1 个 Token，就需要从显存搬运 140 GB 权重。而执行的浮点运算量约为：
  $$2 \times 70 \times 10^9 = 1.4 \times 10^{11} \text{ 次 FLOPs} = 140 \text{ GFLOPs}$$
* **耗时推导**：假设使用的是显存带宽为 $2 \text{ TB/s}$（即 $2000 \text{ GB/s}$）的高性能计算卡，暂且忽略 KV Cache 读写与网络激活传输，单次搬运 140 GB 权重的纯硬件时间下限为：
  $$\text{单步搬运时间} = \frac{140 \text{ GB}}{2000 \text{ GB/s}} = 0.07 \text{ 秒} = 70 \text{ 毫秒}$$
  这对应着单流解码速度的理论上限仅为：
  $$\frac{1}{0.07} \approx 14.3 \text{ Tokens/s}$$

如果一张显卡拥有每秒 1000 TFLOPs 的 FP16 算力，计算这 140 GFLOPs 理论上仅需 $0.14$ 毫秒，剩余的 69.86 毫秒计算核心全部在空闲等待显存数据送达。若想深入了解底层访存瓶颈推导，可参考 [大模型推理为什么慢？瓶颈在哪里？](/llm-100/deployment/inference-bottlenecks.md)。

因此，在单并发 Decode 阶段，盲目增加计算核心的 TFLOPs 几乎无法降低 TPOT，**显存带宽才是此时的硬性物理瓶颈**。

## 方案一：批处理演进（解决多并发吞吐瓶颈）

既然单并发 Decode 阶段严重受限于显存带宽，最直接的工程优化思路就是**批处理（Batching）**：将多个并发请求的输入向量组合在一起，模型权重从显存读取一次后，同时为批次内的多个请求完成计算，从而将计算强度成倍提升，让 GPU 从访存受限逐步回到计算受限。

然而，大语言模型生成的文本长度不可预知，传统的批处理方式会产生严重的资源浪费：

### 1. 静态批处理（Static Batching）的缺陷
传统深度学习推理采用静态批处理：多个请求打包在一起送入模型，统一开始、统一结束。
* **填充浪费（Padding Bubbles）**：批次中不同请求的输入和输出长度各异，短请求必须用无意义的 `<pad>` 标记补齐到批次内最长请求的长度，造成算力与显存的无效消耗。
* **长尾等待**：先生成完毕的请求无法提前返回释放资源，必须等待批次内最后一个请求全部生成完成，大幅恶化了短请求的端到端延迟。

### 2. 连续批处理（Continuous Batching）机制
连续批处理（也称迭代级调度，Iteration-level Scheduling）打破了“按请求打包”的限制，改为“按单次生成步（Iteration）打包”：
* **动态插拔**：调度器在模型前向计算的每一步结束后介入检查。当批次中某个请求输出了结束符（EOS）或达到最大长度，该请求立刻完成并退出；等待队列中的新请求随即在下一个生成步插槽补入。
* **消除填充**：配合按需分页管理显存的机制（如 [vLLM 为什么推理速度快？](/llm-100/deployment/vllm-inference.md) 中解析的 PagedAttention），请求在显存中无需分配连续的物理空间，彻底消除了 `<pad>` 填充浪费。新请求的 Prefill 步骤也可以分块插入 Decode 批次中（Chunked Prefill），使得整体吞吐量获得数倍提升。

**适用边界**：连续批处理主要解决多并发场景下的服务器吞吐利用率，在只有单个用户发起的低并发场景下，它并不能减少权重搬运的绝对时间，因而无法提升单用户的 TPOT。

## 方案二：权重量化（解绑单并发访存带宽瓶颈）

对于低并发、单用户交互场景，既然受限于显存带宽，加速的物理手段就是**减少每次前向计算必须从显存读取的字节数**。这就是仅权重量化（Weight-only Quantization）的核心动机。

### 1. 搬运体积与延迟的关系
在常见的半精度（FP16/BF16）格式下，每个参数占据 16 位（2 字节）。如果将权重压缩为低比特整数或微缩浮点格式：
* **INT8 量化**：每个参数占 1 字节，权重体积减小 50%。
* **INT4 / FP4 量化**：每个参数占 0.5 字节（4 位），权重体积减少至原先的 25%。

继续沿用前文的 70B 模型算例：
在 INT4 量化下，参数总搬运量由 140 GB 下降至约 35 GB。在同样的 2 TB/s 显存带宽下：
$$\text{单步搬运时间} = \frac{35 \text{ GB}}{2000 \text{ GB/s}} = 0.0175 \text{ 秒} = 17.5 \text{ 毫秒}$$
单流解码速度的理论上限从约 14.3 Tokens/s 提升至约 57.1 Tokens/s。

```
[高带宽显存 HBM] --- (搬运 4-bit 压缩权重) ---> [计算核心片上缓存 SRAM]
                                                      |
                                                      v
                                           [在线反量化为 FP16]
                                                      |
                                                      v
[输入向量 X (FP16)] ---------------------> [张量核心浮点矩阵乘法 GEMV]
```

### 2. 机制与适用边界
目前主流的推理权重量化方案（如 AWQ、GPTQ）通常采用“量化存储、计算时动态反量化”的设计：模型参数以 INT4 格式存放在显存中以节约显存占用并减少总线带宽搬运，在加载至片上高速缓存（SRAM）后再还原为 FP16，与未经量化的 FP16 激活向量进行浮点乘加运算。

**代价与前置条件**：
* **精度损耗风险**：将数值范围压缩到 4 位容易破坏极端异常值（Outliers）。如果量化算法没有保护好关键通道的权重动态范围，会导致模型困惑度（Perplexity）上升，在代码生成、复杂数学推理等任务中可能出现回答质量下降。
* **并发饱和失效**：量化主要改善低并发下 Decode 的显存带宽瓶颈。如果在高并发下系统已经处于算力饱和（Compute-bound）状态，由于增加了片上在线反量化的计算开销，单纯的权重量化可能不会带来显著加速，甚至可能轻微降低吞吐。

## 方案三：投机采样（打破自回归串行依赖）

自回归解码速度慢的另一个根源在于串行时间依赖：生成第 $N$ 个 Token 必须以第 $N-1$ 个 Token 的输出作为输入，无法在时间轴上直接并行。

投机采样（Speculative Decoding）通过组合一个小巧的草稿模型（Draft Model）和一个大目标模型（Target Model），在不改变输出质量的前提下打破这一串行约束。

### 1. 执行流程三步走
1. **草稿生成（Drafting）**：使用一个体积小很多、运行极快的草稿模型（通常与目标模型共享同一词表），以自回归方式迅速连续生成 $K$ 个候选 Token（例如 $K=4$）。因为小模型参数量少、访存负担轻，草稿生成耗时极短。
2. **并行验证（Verification）**：将这 $K$ 个候选 Token 与原输入拼接，一次性送入大目标模型。由于这 $K$ 个 Token 已经给出，大模型可以采用类似 Prefill 的**并行前向计算**，在单个推理步内直接得出这 $K$ 个位置在目标模型下的预测概率分布。
3. **拒绝判定与回退（Rejection Sampling & Recovery）**：大模型逐个比对草稿 Token 与大模型计算出的条件概率分布。若判定通过则接受该 Token；一旦在第 $m$ 个 Token 处发生分歧并被拒绝，系统直接丢弃第 $m$ 个及其后面的所有草稿，并以大模型的真实概率分布当场采样出一个修正 Token，随后进入下一轮循环。

```
步骤 1 (草稿模型快速串行推测): 
  输入 -> [草稿小模型] -> t_1 -> [草稿小模型] -> t_2 -> [草稿小模型] -> t_3

步骤 2 (目标大模型单步并行验证): 
  [输入, t_1, t_2, t_3] ---> [目标大模型执行一次前向]
                                 |
                                 v
步骤 3 (逐位验证与修正): 
  t_1: 验证通过
  t_2: 验证未通过，由大模型分布重新采样为 t_2_new
  t_3: 废弃
  本轮有效产出: [t_1, t_2_new] (仅用 1 次大模型前向获得了 2 个有效 Token)
```

### 2. 理论保证与边界条件
* **输出一致性**：投机采样采用修改版拒绝采样机制。在数学上可以证明：**只要修正判定准则满足概率转移条件，最终输出序列的统计概率分布与单独由大模型自回归采样的理论分布完全一致**；若使用贪婪解码（Temperature=0），输出结果与单独使用大模型完全相同。因此，草稿模型的能力差异只会改变“草稿被接受的概率”，不会导致最终生成质量受损。
* **边界条件**：如果草稿模型的预测准确率很低（例如遇到代码符号或强逻辑推演），大模型频繁拒绝草稿，那么草稿模型的计算时间叠加大模型的验证前向开销，反而会导致端到端生成延迟比直接用大模型自回归更慢。此外，系统需要显存同时常驻两个模型的权重。

## 方案四：底层算子优化（FlashAttention 与访存减少）

除了请求调度、模型量化与协作架构，在单次前向计算的代码实现层面，核心算子对 GPU 硬件层级缓存的调度方式也会直接改变运行耗时。最具代表性的就是针对自注意力机制的 FlashAttention。

### 1. GPU 存储层级的速度差异
GPU 芯片内部的存储单元有着明确的速度与容量阶梯：
* **显存（HBM / VRAM）**：容量大（24 GB 到 80 GB 以上），但带宽相对较低（通常为 1 到 3 TB/s），访问延迟高。
* **片上高速缓存（SRAM / Shared Memory）**：位于计算核心内部，容量极小（单卡仅几十兆字节），但带宽极高（可达十数 TB/s 至数十 TB/s），访问延迟极低。

### 2. 标准 Attention 的显存往返问题
标准 Self-Attention 的公式为：
$$O = \text{softmax}\left(\frac{Q K^T}{\sqrt{d}}\right) V$$
在朴素实现中，计算流程多次往返显存：
1. 从显存读取 $Q$ 和 $K$，计算得到注意力分数矩阵 $S = Q K^T$，将尺寸为 $(B, H, L, L)$ 的完整矩阵**写出到显存**。
2. 从显存重新读取矩阵 $S$，执行按行 Softmax 归一化，再将结果矩阵 $P$ **写出到显存**。
3. 再次从显存读取矩阵 $P$ 与矩阵 $V$，执行矩阵乘法计算输出 $O$，最后写回显存。

当输入序列长度 $L$ 增加时，$L \times L$ 矩阵的数据体积呈平方级膨胀。GPU 大量时间消耗在漫长的显存读写等待中。

### 3. FlashAttention 的优化机制：分块与在线更新
FlashAttention 的优化目标是**大幅减少对显存（HBM）的读写次数，将尽可能多的计算留在片上 SRAM 中连续完成**：
* **分块计算（Tiling）**：将输入矩阵 $Q, K, V$ 拆分为适合片上 SRAM 尺寸的数据块，分批载入片上缓存。
* **在线 Softmax（Online Softmax）**：利用 Softmax 的数学递推性质，在遍历数据块的过程中动态维护局部的行最大值和分母归一化因子，就地累加更新输出结果，无需在显存中写出中间的 $L \times L$ 大矩阵。

需要明确区分的是：**FlashAttention 并没有降低全自注意力机制本身的理论算术浮点计算量（仍为 $O(L^2)$），它降低的是显存读写（IO）的数据量，将显存访问复杂度从 $O(L^2)$ 降到了 $O(L)$**。在长文本 Prefill 和超长上下文场景下，这种算子融合带来的显存节约和提速尤为显著。

## 推理加速技术全景与选型对比

在实际工程部署中，各种加速方案针对的瓶颈阶段与适用场景有所不同，需要根据具体业务形态进行组合选型：

| 加速方案 | 针对的核心物理瓶颈 | 主要优化指标 | 适用场景与前置条件 | 主要代价与边界 |
| :--- | :--- | :--- | :--- | :--- |
| **连续批处理 (Continuous Batching)** | 请求长度不一时静态打包产生的填充气泡与长尾等待 | 系统吞吐量 (Total Tokens/s) | 多用户高并发请求；需搭配动态显存管理（如 PagedAttention） | 单用户低并发下无法降低单字生成延迟 |
| **权重量化 (AWQ / GPTQ / FP4)** | 单流或低并发 Decode 阶段的显存带宽限制 (Memory-bound) | 单字解码延迟 (TPOT)、显存占用 | 低并发、对单请求延迟要求高的交互式对话 | 极低比特下可能存在微弱精度损失；高并发饱和时收益降低 |
| **投机采样 (Speculative Decoding)** | 自回归生成必须逐字展开的单步串行时间依赖 | 单字解码延迟 (TPOT) | 低并发、追求极致交互打字速度；需准备配套的草稿模型 | 需额外显存容纳草稿模型；草稿命中率低时端到端延迟反而增加 |
| **算子优化 (FlashAttention 系列)** | 中间注意力矩阵在片外显存与片上缓存间的频繁读写 | 首字延迟 (TTFT)、长文本计算效率 | 各种场景均推荐作为底层标配，长文本下收益更明显 | 仅优化访存 IO，不改变算法本身的平方级算术计算量；依赖特定硬件算子支持 |

在典型的线上生产环境中，这些技术通常可以正交组合：使用 FlashAttention 优化底层算子执行，利用 AWQ 或 INT8 对大模型权重进行压缩以降低显存占用与访存带宽需求，通过连续批处理框架支撑高密度的多租户请求，并在算力允许且要求极致响应速度的高优先级接口上开启投机采样。

在解决了推理延迟与吞吐问题后，实际文本生成系统还需防范内容截断、重复死循环等输出异常。关于生成质量控制与异常防御机制，请继续阅读 [大模型生成常见问题](/fundamentals/inference-and-generation/generation-pitfalls.md)。
