下游业务系统与微服务通常需要处理格式严格的机器可读数据（例如 JSON、XML 或 SQL）。如果程序接收到一段带有寒暄、排版自由甚至夹杂未闭合括号的自然语言，解析器会直接报错中断。

大语言模型本质上是逐字预测下一个 Token 概率的生成模型。要让一个基于概率采样的模型稳定输出合规的数据格式，并参与外部业务调用，核心在于两项技术：**结构化输出（Structured Outputs）**与**工具调用（Function Calling）**。

## 贯穿例子：患者挂号信息的提取与调用

为了直观理解整套机制，本文使用一个具体的医院挂号场景作为贯穿例子。

假设用户在对话框中输入：
> “我是李华，今年 34 岁。最近三天一直咳嗽，想挂呼吸内科的号。”

下游系统的目标包含两步：
1. **提取结构化数据**：将自然语言转换为严格的 JSON 对象：
   ```json
   {
     "name": "李华",
     "age": 34,
     "department": "呼吸内科"
   }
   ```
2. **调用外部接口**：根据提取出的参数，调用医院后台挂号服务 `create_appointment(name="李华", age=34, department="呼吸内科")`。

下面我们来看大模型在处理这类任务时会遇到什么问题，以及技术上如何一步步解决。

---

## 自由生成为何容易导致程序崩溃

大模型在生成文本时，是在词表（通常包含数万到十几万个 Token）中根据概率分布逐个采样。模型本身并不内置 JSON 解析器，它只是预测“看起来最合理”的下一个字符片段。

直接让模型输出 JSON 时，常常会出现以下四类破坏下游解析的问题：

1. **前缀闲聊与礼貌用语**：模型往往倾向于在开头输出“好的，为您整理的信息如下：”，或者在末尾附带“请确认信息是否正确”。标准 JSON 解析器在第一个字节遇到非 `{` 字符时就会直接抛出语法异常。
2. **括号与闭合符缺失**：复杂或嵌套的 JSON 需要严格配对的 `{}` 与 `[]`。如果模型生成过长，或者触发了最大输出长度限制（`max_tokens`），文本会在半途中断，留下未闭合的结构。
3. **非法转义**：当字段内容本身包含双引号、换行符等特殊字符时，模型若直接输出未加反斜杠转义的双引号（如 `"主诉": "咳嗽"伴有头痛""`），会破坏 JSON 的字符串边界，导致解析中断。
4. **字段名漂移**：系统定义的数据模式（Schema）要求字段名为 `department`，模型却可能自由发挥输出为 `dept` 或 `keshi`，导致下游程序按键名取值时拿到空值（`None` / `KeyError`）。

```text
# 下游解析器崩溃的典型输出示例
好的，提取出的患者信息如下：
{
  "name": "李华",
  "age": 34,
  "complaint": "主诉"咳嗽三天"，伴有低烧",  <-- 未转义的引号导致语法损坏
  "department": "呼吸内科"
                                           <-- 达到长度限制提前中断，缺失闭合大括号
```

![自由文本输出导致下游解析崩溃场景](/images/content-rebuild/c9887e2e98745552/fig-1.png)

如上图所示，只要模型的输出混入了自由文本前缀或缺少结束符号，下游的语法解析器就会直接中断业务调用。

## 方案一：提示工程与监督微调（概率软引导）

最容易想到的方案是通过提示工程（Prompt Engineering）或微调（SFT）来规范输出。

### 提示与微调的运作机制

开发者可以在提示词中定义 JSON Schema，添加“仅输出合规 JSON，不要包含任何前缀和后缀”的指令，并给出几个标准的示范样例（Few-shot）。更进一步，服务商可以通过包含海量标准 JSON 数据集的指令微调，让模型学习在特定指令下抑制闲聊倾向（早期的 JSON Mode 主要是这种实现）。

这种做法的机制是：**改变模型在每个生成步上的条件概率分布，让符合格式的 Token 拥有更高的被选概率**。

<ReadMoreLock />

### 概率软引导为什么无法彻底杜绝报错

只要模型的采样范围仍然覆盖整个词表，输出合规性就仍然是一个概率问题，不能算作确定性保证：

- **长序列的概率衰减**：为了说明问题，我们可以做一个简化的教学假设——假设生成一个完整的 JSON 需要 200 个 Token，每一步输出合规字符的概率独立且恒定为 $99.9\%$。此时全序列 200 步完全合规的概率为 $0.999^{200} \approx 81.8\%$。虽然真实生成中每一步存在上下文依赖，并非严格独立，但这一算例直观展示了只要非零的非法概率尾部存在，随着序列增长，撞上非法 Token 的风险就会累积。
- **生成截断（Max Tokens）**：提示词无法干预推理引擎在达到 `max_tokens` 阈值时的强制熔断。一旦预算耗尽，模型停在半空，依然会产生残缺格式。
- **注意力漂移**：当提示词上下文非常庞大时，模型可能会受到其他文本的语义干扰，在某个键名或分隔符处发生偶发格式漂移。

![概率软引导机制与其失效模式](/images/content-rebuild/c9887e2e98745552/fig-2.png)

从上图可以看到，概率软引导只是抬高了合法 Token 的概率高度，但非法 Token 的概率并未降为零，自回归的长分支中依然潜藏着格式损坏的可能。

## 方案二：语法约束解码（Constrained Decoding）

为了从机制上解决格式破损，现代推理引擎（如 Outlines、llama.cpp 的 Grammar 引擎，以及商业大模型 API 的 Strict JSON 模式）引入了**语法约束解码（Constrained Decoding）**。

它的核心逻辑在于：**不再寄希望于模型“自觉选择”合规字符，而是在自回归采样的每一个生成步，通过状态机在输出层强行剔除所有会导致语法非法的 Token。**

### 状态机与文法规则

在计算机理论中，JSON Schema 或编程语言可以被形式文法精确描述：
- 简单的正则文法可以通过**确定性有限状态自动机（DFA）**追踪。
- 包含任意层级配对括号、嵌套对象的 JSON，则属于上下文无关文法（CFG），需要使用**下推自动机（Pushdown Automaton）**或维护一个语法解析状态栈来追踪括号配对深度与语法位置。

状态机在每一步都知道当前处于什么阶段：是在对象开头、键名引号内、冒号分隔符后、数值输入中，还是等待右括号闭合。

### Logits 掩码（Logit Masking）流程

结合 [大模型推理是什么？](/fundamentals/inference-and-generation/inference-pipeline.md) 中介绍的解码循环，约束解码在每一步实施以下操作：

1. **前向传播计算原始 Logits**：模型计算出词表中所有 Token 的未归一化对数得分向量 $\mathbf{z}_t$。
2. **状态机确定合法候选集**：状态机根据当前已生成的文本前缀，检查词表中的每一个 Token。只有拼接该 Token 后仍然能符合文法规范的词，才被纳入合法集合 $V_{\text{valid}}$。
3. **施加负无穷掩码**：将不在合法集合内的所有 Token 对应的 Logit 强制设为负无穷大（$-\infty$）：
   $$\tilde{z}_{t, i} = \begin{cases} z_{t, i}, & \text{if } i \in V_{\text{valid}} \\ -\infty, & \text{if } i \notin V_{\text{valid}} \end{cases}$$
4. **Softmax 归一化与采样**：
   $$P(y_t = i) = \frac{e^{\tilde{z}_{t, i}}}{\sum_{j \in V} e^{\tilde{z}_{t, j}}}$$

经过此项计算，所有非法 Token 的采样概率被数学强制归零。模型想输出闲聊词或破坏语法的字符，在物理采样层已经没有任何概率可能。

![状态机约束解码的 Logits 掩码机制](/images/content-rebuild/c9887e2e98745552/fig-3.png)

### 逐步演练：提取患者挂号信息

以生成 `{"name": "李华", "age": 34}` 为例，观察状态机的每步控制：

- **第 1 步（初始状态）**：状态机只允许 JSON 起始符。此时词表中除 `{` 以外的所有 Token 全部被掩码为 $-\infty$。模型只能输出 `{`。
- **第 2 步（期望键名）**：必须输出满足模式的键名。此时合法的 Token 路径被限制在 `"name":` 相关的前缀上，任何闲聊中文、数字都被屏蔽。
- **第 3 步（期望姓名字符串）**：状态机允许输入合法 UTF-8 字符并等待闭合双引号。采样生成 `"李华"` 后，状态机转移到逗号或结束符检测。
- **第 4 步（键名与数值）**：输出 `, "age":` 后，状态机进入整数接收状态。此时中文字符、字母、小数点全部被设为 $-\infty$，仅数字字符 `0-9` 允许保留概率。模型采样输出 `34`。
- **第 5 步（闭合与终止）**：字段输出完毕，状态机仅允许闭合大括号 `}`，随后仅允许序列结束符（`<eos>`）。模型正常停止。

在整个生成链路中，只要最大输出长度没有被强行截断，产出的文本在文法结构上必然是严格合法的。

### 最小化掩码机制模拟（Python）

下面用一段简短的 Python 代码模拟 Logit 掩码的执行过程：

```python
import numpy as np

def softmax(x):
    e_x = np.exp(x - np.max(x))
    return e_x / e_x.sum(axis=-1, keepdims=True)

# 模拟一个小型词表与模型输出的原始得分
vocab = {0: "{", 1: "好的，为您整理：", 2: '"name":', 3: '"李华"', 4: "}"}
raw_logits = np.array([1.5, 4.2, 0.3, -0.5, -1.0])

# 状态机当前处于起始步，规定只能以 "{" 开头
valid_token_ids = {0}

# 施加掩码：将非合法 Token 置为负无穷
masked_logits = np.copy(raw_logits)
for token_id in vocab:
    if token_id not in valid_token_ids:
        masked_logits[token_id] = -np.inf

probs = softmax(masked_logits)

print("未加约束时的最高分词:", vocab[np.argmax(raw_logits)])    # 输出: "好的，为您整理："
print("约束掩码后的最终采样词:", vocab[np.argmax(masked_logits)])  # 输出: "{"
print("闲聊词采样概率:", probs[1])                                # 输出: 0.0
```

## 约束解码的代价：延迟与性能开销

虽然约束解码彻底解决了语法损坏，但它并非零运行成本，在生产部署中主要带来两处额外开销：

1. **首字延迟（TTFT）增加**：在生成第一个 Token 之前，推理引擎必须先将用户提供的复杂 JSON Schema 解析并构建为状态机索引（通常是词表前缀树 Trie）。复杂的嵌套结构可能带来数毫秒到上百毫秒的预编译耗时。
2. **单步解码吞吐下降**：在自回归解码的每一步，系统都要查询状态机并根据当前状态动态构建掩码张量。若优化不佳，频繁的 CPU 状态转移与 GPU 掩码同步可能会拖慢整体吞吐。

现代推理框架（如 vLLM 集成 XGrammar、Outlines）通过预编译跳转表和 GPU 核函数加速，已经将单步掩码的延迟压缩至极低水平，但在高并发场景下依然需要评估其对计算资源的占用。

## Function Calling 是怎么运转的？

在掌握了结构化输出之后，就能理解大模型与外部工具交互的核心功能——**工具调用（Function Calling / Tool Use）**。

很多初学者会误以为大模型可以直接连接数据库、访问网络或运行 Python 脚本。这是对模型职责的误解。

### 核心认知：模型只做决策与填参，宿主负责物理执行

大模型本质上是一个被动接受文本、输出文本的张量计算程序，它本身**没有网络访问权、操作系统进程权限或数据库读写能力**。

Function Calling 的实质是：**模型根据上下文和工具说明，输出结构化的调用参数；运行模型的外部程序（宿主环境 Host Environment）截获这一数据，代为发起网络请求，再将执行结果喂回模型。**

### 标准四步交互时序

```text
+-----------------------+                         +----------------------+
|   客户端 / 宿主程序   |                         |      大模型服务      |
+-----------+-----------+                         +----------+-----------+
            |                                                |
            | 1. 发起请求: 用户提问 + 工具声明(JSON Schema)  |
            |----------------------------------------------->|
            |                                                |
            | 2. 返回结果: 结构化调用意图 (函数名与入参)     |
            |<-----------------------------------------------|
            |                                                |
    [宿主本地验证参数]                                       |
    [执行真实代码/网络请求]                                  |
    [获取执行结果]                                           |
            |                                                |
            | 3. 回写上下文: 追加 role="tool" 消息及执行结果 |
            |----------------------------------------------->|
            |                                                |
            | 4. 最终输出: 综合工具结果，生成自然语言答复   |
            |<-----------------------------------------------|
            v                                                v
```

1. **工具声明（Tool Declaration）**：宿主程序向模型发起请求，在参数中传入工具列表及其 JSON Schema（包含函数名称、功能描述和输入参数类型定义）。
2. **意图生成（Tool Call Generation）**：模型判断完成该任务必须借助外部能力，停止输出普通聊天文本，转而输出包含具体函数名与入参的结构化载荷（例如 `{"name": "create_appointment", "arguments": {"name": "李华", "age": 34, "department": "呼吸内科"}}`）。
3. **宿主执行（Host Execution）**：宿主程序拦截到该输出，核验参数格式，调用真实的医院挂号 API，并拿到返回值（例如 `{"status": "success", "appointment_id": "H20260401-08"}`）。
4. **回写与终答（Completion）**：宿主程序将此返回数据包装为带有 `tool` 角色的消息追加至会话历史，再次调用模型。模型综合真实返回值，输出面向用户的自然语言答复：“已为您成功挂号呼吸内科，预约编号为 H20260401-08。”

![Function Calling 的四步交互回路](/images/content-rebuild/c9887e2e98745552/fig-5.png)

时序划分明确显示了边界：虚线左侧是宿主程序负责的安全校验与物理执行，虚线右侧是模型负责的语义判断与参数生成。

## 语法合规不等于业务语义正确

工程实践中常见的一个误区是：**认为开启了严格约束解码，输出的数据就必定是真实且正确的。**

### 形式文法与事实逻辑的脱节

约束解码只能检查输出的 Token 是否符合文法规则（例如“此处必须是一个合规整数”），但**无法审查数值背后的逻辑一致性与客观事实**：

- **类型正确但数值荒谬**：Schema 规定 `age` 必须是整数，模型可以输出 `"age": -150`。从 JSON 语法角度完全合法，但在生物学和业务逻辑上毫无意义。
- **结构合法但逻辑相悖**：Schema 规定了航班的 `departure_time`（起飞时间）与 `arrival_time`（到达时间）均为 ISO-8601 字符串。模型可以输出格式极度标准的日期，但起飞时间可能晚于到达时间。
- **无中生有的结构化幻觉**：当用户输入未包含某个必要字段，而 Schema 规定该字段非空时，模型在约束解码的强迫下会凭空捏造一个合规的虚假值填充进去。

```json
// 语法校验完全通过，但业务语义完全崩塌的结构体
{
  "name": "李华",
  "age": -150,                                // 负数年龄违背常理
  "appointment_date": "2026-02-30",           // 不存在的公历日期
  "symptoms": "主诉咳嗽三天，但无任何不适"      // 语义自相矛盾
}
```

### 生产环境的多层防御方案

因此，在实际工程中不能仅依赖模型侧的语法约束，必须建立分层防御机制：

1. **推理层约束解码**：使用 Strict JSON Schema 或 Grammar 约束，杜绝语法解析错误、括号缺失与字段名漂移，保证下游解析器不崩溃。
2. **业务层数据验证**：在宿主环境使用 Pydantic 或 Zod 等验证框架，针对业务逻辑设置边界断言（如区间校验 `0 < age < 120`、跨字段时间先后逻辑校验）。
3. **错误反馈与重试回路**：当应用层校验不通过时，捕获具体的校验错误信息（例如 `age must be greater than 0`），将其作为提示写回会话历史，请求模型修正。
4. **硬性兜底**：设定重试上限（例如 2 次），超过上限后转入人工核验或返回降级预设值，避免无效死循环。

关于提示词中如何编写更精确的字段描述，可进一步参考 [结构化输出 Prompt 应该怎么写？](/interview/prompt-interview/structured-output.md)。

## 总结与阅读索引

大模型与下游软件系统的对接，经历了从“靠提示词软约束”到“靠状态机强约束”的演进。提示工程改变的是采样概率，无法消除长尾破损；语法约束解码通过在 Logits 层动态施加 $-\infty$ 掩码，从形式文法层面锁定了语法正确性。工具调用则是基于结构化输出建立的外部协同机制，由模型提供意图与参数，宿主程序负责物理执行。

在掌握了模型如何输出结构化数据与调用工具后，另一个制约大模型处理庞大 Schema 和复杂工具列表的物理瓶颈浮现出来——那就是模型的上下文处理容量。下一讲我们将深入讨论：[上下文长度是什么？](/fundamentals/inference-and-generation/context-length.md)。
