在构建大语言模型（LLM）应用时，许多开发者习惯把各种提示词、脚本使用说明和边界规则全部塞进系统提示词（System Prompt）。随着功能增加，上下文窗口很快被大量未激活的规则占满，不仅增加 Token 成本，还会稀释模型的注意力。

根据 [Agent Skills 官方规范](https://agentskills.io/specification)，一个标准的 Agent Skill 是以目录为单位组织的独立功能单元。它通过结构化的元数据让宿主程序在启动时只加载基础描述；在用户显式指定或意图路由命中该任务时，才载入核心指引，并在需要时动态读取关联文档或执行脚本。本文以一个贯穿全程的 `sql-query-audit`（SQL 静态安全与性能审查）技能为例，解析一个规范的 Skill 应当如何组织目录、编写 Frontmatter 元数据、编排执行步骤并划定安全边界。

## 目录结构与 SKILL.md Frontmatter 字段约束

在 [Agent Skills 官方规范](https://agentskills.io/specification) 中，每一个技能包必须是一个独立目录，其目录名称必须与技能的 `name` 字段完全一致。目录内必须包含 `SKILL.md`，并可按需选配脚本、参考资料与静态资源目录：

```text
sql-query-audit/
├── SKILL.md           # 核心规范：元数据与操作指引（必需）
├── scripts/           # 辅助代码：供 Agent 调用的脚本（可选）
│   └── dry_run.py
├── references/        # 扩展参考：详尽的参考规范与错误码（可选）
│   └── syntax_rules.md
└── assets/            # 静态模板：输出样例与表结构模板（可选）
    └── report_template.md
```

`SKILL.md` 的顶部必须包含由三连虚线包裹的 YAML Frontmatter 元数据块，紧接着是 Markdown 格式的正文指引。

![SKILL.md 核心字段与目录结构规范分解](/images/content-rebuild/67832aea5d9d42eb/fig-1.png)

### 核心字段与规范约束

1. **`name`（必需）**：
   - **长度与字符限制**：长度在 1 至 64 个字符之间，仅允许小写英文字母（`a-z`）、数字（`0-9`）和连字符（`-`）。
   - **边界规则**：首尾不得包含连字符，不得出现连续两个连字符（例如 `sql--audit` 属于非法命名），且必须与技能外层目录名保持一致。

2. **`description`（必需）**：
   - **长度与内容限制**：非空字符串，最大长度为 1024 个字符。
   - **作用**：供宿主与模型在意图路由阶段读取，必须明确说明“能做什么”和“何时使用”。

3. **`compatibility`（可选）**：
   - **长度限制**：最大 500 个字符。
   - **作用**：声明运行该技能所需的环境依赖，例如指定系统工具 `compatibility: 需要系统安装 Python 3.10+ 及 sqlparse 库`。

4. **`metadata`（可选）**：
   - **格式**：键值均为字符串的映射字典（`map[string]string`）。
   - **作用**：记录版本号、维护者等自定义信息，例如 `version: "1.1.0"`。

5. **`allowed-tools`（可选，实验性）**：
   - **格式**：以空格分隔的工具名称字符串，例如 `allowed-tools: Bash(python:*) Read`。
   - **约束条件**：官方规范将其标记为实验性字段。它向宿主提供工具使用建议，但实际的工具权限隔离、沙箱限制仍必须由宿主运行时程序实现，不能假设写在此处就天然具备权限阻断能力。关于工具与技能的分工，可参考 [MCP 与 Skills 架构定位辨析](/interview/agent-interview/mcp-vs-skills.md)。

以下是一个符合规范的 `SKILL.md` 头部示例：

```yaml
---
name: sql-query-audit
description: 审核面向 MySQL 8.0 的查询与变更语句，识别全表扫描风险、缺少索引及敏感字段未脱敏问题。当用户请求优化 SQL、评估慢查询隐患或提交上线前 SQL 审核时使用。当用户仅需跨数据库语法转换或需要直接向数据库写入数据时不要使用。
license: Apache-2.0
compatibility: 需要系统安装 Python 3.10+ 及相关解析库
metadata:
  author: data-platform-team
  version: "1.1.0"
allowed-tools: Bash(python:*) Read
---
```

## description 描述工程：意图匹配与排除边界

在支持多技能的 Agent 架构中，系统初始化时通常不会将所有技能的正文全部塞入上下文，而是仅在预留区注入各个技能的 `name` 与 `description`。这个阶段每个技能占用的上下文通常在 100 Token 左右。

此时，`description` 是模型判断当前任务是否应当调用该技能的关键依据。如果描述不清晰，容易引发两类问题：
- **漏触发**：用户提出了明确诉求，但描述中缺乏具体场景词，模型未匹配到技能，直接退回到泛化回答；
- **误触发**：描述过于宽泛（例如仅写“处理 SQL 的工具”），用户在询问通用 SQL 语法常识或要求生成测试数据时，模型也错误激活该技能，造成不必要的上下文消耗。

![description 意图匹配与排除边界流向图](/images/content-rebuild/67832aea5d9d42eb/fig-2.png)

### 编写描述的推荐结构

根据 [Anthropic 智能体构建实践指南](https://www.anthropic.com/engineering/building-effective-agents)，当有多个工具或技能可选时，清晰划定触发范围能有效降低决策冲突。编写 `description` 推荐包含三部分内容：

$$\text{Description} = \text{支持的核心能力} + \text{明确的触发场景与动词} + \text{反向排除条件}$$

#### 模糊写法（不推荐）：
```yaml
description: 数据库相关操作辅助工具，帮助开发者处理 SQL 代码。
```
*问题*：没有指明具体的数据库引擎，没有动作词，也没有说明不适用的范围，模型在面对生成随机数据、修复连接报错等任务时容易误选。

#### 明确写法（推荐）：
```yaml
description: 审核面向 MySQL 8.0 的 DDL/DML 语句，识别缺少索引、全表扫描和敏感字段越权。当用户要求审查慢查询、评估索引命中率或提交上线脚本静态安全检查时使用。当用户要求执行数据写入、数据库备份或纯语法转换（如 Oracle 转 MySQL）时不要使用。
```

明确列出“不要使用”的排除边界，有助于模型在处理边缘请求时做出更稳定的路由判断。当然，这也取决于模型本身的意图理解能力，在多技能数量较多时，仍需建立自动化测试集验证触发准确率。

## 渐进式内容编排：步骤主干与深度资料分离

当宿主根据用户显式指定或意图路由激活某一 Skill 后，才会把该技能的 `SKILL.md` 正文加载进上下文。官方规范建议将主文件的正文控制在 500 行以内，内容通常建议在 5000 Token 以内。

如果把各种数据库方言差异、冗长的错误码对照表或几十页的合规条款全部堆在 `SKILL.md` 中，会迅速挤占上下文窗口，影响模型的长文本注意力。解决此问题的方案是**渐进式披露（Progressive Disclosure）**。

![渐进式披露三层加载机制与 Token 预算流转](/images/content-rebuild/67832aea5d9d42eb/fig-3.png)

### 三层分级加载结构

1. **Level 1（元数据层，常驻）**：包含所有 Skill 的 `name` 和 `description`，用于意图初筛与路由；
2. **Level 2（主干流程层，激活后载入）**：`SKILL.md` 正文，包含任务的前置检查、执行步骤判定树和输出契约；
3. **Level 3（深度资料层，按需读取）**：将细化规则、专有对照表沉淀到外部文件（如 `references/` 或 `scripts/`），主干仅保留条件分支。只有当步骤分支明确需要时，模型才发起工具调用读取对应文件。

需要说明的是，渐进式披露能够降低初始载入成本，但一旦模型调用工具将外部文件读入上下文，后续多轮对话依然会占用相应窗口，并非“完全不消耗上下文”。

![主文件精简与多级参考文档的分离引用模型](/images/content-rebuild/67832aea5d9d42eb/fig-4.png)

### 相对路径引用规则

在 `SKILL.md` 正文中引用辅助文件时，官方规范要求使用以当前技能根目录为基准的**相对路径**，并建议保持一层引用关系，避免多级嵌套：

```markdown
## 审查流程

1. 解析传入的 SQL 语句，提取涉及的表名与 WHERE 条件字段。
2. 检查多表关联与复合索引规则。仅当查询包含 2 个以上 JOIN 条件或包含范围查询组合时，读取 `references/syntax_rules.md` 进行规则核对。
3. 执行静态语法校验：
   运行命令：`python3 scripts/dry_run.py --input <sql_file>`
4. 整理最终审查意见，必须严格按照 `assets/report_template.md` 的模板格式输出。
```

通过把规则细节分离到子文件中，主干指引只需负责流程编排与状态判断，结构更清晰，也便于团队单独维护规则集或测试脚本。

## 输入前置条件与结构化输出契约

为了让 Skill 的输出能可靠接入后续的自动化流程，或者让用户获得一致的体验，在编写正文时必须对输入和输出做形式化约束。

![结构化输入输出约束与校验流水线](/images/content-rebuild/67832aea5d9d42eb/fig-5.png)

### 1. 输入前置声明（Prerequisites）

直接告诉模型在执行前必须检查的要素。如果关键要素缺失，要求模型暂停并主动向用户确认，避免根据概率自行假设或编造：

```markdown
## 输入前置检查
在开始分析前，必须核对以下输入要素：
- 必须包含待审计的 SQL 文本内容；
- 必须指定数据库版本（若用户未声明，默认按 MySQL 8.0 规则处理，并向用户提示默认假设）；
- 若 SQL 中包含多表 JOIN，必须提供相关表的索引定义或 DDL。若未提供，暂停分析并输出：“请提供关联表的建表语句（DDL）以完成复合索引审查”。
```

### 2. 输出契约规范（Output Contract）

在正文中明确规定输出的 Markdown 结构或 JSON 格式，并给出占位模板：

```markdown
## 输出报告契约
审查完成后，必须严格使用以下格式输出，不得省略审计状态与风险等级字段：

```markdown
# SQL 审计诊断报告
- **审计状态**：[通过 / 警告 / 阻断]
- **涉及对象**：`库名.表名`
- **总体风险**：[低 / 中 / 高]

### 缺陷详情
| 规则编号 | 风险级别 | 触发代码片段 | 改进建议 |
| :--- | :--- | :--- | :--- |
| SEC-01 | 高 | `SELECT *` | 请明确列出所需字段 |

### 优化建议说明
[针对全表扫描与索引未命中的修改说明]
\```
```

提供明确的模板能够减少自由文本带来的格式不确定性，方便下游程序提取字段或直接展示在前端界面。

## 防御性规则与异常处理：明确边界与失败分支

在编写 Skill 时需要明确一个事实：**Skill 只是提供给 LLM 的自然语言操作指引，它不是操作系统的沙箱，不能提供真正的强制权限隔离。**

虽然可以在元数据中声明 `allowed-tools`，但系统是否真正拦截未授权调用，取决于宿主运行时的实现（例如使用 LangGraph、MCP Server 或自定义沙箱环境）。关于宿主状态控制与编排，可参考 [LangGraph 官方文档](https://docs.langchain.com/oss/python/langgraph/overview)。在 Skill 正文内编写的防御规则，属于提示词层面的意图约束，必须与程序级权限控制配合使用。

![防御性安全边界与异常处理闭环](/images/content-rebuild/67832aea5d9d42eb/fig-6.png)

### 1. 负面安全约束（Negative Constraints）

避免使用含糊的建议口吻，使用明确的排他性动作指令：

- **只读操作限制**：“本技能仅允许对 SQL 语句进行静态词法解析与模拟执行。严禁在生产或测试数据库中调用任何包含 `INSERT`、`UPDATE`、`DELETE`、`DROP`、`ALTER` 的数据修改指令。”
- **敏感信息脱敏**：“如果执行脚本返回的结果或用户提供的 SQL 包含明文密码、密钥或手机号，在生成报告前必须进行脱敏掩码处理（例如将手机号中间四位替换为 `****`），严禁在最终输出中回显明文。”

### 2. 失败分支与兜底流程

在调用外部脚本或模型处理出现异常时，模型容易产生“忽略报错并自行编造成功报告”的退化行为。因此，正文中必须提供针对非零退出码和异常情况的明确降级分支：

```markdown
## 异常与失败分支处理规程

当执行 `scripts/dry_run.py` 遇到非零退出码（Exit Code != 0）或报错输出时，严格按以下步骤处理：
1. 记录退出码与具体的错误输出（stderr）。
2. 立即终止后续优化报告的生成，不得自行假设该 SQL 语法合法。
3. 按以下格式向用户返回错误排查建议：
   “静态语法检查失败（退出码：{exit_code}）。
   错误原因：{stderr}。
   请检查 SQL 语句是否存在括号不匹配或关键字拼写错误后重新提交。”
```

关于更多具体场景的封装流程与完整工程实现，可在后续章节 [常用任务封装实战](/frontier/agent-skills/skill-encapsulation.md) 中结合端到端案例进一步学习。

## 思考与检验

完成本篇内容后，可以通过以下两个问题检验对 Skill 编写规范的理解：

1. **当一个业务场景的参考文档超过 2000 行时，为什么不应直接把它们全部写在 `SKILL.md` 中？按相对路径拆分后，应该在何时让模型去加载它？**
2. **如果只在 `SKILL.md` 中写下“严禁删除数据库数据”，能否完全保证生产环境的数据安全？在系统工程架构上还需要哪些配合？**
