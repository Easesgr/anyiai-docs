如果让 AI 助手去完成“整理一份季度销售数据报告”的任务，开发者通常会遇到两类典型困境：只给模型提供数据库查询和图表生成的工具，模型往往不知道统计口径、异常值过滤标准或报告排版规范，容易漏步或格式混乱；但如果把几十个业务部门的完整报告撰写规范一股脑全塞进系统提示词，请求上下文又会迅速臃肿，关键指令反而容易被冲淡。

近年来以 `SKILL.md` 为核心载体的 Agent Skills 规范为这类问题提供了解法。但它经常被误解为“新语法的提示词”或“必须按部就班执行的工作流”。要理清 Agent Skills 的定位，我们需要以“整理数据报告”为线索，拆解模型、宿主环境与工具之间的真实协作关系。

## 从“整理数据报告”说起：指导文档与工具执行

在以大语言模型为核心的代理系统中，模型通常在 [Agent 执行循环](/interview/agent-interview/agent-loop.md) 中推进任务：接收目标、分析现状、决定调用工具、获取环境反馈并调整下一步规划。

在“整理数据报告”这个具体任务里，不同组件承担的分工完全不同：

1. **执行动作的工具（Tool）**：
   宿主程序向模型暴露 `query_database(sql)` 和 `generate_chart(data, type)` 两个工具。工具包含函数签名和参数说明，它的作用是**执行具体操作并返回环境真实数据**。但工具本身并不教模型“遇到同比为负时要标红”、“退款数据是否计入销售额”这类业务判断。
2. **常驻会话的提示词（Prompt）**：
   提示词负责全局人设与通用约束，例如“你是一个专业的数据分析助手，语气保持客观”。如果把“销售报告规范”、“库存盘点规范”、“合规审计规范”等所有业务流程全部写入系统提示词，不仅单次请求消耗大量 Token，更会带来严重的 [Agent 上下文管理](/interview/agent-interview/context-management.md) 负担，模型在长篇无关文本中更容易忽视当前的重点约束。
3. **按需查阅的技能规范（Agent Skill）**：
   开发者可以将“销售报告整理”打包成一个独立的 Skill 目录。里面包含一份 `SKILL.md`，写明“何时适用”、“提取销售数据的推荐步骤”、“异常数据的核验清单”以及“报告标准结构”。此外，还可以附带计算环比的辅助脚本或指标解释文件。它就像放在书架上的操作说明书，只有当用户明确要求处理销售数据时，才由宿主提供给模型阅读。

![工程痛点：全量系统提示词与裸工具调用的局限](/images/content-rebuild/f9ab97c7f3aa6a98/fig-1.png)

简而言之，工具是“手和脚”，负责改变外部状态或拉取数据；提示词是“全局身份”，定义基础交互风格；而 Skill 则是“任务操作手册”，按需指导模型在特定情境下如何妥善使用工具。

## 职责、载体与外部动作：核心概念对比

在目前的 Agent 生态中，Prompt、Tool Calling、MCP 与 Agent Skill 常被混在一起讨论。它们并不是规范规定的上下级层级，而是各司其职的协作角色：

| 维度 | 系统提示词 (Prompt) | 工具调用 (Tool Calling) | 模型上下文协议 (MCP) | Agent Skill 规范 |
| :--- | :--- | :--- | :--- | :--- |
| **核心职责** | 设定全局角色、基本原则与交互基调 | 由模型产出参数，通知宿主执行外部功能并返回结果 | 标准化外部工具与数据源的发现与连接方式 | 提供特定领域的任务指导、操作步骤与资源组织规范 |
| **存在载体** | 模型推理请求中的文本序列 | 模型的结构化标记输出与宿主运行时的接口定义 | 应用程序间通信协议（基于 stdio、Streamable HTTP 等传输） | 包含 `SKILL.md` 及可选资源的结构化磁盘目录 |
| **是否直接产生外部动作** | 否（仅影响模型概率生成） | 是（由宿主拦截参数并实际调用系统接口或外部服务） | 否（作为连接通道协助分发调用，本身不定义业务逻辑） | 否（作为文档指引被模型阅读，不直接发起外部系统修改） |

在“整理数据报告”的场景下，这四者的协作链路如下：
- **MCP** 帮系统把远端的企业数仓安全接入进来，告诉宿主当前有哪些数据接口可用。
- **Prompt** 提醒模型“输出结果要严谨，不要虚构数字”。
- **Skill** 是一份《季度销售报告制作指南》，在模型接单后载入上下文，告诉模型先核对退款表、再拉取销售明细、最后用柱状图呈现趋势。
- **Tool Calling** 是模型根据指南，向宿主发出 `query_database(sql="...")` 的具体动作。

![四种机制在任务中的角色卡片与协作关系](/images/content-rebuild/f9ab97c7f3aa6a98/fig-2.png)

工具并不局限于极简的原子操作，也可以包含复杂的内部业务逻辑和状态变化；而 MCP 作为应用层协议，既可以通过本地 stdio 管道工作，也可以走 Streamable HTTP 服务（早期的 HTTP+SSE 为兼容支持），不强制要求持久长连接。理解它们各自的边界，有助于在设计系统时避免重复造轮子。

## 渐进式加载：按需阅读说明书以缓解上下文压力

根据 Agent Skills 规范，一个合规的技能目录至少包含一个 `SKILL.md` 文件，并可按需配备脚本与参考文档：

```text
sales-report/
├── SKILL.md          # 必选：元数据（YAML frontmatter）与指导正文（Markdown）
├── scripts/          # 可选：数据提取或格式清洗等可执行代码
├── references/       # 可选：指标定义字典、字段规范等参考资料
└── assets/           # 可选：报告排版模版等静态资源
```

宿主环境之所以能注册数十个技能而不至于让上下文瞬间被撑满，靠的是**渐进式加载（Progressive Disclosure）**的设计思路。该机制通常将内容拆为三部分按需呈现：

![渐进式加载的三层递进机制时序](/images/content-rebuild/f9ab97c7f3aa6a98/fig-3.png)

### 1. 元数据层（Metadata）
宿主初始化时，通常只读取 `SKILL.md` 顶部的 YAML Frontmatter：

```yaml
---
name: sales-report
description: 规范化提取季度与月度销售数据，清洗退款项并生成可视化分析报告。当用户需要销售汇总或财务报表时使用。
---
```
每个技能的元数据通常占用几十到上百 Token，具体开销取决于描述文本长度和分词器。宿主系统将这些精简目录注入系统上下文，供模型判断当前任务该查阅哪份说明书。注意，将元数据常驻并不等于绝对不会超限，技能目录过多时依然需要通过分类、向量初筛或宿主过滤来进一步控制底噪。

### 2. 指导正文层（Instructions）
只有当用户提出“帮我整理 Q3 销售数据”，且模型或宿主路由命中该任务意图时，宿主才将 `SKILL.md` 的正文内容载入上下文。正文中记录了核心流程、校验规则和边界注意项。规范建议将主文件长度控制在合理范围（推荐正文控制在 500 行以内，Token 量通常建议在 5000 以内），避免说明书本身占用过多窗口。

### 3. 辅助资源层（Resources）
技能目录下的 `scripts/clean_data.py` 或 `references/metrics.md`（指标字典），**在初次激活时通常并不会自动展开塞进上下文**。正文中只保留相对路径说明。只有当模型在推演中发现“需要核对某个特殊部门的口径”时，才通过宿主的文件读取工具或脚本执行环境去调阅该文件。

需要指出的是，按需加载是一种工程上的取舍优化，它能显著减少常驻干扰信息，但并不能在理论上“绝对杜绝上下文溢出”或“彻底消除模型选错技能的概率”。当业务场景本身极其复杂时，模型依然可能由于描述模糊而错选技能，这需要配合清晰的 description 描述与充分的测试来改善。

### 算例示意：全量注入与按需加载的 Token 占用对比

为直观说明两种管理方式的差异，我们建立一个包含 20 个领域技能的测试场景（全部为示意数据）：
- 每个技能的元数据平均为 80 Token；
- 每个技能的主体说明平均为 2500 Token；
- 报告任务还需要查阅一份 4000 Token 的指标参考资料。

在相同的工作量与相同类别的资料开销下，两种方式的处理对比如下：

```python
# 模拟静态全量注入 vs 渐进式加载的 Token 占用开销（示意算例）
num_skills = 20
tokens_metadata = 80
tokens_body = 2500
tokens_ref = 4000

# 方案 A：全量注入（所有技能元数据 + 所有技能正文全部常驻 + 1 份任务参考资料）
full_injection_tokens = (
    (num_skills * tokens_metadata)
    + (num_skills * tokens_body)
    + tokens_ref
)

# 方案 B：按需加载（所有技能元数据常驻 + 仅激活 1 个技能正文 + 1 份任务参考资料）
active_skills = 1
on_demand_tokens = (
    (num_skills * tokens_metadata)
    + (active_skills * tokens_body)
    + tokens_ref
)

print(f"全量加载占用 Token: {full_injection_tokens}")  # 输出：55600
print(f"按需加载占用 Token: {on_demand_tokens}")        # 输出：8100
```

![全量加载与按需加载的 Token 占用对比看板](/images/content-rebuild/f9ab97c7f3aa6a98/fig-4.png)

全量方式将 20 个技能的说明文档一次性全部推入上下文，总开销达到 55600 Token；而按需方式在初始阶段仅挂载元数据目录，命中特定任务后载入当前技能正文与必要资料，总体占用为 8100 Token。这种方式让大部分上下文预算得以留给正在进行的推理与真实业务数据。

## 激活不等于执行：规范指导与代码编排的区别

在工程实践中，容易产生一种直觉偏差：“激活了一个 Skill，就相当于运行了一段工作流代码”。这种理解混淆了**自然语言指导**与**程序状态机**的机制差异。

### 1. Skill 是指导说明，而非硬编码图编排
在 [LangGraph 等低层编排框架](https://docs.langchain.com/oss/python/langgraph/overview) 中，系统的核心特征是**通过预定义代码路径来混合确定性步骤与模型推理步骤**。状态的转移、节点间的分支跳转由 Python/TypeScript 状态图强行约束。如果代码规定“数据查询失败后重试 3 次”，宿主环境就会严格照此执行。

而 Agent Skill 是一份写给模型的**文本规范**。当宿主把《季度销售报告制作指南》注入上下文后，模型获得的只是操作建议。模型后续仍然是在概率驱动下决定“先调哪个接口”、“怎么组织回复”。模型遵循指南的程度受注意力与提示质量影响，并不存在一个外部操作系统直接将文档翻译为不可更改的硬性执行流水线。如果需要严格的故障恢复与审计，仍需结合程序级的 [Agent 错误恢复策略](/interview/agent-interview/agent-error-handling.md)。

![激活与执行链路图：Skill 指导 vs 工作流硬编码编排](/images/content-rebuild/f9ab97c7f3aa6a98/fig-5.png)

### 2. 调度权限取决于宿主实现
在 Skill 的元数据中，虽然规范提供了 `allowed-tools` 字段（如 `allowed-tools: Read Bash(python:*)`），但这属于实验性的工具范围声明，并不等同于操作系统层面的沙盒权限隔离。具体的工具拦截、鉴权与文件读取，完全取决于外部宿主程序（如 Claude Code 或自定义 Agent 运行时）的实现逻辑。

同样地，当宿主把 Skill 文件装载到模型记忆中时，这一“激活”行为本身通常只是文本加载操作，并不直接产生对外部业务数据的修改。至于后续是否调用系统接口，依然由模型根据上下文推理决定。

## 架构选型：普通工具、工作流与 Skill 怎么选

在处理数据报告以及其他业务需求时，不必将所有逻辑都硬塞进 Skill，也不宜把所有流程写死为静态代码。合理的选型应当基于任务对**确定性控制、步骤动态性与领域经验复用**的要求：

![架构选型决策树：普通工具、硬编码工作流与 Agent Skill 的判定路径](/images/content-rebuild/f9ab97c7f3aa6a98/fig-6.png)

### 选型判断维度

1. **满足以下条件时，直接使用普通工具调用（Tool Calling）**：
   - 任务是参数结构清晰的功能接口（如：按用户 ID 查订单、调用现成的发邮件接口）；
   - 操作过程不需要在上下文里额外讲解多步排错规程与领域经验，模型通过参数说明（Schema）即可正确调用。工具内部可以包含复杂的业务逻辑和状态变更，只要接口边界清晰即可。

2. **满足以下条件时，采用代码编排工作流（Workflow Engine）**：
   - 流程需要强控制流约束与严格审计追溯（如：生成报告后自动发起线上报销审批、财务账目扣减；尽管网络与模型推理仍有不确定性，但节点路由与审批门禁必须由宿主代码硬性约束）；
   - 节点之间的前后置依赖必须由程序逻辑保障，不允许因模型的自回归波动而跳过某个审批步骤。关于框架选型可参阅 [常见 Agent 框架横评](/interview/agent-interview/agent-frameworks.md)。

3. **满足以下条件时，编写 Agent Skill**：
   - **任务多步且需要柔性判断**：在整理数据报告时，模型需要根据取回的数据量大小，自主决定是画折线图还是汇总成 Markdown 表格；
   - **包含大量专家实践经验**：需要沉淀特定领域的排查习惯与注意项（如“统计口径须剔除内网测试账号”、“环比计算需排除节假日偏差”）；
   - **需要在多个场景或多个 Agent 间共享**：把这套经验文档化封装后，无论是命令行助手还是网页端智能体，挂载该 Skill 目录就能复用这套标准。

关于如何编写标准化的目录字段与组织脚本，可参考 [可复用 Agent Skill 的结构规范](/frontier/agent-skills/reusable-skill.md)；如需将企业现有业务手册转化为技能包，可进一步阅读 [常用任务封装实战](/frontier/agent-skills/skill-encapsulation.md)。
