用户与大语言模型对话时，交互通常不是一次完成的，而是多轮往返：

* **第一轮**：用户输入“我想买一张明天去上海的高铁票”，助手询问“请问您从哪里出发？计划什么时间走？”
* **第二轮**：用户回答“北京，上午9点左右”。

在第二轮中，用户的输入只有“北京，上午9点左右”，既没有提目的地“上海”，也没有提买高铁票。如果直接把这句话单独发给模型，模型根本无法推断用户的真实意图。然而在实际使用中，助手却能准确识别“从北京到上海、明天上午9点的高铁票”。

这种看似连贯的跨轮次记忆，并不是因为大模型本身“记住了”上文，而是外部工程系统在每次请求时重新组装上下文的结果。

![多轮对话专题技术图谱与架构全景](/images/content-rebuild/9d20b03d9aaec125/cover.png)

本专题旨在梳理多轮对话系统的工程实现链路，分析无状态模型与时序业务需求之间的矛盾，并建立物理上下文控制与业务状态机协同的落地框架。

### 核心矛盾：无状态模型与连续会话需求

大语言模型的标准推理接口（例如云端提供的 HTTP Completions 或 Chat API）在协议层面是**无状态**（Stateless）的。模型每次执行前向计算时，只针对当前收到的输入 Token 序列进行推理，不会在两次独立的 API 请求之间自动保留上一轮计算的隐层激活值或对话记忆。

<ReadMoreLock />

![无状态推理接口与外部工程状态注入机制](/images/content-rebuild/9d20b03d9aaec125/fig-1.png)

所谓的“多轮记忆”，其真实的工程执行过程如下：

1. **存储历史**：用户在第一轮发出请求并收到回复后，工程后端的数据库（如 Redis、PostgreSQL）将这两条消息记录在与该用户 `session_id` 绑定的存储区。
2. **重组请求**：当用户在第二轮输入新内容时，后端程序先从存储中拉出先前的对话记录，将它们格式化为一个包含历史消息的消息列表（`messages` 数组），最后追加当前用户的输入。
3. **全量发送**：组装好的完整历史消息列表被一次性发给大模型接口进行自回归生成。

这意味着，模型在第 $N$ 轮表现出的“记忆力”，完全来自工程层在第 $N$ 次请求前显式拼接并传入的历史上下文。

需要区分的是，现代推理引擎采用的前缀缓存（Prefix Caching，如 vLLM 或服务端 KV Cache 优化）属于物理层面的推理算力与显存读写复用技术，用于减少重复计算相同的 Prompt 前缀，并不改变应用层“每次调用均需提供完整上下文”的无状态接口规范。

### 系统面临的两大挑战：物理开销与业务确定性

如果多轮对话仅仅是“把历史记录不断追加到 Prompt 中”，工程实现并不复杂。但随着对话轮次增加，简单的历史追加会迅速触发两类工程挑战：

![物理上下文与业务意图双轨控制架构](/images/content-rebuild/9d20b03d9aaec125/fig-2.png)

#### 1. 物理上下文的开销与性能边界

随着轮次增加，请求携带的 Token 数量线性增长。这会带来直接的物理后果：
* **调用成本与延迟上升**：主流商业 API 均按输入 Token 量计费，长上下文会显著增加单次调用的费用；同时，输入越长，模型 Prefill（预填充）阶段的计算开销与首字延迟（TTFT）越高。
* **长文本注意力衰减**：当历史上下文达到数万 Token 时，模型在复杂长文本中准确定位关键信息（如第 2 轮提到的特定约束条件）的稳定性会下降，即所谓长文本注意力稀释问题。

物理上下文管理的目标，就是在有限的 Token 预算内，通过滑动窗口截断、定期分段摘要、提取关键事实记忆等手段，以最小的信息损失维持长会话可用性。

#### 2. 业务流转与确定性控制

在售前咨询、政务办理、票务预订等业务场景中，交互有明确的业务逻辑要求（例如订票必须收集齐“出发地、目的地、日期、班次”四个槽位才能提交订单）。

仅靠大模型自由补全历史，极易出现以下问题：
* **用户中途改口**：用户先说“去上海”，后来说“算了改成去杭州”。纯依赖文本拼接容易导致模型提取出相互矛盾的信息，或覆盖了正确的实体。
* **分支跳转与恢复**：用户在订票过程中突然插话询问“行李托运规则”，解答完毕后，系统需要能够主动拉回原有订票流程，而不是遗忘已经收集的参数。

业务状态机的目标，是将模型提取的槽位与结构化的状态转移规则（如有限状态机 FSM）结合，用确定性代码控制业务流转分支与异常回滚。

### 评测维度与工程指标

衡量多轮对话系统的表现，不能只依赖单次回复的语言流畅度，需要建立面向全会话生命周期的量化指标（评测体系基础可参考[评测指标](/fundamentals/evaluation-metrics/README.md)）：

![多轮系统工程评测与鲁棒性度量体系](/images/content-rebuild/9d20b03d9aaec125/fig-3.png)

* **端到端任务完成率（Task Success Rate, TSR）**：
  $$\text{TSR} = \frac{\text{成功完成全部业务动作且数据正确的会话数}}{\text{总会话数}}$$
  用于评估在无需人工介入的前提下，系统完整收集必要信息并成功调用后端接口的比例。
* **平均交互轮次（Average Turns to Completion）**：
  在成功完成任务的会话中，用户与系统平均往返的轮次。轮次越少，说明系统的澄清提问与槽位抽取效率越高。
* **改口与打断恢复成功率（Interruption Recovery Rate）**：
  在包含中途改口、否定、插入无关提问的测试集中，系统在完成插话回复后，成功回到原主流程并保留未修改参数的比例。
* **单会话 Token 消耗量（Token Consumption per Session）**：
  整个会话生命周期内累计消耗的 Prompt Token 与 Completion Token 总量，是评估系统运营成本的核心物理指标。
