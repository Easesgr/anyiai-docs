大语言模型本质上是无状态的（Stateless），单次 API 调用无法保留任何前序记忆。用户感受到的“连续对话”，完全是由应用层在每次请求时，将历史交互重新拼接成一个提示词（Prompt）投递给模型实现的。

然而，会话历史在时间维度上线性增长，而模型的物理上下文窗口、计算开销以及首字生成延迟（TTFT）都有严格限制。即便是窗口支持数十万 Token 的长上下文模型，如果不加控制地全量拼接历史，也会导致单次推理成本飙升、响应显著变慢，并出现注意力分散与长程约束丢失等问题（关于注意力机理可参考[上下文窗口与注意力边界](/fundamentals/llm-basics/context-window.md)）。

本文通过一个贯穿始终的**生产运维助手**案例，拆解上下文在存储层与推理层之间的流转逻辑，对比机械修剪、语义压缩与显式状态外置三种核心策略，并给出一套可落地的分级组装架构与容错处理方案。

## 贯穿案例：运维助手面临的三重上下文困境

为了看清不同上下文管理策略的实际表现，我们设定一个典型的多轮任务型交互场景：

- **第 1 轮**：用户发出核心指令：“排查线上 `payment-service` 异常，目标集群是 `prod-k8s-01`。今晚有促销，**禁止在 22:00 前执行发布，且任何操作只能先跑 dry-run**。”
- **第 3 轮**：助手调用日志工具排查报错，工具返回了长达 4,000 Token 的 Java 堆栈跟踪日志。
- **第 8 轮**：用户与助手深入讨论了 5 轮具体的修复方案。
- **第 15 轮**：排查结束，用户简短指示：“方案可行，直接执行部署吧。”

如果应用层缺乏合理的上下文管理机制，这个交互将迅速遭遇三种典型故障：

1. **首轮约束丢失**：若采用简单滑动窗口截断，第 1 轮声明的“禁止 22:00 前发布”和“只能 dry-run”在第 15 轮已被移出提示词，助手会直接在生产环境执行高危发布。
2. **单轮巨量输入挤出正常历史**：第 3 轮工具返回的 4,000 Token 堆栈日志若完整保留，会瞬间挤占当次调用的 Token 预算，导致更早的对话被提前截断。
3. **语义摘要失真**：若依赖自由文本总结，经过多次滚动摘要后，“禁止在 22:00 前发布”可能被压缩改写成“涉及 22:00 部署”，排他性否定约束在重述中发生漂移。

## 会话上下文生命周期：解耦存储层与推理层

解决上述矛盾的前提，是在系统架构中明确区分“会话记录的持久化存储”与“模型推理时的上下文输入”。

1. **持久化存储层（Persistence Layer）**：通常依托关系型数据库或文档数据库。职责是完整记录交互全过程，包括系统指令、用户发言、助手回复、思考链路、工具调用参数以及工具返回的原始载荷。这里的记录按时间单调递增，供审计、回放与分析使用，通常永不丢弃。
2. **上下文组装层（Assembly Layer）**：运行于后端服务内存中。当收到新的用户输入时，组装层从存储层拉取历史记录，依据预设的 Token 预算和优先级规则，对记录进行过滤、摘要、变量提取与截断，组装成临时性的 `messages` 列表。
3. **即时推理层（Inference Layer）**：无状态模型接收这次组装后的输入，完成单步自回归生成。生成完毕后，助手输出再写回存储层。

```
[持久存储层 (如 PostgreSQL / MongoDB)]
       │ (读取完整历史：含用户输入、助手回复、工具原始返回)
       ▼
[上下文组装引擎 (Application Server)]
       ├── 提取不可变系统指令 (System Prompt)
       ├── 读取或更新显式变量 (State Extractor & KV Store)
       ├── 生成或调用异步摘要 (Recursive Summarizer)
       └── 滑动截断最新交互消息 (Sliding Window Clipper)
       │
       ▼ (输出受控 Token 预算的临时 Prompt)
[模型推理层 (LLM Gateway)] ───► 生成响应 ───► 写回存储层
```

![上下文生命周期架构：解耦存储层原始记录、组装层处理管线与推理层即时输入](/images/content-rebuild/4cf51ac92d0b332a/fig-1.png)

存储层保障数据资产的完整性，组装层则在有限的 Token 预算下，动态提取对当前推理决策最有价值的信息切片。在[多轮对话为何困难](/frontier/multi-turn-dialogue/why-multi-turn-hard.md)中讨论的指代消解与累积误差，很大程度上取决于组装层能否提供足够准确的信息。

## 机械修剪策略：滑动窗口与 Token 预算截断

机械修剪是指按照预定义的固定规则，直接裁剪超出范围的历史消息。这类方法实现成本最低，但也最容易产生语义盲区。

### 1. 固定轮数滑动窗口（Turn-based Sliding Window）

设定保留最近 $k$ 轮对话（即 $2k$ 条消息，包含对应的人机往返）。

```python
def get_window_by_turns(messages: list[dict], max_turns: int = 5) -> list[dict]:
    # 1 轮通常包含 1 条 user 提问和 1 条 assistant 回复
    max_messages = max_turns * 2
    return messages[-max_messages:]
```

**局限**：
- **无法应对长度突变**：在运维助手案例中，普通对话每轮通常只有几十个 Token，但第 3 轮工具返回的堆栈日志达 4,000 Token。如果固定保留 5 轮，单次请求的 Token 消耗可能瞬间激增数倍，甚至超出物理窗口限制。
- **核心前序规则丢失**：固定轮数一旦推进到第 6 轮以上，第 1 轮中关于“22:00 前禁发、必须 dry-run”的关键指令被直接剔除。

### 2. 严格 Token 预算截断（Token-budget Truncation）

为了避免长度波动，更合理的机械修剪是从最新的输入开始，**逆序向前累计 Token 开销**，直到达到预设的预算上限：

1. 预留系统提示词（System Prompt）所需的 Token。
2. 从最新一条消息逆向遍历历史记录，使用分词器计算每条消息的 Token 开销。
3. 累计 Token 达到阈值时停止遍历，截断点之前的更早消息全部丢弃。

![机械修剪策略对比：滑动轮数机制与基于严格 Token 预算的逆序截断过程及边界失效](/images/content-rebuild/4cf51ac92d0b332a/fig-2.png)

无论是按轮数截断还是按 Token 截断，机械修剪的核心缺陷都是**在语义层面盲目操作**。它们把包含核心约束的初始指令与无关紧要的排查闲聊同等对待，一旦超出边界便直接丢弃。此外，如果逆序遍历时仅按单条消息简单切分，还极易拆散工具调用（Tool Call 与 Tool Result），导致因缺少匹配的 `tool_call_id` 而触发 API 协议校验报错（如 400 Bad Request）。要保留长程事实并确保消息结构合法，必须引入语义压缩、显式追踪与成对感知截断。

## 语义压缩机制：增量递归摘要

语义压缩的核心思路是：用更少的 Token 重述远期历史的事实脉络，将自由文本转为高密度的抽象总结。工业界最常见的实现是**增量递归摘要（Recursive Summarization）**。

### 增量摘要工作流

增量摘要不需要在每次用户提问时都重新总结全量历史。通常会设置一个水位线（Watermark）：

1. 当滑动窗口之外累积的未压缩原始消息超过设定的批次大小时（如累积达 2,000 Token），触发摘要任务。
2. 摘要模块将**前一次保存的已有摘要**与**本次待压缩的对话片段**拼接，调用轻量模型生成一份新摘要：
   $$\text{Summary}_{t} = \text{Summarize}(\text{Summary}_{t-1}, \text{Messages}_{\text{new}})$$
3. 组装输入时，将最新的滚动摘要作为背景段落注入到前置提示词中，其后衔接最近几轮保留完整的原始消息。

### 对话摘要的 Prompt 约束

通用的文本摘要指令极易抹去对多轮会话至关重要的细粒度信息。实践中，多轮对话摘要提示词通常需要包含明确的排他性与实体保留规则：

```text
你是一个多轮对话记忆提取器。请将【已有摘要】与【最新对话记录】合并为一份更新后的紧凑摘要。
规则：
1. 严格保留用户提出的硬性偏好、业务限制与排他条件（如不要什么、禁止什么）。
2. 严格保留所有具名实体（如集群名称、服务名称、工单编号、错误码）。
3. 记录当前尚未解决的遗留任务。
4. 移除寒暄、语气词及已确认无效的排查尝试。
5. 篇幅严格控制在 300 汉字以内，输出纯文本事实陈述。
```

### 语义损耗与信息衰减

增量摘要能够有效压缩篇幅，但存在内在物理缺陷：**多代递归传递中的信息衰退（Generation Loss）**。

当自然语言被轻量模型多次重述后，排他性条件容易被模糊化。例如在运维案例中，原始输入为“禁止在 22:00 前执行发布”，在第二次或第三次递归合并后，摘要模型很可能浓缩为“讨论了 22:00 的发布操作”，否定词与前置假设一旦丢失，系统便无法守住安全底线。因此，涉及核心业务逻辑的变量不能仅靠自由文本摘要维护。

## 显式状态外置：从自然语言到结构化字典

要彻底解决关键业务变量在多轮对话中被淡化或遗忘的问题，最可靠的手段不是无限拉长上下文窗口，而是**将状态追踪从自然语言中剥离，交由程序做显式外置管理（Explicit State Tracking）**。

显式状态是一组保存在会话元数据中的强类型键值字典（Key-Value）。针对运维助手场景，可以维护如下结构：

```json
{
  "target_cluster": "prod-k8s-01",
  "service_name": "payment-service",
  "constraints": {
    "dry_run_only": true,
    "earliest_release_time": "22:00"
  },
  "current_ticket": "OPS-4091"
}
```

### 状态的提取与更新方式

将非结构化对话转换为结构化状态主要有两种工程路径：

1. **伴随式工具调用（Inline Tool Call）**：在核心模型生成回复时，注册一个名为 `update_session_state` 的内置工具。当模型识别到用户输入中包含参数变更或新增约束时，由模型输出结构化的参数调用，系统拦截该调用并更新底层数据库。
2. **旁路提取器（Sidecar Extractor）**：在用户发送消息后，由异步轻量模型并行运行一个小任务，专门比对当前用户输入是否触发了预定义 Schema 中的字段更新，更新后写入会话缓存（如 Redis）。

![显式状态提取机制：非结构化对话流经抽取器，持久化为强类型键值字典](/images/content-rebuild/4cf51ac92d0b332a/fig-4.png)

无论后续对话进行了多少轮、滑动窗口如何修剪，提取出的强类型状态都会以顶层结构化卡片的形式注入模型输入。核心操作参数与安全底线不再受自然语言截断的影响。

## 分级组装架构：四槽位上下文组装实践

综合上述技术，在实际工程中可以采用**四槽位分级组装架构（Multi-slot Context Assembly）**。将单次请求的物理 Token 预算（例如设定为 4,000 Token）严格划分为四个独立槽位：

1. **Slot 1: 系统指令（System Instruction）**：不可压缩的全局设定，声明助手角色、安全边界与工具协议。
2. **Slot 2: 显式状态卡片（Explicit State Card）**：由外置键值字典渲染而成的结构化文本，承载关键业务参数与硬性约束。
3. **Slot 3: 滚动摘要（Rolling Summary）**：对更早之前被滑动窗口移出的消息所生成的紧凑事实摘要。
4. **Slot 4: 近期滑动窗口（Sliding Window Messages）**：保留最近几轮（通常为 3 到 5 轮）原始交互，确保当前对话的连贯性与即时指代关系的清晰度。

![分级组装四槽位架构：固定指令、状态卡片、滚动摘要与滑动窗口在 Token 预算内的物理配比](/images/content-rebuild/4cf51ac92d0b332a/fig-5.png)

### 组装逻辑参考实现

以下 Python 代码演示了如何根据 Token 预算自顶向下分配配额，保证核心状态不丢失，并对滑动窗口执行逆序安全裁剪：

```python
from typing import Any

def estimate_tokens(text: str) -> int:
    """
    示意性分词计数函数。
    实际工程中应使用与目标模型匹配的分词库（如 tiktoken 或 transformers 的 AutoTokenizer）。
    此处按平均每 2 个字符折算约 1 个 Token 作为估算。
    """
    return len(text) // 2 + 1

def assemble_context(
    system_prompt: str,
    explicit_state: dict[str, Any],
    rolling_summary: str,
    raw_messages: list[dict[str, str]],
    max_total_budget: int = 4000,
) -> list[dict[str, str]]:
    """
    按照四槽位预算分级组装多轮上下文。
    """
    final_messages: list[dict[str, str]] = []
    
    # 1. 组装 Slot 1: 基础系统指令
    base_system = system_prompt.strip()
    
    # 2. 组装 Slot 2: 显式状态卡片 (渲染为纯文本)
    state_lines = ["\n[当前会话显式状态与安全约束]"]
    for k, v in explicit_state.items():
        state_lines.append(f"- {k}: {v}")
    state_card = "\n".join(state_lines)
    
    # 3. 组装 Slot 3: 滚动摘要
    summary_section = f"\n[远期历史对话摘要]\n{rolling_summary}" if rolling_summary else ""
    
    # 合并前三项，作为顶层系统消息
    combined_system_text = f"{base_system}\n{state_card}\n{summary_section}".strip()
    system_tokens = estimate_tokens(combined_system_text)
    
    if system_tokens >= max_total_budget:
        raise ValueError("系统提示词、状态卡片与摘要的 Token 总和已超出预算上限，需压缩状态或摘要！")
    
    final_messages.append({"role": "system", "content": combined_system_text})
    remaining_budget = max_total_budget - system_tokens
    
    # 4. 组装 Slot 4: 逆序填充最新滑动窗口消息
    window_messages: list[dict[str, str]] = []
    for msg in reversed(raw_messages):
        # 兼容工具调用等场景下 content 可能为 None 的情况
        content = msg.get("content") or ""
        msg_tokens = estimate_tokens(content)
        if remaining_budget - msg_tokens < 0:
            if not window_messages:
                raise ValueError("最新单条消息已超出剩余可用 Token 预算，无法完成组装！")
            # 预算耗尽，停止向前回溯更早历史
            break
        window_messages.append(msg)
        remaining_budget -= msg_tokens
        
    # 恢复消息正序排列（工程中还需校验避免首条消息为孤立 tool 响应）
    window_messages.reverse()
    final_messages.extend(window_messages)
    
    return final_messages
```

## 降级与容错：异常处理机制

多轮上下文工程涉及网络交互、异步模型调用与可变长度文本输入，系统必须具备明确的异常降级路径。

### 1. 摘要生成超时与实体校验

增量摘要通常由辅助模型异步生成，可能发生两类问题：
- **调用超时或接口报错**：系统应降级为“跳过本次摘要更新”，直接通过滑动窗口硬截断历史，并在监控中发出告警，绝不能阻断主对话链路。
- **摘要幻觉引入**：小型模型在重述时可能捏造实体。可使用**实体一致性比对**进行规则校验：提取原始对话段落中的核心具名实体（如正则表达式提取的工单号、服务名、参数值），比对它们在生成摘要中的覆盖率。若核心实体缺失，丢弃该摘要，降级为基于关键句抽取的机械修剪。

### 2. 工具超大返回结果的折叠修剪（Tool Output Squashing）

在第 3 轮日志排查中，工具返回了数千 Token 的堆栈报错。如果将其完整写入滑动窗口，会瞬间挤占当次调用的全部预算。

**应对方案**：针对 `role: tool` 的消息设置单条上限（例如 800 Token）。当工具返回超过限制时，由系统执行头尾截断（保留前 400 Token 与后 400 Token），并在中间插入省略占位标记 `[... 原始日志已折叠 X 字符 ...]`。如果排查依赖全量信息，应将完整日志落盘存储至文件或对象存储，只在上下文中传递文件下载链接与关键诊断行。

### 3. 会话污染与主动重置（Context Resetting）

如果多轮对话中产生了严重的误解或死循环，错误的上下文输入会导致模型持续产生幻觉。此时继续压缩或修剪已被污染的自然语言已失去意义。系统应提供会话重置入口：保留 Slot 2 中的用户元数据与显式状态，清空 Slot 3 摘要与 Slot 4 历史记录，以干净的上下文开启新一轮交互。

| 方案维度 | 纯滑动窗口修剪 | 增量递归摘要 | 显式状态外置 | 四槽位分级组装 |
| :--- | :--- | :--- | :--- | :--- |
| **开发复杂度** | 极低（几十行代码） | 中等（需设计异步总结链路） | 中等（需定义 Schema 与提取器） | 较高（需统一状态机、配额管理与降级） |
| **额外调用成本** | 无额外调用成本 | 存在轻量摘要模型的推理成本 | 存在提取器模型的推理成本 | 成本可控，能有效降低主模型开销 |
| **长程约束保持率** | 较差（超出窗口即丢弃） | 一般（多轮传递存在语义损耗） | 极高（强类型字段持久保留） | 极高（强类型约束 + 宏观语义兼顾） |
| **首字生成延迟** | 极低 | 异步生成时无感知，同步会阻塞 | 异步提取时无感知 | 优（上下文 Token 严格受控，TTFT 稳定） |
| **典型适用场景** | 短会话、轻量问答、无状态单步任务 | 自由文本创作、泛主题闲聊、头脑风暴 | 结构化流程（表单填写、工单申报、点餐） | 复杂运维助手、企业客服、长流程 Agent |

通过在持久存储层保留完整审计轨迹，在上下文组装层利用滑动窗口保证局部连贯性、利用增量摘要保留宏观脉络，并通过显式状态外置固化核心约束，开发者可以在有限的模型上下文配额内，构建兼具长程记忆与操作确定性的对话系统。在上下文稳定组装的基础上，关于如何进一步识别并应对用户意图的即时跳跃与动态切换，可参阅下一讲[多轮对话中的意图追踪与动态转移](/frontier/multi-turn-dialogue/intent-tracking.md)。
