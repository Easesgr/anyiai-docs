在上一讲[/frontier/local-llm/what-is-local-llm.md](/frontier/local-llm/what-is-local-llm.md)中，我们梳理了本地部署大语言模型的硬件约束与显存需求。当进入实际部署阶段时，很多开发者面对社区中的 llama.cpp、Ollama、LM Studio 和 vLLM 会感到困惑：它们究竟有什么区别？为什么有的适合个人笔记本，有的只能跑在 Linux 服务器上？

**结论先行**：这四款工具并不是同一层次的竞品，而是分工不同的组件与系统：
- **llama.cpp** 是底层的跨平台张量计算引擎，核心能力是支持 CPU/GPU 混合层卸载和 GGUF 格式，适合资源受限或异构硬件的单人环境。
- **Ollama** 是基于 llama.cpp 构建的命令行服务管理器，引入类似 Docker 的镜像打包（Modelfile）和后台守护进程，适合个人快速开发与脚本调用。
- **LM Studio** 是基于 llama.cpp 构建的桌面可视化应用，提供直观的参数滑块与性能监视器，适合快速下载、调参试错与模型对比。
- **vLLM** 是专为高并发服务端设计的独立推理系统，核心能力是 PagedAttention 显存分页和连续批处理（Continuous Batching），适合私有化机房供多用户并发调用的生产环境。

**贯穿示例**：本文将以在本地部署一个约 80 亿参数（8B）的开源指令模型（如 Qwen2.5-8B）为例，分析同一个模型在单卡笔记本、桌面工作站和私有机房服务器上运行时，上述工具在显存分配、访存带宽和任务调度上的具体行为差异。

## 运行时技术栈分层：计算引擎与服务包装

大语言模型的本地软件栈可以清晰地拆分为两层：**底层计算引擎**与**上层服务/交互封装**。

底层的计算引擎直接对接硬件驱动（如 NVIDIA CUDA、AMD ROCm、Apple Metal 或 CPU 向量指令集）。它的工作包括读取并反量化权重、管理计算注意力机制所需的键值缓存（KV Cache），以及逐个 Token 推进自回归解码循环。这一层的典型代表是 **llama.cpp** 与 **vLLM**。

上层封装则不直接编写 GPU 核心算子，而是将底层引擎作为子进程或动态链接库引入，在外层补齐模型拉取、文件解析、配置管理、REST API 暴露或桌面图形界面。这一层的典型代表是 **Ollama** 和 **LM Studio**。

![底层推理引擎与上层服务封装的调用链路关系](/images/content-rebuild/e7157283752e51c9/fig-1.png)

如果需要评估推理吞吐率和显存利用率，关键看底层计算引擎的设计；如果需要评估本地调试效率与服务集成成本，关键看上层包装的自动化程度。

## llama.cpp：跨平台支持与混合层卸载

`llama.cpp` 是 Georgi Gerganov 主导开发的纯 C/C++ 推理库，不依赖庞大的深度学习运行时框架。它支持 x86（AVX2/AVX-512）、ARM（NEON）以及主流 GPU 平台，同时确立了本地部署中广泛使用的二进制文件格式——**GGUF**。

### GGUF 文件与内存映射（mmap）

GGUF 格式将模型的超参数、分词器词表（Tokenizer）、层张量元数据和量化权重整合为一个单文件。在读取模型时，llama.cpp 依赖操作系统的内存映射机制（`mmap`）：程序启动时仅将文件虚拟地址映射至进程地址空间，而不必在初始化阶段将整个数吉字节（GB）的文件一次性拷贝进堆内存。这样不仅缩短了启动时间，也让多个进程共享同一份只读物理内存页面成为可能。

GGUF 提供了多种整型量化类型，例如 `Q4_K_M`、`Q5_K_M` 和 `Q8_0`。其中 `K` 代表 K-quants（分组量化），`M` 代表混合位宽策略：对输出质量影响较大的关键权重（如注意力机制的 V 矩阵、输出投影矩阵，以及前馈网络的下投影矩阵 ffn_down）保留 6 位较高精度（Q6_K），对其余权重采用 4 位较低精度（Q4_K），从而在控制精度损失的同时将 8B 模型的显存占用从 16 位浮点数的约 16 GB 压缩至 5 GB 左右。

### 混合层卸载（Layer Offloading）原理与瓶颈转移

个人设备最常见的情况是：**显存不足以容纳整个模型，但系统内存还有空闲**。llama.cpp 提供了混合层卸载机制（启动参数 `-ngl` 或 `--n-gpu-layers`），允许把模型的部分层放在显存中，其余层留在系统内存中由 CPU 运算。

以一个包含 32 个 Transformer 层的 8B 模型为例，假设显存只能容纳 8 层，开发者设置卸载 8 层到 GPU：
1. **前 8 层计算**：输入 Token 经 Embedding 后，中间激活值送入 GPU 显存，前 8 层在 GPU 上完成计算。此阶段受限于 GPU 显存带宽（如常见显卡的 250–500 GB/s）。
2. **跨总线传输**：第 8 层计算完毕后，GPU 将该层的输出张量通过 PCIe 总线复制回系统内存。
3. **后 24 层计算**：CPU 调用向量指令集接管剩余 24 层的矩阵乘法。由于 CPU 没有高带宽的显存，每次生成一个新 Token，都必须从系统内存（双通道 DDR5 带宽通常在 40–80 GB/s）中完整读取这 24 层的权重。
4. **输出处理**：最终的输出归一化与采样可以由 CPU 完成，也可以再传回 GPU 执行。

![llama.cpp 混合层卸载中的张量流动与 PCIe 瓶颈](/images/content-rebuild/e7157283752e51c9/fig-2.png)

#### 算例：单请求自回归阶段的纯带宽受限估算

在批大小（Batch Size）为 1 的自回归解码阶段，计算强度通常极低，生成每个 Token 都需要将所有参与运算的层权重从存储介质读取一次。以下对比展示不同卸载比例下的理论读取耗时（假设忽略计算时延与极小的 KV Cache 读取耗时，仅计算权重访存时间）：

- **基准假设**：8B 模型的 `Q4_K_M` 权重文件大小为 4.9 GB，共 32 层，平均每层约 153 MB。显存带宽设为 272 GB/s（类似 RTX 4060 桌面版），系统内存单核/多核实际可达读取带宽设为 40 GB/s。
- **场景 A：32 层全部卸载到 GPU**
  - 单 Token 读取 4.9 GB 权重耗时：$4.9 \text{ GB} / 272 \text{ GB/s} \approx 18.0 \text{ ms}$。
  - 理论访存速率上限：$1000 / 18.0 \approx 55.5 \text{ tokens/s}$。
- **场景 B：仅卸载 8 层到 GPU，剩余 24 层留在内存**
  - GPU 读取 8 层（约 1.22 GB）耗时：$1.22 \text{ GB} / 272 \text{ GB/s} \approx 4.5 \text{ ms}$。
  - PCIe 复制单 Token 的激活张量：体积仅数十 KB，耗时小于 0.1 ms。
  - CPU 读取 24 层（约 3.68 GB）耗时：$3.68 \text{ GB} / 40 \text{ GB/s} \approx 92.0 \text{ ms}$。
  - 单 Token 权重总读取耗时：$4.5 + 92.0 = 96.5 \text{ ms}$。
  - 理论访存速率上限降为：$1000 / 96.5 \approx 10.4 \text{ tokens/s}$。

**工程结论**：一旦模型未能完整放入显存，推理速度将被较慢的系统内存带宽主导。因此在使用 llama.cpp 时，应根据实际可用显存尽可能拉高 `-ngl` 的层数，减少留在系统内存中的层数。

## Ollama：守护进程与模型镜像管理

Ollama 是针对本地开发与轻量脚本调用设计的高集成度工具。它的核心贡献是简化了模型的获取、编译和进程管理流程。

### 软件结构

Ollama 自身并不重新实现张量运算，它的内部主要分为两个部分：
1. **Go 语言守护进程**：后台常驻，默认监听本地 `11434` 端口。它对外暴露模型拉取、删除、生成以及兼容 OpenAI 的 HTTP API。
2. **底层执行器（Runner）**：Ollama 预编译了针对不同指令集（AVX2）与图形后端（CUDA、Metal、ROCm）的 llama.cpp 动态库。当接收到推理请求时，守护进程根据宿主机硬件动态启动对应的 runner 子进程，并通过进程间通信发送计算任务。
3. **显存保活控制**：Ollama 具备默认的生命周期管理机制（Keep-alive，默认 5 分钟）。请求结束后模型仍驻留在显存中，若超时无新请求则自动卸载，以便将显存归还给桌面操作系统。

![Ollama 的守护进程与底层 llama.cpp Runner 架构](/images/content-rebuild/e7157283752e51c9/fig-3.png)

### Modelfile 的组织方式

Ollama 借鉴了容器镜像（Dockerfile）的思想，使用 `Modelfile` 将基础权重、采样参数和提示词模版绑定在一起：

```dockerfile
# 指定基础权重（支持远程仓库或本地 GGUF 文件）
FROM ./qwen2.5-8b-instruct-q4_k_m.gguf

# 设定推理采样参数
PARAMETER temperature 0.7
PARAMETER top_p 0.9
PARAMETER stop "<|im_end|>"

# 注入系统提示词（System Prompt）
SYSTEM """你是一个代码审查助手，请用简练的中文指出潜在问题。"""

# 定义对话模板引擎
TEMPLATE """{{ if .System }}<|im_start|>system
{{ .System }}<|im_end|>
{{ end }}{{ if .Prompt }}<|im_start|>user
{{ .Prompt }}<|im_end|>
{{ end }}<|im_start|>assistant
{{ .Response }}<|im_end|>"""
```

通过 `ollama create my-assistant -f Modelfile`，Ollama 会计算各层配置与权重的哈希值，将其分层存储在本地目录中。这种方式极大降低了本地工具链与脚本对接的摩擦成本。

**适用边界**：Ollama 适合个人开发环境和轻量工具调用。其并发控制较为基础，如果将其直接置于数十人共享的生产流量入口，排队等待和单实例资源争抢会使得请求延迟显著增加。

## LM Studio：可视化桌面调试与参数评测

LM Studio 是专为桌面开发者设计的图形化交互工作台，同样以内嵌的 llama.cpp 作为计算核心，侧重于可视化调试。

![LM Studio 可视化调试面板与本地 API 服务器界面](/images/content-rebuild/e7157283752e51c9/fig-4.png)

### 核心功能与使用价值

1. **量化版本与硬件评估**：LM Studio 内部集成了模型浏览界面，能根据当前设备的显存与内存大小，预估不同量化级别（从 2-bit 到 8-bit）是否可以完全放入显存，避免用户下载后因显存溢出而无法运行。
2. **交互式采样调参**：在右侧控制面板中，温度（Temperature）、Top-P、重复惩罚（Repeat Penalty）以及上下文长度（Context Length）均可通过滑动条实时调整，便于直观比对不同超参数对输出连贯性与幻觉的影响。
3. **实时性能监控**：在对话界面中直接显示每秒生成的 Token 数（Tokens/s）以及首字延迟（TTFT，Time To First Token），为硬件基准测试提供直接参考。
4. **无头模式限制**：LM Studio 是带有 Electron 界面的桌面端应用，没有为 Linux 无桌面（Headless）环境提供标准轻量系统服务包，因此不适合用于云端集群的无感部署。

## vLLM：高并发服务端的 PagedAttention 与连续批处理

当需求从“个人本地自测”升级到“私有云多用户并发访问”（例如企业内部知识库 RAG 场景）时，单请求引擎的弊端就会凸显：并发请求下显存迅速耗尽，吞吐率无法随用户增加而线性扩展。**vLLM** 是专为解决多并发高吞吐问题而设计的生产级推理框架。

### 传统显存分配的碎片问题

在模型生成过程中，每个会话都需要缓存历史 Token 计算出的 Key 和 Value 向量，这部分数据称为 **KV Cache**。

在传统推理系统中，为了保证 GPU 算子的高效连续内存访问，系统通常在请求进入时，就按照其可能达到的最大上下文长度（例如 4096）**预先分配一大块连续的显存空间**：
- **内部碎片**：用户实际上可能只问了一句简短的话并得到 100 字的回复，剩余分配给 3900 个 Token 的显存空间在此期间被独占锁定，无法借给其他请求。
- **外部碎片**：各请求到达和结束的时机不同，显存反复申请与释放后，会留下许多分散的小块空闲显存，由于它们在物理上不连续，无法再容纳一个长上下文请求。

### PagedAttention 原理：显存分页映射

vLLM 借鉴了操作系统操作内存的虚拟内存分页（Virtual Memory Paging）思想，提出了 **PagedAttention**：

1. **逻辑切块**：将每个序列的 KV Cache 逻辑上划分为固定大小的块（KV Blocks），例如每个块固定存储 16 个 Token 的键值向量。
2. **离散物理块池**：预先在 GPU 显存中开辟一块连续内存池划分为若干物理块，物理块在显存中的地址无需连续排列。
3. **页表映射（Block Table）**：为每个并发请求维护一个轻量级的页表，记录逻辑块号与物理块号的对应关系。当序列生成产生新的 KV 向量时，如果当前物理块未填满，就直接追加；一旦填满，调度器从物理池中申请一个新块，并在页表中记录映射。

![传统连续显存分配与 PagedAttention 显存分页机制对比](/images/content-rebuild/e7157283752e51c9/fig-5.png)

**效果**：显存浪费被限制在每个序列最后一个未填满的物理块内（最多浪费 15 个 Token 的存储），显存碎片被大幅减少。此外，PagedAttention 还使得多个请求能够自然实现**前缀共享（Prefix Caching）**：对于包含相同长系统提示词或长文档的请求，所有页表直接映射到同一份物理块，无需重复拷贝。

### 连续批处理（Continuous Batching）

传统的批处理（Static Batching）必须等待同一批次中耗时最长的请求结束，才能整体释放资源并接收新请求，这导致短请求用户被长请求严重阻塞。

vLLM 采用**迭代级别调度（Iteration-level Scheduling）**：
- 调度器在自回归生成的每一次前向推理步（Step）中进行调度。
- 当某个请求生成了结束符号（`<eos>`），系统立刻在下一个 Step 将其释放，并将其物理块归还池中；同时，等待队列中的新请求可以立即填补该空位进入批次。

这使得 GPU 计算核心在面对并发请求时能维持在较高的利用率状态，整体系统的综合吞吐率（每秒处理的总 Token 数）通常远高于单请求桌面工具。

## 四款工具的横向选型矩阵

| 评估维度 | llama.cpp | Ollama | LM Studio | vLLM |
| :--- | :--- | :--- | :--- | :--- |
| **主要定位** | 底层跨平台推导引擎 | 个人轻量服务化工具 | 桌面端可视化交互平台 | 企业级高并发推理服务 |
| **核心优势** | 极低内存开销、全平台混合层卸载 | 开箱即用、Modelfile 镜像封装、基础 REST API | 图形界面调参、量化版本对比、实时指标曲线 | PagedAttention 分页缓存、连续批处理、多卡分布式（TP/PP） |
| **并发处理能力** | 基础（适合单会话） | 弱至中等（支持简单排队，多并发容易显存吃紧） | 基础（面向单用户交互） | **极高**（面向多客户端高吞吐设计） |
| **目标运行硬件** | 个人电脑 CPU、Apple Silicon、混合显存显卡 | 笔记本、个人工作站 | 带有图形桌面的个人电脑 | 配备标准数据中心 GPU（NVIDIA/AMD）的 Linux 服务器 |
| **支持的主要权重** | GGUF | GGUF | GGUF | HuggingFace Safetensors、AWQ、GPTQ、FP8 |
| **典型交付形态** | 编译后的可执行文件或 C++ 库 | 后台系统 Daemon 进程 | 桌面 GUI 应用程序 | Python / C++ 服务包、Docker 容器镜像 |

### 场景落地建议

1. **个人本地开发与小工具集成**：
   - **建议使用 Ollama**。通过 CLI 一键拉取模型，使用标准 OpenAI 兼容接口对接本地开发环境，兼顾了配置简便性与脚本调用灵活性。
2. **提示词调试、量化对比与体验验证**：
   - **建议使用 LM Studio**。利用图形滑块调节温度与上下文长度，能直观比对同一模型不同量化版本（如 Q4 与 Q8）的生成质量差异。
3. **低算力设备、嵌入式硬件或 CPU 运行环境**：
   - **建议使用 llama.cpp**。直接编译单二进制文件运行，无需 Python 依赖，通过精细指定 `-ngl` 参数压榨每一兆字节显存的计算潜力。
4. **企业内部应用服务与高并发知识库（RAG）生产环境**：
   - **建议使用 vLLM**。在配备 Linux 独立 GPU（如 NVIDIA/AMD）的前提下，当需要为团队多人提供稳定的 API 访问时，PagedAttention 与连续批处理能有效减少显存浪费并降低排队阻塞，保持高吞吐输出；若处于纯 CPU、macOS 或显存受限的消费级设备上，则更适合通过多实例部署 llama.cpp 或 Ollama 提供服务。

明确了运行时的架构差异与选型依据后，下一步是将这些本地服务接入具体业务逻辑。在下一讲[/frontier/local-llm/local-llm-integration.md](/frontier/local-llm/local-llm-integration.md)中，我们将讨论如何利用 OpenAI 兼容 API、结构化工具调用（Tool Calling）和上下文管理，让本地模型与外部系统完成集成。
