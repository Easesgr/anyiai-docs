在规划大语言模型的应用架构时，工程团队通常面临两条路线：一是直接调用云端厂商提供的商用 API，二是在本地工作站或私有服务器上下载开源模型权重并自行运行。许多团队在选型时容易走向两个极端：要么出于对数据出境的恐慌，盲目采购高价 GPU，结果遇到显存溢出或算力常年闲置；要么认为云端 API 单价极低，忽略了业务量上涨后的长期费用与网络长尾延迟。

要做好技术选型，必须从物理硬件的运行机制切入，搞清楚模型在本地运行时究竟在消耗什么资源、为什么有时速度很慢，并通过全生命周期持有成本（TCO）建立清晰的决策边界。

## 什么是本地大模型：从磁盘文件到显存计算

所谓“本地大模型”，并不是某种特殊形态的算法，而是指**由使用者完全掌控物理计算硬件，将开源模型的权重文件（如 GGUF 或 Safetensors 格式）载入本地内存或显存，并在本地硬件上独立完成推理计算的运行模式**。如果读者对大模型底层如何把文本转化为向量尚未建立直觉，可以先参考 [大模型到底是什么？](/fundamentals/llm-basics/what-is-llm.md) 与 [Token 到底是什么？](/fundamentals/token-and-tokenizer/what-is-token.md)。

以一个典型的内网应用场景为例：某团队希望在本地运行一个 7B（70 亿参数）级别的模型，用来辅助阅读内部技术规范。在本地启动模型时，硬件系统会经历三个连续的物理阶段：

1. **磁盘读取与权重反序列化**：操作系统从固态硬盘中读取模型权重文件，并按配置将其载入系统内存（RAM）或直接复制到显卡的独立显存（VRAM）中。
2. **显存静态与动态空间切分**：显存一旦分配，会被划分为**静态只读区**（存放模型本身的参数权重，推理全程大小固定）和**动态工作区**（存放输入输出的 KV Cache 缓存、各网络层计算时的临时中间激活值，以及推理框架自身的运行环境）。
3. **两阶段推理计算**：
   - **预填充阶段（Prefill）**：模型一次性并行处理用户输入的全部 Prompt 提示词，计算对应的 Key 与 Value 张量并写入显存。这一阶段涉及大量矩阵乘法，属于**算力密集型（Compute-bound）**任务，GPU 的张量核心（Tensor Core）利用率通常较高。
   - **解码阶段（Decode）**：模型开始逐个生成后续 Token。每生成一个新 Token，都需要将显存中的全部模型权重完整遍历读取一次。在单请求（Batch Size = 1）场景下，计算量很小，但读取的数据量极大，因而属于典型的**访存密集型（Memory-bound）**任务。

![本地大模型推理流水线与显存切分示意图](/images/content-rebuild/977c42ffc5258b3d/fig-1.png)

### 为什么生成速度常常受限于显存带宽？

很多初学者误以为本地大模型生成慢是因为显卡“算力不够”，但在单并发解码阶段，制约生成速度的真正瓶颈往往是**显存的物理传输带宽（Memory Bandwidth）**。

在生成单个 Token 时，算子需要将几十亿个参数从显存搬运进计算核心。单并发下的理论极限生成速度可以粗略估算为：

$$v_{\text{decode}} \approx \frac{\text{显存物理带宽 (GB/s)}}{\text{模型实际占用显存 (GB)}}$$

假设一张消费级显卡的显存带宽为 $500\text{ GB/s}$，运行一个占用 $10\text{ GB}$ 显存的模型，即使完全不计计算延迟，每秒最多也只能把权重读取 50 次，即理论生成上限约为 $50\text{ Token/s}$。如果把模型放在系统内存（DDR4/DDR5 双通道带宽通常仅为 $40\sim80\text{ GB/s}$）中依靠 CPU 计算，即使 CPU 核心再多，生成速度也会跌至 $4\sim8\text{ Token/s}$。

## 硬件资源推演：参数量、量化与 KV Cache 计算

评估本地硬件能否支撑某个模型，必须进行严谨的显存预算推导。运行大模型所需的总显存 $M_{\text{total}}$ 主要由三部分构成：

$$M_{\text{total}} = M_{\text{weights}} + M_{\text{kv\_cache}} + M_{\text{overhead}}$$

其中：
- $M_{\text{weights}}$ 为模型权重占用的静态显存；
- $M_{\text{kv\_cache}}$ 为维护上下文注意力所需的动态显存；
- $M_{\text{overhead}}$ 为 CUDA 上下文、推理框架运行环境及算子临时激活值占用的预留显存（通常需预留 $1.0\sim1.5\text{ GB}$）。

### 权重显存与量化精度

模型参数量（Parameters, 简写为 $P$）与存储格式决定了静态权重的大小：
- **FP16 / BF16（半精度浮点）**：每个参数占 16 bits（2 字节），$M_{\text{weights}} \approx P \times 2\text{ 字节}$；
- **INT8（8位量化）**：每个参数占 8 bits（1 字节），$M_{\text{weights}} \approx P \times 1\text{ 字节}$；
- **INT4 / Q4（4位量化）**：每个参数理论占 4 bits（0.5 字节），加上量化分组缩放与偏移量等元数据，实际占用约为 $P \times 0.55\sim0.6\text{ 字节}$。

以常见的 70 亿参数（7B）模型为例：
- 在 FP16 精度下，纯权重需要约 $14\text{ GB}$ 显存；
- 采用主流的 4-bit 量化（如 GGUF 的 Q4_K_M 格式）后，纯权重显存可压缩至约 $4.3\text{ GB}$。

![参数量、量化位宽与显存容量的关系示意](/images/content-rebuild/977c42ffc5258b3d/fig-2.png)

### KV Cache 的显存推导与算例

模型在逐字生成时，为了避免对历史输入的注意力矩阵进行重复计算，会将每一层已生成的 Key 与 Value 向量保存在显存中。这部分缓存随着输入提示词长度与输出长度的增加而线性增长。

在标准多头注意力（Multi-Head Attention, MHA）下，KV Cache 显存大小公式为：

$$M_{\text{kv\_cache}} = 2 \times L \times H \times D \times S \times B \times b_{\text{kv}}$$

- $L$：Transformer 网络层数（Layers）；
- $H$：Key 和 Value 的注意力头数（Heads）；
- $D$：每个注意力头的维度（Head Dimension）；
- $S$：上下文序列长度（Sequence Length，包含 Prompt 与已生成 Token）；
- $B$：并发批处理大小（Batch Size）；
- $b_{\text{kv}}$：KV Cache 存储精度（FP16 下为 2 字节）；
- 常数 $2$：分别保存 Key 和 Value 两组向量。

当前主流开源模型（如 Llama 3 8B、Qwen 2.5 7B）普遍采用了分组查询注意力（Grouped-Query Attention, GQA），将 Key 和 Value 的头数缩减为 $H_{\text{kv}}$（通常为 Query 头数的 $1/4$ 或 $1/8$），大幅降低了 KV Cache 的显存开销。

**【推导算例：7B 模型在 4-bit 量化下的单并发显存需求】**
- **设定条件**：采用 GQA 结构的 7B 模型，$L = 32$，$H_{\text{kv}} = 8$，$D = 128$。使用 Q4_K_M 量化，单并发（$B=1$），运行上下文窗口设为 4,096 Token（$S=4096$），KV Cache 使用 FP16 存储（$b_{\text{kv}}=2$ 字节）。
- **步骤一：计算权重显存**
  $$M_{\text{weights}} \approx 4.3\text{ GB}$$
- **步骤二：计算 4K 上下文 KV Cache 显存**
  $$M_{\text{kv\_cache}} = 2 \times 32 \times 8 \times 128 \times 4096 \times 1 \times 2 \text{ 字节} = 536,870,912 \text{ 字节} \approx 0.5\text{ GB}$$
  （注：若上下文扩大到 32K Token，该项将增至约 $4.0\text{ GB}$；若为早期未采用 GQA 的架构，显存占用还将成倍增加）。
- **步骤三：计入推理框架与运行时预留**
  推理框架（如 llama.cpp 或 vLLM）初始化及激活值显存预留取 $1.2\text{ GB}$。
- **步骤四：汇总总显存**
  $$M_{\text{total}} = 4.3\text{ GB} + 0.5\text{ GB} + 1.2\text{ GB} = 6.0\text{ GB}$$
- **选型结论**：本地设备至少需要配备 **8 GB 独立显存**，才能确保该模型在 4K 上下文内稳定运行。如果硬件仅有 6 GB 显存，遇到长提示词时极易触发显存溢出（Out-of-Memory, OOM），或者被迫将部分层卸载（Offload）到系统内存，导致生成速度大幅下滑。

## 本地部署与云端 API 的全方位对比

技术选型不能只看显存大小，还需要将模型运行置于完整的系统生命周期与网络拓扑中考量。

![本地部署与云端 API 数据路径与风险点对比](/images/content-rebuild/977c42ffc5258b3d/fig-3.png)

### 1. 数据隐私与合规边界

数据隐私是许多团队考虑本地部署的核心动因，但需要区分“协议合规”与“物理隔离”：
- **云端商用 API**：主流云服务商在企业级协议中通常承诺不会将 API 传输的数据用于公共基础模型训练，并提供传输加密与落盘加密。然而，业务载荷客观上穿透了内网边界，在服务商的多租户集群中流转。
- **物理隔离网络**：在金融核心账务、涉密单位、未公开核心源码库或强监管行业中，**禁止业务数据流向外部公网**是硬性安全规定。此时，不论云端协议如何严密，都必须采用断网物理隔离（Air-gapped）的本地私有化方案。

### 2. 延迟特征的构成差异

评估模型响应延迟时，必须拆分为两个指标：**首字延迟（Time to First Token, TTFT）**与**后续生成耗时（Time Per Output Token, TPOT）**：
- **云端 API**：TTFT 必然包含客户端到云端数据中心的多跳网络往返时间（RTT）以及网关鉴权排队延迟，跨地域公网 RTT 通常在 $30\sim200\text{ ms}$。但由于云端集群普遍配备搭载高带宽显存（如 HBM）的高端硬件，且多并发批处理成熟，其后续生成 TPOT 往往更稳定、更快速。
- **本地部署**：TTFT 消除了公网传输开销，内网通信延迟通常小于 $5\text{ ms}$。但受限于本地硬件的显存带宽，在单并发或硬件配置较低时，后续生成 TPOT 可能会明显慢于云端旗舰集群。本地部署的核心收益在于**网络传输零抖动与响应确定性**，而非极速的吞吐峰值。

### 3. 可用性与系统运维负担

两种模式对应的故障特征截然不同：

| 评估维度 | 云端托管 API 方案 | 本地私有化部署方案 |
| :--- | :--- | :--- |
| **核心依赖** | 公网连通性、服务商服务等级协议（SLA） | 物理显卡硬件、机房供电散热、本地驱动栈与推理服务进程 |
| **典型故障表现** | HTTP 429（接口限流）、HTTP 502/503（云端宕机）、网络丢包重试 | 显存 OOM 崩溃、显卡过热降频、CUDA 驱动版本冲突、显存碎片化 |
| **运维工作量** | 极低：仅需管理客户端的重试熔断机制与 API Key 轮转 | 较高：需负责硬件监控、进程守护、驱动补丁、模型量化版本维护 |
| **模型演进方式** | 服务商统一迭代升级或下线端点，可能引发输出风格静默漂移 | 权重文件本地固定，输出表现长期一致；升级新模型需自行验证适配 |

## 综合持有成本（TCO）算例推导

关于本地部署常有一种误解：“购买显卡是一次性支出，之后每次调用都免费”。这种核算忽略了硬件折旧、机房电费制冷以及不可忽视的工程维护人力。必须通过**全生命周期持有成本（Total Cost of Ownership, TCO）**进行定量比对。

### 本地部署的年度成本构成

本地硬件的年度综合成本 $C_{\text{local\_annual}}$ 可表示为：

$$C_{\text{local\_annual}} = \frac{C_{\text{CAPEX}}}{N_{\text{years}}} + C_{\text{power}} + C_{\text{maintenance}}$$

1. **资本支出（CAPEX）折旧**：GPU 工作站或服务器采购费用，通用硬件通常按 $N=3$ 年进行线性折旧。
2. **能源与电力开销**：整机运行功耗加上机房制冷消耗（通过能效比 PUE 体现，通常取 $1.3\sim1.5$）：
   $$C_{\text{power}} = P_{\text{kW}} \times \text{PUE} \times 24\text{ h} \times 365\text{ d} \times \text{电价}$$
3. **运维人力与环境分摊**：设备监控、系统故障排查所占用的工时成本。

### 成本临界点算例

我们设定一个常见的对比算例：

**【情景假设】**
- **业务需求**：内网系统需要运行一个 14B 级别的指令模型进行文档批处理与信息提取。
- **云端 API 计费**：假设使用同等能力商用 API，输入输出混合计费综合单价折合为 $0.003\text{ 元} / 1,000\text{ Token}$（即 3 元 / 百万 Token）。
- **本地硬件方案**：配置一台搭载 24 GB 显存 GPU 的专用工作站。
  - 整机及显卡采购成本 $C_{\text{CAPEX}} = 24,000\text{ 元}$，按 3 年折旧，每年折旧费为 $8,000\text{ 元}$；
  - 系统平均运行功耗按 $350\text{ W} = 0.35\text{ kW}$ 计，PUE 取 $1.4$，商业电费按 $1.0\text{ 元/度}$ 计：
    $$C_{\text{power}} = 0.35 \times 1.4 \times 24 \times 365 \times 1.0 \approx 4,292\text{ 元/年}$$
  - 保守估计日常运维与机位分摊成本：$C_{\text{maintenance}} = 2,500\text{ 元/年}$；
  - 本地固定年化成本合计：$C_{\text{local\_annual}} = 8,000 + 4,292 + 2,500 = 14,792\text{ 元/年}$。

![TCO 综合成本与日均 Token 吞吐量的平衡曲线](/images/content-rebuild/977c42ffc5258b3d/fig-5.png)

**【临界点计算】**

计算使得云端调用总费用等于本地年化成本的年度 Token 消耗量 $T_{\text{annual}}$：

$$T_{\text{annual}} \times \left(\frac{0.003\text{ 元}}{1,000\text{ Token}}\right) = 14,792\text{ 元}$$

$$T_{\text{annual}} \approx 4.93 \times 10^9 \text{ Token} \approx 49.3 \text{ 亿 Token/年}$$

折算为日均调用量：

$$T_{\text{daily}} = \frac{49.3\text{ 亿}}{365} \approx 1,350\text{ 万 Token/天}$$

**【经济学分析】**：
- 如果系统处于早期开发验证阶段，或者属于低频办公场景，每天调用量只有几十万到两三百万 Token，**调用云端 API 具备显著的经济优势**，且不需要承担硬件闲置与贬值风险。
- 只有当业务规模扩大、形成 24 小时持续稳定的吞吐需求（例如自动化日志过滤、持续代码扫描），日均吞吐稳定超过 **1,000 万 ~ 1,500 万 Token** 且算力利用率较高时，自建本地部署的边际成本优势才会显现。
- 如果调用量存在严重的潮汐特征（如白天集中、夜间完全闲置），设备整体利用率不高，自建硬件的收本周期还会进一步拉长。

## 架构选型决策路径

结合物理机制、合规属性与成本临界点，我们可以梳理出清晰的选型路径：

![大模型私有化部署与云端 API 架构决策树](/images/content-rebuild/977c42ffc5258b3d/fig-6.png)

### 适合选择本地私有化部署的场景

1. **严格物理隔离环境**：涉及金融核心、政企涉密内网、工控网络等切断外部公网连接的环境，接入外网 API 是合规否决项。
2. **高度敏感的核心资产**：未公开的核心算法代码、实验原始数据等，团队承受不起任何因网络攻击或凭证泄露导致的数据外溢风险。
3. **确定性超低网络延迟要求**：边缘设备控制、机器人实时响应等场景，需要微秒级内网直连，无法承受公网握手与路由抖动。
4. **高负荷全天候批量处理**：全天持续满载运行的任务，长期 Token 消耗量已大幅越过 TCO 成本临界线。

### 优先推荐选用云端商用 API 的场景

1. **业务原型开发与敏捷验证**：处于验证期或需求变动频繁的业务，调用 API 可以实现零前期投入与按需付费，避免沉没成本。
2. **超长上下文与前沿深度推理**：需要单次分析整本技术手册、数百页财报或复杂逻辑分析（输入超过 64K~128K Token）。在本地运行长上下文对显存需求极高，且端侧小模型在长距离注意力保持上往往弱于云端前沿大模型。
3. **多模态与复杂工具调用链路**：业务重度依赖复杂的网络检索、多层函数调用（Function Calling）以及图像识别等能力。若对多模态输入机制尚不清晰，可参阅 [多模态模型是什么？](/fundamentals/multimodal-basics/what-is-multimodal.md)。端侧轻量模型在长链条工具调用的稳定性上与前沿商用模型仍有客观差距。
4. **团队缺乏基础设施运维人力**：没有专人负责 GPU 驱动兼容、容器调度与健康监控的团队，自建服务容易陷入维护泥潭，直接调用托管 API 更为稳妥。
