传统的检索增强生成（RAG）通常按照固定的单向顺序执行：接收用户问题、转换为向量、检索相关文档切片、拼接成提示词交由大语言模型（LLM）生成回答。这套流程被称为线性流水线。

在处理简单的事实查询时，线性流水线足以胜任。但当遇到跨实体比较或依赖前置结果的多跳问题时，单次检索往往无法一次性收集完整证据。

例如，用户提出这样一个问题：**“测算平台 A 和平台 B 当前 70B 模型的按 Token 计费差价，并给出每天 100 万输入/输出 Token 下的月度成本差额。”**

如果使用传统线性 RAG，系统只能把整段长句打包做一次检索：
1. 检索器返回的内容可能只包含平台 A 的定价，平台 B 的信息完全未被召回；
2. 召回的文档可能是去年的旧归档，缺乏时效性校验；
3. 最终大模型面对残缺的上下文，要么回答“数据不全无法计算”，要么利用预训练参数中的过时信息编造结果。

Agentic RAG 的核心改变，是将大语言模型从单纯的“末端总结器”升级为**“控制检索流程的决策节点”**。系统将检索、改写、计算等能力封装为工具，由模型与状态机配合，动态规划多步执行路径。

## 一、架构演进：从单向流水线到状态控制流

根据 Anthropic 对智能体系统的架构定义，复合大模型系统可以清晰地区分为两类：
- **工作流（Workflows）**：通过预设代码路径编排模型与工具，由逻辑管道或条件分支主导控制流。
- **智能体（Agents）**：由大模型动态引导执行流程和工具调用，决定下一步做什么。

检索增强系统的发展历程正体现了从静态工作流向混合控制流的演化：

```
1. 朴素 RAG (Naive RAG)
[用户输入] ──> [向量检索] ──> [拼接上下文] ──> [单次生成] ──> [输出结果]

2. 高级模块化 RAG (Advanced RAG)
[用户输入] ──> [查询扩展] ──> [向量+BM25混合检索] ──> [RRF融合排序] ──> [交叉编码重排] ──> [单次生成]

3. 动态状态控制 (Agentic RAG)
                    ┌──────────────┐
                    │  用户输入问题  │
                    └──────┬───────┘
                           │
                           ▼
                     [状态控制器/LLM] ◄────────────────┐
                           │                           │
               ┌───────────┼───────────┐               │ 证据不足
               ▼           ▼           ▼               │ 改写重试
          [子任务拆解] [检索工具A] [检索工具B]         │
               │           │           │               │
               └───────────┼───────────┘               │
                           ▼                           │
                     [证据完整性校验] ──(未通过校验)────┘
                           │
                       (校验通过)
                           │
                           ▼
                     [最终回答合成]
```

1. **朴素 RAG（Naive RAG）**：单进单出。检索与生成的步骤在代码中完全写死，中间没有检查机制，一旦初次检索未命中即告失败。
2. **高级模块化 RAG（Advanced RAG）**：引入了更成熟的工程组件，例如稠密向量与 BM25 稀疏检索混合、倒数排名融合（RRF）以及 Cross-encoder 重排序。召回质量提升了，但控制流依然是预设的单向有向无环图，无法在运行时根据检索结果反思“证据够不够”。
3. **动态状态控制（Agentic RAG）**：系统通常由状态图（如 LangGraph）驱动，将检索操作封装为受控工具。系统在每一步运行后检查状态变量：如果检索出的证据缺少关键字段，触发改写重试；如果问题包含多个独立实体，拆解为多个子检索分支并行查询。

## 二、工程权衡：质量收益与系统开销的算例对比

引入动态回环并非零成本的架构升级。在系统设计中，灵活性与成本、时延直接冲突。我们以处理前文提到的“双平台 70B 模型价格比对与月度测算”为例，进行同等任务下的基准开销测算：

### 1. 资源消耗与时延对比（示意算例）

设：嵌入检索单次耗时 30ms，BM25 检索耗时 20ms，重排序耗时 80ms；大模型输入处理速率为 50 tokens/ms，首字生成延迟（TTFT）为 400ms，每输出 1 token 耗时 20ms。

| 指标维度 | 传统单向 RAG (混合检索+重排) | Agentic RAG (拆解查询 + 2次检索 + 1次自检修正) |
| :--- | :--- | :--- |
| **LLM 调用次数** | **1 次**（最终生成） | **4 次**（规划拆解 $\to$ 子检索A $\to$ 改写重查B $\to$ 最终合成） |
| **工具调用次数** | **1 次**（批量混合召回） | **3 次**（定向检索 A、初次检索 B、补充检索 B） |
| **输入 Token 总量** | 约 2,000 tokens | 约 7,500 tokens（多轮状态与上下文累积传递） |
| **输出 Token 总量** | 约 500 tokens | 约 1,200 tokens（包含中间推理、JSON 工具参数与最终答案） |
| **端到端 P95 延迟** | **~10.5 秒** | **~26.0 秒** |
| **单次请求费用估算** | 基准成本 $1\times$ | 约 $3.5\times \sim 4.5\times$ |
| **跨实体问题回答完整率** | 较低（易遗漏单侧平台数据） | 显著提高（通过状态机显式补齐两侧证据） |

*注：上述数值为同一硬件配置与模型服务下的典型工程估算（端到端延迟由检索耗时、各轮首字生成延迟 TTFT 与解码生成耗时累加构成，如传统单向 RAG 在 20ms/token 解码速率下输出 500 tokens 耗时即达 10.0 秒），实际表现取决于网络环境、并发量及具体提示词长度。*

### 2. 核心架构风险
- **时延放大**：每一次 LLM 决策与工具调用都是串行阻塞点，端到端延迟呈倍数增加。
- **死循环与偏航**：如果证据评估逻辑提示词编写不严密，模型可能反复改写无意义的查询词，最终耗尽 Token 触发超时截断。
- **非确定性放大**：单向流程只存在 1 次模型输出随机性，而包含 4 次模型决策的 Agent 系统，任何一步产生解析错误（如生成的 JSON 参数不合法），都会导致下游链路异常。

因此，在工程实践中应遵循审慎原则：**凡是可以通过优化文档元数据过滤（Metadata Filtering）、增强切片策略或使用静态混合检索解决的场景，切勿过早引入自主循环。**

## 四、前置工程准备与基准测试规范

在开始构建智能体控制回路前，必须在工程环境中建立可量化的评估基准，杜绝“凭感觉调优”：

```python
# 最小可观测状态图结构示例（基于 LangGraph 概念）
from typing import TypedDict, List
from langgraph.graph import StateGraph, START, END

class AgentState(TypedDict):
    question: str
    sub_queries: List[str]
    documents: List[str]
    retry_count: int
    is_sufficient: bool
    final_answer: str

def route_or_plan(state: AgentState):
    # 确定性代码逻辑与模型决策可混用
    if state["retry_count"] >= 3:
        return "synthesize"  # 达到重试上限，强制截断至合成节点
    return "retrieve"

workflow = StateGraph(AgentState)
# 节点添加与控制流编排...
```

### 落地前必须建立的指标项：
1. **固化检索基线**：在接入模型决策前，先基于固定数据集（如包含标准问答对与参考文档切片的测试集），测量纯检索阶段的召回率（Recall@K）与倒数排名均值（MRR）。
2. **设立 Agent 专有指标**：
   - **收敛率（Convergence Rate）**：多步循环在限定步数内正常完成的比例，异常跳出或超时的请求记为失败。
   - **平均工具调用步数（Mean Tool Steps）**：衡量规划器是否存在多余的冗余调用。
   - **P95 / P99 响应延迟**：监控最坏情况下的系统响应耗时，确保满足线上 SLA 要求。
3. **全链路追踪（Traceability）**：在系统初始化时接入 LangSmith、Graphsignal 或基于 OpenTelemetry 的链路追踪系统，对每一次状态流转、工具输入参数及返回内容进行持久化记录，以便排查模型幻觉与偏航链路。
