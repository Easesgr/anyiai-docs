在上一篇[Workflow 工作流到底是什么？为什么很多自动化任务都需要流程编排？](/frontier/workflow-orchestration/what-is-workflow.md)中，我们讨论了为什么复杂任务不能只靠单次大模型提示词，而需要拆解为清晰受控的编排流程。

但在实际写代码或使用编排框架时，许多人会遇到一系列具体概念：节点、边、全局状态、条件路由。它们到底分别负责什么？彼此之间如何传递数据？

简单来说：
* **节点（Node）** 是干活的具体步骤；
* **边（Edge）** 是步骤之间的流转方向；
* **状态（State）** 是随流程演进的共享账本；
* **条件分支（Router）** 是在路口根据检查结果选择走哪条路。

为了看清它们如何配合，本文以一个具体的任务贯穿始终：**技术文章自动初审与润色流水线**。这个流程接收作者的草稿，进行格式与合规检查，若有问题则退回自动润色，确认合格后再准备发布。

---

## 一、节点（Node）：执行具体任务的最小逻辑单元

节点是工作流中负责实际计算的基本单元。在程序层面，一个节点通常就是一个接收输入、完成特定处理、返回输出结果的函数。

![节点内部契约结构示意图](/images/content-rebuild/31298a2d3328141d/fig-1.png)

### 1. 节点的执行过程
在标准设计中，节点应当保持单一职责，不应该在函数内部直接调用下一个节点，也不应该越权直接改写全局环境中与自己无关的变量。

典型的节点执行流程分为三步：
1. **读取数据**：从当前工作流的状态中获取自己所需的字段（如待审文章草稿）。
2. **执行处理**：调用大模型、检索数据库或运行一段规则代码（如检查文章字数是否超标）。
3. **返回增量**：将计算结果整理为规范的数据结构并返回，交由工作流引擎合并回状态中。

### 2. 为什么节点不能直接透传自由文本？
如果一个节点调用大模型后，直接把模型的自然语言回复作为文本抛给下一个节点，下游节点就必须用正则去截取或者再调一次模型去“猜”上游到底想表达什么。这种方式极易因提示词变动或模型偶发输出格式漂移而报错。

工程实践中，节点间传递的数据需要通过数据模型显式声明字段格式（例如在 Python 中使用 Pydantic）：

```python
from typing import Optional, List
from pydantic import BaseModel, Field

# 节点输入数据定义
class ContentEvaluationInput(BaseModel):
    draft_text: str = Field(..., min_length=10, description="待审校的正文草稿")
    max_length_limit: int = Field(default=2000, description="最大字符限制")

# 节点输出数据定义
class ContentEvaluationOutput(BaseModel):
    passed: bool = Field(..., description="是否通过质检")
    quality_score: float = Field(..., ge=0.0, le=1.0, description="质量评分")
    violations: List[str] = Field(default_factory=list, description="违规或待修改要点")
    suggested_revision: Optional[str] = Field(default=None, description="修改建议")
```

当节点的大模型输出不符合 Schema 要求时，校验机制能在当前节点内立刻捕获异常并决定重试，避免非法格式的数据污染下游流程。

## 二、有向边（Edge）：定义步骤之间的依赖关系

节点定义了“谁来干活”，而边则定义了“按什么次序干活”。有向边连接了两个节点，指明了控制流的流转路径。

![有向边拓扑与汇聚机制](/images/content-rebuild/31298a2d3328141d/fig-2.png)

### 1. 串行边（Sequential Edge）
最常见的依赖关系是串行：$A \to B$。节点 $B$ 的启动严格依赖于节点 $A$ 的成功执行与结果提交。
在文章审核流水线中，“提取文本”到“敏感词过滤”往往是串行的，只有文本提取成功且过滤通过，后续检查才有意义。

### 2. 扇出并发（Fan-out）
当某个节点的输出可以被多个互不依赖的任务同时消费时，可以通过边进行扇出分发：$A \to \{B, C\}$。
例如，草稿准备完毕后，可以同时并发派发给“代码合规检查节点”和“排版风格检查节点”，两个任务并行运行，缩短总体等待时间。

### 3. 多分支汇聚（Fan-in / Join）
并发执行的节点在进入下一步前，通常需要汇合为统一的控制流：$\{B, C\} \to D$。此时，节点 $D$ 的触发取决于预设的汇聚策略：
* **全量等待（Wait All）**：节点 $D$ 必须等到 $B$ 和 $C$ 均执行完毕且提交结果后才会被调度。这是最常见的数据一致性汇聚方式。
* **任一就绪（Wait Any / Race）**：只要 $B$ 或 $C$ 中任意一个返回结果，节点 $D$ 就立刻被唤醒，剩余未完成节点被取消或忽略结果。通常用于多模型竞速或缓存优先返回的场景。

## 三、状态（State）：跨节点的共享账本与并发写隔离

在现代状态机工作流架构中，各个节点本身尽量保持无状态，业务全生命周期产生的数据统一挂载在**状态容器（State Container）**中。

![状态容器更新机制与并发写隔离](/images/content-rebuild/31298a2d3328141d/fig-3.png)

### 1. 状态结构与更新策略（Reducer）
工作流引擎会维护一个公共的数据字典。当节点运行完毕并返回字典增量时，引擎根据预设规则（归约器 Reducer）决定如何合并数据：
* **覆盖模式（Overwrite）**：新值替换旧值。例如更新当前处理阶段 `current_step = "reviewing"`。
* **追加模式（Append）**：保留历史执行痕迹，将新元素追加到列表中。例如累加修改日志或多轮对话历史。

```python
from typing import Annotated, TypedDict, List
import operator

# 定义工作流共享状态
class WorkflowState(TypedDict):
    task_id: str
    input_query: str
    # 使用 operator.add 声明该字段采用列表追加策略，而非直接覆盖旧列表
    audit_logs: Annotated[List[str], operator.add]
    current_draft: str
    iteration_count: int
    is_passed: bool
    is_terminal: bool
```

### 2. 并发写冲突与命名空间隔离
当流水线通过扇出并发执行节点 $B$（排版检查）和节点 $C$（敏感词检查）时，如果两者同时向状态中的同一个非列表字段写入数据，后完成的节点就会覆盖先完成节点的内容。

为了避免竞态冲突：
1. 优先为并发分支分配独立的字段键名（如 `style_check_result` 与 `security_check_result`）。
2. 若必须写入同一字段，该字段必须显式声明聚合函数（如列表连接或字典键合并）。

## 四、条件分支（Router）：根据判断结果决定走哪条路

流程不可能总是一条直线走到底。当审核发现问题时需要回退修改，通过审核后需要进入发布，这种根据状态做决定的机制就是**条件分支（也称为路由，Router）**。

![条件路由器判别机制对比](/images/content-rebuild/31298a2d3328141d/fig-4.png)

### 1. 条件分支的执行方式
条件分支在代码中通常体现为一个纯逻辑判断函数。它读取当前状态中的关键字段，返回一个目标节点的名称标识，工作流引擎根据这个返回值决定下一步激活哪个节点：

```python
def route_after_evaluation(state: WorkflowState) -> str:
    # 路由函数只做规则判断，不执行耗时计算或调用大模型
    if state.get("is_terminal", False):
        return "end_node"
        
    # 读取前置质检节点写入的强类型布尔字段，避免使用字符串子串匹配
    if not state.get("is_passed", False):
        # 结合重试计数器判断是继续修改还是转人工
        if state.get("iteration_count", 0) >= 3:
            return "escalate_to_human_node"  # 达到阈值，转入人工处理
        return "revise_draft_node"            # 未达阈值，进入自动修改节点
        
    return "publish_node"                     # 审核通过，进入发布环节
```

### 2. 避免对非结构化文本进行模糊匹配
写路由时容易出现一个典型误区：直接在路由函数中判断模型生成的自然语言字符串（例如 `if "通过" in llm_output:`）。

大模型回复中可能包含类似“虽然整体没有完全通过，但写得还行”的句子，简单的子字符串匹配会产生严重误判。因此，**条件路由的输入必须来自于前置节点已解析好的强类型字段（如布尔值或枚举状态值）**，保证分流逻辑确定可靠。

## 五、循环与安全退出：避免自修正链路进入死循环

在让模型自我检查、自我修正的流程中，拓扑图中必然会出现回环路径：草稿生成 $\to$ 质检评估 $\to$ 不合格则修改 $\to$ 重新生成 $\to$ 再次质检。

![自修正循环拓扑与防死循环保护](/images/content-rebuild/31298a2d3328141d/fig-5.png)

### 1. 循环可能带来的工程问题
引入循环后，系统会面临两个潜在隐患：
* **震荡死循环**：大模型在互相冲突的修改建议之间来回摇摆，评估节点持续判定不通过，导致工作流在循环中反复消耗调用额度与时间。
* **上下文无限膨胀**：如果在循环中将每一次修改的草稿全量追加进状态列表，并无节制地传给大模型，几轮迭代后就会逼近上下文窗口上限，导致延迟剧增甚至调用失败。

### 2. 安全退出防护措施
带循环的工作流中，必须在状态和分支中加入防护逻辑：
* **显式设置迭代计数器（Iteration Limit）**：状态中维护一个递增的数字 `iteration_count`，每经过一次修改节点便加 1。当达到安全阈值（如 3 次）时，条件路由强制终止循环，将任务导向人工兜底分支。
* **修剪历史状态（Context Pruning）**：修改节点在获取上下文时，只保留上一轮的具体建议与最新草稿，丢弃早期的中间过渡版本，确保上下文长度可控。

## 六、节点级容错：超时控制、重试与降级

在串联了多个外部 API、检索组件和大模型的流程中，单个节点出现瞬态网络抖动或服务波动是不可避免的。工作流的健壮性取决于节点级的容错能力。

![节点级重试与降级流转机制](/images/content-rebuild/31298a2d3328141d/fig-6.png)

### 1. 瞬态错误的指数退避重试
对于 API 速率限制（如 429）或临时网络抖动，节点应配置自动重试机制。重试间隔通常采用指数退避并结合微小随机时间（如 1s、2s、4s 等），避免在服务恢复瞬间所有并发请求同时发起挤兑。

### 2. 超时硬截断
大模型的生成耗时可能受服务负载影响产生波动，数据库检索也可能因网络故障挂起。每个节点必须设置明确的超时时间（例如大模型调用设为 30 秒，数据库检索设为 5 秒）。超时触发后主动取消请求，防止整个工作流执行线程被无限期阻塞。

### 3. 预设降级方案（Fallback）
当节点多次重试依然失败时，流程不应直接崩溃抛错，而应执行预先指定的降级路径：
* **模型降级**：主力大参数模型不可用时，降级调用轻量备用模型完成基础摘要。
* **策略降级**：质检服务发生异常时，默认判定为待核实状态并转入人工审核，而不是盲目放行未经校验的内容。
