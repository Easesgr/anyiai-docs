大模型单次生成带有概率随机性，而业务软件需要稳定的输入输出。面对多步骤、长链路的数据处理任务，如果只依靠一个包含全部要求的大提示词，系统容易出现格式漂移、计算错误和难以定位的中途崩溃。

工作流编排（Workflow Orchestration）解决这个问题的思路，是把任务拆分成多个输入输出契约明确的计算节点，通过显式定义的状态和拓扑边组织执行流程。编排本身并不能消除模型单步推理的随机性，但它能把随机性局限在单个步骤内，并在格式错误或调用超时时提供局部重试、条件分支降级与人工接入机制。

### 贯穿示例：从单步巨型提示词到可控工作流

以“财报结构化提取与核验简报生成”任务为例，完整的处理过程包含四个阶段：

1. **解析与抽取**：从数十页财报文本中提取营业收入、营业成本、净利润等基础指标。
2. **数值逻辑校验**：核验“毛利润 = 营业收入 - 营业成本”等账目勾稽关系。
3. **异常处理**：若校验通过，继续生成经营分析；若校验失败，重试提取或触发人工审核。
4. **成果生成与入库**：生成分析摘要并输出结构化 JSON，存入数据库。

如果将上述所有要求写进一段几千字的提示词，直接交给模型一次性输出，系统通常会遇到三类困难：

* **算术与规则不稳定**：模型擅长归纳与文字表述，但在多位浮点数减法上容易出现偶然失误。直接让模型“自己核算并纠错”，无法通过确定性代码拦截错误。
* **单点故障牵连全局**：一旦中途网络连接超时，或者生成的 JSON 末尾缺少闭合括号，整段耗时几分钟的生成过程全部报废，只能全量重新请求。
* **链路不可观测**：当输出数据出现偏差时，运维人员无法直接判断问题出在原始数据提取不全、校验规则理解偏差，还是最终摘要环节的信息混淆。

通过工作流编排，上述流程被拆解为一个包含代码节点与模型节点的执行图。数值计算由 Python 代码直接完成，格式检验由严格的模式校验器（Schema Validator）拦截，模型仅负责阅读理解和文字整理。局部出错时，系统只需重新执行提取节点，而不影响前面的解析成果。

### 常见设计误区与边界考量

在将模型接入工作流时，常见的工程误区包括以下三项：

1. **用模型替代规则代码**：在工作流中调用大模型执行日期格式转换、浮点数求和或正则表达式抽取。这类操作用本地代码不仅计算开销几乎为零，而且结果稳定；交给模型反而会增加调用成本、网络延迟以及偶发格式漂移的概率。
2. **缺乏状态隔离与并发保护**：在多分支并行执行时，多个节点若直接并发修改同一个无锁共享对象，容易引起状态互相覆盖。稳妥的做法是由各分支节点返回独立的增量更新字典，由主执行引擎统一合并并写入状态快照。
3. **循环重试未设退出上限**：在构建“模型生成 -> 格式校验 -> 校验失败则打回重试”的回路时，必须显式设置最大尝试次数（如 `max_retries = 3`）。如果模型持续产生不符合要求的输出，流程必须中断并触发降级逻辑，防止无意义地消耗调用配额。

### 设计验收与关联知识

完成一个工作流设计后，可以通过两项指标进行检验：
* **局部故障隔离性**：断开某个非关键节点的网络或人工注入格式错误，流程是否能够在该节点处捕获异常并执行重试/降级，而不是导致全局崩溃且丢失已产生的数据。
* **状态可重现性**：从持久化数据库中读取任意历史步骤的状态快照，是否能够准确复现该步骤的输入环境，便于离线排查逻辑问题。
