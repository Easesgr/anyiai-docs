把一个复杂的业务需求交给大模型时，很多开发者最初的做法是写一段两千字的长提示词（Prompt），希望模型一步到位输出结果。这种方式在简单任务上有效，但在长篇研报生成、跨格式资料整理等复杂场景中极易失效：模型单次输出有长度上限，注意力在长文本中可能出现遗漏，更关键的是整个过程缺乏状态记录，一旦中途出错只能推倒重跑。

解决重复性复杂任务的核心是**工作流拆解**：把一个黑盒任务分解为由确定性代码、外部输入输出（I/O）与模型推理共同构成的有向图（包括无环的 DAG 或包含重试循环的状态图）。前两篇文章[《Workflow 工作流到底是什么？为什么很多自动化任务都需要流程编排？》](/frontier/workflow-orchestration/what-is-workflow.md)与[《工作流里的节点、边、状态和条件分支分别是什么？》](/frontier/workflow-orchestration/workflow-concepts.md)介绍了节点与状态的概念。本文以“行业研报生成”和“多源资料清洗”两个具体场景为例，展开拆解步骤、状态设计、质检门禁与异常处理机制。

### 复杂任务的拆解准则：区分规则、I/O 与模型调用

把业务任务拆解成工作流时，首要动作是把不同性质的计算逻辑分开。一个健壮的自动化流程通常包含三类节点：

1. **确定性规则节点**：由本地程序执行，输出确定、耗时短、无外部网络开销。例如正则提取、JSON 格式解析、字数校验和字符串拼接。
2. **外部 I/O 节点**：涉及网络通信，存在超时或中断风险。例如爬虫抓取网页、读取本地 PDF、请求搜索引擎 API 或查询向量数据库。
3. **概率性模型推理节点**：调用大语言模型进行发散生成、摘要或意图理解。此类节点不仅存在网络延迟和成本开销，其输出内容和格式也存在概率波动。

在连接这三类节点时，应遵守两条工程原则：

* **输入前置断言**：在进入成本高昂的模型推理或批量检索前，先用本地代码检查入参是否完整、格式是否符合 Schema、文本是否为空。不符合条件直接抛出错误或终止分支，避免浪费调用额度。
* **单节点职责单一**：避免让同一个节点既做“网络抓取”，又做“信息提炼”，还做“段落润色”。职责分离才能精确定位错误发生在哪个环节，并允许针对单一环节单独重试。

### 案例一：多阶段研报生成流

撰写一份结构严谨的行业研报，如果直接发送指令“请写一份一万字的半导体产业研报”，模型受单次输出 Token 上限和上下文注意力限制，通常只会产出泛泛而谈的提纲式流水账。将其拆解为工作流后，可划分为四个阶段：

#### 1. 结构化大纲规划
输入研究主题后，第一个节点调用规划提示词，强制模型产出标准 JSON 格式的目录树。每个章节对象必须包含唯一标识符 `section_id`、章节标题 `title`、核心观点要点 `key_points`，以及本节专用检索关键词 `search_queries`。这一阶段只产出骨架，不生成正文。

#### 2. 定向检索与证据挂载
工作流引擎解析目录树中的 `search_queries`，调用搜索接口或内部检索模块抓取对应资料。关于知识库检索的详细机制，可参考[《RAG 的完整工作流程是怎样的？核心步骤有哪些？》](/interview/rag-interview/rag-complete-workflow.md)。检索到的参考段落存入该章节的独立上下文槽位，实现数据与章节的局部隔离，避免无关信息污染其他章节。

#### 3. 章节并行草拟（Fan-out 并发）
引擎根据目录树数组发起并行任务，每个子 Worker 仅接收单章的目标、要点与挂载的检索资料，独立生成该章节草稿。通过限制单次输入的上下文范围，模型可以集中处理当前主题，提高论述的信息密度。

#### 4. 汇聚质检与润色（Fan-in & Loop）
所有分支执行完毕后进入汇聚节点（Join）。汇聚后的文本由质检节点核验事实一致性，未达到标准的章节被打回局部重写，通过后再由统一润色节点调整章节间的承接词句，拼装成最终文档。

### 状态设计与质检门禁（Gatekeeper）实现

在多步骤流转中，工作流的状态（State）需要在节点间透明传递。为支持局部重写而不影响已完成章节，状态通常设计为字典或结构体。

```python
# 研报生成工作流状态定义示意
from typing import TypedDict, Dict, List, Optional

class SectionState(TypedDict):
    title: str
    key_points: List[str]
    search_evidence: List[str]
    draft_text: Optional[str]
    verification_score: float
    retry_count: int
    status: str  # "PENDING" | "GENERATED" | "PASSED" | "FAILED"

class ReportWorkflowState(TypedDict):
    topic: str
    outline: List[str]  # 章节 ID 列表
    sections: Dict[str, SectionState]  # 各章节细分状态字典
    global_retry_limit: int
    final_markdown: Optional[str]
```

#### 质检门禁的双层校验机制
质检门禁的作用是防止格式错乱或低质文本流入下游。它分为确定性规则和模型评估两层：

1. **硬规则过滤**：用代码检查草稿长度是否达到最低字数、标题标记是否闭合、关键引用标记是否存在。这部分耗时在毫秒级且无调用费用。
2. **软标准评估**：调用判别模型，比对草稿中的数值或论点是否与 `search_evidence` 一致，并给出 0 到 1 之间的置信度评分 `verification_score`。

```python
def gatekeeper_router(section: SectionState) -> str:
    """门禁质检条件分支路由函数"""
    # 1. 防死循环校验：达到重试上限直接转入人工复核或异常终止
    if section.get("retry_count", 0) >= 2:
        return "route_fallback_review"
    
    # 2. 确定性硬规则检查（字数、关键标记等）
    draft = section.get("draft_text", "")
    if not draft or len(draft) < 300:
        return "route_rewrite"  # 字数不足，退回重写
    
    # 3. 软标准模型评分判断（假设置信度阈值为 0.8）
    if section.get("verification_score", 0.0) >= 0.8:
        return "route_pass"
    
    return "route_rewrite"
```

门禁路由必须绑定 `retry_count`，避免因模型随机性或证据缺失导致整个工作流陷入死循环。

### 案例二：多源资料整理与清洗流

与偏向发散生成的研报流不同，资料整理属于**收敛型任务**，核心目标是提升数据纯度并提取规整的键值数据。

假设需要从企业官网 HTML、PDF 招股书和财务报表 CSV 中提取融资历程与专利数据：

#### 1. 异构数据解析
各类文件的物理存储格式差异很大。解析节点使用专用工具（如 HTML 正文提取库、PDF 文本解析器）去除样式标签，提取出统一的纯文本或 Markdown 片段，并挂载元数据（`source_id`、`url`、`timestamp`）。

#### 2. 本地规则初筛
未经清洗的网页中常常含有大量的导航条、版权页脚和侧边栏推荐。如果直接将原始文本送给大模型，不仅增加 Token 消耗，而且长文本中的噪声会提高漏抽和误抽的概率。
初筛节点通过本地规则过滤无关内容：
* 正则表达式筛选：仅保留包含“融资”、“轮次”、“专利”、“发明人”等目标关键词的段落；
* 去重处理：利用 MinHash 或段落哈希快速剔除重复转载文本。
在富含无关布局或模板信息的网页与文档场景中，规则初筛通常能够过滤掉相当比例的噪声文本（具体削减幅度取决于原始数据源质量），显著减少后续模型调用量。

#### 3. 结构化约束抽取
将清洗后的段落送入抽取模型，并开启结构化输出模式（如 JSON Schema 校验），严格限定字段类型（数字、日期、字符串数组），保证下游入库时不需要编写复杂的容错解析逻辑。

#### 4. 冲突裁决与合并
当两个数据源对同一指标产生冲突时（例如 A 报告显示净利润为 5000 万元，B 报告显示为 4200 万元），不能由模型随机二选一。工作流应通过确定性逻辑进行裁决：优先比对数据更新时间戳；若时间戳相同但统计口径不同，则在数据对象中保留两条记录并打上“需人工复核”标签。

### 应对运行异常的工程机制

工作流在批量运行和高并发场景下，网络抖动、模型服务超时或输出截断属于常态。必须在编排层设计防御机制：

#### 1. 局部并发失败隔离与状态重试
在章节并行生成时，如果章节 3 因网络超时失败，其余 4 个章节已成功生成，工作流引擎不能将整个任务报错崩溃，也不能全量重新生成。
* **异常隔离**：并发线程捕获局部异常，将该章节状态标记为 `FAILED`，并记录错误原因；
* **定向重试**：汇聚节点仅对标记为失败的章节发起退避重试（Backoff Retry），已成功章节的状态保留在持久化存储中，避免重复计费和耗时。

#### 2. 上下文分块与规整
单篇文档过长超出模型有效窗口时，简单的字符切分可能会把表格截断在中间或在句子中途切碎。切分节点应按照文档层级（标题层级、换行符）自适应分块，确保每个分块在上下文预算范围内语义完整，分别进入抽取节点后再做结果聚合。

#### 3. 检查点与人工挂起恢复（Human-in-the-loop）
对于财务、合同等高风险场景，关键节点需要人工把关。使用支持状态机的编排引擎（如[《LangGraph 为什么适合构建可控 Agent 流程？》](/llm-100/agent-engineering/langgraph-controlled-workflow.md)所介绍的模式）时，可以引入中断机制：
* **检查点持久化（Checkpointing）**：在质检节点后将全局状态序列化写入数据库；
* **挂起流程（Suspend）**：工作流停止消耗计算资源，向管理端推送待审核任务；
* **恢复执行（Resume）**：人工确认或修改字段后，引擎根据检查点读取最新状态，继续触发下游的发布或入库节点。

### 性能观测与拓扑优化

搭建好工作流后，需要通过可观测性工具收集节点维度的运行数据：
* `latency`：各节点的端到端执行耗时；
* `token_usage`：模型调用的输入与输出 Token 数量；
* `retry_rate`：各节点的重试次数占比。

#### 常见优化方向：
* **消除长尾瓶颈**：在并行分支中，总耗时取决于最慢的分支（木桶效应）。如果某一章节由于检索返回量过大导致生成过慢，应限制检索注入的上下文长度上限，防止单个分支拖慢全局。
* **用本地代码替换无意义的模型调用**：检查工作流中是否包含让模型做“日期标准化”、“去除超链接”、“简单正则匹配”的节点。把这些操作替换为本地代码后，处理时间能从秒级降低至毫秒级，同时杜绝格式幻觉。
* **匹配合适的控制架构**：路径固定、容错要求高的场景适合严格的 DAG 工作流；若任务需要根据外部环境动态决策调用哪些工具，可参考[《RAG、Agent、Workflow 在系统设计中分别适合解决什么问题？》](/interview/ai-system-design-interview/rag-agent-workflow.md)与[《MCP 的工作流程是什么？》](/interview/agent-interview/mcp-workflow.md)进行组合。若需构建端到端自动化项目，可进一步参考[《AI 自动化工作流》](/projects/ai-workflow-automation.md)。
