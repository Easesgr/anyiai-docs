在开发基于大语言模型的自动化系统时，开发者往往会经历一个典型阶段：起初尝试写一段巨细靡遗的长提示词，试图让模型一步到位搞定所有事；但当任务涉及多步业务校验、外部接口调用和严格的数据输出时，系统经常在偶发格式错误或漏掉某条业务规则上卡住。

工作流（Workflow）编排解决这个问题的思路很直接：**用编写好的程序代码负责流程调度、状态存储和数据校验，把大语言模型的调用限制在局部明确的单一任务节点中**。这样既能利用模型的自然语言理解能力，又能让全流程处于受控、可追踪、易重试的状态。

以常见的电商售后自动化为例：用户发来一句“我想退掉昨天的衣服，尺码买小了，订单号 ORD-2026-X”。如果指望一段提示词一次性完成“提取单号、查数据库验证物流、核验退货规则、计算应退金额、向支付网关发起退款”全流程，模型很可能会在复杂推理中遗漏退货时效校验，或者输出格式微小漂移导致支付接口调用崩溃。如果改为工作流，则把过程拆解为提取信息、接口核验、规则分支与最终通知几个独立阶段，每一步由代码做强校验，出现问题只在局部排查。

![工作流编排在确定性控制与模型概率生成之间的定位关系](/images/content-rebuild/f73d2fd21c8a5a69/cover.png)

上图展示了从单次端到端长提示词向工作流编排过渡的结构变化。左侧把所有业务目标与限制全部塞进单次提示词，模型在长上下文中的细微误判会扩散到整条任务中；右侧的工作流编排则通过程序代码将任务划分为独立阶段，每个节点拥有独立的输入、输出和检验逻辑。

## 为什么单次调用难以应对复杂自动化任务？

大语言模型是基于上下文进行自回归采样的概率模型。当在单次调用中堆叠过多指令时，系统的失控风险会随任务步骤的增加而快速上升，主要表现在以下三个方面：

### 1. 指令竞争与边缘约束遗漏
当一段提示词同时包含角色设定、背景事实、字段格式要求、负面约束（禁止事项）以及多步骤推理逻辑时，模型对不同约束的遵循能力会出现注意力分散。开发者经常发现，模型很好地完成了长文本概括，却忽视了末尾“金额字段必须保留两位小数且不得包含货币符号”的硬性要求。

### 2. 输出格式漂移导致下游系统报错
生产环境中的业务接口通常要求严格的 JSON 或特定数据结构。即使在调用时开启了 JSON 模式，单次调用如果同时承担复杂业务逻辑推理，模型仍可能在极端情况下返回缺失键名、类型不匹配或带有多余文本包裹的数据。这些非预期的格式漂移，会直接打崩下游微服务或数据库的反序列化逻辑。

### 3. 多步依赖下的级联误差累积
设想一个自动化任务包含 $n$ 个前后串联的判断环节。假设各个判断环节彼此独立，且每一步在单次调用中的准确率均为 $p$（其中 $0 < p < 1$），那么在没有任何中间纠错拦截的情况下，端到端单次运行全部正确的概率估算示意为：
$$P_{\text{total}} = \prod_{i=1}^{n} p_i = p^n$$
*说明：该公式仅用于展示步骤串联下的概率乘积效应。在真实场景中，前置步骤如果出现错误事实或漂移，会作为下游推理的输入，导致后续步骤产生更严重的级联偏差。*

![单次长提示词任务与多步骤流水线调用中的误差传递机制对比](/images/content-rebuild/f73d2fd21c8a5a69/fig-1.png)

上图对比了单次端到端调用与分步流水线调用的错误传导差异。在单次调用中，中间环节出现的任何事实偏差都会污染后续输出；而在分步工作流中，前置节点的输出必须经过宿主代码的逻辑检查，不合规的数据会被拦截或触发重试，阻止错误继续向下游蔓延。

## 工作流的协作机制：代码骨架与模型节点

工作流编排的核心架构由两部分组成：
- **确定性代码骨架**：由 Python、Go 等编程语言或工作流引擎（如 Temporal、Dify、LangGraph）编写，负责调度执行顺序、维护状态机、处理条件分支、执行数据模式（Schema）校验以及外部系统调用。
- **语义处理节点**：将大模型（[什么是大模型](/fundamentals/llm-basics/what-is-llm.md)）封装在特定节点内，仅负责自然语言信息提取、意图分类、文本润色等模型擅长的非结构化数据处理任务。

<ReadMoreLock />

需要指出的是：**把模型放入工作流中，并不意味着模型本身的幻觉或偶发错误会凭空消失**。如果某个节点提取了错误的单号，下游如果不做校验，错误依然会沿着流程传递。工作流的实际工程意义在于：它通过代码在节点之间设置了“检查站”，当模型输出不合规时，可以即时阻断并报警，而不是任由脏数据写入核心数据库。

以下是一段最小可运行的 Python 示例，演示了代码骨架如何通过数据模式校验拦截异常模型输出，并根据合规规则控制执行分支：

```python
import json
from typing import Dict, Any

class WorkflowContext:
    def __init__(self, raw_input: str):
        self.state: Dict[str, Any] = {"raw_input": raw_input}
        self.errors: list[str] = []

def mock_llm_extractor(text: str) -> str:
    # 模拟模型输出的 JSON 文本
    return '{"user_intent": "refund", "confidence": 0.92, "order_id": "ORD-2026-X"}'

def node_extract_intent(ctx: WorkflowContext) -> bool:
    """节点 1：调用模型抽取意图，并通过程序进行强模式校验"""
    llm_output = mock_llm_extractor(ctx.state["raw_input"])
    try:
        parsed = json.loads(llm_output)
        # 校验必需字段与数值范围
        required_fields = {"user_intent", "confidence", "order_id"}
        if not required_fields.issubset(parsed.keys()):
            raise ValueError(f"缺失关键字段: {required_fields - parsed.keys()}")
        if not (0.0 <= parsed["confidence"] <= 1.0):
            raise ValueError("置信度数值超出 [0, 1] 范围")
            
        # 校验通过，写入上下文状态
        ctx.state["intent_data"] = parsed
        return True
    except Exception as e:
        ctx.errors.append(f"节点 [ExtractIntent] 校验未通过: {str(e)}")
        return False

def node_route_action(ctx: WorkflowContext) -> str:
    """节点 2：由业务代码决定的路由分支"""
    intent = ctx.state["intent_data"]["user_intent"]
    confidence = ctx.state["intent_data"]["confidence"]
    
    # 业务硬规则：低置信度强制走人工核验
    if confidence < 0.8:
        return "route_human_review"
    if intent == "refund":
        return "route_process_refund"
    return "route_general_faq"

# 调度主流程
context = WorkflowContext(raw_input="我想退掉昨天的订单 ORD-2026-X")
if node_extract_intent(context):
    next_step = node_route_action(context)
    print(f"工作流正常流转，下一执行节点: {next_step}")
else:
    print(f"工作流被程序阻断: {context.errors}")
```

![确定性宿主程序骨架与非确定性大模型节点的协作数据流](/images/content-rebuild/f73d2fd21c8a5a69/fig-2.png)

上图展示了宿主程序与模型节点的数据流转：原始输入进入工作流后，由上下文状态机统一管理；模型节点仅在局部被调用；其返回结果经程序做结构和业务边界校验，合格后才写入持久化状态机，校验失败则流向重试或错误处理分支。

## 工作流与自主智能体的核心差异：控制权在谁手里

在很多讨论中，开发者容易把 [AI Agent（智能体）](/interview/agent-interview/what-is-agent.md) 与 Workflow 混为一谈。两者的根本区别不在于是否调用了外部工具，而在于**调度控制权的归属**：

| 对比维度 | 工作流编排（Workflow） | 自主智能体（Autonomous Agent） |
| :--- | :--- | :--- |
| **决策控制权** | 由开发者预先编写的代码或图拓扑控制 | 由大模型在推理循环中动态决定下一步动作 |
| **执行路径** | 路径预先定义，按条件分支与状态机流转 | 路径开放，模型根据环境反馈动态尝试新步骤 |
| **工具调用方式** | 在指定节点由程序规则触发特定工具 | 由模型根据任务目标自主判断调用哪个工具 |
| **调试与复现** | 节点边界清晰且上下文可记录，便于隔离排查与单步重现 | 依赖长链条自回归推理，环境反馈与推理交织，定位较复杂 |
| **典型适配场景** | 退款审批、发票报销、合同初审等强规则任务 | 开源项目排错、开放性研究调研、复杂代码生成 |

在进行系统架构设计时（详细选型逻辑可参考 [RAG、Agent 与 Workflow 的架构选型](/interview/ai-system-design-interview/rag-agent-workflow.md)），越是涉及资金操作、合规审查或权限变更的任务，控制权越需要留在代码工作流中；而面对路径不确定、需要试错探索的任务，才适合将控制权交给 Agent。

![工作流确定性编排与智能体自主循环的决策主权对比](/images/content-rebuild/f73d2fd21c8a5a69/fig-3.png)

上图展示了两类模式的运行时差异：工作流依靠代码规则沿着预设图结构流转，每一步分支边界清晰；Agent 则由模型主导“思考-行动-观察”的自回归循环，由模型动态决定何时终止任务。

## 常见的三种编排模式与选型边界

在实际业务中，工程架构并不是在“固定死板”和“完全自主”之间做二选一，而是一个连续的光谱：

```
[ 静态顺序流水线 ] ────> [ 条件分支工作流 ] ────> [ 自主规划智能体 ]
  高控制力 / 低灵活性        适中控制力 / 适度灵活性        低控制力 / 高灵活性
  代码指定线性步骤           代码预设分支与退出条件        模型自主决定探索路径
```

### 1. 静态顺序流水线（Sequential Pipeline）
- **机制**：步骤按照固定次序串行推进，不包含动态路由分支。
- **适用条件**：输入输出关系固定的标准流水线。例如：客服通话录音 $\rightarrow$ 语音转文字 $\rightarrow$ 提取会话摘要 $\rightarrow$ 归档入库。

### 2. 条件分支工作流（DAG / 状态机工作流）
- **机制**：由显式的路由节点（Router）根据前置步骤的数据或模型评分，决定下一步走哪个预设分支，并支持固定轮次的循环纠错。
- **适用条件**：包含明确的业务规则分流。例如：审核退款申请，若模型抽取的订单金额小于 50 元且用户信誉良好，流向自动退款接口；若金额大于 500 元或置信度偏低，流向人工审核分支。

### 3. 自主规划智能体（Planner / ReAct Loop）
- **机制**：给模型设定终极目标和可用工具库，由模型自发拆解步骤、调用工具、观察返回值并调整后续策略。
- **适用条件**：路径无法提前穷举。例如：分析某项线上服务偶发变慢的根因，需要根据日志内容动态决定查询指标、查看堆栈还是检查网络拓扑。

**选型边界规则**：如果任务中包含不可逾越的业务红线（例如“向用户退款前必须核实退货快递单号是否有效”），该逻辑应以硬编码的形式写在工作流中，而不宜交由模型自主决定“这次要不要验证快递单号”。

![从静态流水线、条件分支到自主规划的灵活性与控制力权衡象限](/images/content-rebuild/f73d2fd21c8a5a69/fig-4.png)

上图展示了三类模式在控制力与灵活性之间的取舍。静态流水线和分支工作流为业务提供了较高的可预测性和合规边界，而自主规划智能体则在未知任务的探索上具备更强灵活性。

## 为什么复杂自动化任务倾向于使用流程编排？

引入工作流虽然增加了代码骨架的开发成本，但在工程层面带来了四项核心能力：

### 1. 断点缓存（Checkpointing）
调用大模型不仅耗时较长，而且每一次调用都会消耗 [Token](/fundamentals/token-and-tokenizer/what-is-token.md)。假设一个自动化任务包含 4 个步骤，第 4 步因为外部接口超时失败。在单次调用方案中，只能从头重跑整个提示词；而在工作流架构下，系统可以把前 3 步处理好的状态保存在数据库或缓存中，重试时直接从第 4 步恢复，避免重复消耗资源和时间。

### 2. 单步调试与调用追踪（Trace）
长提示词如果输出不及预期，开发者很难判断是哪一句描述引发了歧义。在工作流中，每个节点都有明确的输入、输出、处理耗时与 Token 开销日志。开发者可以把失败节点的输入数据单独提取出来，编写单元测试进行局部调优，排查效率显著提升。

### 3. 超时与重试策略（Retry & Timeout）
外部模型接口偶发超时或遭遇限流（Rate Limit）是常见现象。工作流允许针对具体节点配置不同的重试机制：对轻量级的文本抽取节点设置指数退避重试，对高耗时的总结节点设置超时熔断，防止单一故障阻塞全局任务。

### 4. 语义降级与兜底保护（Fallback）
当主力模型响应超时或格式校验连续失败时，工作流可以通过代码捕获异常，自动切换为备用模型，或者直接返回预设的默认模板，避免整个前端应用直接抛出未捕获的系统异常。

上图展示了工作流应对节点异常的容错机制：当中间节点校验失败或网络中断时，系统依赖检查点机制进行局部重试或降级，保护前置节点的计算结果，同时避免脏数据污染后续流程。

## 宏观工作流与微观智能体的组合

在实际工程中，工作流与智能体并不是排他的对立关系，许多成熟系统采用**混合架构（Hybrid Architecture）**：在宏观层面上使用工作流把控不可跳过的业务边界；在微观层面上，将需要动态探索的环节封装为一个微型 Agent 作为工作流的一个节点。

还是以售后争议处理为例：
- **宏观工作流**：接收售后申请 $\rightarrow$ **异常证据排查节点（微型 Agent）** $\rightarrow$ 财务风控硬规则校验 $\rightarrow$ 执行退款或驳回。
- **微观 Agent**：在证据排查节点内部，微型 Agent 可以根据情况自主决定是去查物流详情、比对退货照片还是检索售后聊天记录，并整理出一份结构化的排查结果；排查结束后，控制权交还给外层工作流，继续执行不可跳过的财务硬规则。

![工作流作为宏观骨架调度微观智能体子节点的混合架构示意](/images/content-rebuild/f73d2fd21c8a5a69/fig-6.png)

上图展示了宏观工作流与微观 Agent 的协作方式：外层工作流保证端到端业务底线不被突破，内层 Agent 在受控的沙盒节点内完成发散性检索与工具调用。
