在将大语言模型接入业务系统时，许多团队通常会先尝试直接写一个长提示词（Prompt），期望模型一次性完成所有分析、决策和结果输出。然而随着业务复杂度上升，直接调用单次模型的脆弱性很快就会暴露：输出格式偶尔漏掉字段、多步骤推理容易遗漏前置条件、长耗时任务可能因网络抖动中断，以及涉及扣款、发信等外部写操作时无法安全重试。

大模型本质上是一个具备概率特征的生成组件。要让它在企业业务中稳定发挥作用，关键不在于追求“一次写出完美的 Prompt”，而在于**用确定性的程序逻辑（如状态流转、规则验证、错误处理与外部持久化）来包裹、约束并串联非确定性的模型调用**。这种以代码控制流程、让模型承担具体局部分析任务的工程架构，就是 **AI 工作流（AI Workflow）**。

以常见的“电商退款争议处理”为例：如果只用单次 Prompt 处理，系统必须在一个黑盒上下文内同时核对物流信息、评估用户信誉、判定退款金额并触发银行接口。一旦模型误判或接口调用超时，系统很难确定已经执行到了哪一步，极易发生重复退款或直接报错退出。而在工作流设计下，该任务被拆解为顺序明确、带规则校验的链路：先通过规则引擎拉取凭证，再调用模型判断责任归属；遇到大额争议时挂起等待人工复核；最终在确认无误后，带上唯一防重流水号调用退款服务。每一步输入输出都有契约，出错即可局部重试。

## 二、四种常见拓扑结构与业务场景

工作流引擎虽然有不同的开源实现，但在控制逻辑层面，主要由以下四种基础拓扑模式组合而成。我们继续以“退款争议处理”业务映射其具体动作：

| 拓扑模式 | 结构特点 | 退款业务对应动作 | 关键工程注意事项 |
| :--- | :--- | :--- | :--- |
| **顺序链 (Sequential)** | 上游输出经校验后作为下游输入，单向线性推进 | 提取退款诉求文本 -> 解析出订单号与问题类型 | 避免单节点异常阻断整条链路，每一步需有格式降级或明确报错 |
| **并行扇出/汇聚 (Fan-out/in)** | 从一个入口分发到多路独立任务，并在汇聚节点汇总 | 并行查询物流系统、支付扣款流水与用户信誉分，汇总供后续判断 | 汇聚节点耗时取决于最慢分支，多路调用需要设置合理的单路超时时间 |
| **条件分支 (Routing)** | 通过预设规则或轻量分类模型，将请求分流至特定子链路 | 小额常规申请进入自动处理分支，涉嫌欺诈或大额退款进入审核分支 | 分流条件须具备确定性兜底逻辑，避免未知类别导致路由落空 |
| **人工介入环路 (Human-in-the-loop)** | 在高风险节点冻结当前上下文并持久化，等待人工确认后恢复执行 | 退款金额超过阈值时生成审核工单，客服点击确认后唤醒后续打款 | 严禁使用 HTTP 长连接或线程阻塞挂起，必须依靠外部数据库持久化状态 |

![典型 AI 工作流拓扑模式对比](/images/content-rebuild/21a9d9e54f96279c/fig-2.png)

上图对比了从线性流水线到带状态人机回环的控制拓扑结构。普通的内存条件分支无须额外落盘，但在涉及人工介入挂起、外部长异步等待或关键故障恢复点时，系统通常需要依赖外部持久化存储来记录中间状态，防止进程重启导致链路上下文丢失。

## 三、何时该引入工作流引擎？选型与验收清单

引入专门的工作流引擎（如 Temporal、Camunda 或面向 AI 的编排框架）会增加额外的部署与状态维护成本。并非所有涉及大模型的系统都需要复杂框架。团队可以依据任务的“状态复杂度”与“是否有外部副作用”进行评估：

```python
# 业务架构选型评估示意（启发式规则，供工程设计参考）
def evaluate_workflow_architecture(steps_count: int, has_side_effects: bool, is_long_running: bool) -> str:
    # 1. 简易无状态任务：只读分析、单次总结
    if steps_count <= 2 and not has_side_effects and not is_long_running:
        return "轻量级函数调用 / 原生 SDK 脚本即可满足需求"
    
    # 2. 存在外部写操作或长时间跨度的人工介入：需要状态持久化保障
    if has_side_effects or is_long_running:
        return "建议引入具备持久化状态机与重试保障的工作流引擎"
        
    # 3. 步骤较多但全部为只读查询与文本计算
    return "建议采用轻量级内存管道（Pipeline 模式），无需重型引擎"
```

在上述评估中，**是否涉及外部写操作（如扣款、发信、写库）**以及**是否需要跨进程/跨天恢复任务**是核心分水岭。纯粹的只读问答即使步骤稍多，普通内存管道即可胜任；一旦涉及真实外部变更，就必须具备失败重试的幂等保护和状态落盘能力。

![业务架构选型评估与验收维度示意图](/images/content-rebuild/21a9d9e54f96279c/fig-3.png)

上图指示了工程团队在选择架构方案时的关键权衡点：当任务涉及不可逆的外部写操作副作用或需要长时间跨度异步挂起时，通常建议引入具备断点续跑与幂等保障的状态机引擎。

### 系统验收清单

完成本专题的学习与搭建后，可以通过以下四项标准来检验工作流系统的可用性：

- **数据契约与防御**：模型节点输出是否配置了严格的数据结构校验（如 Pydantic / JSON Schema）？当解析失败时，系统是否有格式重试或降级兜底逻辑，而不是直接将解析报错抛给前端？
- **幂等性与重试隔离**：在调用带副作用的外部服务时，是否传递了业务唯一幂等键（Idempotency Key）？当网络超时引发重试时，能否保证外部服务不会被重复执行？
- **无损挂起与唤醒**：面对人工审批或第三方慢回调任务，系统是否将执行上下文完整落库并释放计算资源？服务器重启或节点漂移后能否基于状态记录准确续跑？
- **链路可追踪性**：每次执行请求是否拥有全局唯一的 `trace_id`？当最终输出不符合预期时，能否清晰回溯是哪一个节点的输入偏离、工具调用超时还是模型推理异常所致？
