在很多演示或对话场景中，调用大模型往往只需要一个提示词（Prompt）：把要求和背景丢给模型，等待生成结果。但在实际业务中（例如采购合同审核、财务报表解析、工单自动流转），如果尝试用一个“超级提示词”让模型一次性完成所有事情，系统往往非常脆弱。

解决这个问题的常用方案是 **AI 工作流（AI Workflow）**。AI 工作流并没有改变大模型本身的概率输出特性，而是用传统的确定性程序把任务拆分成多个环节，在大模型、业务规则代码和外部接口之间传递显式状态，并在关键节点设置检查关卡。本文通过一个具体的业务例子，解释为什么单次调用难以应对复杂业务、AI 工作流由哪些部分组成，以及它与自主智能体（Agent）的选型边界。

## 贯穿示例与核心结论

为了直观理解，我们来看一个典型的业务需求：**采购合同自动审核入库**。

这个任务需要完成以下步骤：
1. 从几万字的非结构化合同文本中抽取供应商名称、采购总金额、是否包含违约赔偿条款；
2. 校验金额格式是否合法、是否为正数；
3. 结合公司采购风控规则：如果合同金额大于 1 万元，必须包含违约赔偿条款；
4. 输出标准结论并同步给下游 ERP 财务系统。

如果采用**单次模型调用**方案，工程师会把全部原文、抽取要求、合规规则和 JSON 输出格式写进一段超长提示词，让模型直接返回最终结果。这种做法往往在测试集上表现不错，一旦上线就会遇到严重的不稳定性。

**核心结论**：复杂业务之所以需要 AI 工作流，是因为业务系统通常要求强类型的输入输出与明确的执行路径，而大语言模型本质上是概率推断。AI 工作流通过将任务拆分为离散节点，在节点之间设置程序校验与重试逻辑，把潜在的错误拦截在局部，避免一个字段的异常毁掉整条业务链路。

## 单次模型调用的三个常见工程问题

尝试用单次调用解决长链条任务时，通常会遇到以下三个工程难题：

### 1. 指令堆叠与注意力分散

当一条提示词同时要求大模型“通读全文、精确抽取字段、核算金额逻辑、比对风控合规条文，并按指定 JSON 格式输出”时，指令的复杂度急剧上升。虽然现代大模型的上下文窗口已扩展到数十万 [Token](/fundamentals/token-and-tokenizer/what-is-token.md)，但当输入过长且约束条件过多时，模型对密集规则的遵从度容易出现波动。开发者经常会发现，模型在满足了输出格式的同时，漏掉了核心的违约判断规则。

### 2. 中间过程不可见与误差向后传递

在单次端到端生成中，模型的推导过程对外部系统是完全封闭的。如果模型在抽取阶段把合同金额“50,000 元”误识别成了“5,000 元”，这个错误信息会直接作为它自身后续推导的上下文，导致合规判断完全走偏。外部系统无法在“抽取完成但尚未判断”的时间点进行拦截与纠错。

### 3. 单点格式破损导致链路崩溃

企业系统与模型交互通常依赖结构化格式（如 JSON）。如果要求模型一次性输出深层嵌套的多个业务字段，只要自回归生成在最后一个字段少输出了一个闭合括号，或者在结尾夹带了一句自然语言解释，系统的 JSON 解析器就会直接抛出语法异常。这一次请求消耗的计算时间与网络开销全部作废，必须从头重新请求。

## AI 工作流的三大要素：节点、边与状态

为了解决单次调用的不确定性，工程上将任务组织为图结构或状态机：

> **AI 工作流（AI Workflow）** 是由程序代码显式编排的执行网络。它将大模型调用、代码逻辑（如数据清洗、格式校验）以及外部系统 API 组织成有向图（通常是有向无环图 DAG 或带有限回环的状态机），通过明确的数据载体传递上下文。

一个标准的 AI 工作流包含三个基本组件：

1. **节点（Node）**：执行单一职责的处理单元。节点不只有大模型调用，还包括数据清洗代码、Pydantic 模式校验、外部数据库查询接口或人工审批环节。
2. **边（Edge）**：连接节点的控制流。它定义了任务的流转次序，可以是固定的先后顺序，也可以是依据上一步返回结果判定的条件分支（例如：如果校验失败，走向重试边；如果校验成功，走向风控核算边）。
3. **状态（State）**：在节点之间流转的共享上下文数据。状态通常被定义为具有明确字段类型的对象（如 Python 数据类或字典）。每个节点读取它所需要的字段，并在处理完成后更新相应字段。

```
[输入合同文本] ──> [节点 1: LLM 结构化抽取] ──(校验通过)──> [节点 2: 代码比对风控规则] ──> [节点 3: 汇总输出]
                               │
                           (校验失败)
                               └──> [局部重试或降级告警]
```

## 错误隔离与概率收敛机制

AI 工作流提升稳定性的方式，不是消除大模型输出的波动，而是**控制波动的扩散范围**。

### 1. 任务职责切分

把原本混杂在一条提示词里的多重目标解耦。例如在合同审核中，把“提取数据”和“比对规则”分开。大模型只负责从自然语言中抽取结构化字段，而“金额是否大于 1 万”、“是否有违约条款”这类确定性的逻辑判断，完全交由纯代码执行。代码规则执行成本低、速度快且结果确定，不需要消耗大模型算力。

### 2. 校验拦截与局部重试

在模型节点下游紧跟一个校验环节。如果模型输出的字段缺失或格式错误，系统不需要重新跑整套业务，而是在局部使用包含错误提示的简短提示词，仅针对当前抽取节点发起重试；若多次重试仍不合格，则走预设的降级分支或转人工处理，防止脏数据流入后续节点。

### 3. 概率收敛示意算例

我们通过一个简化的教学算例来说明局部重试对系统整体表现的影响：

假设一项任务包含 3 个前后依赖的子步骤。为了进行数值对比，我们建立以下**教学假设**：
- 假设将 3 个任务合并在一条复杂提示词中单次调用时，端到端成功率为 $P_{\text{single}} = 0.70$；
- 拆分成 3 个独立节点后，每个节点的提示词更聚焦，设单个节点单次执行成功的基准概率为 $p = 0.90$；
- 假定在单个节点内，第一次尝试与重试尝试的失败原因相互独立，且每次调用成功率恒定为 $0.90$。

如果没有局部重试机制，3 个节点串联后的整体成功率为：
$$P_{\text{no\_retry}} = 0.90 \times 0.90 \times 0.90 \approx 0.729$$

如果为每个节点配置局部校验，并允许最多重试 1 次（即每个节点最多尝试 2 次）。在独立性假设下，单个节点 2 次尝试全部失败的概率为 $(1 - 0.90)^2 = 0.01$，因此单节点的达标率提高到：
$$p_{\text{node}} = 1 - 0.01 = 0.99$$

3 个节点相连后，整个系统的达标率近似为：
$$P_{\text{workflow}} = 0.99^3 \approx 0.970$$

> **注意**：上述推导依赖“重试之间相互独立”的理想假设，仅作为解释“局部错误拦截与重试”工程机制的示意算例。在实际生产中，若输入文档本身语义模糊或缺失信息，模型重试也可能持续失败，实际系统的成功率取决于数据质量、提示词设计和兜底降级方案。

## 可验证的最小工作流示例代码

下面是用 Python 编写的一个轻量演示脚本。代码展示了如何使用 Pydantic 定义状态契约，并在抽取失败时进行局部拦截与重试，随后由代码节点完成风控核算：

```python
from typing import Dict, Any, Optional
from pydantic import BaseModel, ValidationError, Field

# 1. 定义数据契约
class ExtractedContract(BaseModel):
    vendor_name: str
    total_amount: float = Field(..., gt=0)
    has_indemnity_clause: bool

# 2. 模拟 LLM 节点（此处注入一个模拟错误：第 1 次金额为负数，第 2 次修正）
def mock_llm_extractor(text: str, attempt: int) -> Dict[str, Any]:
    if attempt == 1:
        # 模拟模型输出非法数据，触发校验拦截
        return {"vendor_name": "Acme Corp", "total_amount": -100.0, "has_indemnity_clause": True}
    # 模拟重试后输出正确格式
    return {"vendor_name": "Acme Corp", "total_amount": 50000.0, "has_indemnity_clause": True}

# 3. 工作流执行流程
def run_contract_workflow(raw_doc: str) -> Dict[str, Any]:
    # 初始化全局状态
    state: Dict[str, Any] = {
        "raw_doc": raw_doc,
        "retry_count": 0,
        "contract_data": None,
        "review_status": "INIT",
        "final_report": ""
    }
    print(f"[Workflow 开始] 输入文本长度: {len(raw_doc)}")

    # ---- 节点 1: 抽取与数据契约校验（最多尝试 2 次）----
    extracted_obj: Optional[ExtractedContract] = None
    for attempt in range(1, 3):
        raw_output = mock_llm_extractor(state["raw_doc"], attempt)
        try:
            extracted_obj = ExtractedContract(**raw_output)
            # 兼容 Pydantic v1 与 v2 的字典导出
            state["contract_data"] = extracted_obj.model_dump() if hasattr(extracted_obj, "model_dump") else extracted_obj.dict()
            print(f"[节点 1: 抽取成功] 第 {attempt} 次调用符合规范")
            break
        except ValidationError as e:
            print(f"[节点 1: 校验拦截] 第 {attempt} 次输出不合规: {e.errors()[0]['msg']}，触发局部重试...")
            state["retry_count"] += 1

    if not extracted_obj:
        state["review_status"] = "REJECTED_INVALID_DATA"
        print("[Workflow 终止] 连续校验未通过，转人工处理")
        return state

    # ---- 节点 2: 业务风控核算（纯 Python 代码逻辑）----
    amount = state["contract_data"]["total_amount"]
    has_clause = state["contract_data"]["has_indemnity_clause"]
    if amount > 10000.0 and not has_clause:
        state["review_status"] = "RISK_HIGH"
    else:
        state["review_status"] = "PASSED_NORMAL"
    print(f"[节点 2: 规则核算] 判定状态为: {state['review_status']}")

    # ---- 节点 3: 生成业务摘要 ----
    state["final_report"] = f"供应商 {state['contract_data']['vendor_name']} 审核完成，结果：{state['review_status']}"
    print(f"[Workflow 完成] {state['final_report']}")
    return state

# 运行测试脚本
if __name__ == "__main__":
    final_state = run_contract_workflow("合同原文：甲方采购总计 50000 元...")
```

在这个小实验中，第 1 次调用的负数金额被直接拦截在节点 1 内部，通过局部重试纠正，没有让异常数据流入节点 2，从而保护了整条业务线。

## 工作流与自主智能体（Agent）的选型边界

在开发中，开发者常问：什么时候该用 AI 工作流（Workflow），什么时候该用自主智能体（Agent）？

两者的核心区别在于**主控权在代码还是在模型**：

| 对比维度 | AI 工作流 (AI Workflow) | 自主智能体 (Autonomous Agent) |
| :--- | :--- | :--- |
| **拓扑结构** | **静态预定义**（开发者预先写好图或状态机） | **运行时动态决定**（模型根据环境反馈决定下一步调用什么工具） |
| **控制权中心** | 外部程序代码掌控主循环 | 大语言模型掌控推演决策主循环 |
| **分支预测** | 所有分支、重试条件和降级策略预先枚举 | 由模型根据中间结果动态规划路径 |
| **执行成本与耗时** | 相对固定且可预测（调用次数与 Token 上限明确） | 波动较大（取决于模型规划的步数，需防范死循环） |
| **排查与可观测性** | 容易观测（每个节点的输入输出及耗时清晰） | 依赖解析模型的思考与调用日志，归因成本相对较高 |
| **适合场景** | 流程明确的审批、文档解析、报表对账、自动化工单 | 开放式资料检索、复杂代码调试、探索性数据分析 |

关于自主智能体的详细机制，可以参考 [/interview/agent-interview/what-is-agent.md](/interview/agent-interview/what-is-agent.md)；两者的混合架构选型对比可见 [/interview/ai-system-design-interview/rag-agent-workflow.md](/interview/ai-system-design-interview/rag-agent-workflow.md)。

工程实践中推荐的选型经验是：**如果业务步骤和规则能够被清晰梳理出来，优先选择确定性更高、更容易排错的工作流；只有当任务环境完全开放、无法预先穷举执行路径时，再考虑让 Agent 全权自主规划。**

## 四种常见的工作流拓扑模式

在实际系统搭建中，AI 工作流通常由以下四种经典模式组合而成：

### 1. 顺序管道（Sequential Pipeline）
最基础的串联模式。前一个节点的输出经过校验和格式转换后，作为下一个节点的输入。例如：文档 OCR $\rightarrow$ 文本清洗 $\rightarrow$ 核心要素提取 $\rightarrow$ 数据入库。

### 2. 条件路由（Routing）
由先导节点根据输入内容进行分类，随后分流至不同的下游路径。例如工单处理中心：先由分类节点判断用户诉求，技术问题路由至知识库检索节点，退款投诉路由至订单系统核验接口，闲聊咨询路由至通用回复节点。

### 3. 并行汇聚（Fan-out / Fan-in）
将同一份数据分发给多个并行的独立节点同时处理，最后由汇聚节点汇总。例如企业资质审核：同一份财报同时触发“税务合规分析”、“诉讼风险排查”和“财务健康度打分”三个并行节点，全部执行完毕后由仲裁规则生成综合授信报告。

### 4. 评估-优化循环（Evaluator-Optimizer Loop）
由“生成节点”和“评估节点”组成双节点闭环。生成节点产出初稿，评估节点依据预定标准打分并给出修改意见；若未达标，则携带修改意见返回生成节点重新润色。在工程实现中，**必须显式设置最大回环次数**（如最多 3 次），避免由于评分阈值过高导致陷入死循环与 Token 耗尽。

## 总结

大模型擅长理解与生成非结构化语言，但软件系统需要确定性契约与稳定的执行预期。AI 工作流的作用就是在这两者之间架起一道缓冲层：它通过任务拆解、状态显式传递、分段校验与受控重试，把大模型偶发的格式破损或抽取偏差限制在局部，保障整笔业务的正常运转。
