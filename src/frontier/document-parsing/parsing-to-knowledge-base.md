文档解析器完成版面分析和文字提取后，输出的通常是带有坐标框的 JSON 碎片、无层级的段落流或粗糙的 HTML/Markdown 文本。如果把这些原始文本直接按固定字数切开并存入向量数据库，问答系统往往会出现以下问题：

1. **检索假阳性**：检索模型召回了高频重复的页眉、免责声明或全是点状虚线的目录页，没有实质答案。
2. **语义断章取义**：一段具体的管理条款被硬生生切成两半，或者缺少上级章节说明，检索模型和大语言模型（LLM）都无法判断这条规定到底属于哪份制度、针对哪个部门。
3. **表格维度丢失**：表格被中间腰斩，后半段切片只有冰冷的数字，缺少表头说明，LLM 只能凭空猜测数据含义。

我们在[《AI 应用中的文件解析是什么？PDF、Word、Markdown、表格分别怎么处理？》](/frontier/document-parsing/what-is-file-parsing.md)与[《PDF 解析为什么容易出错？文本、表格、图片和版面结构如何保留？》](/frontier/document-parsing/pdf-parsing.md)中讨论了如何从物理文件中提取文本与版面元素。本文讨论文档解析完成之后的步骤：如何清洗噪声、建立结构化语法树、执行结构感知切分（Structure-aware Chunking）、注入上下文面包屑，并提取元数据构建多路索引。

## 贯穿示例：一份真实的运维管理规范

为了让后处理流水线每一步的作用更直观，我们以一份名为《数据中心基础设施运维规程（2024版）》的内部文档为例。该文档在解析后，上游输出了如下内容片段：

```text
[页眉: XX科技数据中心运行管理体系 (2024版) | 内部资料] (页面高度占比: 3%)

目录
1.1 总体目标 .................................................... 3
1.2 机房门禁与离岗管理 .......................................... 12

第一章 基础设施安全规范
1.2 机房门禁与离岗管理
第二条：巡检人员擅自脱岗超过30分钟者，初次通报批评；年内累计两次违规，取消机房物理准入权限并扣除当月绩效。

表 1-2：违规等级划分
| 违规类型 | 停留时长上限 | 首次处罚 | 二次处罚 |
| :--- | :--- | :--- | :--- |
| 擅自脱岗 | 30分钟 | 通报批评 | 取消准入 |
| 未刷卡尾随 | 0分钟 | 停权整改 | 辞退通报 |

[页脚: 第 12 页 共 85 页] (页面高度占比: 97%)
```

如果对这段内容做机械处理，比如每 100 字直接切一刀，目录会被切成独立切片，表格会被切掉表头，而“第二条：巡检人员擅自脱岗……”所在的切片中，完全不会出现“数据中心”或“机房门禁”字样。用户提问“数据中心机房脱岗如何处罚？”时，向量模型很可能无法召回这段文字。

## 解析结果标准化：统一抽象语法树（AST）

上游解析器输出的形态往往差异很大：PDF 提取通常输出带有坐标框（Bounding Box）的元素列表，DOCX 解析通常输出段落和样式属性，HTML 则是 DOM 树结构。如果分块与清洗逻辑直接去适配各种格式，代码会高度耦合。

工程上通行的做法是在解析层与分块层之间引入**中间抽象语法树（AST）**。AST 为文档定义了通用的节点类型：

* **Document（根节点）**：承载文档级全局属性（如文档 ID、文件名、总页数、安全等级）。
* **Heading（标题节点）**：带有层级深度标记（Level 1 到 Level 6），记录文档的章节骨架。
* **Paragraph（段落节点）**：承载连续的正文文本，记录所属页码、起止字符位置。
* **Table（表格节点）**：保留结构化的单元格二维矩阵，保存跨行（Rowspan）、跨列（Colspan）、表头（Header）以及表格说明（Caption）。
* **CodeBlock / Formula（代码与公式节点）**：单独标记语言类型或 LaTeX 表达式，不参与普通自然语言的标点切分。

![从异构文档流到统一抽象语法树与线性规范化表示](/images/content-rebuild/2943bd0193ac4174/fig-1.png)

很多系统习惯在解析完成后直接把结果拼装成一篇 Markdown 字符串传给下游。这种方式直观且轻量，但会提前丢失节点在原文档中的物理页码、坐标框和父子引用关系。推荐的做法是在内存中维持 AST 树形对象，在最终完成切分、准备送入 Embedding 模型或大模型上下文之前，再将节点序列化为 Markdown 字符串。

## 数据清洗：降低检索假阳性与特征污染

解析器吐出的文本中往往包含大量无检索价值的内容。如果不加清洗，这些内容不仅浪费上下文窗口，还会破坏相似度计算。

### 1. 跨页页眉与页脚过滤
在贯穿示例中，“`XX科技数据中心运行管理体系 (2024版)`”和“`第 12 页 共 85 页`”出现在每一页。如果任由它们混入正文：
* 在关键词检索（如 BM25）中，“数据中心”、“管理体系”等词频在每个切片中被无差别拉高，破坏词频权重的区分度。
* 在向量检索中，所有切片因为包含了相同的前缀或后缀，在向量空间中都会被拉近，稀释了正文的核心语义差异。

**过滤方式**：
* **坐标区间初筛**：利用版面分析给出的相对坐标，若文本块始终落在页面顶部 5% 或底部 5% 的高度范围内，标记为候选噪声。
* **跨页文本相似度比对**：去除变动的数字（如页码“第 12 页”替换为通配符），比对多页之间候选文本的编辑距离（Levenshtein Distance）或哈希值。若在多页连续出现且相似度高于阈值（例如 0.85），则判定为页眉页脚，从 AST 中剪除。

### 2. 目录页（TOC）识别与剔除
示例中的目录包含了“`1.2 机房门禁与离岗管理 ...... 12`”。当用户询问“机房门禁管理规定”时，目录行与问题的关键词高度吻合，向量表征也极为接近，检索系统极容易以高分把目录切片召回给大模型。但目录切片只有标题和虚线点，缺乏具体规定，最终导致 LLM 生成“文档未提供具体细节”。

**过滤方式**：
在构建 AST 时，检测以“目录”、“Table of Contents”开头的页面，或统计页面中“标题 + 虚线点/连续空格 + 数字”的模式占比。一旦某一页的目录行密度超过 60%，将该页节点从向量检索切分队列中剔除，仅保留作为文档层级的导航元数据。

### 3. 控制字符与无意义空白整理
文档转换过程中常残留不可见字符，需要做确定性替换：
* **Unicode 清理**：移除乱码占位符 `�`、软连字符 `­`、零宽空格 `​` 等非打印控制字符。
* **空白字符归一化**：将连续多个换行符规范为最多两个 `

`，连续空格合并为单个空格。对于代码块（CodeBlock），必须跳过空格归一化，保留其代码缩进。

## 结构感知分块（Structure-aware Chunking）

传统 RAG 常用**固定长度切分（Fixed-size Chunking）**：比如每 300 字符切一段，重叠 30 字符。这种切分不考虑语义边界，存在明显缺陷：

1. **语句截断**：切分点可能落在专有名词或因果关联句之间。例如将“年化收益率不超过 3.65%”截断为“年化收益率不超过 3.”与“65%”两个碎片。
2. **表格破坏**：直接在 Markdown 表格中间横切一刀，下半部分切片没有表头，单元格数据彻底丧失含义。
3. **标题孤立**：切片与其所属的大章节完全割裂，形成语义孤岛。

### 基于 AST 的自顶向下切分机制
结构感知分块以 AST 为基准，遵循“优先大纲划分，叶子节点退化到标点”的策略：

![固定截断与结构感知分块的切分对比](/images/content-rebuild/2943bd0193ac4174/fig-3.png)

切分状态机主要包含四个步骤：

1. **大纲树深度优先遍历**：从一级标题（H1）向下递归检查。如果一个章节（包含其下属的所有小节和段落）的 Token 总量未超过单块上限（如 512 Tokens），则将该章节整合成一个完整 Chunk，不进行碎切。
2. **超限分支下钻**：若该章节内容总长度超过上限，则保留当前标题作为路径上下文，下钻到二级标题（H2）、三级标题（H3）继续划分。
3. **叶子段落贪心聚合与断句**：当到达没有子标题的正文段落序列时，按自然段累加文本。若单一段落自身超出 Token 上限，再在段落内部按照标点符号优先级（句号 `。`、问号 `？`、感叹号 `！`、分号 `；`）进行二级断句截断。
4. **表格节点原子保护**：表格默认视为最小语义单元。如果中小型表格略微超出 Token 阈值（如超出 15% 以内），允许弹性上浮单块上限；如果超大表格必须跨块拆分，必须在每一个拆分出的子切片首部强制补齐原始表头和分隔符行，保证每一行数据都能与列名对应。

## 语义孤立修补：面包屑路径与父子切块

即使完成了结构感知分块，如果单独提取叶子段落，依然存在**语义孤立**问题。

在贯穿示例中，切分出的正文是：
> “第二条：巡检人员擅自脱岗超过30分钟者，初次通报批评；年内累计两次违规，取消机房物理准入权限并扣除当月绩效。”

这段文字虽然语句完整，但文本中没有“数据中心”或“机房门禁”。如果用户提问“数据中心机房脱岗有什么后果？”，单纯计算正文与问题的向量相似度，距离会比较远。

### 面包屑路径注入（Breadcrumb Injection）
解决此问题最简单且计算成本最低的方案，是在将 Chunk 送入向量模型前，把该节点在 AST 中的完整标题路径以特定格式拼接到 Chunk 首部：

```text
[规章: 数据中心基础设施运维规程(2024版) > 第一章 基础设施安全规范 > 1.2 机房门禁与离岗管理]
第二条：巡检人员擅自脱岗超过30分钟者，初次通报批评；年内累计两次违规，取消机房物理准入权限并扣除当月绩效。
```

![面包屑标题路径注入与父子块召回机制](/images/content-rebuild/2943bd0193ac4174/fig-4.png)

注入面包屑路径能带来两项直接收益：
* **向量特征对齐**：章节路径中的“数据中心”、“基础设施安全”、“机房门禁”等词汇直接参与 Embedding 计算，短文本切片在向量空间中会被拉向主题聚类中心，显著提升特定领域下的问答召回率。
* **LLM 理解防漂移**：当检索结果返回给 LLM 时，模型可以清晰看到这段条款归属于哪个规范的哪一节，避免把不同规程中的相似罚则混淆。

### 滑动窗口与父子分块（Parent-Child Chunking）
相邻切片之间通常会设置 10% 到 15% 的重叠字符（Overlap），以防切分边界处的代词和转折关系被切断。但重叠不能无限制放大：过大的重叠会导致向量数据库体积大幅增加，并且容易在检索前几名中召回内容几乎重复的切片。

对于需要兼顾“高精度检索”与“完整语境生成”的场景，工程上常采用**父子分块（Parent-Child Chunking）**方案：
1. **切分双层切片**：父切片（Parent Chunk）保持较大篇幅（如 1000~1500 Tokens），保留完整段落和上下文关系；子切片（Child Chunk）保持较小篇幅（如 200~300 Tokens），专注于表达单一语义点。
2. **索引与召回分离**：系统仅对子切片计算 Embedding 并建立索引，保证向量检索时能够敏锐击中细节。一旦某个子切片被检索召回，系统不把子切片直接给大模型，而是通过其保存的 `parent_id` 找到对应的父切片，将更大更完整的上下文喂给大模型。

## 元数据提取：确定性规则与模型标注

知识库系统不能仅靠纯文本向量比对。在实际业务中，用户提问往往带有属性约束，例如“查询**2024年**关于**机房准入**的处罚”。如果在检索时只用向量算相似度，极容易召回 2022 年或 2023 年的历史条款。因此，入库流水线必须为每个切片挂载结构化元数据。

元数据按粒度分为**文档级**与**切片级**：

| 元数据字段名 | 粒度 | 提取方式 | 典型用途与作用 |
| :--- | :--- | :--- | :--- |
| `doc_id` / `source_url` | 文档级 | 任务上下文 / 规则注入 | 原文档溯源、文档详情与下载跳转 |
| `tenant_id` / `acl_level` | 文档级 | 权限系统鉴权传入 | 多租户隔离、用户阅读权限硬过滤 |
| `publish_date` | 文档级 | 属性解析 / 正则抽取 | 时间区间过滤（如筛选最新生效条例） |
| `breadcrumb` | 切片级 | AST 树深度遍历生成 | 章节层级溯源、向量表征语义增强 |
| `page_num` | 切片级 | 版面解析结果关联 | 前端原文高亮跳转与引用角标标注 |
| `content_type` | 切片级 | AST 节点属性（text / table / code） | Prompt 渲染分支选择、不同模态排序加权 |
| `keywords` | 切片级 | TF-IDF / 快速小模型抽取 | 倒排关键词索引、BM25 混合检索补强 |

![规则引擎与小模型双轨元数据富化架构](/images/content-rebuild/2943bd0193ac4174/fig-5.png)

**抽取工程的分工原则**：
* **规则引擎优先**：文件路径、创建时间、标题层级、页码映射、固定正则表达式（如日期、条款编号），必须由确定性代码在内存中以毫秒级完成，不引入模型推理开销。
* **轻量模型异步抽取**：实体识别（NER）、主题打标、单句摘要等开放式属性，可采用轻量小模型处理。如果需要调用大模型处理摘要，应采用离线异步任务或批量流水线执行，不要将其放在同步上传的主路径上阻塞整个系统。相关存储配合可参考[《什么是向量数据库？在基于大模型的应用开发中，向量数据库主要解决什么问题？》](/interview/rag-interview/vector-database.md)。

## 结构感知分块与面包屑注入实现

以下 Python 示例演示如何基于简化的大纲树结构，执行带有面包屑路径注入的递归切分。为方便读者直接运行测试，本代码使用字符计数模拟 Token 预算（在真实生产环境中，应使用目标嵌入模型对应的 Tokenizer 计算长度）：

```python
import re
from typing import List, Dict, Any

class OutlineNode:
    def __init__(self, title: str, level: int, content: str = ""):
        self.title = title
        self.level = level
        self.content = content
        self.children: List['OutlineNode'] = []

def build_chunks_with_breadcrumbs(
    node: OutlineNode,
    current_path: List[str],
    max_chars: int = 120,
    overlap: int = 15
) -> List[Dict[str, Any]]:
    """
    自顶向下递归切分大纲树，并将完整大纲路径注入每个 Chunk 首部。
    """
    chunks = []
    new_path = current_path + [node.title] if node.title else current_path
    breadcrumb_str = " > ".join(new_path)
    
    # 1. 处理当前节点所包含的正文内容
    text = node.content.strip()
    if text:
        prefix = f"[{breadcrumb_str}]\n" if breadcrumb_str else ""
        available_len = max_chars - len(prefix)
        
        # 若当前文本长度超过单块预算，进行句子级切分
        if len(text) > available_len:
            # 按照常见中文标点切分成带标点的句子列表
            raw_sentences = re.split(r'([。！？；\n])', text)
            sentences = []
            for i in range(0, len(raw_sentences) - 1, 2):
                sentences.append(raw_sentences[i] + raw_sentences[i+1])
            if len(raw_sentences) % 2 == 1 and raw_sentences[-1]:
                sentences.append(raw_sentences[-1])
            
            current_body = ""
            for s in sentences:
                if not s.strip():
                    continue
                # 当前累积长度若超出预算，先封包输出前一个 Chunk
                if len(current_body) + len(s) > available_len and current_body:
                    full_text = prefix + current_body
                    chunks.append({
                        "text": full_text,
                        "breadcrumb": breadcrumb_str,
                        "char_count": len(full_text)
                    })
                    # 滑动重叠处理：截取上一块尾部字符保留在下一块头部
                    tail = current_body[-overlap:] if len(current_body) > overlap else current_body
                    current_body = tail + s
                else:
                    current_body += s
            
            if current_body.strip():
                full_text = prefix + current_body
                chunks.append({
                    "text": full_text,
                    "breadcrumb": breadcrumb_str,
                    "char_count": len(full_text)
                })
        else:
            # 未超预算，直接封装为单块
            full_text = prefix + text
            chunks.append({
                "text": full_text,
                "breadcrumb": breadcrumb_str,
                "char_count": len(full_text)
            })
            
    # 2. 递归遍历子节点
    for child in node.children:
        chunks.extend(build_chunks_with_breadcrumbs(child, new_path, max_chars, overlap))
        
    return chunks

# --- 运行验证 ---
if __name__ == "__main__":
    # 构造示例大纲 AST
    root = OutlineNode(title="数据中心运维规程", level=1)
    sec1 = OutlineNode(title="基础设施安全规范", level=2)
    sec1_2 = OutlineNode(
        title="机房门禁与离岗管理",
        level=3,
```

## 入库校验与检索质量测试

切分和元数据准备完成后，不能直接盲目地向生产数据库批量写入，需要设置校验与离线质量验证环节。

![入库守门与索引可观测性监控看板](/images/content-rebuild/2943bd0193ac4174/fig-6.png)

### 1. 向量生成与写入校验
* **超长与过短熔断**：统计每个切片的文本长度与 Token 数量。低于极小阈值（如正文少于 15 个字符）的片段，通常是清洗残留的标点或空标题，应当直接丢弃并记录告警日志；若切片超出向量模型的最大输入 Token 上限，切片必须阻断写入，避免模型静默截断后半部分导致索引失真。
* **向量数值合法性校验**：批量调用 Embedding 模型后，入库程序应检查返回的数组维度是否与数据库 Schema 严格一致，并扫描是否存在 `NaN`、`Inf` 或全零向量。发现异常切片需重试或隔离至死信队列。
* **主键幂等设计**：根据“文档 ID + 文档版本号 + 切块序号”或者对“切块标准化文本 + 元数据”进行 SHA-256 哈希计算，生成唯一 Chunk ID。文档重新上传或版本更新时，根据主键执行 Upsert（更新插入），防止旧版本的冗余切片残留导致检索结果重复污染。

### 2. 离线检索质量验证（Golden Test Set）
评估切分和清洗参数好坏的最有效方法是维护一套**标准黄金测试集（Golden Test Set）**：
* 整理 50 到 100 个具有业务代表性的用户真实问题，并标注文档中能够准确回答这些问题的标准切片（Ground Truth Chunks）。
* 每当调整分块大小、重叠窗口比例或清洗规则时，在预发环境重新跑一遍切分与索引，然后自动化执行测试集。
* 计算检索评估指标：
  * **Hit@K（前 K 项召回率）**：标准答案切片是否出现在检索结果的前 K 个切片中。
  * **MRR（Mean Reciprocal Rank，平均倒数排名）**：标准答案切片在检索结果中排名的倒数均值。若标准切片排在第 1 名，倒数为 1；排在第 2 名，倒数为 0.5。MRR 越接近 1，说明核心上下文排在越靠前的位置。

如果调整分块策略后 Hit@5 或 MRR 发生明显下降，说明当前的切分边界破坏了核心语义，或者引入了过多噪声干扰，应及时阻断变更发布。
