在检索增强生成（RAG）系统中，大模型回答质量的前提是输入上下文必须准确。如果文档解析阶段将双栏排版误拼成通栏，或者把表格内容拆解成无序字符，无论下游使用多优秀的向量模型，检索出来的片段都带有逻辑缺陷。

以一份《服务器运维安全规范》PDF 为例：页面上方是分级标题，下方是双栏文字，中间嵌有一张端口开放策略表。若解析器只按底层绘制指令的先后顺序提取字符，左栏的第一行会与右栏的第一行强行拼在一起，表格中的端口号“3306”、协议“TCP”与来源“内网”也会丢失行列对齐关系。当用户提问“数据库默认端口允许哪些来源访问”时，检索阶段只能提供错乱的文本块，模型推理必然出错。

文档解析的核心任务，就是**识别不同格式文件的物理存储方式，将其还原为符合人类阅读顺序、保留标题层级与表格拓扑的结构化数据，并切分成适合向量索引的语义切块**。

## 专题学习路径与核心模块

围绕文档解析与知识库入库，本专题从格式原理、排版还原到工程落地分为三个递进阶段：

### 1. 认知建立：不同文件格式的物理存储与解析差异
文档格式决定了提取结构的难易程度：
* **Word（`.docx`）**：本质是一个基于 OpenXML 标准的压缩包，内部以树状 XML 节点组织内容（如段落 `<w:p>`、表格 `<w:tbl>`）。解析的关键是遍历 XML 标签树并提取样式大纲，结构天然完整。
* **Markdown**：纯文本存储，使用明确的标记符号表达标题层级（`#`）、列表和表格，可以直接转换为抽象语法树（AST）进行精准切分。
* **表格文件（`.xlsx` / `.csv`）**：以行列网格元数据存储，行与列具有强字段约束。解析难点主要在于处理多级复合表头以及展开合并单元格。
* **PDF**：设计目标是打印与屏幕精确渲染，底层记录的是页面绝对坐标系上的绘制指令（如在坐标 `(x, y)` 处绘制字符串、在两点间画线），完全丢失了段落、分栏和表格的逻辑归属。

更深入的格式解析与技术选型见：[/frontier/document-parsing/what-is-file-parsing.md](/frontier/document-parsing/what-is-file-parsing.md)

---

### 2. 还原机制：PDF 绘制指令流、几何排序与视觉版面分析
PDF 是文档处理中挑战最大的载体。要准确还原阅读流，需要结合规则计算与视觉模型：
* **文字块提取与几何重排**：页面中的文字块存储顺序取决于生成工具的写入流，并不等于人类阅读顺序。解析器需要先获取每个字符或单词的坐标框（Bounding Box：`[x0, y0, x1, y1]`），利用投影重叠算法判定分栏边界，再在每一栏内自上而下、行内自左向右完成重排。
* **表格拓扑还原**：对于带边框的表格，解析器通过检测矢量画线指令的交叉点来定位单元格边界；对于无边框表格，则依赖文本块的横纵对齐规则，或利用深度学习表格识别模型预测行列分割线。
* **视觉版面分析（Layout Analysis）**：遇到图文混排、浮动插图或扫描件时，纯几何规则容易把页眉、页脚和图注混入正文。此时需要引入基于计算机视觉的目标检测模型（如 YOLO 变体或 LayoutLM 系列），先将页面划分为标题、正文段落、表格、图片和页眉页脚等不同功能区域，再对各个区域分别应用特定的提取逻辑。

### 3. 工程落地：统一中间表示、语义切块与元数据入库
解析出来的文本块不能直接写入向量库，需要通过统一的数据管道完成清洗与索引：
* **统一中间表示（Intermediate Representation, IR）**：下游切块和向量化模块不应直接耦合底层各类解析库的私有输出。无论输入是 PDF、Word 还是网页，解析引擎都应统一输出结构一致的抽象语法树或 JSON 对象。
* **层级继承与语义分块**：避免机械地按固定字符长度暴力硬切。应依据标题层级，将章节路径（如“1. 系统网络隔离规范 > 1.2 端口策略”）以面包屑元数据的形式注入每一个叶子切块中；对于表格，优先按行序列化并保留完整表头，避免单元格离开表格后失去上下文语义。
* **质检与幂等写入**：在切块进入向量数据库前，执行字符长度过滤、乱码检测以及哈希去重；入库操作基于“文档 ID + 切块 ID”执行幂等覆盖（Upsert），防止重复入库导致数据膨胀。

## 统一中间表示（IR）最小规范示例

为确保解析模块与下游切块模块解耦，生产系统中建议定义明确的 JSON 契约。以下是一个标准的最小化输出示例：

```json
{
  "doc_id": "doc_sec_spec_001",
  "page_count": 8,
  "blocks": [
    {
      "block_id": "blk_001",
      "page_idx": 0,
      "type": "header",
      "level": 1,
      "text": "1. 系统网络隔离规范",
      "bbox": [72.0, 100.5, 400.0, 120.5]
    },
    {
      "block_id": "blk_002",
      "page_idx": 0,
      "type": "paragraph",
      "text": "核心业务系统必须部署在私有网络隔离区，严禁直接绑定公网 IP。",
      "bbox": [72.0, 130.0, 520.0, 160.0]
    },
    {
      "block_id": "blk_003",
      "page_idx": 0,
      "type": "table",
      "rows": [
        ["端口号", "协议", "访问方向", "允许来源"],
        ["3306", "TCP", "入站", "应用服务器子网"]
      ],
      "bbox": [72.0, 180.0, 520.0, 260.0]
    }
  ]
}
```

**使用说明**：下游的分块器只需检查 `type` 与 `level`。遇到 `header` 则刷新上下文层级路径，遇到 `table` 则按行拼接表头，遇到 `paragraph` 则累加字符并检查窗口容量。下游逻辑完全无需感知数据最初来自 PDF 坐标聚类还是 Word 的 XML 遍历。

## 生产部署架构：异步队列与双轨降级

文档解析涉及密集的 CPU 计算（排版渲染）与 GPU 推理（版面分析与 OCR）。在高并发请求下，如果使用同步 HTTP 接口处理文件，网关会因长时间等待而超时，且极易拖垮主服务。

![生产级解析流水线的双轨路由与降级熔断机制](/images/content-rebuild/9da5d3cb5bee6c2f/fig-3.png)

健壮的解析系统通常采用**异步队列与双轨调度**架构：
1. **主轨（轻量规则引擎）**：用户上传文件到对象存储后，服务端将任务推入消息队列（如 Kafka、RabbitMQ）。轻量 Worker 优先使用基于规则的库（如 PyMuPDF、python-docx）提取原生文本与矢量几何信息，单页处理时间一般在几十毫秒到几百毫秒之间。
2. **门控检测与旁路降级**：轻量解析完成后，系统执行质量检查。若发现页面无文本（全图扫描件）、乱码字符比例高于阈值，或者版面高度复杂触发了解析异常，任务将自动转入旁路队列，调度配备 GPU 的深度版面模型或多模态 OCR 集群进行重新识别。
3. **死信隔离与重试控制**：如果深度解析依然失败（如文件密码损坏、格式畸变），Worker 在达到设定的最大重试次数（如 2 次）后停止重试，直接将任务移入死信队列并记录错误上下文，向外层返回明确的状态码，避免无限重试耗尽计算集群。

通过统一的中间数据格式和双轨调度机制，系统既能以低成本快速处理绝大多数原生结构文档，又能在遇到复杂文件与扫描件时平滑降级，为后续切块与向量索引提供稳定的数据保障。关于分块后的向量表征与检索原理，可进一步查阅专题：[Embedding 基础](/fundamentals/embedding/README.md) 与 [AI 工程架构](/architecture/README.md)。
