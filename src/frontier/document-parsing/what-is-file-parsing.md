在搭建检索增强生成（RAG）或文档智能体时，很多开发者容易把精力全放在向量检索、重排或提示词上。但如果进入检索库的文字本身顺序颠倒、表格行列错位、标题层级丢失，下游的模型推理就很容易产生幻觉或直接检索失败。

大语言模型（LLM）处理的是一维线性 Token 序列。而人类日常使用的文档——无论是包含多级样式的 Word、带有合并单元格的 Excel，还是基于打印坐标签发的 PDF——底层的数据组织形式差别极大。**文件解析的核心任务，是把这些格式不同、排版各异的文档，还原成既保留大纲层级与表格对应关系，又适合大模型阅读的结构化文本（通常为 Markdown 或 JSON）。**

为了看清不同格式的差异，我们用一份典型的《2024年季度运营报告》作为贯穿示例。这份文档包含：
1. **标题层级**：一级标题“一、业务概况”与二级标题“1. 核心指标”；
2. **多行合并表格**：表头第一行跨两列合并为“2024年”，第二行细分为“Q1”和“Q2”，下方对应业务线与数值；
3. **排版正文**：包含左右双栏说明与局部加粗样式。

面对同一份内容，不同格式在底层是如何存储的？解析器又该如何处理？

## 文件解析要做什么：从字节流到结构化语法树

在操作系统层面，文档只是二进制文件流。单纯的“文本提取”（如调用系统命令抽取一段无格式纯文字）与“文档解析”有明确的边界：

1. **保留大纲树状层级**：文档由“一级标题 -> 二级标题 -> 正文段落 -> 列表项”构成。如果丢失层级，后续的文本分块（Chunking）只能按照固定字数强行切断，把标题与正文切分到两个完全不同的数据块中。
2. **保留表格二维对应关系**：数值 `1450` 只有挂在“软件服务”这一行、“2024年 Q2”这一列下才有业务含义。如果丢失行列关联，它就会退化为一个孤立无意义的数字。
3. **保留内嵌元素标记**：超链接、代码块、行内公式与图片说明，需要在转换过程中标注出来，方便后续分支处理。

```
[原始文件字节流] 
      │
      ▼
[格式解包 / 页面渲染] (ZIP 解包、XML 遍历、PDF 操作符扫描、图像光栅化)
      │
      ▼
[逻辑结构语法树 AST] (Heading 1/2, Paragraph, Table[row, col], Image)
      │
      ▼
[线性上下文序列] (标准 Markdown、结构化 JSON、附带层级路径的文本块)
```

![文件解析全流程：从底层字节流、逻辑语法树到线性上下文的转换关系](/images/content-rebuild/2fc75effaf647cd9/fig-1.png)

解析引擎先将底层数据还原为包含逻辑关系的抽象语法树（AST），再线性化为大模型便于理解的文本序列。

## 纯文本与 Markdown：显式标记带来的低损耗解析

在所有文本格式中，纯文本（TXT）与 Markdown 是最直接的输入形式，但二者在结构保留能力上有很大差距。

### 纯文本的隐式排版缺陷

纯文本没有元数据。排版逻辑完全靠人为习惯，例如开头缩进四个空格、空两行换章节、或者手动输入数字 `1. `。程序处理纯文本时，只能依赖正则表达式去猜测哪一行是标题。一旦正文中出现“1. 这是个补充说明”，就很容易被误判为新的小节，造成大纲切分错误。

### Markdown 的语法树结构

Markdown 之所以广泛用于大模型管道，核心在于它的标记是确定性的：

* **明确的语法规则与低解析开销**：Markdown 采用 `#`、`-`、`|` 等轻量字符标明层级。成熟的 CommonMark 解析库可以在极低 CPU 开销下直接生成文档结构树。
* **符号冗余少**：相比 HTML 成对闭合的 `<h1>...</h1>` 或 `<table><tr><td>...</td></tr></table>`，Markdown 语法标记占用字符少，能节约上下文窗口。

以示例报告的片段为例：

```markdown
# 一、业务概况

## 1. 核心指标
本季度各线业务交付正常。

* 核心交付线：
  * 软件服务
  * 硬件交付
```

解析库在内存中会将其映射为标准的树结构：

```
Root
 └── Heading (level=1, text="一、业务概况")
      └── Heading (level=2, text="1. 核心指标")
           ├── Paragraph (text="本季度各线业务交付正常。")
           └── List (ordered=false)
                └── ListItem (text="核心交付线：")
                     └── List (ordered=false)
                          ├── ListItem (text="软件服务")
                          └── ListItem (text="硬件交付")
```

![纯文本与 Markdown 在结构化信息保留上的对比](/images/content-rebuild/2fc75effaf647cd9/fig-2.png)

### 解析异常处理

处理 Markdown 并非没有特殊情况：
1. **夹杂内联 HTML 标签**：从网页复制转出的 Markdown 常混杂 `<span style="...">` 标签。解析管线需要配置过滤规则，移除无语义的样式属性，只保留纯文本内容。
2. **不规范表格退化**：原生 Markdown 表格只支持标准单层行列。如果单元格内含有未经转义的换行符或缺少分隔竖线，解析库常会将其直接回退降级为普通正文段落。

## Word（DOCX）：基于 OpenXML 树的样式提取与回退机制

现代 `.docx` 文件不是单一的二进制文件，而是遵循 OpenXML 标准的 ZIP 压缩包。

如果将一个 `.docx` 文件后缀改为 `.zip` 并解压，可以看到清晰的目录结构：

```
my_document/
├── [Content_Types].xml
├── word/
│   ├── document.xml          <-- 正文内容与段落节点流
│   ├── styles.xml            <-- 预设样式定义（如 Heading 1, Normal 等）
│   ├── numbering.xml         <-- 列表项编号与缩进
│   ├── _rels/
│   │   └── document.xml.rels <-- 超链接与外部引用关系
│   └── media/                <-- 内嵌的图片与多媒体文件
```

<ReadMoreLock />

### 样式提取机制

在 `word/document.xml` 中，文本被划分为段落（`<w:p>`）、文本运行块（`<w:r>`）以及字符实体（`<w:t>`）：

```xml
<w:p>
  <w:pPr>
    <w:pStyle w:val="Heading1"/>
  </w:pPr>
  <w:r>
    <w:t>一、业务概况</w:t>
  </w:r>
</w:p>
```

提取器在读取时，直接检查段落属性 `<w:pPr>` 下的 `<w:pStyle>`。如果其引用了 `Heading1`，程序即可明确将其识别为一级标题，并映射为 Markdown 的 `# 一、业务概况`。表格则存储在 `<w:tbl>` 下，由行 `<w:tr>` 和单元格 `<w:tc>` 逐层嵌套。

![DOCX 文件的 OpenXML 内部解包与样式提取机制](/images/content-rebuild/2fc75effaf647cd9/fig-3.png)

### 现实中的非规范排版与回退推断

上述机制顺利运行的前提是：**文档撰写者规范使用了样式库**。

在实际业务中，许多用户排版时不点“标题 1”，而是选中一段普通文本，手动将字号设为“22pt”并点击“加粗”。在底层 XML 中，这段内容并没有标题属性：

```xml
<w:p>
  <w:r>
    <w:rPr>
      <w:b/>
      <w:sz w:val="44"/> <!-- 44半磅 = 22pt -->
    </w:rPr>
    <w:t>一、业务概况</w:t>
  </w:r>
</w:p>
```

若解析器仅按 `<w:pStyle>` 抓取，该段落就会被误当成普通正文，导致大纲断层。成熟的 Word 解析管线通常采用双层逻辑：

1. **优先样式表匹配**：读取 `styles.xml`，匹配标准标题继承关系；
2. **字号启发式回退**：当段落未声明预设样式时，收集全文字号与加粗状态，统计字号分布。若某独立段落字号显著大于正文均值（例如排在全文字号前 5% 且带有加粗），则推断并降级标记为对应级别的标题。

## 表格文件（Excel/CSV）：行列对齐、合并单元格与序列化

处理表格文件时，最大的挑战是维度的变化：表格依赖行与列的二维空间交叉定位，而大模型接收的是从左到右单向展开的一维文本流。

### CSV 的特性与局限

CSV 是纯文本矩阵，用换行区分行，用逗号区分列。它的优势是格式简单、解析极快、几乎不占额外内存。

但 CSV 无法保存复杂元数据：
* 无法表达多级表头与单元格合并；
* 无法在同一个文件中直接表达多个工作表（Sheet）；
* 单元格内容一旦包含逗号或换行符，如果转义符号缺失或不统一，整行数据就会发生错位。

### Excel（XLSX）的多行表头与合并单元格问题

以贯穿示例中的多级财务表头为例：

| 业务线 | 2024年（合并跨 2 列） | | 
| :--- | :--- | :--- |
| | **Q1** | **Q2** |
| 软件服务 | 1200 | 1450 |
| 硬件交付 | 800 | 950 |

如果解析器机械地将合并单元格转成纯文本，第二列保留“2024年”，第三列留空，转出后的 Markdown 会变成：

```markdown
| 业务线 | 2024年 |  |
|  | Q1 | Q2 |
| 软件服务 | 1200 | 1450 |
| 硬件交付 | 800 | 950 |
```

在模型按行阅读时，数值 `1450` 对应的表头第一行是空白，第二行是 `Q2`。模型极易丢失“2024年”的上下文，进而产生“哪个季度的 1450”这种事实混淆。

![多级表头与合并单元格在展平为线性文本时的转换机制](/images/content-rebuild/2fc75effaf647cd9/fig-4.png)

### 表格序列化的工程处理

为了让表格在一维化后依然语义清晰，通常需要进行规范化处理：

1. **前向填充与多级表头拼接**：读取工作表中的 `<mergeCell>` 标签，把合并范围内的值向右、向下广播复制。随后将多层表头自上而下拼接成复合字段名，例如把第一列第二层拼成 `业务线`，后两列分别拼成 `2024年_Q1`、`2024年_Q2`。
2. **根据任务选择序列化输出形式**：
   * **Markdown 表格**：适合表头单层、数据规整的中小型表格，文字占用较少；
   * **结构化 JSON 列表**：适合需要单行切分向量化的场景。将每一行数据转换为一个独立的 JSON 字典，列名作为 Key 重复带入每行。虽然增加了 Token 数量，但保证了单行被切分独立存放时仍具备完整上下文。

```json
[
  {"业务线": "软件服务", "2024年_Q1": 1200, "2024年_Q2": 1450},
  {"业务线": "硬件交付", "2024年_Q1": 800, "2024年_Q2": 950}
]
```

## PDF 格式：为什么排版型文档最难解析？

在所有常见文档中，PDF 往往是信息丢失和顺序错乱最严重的文件类型。这源于它的设计初衷。

### 打印指令集与阅读逻辑流的差异

Word 与 Markdown 的设计是为了**编辑与结构表达**；而 PDF 脱胎于打印页面描述语言 PostScript，目标是在任何屏幕和打印设备上**保证视觉像素完全一致**。它存储的是物理画笔的坐标与绘制指令。

查看一段真实的 PDF 底层内容指令流：

```ps
BT
/F1 12.0000 Tf                           % 指定字体与字号 12pt
1.0000 0 0 1.0000 72.0000 712.0000 Tm   % 移动画笔到物理坐标点 (72, 712)
[ (一、业务概况) ] TJ                     % 绘制文字片段
ET
BT
1.0000 0 0 1.0000 300.0000 712.0000 Tm  % 画笔跳至 (300, 712)
(1. 核心指标) Tj
ET
```

![PDF 物理绘制坐标流与人类阅读流的脱节机理示意图](/images/content-rebuild/2fc75effaf647cd9/fig-5.png)

这段指令暴露出 PDF 解析的核心难点：
* **没有原生的“段落”与“换行”**：换行在底层只是画笔的 Y 坐标向下平移；
* **没有固定的“空格字符”**：字与字之间的距离，很多时候只是画笔坐标的小幅度位移；
* **存储顺序不等于阅读顺序**：排版软件生成 PDF 时，可能先画页脚，再画右侧小栏，最后画正文。如果直接按文件流读取字符，提取出的内容完全可能是错乱的；
* **双栏混排错位**：如果报告正文采用左右两栏排版，两栏的 Y 坐标重叠。基于简单坐标由上至下抓取文字的程序，会把左栏的第一行和右栏的第一行拼在同一句话里，导致语义彻底混乱。

关于 PDF 底层绘制流与复杂版面重构的深度数学与坐标推导，在后续专题文章 [/frontier/document-parsing/pdf-parsing.md](/frontier/document-parsing/pdf-parsing.md) 中有进一步展开。

## 工程选型：规则提取、几何版面分析与多模态模型

面对不同的格式与场景，没有单一方案能同时满足速度、成本与极高排版复杂度的要求。当前工程实践主要分为三类路径：

![规则提取、几何重构与视觉多模态大模型的选型权衡雷达图](/images/content-rebuild/2fc75effaf647cd9/fig-6.png)

### 三类技术路径对比

| 方案类型 | 核心技术与代表工具 | 硬件资源要求 | 单页平均延时 | 适用场景与优势 | 局限性与失败场景 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **1. 纯规则提取** | `pypdf`, `pdfplumber`, `python-docx`, `openpyxl` | 纯 CPU，内存开销小 | 5ms ~ 50ms | 成本低、解析极快；适合标准 Markdown、原生 DOCX 及规整单栏 PDF | 遇到双栏混排、扫描件图片、无框线表格时无法正确还原 |
| **2. 几何版面重构** | 版面检测模型 (YOLO / LayoutLM) + OCR + 坐标几何排序 | CPU / 中低端推理 GPU | 200ms ~ 1500ms | 能根据视觉包围框重构双栏阅读顺序，支持带线表格与扫描件识别 | 流水线较长：版面检测框如果出现切分偏差，错误会直接带入 OCR 与文本组合中 |
| **3. 端到端多模态模型 (VLM)** | 多模态大模型 (GPT-4o, Claude 3.5 Sonnet) 或垂直文档模型 | 高端推理 GPU 或商用 API | 1000ms ~ 5000ms+ | 泛化能力强，对印章覆盖、倾斜手写、复杂图文混排容忍度高 | 算力与 Token 成本高昂；在极长文档解析时仍需防范细小数字生成错误 |

### 实用分流流水线设计

在生产环境中，推荐根据输入文件类型和特征构建分流管道：

1. **格式首层分流**：
   * `.md`、`.txt`：执行轻量语法树清洗与规范化，直接进入文本块切分；
   * `.docx`：优先通过 OpenXML 读取段落样式，未标样式的文本结合字号直方图推断大纲；
   * `.xlsx`、`.csv`：识别合并单元格执行前向填充，多级表头展开拼接为复合键，按行序列化为自包含 JSON；
2. **PDF 二级分流**：
   * 首先检测是否存在原生文字层。如果是带文字层且文字分布为标准单栏，走规则流式提取；
   * 如果检测到多栏布局、表格网格密集，路由至几何版面重构工具；
   * 如果为无文字层的扫描图片，或者包含手写体、复杂公式图表，再分流至 OCR 引擎或多模态大模型处理。

完成统一格式解析后，结构化文本如何切分分块并灌入下游系统，可进一步阅读专题文章 [/frontier/document-parsing/parsing-to-knowledge-base.md](/frontier/document-parsing/parsing-to-knowledge-base.md)。如需查阅关于 RAG 多格式解析的高频面试口述要点，可参考面试专题 [/interview/rag-interview/rag-multiformat-parsing.md](/interview/rag-interview/rag-multiformat-parsing.md)。
