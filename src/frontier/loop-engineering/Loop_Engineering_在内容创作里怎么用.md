在[/frontier/loop-engineering/最简单的_Loop_写代码_跑测试_自动修复.md](/frontier/loop-engineering/最简单的_Loop_写代码_跑测试_自动修复.md)中，循环能够自动运行，核心在于代码拥有确定性的判定环境：编译器会返回明确的退出码，测试用例会直接给出断言结果（通过或失败）。一旦断言失败，测试框架还会给出调用栈和行号，模型只要针对报错信息修改即可。

但在撰写技术文档、行业分析等长文内容时，整个环境变了：**文本没有编译器，也没有确定性的测试断言**。如果只是把草稿重新塞回模型并提示“请继续优化”，系统往往会陷入两种困境：要么盲目赞美草稿而看不出毛病，要么每次修改都推翻重写，导致改好了后半段却弄丢了前半段。本文将通过撰写一篇“Redis 持久化机制解析”的技术博客作为贯穿例子，说明如何在缺乏客观编译器的情况下，设计分层校验、审校分离与差分修补的反馈循环。

## 为什么简单的“反复修改”在写作中容易失控？

要在自然语言创作中建立自动化循环，首先需要理解为什么普通的单模型多次迭代很难收敛。

### 1. 评价标准是多维权衡，而非二元判定
代码语法是否正确只有对或错两种状态。但评价一篇文章的好坏，往往涉及多个互相冲突的维度。例如，展开更多的底层源码细节能提高严谨度，却会拉长篇幅并增加初学者的阅读负担；精简文字能提升阅读速度，却可能漏掉关键前提。如果只给出一句模糊的指令（如“请审查并优化上文”），模型缺乏固定的评估参照系，每一轮修改的标准都会随采样随机性发生偏移。

### 2. 同一上下文的自我迎合与审查盲区
让生成草稿的模型在同一个会话里审查自己的文字，通常很难获得有效的修改意见。这主要受两个机制影响：
* **自回归上下文偏置**：模型生成草稿时，前文的 Token 已经构成了当前推理的主干输入。在自注意力计算中，模型顺着自己刚刚生成的推导逻辑继续生成时，天然倾向于认为当前表述合理，难以跳出既定语境发现遗漏。
* **顺从训练倾向（Sycophancy）**：大语言模型在微调阶段习得了顺应上下文语气与既定事实的模式。当被要求“评价上文”时，若没有严格的反向设问或独立角色约束，它往往倾向于给出温和赞顺的反馈（例如“结构清晰、阐述完整”），从而漏过事实模糊或逻辑跳跃的问题。

### 3. 全文重写引发的内容漂移
在缺乏修改范围限制时，全篇重写极易发生连锁反应。例如在“Redis 持久化”的例子中：第一轮循环修正了 AOF 章节的技术名词，第二轮为了配合该处的行文语气又改写了开篇引言，第三轮又因引言风格变化改动了结尾总结。几轮下来，消耗了大量 Token，但整篇文章的结构却持续漂移，最终产物甚至不如初始草稿稳定。

## 第一层防线：用低成本程序拦截硬性规格错误

面对弱确定性任务，首要的工程原则是：**不要把所有校验都交给大模型。凡是能用规则代码检查的，坚决不用大模型推理。**

正如[/frontier/loop-engineering/Loop_的灵魂不是执行_而是验证.md](/frontier/loop-engineering/Loop_的灵魂不是执行_而是验证.md)所述，验证器应当分层设计。硬性规格校验不依赖模型的语义理解能力，而是由本地脚本在毫秒级内完成：

| 校验维度 | 检查工具 | 异常表现（以 Redis 文章为例） | 处理方式 |
| :--- | :--- | :--- | :--- |
| **长度范围** | 字符统计函数 | 要求 2000-3000 字，实际仅生成 1200 字 | 触发局部扩写分支 |
| **目录结构** | Markdown 解析器 | 缺少二级标题 `## AOF 持久化` | 驳回并要求补齐指定小节 |
| **必备要素** | 正则匹配 / 集合包含 | 全文未提及 `fork` 或 `写时复制`（COW） | 在修补要求中作为必填词注入 |
| **禁用词过滤** | 字符串匹配 / AC 自动机 | 出现“绝对零丢数据”、“保姆级教程”等词汇 | 精确定位位置，直接替换或要求重写该句 |

```python
# 确定性硬规格校验器示例
from typing import List, Dict, Any
import re

def validate_hard_constraints(text: str, schema: Dict[str, Any]) -> List[str]:
    violations = []
    
    # 1. 字数范围检查（避免模型不擅长计数的缺陷）
    char_count = len(text.strip())
    if not (schema["min_chars"] <= char_count <= schema["max_chars"]):
        violations.append(f"字数不合规: 当前 {char_count} 字，要求 [{schema['min_chars']}, {schema['max_chars']}]")
    
    # 2. 必备章节检查（提取 Markdown 二级标题）
    headers = set(re.findall(r"^##\s+(.+)$", text, re.MULTILINE))
    missing_sections = set(schema["required_sections"]) - headers
    if missing_sections:
        violations.append(f"缺失必备章节: {list(missing_sections)}")
        
    # 3. 禁用词列表精确扫描
    found_forbidden = [w for w in schema["forbidden_words"] if w in text]
    if found_forbidden:
        violations.append(f"包含禁用词汇: {found_forbidden}")
        
    return violations
```

通过规则脚本拦截后，格式不合格的稿件会直接被打回，明确要求补充章节或修改字数。只有当草稿满足基本规格后，才会进入语义审校阶段，避免在篇幅严重不足的残缺稿件上空耗语义推理成本。

## 第二层防线：拆解主观维度的量表打分

通过了格式和硬规则后，文章才需要进入语义质量评估。为了避免大模型给出模糊的“写得还行，打 80 分”，系统需要引入**评分量表（Rubric）**，将主观质量拆解为几个相互独立、标准明确的评估维度。

在技术长文撰写中，通常拆分为三个互不重叠的维度：

### 1. 事实一致性与依据支持（Factual Consistency）
* **评估定义**：正文中陈述的技术机制是否有依据，是否存在捏造现象或夸大结论。
* **评分档位参考**：
  * 5 分：机制准确，清楚标明了生效前提（如明确说明 RDB 的 bgsave 依赖子进程写时复制，且存在丢数据窗口）。
  * 3 分：结论大致正确，但混淆了概念前提（如把 AOF 的 `appendfsync always` 误写成完全没有磁盘写入性能损耗）。
  * 1 分：出现严重事实错误（如宣称 RDB 可以在单线程内实现零延迟实时持久化）。

### 2. 论述逻辑与过渡衔接（Logical Coherence）
* **评估定义**：段落之间是否存在自然的推导关系，前后结论是否一致，是否有无过渡的技术名词突现。
* **评分档位参考**：
  * 5 分：推导顺畅，先讲内存数据面临掉电风险的问题背景，再对比 RDB 快照与 AOF 日志两种解决思路，层次分明。
  * 3 分：各小节内容各自正确，但小节之间像是孤立的技术卡片拼凑，缺乏过渡。
  * 1 分：前后论据互相矛盾（前文称 AOF 实时性高，后文又称 AOF 丢数据风险大于 RDB）。

### 3. 表述精度与信息密度（Tone & Density）
* **评估定义**：是否使用具体对象和动词，是否存在无意义的形容词堆砌与空话套话。
* **评分档位参考**：
  * 5 分：语言凝练，专注于参数、数据流向和状态转换，行文简洁。
  * 3 分：能说清问题，但夹杂部分“众所周知”、“可以说非常关键”等冗余转折。
  * 1 分：充斥大量营销式套话，有效技术信息极低。

在调用评估模型时，提示词中需强制要求模型**先列举违背量表标准的具体引文与缺陷说明，最后再输出离散分值（1 至 5 分）**。这种类似 [/llm-100/prompt-engineering/CoT_思维链提示为什么有效.md](/llm-100/prompt-engineering/CoT_思维链提示为什么有效.md) 的生成顺序，能促使模型根据事实依据做出判断，而不是无依据地直接打分。

## 架构隔离：审校角色与撰写角色分离

为了避免模型自我审查带来的盲区，系统在执行链路中需要将**撰写者（Writer）与审校者（Critic）进行物理隔离**。

```
[用户输入大纲与参考材料] 
          │
          ▼
┌───────────────────┐     生成全篇草稿
│ 撰写角色 (Writer) ├──────────────────┐
└───────────────────┘                  │
                                       ▼
                             ┌───────────────────┐
                             │ 规格硬校验脚本    │ ──(未通过)──> 打回重修硬指标
                             └─────────┬─────────┘
                                       │(通过)
                                       ▼
┌───────────────────┐     提交独立审校请求
│ 审校角色 (Critic) │ <────────────────┘ (不包含撰写历史对话，
└─────────┬─────────┘                     只传入评分量表与当前裸文本)
          │
          │ 输出结构化反馈：问题段落 ID、缺陷说明、修改建议
          ▼
┌───────────────────┐
│ 差分修补调度器    │ ──> 提取目标段落，单独触发局部修改 Prompt
└───────────────────┘
```

实现审校分离时有三个关键工程细节：

1. **清空生成历史**：审校模型的请求中**不能包含**撰写模型刚才的思考过程或多轮对话记录。审校上下文只放入任务原始要求、评分量表、已知参考资料以及当前的裸文本。这样可以消除撰写过程中的中间推导对审校判断的诱导。
2. **审校提示词设定**：给审校模型设定明确的职责定位，要求其充当严谨的技术校对人员，重点寻找断言漏洞、逻辑跳跃与空洞词汇。同时必须提醒审校者只针对量表中的实际缺陷提出修改，防止因过度挑剔引发无意义的反复改写。
3. **采样参数调优**：撰写模型可配置适当的多样性采样参数（可参考 [/llm-100/prompt-engineering/Temperature_Top-p_Top-k_分别控制什么.md](/llm-100/prompt-engineering/Temperature_Top-p_Top-k_分别控制什么.md)）；而审校模型建议将 `Temperature` 设为 0 或接近 0，以获得更稳定、更一致的打分与缺陷归因结果。

## 修复策略：段落级差分修补，避免整篇重写

在软件工程中，自动化工具提交补丁通常遵循最小修改原则（Minimal Diff），哪里报错改哪里。长文创作的反馈循环也应当遵循这一机制：**执行段落级的差分修补（Differential Patching），避免触发整篇重写**。

### 为什么整篇重写容易导致系统发散？
假设审校模型指出：“第 3 小节对 AOF 重写（rewrite）机制的描述有误，误把 `fork` 子进程写成了在主线程中阻塞执行”。如果把这条意见连同整篇草稿打包给模型并要求“重新修改全文”，撰写模型在修改第 3 小节的同时，很可能改变第 1 小节的过渡句，删掉第 2 小节原本很准确的例子，甚至在其他地方引入新的错漏。整篇重写的改动范围过大，破坏了上一轮已经验证合格的内容，导致循环无法平稳收敛。

### 差分修补的三步执行流程

1. **切片与段落标识（Chunking & Addressing）**：
   将文章按 Markdown 章节与自然段解析为文档节点树，为每个段落分配唯一标识（例如 `section_3_p_2`）。审校模型在指出问题时，必须指定对应的段落编号与需要修改的原句。
2. **提供边界上下文的局部修补（Contextual Patching）**：
   系统只将有缺陷的段落提交给模型进行修改，同时附带其**前一段的结尾**与**后一段的开头**作为承接约束，确保新修改的段落能够自然融入上下文。
3. **文档树替换重组（Stitching）**：
   由本地程序直接将修改后的段落替换到原文档树对应的节点中，重新组合成完整的 Markdown 文档，再进入下一轮检查。

```python
# 差分修补提示词组装示意
def build_patch_prompt(doc_tree: Any, target_id: str, critique: str) -> str:
    # 提取前后相邻段落以保持语义衔接
    prev_context = doc_tree.get_prev_snippet(target_id)
    next_context = doc_tree.get_next_snippet(target_id)
    current_text = doc_tree.get_node_text(target_id)
    
    prompt = f"""
你正在修改技术文章中的一个特定段落。

[前文结尾]
{prev_context}

[待修改段落原文]
{current_text}

[后文开头]
{next_context}

[审校意见与事实纠正]
{critique}

[修改要求]
1. 针对审校意见修改该段落，严格确保与前文结尾和后文开头的逻辑衔接。
2. 仅输出修改后的段落正文，不要输出任何开场白、解释说明或外部标记。
"""
    return prompt
```

## 停止策略：加权综合评分与熔断退出

因为自然语言主观评价很难达到绝对的满分，缺乏明确停止条件的循环会不断空转直到耗尽最大轮次。

### 综合得分计算
在每一轮修补完成后，根据量表维度计算当前轮次 $t$ 的加权综合得分 $S^{(t)}$：

$$S^{(t)} = w_{\text{fact}} S_{\text{fact}}^{(t)} + w_{\text{logic}} S_{\text{logic}}^{(t)} + w_{\text{style}} S_{\text{style}}^{(t)}$$

权重根据任务类型配置，满足归一化条件：

$$w_{\text{fact}} + w_{\text{logic}} + w_{\text{style}} = 1.0$$

在严谨的技术文档中，事实与逻辑权重要明显高于文风修饰。常见的一组配置为：
* $w_{\text{fact}} = 0.50$
* $w_{\text{logic}} = 0.35$
* $w_{\text{style}} = 0.15$

### 退出条件与回滚机制
循环在每轮差分修补后更新状态，由以下条件控制退出：

1. **达标退出**：
   当硬性规则全部通过，且综合得分 $S^{(t)} \ge 4.2$（满分为 5 分），同时事实分 $S_{\text{fact}}^{(t)} \ge 4.0$ 时，视为质量达标，终止循环并输出结果。
2. **收益递减与倒退熔断**：
   若本轮得分相比上一轮的提升量 $\Delta S = S^{(t)} - S^{(t-1)}$ 低于阈值（例如 $\Delta S < 0.1$），或者得分出现下降（$S^{(t)} < S^{(t-1)}$），说明继续自动修改的边际收益极低，甚至已经开始破坏既有内容。此时触发熔断退出，**程序回滚并输出历史得分最高的快照版本**。
3. **最大轮数保护**：
   设定固定的循环上限（例如 3 轮）。如果在 3 轮差分修补后仍未达标，通常意味着任务大纲、参考资料或初始输入存在根本矛盾，继续迭代只会浪费算力，系统应停止循环并交由人工介入。

## 适用边界与工程权衡

引入反馈循环可以有效提高初稿的质量基线，但它在工程架构上也带来了明确的成本代偿：

* **推理成本与耗时成倍增加**：单次提示词生成只需要 1 次模型推理；而包含硬性过滤、量表打分与段落差分修补的循环，单篇文章通常需要消耗 3 到 6 次以上的模型调用。因此，这种架构适合异步的技术文档写作、研报批量生成，而不适合需要秒级响应的实时聊天场景。
* **审校模型能力构成系统上限**：如果审校模型本身的知识储备存在漏洞，或者误判了参考资料中的技术定义，它给出的负面意见会误导撰写模型，导致段落被改错。量表必须提供清晰的客观事实依据供审校模型对照。
* **局部缝合处的语调连贯性**：虽然差分修补避免了全文漂移，但在极少数情况下，新重写的段落可能与未修改的上下文产生微妙的用词习惯差异。因此在实际工程中，最合理的模式是由反馈循环将初稿自动打磨到 85 分以上，再交由人工编辑做最终的快速通读和定稿。

在设计更复杂的循环时，还会遇到诸如死循环震荡、Prompt 上下文膨胀等稳定性问题，相关分析与防御措施见下一篇 [/frontier/loop-engineering/Loop_Engineering_的坑_无限循环_烧_Token_越改越差.md](/frontier/loop-engineering/Loop_Engineering_的坑_无限循环_烧_Token_越改越差.md)。
