在构建大模型自动化闭环（Loop Engineering）时，最让开发者头疼的往往不是“模型不干活”，而是“模型一直在干活，却把代码越改越乱”。当系统获得“修改代码 -> 运行测试 -> 读取报错 -> 再次修改”的自治权力后，如果没有严格的调度拦截规则，它很可能会迅速耗尽 API 预算，甚至在几个错误状态之间来回跳跃。

在上一讲[/frontier/loop-engineering/最简单的_Loop_写代码_跑测试_自动修复.md](/frontier/loop-engineering/最简单的_Loop_写代码_跑测试_自动修复.md)中，我们实现了一个能跑通单测并自动修复的基础闭环。本篇将通过一个贯穿示例，剖析循环在真实运行时容易出现的退化震荡、假收敛死循环与上下文膨胀问题，并给出可落地的工程拦截规则。

### 贯穿示例：购物车折扣函数自动修复

为了直观理解循环为什么会失控，我们来看一个具体的任务场景。假设我们需要模型编写一个电商购物车折扣计算函数 `calculate_discount(cart, user_type, coupon_code)`：

- 规则 1（基线逻辑）：普通用户（`NORMAL`）满 200 减 20；VIP 用户享受全单 8 折。
- 规则 2（目标修复）：新增优惠券码 `SAVE10`，可以在满足条件时再减 10 元，且最低支付金额不能低于 0 元。

初始代码由模型生成后，已有一套包含 5 个用例的测试集，其中针对普通用户和 VIP 基础折扣的 3 个用例全部通过，新增优惠券的 2 个测试用例未通过。我们启动自动化修复循环，模型随即展开了以下行动：

1. **第 1 轮**：模型看到 `test_vip_with_coupon` 失败，直接在函数第一行硬编码了针对 VIP 和优惠券的特殊返回。结果：优惠券测试通过了，但原本正常的无券 VIP 用例挂掉了。
2. **第 2 轮**：外层调度器把新的挂起日志喂给模型。模型为了修复无券 VIP 用例，把判断逻辑整体改写，结果普通用户的满减逻辑被误伤破坏。
3. **第 3 轮**：模型开始尝试重写整段函数，但在低温采样下，它对某处逻辑产生了固定执念，生成的代码与第 1 轮完全一致。
4. **第 4 轮**：模型连续报错后，在输出中写了一段“我很抱歉，已经按照要求全面修复了上述问题”的自然语言总结，并且没有调用任何文件修改工具。外层调度器如果仅判断“模型没有提出新的修改要求”，就会误以为修复顺利收敛。

这个简单的例子完整暴露了自动化循环的三大核心隐患：**退化震荡**、**死循环与假收敛**，以及在此过程中随轮次二次方累积的 **Token 膨胀**。

---

### 退化震荡：修此坏彼的成因

“退化震荡”（Oscillation）是指模型在多轮修改中，为了解决当前轮次暴露的局部错误，破坏了此前已经测试通过的功能。表现为状态在两个或多个局部极值之间反复横跳。

退化震荡通常源于两个工程因素：

1. **局部反馈诱发捷径修补（Shortcut Patching）**：如果调度器在当前轮次只把“刚才失败的测试用例输出”塞进 Prompt，模型的注意力会完全聚焦于消除这几行报错，进而采取最小编辑距离的贪心打补丁方式。在缺乏全局约制的情况下，这种局部修补极易破坏隐性契约。
2. **多目标约束的不可见性**：复杂的业务规则往往隐含在基线代码的历史设计中。当模型只看到报错堆栈时，它并不知道哪些现存分支承载了不可妥协的边界保护，导致它在“修复测试 A 导致测试 B 失败”与“修复测试 B 导致测试 A 失败”之间周期性往复。

![退化震荡机制与状态往复](/images/content-rebuild/8900c6fd81483504/fig-1.png)

如上图所示，当外部环境缺乏跨轮次的状态记忆与全局验证时，循环轨迹不会向全绿（All Passed）收敛，而是在两个局部状态之间反复震荡。每一轮单看修改都在解决局部报错，整体可用性却在持续倒退。

### 死循环与假收敛：为什么会在原地打转？

除了退化震荡，无终止条件的循环还常遇到两类停滞问题：不可满足死循环和假收敛退出。

#### 1. 矛盾约束与不可满足需求
当需求规格本身存在逻辑冲突（例如需求描述要求“函数保持纯原生，不依赖任何第三方库”，但测试用例却断言了一个第三方库特有的浮点精度舍入结果），客观上根本不存在能通过全部测试的代码。如果循环只以“测试是否全过”作为退出条件，系统就会在解空间之外做无休止的无效排列组合，直到触发超时。

#### 2. 低温采样下的认知死锁
为了追求输出的稳定性，代码生成场景通常会将采样温度设为极低值（如 $\text{Temperature} = 0.0$）。在确定性解码下，如果环境反馈给模型的报错信息较为简略（例如仅有 `AssertionError` 而没有变量上下文），模型对该问题的条件概率预测几乎保持不变。它极易在后续轮次中，以微调缩进、替换变量名等表面形式重复提交同构方案，陷入认知死锁。

#### 3. “不调用工具”不等于“任务完成”
一个常见的调度器缺陷是把“模型停止生成工具调用（Tool Calls）”作为循环顺利完成的标志。当模型在连续报错后进入防御机制，或者上下文过长导致工具调用格式丢失时，它往往会输出一段客套话（如“以上是为您重构的代码，请查收”）并停止生成工具指令。如果调度器只检测 `len(tool_calls) == 0`，就会把这种认输放弃误判为绿灯通过，造成严重的静默故障。

### 上下文膨胀：多轮迭代中的开销暴涨

在朴素的循环实现中，开发者往往直接将每一轮模型的输出和环境的测试日志追加到同一个对话历史中。这种做法会导致输入 Token 随轮次呈二次方加速累积。

#### 上下文膨胀算例
我们以一个具体的参数假设来推算开销。设：
- 系统提示与初始任务规格固定为 $T_{\text{sys}} = 2000$ Token；
- 模型每轮生成的代码与解释平均占用 $T_{\text{gen}} = 800$ Token；
- 运行测试产生的执行堆栈与环境输出占用 $T_{\text{obs}} = 1200$ Token。

若采用“保留全量历史对话”的做法，在第 $k$ 轮推理时，输入到模型的前置上下文长度为：

$$L(k) = T_{\text{sys}} + (k - 1) \times (T_{\text{gen}} + T_{\text{obs}}) = 2000 + (k - 1) \times 2000$$

进行 $N$ 轮尝试时，累积消耗的输入（Prefill）Token 总量为各轮输入长度之和：

$$S_{\text{prefill}} = \sum_{k=1}^{N} L(k) = N \cdot T_{\text{sys}} + 2000 \times \frac{(N-1)N}{2}$$

当 $N = 10$ 轮时：
- 线性基础开销部分：$10 \times 2000 = 20{,}000$ Token
- 历史累积二次方部分：$2000 \times \frac{9 \times 10}{2} = 90{,}000$ Token
- 累积输入消耗达到 $110{,}000$ Token，输出端生成 $10 \times 800 = 8{,}000$ Token。

作为对比，如果外层调度器采用**差分切片模式**，每轮只输入系统提示、当前最新的代码快照以及当前轮次清洗后的关键报错堆栈，不保留前 9 轮的废弃代码与冗余日志。假设切片后的上下文恒定维持在 $4000$ Token 左右，则 10 轮迭代的输入 Token 总量仅为：

$$10 \times 4000 = 40{,}000\text{ Token}$$

在相同轮次下，差分切片节省了超过 $63.6\%$ 的输入开销。关于 Token 计费与预算核算模型，可进一步参考[/fundamentals/token-and-tokenizer/token-budget.md](/fundamentals/token-and-tokenizer/token-budget.md)。

![上下文历史累积与清理对比算例](/images/content-rebuild/8900c6fd81483504/fig-3.png)

除了经济成本，上下文膨胀还会直接影响模型的推理质量。随着大量过时的错误代码和堆栈日志塞满注意力窗口，模型对最初设定的核心业务规则的关注度会被稀释，容易出现“越改越偏、代码越写越冗余”的现象。

### 防御策略一：全量回归拦截与差分状态切片

要从根本上阻断退化震荡，外层宿主系统必须在调度层建立两道确定性护栏：全量回归拦截与差分状态输入。

#### 1. 全量回归测试（Full Regression Test）与强制回滚
在循环执行测试时，**严禁只运行当前失败的目标用例**。调度器必须把测试集拆分为明确的两组：
- **基线测试集（Base Tests）**：进入本轮循环前系统已经通过的所有既有用例；
- **目标测试集（Target Tests）**：本次迭代需要攻克的增量功能或 Bug 修复用例。

每一轮代码变更后，测试运行器必须全量执行这两组测试，并按照如下状态转移规则决策：

| 测试执行表现 | 调度决策 | 动作说明 |
| :--- | :--- | :--- |
| 目标用例通过，基线用例 100% 通过 | **任务成功，跳出循环** | 达到目标且无退化，顺利收敛 |
| 目标用例未通过，基线用例 100% 通过 | **接受改动，进入下一轮** | 保护了既有逻辑，允许继续探索 |
| 基线用例出现任何失败（Regression） | **强制回滚（Rollback）改动** | 拒绝破坏旧功能的代码，恢复基准分支 |

一旦触发基线用例失败，宿主环境立即执行 `git checkout` 回滚到改动前的稳定版本，并将“改动破坏了既有用例 X，改动已撤回”作为负向反馈传给下一轮 Prompt。通过阻断坏代码落地，退化震荡链条在第一轮就会被物理斩断。

#### 2. 差分状态切片（Diff Slicing）
不要将上千行的完整控制台日志直接回灌给模型。调度器应在宿主端对测试输出做结构化过滤：
- 过滤环境初始化、第三方库加载等无关杂音，只保留异常类型、关键断言表达式及最末级调用堆栈；
- 传入统一的 Unified Diff 补丁而非全量文件，帮助模型聚焦于相对上一稳定版本的具体变化。

需要注意的是，差分切片虽然极大节省了 Token 并减轻了注意力分散，但也抹去了“前几轮踩过哪些坑”的历史信息。因此，必须搭配下文的状态哈希判重，防止模型重复犯同样的错误。

### 防御策略二：状态哈希判重、采样调度与三层硬熔断

针对不可满足死循环和局部死锁，调度器必须借助宿主端确定性的代码规则进行强干预，而不是指望模型“自己醒悟”。

```python
import hashlib
import time
from dataclasses import dataclass, field
from typing import Set, Tuple, Optional

@dataclass
class LoopGuard:
    max_steps: int = 5
    max_cost_tokens: int = 50_000
    timeout_seconds: float = 120.0
    seen_state_hashes: Set[str] = field(default_factory=set)
    current_step: int = 0
    accumulated_tokens: int = 0
    start_time: float = field(default_factory=time.time)

    def check_and_record_state(self, code: str) -> Tuple[bool, str]:
        """
        通过归一化代码哈希检测是否陷入原地死循环
        """
        # 去除空白字符与换行干扰，计算规范化文本哈希
        normalized_code = "".join(code.split())
        code_hash = hashlib.sha256(normalized_code.encode("utf-8")).hexdigest()
        
        if code_hash in self.seen_state_hashes:
            return False, "DETECTED_DUPLICATE_STATE: 代码回到了之前出现过的相同状态，陷入震荡死循环"
        
        self.seen_state_hashes.add(code_hash)
        return True, "STATE_ACCEPTED"

    def should_abort(self, step_tokens: int) -> Tuple[bool, Optional[str]]:
        """
        三层硬熔断判定：步数、Token 预算与物理限制
        """
        self.current_step += 1
        self.accumulated_tokens += step_tokens

        if self.current_step > self.max_steps:
            return True, f"ABORT_STEP_LIMIT: 达到最大迭代步数 {self.max_steps}"
        
        if self.accumulated_tokens > self.max_cost_tokens:
            return True, f"ABORT_TOKEN_BUDGET: 消耗 Token {self.accumulated_tokens} 超过预算 {self.max_cost_tokens}"
        
        if time.time() - self.start_time > self.timeout_seconds:
            return True, f"ABORT_TIMEOUT: 运行时间超过物理限制 {self.timeout_seconds} 秒"

        return False, None
```

#### 1. 状态哈希判重（State Hashing）
如上方代码所示，调度器在获取模型生成的代码后，先去除空白符做规范化，并计算 SHA-256 哈希值。如果该哈希值已存在于集合中，意味着模型输出了与之前某一轮完全相同的代码，闭环形成了 $A \rightarrow B \rightarrow A$ 的死结。宿主系统应立即熔断该分支，阻止无效轮询。

#### 2. 多样化采样调度（Sampling Escalation）
在第 1 轮尝试时，使用 $\text{Temperature} = 0.0$，优先执行高确定性的标准实现。当系统连续两轮改动未取得实质进展（通过的用例数未增加）但尚未触发死循环时，调度器可动态拉高采样温度（例如调整到 $0.5$），或者向下一轮 Prompt 注入算法变异提示（“请完全放弃当前的实现逻辑，改用查表法或另一种数据结构重写”），协助模型逃离局部极值。

#### 3. 三层硬性截断
工程宿主必须为每次 Loop 执行配置不可逾越的熔断线：
- **步数上限（Max Steps）**：通常根据任务复杂度设置为 3 到 6 步，超过此阈值模型自行修复的概率通常呈长尾衰减；
- **Token 预算墙（Token Budget）**：严格限制单次任务累积消耗，达到上限立即掐断，防止账单失控，详见[/architecture/token-cost.md](/architecture/token-cost.md)；
- **挂钟物理超时（Wall-Clock Timeout）**：设置整体运行物理时长（如 120 秒），防止宿主沙箱因死锁代码耗尽线程。

### 生产监控告警与人机交接流转

在真实业务环境中，不能假设自动化闭环能够 100% 独立解决所有缺陷。健全的系统需要在自动化失效时提供平滑的交接机制。

#### 1. 评估收敛曲线（Convergence Curve）
监控系统应当记录每一轮迭代的测试通过率：
- 健康的任务曲线应当呈现严格单调递增，或者在前 2 轮内快速达标；
- 如果曲线在第 3 轮呈现波浪形波动（如 $60\% \rightarrow 80\% \rightarrow 60\%$），监控引擎应判定系统已陷入震荡，立刻终止自动修改。

#### 2. 统计轮次分布（Iteration Distribution）
在服务集群层面，统计所有任务的解决步数分布：
- 运行良好的系统通常呈现前倾分布，大部分可修复的任务在 1-2 轮内完成；
- 若长尾分布（达到步数上限才退出的任务）比例明显偏高，通常说明目标测试集质量不高、前置 Prompt 指令含糊，或者当前任务复杂度超出了模型承载能力，应当发出配置预警。

#### 3. 降级人工接管（Human-in-the-Loop）
熔断不是让程序直接抛出异常崩溃，而是触发自动化向人工的平稳过渡：
1. 调度系统自动回滚到整个循环过程中**通过测试数最多**的历史快照版本；
2. 收集各轮的 `git diff`、最终未通过的单测堆栈以及 Token 审计开销；
3. 自动生成一个包含上述结构化信息的工单或 Pull Request，交由人工工程师接管排查。
