在开发大语言模型（LLM）应用时，很多开发者最先接触的是在测试窗口里调整一段提示词（Prompt）。但当应用接入真实业务系统后，只靠调整提示词的文本措辞，往往很难维持输出的稳定性。

以一个企业级售后支持助手为例：用户提问时，系统不仅要向模型发送预设的人设提示词，还要动态拉取近 5 轮对话记录、从知识库检索 5 篇产品说明书切片、调用订单接口获取当前物流状态，并要求模型严格按照 JSON 格式输出。此时，开发者会立刻遇到三个具体问题：

1. 所有内容拼接在一起，总长度可能突破模型的上下文上限，导致接口报错；
2. 检索出来的多篇技术文档夹杂着无关内容，模型容易忽略核心故障代码；
3. 历史对话过长，挤占了放置关键维修手册的空间。

上下文工程（Context Engineering）正是为了解决这些运行时问题而形成的方法。它的核心目标是在有限的 Token 预算和时延要求下，从多个数据源筛选、压缩并排布信息，为大模型提供低噪声、结构清晰且信息密度高的运行时输入。

### 为什么窗口变大后，依然需要上下文工程？

随着模型架构的演进，原生上下文窗口已经从早期的 4,096 Token 扩展至 128,000 Token 甚至更长。但窗口增大并没有消除上下文管理的必要，反而带来了新的工程权衡：

- **有效信息稀释**：自注意力机制允许模型在整个输入序列中分配权重。但在长输入中，无关背景和检索噪声会分散模型的注意力权重。在实际测试中，长文本中间位置的关键信息容易被模型忽略（即“大海捞针”效应），导致提取准确率下降。
- **计算开销与首字延迟**：在大模型推理的预填充阶段（Prefill），计算量与输入序列长度密切相关。在全注意力机制下，计算复杂度随输入长度呈二次方增长。输入的内容越多，生成第一个字符的延迟（Time to First Token, TTFT）越长，调用商业 API 的 Token 计费成本也会直接上升。
- **数据来源的异构与不可控**：运行时的输入通常由静态指令、多轮对话、外部文档、工具执行结果和输出模式约束混合而成。由于外部数据长度不可控，直接静态拼接随时可能引发超出窗口硬限制的系统故障。

### 静态 Prompt 与动态 Context 的边界

理解上下文工程，首先需要理清静态提示词（Prompt）与动态上下文（Context）的分工：

- **静态 Prompt 编写**：主要发生在应用设计期。它定义了模型的通用角色、任务目标、语气风格和少样本示例（Few-shot Examples），通常以固定的模板形式存放在代码仓库或配置中心中。
- **动态 Context 编排**：发生在系统运行期。服务收到用户请求后，由程序从数据库拉取会话状态、从检索系统召回知识切片、调用外部 API 获取实时数据，再经过过滤、压缩、优先级排序与格式组装，最终打包成提交给模型的完整输入。

#### 动态组装流程算例

假设系统为单次请求预留了 4,000 Token 的总输入预算（模型最大窗口已扣除预期输出长度）。此时系统收集到的待装配内容如下：

```text
输入总预算上限: 4,000 Tokens (已扣除输出生成预留)
待装配候选项：
- 系统角色指令与安全红线 (固定配置) : 300 Tokens
- 输出 JSON Schema 定义 (固定配置) : 200 Tokens
- 用户当前输入 Query (动态输入) : 150 Tokens
- 向量检索知识切片 5 条 (动态数据) : 2,500 Tokens
- 历史多轮对话记录 6 轮 (动态数据) : 1,800 Tokens

候选项总量: 300 + 200 + 150 + 2,500 + 1,800 = 4,950 Tokens
超出预算: 950 Tokens
```

如果采用简单的字符串拼接，请求会因超出 4,000 Token 限制而被模型网关拒绝；如果直接从文本末尾强行截断，可能截断尾部的 JSON Schema 定义，导致模型无法按格式输出。

上下文编排流水线会采取**基于优先级的动态裁剪**：

1. **绝对锁定层（不可淘汰）**：保留系统指令（300 Tokens）、输出格式定义（200 Tokens）和用户当前输入（150 Tokens），小计 650 Tokens。剩余可用空间为 `4,000 - 650 = 3,350 Tokens`。
2. **历史压缩层**：将 6 轮对话（1,800 Tokens）中较早的 4 轮提取为语义摘要，仅保留最近 2 轮原文，将历史对话总体压缩至 600 Tokens。剩余可用空间变为 `3,350 - 600 = 2,750 Tokens`。
3. **知识重排淘汰层**：知识切片总需求为 2,500 Tokens，当前可用空间充裕（2,750 Tokens）。此时无需截断检索切片，可全量装入。
4. **最终装配总量**：`650 + 600 + 2,500 = 3,750 Tokens`，完全处于 4,000 Token 预算之内，同时保留了格式契约与核心知识。

### 上下文工程的量化验收指标

上下文组织的质量不能仅凭几组测试样例的人工观感判定，应当通过明确的工程指标进行监控和持续调优：

![上下文组织质量的四大工程评估维度与验收闭环](/images/content-rebuild/474d44e36418be93/fig-3.png)

- **有效信息密度（Signal-to-Noise Ratio）**：在业务任务评测得分持平的前提下，单次请求所消耗的平均输入 Token 数。在保证质量的前提下，输入 Token 越少，信息密度越高，系统推理延迟与 API 成本越低。
- **输出结构合规率（Schema Conformance Rate）**：下游系统在不需要进行多重正则替换或容错修补的情况下，直接成功将模型输出解析为预设结构（如 JSON、Pydantic 对象）的请求比例。
- **异常兜底覆盖率（Fallback / Escape Rate）**：当外部检索内容缺失、数据冲突或用户提问超出范围时，模型能够依据上下文中预设的兜底规则，明确返回“信息不足/无法处理”等安全状态的比例，而非自行编造不实信息。
- **预算超限截断率（Budget Overflow Rate）**：由于上下文组装逻辑不严谨，导致运行时触发模型网关硬性长度限制而发生异常报错的请求比例。成熟的上下文编排系统应通过程序化预算检查，将该指标压制至零。
