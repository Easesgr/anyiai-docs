面对一本数百页的技术规范、合同合集或研究报告时，工程实现通常有三条主要路线：一是把几十万字直接塞进大模型的长上下文窗口；二是按段落切块建立向量索引（分段检索 RAG）；三是先分章节生成摘要，再逐级聚合形成多层摘要树（Map-Reduce）。

![长文档问答架构选型全景](/images/content-rebuild/2c8da3be1acccb61/cover.png)

这三种做法各自有明确的物理边界与计算代价。选型的核心依据并非单纯看文档有多长，而是看用户的提问方式依赖文档多大范围的信息，以及业务对首字返回时间（TTFT）和单次调用成本的容忍度。本文结合一个贯穿始终的运维手册场景，拆解三类方案的工作机制、性能瓶颈与复合路由设计。

在深入讨论前，推荐先阅读[长上下文模型能解决什么问题？为什么不是上下文越长效果越好？](/frontier/long-context-app/what-is-long-context.md)了解长序列下的信息利用规律，以及[长上下文应用有哪些坑？位置衰减、信息淹没和成本过高怎么处理？](/frontier/long-context-app/long-context-pitfalls.md)了解注意力分散与延迟瓶颈。

## 一个贯穿场景：三类截然不同的提问需求

假设我们正在为一套 500 页、约 20 万 Token 的《电商系统微服务架构与应急运维手册》开发智能问答助手。用户的提问通常落在三种不同的信息分布模式中：

![三类任务拓扑的语义与计算特征](/images/content-rebuild/2c8da3be1acccb61/fig-1.png)

### 1. 定点事实查找（Point Fact Lookup）
* **典型问题**：“根据第 4.2 节的配置说明，订单服务的数据库连接池最大等待时间是多少毫秒？”
* **信息分布**：答案仅存在于某个具体的表格或段落中，不依赖其他章节的推理。
* **需求重点**：高精确度。只要准确定位这一小段文本，模型即可回答；输入过多无关文本反而可能引入噪音干扰。

### 2. 跨章节关联推理（Multi-hop Reasoning）
* **典型问题**：“第 3 章定义的鉴权 Token 刷新周期，与第 18 章描述的跨机房容灾降级流程是否存在冲突？在容灾触发时鉴权缓存如何保证一致性？”
* **信息分布**：线索分别落在相隔甚远的两章，需要将两处前提条件组合在一起推导答案。
* **需求重点**：证据链的完整性。如果只检索出一处片段，模型将因缺乏另一半约束而产生错误推断。

### 3. 全局主旨与全量盘点（Global Aggregation）
* **典型问题**：“整理全手册中所有触发系统自动降级的告警代码，并按受影响的业务域列出恢复步骤。”
* **信息分布**：信息分散在几十个章节中，没有哪一段文本包含完整列表。
* **需求重点**：高覆盖率。如果依靠相似度检索挑出前几条，必然漏掉大部分告警代码，导致回答残缺。

## 方案一：全文直填（Full-Context）

全文直填跳过任何前置切块或索引步骤，将整篇 20 万 Token 的手册直接拼入 Prompt，让模型依靠自身的长程注意力完成理解与生成。

![全量长上下文直填的工作机制与延迟因果](/images/content-rebuild/2c8da3be1acccb61/fig-2.png)

### 工作机制与优势
* **零切块信息损失**：没有切分导致的句子截断，保留完整的层级标题、表格结构和代词指代关系。
* **跨章节可见性**：所有 Token 在模型的注意力矩阵中对彼此开放，具备从全篇各处关联线索的上限能力。
* **链路极简**：无需搭建和维护向量数据库、分块流水线和重排服务。

### 首字延迟与计算开销瓶颈
大模型推理通常分为两个阶段：
1. **预填充阶段（Prefill）**：模型一次性读入所有 Prompt Token，计算注意力并将中间产生的 Key-Value 向量写入显存（即 KV Cache）。这个阶段只生成第一个输出 Token。
2. **解码阶段（Decode）**：模型基于已有的 KV Cache，逐字自回归生成后续 Token。

在标准全注意力（Self-Attention）机制下，Prefill 阶段的计算量随输入序列长度 $L$ 呈二次方增长（$O(L^2)$ 浮点运算）。即便采用 FlashAttention 这类高效算子，它优化的是 GPU 高速显存（SRAM）与全局显存（HBM）之间的数据搬运开销，并未改变理论计算量。

当一次性输入 20 万 Token 时：
* **首字时延（TTFT）大幅拉长**：在未命中提示词缓存的冷启动状态下，单次 Prefill 往往耗时数秒到十余秒。对于要求 1~2 秒内给出反馈的在线对话系统而言，这种等待较难接受。
* **单次成本线性叠加**：商用 API 按输入 Token 计费。如果用户追问 5 轮，每轮都重新传入 20 万 Token，总费用将迅速累积。
* **前缀缓存（Prompt Caching）的限制**：前缀缓存能将后续请求的 Prefill 耗时降低，但前提是文档内容和前缀位置完全一致，且模型服务端在此期间未释放该显存缓存。一旦前缀变动或缓存失效，长延迟与高费用仍会发生。

**适用条件**：文档长度中等（通常在 32k Token 以内）、并发量较低的高价值分析任务，或推理端具备高稳定性前缀缓存的基础设施。

## 方案二：分段检索（RAG）

分段检索在离线阶段将文档切分成若干片段（Chunk，例如每段 500 Token），经由嵌入模型转换为向量并存入向量数据库。在线请求到来时，系统通过问题向量与切片向量的比对，仅召回相关度最高的 Top-$K$ 个切片组装成上下文送入模型。

![分段检索切分边界与语义撕裂困境](/images/content-rebuild/2c8da3be1acccb61/fig-3.png)

### 优势与性能表现
* **首字时延极低**：送入模型的上下文仅包含 Top-$K$ 切片（通常在 2k~4k Token），Prefill 阶段计算量极小，首字通常可在 1 秒内返回。
* **运行成本低廉**：每次推理的 Token 消耗固定且可控，不受原始文档规模影响。

### 物理局限与失效模式
1. **切块导致的语义割裂**：
   若切分边界恰好落在关键段落中间，后半段可能出现“该参数严禁超过 1000ms”，而主语“订单超时取消等待时间”留在前半段。由于缺乏主语，后半段的语义向量与用户提问的相似度大幅降低，导致检索阶段被漏判。
2. **多跳因果线索遗漏**：
   当问题询问“鉴权 Token 刷新与机房降级的冲突”时，向量检索通常只能匹配到明确包含这类关键词的片段。如果第 3 章的 Token 刷新机制表述为基础协议，并未提及任何“降级”字眼，它在向量召回中的排名可能排在几十名开外，无法进入上下文。
3. **全局聚合任务完全失效**：
   针对“统计手册中所有告警代码”的问题，向量相似度无法把全书 30 多处分散的告警片段全数捞出。Top-$K$ 机制只能带出少量片段，导致模型基于不完全信息给出残缺回答。

**工程缓解策略**：
* **父子分块（Parent-Child Chunking）**：使用较小的子切片（如 200 Token）进行向量索引以保证匹配度；命中后，将包含完整上下文的父切片（如 1000 Token）提取出来组装上下文。
* **混合检索与重排序（Hybrid Search + Reranker）**：结合 BM25 关键词匹配与稠密向量检索，并通过 Cross-Encoder 重排模型重新打分，提升多条件事实检索的稳定性。

## 方案三：分层摘要（Map-Reduce）

面对宏观归纳与全篇盘点需求，分层摘要（Map-Reduce 范式）通过预先或动态的层级压缩来解决信息覆盖问题。

![分层摘要与Map-Reduce流水线](/images/content-rebuild/2c8da3be1acccb61/fig-4.png)

### 机制与执行流水线
该架构通过层次化聚合建立文档的摘要树：
1. **Map 阶段（局部抽取）**：将整篇手册切分为若干独立章节或逻辑区间，并发调用大模型对每个区间提炼核心事实、规则与列表。
2. **Reduce 阶段（多级合并）**：将相邻区间的局部摘要再次拼接，并发调用模型生成更高维度的章节综述，直到最后生成全手册的顶层概要。
3. **查询响应**：当收到全局盘点类问题时，系统直接读取顶层或中间层的结构化摘要进行回答；若发现某个关键分支需要验证，再顺着索引下钻到对应的原文区间。

### 适用条件与权衡
* **信息压缩的有损性**：每一次 Reduce 都是一次有损提炼。边缘参数（如特定服务端口号、冷门配置阈值）在向上汇总时往往会被模型舍弃，因此摘要树不适合处理高精度定点提问。
* **离线构建成本高**：生成整套摘要树需要数十次甚至数百次模型调用，构建周期较长，适合版本相对固定的手册类文档。
* **在线动态执行延迟偏高**：若在用户提问时动态发起全篇的 Map-Reduce，系统整体时延将取决于并发分支中最慢的那次调用，响应时间往往以数十秒计。

## 复合架构设计：意图与规模驱动的动态路由

单一路线无法兼顾秒级响应、超低费用与全覆盖推理。工程上行之有效的方案是引入轻量**动态路由（Dynamic Router）**，根据文档规模与提问意图将请求分流至最合适的处理链路。

![动态路由复合架构流程设计](/images/content-rebuild/2c8da3be1acccb61/fig-5.png)

### 路由判定逻辑

调度器按照以下三个步骤分流请求：
1. **规模初筛**：如果目标文档本身较短（如不超过 32k Token），无论何种问题，全文直填的延迟与成本都在合理区间，直接走长上下文链路。
2. **意图分类**：对于超长文档，通过轻量分类模型或规则关键词将意图划分为“定点事实”、“跨章推理”与“全局聚合”。
3. **缓存感知**：如果当前文档在推理集群中已确认存在高命中率的前缀缓存，跨章节推理优先走全文直填；否则走带重排的多跳检索流程。

```python
# 长文档问答路由调度实现示例
class DocQARouter:
    def __init__(self, doc_service, rag_engine, summary_tree, llm_client):
        self.doc_service = doc_service
        self.rag_engine = rag_engine
        self.summary_tree = summary_tree
        self.llm_client = llm_client

    def answer_query(self, doc_id: str, query: str) -> str:
        doc_tokens = self.doc_service.get_token_length(doc_id)
        intent = self.doc_service.predict_intent(query)  # POINT, MULTI_HOP, GLOBAL
        cache_ready = self.llm_client.check_prefix_cache_available(doc_id)

        # 规则 1：短文档，或中长文档已缓存且属于多跳问题 -> 全文直填
        if doc_tokens <= 32000 or (doc_tokens <= 128000 and cache_ready and intent == "MULTI_HOP"):
            full_text = self.doc_service.get_full_content(doc_id)
            prompt = f"基于以下完整文档回答问题。\n文档：{full_text}\n问题：{query}"
            return self.llm_client.generate(prompt)

        # 规则 2：全局综述、统计盘点类问题 -> 走摘要树聚合
        if intent == "GLOBAL":
            summary_context = self.summary_tree.get_aggregated_summaries(doc_id)
            prompt = f"基于以下章节摘要梳理全貌并回答。\n摘要：{summary_context}\n问题：{query}"
            return self.llm_client.generate(prompt)

        # 规则 3：定点事实或常规多跳 -> 混合检索 RAG (小块匹配 + 父块展开)
        retrieved_chunks = self.rag_engine.hybrid_search(
            doc_id=doc_id,
            query=query,
            top_k=6,
            expand_to_parent=True
        )
        context_text = "\n\n".join(retrieved_chunks)
        prompt = f"根据参考片段回答问题。\n参考资料：\n{context_text}\n问题：{query}"
        return self.llm_client.generate(prompt)
```

对于具体如何组装检索结果和构建提示词，可以参考[大模型应用系统怎么设计？](/fundamentals/llm-basics/app-system-design.md)以及[上下文管理](/architecture/context-management.md)。

## 方案量化对比与选型基准

在评估长文档问答方案时，建议围绕首字延迟、单次调用输入量、定点准确率与全局覆盖度四个维度建立量化基线。

![生产落地选型权衡三维坐标图](/images/content-rebuild/2c8da3be1acccb61/fig-6.png)

下表以一份 20 万 Token 文档、单次输出约 300 Token 的典型调用为例，对比各方案的技术指标与适用边界：

| 维度 | 方案一：全文直填（无前缀缓存） | 方案二：分段检索（RAG） | 方案三：分层摘要（Map-Reduce） | 方案四：动态路由复合方案 |
| :--- | :--- | :--- | :--- | :--- |
| **首字时延（TTFT）** | 偏长（受 Prefill 算力限制，约 4~12s） | **极短**（上下文小，约 0.5~1.2s） | 中等（在线读顶层摘要时约 1~2s） | **自适应**（绝大多数查询在 0.8~2.5s） |
| **单次推理计算输入** | 极高（每次计算约 200,000 Token） | **极低**（仅计算召回的 2,000~4,000 Token） | 较低（仅计算摘要树相关节点，约 5,000 Token） | **可控**（高频定点走轻量输入，仅必要时计算长输入） |
| **定点参数准确度** | 中~高（易受中间信息丢失干扰） | **高**（命中父切片时信息针对性极强） | 较低（参数级细节常在摘要阶段被压缩遗漏） | **高**（定点意图精确分流至父子切片链路） |
| **跨章节多跳推理** | **高**（全序列对齐，保留全局推导链条） | 低~中（依赖检索能否同时捞全互不包含关键词的片段） | 中等（依赖摘要层是否保留了两处的关联信息） | **中~高**（结合多跳重排，或在有缓存时升至全量） |
| **全局盘点覆盖率** | 中等（受模型单次最大输出长度与注意力稀释限制） | 极差（局部采样无法代表整体） | **极高**（自底向上构建，全篇分支均被纳入） | **高**（全局问题自动路由至摘要树链路） |

以技术文档与运维支持等典型问答场景为例，用户提问往往呈现高度倾斜的分布特征：高频的定点事实查询通常占据绝大部分流量（示意如 70%~80%），跨章节推导次之（如 15%~20%），全局盘点相对低频（如 5%~10%）。通过动态路由层将不同问题分派至对口流水线，系统既能在大多数请求中保持毫秒级首字返回与极低 Token 成本，又不会在全局盘点和深层多跳问题上出现致命的检索盲区。

关于状态机编排与更复杂的上下文调度策略，可参考[AI 系统设计](/architecture/ai-system-design.md)及[Agent 的上下文管理为什么重要？](/interview/agent-interview/context-management.md)。
