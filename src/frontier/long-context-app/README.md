模型上下文窗口从早期的 4k、8k 扩展到 128k、1M 乃至更高，意味着模型单次能够接收整本手册或完整代码库。然而在工程落地中，“能够接收”并不等于“开箱即用”。直接把长文本填满上下文，往往会带来首字延迟（TTFT）激增、显存被键值缓存（KV Cache）挤占、并发吞吐暴跌以及注意力分配不均等现实问题。

本专题旨在梳理长上下文技术的运行机制、开销构成、常见缺陷与工程解决方案，帮助开发者在实际业务中兼顾检索准确率、响应速度与硬件成本。

## 一个贯穿例子：10 万 Token 的架构设计文档

为了直观理解长上下文带来的工程影响，我们设定一个典型的业务场景：

某团队需要针对一份 10 万 Token（约合 15 万至 20 万中文字符）的《核心交易系统设计与接口规范》搭建智能问答助手。系统需要应对两类提问：
1. **全局推理型**：“请梳理订单从创建、超时未支付、库存回滚到消息通知的完整状态流转路径。”
2. **单点查询型**：“退款接口中的 `refund_source` 字段支持哪些枚举值？”

如果技术团队直接采用最简方案——每次用户提问时，都将这份 10 万 Token 的文档完整拼接到 Prompt 中发送给大模型，系统会立即遭遇两道物理瓶颈。

## 预填充计算与 KV 缓存显存的工程代价

大模型的单次推理过程可以拆分为两个阶段：预填充阶段（Prefill）与逐字解码阶段（Decode）。关于推理阶段的底层基础，可参考[上下文长度是什么？](/fundamentals/inference-and-generation/context-length.md)与[推理与生成](/fundamentals/inference-and-generation/README.md)。

1. **Prefill 阶段的计算与首字延迟（TTFT）**：
   模型在生成第一个输出 Token 之前，必须一次性计算输入 Prompt 中所有 Token 之间的自注意力矩阵。虽然 FlashAttention 等算子优化极大减少了 GPU 高带宽显存（HBM）与片上片内缓存（SRAM）之间的数据搬运，但全注意力的理论算术计算量仍然随着输入序列长度呈二次方（$O(N^2)$）增长。对于 10 万 Token 的输入，Prefill 计算需要消耗大量浮点运算，导致首字延迟（Time to First Token）通常长达数秒甚至十几秒。
2. **Decode 阶段的 KV Cache 显存占用**：
   为了在自回归生成时不必在每个步骤重新计算历史 Token 的 Key 和 Value 向量，模型会将这些中间张量缓存在显存中，这部分显存称为 KV Cache。KV Cache 的显存大小与序列长度呈严格线性关系：
   $$\text{KV Cache 显存大小} = 2 \times \text{模型层数} \times \text{KV 头数} \times \text{头维度} \times \text{序列长度} \times \text{数值精度字节数}$$
   以一个采用分组查询注意力（GQA，例如 KV 头数为 8、隐藏层维度每头 128、共 32 层、采用 BF16 精度占 2 字节）的开源 8B 模型为例，单次处理 100,000 Token 的上下文，仅 KV Cache 自身就需要占用：
   $$2 \times 32 \times 8 \times 128 \times 100,000 \times 2 \text{ 字节} = 13,107,200,000 \text{ 字节} \approx 12.21\text{ GiB (约 13.11 GB)}$$
   如果是多并发环境，若同时有 20 个独立长请求并发（无共享前缀），单是 KV Cache 就需要占据超过 240 GiB 的显存。这需要多张 80 GB 高端 GPU 才能承载，否则会迅速耗尽显存导致服务排队或拒绝请求。

## 长上下文与检索增强（RAG）的工程分工

行业内曾有一种说法：“长上下文足够大之后，RAG 就不再需要了”。这种看法混淆了“工作内存”与“外部持久存储”的分工。

![长上下文与检索增强在处理路径上的协同分工](/images/content-rebuild/3079c177e60405a7/fig-1.png)

* **检索增强（RAG）**：如同计算机的**硬盘检索与虚拟内存分页**。它通过向量检索、关键词匹配或知识图谱，从海量知识库中粗筛出数千 Token 的关键片段。它的优势在于单次推理计算量小、显存占用极低、并发吞吐高；短板在于当遇到需要跨越十几个章节、多模块联合推导的全局时序问题时，文本分块可能会切断因果链条。
* **长上下文（Long-Context）**：如同计算机的**物理工作内存（RAM）**。它将整篇文档的原生序列完整展开，允许模型通过注意力机制建立全局段落间的直接关联。它的优势在于能高质量处理代码重构、跨模块依赖分析与复杂篇章总结；短板在于单次推理成本高昂、并发能力脆弱。

### 算例对比：三种处理架构的开销与性能估算

假设我们仍针对上述包含 100,000 Token 的设计文档，承接 1,000 次独立用户提问。为了公平对比，我们假设每次生成的回答均为 200 Token，使用同一款支持长文本的开源模型（数据为相同硬件条件下的教学测算示意）：

| 架构策略 | 单次输入计算 Token | 1,000 次累计输入 Prefill 计算量 | 预估首字延迟（TTFT） | 显存与存储额外开销 | 跨章节复杂推理表现 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **无缓存直接全文输入** | 100,000 Token | 100,000,000 Token | 高（约 3.0~8.0 秒） | 无常驻显存，但并发时动态显存极高 | 高（保留完整全局链条） |
| **前缀缓存（Prefix Caching）** | ~200 Token（99,800 命中缓存） | 约 100,000（首击）+ 200,000 Token | 低（约 0.3~0.8 秒） | 需持续常驻 10 万 Token 的 KV 显存（约 12~13 GB） | 高（保留完整全局链条） |
| **片段切片检索（RAG）** | ~3,000 Token（检索 Top-K 片段） | 3,000,000 Token | 低（约 0.4~1.0 秒） | 需维护向量索引数据库（外部存储） | 中等（易受切片孤岛影响） |

算例说明：如果没有前缀缓存（Prefix Caching）技术的支持，直接全文输入会造成巨额的重复计算算力和不可接受的首字等待。更多上下文调度与缓存优化策略可阅读[上下文管理](/architecture/context-management.md)。

## 专题验收标准：三维评估基准

搭建一个长文本应用系统时，不能仅凭单次提问的输出感觉来判断好坏，建议围绕以下三个核心维度建立权衡与验收基准：

![长上下文系统落地的三维评估基准与验收指标](/images/content-rebuild/3079c177e60405a7/fig-3.png)

1. **精度与推理完整性（Accuracy）**：
   不仅测试单点事实提取率，还要构建跨章节多跳问答测试集。验证当关键信息分别位于 Prompt 的前 10%、中间 50% 与后 10% 位置时，模型的回答准确率与拒答率表现。关于评测体系设计，可参考[评测指标](/fundamentals/evaluation-metrics/README.md)。
2. **时延体验（Latency）**：
   以首字延迟（TTFT）与每秒输出 Token 数（TPS）为核心考核指标。针对交互式应用，TTFT 超过服务等级协议（SLA，例如 3 秒）的场景，必须介入前缀缓存预热或自适应路由降级为片段检索。
3. **吞吐与硬件成本（Throughput & Cost）**：
   量化系统在目标并发度下的 GPU 显存峰值（KV Cache 占用）和平均 Token 成本。对于长文本高频交互，必须明确界定何时依赖显存缓存常驻、何时采用离线结构化摘要降维。
