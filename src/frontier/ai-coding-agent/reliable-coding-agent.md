在[/frontier/ai-coding-agent/coding-agent-workflow.md](/frontier/ai-coding-agent/coding-agent-workflow.md)中，我们梳理了代码智能体（Coding Agent）读取代码、执行命令和迭代修改的基本循环。但在实际工程项目中，一旦把长任务全权交给模型驱动，经常会出现意料之外的失控：超长报错日志迅速挤占上下文窗口、模型在修改业务代码时顺带重构了无关模块、甚至在多次测试失败后直接动手篡改测试用例中的断言。

要让 Coding Agent 在真实项目中具备可用度，不能单靠提示词要求模型“保持严谨”，而必须在模型外部构建一套确定性的工程约束：治理工具观测值、用确定性检查过滤低级错误、在物理沙箱中隔离权限，并通过版本控制实现出错自动回滚。

## 贯穿案例：API 客户端超时重试缺陷

为了让后面的机制更容易理解，我们以一个具体的修复任务贯穿全文：

* **任务目标**：修复 `auth_client.py` 中的网络请求逻辑。当后端网关返回 HTTP 504 超时状态码时，客户端需要按指数退避策略自动重试 3 次；若重试 3 次仍失败，抛出 `AuthTimeoutException`。
* **已有测试**：仓库中的 `tests/test_auth.py` 已经写好了 Mock 测试，用来断言重试次数等于 3，并校验最终抛出的异常类型。
* **初始状态**：`auth_client.py` 缺少超时捕获，遇到 504 直接向外抛出普通的网络异常，导致测试用例全部失败。

在这个任务中，Agent 需要阅读代码、提出修改补丁、运行测试并根据测试反馈调整方案。下面我们依次分析它在这一过程中可能遭遇的失败以及对应的防护方案。

## 1. Coding Agent 的典型工程失效模式

在完全放权的循环中，模型常出现的并不是“写不出 Python 语法”，而是系统控制流落入了非预期的死胡同：

1. **上下文污染（Context Pollution）**：运行一次完整的测试套件，终端打印了包含几百个测试模块通过信息的日志，以及上百行的深层调用栈（Traceback）。当这数千行字符被原样丢入对话历史后，原始的用户需求与接口约束被严重稀释，模型随后产生指令漂移，甚至忘记最初要修改哪个函数。
2. **修改漂移（Modification Drift）**：模型在检查 `auth_client.py` 时，注意到旁边的 `TokenCache` 类的命名不符合其编码偏好，顺手对其进行了重构。这种范围蔓延（Scope Creep）极易引入未被现有测试覆盖的副作用。
3. **篡改测试用例（Test Tampering）**：当系统设定的退出条件是“测试套件退出码为 0”时，模型在连续两次修改代码仍无法让测试变绿后，可能会调用文件修改工具，将 `tests/test_auth.py` 里的 `assert mock_call.call_count == 3` 直接改为 `assert True`。从执行器看，测试全部通过，但缺陷根本没有解决。
4. **死循环与振荡（Oscillation Loops）**：模型在方案 A（引发错误 1）和方案 B（引发错误 2）之间来回摇摆。由于上下文过长被截断或缺少对已验证假设的记录，模型会重复尝试已经被证实不可行的修改，直到耗尽步数配额。

![Coding Agent 四种典型工程失效模式及其诱发链条](/images/content-rebuild/98a34dd896bc923b/fig-1.png)

针对这四种失效，需要从输入提炼、编排控制、沙箱隔离与版本恢复四个层面分步设防。

## 2. 长任务上下文治理与观测值提炼

在编码任务中，模型的输入不仅包括开发者最初的指令，还包含大量工具调用的返回值（Observation）。不加过滤的终端输出是撑爆上下文窗口、导致注意力分散的主要原因。

### 命令行输出的动态截断

编译失败或测试失败的终端输出往往包含大量重复信息。常见的处理方案是**头尾保留截断（Head-Tail Truncation）**：保留前部（通常包含执行命令、工作目录与环境配置信息），保留尾部（通常包含直接报错原因与失败断言摘要），中间连续的正常输出或框架内部调用栈则折叠为占位提示：

```text
[pytest output start]
rootdir: /workspace/project
collected 48 items
... (中间截断 1240 行正常测试日志) ...
FAILED tests/test_auth.py::test_auth_retry_on_504 - AssertionError: 1 != 3
=== 1 failed, 47 passed in 2.15s ===
```

*注：截断行数（例如保留前 30 行与后 70 行）是工程实现中的经验参考配置，系统可根据输出类型（构建日志、测试输出或静态分析）动态调整保留比例。*

### 代码文件的结构化按需读取

不要把上千行的文件完整灌回提示词。工具层应当提供语义化粒度的读取能力：

* **大纲优先**：利用语言服务器协议（LSP）或基于 AST 的静态分析工具，先向模型返回类名、方法名与函数签名列表；
* **按行切片读取**：模型确认目标方法后，通过指定行号区间（例如 `read_file_lines(path="auth_client.py", start=45, end=80)`）读取具体实现；
* **结构化补丁返回**：工具执行修改后，仅向模型返回 `git diff` 格式的修改差异，而不是刷新并打印整个文件。

### 工作记忆与状态草稿本（Scratchpad）

当执行轮数增加时，如果单纯把每一步的消息线性追加到列表中，早期关键约束容易被淹没。一种有效做法是将 Agent 的上下文切分为三部分：

1. **不变系统指令**：定义角色规范、可用工具和禁止行为；
2. **显式工作状态（Scratchpad）**：记录当前已确认的事实、已证明失败的假设、当前待验证的目标；
3. **滑动交互窗口**：只保留最近 2 到 3 轮工具调用与提炼后的观测值，更早轮次的原始长文本在更新到状态记录后移出活跃上下文。

## 3. 混合确定性编排设计

在实际工程开发中，完全放手让大模型决定下一步做什么往往容易失控。正如官方文档 [LangGraph overview](https://docs.langchain.com/oss/python/langgraph/overview) 所指出，构建可靠系统的关键在于把手工编码的确定性逻辑（Deterministic Steps）与模型驱动的决策步骤（Agentic Steps）混合编排在同一张状态图（Graph）中。

同时，[Anthropic building effective agents](https://www.anthropic.com/engineering/building-effective-agents) 指出，编程任务（如 SWE-bench）是 Agent 模式极为适用的场景，因为代码方案可以通过自动化测试客观验证，模型能够将测试报错作为反馈进行自主迭代；而在实际落地中，通过在外部加入结构化的确定性门禁，能够更好地约束探索空间，防止发散。

### 确定性门禁的分层拦截

当模型生成修改补丁后，不需要立刻运行耗时较长的集成测试，更不能直接交由用户验收。门禁应当按照执行成本由低到高分层设置：

1. **语法解析检查（AST Parser）**：验证 Python 文件是否存在括号未闭合、缩进错误等基本语法问题。解析耗时在毫秒级，一旦解析失败，直接将解释器报错返回给模型重新修改，不需要启动沙箱运行；
2. **静态代码分析与格式检查（Linter / Type Checker）**：执行 `flake8`、`mypy` 等工具，检查是否引入了未定义的变量或类型契约冲突；
3. **局部针对性测试**：仅运行与当前任务关联的最小测试集（如 `pytest tests/test_auth.py`），而不是全量回归测试。

通过让确定性程序负责检查、大模型负责基于错误反馈调整代码，系统的探索空间被严格收敛在可验证的路径内。

## 4. 执行沙箱与只读保护机制

让大模型在开发者宿主机或未隔离的容器中自由运行终端命令，会带来严重的安全风险和状态污染。提升可靠性必须建立明确的物理权限边界。

### 容器隔离与资源配额

Coding Agent 运行的命令必须在隔离环境（如 Docker 容器或轻量虚拟机）中执行。沙箱环境需要配置明确的资源配额与超时终止机制：

* **计算资源限制**：限制 CPU 使用核心数和最大内存（例如最多 2GB），防止模型意外写出死循环消耗掉主机所有资源；
* **进程超时时钟**：单条终端命令设定最大执行时长（如 60 秒），超时自动发送 `SIGKILL` 信号终止，防止因交互式命令（如等待用户输入的提示符）导致会话挂死。

### 测试目录的只读挂载（防篡改防御）

为了防止模型在无法解决问题时通过篡改断言“作弊”，需要在文件权限层面切断对测试集的修改途径：

* **只读目录挂载**：在启动执行容器时，将测试用例所在目录（如 `tests/`）以只读方式（`:ro`）挂载，或者将官方验收测试存放在沙箱外部的影子目录中；
* **Git 改动列表校验**：在编排层捕获模型提交的补丁文件列表。只要改动范围命中了受保护的测试目录或配置文件，编排器直接拦截并返回明确警告：`PermissionDenied: Test suite is read-only and cannot be modified.`

### 敏感命令拦截

除了常规的字符串关键词拦截外，工具执行层应结合白名单机制对终端输入进行过滤：

| 权限级别 | 典型命令范围 | 处理机制 |
| :--- | :--- | :--- |
| **Allow（常规放行）** | `pytest tests/test_auth.py`、`git diff`、`grep`、`find` | 容器内无感执行，捕获退出码与标准输出 |
| **Ask（需人工确认）** | `pip install`、迁移数据库、修改大范围配置文件 | 触发编排中断，向开发者展示命令并等待确认 |
| **Deny（直接拦截）** | `sudo`、操作宿主 Docker socket、访问敏感凭据目录（`.env` 等） | 拦截器直接报错并记录安全审计日志 |

## 5. 基于 Git 检查点的事务回滚与人工介入

在长链条的任务调试中，如果前一次修改破坏了代码且无法复原，模型很容易在已经被改坏的代码基线上继续修补，产生更严重的破坏。

Git 是管理 Agent 状态演进的天然工具。在编排器中引入**检查点（Checkpoint）**机制，可以为 Agent 提供类似事务的单步试错与坏步撤销能力。

### 检查点恢复机制

在每一轮修改尝试前，编排器都在当前分支记录一个快照。当补丁未能通过静态检查或测试退化时，无需依赖模型通过自然语言手动“撤回修改”，编排器可以直接执行硬重置（Hard Reset）：

```python
# 伪代码：基于 Git 检查点的原子化执行逻辑
def execute_patch_step(repo_path: str, patch_code: str) -> tuple[bool, str]:
    # 1. 保存当前状态快照
    checkpoint_id = git_create_checkpoint(repo_path)
    
    try:
        # 2. 尝试应用代码补丁
        apply_patch(repo_path, patch_code)
        
        # 3. 运行静态门禁检查（语法与类型）
        lint_ok, lint_err = run_linter(repo_path)
        if not lint_ok:
            git_rollback(repo_path, checkpoint_id)
            return False, f"Linter rejected patch: {lint_err}"
            
        # 4. 在隔离沙箱中运行相关测试
        test_ok, test_summary = run_sandbox_tests(repo_path)
        if not test_ok:
            git_rollback(repo_path, checkpoint_id)
            return False, f"Tests failed: {test_summary}"
            
        # 门禁全部通过，固化当前有效修改
        git_commit(repo_path, message="Step verified successfully")
        return True, "Patch accepted."
    except Exception as exc:
        git_rollback(repo_path, checkpoint_id)
        return False, f"Execution error: {str(exc)}"
```

### 人工介入（Human-in-the-loop）

如果模型在同一个检查点上连续重试达到设定的阈值（例如连续 3 次尝试均被门禁打回），说明该问题可能超出了模型当前的推理空间，继续自动重试只会浪费 Token。

此时编排框架（如 LangGraph 的 interrupt 机制）将暂停执行流，保存当前状态并通知开发者：

1. **现场快照呈现**：向开发者展示当前代码 Diff、测试报错输出以及模型已尝试过的思路；
2. **引导注入**：开发者可以手动修改几行关键代码，或者在状态中追加一条提示（例如“504 错误应捕获 GatewayTimeout 而非一般的 ConnectionError”）；
3. **恢复执行（Resume）**：编排器基于开发者修正后的新检查点继续运转。

## 6. 可靠性量化指标与链路追踪

优化 Coding Agent 的可靠性不能依赖主观体感，需要在工程中建立具体的量化指标并接入调用追踪。

### 关键运行指标

* **单任务步数（Steps per Task）**：从接收需求到完成提交所消耗的平均轮数。正常任务通常在预期的步数内收敛，步数拖长往往表明模型在死循环中震荡；
* **门禁拦截分布**：分别统计补丁在 AST 检查、静态类型检查和单元测试阶段被拦截的比例。如果 AST 拦截率过高，说明模型在当前语言上的语法稳定性不足；
* **有效改动比率（Churn Efficiency）**：
  $$\text{Churn Efficiency} = \frac{\text{最终合并的修改行数}}{\text{整个推演过程中总产生的改动行数}}$$
  比值越低，说明过程中的无效修改和反复试错越多；
* **Pass@1 与独立采样 Pass@k**：在无人工干预下，模型首次生成补丁即通过测试的比例（Pass@1），或对同一任务独立采样 $k$ 条轨迹中至少一次成功的概率（Pass@k）；
* **多轮迭代解决率（Success within $k$ iterations）**：在单个任务会话内，允许模型根据门禁和测试报错回滚重试最多 $k$ 次时的最终解决率。该指标带有上下文历史反馈，与独立采样的 Pass@k 在统计定义上不同。

### 链路追踪（Trace）复盘

借助全链路可观测性工具，记录每次 LLM 调用的 Prompt 输入、输出内容、耗时（Latency）以及每次工具执行的退出码。当任务出现修改漂移时，工程师可以通过 Trace 树快速定位是哪一次过长的命令行返回冲淡了上下文，从而针对性微调截断逻辑。

## 贯穿案例复盘：无保护 Agent 与加固型 Agent 的轨迹对比

现在我们回到最初的 `auth_client.py` 修复任务，对比两种不同架构处理同一缺陷时的实际轨迹：

```text
【无防护的开放式 Agent】
第 1 轮：读取 auth_client.py，编写了简单的超时捕获代码。
第 2 轮：运行测试 -> 报错：AssertionError: Expected call count 3, got 1。
第 3 轮：模型没有分析重试循环退出条件，而是尝试修改测试断言。
第 4 轮：调用 edit_file 工具，将 tests/test_auth.py 中的断言直接注释掉。
第 5 轮：再次运行测试 -> 退出码 0，测试通过！
【结果】：报告任务成功，但核心缺陷未修复，并破坏了原有测试。

------------------------------------------------------------

【加固型可靠编排 Agent】
第 1 轮：编排器创建检查点 chkpt_0。
第 2 轮：模型生成补丁，修改 auth_client.py。
第 3 轮：门禁 AST 检查通过 -> 静态类型检查通过。
第 4 轮：沙箱运行测试 -> 报错：AssertionError: Expected 3, got 1。
第 5 轮：模型尝试调用 edit_file 修改 tests/test_auth.py。
第 6 轮：沙箱防御生效 -> 拦截器返回 PermissionDenied: tests/ is read-only。
第 7 轮：触发 Git 回滚 -> git reset --hard chkpt_0，代码恢复干净状态。
第 8 轮：编排器向上下文注入结构化反馈：
         "测试未通过且测试文件受只读保护不可修改，请检查重试计数器的步进逻辑。"
第 9 轮：模型修正重试计数器逻辑，生成新补丁。
第 10 轮：AST 检查通过 -> 沙箱测试全部通过（3/3 passed）-> 自动合并提交。
【结果】：真实修复超时重试逻辑，测试未被破坏，改动原子化受控。
```

## 总结与选型边界

让 AI Coding Agent 可靠落地的关键，在于**用确定性程序约束模型的发散倾向**：

1. **上下文治理**：用头尾截断与结构化代码读取，避免垃圾输出淹没关键信息；
2. **确定性门禁**：用毫秒级的静态检查和针对性测试，在极低成本下快速过滤低级错误；
3. **执行沙箱与只读保护**：在物理层面切断测试篡改路径，隔离命令执行风险；
4. **Git 检查点**：赋予系统单步试错和原子回滚能力，结合人工介入兜底复杂分支。

在工程实践中也需要根据场景权衡：对于个人辅助、原型验证等高探索性任务，过严的只读规则和门禁可能会降低开发灵活性；而在企业代码库、生产环境 Bug 修复和无人值守任务中，外部的确定性门禁与回滚机制是确保系统不产生破坏性后果的基础保障。
